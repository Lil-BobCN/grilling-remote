# 工作状态同步：orca → 中台

状态：accepted（2026-11-12）
来源：[工作状态同步：orca → 中台](https://github.com/Lil-BobCN/grilling-remote/issues/152)
背景：地图 #139、ADR 0002、ADR 0003、ADR 0005、`中台/设计.md`、Orca 1.4.257

## 问题

中台是决策看板，orca 是执行现场。中台要显示每张票的工作状态，得定清楚六件事：状态有哪些值、各自什么条件触发、票和 worktree 怎么映射、多久拉一次、失败怎么显示、状态存在哪。

## 术语

- **工作状态**：票现在做到哪了，四个值：`未领取`、`进行中`、`等待人`、`被挡`。由执行侧同步到中台，不靠会话链接。
- **离线**：orca 连不上时的全局连接状态，不是票级工作状态。
- **工作状态快照**：`workstate.json`，存每张票的当前状态和同步时间。
- **worktree**：Orca 管理的一次仓库检出，带分支、终端和 agent。

## 决定

### 状态值

1. 票级工作状态四个：`未领取`、`进行中`、`等待人`、`被挡`。
2. `离线` 是全局连接状态。orca 不可达时屏幕顶部出一条提示，票卡保留最后一次状态和时间戳。
3. `已完成` 是票自身的 open/closed 状态，不放进工作状态。票关闭后工作状态停止更新，屏幕按票状态显示已完成。
4. `workspaceStatus` 是 Orca 的手工卡片状态，默认 `todo`、`in-progress`、`in-review`、`completed`。它不随 agent 活动变化，不参与工作状态判定。

### 触发条件

| 状态 | 条件 |
| --- | --- |
| 未领取 | 没有匹配到这张票的 worktree |
| 进行中 | 至少一个关联 worktree 的 `status` 是 `working` |
| 等待人 | `status` 是 `permission` 或 `done`；或所有 agent 的 `state` 是 `done`、`blocked`、`waiting`；或 `status` 是 `inactive`，或 `active` 但没有在跑的 agent |
| 被挡 | 中台票有未关闭的阻塞项，优先于上面三个 |

- `status` 的取值是 `active`、`working`、`permission`、`done`、`inactive`。
- `agents[].state` 的取值是 `working`、`blocked`、`waiting`、`done`。`waiting` 和 `blocked` 表示 agent 在等人处理。
- agent 结束后 `status` 不会变成 `done`。一个 worktree 只剩 `done` 的 agent 时，`status` 仍是 `active`。只看 `status` 会漏掉「等待人」。
- `inactive` 表示 worktree 还在，但没有活终端。归入 `等待人`，因为需要人重新打开或继续。
- `被挡` 由中台按票的 `blocked_by` 算，orca 不提供。被挡和进行中同时出现时，被挡优先；详情里注明「该票有 worktree 在跑」。

### 票和 worktree 的映射

1. 主键是 `(GitHub 仓库, 票号)`。中台启动时读一次 `orca repo list --json`，把 `repoId` 映射到 `gitRemoteIdentity.canonicalKey`，例如 `github.com/Lil-BobCN/grilling-remote`。
2. 一个 worktree 先看 `linkedIssue`。`linkedIssue` 是数字，仓库由 `repoId` 补。
3. 没有 `linkedIssue` 时，用分支名匹配 `issue-(\d+)`。分支命名固定为以 `issue-<票号>` 结尾，例如 `Lil-BobCN/issue-152`。
4. `displayName` 不参与匹配。
5. 一个 worktree 的 `linkedItems` 可能有多条。只有 `linkedIssue` 那张票拿工作状态，其他 issue 和 PR 只算引用。
6. 一张票有多个 worktree 时，按 `permission > working > done > active > inactive` 合并。任一 worktree 需要人，就显示等待人；没有需要人的，任一在跑就显示进行中。
7. 归档的 worktree 不参与匹配。

### 拉取节奏和失败处理

1. 每 2 秒跑一次 `orca worktree ps --json`。单次超时 1.5 秒。
2. 连续 2 次失败或超时，判 `离线`。恢复后立刻再拉一次。
3. `truncated: true` 时加大 `--limit` 重拉，直到拿到全部 worktree。
4. 离线不写业务事件。屏幕顶部显示全局提示，票卡保留最后一次状态和时间戳。
5. 只读 orca，不允许手工改工作状态。手工覆盖会和下一次轮询打架。

### 存哪

1. 工作状态不写业务事件，不进状态哈希。它是外部派生状态，折叠它会让业务状态依赖 orca 是否开着。
2. 单独写 `workstate.json` 快照：每张票的当前状态、进入这个状态的时间、最后一次成功同步时间、离线标记。
3. 不写逐次变化日志。要看「卡了多久」，用 `stateStartedAt` 和 `lastActivityAt`。

## 考虑过的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 用 `workspaceStatus` 当工作状态 | 它是手工卡片状态，不随 agent 活动变化 |
| 只看 worktree 的 `status` | `done` agent 不会抬高 `status`，会漏掉「等待人」 |
| 把离线做成票级状态 | 离线是连接问题，会把所有票搅成同一个值 |
| 把已完成放进工作状态 | 和票的 open/closed 重复，两处可能打架 |
| 每张票单独轮询 orca | 一次 `worktree ps` 就能拿到全部 worktree，按票轮询浪费 |
| 状态变化写业务事件 | 工作状态是外部派生状态，事件日志会依赖 orca 的可用性 |
| 手工改工作状态 | 人和 orca 的优先级没有定义，v1 不做 |

## 后果

- 工作状态只在中台显示，不上 GitHub（ADR 0005）。
- orca 关掉时，屏幕显示离线，票卡停在最后一次状态。
- 工作状态不参与状态哈希，重建时不需要 orca。
- 一张票的领取由 worktree 表示。没有 worktree 就是未领取，GitHub 的 assignee 不参与。
- 分支命名成为映射的一部分。不按 `issue-<N>` 命名时，必须用 `orca worktree create --issue <N>` 显式挂票。
