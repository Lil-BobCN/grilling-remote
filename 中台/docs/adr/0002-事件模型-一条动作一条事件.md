# 事件模型：一条动作一条事件

状态：accepted（2026-11-10）
来源：[事件模型：op、payload、折叠与哈希](https://github.com/Lil-BobCN/grilling-remote/issues/141)
背景：`中台/设计.md`

2026-11-10 扩到 v2：payload 加字段，新增 `decision.void` 和 `premise.edit`。见 `0003-图票与评论模型.md`、`0004-前提模型-状态判定与命令.md`。v1 事件仍按本文折叠。2026-11-12：导入与同步的规则见 `0005-导入与同步.md`，`import` 事件的 payload 和 `sync.jsonl` 的用法以那份为准。

中台的状态全部由 `events.jsonl` 折叠出来。一行一条事件，只追加。服务是唯一写者，写事件时分配 `seq`。折叠按 `seq` 升序处理；`seq` 必须从 1 连续递增，重复、跳号、文件顺序不一致都拒绝启动。事件带 `v`，只接受认识的版本；op 不认识、payload 缺字段或多字段也拒绝启动，报行号和字段名。

## 决定

### 事件行

一行一个 JSON 对象，字段固定：

`v`、`seq`、`ts`、`actor`、`op`、`target`、`payload`、`reason`

`target` 指事件的主角。创建事件指向新对象，编辑和判定指向被改的对象，`overturn` 指向被取代的旧决定。`reason` 可空。

### 一次操作一条事件

创建一张票时，标题、正文、标签、父票、状态写在同一条 `issue.create` 里。之后每次修改各写一条事件。评论单独写 `comment.create`，不和票的创建混在一起。

`import` 也是一条事件，payload 装下源的全部内容：地图、票、评论、决定、前提、覆盖表。实验用地图 #117 的真实数据，一条 57,814 字节，解析和折叠哈希通过。

### op 清单

| op | target | payload |
| --- | --- | --- |
| `import` | 源，如 `github:117` | `map`、`tickets`、`decisions`、`premises`、`coverage` |
| `issue.create` | 新票 id | `title`、`body`、`labels`、`parent`、`state` |
| `issue.edit` | 票 id | `title`、`body`，至少一个 |
| `issue.state` | 票 id | `state` |
| `issue.label` | 票 id | `add[]`、`remove[]` |
| `issue.parent` | 票 id | `parent` |
| `issue.block` | 票 id | `add[]`、`remove[]` |
| `comment.create` | 新评论 id | `issue`、`body` |
| `comment.edit` | 评论 id | `body` |
| `comment.delete` | 评论 id | 空对象 |
| `decision.create` | 新决定 id | `statement`、`group`、`source_ticket`、`output_files` |
| `decision.overturn` | 旧决定 id | `new_decision` |
| `premise.add` | 新前提 id | `decision`、`statement`、`evidence` |
| `premise.judge` | 前提 id | `verdict`、`evidence` |

op 用点号分词，写成 `<实体>.<动作>`。决定不直接改，没有 `decision.edit`；改就是新建决定再 `decision.overturn`。

### 状态哈希

只哈希折叠后的业务状态，不哈希事件文件本身。对象键按字典序排，数组按实体 id 排，数字只允许整数，时间用字符串。包含事件带来的时间，不包含 `seq`、壁钟时间、`board.db` 行号或索引字段。序列化后加 `v1\n` 前缀，再算 SHA-256。

### actor

写请求必须带 `actor`，格式 `human:<名字>` 或 `agent:<名字>`。CLI 从 `--actor` 或 `GRILLING_ACTOR` 取；没给时，有终端记 `human:<系统用户名>`，没有终端记 `agent:unknown`。屏幕固定发 `human:<运营者>`。服务原样记录，不校验真假。

### 编号

服务分配本地号：新票 `I-`、评论 `C-`、决定 `D-`、前提 `P-`。`import` 保留来源编号，含 `D-0001a`、`D-0002e` 这类后缀。同步到 GitHub 后拿到的编号存进同步映射，本地号不变；最终对齐 GitHub 编号。

### 同步状态

同步成功、失败和 GitHub 编号映射单独记进 `sync.jsonl`，不进业务事件，不进状态哈希。屏幕读两份日志。

## 考虑过的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 一次操作拆成多条事件 | 写到一半失败会留下半套数据 |
| 跳过不认识的 op | 状态会悄悄少一块，哈希看起来正常 |
| 把同步状态写进业务事件 | 同步失败会改变状态哈希，重建比对被运维噪音干扰 |
| 用 GitHub 编号当唯一编号 | 新建票在同步前没有 GitHub 号，离线创建做不了；本地号更稳定 |
| 允许直接改决定 | 决定失去只写一次的审计记录；改就用新决定取代旧决定 |

## 后果

- 一条事件可能很大（全量导入约 57KB），JSONL 能装下，但读取时要按行处理。
- 状态哈希只反映业务状态；同步状态要看 `sync.jsonl`。
- 本地号和 GitHub 号是两套编号，中间靠映射表连起来。
- 新增 op 要升 `v`，旧事件仍按旧版本折叠。
