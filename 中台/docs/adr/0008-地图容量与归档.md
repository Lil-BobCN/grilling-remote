# 地图容量与归档

状态：accepted（2026-11-16）
来源：[地图 1 拆分：53 张导入老票迁到归档地图](https://github.com/Lil-BobCN/grilling-remote/issues/376)
背景：地图 1 的 GitHub 父票 #1 已挂满 100 个子票，I-0131 挂不进去。GitHub 规定一个父票最多 100 个子票，已关闭的也算；一张票只能有一个父票。中台 v1 之前禁止改父票，同步只会加父子关系，不会摘。

## 问题

地图会越做越大，GitHub 的 100 个子票上限会再次挡住同步。要定四件事：什么时候归档、归档哪些票、归档图开不开镜像、票怎么换图。

## 术语

- **地图容量**：一张地图能挂多少张票。GitHub 父票最多 100 个子票，中台按票数算。
- **归档地图**：只放历史票的地图，不再新增工作。它有自己的根决定和拆句。

## 决定

1. 地图票数到 80 张就开始计划归档，不等满 100。
2. 只归档已关闭的历史票。open 票和现行工作还依赖的最近关闭票留在原图。
3. 归档地图复制原图的根决定拆句。移动票时，一次 `issue.parent` 事件同时写新父票和 `covers`，`covers` 指向归档图的拆句。
4. 归档地图可以开镜像，也可以关。开镜像时它是一张普通地图，同样受 100 张限制；关镜像时票只在中台，不占 GitHub 子票位。
5. 同步认识两种父子变化。`parent.add` 用 `gh issue edit <子票> --parent <新父票>`，会替换旧父票；`parent.remove` 用 `gh issue edit <父票> --remove-sub-issue <子票>`。计划里出现远端还挂着、中台已经移走的票，就排一条摘除。
6. 第一次同步新地图时，先读已有 GitHub 号的票，不把已有评论当新评论重发。
7. 同步到 100 张时不再反复失败。计划里记 `parent.skip`，给一条容量警告，票照常镜像。

## 考虑过的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 冻结地图 1，以后新票都开新图 | 不迁移最省事，但地图 1 的 100 个位永远满着；open 票要跟进的新票也只能挂到别的图。 |
| 按 Destination 四句拆成四张图 | 一张票经常同时覆盖两三句，`covers` 要硬塞进一张图，流程被切碎。 |
| 归档全部已关闭票 | 移动量大，最近关闭票产出的决定会离开现行地图；现行工作依赖的决定虽然能靠 `derived_from` 带回来，地图视图会瘦得太多。 |
| 归档地图不开镜像 | GitHub 上只剩散落的 closed issue，父子历史看不成一张图。这次选了开镜像。 |
| 直接改 events 或手改 GitHub | 中台是唯一写者，手改会被下一次同步覆盖。 |

## 后果

- 地图 1 的 53 张导入老票迁到归档地图 I-0132，地图 1 剩 48 张现行票，另加一张拆分票 I-0133。
- 归档地图开镜像，GitHub 父票是 #375，占 53 个子票位。
- 票换图后，`covers` 跟着换；`derived_from`、评论、决定、编号不变。
- 地图的票数到 80 张时，运营者要安排一次归档。归档地图自己也会满，满了再开下一张。
