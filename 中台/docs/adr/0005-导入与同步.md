# 导入与同步：中台主记录，GitHub 镜像

状态：accepted（2026-11-12）
来源：[导入与同步：中台主记录，GitHub 镜像](https://github.com/Lil-BobCN/grilling-remote/issues/143)
背景：地图 #139、ADR 0001、ADR 0002、ADR 0003、ADR 0004、`中台/设计.md`

## 问题

中台接管主记录。已有的 GitHub 地图要进来一次；之后所有编辑在中台做，GitHub 只在运营者要求时接收镜像。要定四件事：导入读什么、根决定怎么建、缺的因果怎么显示、同步怎么写和怎么失败。

## 术语

- **导入**：从 GitHub 读一张地图和它的票、评论、决定，写进中台。一张地图只做一次，不改 GitHub。
- **同步**：把中台的当前状态写到 GitHub 镜像。运营者按地图触发，平台执行。
- **镜像开关**：每张地图上的开关，决定这张图是否同步到 GitHub。
- **生成段**：同步时写进 GitHub 地图正文的一段 Markdown，由中台按当前状态生成，带标记，整段替换。

## 决定

### 方向

1. 导入只从 GitHub 到中台，一张地图一次。导入读 GitHub 的 issue、评论、标签、状态；`docs/decisions.md` 和归档只做验收比对，不参与导入。
2. 导入后，所有编辑在中台。Agent 不直接改 GitHub；只有同步引擎写 GitHub。
3. 同步只从中台到 GitHub，由运营者按地图触发。先出计划，确认后执行。

### 导入

- 一张地图一条 `import` 事件，payload 装快照：地图、根决定、票、评论、决定、覆盖、标签、父子。导入只读，不写 GitHub。导入后给已有 issue 和评论写身份映射。
- 根决定编号统一为 `D-<地图号>-ROOT`，如 `D-117-ROOT`、`D-139-ROOT`。主句照抄原文：有 `**主句：**` 用那一句，没有用第一句。拆句用旧覆盖表的「原文片段」列；没有覆盖表才按 `。！？` 切。旧稿 `<details>` 留在正文，不当现行。
- 票的标题、正文、类型、标签、状态、时间、父票全导。父票从正文 `Part of #N` 读。旧图没有原生 sub-issue；第一次同步时补上，正文的 `Part of #N` 保留。
- 评论全导，四列表原样保留。本地 `C-` 号对 GitHub 评论 id。
- 决定从四列表重建。`source_ticket` 取评论所在票，`supersedes` 取「取代」列，`output_files` 取「产出文件」列，`created_at` 取评论时间。31 行全导，含 D-0002b；D-0002b 的状态是 superseded。
- 覆盖 24 行映射到根决定拆句和票的 `covers`。状态按票重算，不用旧状态列。
- 拆票理由留空，屏幕显示「未记录」。票与票、决定与决定的派生不补。旧票从会话记录提取因果是以后的功能，先留在未定项。
- 正文保留 Notes、Not yet specified、Out of scope 和其他散文。旧的 Destination 覆盖表和 Decisions so far 删掉，由生成段重算。
- 重复导入默认拒绝。导入后的编辑都在中台，GitHub 是镜像，不需要第二次导入。

### 镜像开关

- 每张地图一个镜像开关。导入的图默认开，新建的图默认关。
- 关掉时，这张图和下面的票、评论不同步。中台照常读写。
- 打开时，从上次同步的位置补推；关闭期间的改动也算未同步。

### 同步

- 运营者按地图点同步。先出计划：新建、更新、关闭哪些 issue，哪些评论，地图正文哪几段会改写。确认后执行。
- 执行顺序：先建票，再挂标签、父子、阻塞，最后发评论和改写生成段。独立项失败不拖住其他项，依赖项停下。逐项报结果，失败的可以重试。
- 中台为准。GitHub 上的直接修改，下一次同步整段覆盖。`dt sync --check` 只读比对，报出差异。
- issue 只关不删。评论删除走 GitHub 删除，重复删除算成功。
- 离线新建的票先发 `I-` 号，同步后写映射。评论等所属票建好再发。正文里的 `I-` 号不翻译成 GitHub 号。
- 失败写 `sync.jsonl`，屏幕标「同步异常」，可手动重试。`sync.jsonl` 还存 issue 和评论的编号映射、每张地图的同步位置。
- 跨图阻塞：两端都在镜像里的图才写 blocked-by。一端仅在中台时，计划里报「无法镜像」，中台的边保留。

### 生成段

- 同步时在地图正文写一段带标记的 Markdown：Destination、覆盖表、决定清单（陈述、状态、来源票、前提及状态）、票因果表（票、拆票理由、从哪条决定拆出、产出哪条决定、覆盖句）。
- 票的正文和评论照原样镜像，不放进生成段。工作状态和影响清单不上 GitHub。
- 生成段到约 60KB 时截断表格，保留前 N 行，末尾写「完整内容在中台」并附本地地址。同步照常成功。
- 生成段只读。GitHub 上的直接修改会被下一次同步覆盖。

## 考虑过的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 每条决定发一条评论 | 旧图要补 31 条新评论，和「导入只读」冲突，旧四列表和新评论重复 |
| 决定和前提不上 GitHub | GitHub 只剩旧四列表，看不到当前决定和前提，不是完整镜像 |
| 每次写事件自动同步 | 运营者要看完中台再决定推不推；自动推没有确认点 |
| 全局同步 | 一次混进多张图，出问题难定位；按地图更清楚 |
| 同步时把 `I-` 号翻成 GitHub 号 | 中台和 GitHub 两份正文，比对和幂等都要多一层翻译 |
| 生成段超限就拆成评论 | 多一条评论和一套更新逻辑，v1 不值得 |
| 重复导入覆盖 | 会冲掉中台后来写的拆票理由、前提和编辑 |

## 后果

- GitHub 上的地图正文是渲染结果，不是中台正文。直接改 GitHub 会在下一次同步被覆盖。
- 旧图导入后，票都挂在根决定下，拆票理由显示「未记录」。树的下半截是空的，这是旧数据的真实状态。
- 生成段随决定和票增长，65KB 是硬上限。超过 60KB 开始截断。
- 同步引擎是唯一写 GitHub 的一方。Agent 只读中台、只写中台。
- 旧脚本 `scripts/decisions`、`docs/decisions.md`、`check` 继续冻结。地图 `Decisions so far` 手工维护。
