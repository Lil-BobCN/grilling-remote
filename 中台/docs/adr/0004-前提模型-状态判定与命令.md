# 前提模型：状态、判定与命令

状态：accepted（2026-11-10）
来源：[前提模型：状态、判定与命令](https://github.com/Lil-BobCN/grilling-remote/issues/142)
背景：地图 #139、ADR 0002、ADR 0003、`中台/设计.md`

## 问题

一条决定成立依赖什么，要能记下来、能判、判破能触发影响范围。这份 ADR 定前提的字段、状态、判定词、编辑规则和命令形状。影响范围怎么算归《影响清单模型》，屏幕怎么画归《屏幕原型》，这里都不定。

## 实体

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `P-0001` | 服务分配，不复用 |
| `decision` | 决定 id | 所属决定，必填 |
| `statement` | 字符串 | 一句可被证伪的话 |
| `state` | `未验` / `成立` / `已破` / `未知` | 折叠出来，等于最近一次判定；没判过是 `未验` |
| `evidence` | 字符串数组 | 引用，不是全文 |
| `created_at` / `created_by` | | 创建时间和作者 |
| `last_judged_at` / `last_judged_by` | | 最近一次判定的时间和作者，没判过为空 |

一条决定可以挂多条前提。一条前提只属于一条决定；两条决定依赖同一件事，各写一条。

`last_judged_at` / `last_judged_by` 从最近一条 `premise.judge` 折叠，不单独存。

## 状态和判定

状态四个：

| 状态 | 含义 |
| --- | --- |
| `未验` | 新建，还没判过 |
| `成立` | 判过，认为现在成立 |
| `已破` | 判过，认为不成立，决定要重判 |
| `未知` | 判过，但按现在的证据判断不了 |

判定词三个：`成立`、`已破`、`未知`。每判一次写一条 `premise.judge`，状态立刻变成判定词。

`未知` 和 `未验` 不一样：`未验` 是从没判过，`未知` 是判过但判不了。有证据后可以再判，后一次判定覆盖前一次。

决定被推翻后的四档处理（仍成立、需修改、作废、要补问）不在这里用。那四档归《影响清单模型》，是处理决定用的词，不是前提的状态。

## 谁写、能不能改

前提由 agent 写、人审阅，也可以人直接写。谁写的由事件的 `actor` 字段记，不另设字段。

`premise.add` 之后、第一次 `premise.judge` 之前，可以改 `statement` 和 `evidence`，写 `premise.edit`。判过以后陈述锁住，不能再改。要换说法就新建一条前提，旧前提留在决定上，作为当时判定的记录。

新建的前提不会让旧前提失效。决定仍按旧前提已破算，直到有人重判决定。

锁住的是陈述的写法，不是结论。判过的前提可以再判，状态跟着最近一次判定走。

`premise.edit` 不能改 `decision`。要换所属决定，新建一条前提。

## 证据

`evidence` 存引用，不抄全文。可写四种：

| 写法 | 例 |
| --- | --- |
| 票号 | `#142` |
| 相对路径 | `中台/设计.md` |
| 链接 | `https://example.com/...` |
| 原话 | `原话：planner 只读当前仓库的 issue（来自 #139 评论）` |

原话要带来源，单独一句原话不算证据。判定时可以补新证据，新证据追加，不覆盖旧证据。

## 判破之后

`premise.judge` 写入 `verdict: 已破`，状态立刻变 `已破`，并向影响范围的计算方发一个触发。系统只列名单，不自动改决定。

触发怎么消费、范围怎么算，归《影响清单模型：范围、处理动作与生命周期》。屏幕上的视觉信号和提醒条归《屏幕原型：决策图、影响清单与视觉信号》。

## 事件模型

v2 的第 16 个 op 是 `premise.edit`。ADR 0003 的 v2 有 15 个。2026-11-13 升 v4，新增 `premise.annotate`：只改上次判定理由，不动状态和证据。

| op | target | payload |
| --- | --- | --- |
| `premise.add` | 新前提 id | `decision`、`statement`、`evidence` |
| `premise.edit` | 前提 id | `statement`、`evidence`，至少一个 |
| `premise.judge` | 前提 id | `verdict`、`evidence` |
| `premise.annotate` | 前提 id | 空对象；新判定理由走事件外层 `reason` |

`reason` 走事件外层字段，不进 payload。判定必须带理由；`premise.annotate` 也要带，并写进同一个外层字段。

服务收到 `premise.edit` 时检查：这条前提没判过。判过的拒绝，报错让调用方新建前提。

## 命令

命令名和参数细节由《实现内核：事件日志、CLI、导入与同步》定。形状：

```
premise add --decision D-0009 --statement "..." --evidence "#142" --evidence "中台/设计.md"
premise judge P-0009 成立|已破|未知 --evidence "..." --reason "..."
premise edit P-0009 --statement "..." --evidence "..."
```

一次命令只写一条事件。

## 考虑过的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 一条前提挂多条决定 | 判一次要通知多个决定，谁负责判也说不清；两条决定各写一条，代价小 |
| 判过还能改陈述 | 判定和当时的句子对不上，三个月后说不清判的是什么 |
| 判破自动改决定 | 自动改会让人漏掉决定；系统只列名单，人判 |
| 证据抄全文 | 源头改了以后两份说法打架；引用能追回去 |
| 前提状态和决定四档共用一套词 | 两个对象、两种动作，共用词会让屏幕和事件都分不清 |

## 后果

- 事件模型从 15 个 op 变 16 个。ADR 0002 加一条指针。
- 判破会立刻改变前提状态，影响范围的计算要能接住这个事件。
- 屏幕多一个破前提信号；决定颜色要读它挂的前提状态。
- 前提不来自票、决定或文件，来自流程外面的世界。证据字段只记它从哪抄来的。
