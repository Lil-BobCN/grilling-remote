# 设计：决策中台（Decision Board）

日期：2026-11-10
状态：初稿。2026-11-10 起由地图 #139（中台 v1：本机 issue 主记录，GitHub 做镜像）逐票裁定；票上的决定优先于本文。事件模型见 `中台/docs/adr/0002-事件模型-一条动作一条事件.md`。图、票与评论模型见 `中台/docs/adr/0003-图票与评论模型.md`；本文「数据模型」一节和它冲突时，以 ADR 0003 为准。前提模型见 `中台/docs/adr/0004-前提模型-状态判定与命令.md`，前提一节和它冲突时，以 ADR 0004 为准。导入与同步见 `中台/docs/adr/0005-导入与同步.md`，本文「导入 #117」「同步到 GitHub」「验收」「建造顺序」四节和它冲突时，以 ADR 0005 为准。
基线：地图 #117，现行决定 30 条，归档 1 条（D-0002b，被 D-0009 取代），合计 31 条，子票 10 张，覆盖表 24 句。

## 一句话

用一台本机服务替掉 GitHub Issues 做决策的承载物。决定是主记录，票是挂在决定上的工作项，前提是决定能被推翻的依据。状态每次变化记一条事件，屏幕实时显示，破坏性变化推到眼前。

## 为什么换承载物

GitHub Issues 是个存文本的地方。我们现在需要的是存「关系」并且能判断「关系失效」的地方。两回事。

现在的三个硬伤，对应新模型的解法：

| 硬伤 | 现状 | 新模型 |
| --- | --- | --- |
| 决定只记结论，不记依据 | 31 条决定，0 条前提。`check` 八条不变量全查格式，没有一条查「这条还站得住吗」 | 前提是一等记录，有自己的状态 |
| 失效只有人手查 | `chain` 能算出受影响的决定和票，但没人跑，结果也没地方放 | 影响清单是常驻视图，状态变了自动推 |
| 并发读旧状态 | 每个会话读自己分支上的 `docs/decisions.md`，落后就看不见 | 只有一个权威状态，agent 通过 CLI 读，永远最新 |

第三条就是你说的版本控制问题。解法是事件日志，不是加锁。

## 数据模型

四类记录。

### 决定

```
id        D-0001
陈述      一句话。写定了什么，不写「见正文」
状态      active | superseded | void
组        来源票。迁移时按票分组，一个主题一组
出处      票号
产出文件  相对路径
前提      [P-...]
```

### 前提

这条决定成立依赖什么。一句可被证伪的话。

```
id        P-0001
所属      D-0001
陈述      例：planner 只读当前仓库的 issue
状态      未验 | 成立 | 已破 | 未知
证据      [票号、文件路径、链接、原话]
上次判定  谁 / 何时 / 判定词 / 理由
```

状态由判定折叠出来。没判过是 `未验`；判过是最近一次判定的词：`成立`、`已破`、`未知`。`未知` 指判过，但按现在的证据判不了。

前提由 agent 写、人审阅，也可以人直接写。谁写的由事件的 `actor` 记。没判过可以改陈述和证据，判过锁住；要换说法就新建一条，旧前提留在决定上，决定仍按旧前提已破算。

一条前提只属于一条决定。两条决定依赖同一件事，各写一条。

没有前提的决定永远不会被标记失效。它只能被人想起，或者永远想不起。前提就是兜底机制的接口。

### 票

```
id       #124
类型     grilling | research | prototype | task
状态     open | closed
消费     [D-...]   动手前认定仍然有效的决定
产出     [D-...]   grilling 和非 grilling 都能产出
父票     票号
地图     地图票号
```

票型决定边的方向。grilling 主要产出决定；research、prototype、task 主要消费决定，回头看也可能产出。

### 事件

```
seq       自增
ts        时间
actor     谁
op        动作
target    对象
payload   内容
reason    为什么
```

## 写入路径

只有一个写入点：追加一条事件。没有 UPDATE，没有覆盖。

```
events.jsonl   ← 权威。只追加
board.db       ← 索引。随时可删，从 events 重建
```

所有状态都是事件折叠出来的。删掉 `board.db`，重放 `events.jsonl`，得到同一个状态。状态哈希可以比对。

并发怎么处理：单写者。服务进程拿一个文件锁，两个会话同时写，后到的排队，不丢事件。这就是你要的版本控制的效果，代价比加一套多版本机制低得多。

`events.jsonl` 定期提交进 git，提供历史和大范围回滚。

## 读取路径

agent 不读文件，调 CLI。读到的一定是最新状态。

```
dt show D-0002e              一条决定的全部
dt impact show IC-0003       看一个影响清单
dt impact list               列还开着的清单
dt parallel #124 #125        两张票能不能同时做
dt open --group 120          某组里还有什么没做完
dt judge D-0002e 仍成立      四档判定
```

现有 `docs/decisions.md` 降级为导出产物，由 `dt export markdown` 生成。人想看还是能看，但它不再是 agent 的输入。

## 屏幕

分三块。

**左：决定图。** 一个节点一条决定，按组聚拢。节点大小表示下游票数，颜色只由两样东西决定：决定状态和前提状态。

| 样子 | 含义 |
| --- | --- |
| 空心灰 | 没有前提，或前提未验 |
| 实心绿 | 有前提，全部成立 |
| 黄 | 有前提未验完 |
| 红 | 有未处理的已破前提 |
| 划线 | 已被取代或作废 |

票子上的变化不改颜色。票一天开开关关几十次，那是噪音。

红色是提醒，不是事实。判了「仍成立」以后红色消掉；判「要补问」不消，等跟进票关掉再判。再破一条前提，红再亮。规则见 ADR 0006。

**右：决定详情。** 陈述、前提逐条列状态和证据、消费它的票、下游清单。按钮三个：加前提、判前提、推翻。

**下：提醒条。** 只推两种事件：前提变成已破，决定被取代或作废。每行一句人话，带影响清单。

```
P-0003 已破（planner 改成读中央仓）→ 影响清单：2 条决定、3 张开放票   [开始处理]
```

红点亮起的同时右边直接列出受影响的票。只变色不列票，等于让人自己顺着边找一遍。

## 推翻的时候发生什么

一条命令：

```
dt overturn D-0005 --by "新决定的一句话" --source #130
```

这条事件写进去的时候，同时带上影响清单：清单号、范围快照、触发决定。后面自动发生三步：

1. 新建决定，记录取代边，D-0005 变 superseded。
2. 沿因果边算出受影响的决定和票，存进这条事件的 `impact_items`。
3. 屏幕打开影响清单，逐项列待办。

范围为空时不打开清单。判定永远人做，四档：仍成立、需修改、作废、要补问。系统只出名单。

这四档是决定被推翻后的处理动作，不是前提的判定。前提只有 `成立`、`已破`、`未知` 三个词，见 ADR 0004。影响清单的范围、动作和关闭见 ADR 0006。

判定本身也是事件，带理由。三个月后你能回答「这条当时为什么判它仍然成立」。

## 问题目录

Map 推进中会遇到的问题就这些，每项有固定处理动作。表外的问题 v1 不处理，确实需要的按「冒头」开票。

**自动发现的问题**

| 问题 | 怎么看到 | 怎么处理 | 哪张票定 |
| --- | --- | --- | --- |
| 前提判破 | 决定变红，提醒条一行，影响清单打开 | 该决定选四档 | 前提模型、影响清单模型 |
| 决定被取代 | 旧决定划线，影响清单打开 | 受影响的决定选四档，票选五种动作 | 影响清单模型 |
| 决定作废 | 同上 | 同上 | 影响清单模型 |
| 终点换根 | 旧根划线，覆盖表标「失效」，旧句下的票标「吃旧决定」 | 影响清单逐项处理，覆盖表重算 | 影响清单模型、图票模型 |
| 裸决定 | 决定空心灰 | 加前提 | 前提模型 |
| 无源决定 | 屏幕标「无源决定」 | 补来源票；导入的标「未记录」 | 图票模型、导入与同步 |
| 无主票 | 屏幕标「无主票」 | 补 `derived_from` 和拆票理由 | 图票模型、导入与同步 |
| 吃旧决定 | 票标「吃旧决定」 | 改范围、关掉、重开、新建 | 影响清单模型、图票模型 |
| 覆盖缺口 | 覆盖表标红 | 新建票，`covers` 指向这一句 | 影响清单模型、图票模型 |
| 影响清单未清 | 屏幕标「影响清单未清」 | 逐项处理，全部处理完关闭 | 影响清单模型 |
| 工作卡住 | 屏幕标「工作卡住」 | 人去 orca 处理 | 工作状态同步 |
| 同步异常 | 屏幕标「同步异常」 | 重试或重新同步 | 导入与同步 |

**只能靠人发现的问题**

| 问题 | 怎么处理 | 哪张票定 |
| --- | --- | --- |
| 票太大，一次做不完 | 改范围或新建；票不能有子票 | 影响清单模型、图票模型 |
| 两张票做同一件事 | 关掉一张，写并入哪张 | 影响清单模型 |
| 票型、标签、阻塞挂错 | 编辑动作 | 图票模型 |
| 决定陈述要改 | 新建决定取代旧决定 | 图票模型 |
| 票关了但没留下决定或结论 | 关票时写「无结论：理由」 | 工作流程 |
| 影响清单范围算错（漏项或多项） | v1 不手工增删；漏项走日常流程，多项选保留 | 影响清单模型（已知边界） |

**动作词表**

- 决定四档：`仍成立`、`需修改`、`作废`、`要补问`。
- 票五种：`保留`、`改范围`、`关掉`、`重开`、`新建`。合并用关掉加 `impact_merged_into`。

## 并行区域

不手画。算。

两张票能并行，当且仅当它们消费的前提集合没有交集，且互不在对方的影响清单里。

UI 上选几张票，右下角直接出结论：

```
#124 与 #127：可并行。前提无交集。
#124 与 #130：串行。共用 P-0007（planner 只读当前仓）。
```

算出来的边界会跟着决定变。手画的圈不会。

## 导入 #117

只读导入，不改 GitHub 上任何东西。规则见 ADR 0005。

```
dt import github 117
```

读 GitHub 的 issue、评论、标签、状态。得到：

- 10 张票，9 张已关闭，1 张开放（#124）
- 17 条评论
- 31 条决定，含被取代的 D-0002b
- 24 句覆盖表，映射到根决定 `D-117-ROOT` 和票的 `covers`
- 前提 0 条

导入只补能直接读到的边：决定的来源票、取代、覆盖。拆票理由留空，显示「未记录」；票与票、决定与决定的派生不补。旧图的票都挂在根决定下。

### 补前提的节奏

导入完不要求一次补完。按正在动的地图和票补：动哪张票，补它产出的决定。每条决定 1 到 3 句前提。补完一条，那条决定的颜色跟着变；屏幕会告诉你进度，不用统计。

## 同步到 GitHub

GitHub 是只读镜像，不是第二份主记录。运营者在中台改完，按地图点同步；平台先出计划，确认后执行。每张地图一个镜像开关，关掉时只在中台维护。规则见 ADR 0005。

同步写三样：issue、评论、地图正文里的生成段。生成段装 Destination、覆盖表、决定清单和票因果表；票的正文和评论照原样镜像。中台为准，GitHub 上的直接修改会在下一次同步被覆盖。

```
dt sync --check 139    只读比对，打印计划，不调用写接口
dt sync 139            真写
```

生成段到约 60KB 时截断表格，末尾写「完整内容在中台」并附本地地址。同步照常成功。

## 验收

四条硬指标，跑得出来才算做完。

| 编号 | 命令 | 期望 |
| --- | --- | --- |
| 1 | `dt import github 117` | 10 张票、17 条评论、31 条决定（含 D-0002b）、24 句覆盖表、根决定 `D-117-ROOT`；每条陈述与四列表逐字相同；导入期间 GitHub 零改动 |
| 2 | `dt rebuild && dt hash` 跑两次 | 两次哈希相同；删掉 `board.db` 后结果不变 |
| 3 | 给 D-0009 挂前提 P-9，`dt premise judge P-9 已破` | 提醒条出现一行；影响清单打开，列出 D-0009 和受影响的票；逐项处理完清单关闭 |
| 4 | `dt sync --check 139`，再 `dt sync 139` | 先打印计划，GitHub 零改动；同步后中台新建的票和评论几秒内出现在 GitHub；GitHub 上的直接修改在下次同步被覆盖 |

第 3 条是整套东西存在的理由。它跑不通，后面全不用做。

## 不做什么

- 不做 LLM 判冲突。开放式隐式冲突检测五成左右，不够用。
- 不做多用户、权限、登录。一个运营者，两三个会话。
- 不做全树实时语义重算。只算声明过的边。
- 不替代 git。事件日志进 git，不做另一套版本系统。
- 不给客户看。客户侧继续用现有 `customer-kit`。

## 建造顺序

三步，每步都有能看的东西。

**第 1 步：内核。** 事件日志、折叠、`import`、`impact`、`judge`、`overturn`。没有界面。验收：命令行跑通上面第 1、2、3 条。

**第 2 步：屏幕。** 本地 web 服务，三块布局，事件推送。验收：改一条前提，浏览器两秒内变红并列出受影响票。

**第 3 步：并行区与同步。** 验收：选两张票出结论；`dt sync --check` 出计划，`dt sync` 写出镜像。

第 1 步做完就可以开始补前提。第 2 步做完才算能天天用。

## 已知边界

写下来，别指望它解决。

1. 没写下来的前提，图里看不见。屏幕上一片绿只代表你写了的那几条是成立的。
2. 「这条决定还成不成立」要靠证据和人判，图只负责把人叫过来。
3. 补前提是人工成本。跳过去，系统就退化成现在的样子，只是换了个界面。
