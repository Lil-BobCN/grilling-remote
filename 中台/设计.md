# 设计：决策中台（Decision Board）

日期：2026-11-10
状态：初稿。2026-11-10 起由地图 #139（中台 v1：本机 issue 主记录，GitHub 做镜像）逐票裁定；票上的决定优先于本文。事件模型见 `中台/docs/adr/0002-事件模型-一条动作一条事件.md`。
基线：地图 #117，现行决定 30 条，归档 1 条（D-0002b，被 D-0009 取代），合计 31 条，子票 10 张，覆盖表 24 句。

## 一句话

用一台本机服务替掉 GitHub Issues 做决策的承载物。决定是主记录，票是挂在决定上的工作项，前提是决定能被推翻的依据。状态每次变化记一条事件，屏幕实时显示，破坏性变化推到眼前。

## 为什么换承载物

GitHub Issues 是个存文本的地方。我们现在需要的是存「关系」并且能判断「关系失效」的地方。两回事。

现在的三个硬伤，对应新模型的解法：

| 硬伤 | 现状 | 新模型 |
| --- | --- | --- |
| 决定只记结论，不记依据 | 31 条决定，0 条前提。`check` 八条不变量全查格式，没有一条查「这条还站得住吗」 | 前提是一等记录，有自己的状态 |
| 失效只有人手查 | `chain` 能算出影响面，但没人跑，结果也没地方放 | 影响面是常驻视图，状态变了自动推 |
| 并发读旧状态 | 每个会话读自己分支上的 `docs/decisions.md`，落后就看不见 | 只有一个权威状态，agent 通过 CLI 读，永远最新 |

第三条就是你说的版本控制问题。解法是事件日志，不是加锁。

## 数据模型

四类记录。

### 决定

```
id        D-0001
陈述      一句话。写定了什么，不写「见正文」
状态      active | superseded | void
组        来源票。迁移时按票分组，一个主题一组
出处      票号
产出文件  相对路径
前提      [P-...]
```

### 前提（新增）

这条决定成立依赖什么。一句可被证伪的话。

```
id        P-0001
所属      D-0001
陈述      例：planner 只读当前仓库的 issue
状态      未验 | 成立 | 已破 | 未知
证据      [票号或文件路径]
上次判定  谁 / 何时 / 理由
```

没有前提的决定永远不会被标记失效。它只能被人想起，或者永远想不起。前提就是兜底机制的接口。

### 票

```
id       #124
类型     grilling | research | prototype | task
状态     open | closed
消费     [D-...]   动手前认定仍然有效的决定
产出     [D-...]   grilling 和非 grilling 都能产出
父票     票号
地图     地图票号
```

票型决定边的方向。grilling 主要产出决定；research、prototype、task 主要消费决定，回头看也可能产出。

### 事件

```
seq       自增
ts        时间
actor     谁
op        动作
target    对象
payload   内容
reason    为什么
```

## 写入路径

只有一个写入点：追加一条事件。没有 UPDATE，没有覆盖。

```
events.jsonl   ← 权威。只追加
board.db       ← 索引。随时可删，从 events 重建
```

所有状态都是事件折叠出来的。删掉 `board.db`，重放 `events.jsonl`，得到同一个状态。状态哈希可以比对。

并发怎么处理：单写者。服务进程拿一个文件锁，两个会话同时写，后到的排队，不丢事件。这就是你要的版本控制的效果，代价比加一套多版本机制低得多。

`events.jsonl` 定期提交进 git，提供历史和大范围回滚。

## 读取路径

agent 不读文件，调 CLI。读到的一定是最新状态。

```
dt show D-0002e              一条决定的全部
dt impact D-0002e            推翻它会波及什么
dt parallel #124 #125        两张票能不能同时做
dt open --group 120          某组里还有什么没做完
dt judge D-0002e 仍成立      四档判定
```

现有 `docs/decisions.md` 降级为导出产物，由 `dt export markdown` 生成。人想看还是能看，但它不再是 agent 的输入。

## 屏幕

分三块。

**左：决定图。** 一个节点一条决定，按组聚拢。节点大小表示下游票数，颜色只由两样东西决定：决定状态和前提状态。

| 样子 | 含义 |
| --- | --- |
| 空心灰 | 没有前提，或前提未验 |
| 实心绿 | 有前提，全部成立 |
| 黄 | 有前提未验完 |
| 红 | 至少一条前提已破 |
| 划线 | 已被取代或作废 |

票子上的变化不改颜色。票一天开开关关几十次，那是噪音。

**右：决定详情。** 陈述、前提逐条列状态和证据、消费它的票、下游清单。按钮三个：加前提、判前提、推翻。

**下：提醒条。** 只推两种事件：前提变成已破，决定被取代或作废。每行一句人话，带影响面。

```
P-0003 已破（planner 改成读中央仓）→ 波及 2 条决定、3 张开放票   [开始判定]
```

红点亮起的同时右边直接列出受影响的票。只变色不列票，等于让人自己顺着边找一遍。

## 推翻的时候发生什么

一条命令：

```
dt overturn D-0005 --by "新决定的一句话" --source #130
```

后面自动发生四步：

1. 新建决定，记录取代边。
2. D-0005 变 superseded。
3. 算影响面：沿派生边向下，沿取代边反向，再加所有消费它的票。
4. 给每个受影响的决定挂一个「待判定」标记，进提醒条。

判定永远人做，四档：仍成立、需修改、作废、要补问。脚本只出名单。

判定本身也是事件，带理由。三个月后你能回答「这条当时为什么判它仍然成立」。

## 并行区域

不手画。算。

两张票能并行，当且仅当它们消费的前提集合没有交集，且互不在对方的影响面里。

UI 上选几张票，右下角直接出结论：

```
#124 与 #127：可并行。前提无交集。
#124 与 #130：串行。共用 P-0007（planner 只读当前仓）。
```

算出来的边界会跟着决定变。手画的圈不会。

## 迁移 #117

只读导入，不改 GitHub 上任何东西。

```
dt import github 117
```

读三样：关闭票评论里的四列表、归档文件、子票清单。得到：

- 31 条现行决定，1 条归档决定
- 10 张票，9 张已关闭，1 张开放（#124）
- 24 句覆盖表进地图记录
- 前提 0 条

第 0 天屏幕上是一片灰色的 31 个节点。这是诚实的样子：你现在 31 条决定，没有一条记了凭据。

迁移顺带修掉的旧账：归档里 D-0002b 的「取代」列写着「无」，取代关系表里却写着 D-0009。新模型里取代是边，不是列，这类不一致在结构上不可能出现。

### 补前提的节奏

迁移完不要求一次补完。按正在动的组补：动 #124 补 120 那组，动别的补别的。每条决定 1 到 3 句前提，9 个组合计约 30 句。

补完一组，那组节点从灰变绿。屏幕会告诉你进度，不用统计。

## 以后迁回 GitHub

> 2026-11-10 起，GitHub 改为只读镜像，由《导入与同步：中台主记录，GitHub 镜像》重定。本节写的 `dt export github --dry-run/--apply` 是旧方案。

从一开始就留接口，不然后面是重写。

```
dt export github --dry-run    只打印计划，不调用 gh
dt export github --apply      真写
```

映射：一条决定对应一张票的一条评论，带隐藏标记，重复导出是更新不是新建。状态、前提、判定理由各成一段。

`--dry-run` 打出「将新建 N 条评论、修改 M 条」就停。等形态稳定了再 `--apply`。

## 验收

四条硬指标，跑得出来才算做完。

| 编号 | 命令 | 期望 |
| --- | --- | --- |
| 1 | `dt import github 117` | 30 条现行 + 1 条归档，10 张票，0 条前提；每条陈述与 `docs/decisions.md` 逐字相同 |
| 2 | `dt rebuild && dt hash` 跑两次 | 两次哈希相同；删掉 `board.db` 后结果不变 |
| 3 | 给 D-0009 挂前提 P-9，`dt premise judge P-9 broken` | 提醒条出现一行；`dt impact D-0002b` 列出 D-0009；受影响票数和屏幕红点数一致 |
| 4 | `dt export github --dry-run` | 打印计划，GitHub 上零改动（`gh issue view` 前后一致） |

第 3 条是整套东西存在的理由。它跑不通，后面全不用做。

## 不做什么

- 不做 LLM 判冲突。开放式隐式冲突检测五成左右，不够用。
- 不做多用户、权限、登录。一个运营者，两三个会话。
- 不做全树实时语义重算。只算声明过的边。
- 不替代 git。事件日志进 git，不做另一套版本系统。
- 不给客户看。客户侧继续用现有 `customer-kit`。

## 建造顺序

三步，每步都有能看的东西。

**第 1 步：内核。** 事件日志、折叠、`import`、`impact`、`judge`、`overturn`。没有界面。验收：命令行跑通上面第 1、2、3 条。

**第 2 步：屏幕。** 本地 web 服务，三块布局，事件推送。验收：改一条前提，浏览器两秒内变红并列出受影响票。

**第 3 步：并行区与导出。** 验收：选两张票出结论；`export github --dry-run` 出计划。

第 1 步做完就可以开始补前提。第 2 步做完才算能天天用。

## 已知边界

写下来，别指望它解决。

1. 没写下来的前提，图里看不见。屏幕上一片绿只代表你写了的那几条是成立的。
2. 「这条决定还成不成立」要靠证据和人判，图只负责把人叫过来。
3. 补前提是人工成本。跳过去，系统就退化成现在的样子，只是换了个界面。
