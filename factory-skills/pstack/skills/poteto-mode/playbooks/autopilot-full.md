### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in step 5 can carry a lane's result, and every new head needs its own green CI. Trunk means the branch a PR lands on: the integration branch for a ticket PR, the main branch for the integration branch's own PR.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Use `gh` for every PR operation. The `gh` token covers only the current client repo. Each owner is a sub-agent in its own worktree and its own container that builds, writes its PR body with `/pr`, opens the PR through `gh` as ready and never as a draft, proves the change on the real artifact, waits for green CI per the CI rules below, and merges once steps 4 and 5 clear it. Read the `owner` line in `roles.md` for its model. If the file or the line is missing, or the line is not configured, use the parent session's model.

   Open the PR early so CI runs alongside the work. The code is ready only after the `/no-comments` pass, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof and CI are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Wait for green CI with `gh pr checks <pr> --watch`, then read the PR back with `gh pr view <pr> --json state,mergeable,mergeStateStatus,headRefOid`, because ready means GitHub agrees the PR can merge, not only that the checks are green. Classify a failing check before any retrigger. A flake or an infrastructure failure earns one fresh run of the whole workflow, never a retry of one job, and only one. An identical second failure means it was never a flake, so reclassify it and read the failed logs with `gh run view <run-id> --log-failed` instead of retrying blind. A failure in code the diff never touches means a stale base, so check with `git merge-base --is-ancestor` before assuming a flake. A stale base needs a rebase, not another retry. Only a failure in the diff's own code gets a commit.

   Assume the container dies. Soon after starting, push and start a decision trail in the trail store named in your brief per the **show-me-your-work** skill, then push each finished unit before you start the next. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that store, so the scheduler and the root can check it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. Read the `swarm workers` line in `roles.md` for their models, with the same fallback. They re-run the gates, prove the load-bearing behavior live on the real surface through the repo's `verify-<app>` skill (made by `create-verification-skill`) or a named driver, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   The review must pass too, on the same head the swarm verified, so the owner merges only when both pass. Read the `reviewer` line in `roles.md` for the reviewer's model, with the same fallback. A high-risk PR also gets an **interrogate** pass. If the swarm and the review still fail after their fixes, treat it as an environment problem. Stop that lane, notify the operator, and attach the symptom and what was tried.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.

   Re-check that the verdicts still describe the code. A verdict covers a patch, and a rebase moves the PR to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.

   A ticket PR whose base is the integration branch is merged by the merger sub-agent, not by its owner, and the same rules bind it. Read the `merger` line in `roles.md` for its model, with the same fallback. A PR that lands on the main branch is merged by its owner.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then the operator's fresh countersign, because the owner is the one who wants green. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, the scheduler reconciles every 30 seconds until no delegated work is left, because long runs drift and agents stall silently. The scheduler is a plain program, not an agent, so it reads side effects only: pushes, trail rows, PR state, and check results. Each tick it compares every PR head and every running agent against the trail and tells you about any gap, such as an unreported head or an unrecorded agent, so you can have its owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck. The scheduler does not answer it. It notifies you, or the operator when only the operator can answer, and you answer what you can. The scheduler notifies you of a stuck agent at once. Replace it without waiting for its stop to land. A tick that changed something for the operator ends with a short notice to the operator, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** report to the operator in one short notice, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
