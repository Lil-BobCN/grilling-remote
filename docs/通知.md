# 通知

> 状态：现行

一句话：调度器决定发什么、什么时候发；`notifier/` 决定怎么送到、送不到怎么办。调用方把一条事件 JSON 写到临时文件，命令渲染标题和正文，走手机推送和邮件，按 `key` 去重。

来源：2026-11-15 定事件表（来源票 [通知链路与事件表](https://github.com/Lil-BobCN/grilling-remote/issues/215)）；2026-11-16 定模块边界（I-0112），按 D-0334 给四条等人待办加邮件，按 D-0342 加「重传地图已更新」；2026-11-16 按 D-I-0156-ROOT 并入 `docs/archive/合并前-2026-11-16/` 下的模块边界和事件表两篇。后端服务的实现和部署见 `docs/后端服务.md`。

推送只给运营者。客户那条线见 `docs/客户进度.md`。

## 二、责任分界

调度器核心决定发什么、什么时候发；通知模块决定怎么送到、送不到怎么办。通知模块是一个独立命令，调度器核心不管用什么语言，起一个进程调用它。

| 归通知模块 | 归调度器核心 |
| --- | --- |
| 按事件名和字段渲染标题、正文 | 读工单状态，判断该发哪条通知事件 |
| 发邮件和手机推送 | 决定发送时机 |
| 通道失败后的重试、退避 | 等人的待办每 24 小时重发 |
| 3 次仍失败时转另一条通道 | 决定重复发送用哪个 `key` |
| 连续失败时发「通道可能断了」告警 | 决定一条待办什么时候算消失 |
| 按 `key` 去重，记录已推和失败 |  |
| 写日志和发送状态 |  |

这条线的一句话：调度器管时机，通知模块管送达。

## 三、谁触发

工厂事件里，调度器是唯一触发方。它每 30 秒读一遍客户仓，按状态算出该推的事件，把事件交给通知模块。通知模块按模板渲染标题和正文，向推送通道的 `webhook`（外部程序调用 Bot 的地址）发 POST。企业微信 Bot 照正文原样发一条消息，不做路由，不点火。

基础设施告警是另一条触发路径：Mac 上的巡检脚本直接 POST 同一个 webhook，Bot 同样照正文原样发。工厂事件仍只有调度器一个触发方。巡检内容见 `docs/运维手册.md` 第十一节。

- 一个企业微信 Bot 一个内部群，群里只有运营者。Bot 只在群里发消息。手机只收提醒，不做草选；最终决定在 Orca 做。
- 推送只是提醒，不是送达回执。没收到按待办状态重发，见「重复与失败」一节。
- webhook key 只存登录钥匙串，通知模块每次启动时读进内存。通道失败时的重试和兜底见「重复与失败」一节；限流失败不自动重试。
- 推送通道的选型、限流和配置归「通知链换轨」地图（I-0111）。

| 每日抽样 | 调度器每天 8:30 | 运营者 | Bot | 昨天合了 {N} 单 | {客户简称} · {需求名}（PR #{n}）；…… |

出事的 `{原因}` 七种：三圈没进展、超额度、禁区、同类两次、验证评审修不过、部署失败、点火失败。

调度器实现（to-spec）的验收条件：读 PR head 的 `.audit/<票号>.tsv`；看到 `phase=gate`、`result=open` 推一条「需要你答」；看到 `answered` 或 `parked` 停止提醒；有 `open` 行的线不算卡住。

### 每日抽样

每天 8:30 推前一天 00:00 到 24:00 合进主干的单。一单都没有就不发。只列客户简称、需求名和 PR 链接，不写别的。抽样动作不变，见 `docs/工厂流程.md` 的「每天早上抽样」一节。

## 五、输入：一条通知事件

调用方把一条 JSON 写到文件，再把文件路径交给命令。

```json
{
  "v": 1,
  "key": "I-0111:需要你答:PR-123:2026-11-16",
  "event": "需要你答",
  "occurred_at": "2026-11-16T12:00:00+08:00",
  "link": "https://github.com/Lil-BobCN/grilling-remote/pull/123",
  "data": {
    "customer": "B 店",
    "requirement": "预约送货",
    "question": "闸门第三题选哪个方案",
    "recommended": "方案 A",
    "days_waited": 0
  }
}
```

外层字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `v` | 整数 | 格式版本，现在是 1 |
| `key` | 字符串 | 去重键。通知模块不解析内容，只拿它查发送状态 |
| `event` | 字符串 | 事件名，见「事件表」 |
| `occurred_at` | 字符串 | 事件发生时间，ISO 8601 带时区 |
| `link` | 字符串 | 消息里的主链接。每日抽样不用，链接在 `items` 里 |
| `data` | 对象 | 事件自己的字段 |

`data` 必填字段按「事件表」，共 12 类：

| 事件 | `data` 必填字段 |
| --- | --- |
| 新单进队列 | `customer`、`requirement` |
| 重传地图已更新 | `customer`、`requirement` |
| 补缺口提案 | `customer`、`requirement`、`question_count` |
| 该跑 to-spec | `customer`、`requirement` |
| 拆票提案 | `customer`、`requirement`、`ticket_count` |
| 需要你答 | `customer`、`requirement`、`question`、`recommended` |
| 出事 | `customer`、`requirement`、`reason`、`tried` |
| 自己合并 | `customer`、`requirement`、`pr` |
| 部署完成 | `customer`、`requirement`、`address` |
| needs-info | `customer`、`requirement` |
| 点火超时 | `customer`、`requirement` |
| 每日抽样 | `date`、`items`（每项含 `customer`、`requirement`、`pr`，可选 `url` 指向 PR） |

可选字段：

- `data.days_waited`：整数，24 小时重复时填已等天数。模板在正文末尾加「已等 N 天。」。
- `data.pr`：PR 号。`link` 已经指向 PR 时也填，模板要用编号。

标题和正文的固定措辞归通知模块，调用方只给事实。模板按「事件表」，改动要另开票。

## 六、输出和退出码

stdout 一行 JSON：

```json
{"key":"I-0111:需要你答:PR-123:2026-11-16","skipped":false,"results":[{"channel":"push","ok":true,"ms":210},{"channel":"email","ok":true,"ms":840}]}
```

退出码：

| 码 | 含义 |
| --- | --- |
| 0 | 所有启用的通道都送到，或者这个 `key` 已经送过、本次跳过 |
| 1 | 至少一路在重试后仍失败 |
| 2 | 输入、配置或用法错 |

测试时加 `--channel email` 或 `--channel push`，只发一路。不加就发所有启用的通道。

## 七、去重和状态

`state.json` 按 `key` 记一条：

- 已送成功：同一个 `key` 再来，直接跳过，退出码 0，日志写 `duplicate`。
- 上次失败：同一个 `key` 再来，允许再试。
- 重复提醒由调度器换一个新 `key` 触发。比如 24 小时重复的 `key` 带上日期或已等天数。
- 保留窗口 7 天，超期的已推标记和待补发事件在每次发送前清掉。写状态要能扛崩溃，不能留下半条记录。

## 八、通道

### 推送

企业微信 Bot。一个 Bot 一个内部群，群里只有运营者。通知模块向 webhook 发 POST，Bot 照正文原样发一条消息，不做路由，不点火。基础设施告警由 Mac 巡检脚本直接 POST 同一个 webhook。

webhook key 只存登录钥匙串，通知模块每次启动时读进内存。限流失败不自动重试。

### 邮件

由通知模块用独立 SMTP（发信服务）发。基础设施巡检的邮件由巡检脚本自己发，不计入这些。

邮件走两条线：

- 兜底：出事、点火超时、通知通道连续失败。出事先推送、再邮件，推送失败时邮件兜底；点火超时只有邮件；通道连续失败由告警邮件报。
- 等人的待办：补缺口提案、该跑 to-spec、拆票提案、需要你答。推送在前、邮件在后，邮件慢不拖推送。

SMTP 走阿里云邮件推送（D-0279）：`smtpdm.aliyun.com:465`，SSL。发信域是 `mail.afkfactory.space` 子域，发信地址 `notify@mail.afkfactory.space`（D-0280）。

退信处理按 D-0282：同步拒收记日志并计入「通道断了」，异步退信人工看阿里云控制台。

独立 SMTP 到达已验（D-0323，I-0118）：2026-11-16 从本机直发，发出到进 Outlook 收件箱都在 7 秒内；首次进垃圾箱，把发件地址加进安全发件人后正常。

## 九、重复与失败

- 等人的待办：补缺口、拆票、该跑 to-spec、需要你答。每 24 小时重发一次，正文末尾加 `已等 {N} 天。` 补缺口和拆票等到点头，to-spec 等到仓库里有 spec，需要你答等到 trail 里出现 `answered` 或 `parked`。
- 出事、自己合并、部署完成、新单进队列、needs-info、重传地图已更新：只发一次。
- 推送失败：通知模块在原地重试，最多 3 次，间隔 30 秒；邮件只发一次。
- 3 次仍失败：出事立刻改走邮件；其余事件等下一次状态变化或 24 小时重复。四条等人待办本来就发邮件，不走这条转投。
- 推送连续失败：按尝试次数跨事件累计，到 3 次发一封「通知通道可能断了」邮件，一天最多一封；成功一次清零。
- 恢复补发：任意一路下一次发送成功时，把之前失败过这一路的事件各补发一次，只补失败过的通道。
- 两路都断：日志写一条「通道断了」。这是本地记录，两路都断时没有外发通道。
- 已推标记：通知模块记在 `~/.grilling/notifier/state.json`，按事件加通道路记送达；全部通道送到就跳过。崩溃重启后最多重复推一次，保留 7 天。

## 十、不推的事件

- 开始开发。D-M1-001 已定写本地日志。
- 子票状态变化。
- 待客户验收、客户点头。客户走微信，验收不设时限。
- 三条客户微信和已发记录。管理视图标「该发消息」，发过写订单文件的 `messages`；第 2 条只在「部署完成」推送正文里带一句。
- 客户卡住、客户留言。走微信。
- 驳回、关票。运营者自己写评论或关票。重传地图更新走「事件表」的「重传地图已更新」。
- gate 行写 `answered` 或 `parked`。等待中的线继续走，不再提醒。
- 父工单关闭。

## 十一、怎么调用

任何语言都可以。把通知事件写到临时文件，跑命令，读退出码和 stdout。

```bash
python3 -m notifier send --event-file /tmp/notify-event.json
```

命令在仓库根目录跑。不在仓库根目录跑时，把仓库根加进 `PYTHONPATH`。通知模块不读 GitHub，不读中台，不判断状态。所有事实由调用方放进 JSON。

## 十二、测试用替身

用调度器替身脚本 `notifier/dev/standin.py`。它只做三件事：按参数做一次只读查询，组装一条通知事件，把事件交给真正的命令行入口。

```bash
python3 -m notifier.dev.standin --repo Lil-BobCN/grilling-remote --ticket 349 \
  --event 需要你答 --question "闸门第三题选哪个方案" --recommended "方案 A"

python3 -m notifier.dev.standin --repo Lil-BobCN/grilling-remote \
  --event 每日抽样 --date 2026-11-15
```

- 工单上有的字段从 `gh` 读一次。工单上没有的字段用参数补，比如 `reason`、`tried`、`address`、计数。
- 替身用子进程调用 `python3 -m notifier send`，不直接 import，这样测的是真实入口。
- 替身不轮询，不判断下一步，不自己重试。它不是调度器。
- 单元测试用 `notifier/tests/` 下的固定 JSON，不经过替身。
- 调度器核心建成后，核心组装同样的 JSON，调同样的命令，替身退场。

两种自动来源，数据由替身查一次：

```bash
# 每日抽样：读 2026-11-15 当地 00:00 到 24:00 合进主干的 PR
python3 -m notifier.dev.standin --repo Lil-BobCN/grilling-remote \
  --event 每日抽样 --merged-on 2026-11-15 --customer 工厂

# 需要你答：读 PR head 的 .audit/<票号>.tsv，每条 result=open 的 gate 行发一条
python3 -m notifier.dev.standin --repo Lil-BobCN/grilling-remote \
  --audit-pr 123 --audit-ticket 355 --customer 工厂
```

- 合并记录按当地时区整天算，查询会跨两个 UTC 日期，再按 `mergedAt` 过滤。没有合并时不发。
- 工单正文有 `- 客户简称：` 和 `- 需求名：` 时优先用；没有时用 `--customer` 和工单标题。需求名再缺就用 PR 标题。
- gate 行按六列读：`decision` 以 `问：` 开头、`result=open`。推荐答案写在 `decision` 或 `why` 的 `推荐：` 后面，没有就写「未写推荐」。
- trail 是追加式的，问题行不会改。后面的 `答：` 行按出现顺序配给最早的未答问题，`result=answered` 或 `parked` 都算答过，配上后不再提醒。

## 十三、依据

- 触发方式：调度器是唯一状态源，出事类事件只有它能算。企业微信 Bot 看不到工单状态。通知模块只发送，不做路由；见 D-0288。
- 推送只是提醒：旧链路实测延迟约 15 秒，没有送达或已读回执，见 D-0175（已被 D-0343 取代，这句只作旧链路证据）；2026-11-16 企业微信 Bot 的 10 条推送运营者都确认 30 秒内收到（I-0122），仍没有送达回执。
- 合并推送：D-M1-009 已定。E1 漏写通知，补进 `docs/工厂流程.md`。
- 进队列和完成：D-M1-001；完成对应事件表的「部署完成」。
