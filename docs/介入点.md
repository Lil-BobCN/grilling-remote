## 各自看什么

### 一、补缺口：一次列完，逐项答「是」

回传校验通过，仓库和工单建好。形式和客户那边一样，是一轮 grilling。每项带推荐答案，措辞让你答「是」就等于接受。

这一轮里要你定的有六类：

1. 五类技术选择：技术栈、部署到哪、第三方服务与账号、数据怎么存、每月花多少。客户的答案当推荐值。
2. A2 里标了「你答」「你最后定」的题。
3. 合规：收不收个人信息，接不接支付。默认都不。
4. 接缝：测试打在哪一层，理想数量是一个。无人值守时没有客户可问，由你代答。
5. 词汇表：先读客户工作区根目录的 `GLOSSARY.md`，你确认命名后写进客户仓 `GLOSSARY.md`。
6. 查重：先搜 open 和 closed 工单。

补缺口前先看问题树：手动跑 `question-tree`，看三堆。没定的、客户不懂走了推荐答案的、待核实的技术题，后两堆是这一轮要你答的技术题的输入。你改一条答案，它沿依赖边重算下游，哪几题要重判一眼看得出。

agent 能查到的事实，它先查完，不推给你。选项在 Grok Bot 的对话里点，bot 把答案写回工单，调度器下一轮读到。

不回就停在「等你定」，每 24 小时提醒一次，它不猜。猜错了返工更贵。

这一步估计约三分钟，没实测。

### 二、拆票：扫一眼就点

spec 由你手动跑 `to-spec` 写，拆票由机器做。拆完给你一屏：接缝、票单、每票的验收条件。

点「按这个拆」，或者改一条再点。这是视频里「人批准拆分」那一步。这一下长期保留。

这一步估计约两分钟，没实测。

### 三、客户卡住：回一句就够

客户在 `dsh` 里卡住，或答不上，会找客服。通道微信为主，电话兜底，话术见 `customer-kit/安装步骤.md` 的「客服带话」。比如客户问「送货费怎么算，我不敢写」，你回一句，把定下的答案告诉他。

客户说不懂的技术题，agent 已按推荐答案往下问，记进 `.scratch/{需求名}/pending.md`，并告诉客户「开工前会有人确认」。这些在开工前由你确认。

这一步不阻塞工厂。你不回他，单子也照样往下走，只是答案会缺一块。

### 四、每天早上抽样：合并之后看

工厂合主干之前，每个 PR 有一队验证 agent，没写过这份代码，像真实用户那样点来点去找回归。合并前还有一次评审，分标准和 spec 两轴。两样都过了，工厂自己合主干，部署，客户收到地址。你不用点。

你每天早上看前一天合进主干的单：

1. 读 /pr 正文和提交历史，不逐行读 diff。
2. 先看单向门、影响范围大、验证没覆盖到的。「人工判断」条目写在 PR 正文里，也先看。
3. 看模式，不看单个。一个 agent 走捷径是个案。多个 agent 走同一条捷径，就改环境。
4. 发现问题：先回滚，另开分支改，不重开单。记一条：这次的错，本该在哪一层被挡住。

### 五、出事：只有五种情况会叫你

- 同一张票试了三圈还没进展。
- 花的钱超过额度。
- 碰到禁区。判据是两句话：这段改动能不能验证，出事了能不能回滚。有一条答不能，就停。
- 同类问题跨票出现两次，它先自动加一条规则重跑，还不过就叫你。新规则要在出错那次的改动上亮红灯，做不到就不自动加，直接叫你。
- 验证队和评审修了还是过不了。当环境问题，停这条线，通知你，附现象和试过的办法。你修环境，不替这个 PR 改结论。

你到了现场，能做的三件事：让它再试一次、换个做法、或者停掉等白天。

## 一天里，你出现几刻

拿 `docs/工厂流程.md` 里那单 B 店举例。钟点是示意，没有实测。

**10:00** 客户在上传页拖入 zip，勾了「已问完」，服务器校验通过。

**10:04** 服务器建单、建仓。调度器读到新单，经 Grok Bot 推你：`B 店 · 预约送货 · 已进队列`。这条不用动。

**10:20** 你打开 Grok Bot，补缺口。每项带推荐。这单撞上三件：服务器共用还是单独、登录用手机号还是邮箱、要不要在线支付。你答三个「是」。估计三分钟。

**10:22** 你问 `ask-matt` 能不能 `to-spec`，能，手动跑。spec 和五张票写完。

**10:24** 你在 Grok Bot 里扫一眼票单，点「按这个拆」。估计两分钟。

**10:25** 调度器开工，先跑一单。之后一小时你在干别的。

**11:40** 四样证据齐，子票合进需求分支。你不用动。

**11:41** 验证队和评审都过了，工厂自己合主干，部署。你不用动。

**11:42** 客户收到地址。

**第二天早上** 你抽样看前一天合进主干的单。客户要加导出 Excel，开新单，回到 10:20。

如果中间没出事，这单你一共花了约五分钟，另加每天早上的抽样。

## 什么永远不自动

三条边界。

第一，五类技术问题不自动猜。理由很实在：猜错了返工，返工比等你贵。

第二，验证队和评审过不了的 PR，不自己合，也不自己放宽检查。放宽任何一道检查，要验证者的证明，再由你复签。

第三，涉及钱、数据、对外动作的业务参数，不当假设处理，要阻塞等客户答。其余可逆的参数，agent 写成「假设」并标记，客户事后由你经客服带话确认，怎么带归 #52。（推断）

## 还没定的

- 状态标签已定（#5 的 Q4）：四个 `状态:*`，含义和迁移见 `docs/工单模型.md`。待办不做看板，状态只留在 GitHub 的标签上，调度器靠标签判断该不该动。
- 上传页有没有「急」勾选，没定。方案第六节只列登录态、「已问完」和隐私提示；简称、邮箱由账号带出。
- Grok Bot 当收件箱稳不稳，没验。审批过期、例程被暂停、用量限流，都可能让提醒到不了你。邮件兜底也没验。
- 工厂自己合主干时，要不要推你一条。地图 #11 原来要求合并前推一条，不能不让你知道。正稿 E1 改成自己合，没写通知。
- 每天早上抽样，要不要有提醒。

## 和视频比，人在哪

视频默认 spec 和票都经人看过。拆票技能里写着「迭代到用户批准拆分为止」。然后人看 PR，抽空跑 retro。

我们把人挪到前后两头。前面是补缺口和拆票。后面是每天早上抽样。中间不出现。

挪的理由有两个。客户不懂技术，spec 和票没法让他批，只能你扫一眼。合并照素材：每个 PR 一队验证 agent，合并前评审，过了自己合，人在合并之后看模式，不看单个。

PR 里那层「这一改有多险」的信息，补成两栏：单向门还是双向门、影响范围。见 `docs/工厂流程.md` 八节 E1。单向门不再让工厂停下，它决定你抽样先看哪些。
