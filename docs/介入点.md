## 各自看什么

### 一、补缺口：一次列完，逐项答「是」

回传校验通过，仓库和工单建好。形式和客户那边一样，是一轮 grilling。每项带推荐答案，措辞让你答「是」就等于接受。

补缺口 Agent 先解压回传件，读 Mac 上的 `问题树.md`、`pending.md`、`需求草稿.md`、`验收场景.md` 和 `GLOSSARY.md`，把题列好。你不用解压，不用开题单，也不用跑 `question-tree`。

这一轮里要你定的有六类：

1. 五类技术选择：技术栈、部署到哪、第三方服务与账号、数据怎么存、每月花多少。客户的答案当推荐值。客户问部署到哪，标准答案是「我们管理的香港服务器，客户不用买、不用备案、不用碰 DNS」；只支持默认技术栈（Next.js + Postgres），客户自带服务器 v1 不做。
2. A2 里标了「你答」「你最后定」的题。
3. 合规：收不收个人信息，接不接支付。默认都不。
4. 接缝：测试打在哪一层，理想数量是一个。无人值守时没有客户可问，由你代答。
5. 词汇表：先读客户工作区根目录的 `GLOSSARY.md`，你确认命名后写进客户仓 `GLOSSARY.md`。
6. 查重：先搜 open 和 closed 工单。

补缺口前先看问题树：补缺口 Agent 跑 `question-tree`，看三堆。没定的、客户不懂走了推荐答案的、待核实的技术题，后两堆是这一轮要你答的技术题的输入。你给新答案，它沿依赖边重算下游，哪几题要重判一眼看得出。

补缺口 Agent 能查到的事实，它先查完，不推给你。Grok Bot 只把题和推荐答案推到手机。你在 Orca 里确认，补缺口 Agent 写一条 `点头：补缺口` 评论：最终答案、问题树重判、正文影响三段。调度器下一轮读到。其余单把父工单改成 `状态:排队中`，等 to-spec；小需求由它先建一张实现票，父工单直接改成 `状态:开发中`，点火。你要重问，就写 `驳回：补缺口`，它重列。以后只读父工单的人，看这条评论就知道你答了什么、哪几题被作废或要补问。Mac 上的问题树文件是工作副本。

不回就停在「等你定」，每 24 小时提醒一次，它不猜。猜错了返工更贵。

这一步估计约三分钟，没实测。

### 二、拆票：扫一眼就点

小需求没有这一步：只有一张实现票，在补缺口时已经建好。

spec 由你手动跑 `to-spec` 写，拆票由调度器叫 agent 做。拆完在 Orca 里给你一屏：接缝、票单、每票的验收条件。

你说可以，agent 写一条 `点头：拆票` 评论，调度器读到才点火。要改就驳回，agent 重拆。这是视频里「人批准拆分」那一步。这一下长期保留。

这一步估计约两分钟，没实测。

### 三、需要你答：看 trail 里的 gate 行

验证或收尾时，遇到只有你能批的事，实现者在 PR 分支的 `.audit/<票号>.tsv` 写一条 gate 行：问什么、为什么问、推荐怎么做、PR 链接。调度器读到 `result=open`，经 Grok Bot 推你。

你在 Orca 里答：同意、不同意，或先搁置。实现者补一条 `answered` 或 `parked`，调度器停止提醒。搁置的缺口留在 trail 里，最后的报告会列出来。

典型的一处是 `correct` 给检查加例外。`interrogate` 和 `no-comments` 的常规问题由调用方 agent 答，只有它们也定不了才升级给你。

不回就停在这条线，每 24 小时提醒一次。

### 四、客户卡住：回一句就够

客户在 `dsh` 里卡住，或答不上，会找客服。通道微信为主，电话兜底，话术见 `customer-kit/安装步骤.md` 的「客服带话」。比如客户问「送货费怎么算，我不敢写」，你回一句，把定下的答案告诉他。

客户说不懂的技术题，agent 已按推荐答案往下问，记进 `.scratch/{需求名}/pending.md`，并告诉客户「开工前会有人确认」。这些在开工前由你确认。

这一步不阻塞工厂。你不回他，单子也照样往下走，只是答案会缺一块。

### 五、每天早上抽样：合并之后看

工厂合主干之前，每个 PR 有一队验证 agent，没写过这份代码，像真实顾客那样点来点去找回归。合并前还有一次评审，分标准和 spec 两轴。两样都过了，工厂自己合主干，部署，客户收到地址。你不用点。

你每天早上看前一天合进主干的单：

1. 读 /pr 正文和提交历史，不逐行读 diff。
2. 先看单向门、影响范围大、验证没覆盖到的。「人工判断」条目写在 PR 正文里，也先看。
3. 看模式，不看单个。一个 agent 走捷径是个案。多个 agent 走同一条捷径，就改环境。
4. 发现问题：先回滚，另开分支改，不重开单。记一条：这次的错，本该在哪一层被挡住。

### 六、出事：只有五种情况会叫你

- 同一张票试了三圈还没进展。
- 花的钱超过额度。
- 碰到禁区。判据是两句话：这段改动能不能验证，出事了能不能回滚。有一条答不能，就停。
- 同类问题跨票出现两次，它先自动加一条规则重跑，还不过就叫你。新规则要在出错那次的改动上亮红灯，做不到就不自动加，直接叫你。
- 验证队和评审报的问题，实现者修了还是过不了。当环境问题，停这条线，通知你，附现象和试过的办法。你修环境，不替这个 PR 改结论。

你到了现场，能做的三件事：让它再试一次、换个做法、或者停掉等白天。

## 什么永远不自动

三条边界。

第一，五类技术问题不自动猜。理由很实在：猜错了返工，返工比等你贵。

第二，验证队和评审过不了的 PR，不自己合，也不自己放宽检查。放宽任何一道检查，要验证者的证明，再由你复签。

第三，涉及钱、数据、对外动作的业务参数，不当假设处理，要阻塞等客户答。其余可逆的参数，agent 写成「假设」并标记，客户事后由你经客服带话确认，怎么带归 #52。（推断）

## 还没定的

- 状态标签已定（#5 的 Q4）：四个 `状态:*`，含义和迁移见 `docs/工单模型.md`。待办不做看板，状态只留在 GitHub 的标签上，调度器靠标签判断该不该动。
- 上传页「急」勾选已定（2026-11-13，《人工兜底的 SLA 与紧急分级》）：不做。人工兜底不设紧急分级；方案第六节只列登录态、「已问完」和隐私提示；简称、邮箱由账号带出。
- Grok Bot 当收件箱稳不稳，没验。审批过期、例程被暂停、用量限流，都可能让提醒到不了你。邮件兜底也没验。

## 和视频比，人在哪

视频默认 spec 和票都经人看过。拆票技能里写着「迭代到用户批准拆分为止」。然后人看 PR，抽空跑 retro。

我们把人挪到前后两头。前面是补缺口和拆票，中间可能有验证问答，后面是每天早上抽样。

挪的理由有两个。客户不懂技术，spec 和票没法让他批，只能你扫一眼。合并照素材：每个 PR 一队验证 agent，合并前评审，过了自己合，人在合并之后看模式，不看单个。

PR 里那层「这一改有多险」的信息，补成两栏：单向门还是双向门、影响范围。见 `docs/工厂流程.md` 八节 E1。单向门不再让工厂停下，它决定你抽样先看哪些。
