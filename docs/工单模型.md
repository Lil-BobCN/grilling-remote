# 工单模型

一张单一张父工单，一个垂直切片一张子票。四档状态挂在标签上，只有调度器能改。

本文是建仓脚本、拆票 agent、调度器三方的契约。流程在 `docs/工厂流程.md` 第五节 B1，写法看这里。演练记录见 `docs/工单模型-演练记录.md`。

## 一、一单一父工单

| 层级 | 是什么 | 对应什么 | 落在哪 |
| --- | --- | --- | --- |
| 父工单 | 一张单 | 一条需求分支 | 客户仓的一张 issue |
| 子票 | 一个垂直切片 | 一个 worktree、一次 Sandcastle run | 父工单的 sub-issue |

- 一个软件一个仓，工单和代码同仓。同一软件的后续单复用原仓。
- 子票必须挂在父工单下面，不能散在别处。
- 子票挂了，重开一张子票，父工单不动。
- 父工单关了，这张单才算完。

小需求也用这张表。父工单下只挂一张实现子票，区别只在子票从哪来：其余单由拆票 agent 拆，小需求由补缺口 Agent 在补缺口点头时建一张。小需求跳过 spec 和拆票，不跳过子票这一层。

## 二、父工单

标题用客户那句话，不改写。

正文五段。`##` 标题固定，顺序固定，建仓脚本照着填，`to-spec` 照着读。标题改字，这两步都找不到。

不用 `.github/ISSUE_TEMPLATE/`。建单的是服务器上的脚本，客户不建 issue，模板放仓库里没人会点。

```markdown
## 客户原话

> 「……」

日期：2026-11-07

## 客户确认的结论

- ……

## 验收条件

- [ ] ……

## 不做清单

- 无

## 需求全文

- 客户简称：jiefang-shuiguo
- 需求名：yuyue-quhuo
- 全文：https://github.com/<owner>/<repo>/tree/main/docs/requirements/yuyue-quhuo/
```

| 段 | 从哪来 | 怎么写 |
| --- | --- | --- |
| 客户原话 | 上传包里客户说的那句话 | 引号原文，不改写成术语，带日期。走地图时看 `问答记录.md` 开头的 `## 客户原话`；小需求看 `需求草稿.md` 第 1 段第一条 |
| 客户确认的结论 | 小需求取 `需求草稿.md` 的「已经定下的」，其余取 `map.md` 的 Decisions so far | 一行一条，一条一个决定；取冒号后面那句，到句末；链接不抄，行末「按第 N 张改」不抄 |
| 验收条件 | 客户确认过的 `验收场景.md` 条目 | 一条一句，能当场演示；写不出可测条目的，句末标「人工判断」 |
| 不做清单 | 客户说过不做的、这次明确排除的 | 没有就写「无」，整段不删。走地图时看 `map.md` 的 Out of scope；小需求看 `需求草稿.md` 第 5 段 |
| 需求全文 | 上传包 `.scratch/<需求名>/` | 建仓脚本原样拷进客户仓 `docs/requirements/<需求名>/`，这里给完整链接 |

拷进仓的目录开头写一句：「回传快照，以父工单和 spec 为准，不作为决策来源。」回传件是上传那一刻的快照。之后补缺口和写 spec 时的改动不回写快照，不标一句，读的人会把快照当成现行结论。

链接写完整的 URL，不写相对路径。相对路径在 issue 正文里能不能点，没验过，见演练记录。

没被客户确认的想法不进正文，放进需求全文。

## 三、子票

标题写一条切片做完后客户能看到什么，不写实现步骤。一张子票是一片穿过每一层的东西，单独能演示，装得进一个会话。

正文三段：

```markdown
## 垂直切片

顾客打开链接，看到今天的水果、价格和卖完的。

## 验收条件

- [ ] 打开链接，看到当天水果的名单。

## 阻塞

Blocked by: #12
```

- 验收条件只能从父工单的「验收条件」里拆。要新造，先回父工单补一条。
- 阻塞边以 GitHub 原生依赖为准。正文这一行建票时照抄，之后边变了回来改这一行。
- 没有阻塞，整段删掉，不留「Blocked by: 无」。

### 小需求的实现票

小需求跳过 spec 和拆票，但仍要一张子票。没有子票，就没有 worktree、证据和合并的落点。

- 谁建：补缺口 Agent。运营者在 C1 确认完答案，agent 先建这张票，再写 `点头：补缺口`。
- 标题：用父工单标题，也就是客户那句话。
- 正文：`## 垂直切片` 写「整张小需求一次做完」；`## 验收条件` 逐条抄父工单的验收条件；不写 `## 阻塞`。
- 建票时打 `状态:排队中`。这是建票那一刻的例外，和拆票 agent 建子票一样。
- 父工单打 `大小:小需求`，由建仓脚本建父工单时写，之后不改。

## 四、四档状态

四个标签，名字、颜色、说明固定：

| 标签 | 颜色 | GitHub 说明 | 父工单上的意思 | 子票上的意思 |
| --- | --- | --- | --- | --- |
| `状态:已提交` | `#ededed` | 已建单，等技术闸门 | 闸门没答 | 不出现 |
| `状态:排队中` | `#fbca04` | 轮到了，等点火 | 闸门答完，等 spec、等拆票点头 | 拆出来了，等点火 |
| `状态:开发中` | `#1d76db` | 正在跑 | 有子票在跑 | 正在跑 |
| `状态:待验收` | `#0e8a16` | 活干完了，等下一步确认 | 子票全合完，等客户点头 | 四样证据齐，等合并 |

建标签：

```bash
gh label create "状态:已提交" --color ededed --description "已建单，等技术闸门"
gh label create "状态:排队中" --color fbca04 --description "轮到了，等点火"
gh label create "状态:开发中" --color 1d76db --description "正在跑"
gh label create "状态:待验收" --color 0e8a16 --description "活干完了，等下一步确认"
```

**谁写。** 只有调度器。三处例外，都发生在建票那一刻：建仓脚本建父工单时打 `状态:已提交`，拆票 agent 建子票时打 `状态:排队中`，补缺口 Agent 给小需求建实现票时打 `状态:排队中`。建完之后谁都不再碰标签，agent 只把证据写进评论。

标签只表示走到哪一档。spec 在不在、子票拆没拆、拆票点没点头，调度器另看文件和子票，以及父工单评论里的关口标记，不从标签里猜。

`大小:小需求` 不是状态标签。建仓脚本建父工单时，看回传包里是 `需求草稿.md` 就写上；其余单不写。只有建仓脚本写这一下，之后不改。调度器靠它认出小需求。

## 五、迁移

父工单：

| 从 | 到 | 触发 | 谁做 | 调度器顺手做什么 |
| --- | --- | --- | --- | --- |
| 无 | `已提交` | 服务器校验通过，建完仓建单 | 建仓脚本 | 无 |
| `已提交` | `排队中` | 其余单；最新一条关口评论是 `点头：补缺口` | 调度器 | 推「该跑 to-spec」一条，见 `docs/通知与事件表.md` |
| `已提交` | `开发中` | 小需求；最新一条关口评论是 `点头：补缺口`，有一张 open 子票 | 调度器 | 点火那张子票 |
| `排队中` | `开发中` | 其余单；最新一条关口评论是 `点头：拆票`，第一张子票点火 | 调度器 | 叫 Sandcastle |
| `开发中` | `待验收` | 子票全合进需求分支，评审过 | 调度器 | 推「自己合并」一条，见 `docs/通知与事件表.md` |
| `待验收` | `开发中` | 客户驳回 | 调度器，读到你写的 `驳回：` 评论 | 建一张修复子票 |
| `待验收` | 关闭 | 客户点头 | 运营者关票 | 无 |

关票就是客户页的「已完成」信号：页面取关闭时间，不另写评论。关票前没到过「待客户验收」的，不显示已完成。

子票：

| 从 | 到 | 触发 | 谁做 |
| --- | --- | --- | --- |
| 无 | `排队中` | 拆票时建出来；小需求在补缺口点头时建 | 拆票 agent；小需求是补缺口 Agent |
| `排队中` | `开发中` | 点火 | 调度器 |
| `开发中` | `待验收` | 四样证据齐 | 调度器 |
| `待验收` | 关闭 | 合进需求分支 | 调度器 |
| `开发中` | `开发中`，加 `点火超时` | 点火两分钟没回执 | 调度器 |

`点火超时` 是告警标签，不改状态。调度器不自动补点，等人，见 `docs/adr/0005-调度器直接点火.md`。

### 人工关口的信号

补缺口和拆票两个人工关口的提案、点头和驳回，都写成父工单的评论。第一行用固定词：

| 写什么 | 谁写 | 什么时候 |
| --- | --- | --- |
| `提案：补缺口` | 补缺口 Agent | 父工单建好，闸门题和推荐答案列完 |
| `点头：补缺口` | 补缺口 Agent | 运营者在 Orca 里答完并确认，后面写最终答案和问题树重判 |
| `驳回：补缺口` | 补缺口 Agent | 运营者要求重问，后面写理由 |
| `提案：拆票` | 拆票 agent | 子票建好，一行一张票 |
| `点头：拆票` | 拆票 agent | 运营者在 Orca 里看完票单并确认 |
| `驳回：拆票` | 拆票 agent | 运营者要求重拆，后面写理由 |

Grok Bot 只把题、票单和提醒推到手机，不写评论。最终决定在 Mac 的 Orca 里做，agent 替运营者落笔。同一关口只看最新一条评论，新的 `提案：`、`驳回：` 或 `点头：` 盖掉旧的 `点头：`。

`点头：补缺口` 的正文分三段：

```markdown
点头：补缺口

## 最终答案

- 技术栈：Next.js + Postgres
- 树 3「服务器放国内还是海外」：海外
- 树 4「要不要备案」：作废

## 问题树重判

| 日期 | 改了哪条 | 波及 | 判定 |
| --- | --- | --- | --- |
| 2026-11-15 | 3 国内→海外 | 4 | 4 作废 |

## 正文影响

- 「要在线支付」（客户确认的结论）：树 4 作废，正文未改，以本条评论为准。
```

- `## 最终答案` 一行一条，带题号或类别。
- `## 问题树重判` 从 Mac 的 `问题树.md` 的 `## 重判记录` 原样抄，不概括。
- `## 正文影响` 只在重判作废或改变正文某条时写，引原文，写「正文未改，以本条评论为准」；没有写「无」。
- 父工单正文不改。重判只写评论，正文少一个写入者。
- 闸门评论是数据记录，不受 `AGENTS.md` 的 400 字限制，不拆成两条。
- 父工单最新一条 `点头：补缺口` 为准；Mac 上的 `问题树.md`、`pending.md`、`需求草稿.md` 是工作副本。两处对不上，停下报运营者，两边都不改。
- `to-spec` 前改答案：重写一条 `点头：补缺口`，最新一条盖掉旧一条。`to-spec` 后改答案：走改口。

小需求只用补缺口这一次。补缺口 Agent 写 `提案：补缺口` 时，在评论末尾加一节 `## 实现票`，列出那张票的标题和验收条件；运营者确认后，agent 先建子票，再写 `点头：补缺口`，末行写 `实现票：#N`。小需求没有 `提案：拆票` 和 `点头：拆票`。

调度器每 30 秒读一次父工单的评论：

- 其余单；`状态:已提交`，最新一条关口评论是 `点头：补缺口`：改成 `状态:排队中`，推「该跑 to-spec」一条。
- 其余单；`状态:排队中`，仓库里有 spec，没有子票：叫拆票 agent 跑 `to-tickets`。
- 其余单；`状态:排队中`，仓库里有 spec，有 open 子票，最新一条关口评论是 `点头：拆票`：改成 `状态:开发中`，点火第一张没有阻塞的子票。
- 小需求；`状态:已提交`，最新一条关口评论是 `点头：补缺口`，有一张 open 子票：改成 `状态:开发中`，点火那张子票。
- 小需求；`状态:已提交`，最新一条关口评论是 `点头：补缺口`，没有 open 子票：打 `needs-info`，推「需要人看」一条，不猜。
- 小需求却是 `状态:排队中`：状态对不上，打 `needs-info`，推「需要人看」一条，不猜。
- 最新一条关口评论是 `提案：` 或 `驳回：`：停，等下一次点头。

状态对不上任何一行，调度器不猜，打 `needs-info`，推「需要人看」一条。

## 六、驳回

客户不要这次做出来的东西：

1. 客户告诉运营者。客户看不到工单，走微信或电话。
2. 运营者在父工单写一条评论，`驳回：` 开头，后面跟客户原话。
3. 调度器下一轮读到，把父工单从 `待验收` 改回 `开发中`，另开一张子票。子票标题取驳回原话，验收条件写驳回里点名的那几条。
4. 不重开父工单，不把驳回当新需求再开一张。
5. 修复走新分支、新 worktree，合并仍进原需求分支。

小需求同样走这一节。父工单保持 `大小:小需求`，修复子票由调度器建。

## 七、改口

客户改了主意，东西还要做：

1. 运营者在父工单追加一条评论，`改口：` 开头，写原话，再把被改掉的旧条目原文贴进同一条评论。
2. 改父工单正文里受影响的「客户确认的结论」和「验收条件」。
3. 不新建 issue。spec 已经成形，改完重跑 `to-spec`。

补缺口答案的改动分两个窗口：`to-spec` 前，不写 `改口：`，重写一条 `点头：补缺口`；`to-spec` 后，走本节，评论里写明是运营者改的技术答案，旧答案和新答案都贴出来，重跑 `to-spec`。

分界：还在做，说清楚改哪几条，是改口；做完了不要，是驳回。加新功能不走改口。回传前和 to-spec 前这两个窗口之外，加功能开新单，见 `docs/客户工作区方案.md` 第八节。

小需求没有 spec，改口不重跑 `to-spec`。改父工单正文后，实现票继续还是重开，还没定，见 I-0130。

## 八、和五个 triage 标签的关系

客户仓照样有那五个标签，见 `docs/工厂流程.md` 第九节第 4、5 项。它们管人工处理，不管状态：

| 标签 | 谁用 | 什么时候 |
| --- | --- | --- |
| `ready-for-agent` | spec | `to-spec` 发 spec 时打。子票不打 |
| `needs-info` | 调度器 | 状态对不上任何一行，或卡住要人看 |
| `wontfix` | 拆票 agent | 决定不做的切片，打上直接关 |
| `needs-triage`、`ready-for-human` | 人工接管 | v1 不走 |

子票只挂 `状态:*`，不挂 `ready-for-agent`。两边意思一样，都能写就会写岔。
