# 工单模型

> 状态：现行

一张单一张父工单，一个垂直切片一张子票。客户仓另有一张地图 issue，和父工单平级，挂决定票。四档状态只挂在父工单和实现子票上，只有调度器能改。

本文是建仓脚本、补缺口 Agent、拆票 agent、调度器四方的契约。流程在 `docs/工厂流程.md` 第七节 B1 和第八节 C1，写法看这里。演练记录见 `docs/research/工单模型-演练记录.md`。

## 一、一单一父工单

| 层级 | 是什么 | 对应什么 | 落在哪 |
| --- | --- | --- | --- |
| 父工单 | 一张单 | 一条需求分支 | 客户仓的一张 issue |
| 子票 | 一个垂直切片 | 一个 worktree、一次 Sandcastle run | 父工单的 sub-issue |
| 地图 issue | 客户的决策工作副本，和父工单平级 | 一张客户 map | 客户仓的另一张 issue，正文六段 |
| 决定票 | 地图上的一个决定 | 一次对话 | 地图 issue 的 sub-issue |

- 一个软件一个仓，工单和代码同仓。同一软件的后续单复用原仓。
- 实现子票必须挂在父工单下面，不能散在别处。决定票挂在它的地图 issue 下面。
- 地图 issue 和父工单在正文里互相链接。
- 两层票别混：父工单下面挂实现子票，走 `状态:*` 和 `Sandcastle`；地图 issue 下面挂决定票，走 `wayfinder:*`。调度器只认前一层，见第八节。
- spec 是独立 issue，不挂父工单，也不挂子票。
- 子票挂了，重开一张子票，父工单不动。
- 父工单关了，这张单才算完。

小需求也用这张表。父工单下只挂一张实现子票，区别只在子票从哪来：其余单由拆票 agent 拆，小需求由补缺口 Agent 在补缺口点头时建一张。小需求跳过 spec 和拆票，不跳过子票这一层。

## 二、父工单

标题用客户那句话，不改写。

正文五段。`##` 标题固定，顺序固定，建仓脚本照着填，`to-spec` 照着读。标题改字，这两步都找不到。

不用 `.github/ISSUE_TEMPLATE/`。建单的是服务器上的脚本，客户不建 issue，模板放仓库里没人会点。

```markdown
## 客户原话

> 「……」

日期：2026-11-07

## 客户确认的结论

- ……

## 验收条件

- [ ] ……

## 不做清单

- 无

## 需求全文

- 客户简称：jiefang-shuiguo
- 需求名：yuyue-quhuo
- 全文：https://github.com/<owner>/<repo>/tree/main/docs/requirements/yuyue-quhuo/
```

| 段 | 从哪来 | 怎么写 |
| --- | --- | --- |
| 客户原话 | 上传包里客户说的那句话 | 引号原文，不改写成术语，带日期。走地图时看 `问答记录.md` 开头的 `## 客户原话`；小需求看 `需求草稿.md` 第 1 段第一条 |
| 客户确认的结论 | 小需求取 `需求草稿.md` 的「已经定下的」，其余取 `map.md` 的 Decisions so far | 一行一条，一条一个决定；取冒号后面那句，到句末；链接不抄，行末「按第 N 张改」不抄 |
| 验收条件 | 客户确认过的 `验收场景.md` 条目 | 一条一句，能当场演示；写不出可测条目的，句末标「人工判断」；行末「按第 N 张改」不抄 |
| 不做清单 | 客户说过不做的、这次明确排除的 | 没有就写「无」，整段不删。走地图时看 `map.md` 的 Out of scope；小需求看 `需求草稿.md` 第 5 段 |
| 需求全文 | 上传包 `.scratch/<需求名>/` | 建仓脚本原样拷进客户仓 `docs/requirements/<需求名>/`，这里给完整链接。补缺口 Agent 建好地图后，在这一段补一行 `- 地图：<地图 issue 链接>` |

拷进仓的目录开头写一句：「回传快照，以父工单和 spec 为准，不作为决策来源。」回传件是上传那一刻的快照。之后补缺口和写 spec 时的改动不回写快照，不标一句，读的人会把快照当成现行结论。

链接写完整的 URL，不写相对路径。相对路径在 issue 正文里能不能点，没验过，见演练记录。

没被客户确认的想法不进正文，放进需求全文。

## 三、子票和决定票

标题写一条切片做完后客户能看到什么，不写实现步骤。一张子票是一片穿过每一层的东西，单独能演示，装得进一个会话。

正文三段：

```markdown
## 垂直切片

顾客打开链接，看到今天的水果、价格和卖完的。

## 验收条件

- [ ] 打开链接，看到当天水果的名单。

## 阻塞

Blocked by: #12
```

- 验收条件只能从父工单的「验收条件」里拆。要新造，先回父工单补一条。
- 阻塞边以 GitHub 原生依赖为准。正文这一行建票时照抄，之后边变了回来改这一行。
- 没有阻塞，整段删掉，不留「Blocked by: 无」。

### 决定票

地图 issue 下面挂决定票。它也是 sub-issue，但不是实现子票：一个客户决定一张，对应回传里的 `issues/NN-*.md`。

- 标题保留客户文件的编号和名字，形如 `01 空档怎么放`。重传时靠开头的编号配对。
- 正文照票文件抄：`## Question` 原样搬，票头的 `Type:`、`Blocked by:` 和 `Status:` 照格式搬。不改写。
- 票里的 `## 评论` 每条抄成一条 issue 评论。`## 结论` 先留着，等这张票做完，抄成一条结论评论，再关票。
- 地图 issue 的 `Notes` 段第一行写 `- 父工单：<链接>`。
- 挂 `wayfinder:<type>`，不挂 `状态:*`、`ready-for-agent`、`Sandcastle`。调度器不当它是实现活。
- 旧包里的 `问题树.md` 不读。它留在 `docs/requirements/<需求名>/` 的快照里，只作历史。

### 小需求的实现票

小需求跳过 spec 和拆票，但仍要一张子票。没有子票，就没有 worktree、证据和合并的落点。

- 谁建：补缺口 Agent。运营者在 C1 确认完答案，agent 先建这张票，再写 `点头：补缺口`。
- 标题：用父工单标题，也就是客户那句话。
- 正文：`## 垂直切片` 写「整张小需求一次做完」；`## 验收条件` 逐条抄父工单的验收条件；不写 `## 阻塞`。
- 建票时打 `状态:排队中`。这是建票那一刻的例外，和拆票 agent 建子票一样。
- 父工单打 `大小:小需求`，由建仓脚本建父工单时写，之后不改。

## 四、四档状态

四个标签，名字、颜色、说明固定：

| 标签 | 颜色 | GitHub 说明 | 父工单上的意思 | 实现子票上的意思 |
| --- | --- | --- | --- | --- |
| `状态:已提交` | `#ededed` | 已建单，等技术闸门 | 闸门没答 | 不出现 |
| `状态:排队中` | `#fbca04` | 轮到了，等点火 | 闸门答完，等 spec、等拆票点头 | 拆出来了，等点火 |
| `状态:开发中` | `#1d76db` | 正在跑 | 有子票在跑 | 正在跑 |
| `状态:待验收` | `#0e8a16` | 活干完了，等下一步确认 | 子票全合完，等客户点头 | 四样证据齐，等合并 |

建标签：

```bash
gh label create "状态:已提交" --color ededed --description "已建单，等技术闸门"
gh label create "状态:排队中" --color fbca04 --description "轮到了，等点火"
gh label create "状态:开发中" --color 1d76db --description "正在跑"
gh label create "状态:待验收" --color 0e8a16 --description "活干完了，等下一步确认"
```

**谁写。** 只有调度器。三处例外，都发生在建票那一刻：建仓脚本建父工单时打 `状态:已提交`，拆票 agent 建子票时打 `状态:排队中`，补缺口 Agent 给小需求建实现票时打 `状态:排队中`。建完之后谁都不再碰标签，agent 只把证据写进评论。

标签只表示走到哪一档。spec 在不在、子票拆没拆、拆票点没点头，调度器另看文件和子票，以及父工单评论里的关口标记，不从标签里猜。

`大小:小需求` 不是状态标签。建仓脚本建父工单时，看回传包里是 `需求草稿.md` 就写上；其余单不写。只有建仓脚本写这一下，之后不改。调度器靠它认出小需求。

## 五、迁移

父工单：

| 从 | 到 | 触发 | 谁做 | 调度器顺手做什么 |
| --- | --- | --- | --- | --- |
| 无 | `已提交` | 服务器校验通过，建完仓建单 | 建仓脚本 | 无 |
| `已提交` | `排队中` | 其余单；最新一条关口评论是 `点头：补缺口` | 调度器 | 推「该跑 to-spec」一条，见 `docs/通知.md` |
| `已提交` | `开发中` | 小需求；最新一条关口评论是 `点头：补缺口`，有一张 open 子票 | 调度器 | 点火那张子票 |
| `排队中` | `开发中` | 其余单；最新一条关口评论是 `点头：拆票`，第一张子票点火 | 调度器 | 叫 Sandcastle |
| `开发中` | `待验收` | 子票全合进需求分支，评审过 | 调度器 | 推「自己合并」一条，见 `docs/通知.md` |
| `待验收` | `开发中` | 客户驳回 | 调度器，读到你写的 `驳回：` 评论 | 建一张修复子票 |
| `待验收` | 关闭 | 客户点头 | 运营者关票 | 无 |

关票就是客户页的「已完成」信号：页面取关闭时间，不另写评论。关票前没到过「待客户验收」的，不显示已完成。

**锁单点。** `to-spec` 生成 spec 后，Agent 先报父工单状态和最新一条关口评论，再问运营者贴不贴 `ready-for-agent`。运营者确认没有新上传后，才发成 issue 并打标签；有新上传就不贴，丢掉这次 spec。从贴标签这一刻起单子锁住，改口和加功能走新单。没贴前 spec 不算数，调度器看不见，客户还能整包重传。

**队列标签。** 子票建出来只挂 `状态:排队中`。队列标签 `Sandcastle` 由调度器点火时贴给这一轮选中、没有未关闭阻塞的子票；子票进入 `状态:待验收` 或关闭后摘掉。不能用 `状态:排队中` 当队列标签：父工单在 `点头：补缺口` 到 `点头：拆票` 之间也挂它，会被一起捡走。点火前查有没有活，看子票状态和父工单评论，不看队列标签。spec 只挂 `ready-for-agent`，父工单只挂 `状态:*`。

实现子票：

| 从 | 到 | 触发 | 谁做 |
| --- | --- | --- | --- |
| 无 | `排队中` | 拆票草案点头后建出来；小需求在补缺口点头时建 | 拆票 agent；小需求是补缺口 Agent |
| `排队中` | `开发中` | 点火 | 调度器 |
| `开发中` | `待验收` | 四样证据齐 | 调度器 |
| `待验收` | 关闭 | 合进需求分支 | 调度器 |
| `开发中` | `开发中`，加 `点火超时` | 点火两分钟没回执 | 调度器 |

`点火超时` 是告警标签，不改状态。调度器不自动补点，等人，见 `docs/adr/0005-调度器直接点火.md`。

### 人工关口的信号

补缺口和拆票两个人工关口的提案、点头和驳回，加上重传时的改口，都写成父工单的评论。第一行用固定词：

| 写什么 | 谁写 | 什么时候 |
| --- | --- | --- |
| `提案：补缺口` | 补缺口 Agent | 父工单和地图 issue 建好，地图已还原，闸门题和推荐答案列完 |
| `点头：补缺口` | 补缺口 Agent | 地图补完，运营者在 Orca 里答完并确认，后面写最终答案和正文影响 |
| `驳回：补缺口` | 补缺口 Agent | 运营者要求重问，后面写理由 |
| `提案：拆票` | 拆票 agent | 子票草案列好，一行一张票；这时还没建票 |
| `点头：拆票` | 拆票 agent | 运营者在 Orca 里看完草案并确认；确认后拆票 agent 才建子票 |
| `驳回：拆票` | 拆票 agent | 运营者要求重拆，后面写理由 |
| `改口：` | 运营者 | 重传后父工单换成新包，写清这次改了什么 |

企业微信 Bot 只把提醒推到手机，不写评论；题和票单在 Orca 里看。最终决定在 Mac 的 Orca 里做，agent 替运营者落笔。同一关口只看最新一条评论，新的 `提案：`、`驳回：` 或 `点头：` 盖掉旧的 `点头：`。

`点头：补缺口` 的正文分两段：

```markdown
点头：补缺口

## 最终答案

- 技术栈：Next.js + Postgres
- 第 3 题「服务器放国内还是海外」：海外
- 第 4 题「要不要备案」：作废

## 正文影响

- 「要在线支付」（客户确认的结论）：第 4 题作废，正文未改，以本条评论为准。
```

- `## 最终答案` 一行一条，带题号或类别。
- `## 正文影响` 只在最终答案改掉正文某条时写，引原文，写「正文未改，以本条评论为准」；没有写「无」。
- 父工单正文不改。答案只写评论，正文少一个写入者。
- 闸门评论是数据记录，不受 `AGENTS.md` 的 400 字限制，不拆成两条。
- 父工单最新一条 `点头：补缺口` 为准；Mac 上的 `pending.md`、`需求草稿.md` 是回传原件，不改写；旧包里的 `问题树.md` 也不改写。两处对不上，停下报运营者，两边都不改。
- 写 `点头：补缺口` 前先查地图：`Not yet specified` 为空、开放的决定票都关了、未定事项处理完。没补完不写点头，提醒运营者。
- 地图上的最终答案看地图的 `Decisions so far` 和关闭的决定票；技术闸门的最终答案仍看最新一条 `点头：补缺口`。
- `to-spec` 前改答案：重写一条 `点头：补缺口`，最新一条盖掉旧一条。`to-spec` 后锁单，答案不再改，要改走新单，见第七节。

小需求只用补缺口这一次。补缺口 Agent 写 `提案：补缺口` 时，在评论末尾加一节 `## 实现票`，列出那张票的标题和验收条件；运营者确认后，agent 先建子票，再写 `点头：补缺口`，末行写 `实现票：#N`。小需求没有 `提案：拆票` 和 `点头：拆票`。

调度器每 30 秒读一次父工单的评论：

- 地图 issue 和它的决定票：不当实现活。执行票只从父工单的子票里挑；读地图 issue 只看 `重传：<日期>` 评论，推「重传地图已更新」。
- 其余单；`状态:已提交`，最新一条关口评论是 `点头：补缺口`：改成 `状态:排队中`，推「该跑 to-spec」一条。
- 其余单；`状态:排队中`，仓库里有 spec，没有子票：叫拆票 agent 跑 `to-tickets`。
- 其余单；`状态:排队中`，仓库里有 spec，有 open 子票，最新一条关口评论是 `点头：拆票`：改成 `状态:开发中`，点火第一张没有阻塞的子票。
- 小需求；`状态:已提交`，最新一条关口评论是 `点头：补缺口`，有一张 open 子票：改成 `状态:开发中`，点火那张子票。
- 小需求；`状态:已提交`，最新一条关口评论是 `点头：补缺口`，没有 open 子票：打 `needs-info`，推「需要人看」一条，不猜。
- 小需求却是 `状态:排队中`：状态对不上，打 `needs-info`，推「需要人看」一条，不猜。
- 最新一条关口评论是 `提案：` 或 `驳回：`：停，等下一次点头。

状态对不上任何一行，调度器不猜，打 `needs-info`，推「需要人看」一条。

## 六、驳回

客户不要这次做出来的东西：

1. 客户告诉运营者。客户看不到工单，走微信或电话。
2. 运营者在父工单写一条评论，`驳回：` 开头，后面跟客户原话。
3. 调度器下一轮读到，把父工单从 `待验收` 改回 `开发中`，另开一张子票。子票标题取驳回原话，验收条件写驳回里点名的那几条。
4. 不重开父工单，不把驳回当新需求再开一张。
5. 修复走新分支、新 worktree，合并仍进原需求分支。

小需求同样走这一节，父工单保持 `大小:小需求`，修复子票由调度器建。判据是交付结果和父工单的「客户确认的结论」「验收条件」对不上。对得上、客户只是改主意了，不走驳回，按第七节的小需求规则开新单。

## 七、改口

客户改主意、加功能，流程上是一件事：改的都是工作区。

- `to-spec` 没跑完：还是同一单。客户整包重传，服务器记新上传、重跑校验，订单页加一轮。父工单五段和 `docs/requirements/<需求名>/` 快照换成新包，父工单退回 `状态:已提交`，旧的 `提案：` 和 `点头：` 作废，补缺口 Agent 重跑。不新建仓和父工单。

  重跑时地图也跟着换。补缺口 Agent 拿新快照和当前地图 issue 比：按新包换地图正文；决定票按标题开头的编号配对，换正文，追加新评论，结论变了追加新结论；新包没有的票写 `作废：重传` 再关；新包新有的建出来。运营者自己开的票保留，逐张加 `待复查：重传`，在地图 issue 写一条 `重传：<日期>` 评论列出来，由运营者判去留。更新完写新的 `提案：补缺口`。调度器读到 `重传：<日期>` 评论，推一条「重传地图已更新」，见 `docs/通知.md`。
- `to-spec` 跑完、运营者贴了 `ready-for-agent`：锁单。之后的改口和加功能都等这一版交付；结果不符走驳回，改主意或加功能走新单，见 `docs/客户工作区.md` 第九节。

补缺口答案的改动也按这条分：`to-spec` 没跑完，整包重传；`to-spec` 跑完锁单，答案不再改，要改走新单。

分界（其余单）：还在做，说清楚改哪几条；做完了不要，是驳回。改口和加功能不再分开，都按上面的窗口走。

小需求没有 spec，也没有改口。加需求和改主意只有一个窗口：上传工作区之前。上传校验通过、建单之后这一单就锁住，补缺口问答和工厂构建期间都不再收新内容。补缺口只答技术问题，不是加需求的窗口。客户再提的加需求或改动，运营者直接答复，等这一版交付后开新单，按 `docs/客户工作区.md` 第九节的路走。当前工单不改正文，不开新票，实现票不关不重开。

## 八、和五个 triage 标签的关系

客户仓照样有那五个标签，见 `docs/工厂流程.md` 第十一节第 4、5 项。它们管人工处理，不管状态：

| 标签 | 谁用 | 什么时候 |
| --- | --- | --- |
| `ready-for-agent` | spec | `to-spec` 生成 spec 后，Agent 先问运营者贴不贴；贴了才发成 issue。这是锁单点。子票不打 |
| `needs-info` | 调度器 | 状态对不上任何一行，或卡住要人看 |
| `wontfix` | 拆票 agent | 决定不做的切片，打上直接关 |
| `needs-triage`、`ready-for-human` | 人工接管 | v1 不走 |

队列标签 `Sandcastle` 不在这五个里。它由调度器点火时贴给这一轮选中、没有未关闭阻塞的子票；父工单和 spec 不打。

子票建出来只挂 `状态:*`，不挂 `ready-for-agent`；`Sandcastle` 由调度器点火时贴。spec 只挂 `ready-for-agent`，父工单只挂 `状态:*`。

地图 issue 和决定票走另一套：地图挂 `wayfinder:map`，决定票挂 `wayfinder:<type>`。不挂 `状态:*`、`ready-for-agent`、`Sandcastle`，不进队列。调度器不把它们当实现活，见第五节。
