# 工单模型

一个需求一张父工单，一个垂直切片一张子票。四档状态挂在标签上，只有调度器能改。

本文是建仓脚本、拆票 agent、调度器三方的契约。流程在 `docs/工厂流程.md` 第五节 B1，写法看这里。演练记录见 `docs/工单模型-演练记录.md`。

## 一、一需求一单

| 层级 | 是什么 | 对应什么 | 落在哪 |
| --- | --- | --- | --- |
| 父工单 | 一个需求 | 一条需求分支 | 客户仓的一张 issue |
| 子票 | 一个垂直切片 | 一个 worktree、一次 Sandcastle run | 父工单的 sub-issue |

- 一客户一仓，工单和代码同仓。
- 子票必须挂在父工单下面，不能散在别处。
- 子票挂了，重开一张子票，父工单不动。
- 父工单关了，这个需求才算完。

## 二、父工单

标题用客户那句话，不改写。

正文五段。`##` 标题固定，顺序固定，建仓脚本照着填，`to-spec` 照着读。标题改字，这两步都找不到。

不用 `.github/ISSUE_TEMPLATE/`。建单的是服务器上的脚本，客户不建 issue，模板放仓库里没人会点。

```markdown
## 客户原话

> 「……」

日期：2026-11-07

## 客户确认的结论

- ……

## 验收条件

- [ ] ……

## 不做清单

- 无

## 需求全文

- 客户简称：jiefang-shuiguo
- 需求名：yuyue-quhuo
- 全文：https://github.com/<owner>/<repo>/tree/main/docs/requirements/yuyue-quhuo/
```

| 段 | 从哪来 | 怎么写 |
| --- | --- | --- |
| 客户原话 | 上传包里客户说的那句话 | 引号原文，不改写成术语，带日期 |
| 客户确认的结论 | 小需求取 `需求草稿.md` 的「已经定下的」，其余取 `map.md` 的 Decisions so far | 一行一条，一条一个决定 |
| 验收条件 | 客户确认过的场景 | 一条一句，能当场演示；写不出可测条目的，句末标「人工判断」 |
| 不做清单 | 客户说过不做的、这次明确排除的 | 没有就写「无」，整段不删 |
| 需求全文 | 上传包 `.scratch/<需求名>/` | 建仓脚本原样拷进客户仓 `docs/requirements/<需求名>/`，这里给完整链接 |

拷进仓的目录开头写一句：「回传快照，以父工单和 spec 为准，不作为决策来源。」客户本地的 `map.md` 里有你后来会推翻的结论，不标一句，读的人会当成现行。

链接写完整的 URL，不写相对路径。相对路径在 issue 正文里能不能点，没验过，见演练记录。

没被客户确认的想法不进正文，放进需求全文。

## 三、子票

标题写一条切片做完后客户能看到什么，不写实现步骤。一张子票是一片穿过每一层的东西，单独能演示，装得进一个会话。

正文三段：

```markdown
## 垂直切片

顾客打开链接，看到今天的水果、价格和卖完的。

## 验收条件

- [ ] 打开链接，看到当天水果的名单。

## 阻塞

Blocked by: #12
```

- 验收条件只能从父工单的「验收条件」里拆。要新造，先回父工单补一条。
- 阻塞边用 GitHub 原生依赖，命令见 `docs/agents/issue-tracker.md`。正文这一行是给人看的镜像，两边要一致。
- 没有阻塞，整段删掉，不留「Blocked by: 无」。

## 四、四档状态

四个标签，名字、颜色、说明固定：

| 标签 | 颜色 | GitHub 说明 | 父工单上的意思 | 子票上的意思 |
| --- | --- | --- | --- | --- |
| `状态:已提交` | `#ededed` | 已建单，等技术闸门 | 闸门没答 | 不出现 |
| `状态:排队中` | `#fbca04` | 轮到了，等点火 | 闸门答完，等 spec、等拆票点头 | 拆出来了，等点火 |
| `状态:开发中` | `#1d76db` | 正在跑 | 有子票在跑 | 正在跑 |
| `状态:待验收` | `#0e8a16` | 活干完了，等下一步确认 | 子票全合完，等客户点头 | 四样证据齐，等合并 |

建标签：

```bash
gh label create "状态:已提交" --color ededed --description "已建单，等技术闸门"
gh label create "状态:排队中" --color fbca04 --description "轮到了，等点火"
gh label create "状态:开发中" --color 1d76db --description "正在跑"
gh label create "状态:待验收" --color 0e8a16 --description "活干完了，等下一步确认"
```

**谁写。** 只有调度器。两处例外，都发生在建票那一刻：建仓脚本建父工单时打 `状态:已提交`，拆票 agent 建子票时打 `状态:排队中`。建完之后谁都不再碰标签，agent 只把证据写进评论。

标签只表示走到哪一档。spec 在不在、子票拆没拆、拆票点没点头，调度器另看文件和子票，不从标签里猜。

## 五、迁移

父工单：

| 从 | 到 | 触发 | 谁写 | 调度器顺手做什么 |
| --- | --- | --- | --- | --- |
| 无 | `已提交` | 服务器校验通过，建完仓建单 | 建仓脚本 | 无 |
| `已提交` | `排队中` | 技术闸门答完 | 调度器 | 推你一条，提醒手动跑 `to-spec` |
| `排队中` | `开发中` | 拆票点头，第一张子票点火 | 调度器 | 叫 Sandcastle |
| `开发中` | `待验收` | 子票全合进需求分支，评审过 | 调度器 | 推你一条 |
| `待验收` | `开发中` | 客户驳回 | 调度器，读到你写的 `驳回：` 评论 | 建一张修复子票 |
| `待验收` | 关闭 | 客户点头 | 运营者关票 | 无 |

子票：

| 从 | 到 | 触发 | 谁写 |
| --- | --- | --- | --- |
| 无 | `排队中` | 拆票时建出来 | 拆票 agent |
| `排队中` | `开发中` | 点火 | 调度器 |
| `开发中` | `待验收` | 四样证据齐 | 调度器 |
| `待验收` | 关闭 | 合进需求分支 | 调度器 |
| `开发中` | `开发中`，加 `点火超时` | 点火两分钟没回执 | 调度器 |

`点火超时` 是告警标签，不改状态。调度器不自动补点，等人，见 `docs/adr/0005-调度器直接点火.md`。

状态对不上任何一行，调度器不猜，打 `needs-info`，推给你。

## 六、驳回

客户不要这次做出来的东西：

1. 客户告诉运营者。客户看不到工单，走微信或电话。
2. 运营者在父工单写一条评论，`驳回：` 开头，后面跟客户原话。
3. 调度器下一轮读到，把父工单从 `待验收` 改回 `开发中`，另开一张子票。子票标题取驳回原话，验收条件写驳回里点名的那几条。
4. 不重开父工单，不把驳回当新需求再开一张。
5. 修复走新分支、新 worktree，合并仍进原需求分支。

## 七、改口

客户改了主意，东西还要做：

1. 运营者在父工单追加一条评论，`改口：` 开头，写原话，再把被改掉的旧条目原文贴进同一条评论。
2. 改父工单正文里受影响的「客户确认的结论」和「验收条件」。
3. 不新建 issue。spec 已经成形，改完重跑 `to-spec`。

分界：还在做，说清楚改哪几条，是改口；做完了不要，是驳回。

## 八、和五个 triage 标签的关系

客户仓照样有那五个标签，见 `docs/工厂流程.md` 第九节第 4、5 项。它们管人工处理，不管状态：

| 标签 | 谁用 | 什么时候 |
| --- | --- | --- |
| `ready-for-agent` | spec | `to-spec` 发 spec 时打。子票不打 |
| `needs-info` | 调度器 | 状态对不上任何一行，或卡住要人看 |
| `wontfix` | 拆票 agent | 决定不做的切片，打上直接关 |
| `needs-triage`、`ready-for-human` | 人工接管 | v1 不走 |

子票只挂 `状态:*`，不挂 `ready-for-agent`。两边意思一样，都能写就会写岔。
