### 访问链路

访客 → Cloudflare 边缘节点 → 源站 Caddy。边缘节点做 TLS 终止、WAF（Web 应用防火墙）、Bot 防护和限速，再把请求送到这台机器。Caddy 用 Origin CA 证书应答，裸域从 `/data/www` 取文件，`/app/api/*` 反代到 `127.0.0.1:8787`，`upload.` 子域回 `ok`。

源站 80、443 只接受 Cloudflare IPv4 段。2026-11-07 16:25 复核：8 个外部节点直连 80 全超时，8 个节点直连 443 全超时；经 Cloudflare 访问回 200，响应头有 `cf-ray`。SSH 22 仍通。调试和复核要 SSH 到机器上，带客户端证书再对 `127.0.0.1` 发请求，见第三节。

只放 Cloudflare 段不等于只认自家 Cloudflare。别的 Cloudflare 账号也能从 Cloudflare 网络打到源站，不受我们这层 WAF 约束。2026-11-07 起开了 zone 级 Authenticated Origin Pulls（AOP，源站校验 Cloudflare 的客户端证书）：Cloudflare 用我们上传的客户端证书回源，源站只信签发它的私有 CA。global 级没用，它的证书所有账号共用，只能证明请求来自 Cloudflare 网络。细节见下一节。

Cloudflare 侧设置：

| 项 | 值 |
| --- | --- |
| SSL/TLS 模式 | `strict` |
| Authenticated Origin Pulls | zone 级开，自定义客户端证书；global 级关 |
| 最低 TLS | 1.2 |
| Always Use HTTPS | 开 |
| Bot Fight Mode | 关；JS 检测开 |
| WAF | Cloudflare Managed Free Ruleset，入口规则动作 `execute` |
| 限速 | 裸域 `POST /app/api/uploads`，每 IP 每 10 秒 30 次，超了拦截 10 秒 |

2026-11-16：`.dev` 和 `.space` 各有一条边缘限速，条件都是裸域 `POST /app/api/uploads`，每 IP 每 10 秒 30 次，超了拦截 10 秒。实测：同一 IP 连发 31 次，前 30 次到源站（403），第 31 次回 429（`error code: 1015`），10 秒后恢复。应用内限速另算，见 `docs/上传容量实测.md`。

Bot Fight Mode 两个 zone 都保持关；JS 检测保持 `.dev` 开、`.space` 关。免费版会对可疑自动化流量发 JS 挑战，上传和 API 客户端有误伤风险；边缘防护靠 WAF、AOP、登录和应用内限速。

边缘证书是 Universal SSL，覆盖裸域和一级通配，2027-02-01 到期，Cloudflare 负责续期。源站证书换成 Origin CA 后，Caddy 不再向 Let's Encrypt 申请。

### 源站证书

| 项 | 值 |
| --- | --- |
| 证书 | `/etc/caddy/certs/origin.pem` |
| 私钥 | `/etc/caddy/certs/origin.key`，权限 600，属主 `caddy` |
| 签发者 | Cloudflare Origin SSL ECC Certificate Authority |
| 覆盖 | `afkfactory.dev` 和 `*.afkfactory.dev` |
| 有效期 | 2026-11-07 到 2041-11-03 |

这张证书不覆盖 `afkfactory.space`。新 zone 先用 Cloudflare 的 Full 模式复用；2026-11-16 定了签一张覆盖两个 zone 的 Origin CA 并换 `origin.pem`，两个 zone 切 Full (strict)，见第十二节；还没执行。

换证书：在服务器上生成新的私钥和 CSR，用 Cloudflare 控制台或 API 签 15 年 Origin CA，证书和私钥放进 `/etc/caddy/certs/`，`caddy validate` 后 `systemctl reload caddy`。Caddyfile 里的 `tls` 行不用改。

### 源站 mTLS（Authenticated Origin Pulls）

源站现在要求 Cloudflare 回源时出示客户端证书。这层叫 Authenticated Origin Pulls（AOP，源站校验回源身份），开的是 zone 级、自定义证书。zone 级对全 zone 生效，`upload.` 子域以后加 A 记录也自动带上这层；`*.afkfactory.space` 成品子域同样。

Cloudflare 用我们上传的客户端证书回源，源站只信签发它的私有 CA。别的 Cloudflare 账号拿不到这张证书，握手在 TLS 阶段就断了。global 级不用，它的证书所有 Cloudflare 账号共用，只能证明请求来自 Cloudflare 网络，不能证明来自我们账号。

| 项 | 值 |
| --- | --- |
| Cloudflare | zone 级 AOP 开；global 级关；`afkfactory.dev` zone 用序列号结尾 `2C3C` 的证书，2028-11-06 到期；`afkfactory.space` zone 用 `aop-client-2026`，序列号 `0AC5...`，2028-11-14 到期 |
| 源站 CA 证书 | `/etc/caddy/certs/aop-ca.pem`，root 644 |
| CA 私钥 | `/root/aop/aop-ca.key`，root 600 |
| Caddy 配置 | 两个域名块的 `tls` 里加 `client_auth`，`mode require_and_verify`，`trusted_ca_cert_file` 指向上面的 CA 证书 |

Caddy 2.6.2 的写法是 `trusted_ca_cert_file`，不是新版的 `trust_pool`。它只读文件里的第一张证书；要同时信两个 CA，就写两行 `trusted_ca_cert_file`。

**换客户端证书**

现在 `/root/aop/` 里有 `aop-client-2026.crt` 和 `aop-client-2026.key`，SAN 包含 `.dev` 和 `.space`，2028-11-14 到期。`afkfactory.dev` zone 仍用 2028-11-06 到期的旧证书；源站信的是 CA，两张都能过。

换证不用动源站。用 `sudo` 进 `/root/aop` 跑：

```bash
cd /root/aop
openssl genrsa -out aop-client-2026.key 4096
openssl req -new -key aop-client-2026.key -out aop-client-2026.csr -subj "/CN=afkfactory.dev"
cat > aop-client.ext <<'EOF'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=clientAuth
subjectAltName=DNS:afkfactory.dev,DNS:*.afkfactory.dev,DNS:afkfactory.space,DNS:*.afkfactory.space
EOF
openssl x509 -req -in aop-client-2026.csr \
  -CA /etc/caddy/certs/aop-ca.pem -CAkey /root/aop/aop-ca.key \
  -CAcreateserial -out aop-client-2026.crt -days 730 -sha256 -extfile aop-client.ext
chmod 600 aop-client-2026.key
```

1. 把 `aop-client-2026.crt` 和私钥贴进每个要用的 Cloudflare zone 的 zone 级 AOP。新传的证书会接管。
2. 从外面跑 `curl -sSI https://afkfactory.dev/` 和 `curl -sSI https://afkfactory.space/`，都要回 `200` 且响应头有 `cf-ray`。
3. 回控制台删掉旧证书。

删掉 Cloudflare 上的旧证书只是让 Cloudflare 不再用它。源站信的是 CA，旧证书在到期前仍能通过校验。要彻底作废旧证书，把 Caddy 改成 `trusted_leaf_cert_file` 只认当前叶子证书，或者换 CA。

**CA 换证**

CA 证书 2031-11-07 到期。CA 私钥只在服务器上，丢了就重建 CA，源站和 Cloudflare 一起换。

换 CA 时先让源站同时信任新旧两个 CA，避免切换空窗：

1. 把新 CA 证书放到 `/etc/caddy/certs/aop-ca-next.pem`。
2. Caddyfile 里再加一行 `trusted_ca_cert_file /etc/caddy/certs/aop-ca-next.pem`，validate 后 reload。
3. 用新 CA 签一张客户端证书，上传到 Cloudflare，验证回源正常。
4. 删掉旧 CA 那一行和旧证书，reload。

**校验失败时客户端看到什么**

| 场景 | 客户端看到 |
| --- | --- |
| 直连源站，不带客户端证书 | TLS 1.3 握手失败，`tlsv13 alert certificate required`，收不到 HTTP 响应 |
| 直连源站，证书不是本 CA 签发 | 握手失败，`unknown ca` |
| 经 Cloudflare，源站不认 Cloudflare 的证书 | Cloudflare 回 5xx 错误页，访客拿不到源站内容 |
| 经 Cloudflare，正常 | `200`，响应头有 `cf-ray` |

排查时先在服务器上直连源站：

```bash
# 不带证书，应该失败
curl -sSk --resolve afkfactory.dev:443:127.0.0.1 https://afkfactory.dev/

# 带一张本 CA 签发的测试证书，应该回 200 和首页
curl -sSk --cert <测试证书> --key <测试私钥> \
  --resolve afkfactory.dev:443:127.0.0.1 https://afkfactory.dev/
```

第一条报 `certificate required` 才对。第二条能拿到 `200`（首页 HTML），说明 `client_auth` 没生效；第二条也失败，说明 CA 文件或 Caddyfile 有问题。Caddy 2.6.2 默认的 info 日志里看不到客户端证书校验失败，别只看 `journalctl`。

这层挡的是「别的 Cloudflare 账号从 Cloudflare 网络回源」，挡不住 Cloudflare 账号被盗，也挡不住客户端证书私钥泄露。WAF、限速、防火墙仍然要留。

### 真实访客 IP

Caddy 2.6.2 没有 `trusted_proxies`，源站日志里的客户端地址是 Cloudflare 的 IP。官网是静态页，不需要访客 IP，别为此升级 Caddy。

上传服务接进来时，在 Node 里按这个顺序取：先读 `CF-Connecting-IP`，头缺失时退回 `req.socket.remoteAddress`。这两个值只在请求确实来自 Cloudflare 时才可信。上传服务不要直接对公网监听，绑 `127.0.0.1`，由 Caddy 反代。源站已经只放行 Cloudflare 段，这层挡不住同一台机器上的其他进程，反代仍要做。

### 上传体积上限

免费版单次请求上限 100 MB。超过时 Cloudflare 直接回 `413 Payload Too Large`，请求到不了源站。应用层把上限压在 50 MB，留出余量，并在页面上写清楚。

2026-11-07 实测：50 MB POST 到 `https://afkfactory.dev/` 收到 `200`。Caddy 的 `respond` 会提前回包，curl 可能报 `Failed sending data`，属正常。101 MB 返回 `413`，响应体里有 `cloudflare`。

## 六、时钟

2026-11-07 之前一直不同步。`timedatectl` 里 `System clock synchronized: no`，timesyncd 在跑但对不上。

原因：这台机器只有 IPv4 路由，没有 IPv6。timesyncd 默认解析 `ntp.ubuntu.com`，拿到的是 IPv6 地址 `2620:2d:4000:1::41`，包发不出去，它也不换下一个地址。实测往这个地址发包直接 `Network is unreachable`。

修法：在 `/etc/systemd/timesyncd.conf` 里钉两个能通的 IPv4 地址。实测 `ntp.tencent.com`（`119.28.230.190`）和 `time.cloudflare.com`（`162.159.200.1`）都能通，延迟 3 到 7 毫秒。`ntp.ubuntu.com` 的两个 IPv4 地址反而超时，别用。

```ini
[Time]
NTP=119.28.230.190 162.159.200.1
FallbackNTP=ntp.tencent.com time.cloudflare.com
```

改完 `systemctl restart systemd-timesyncd`，等几秒，`timedatectl` 里应该变成 `yes`。

2026-11-07 04:05 复核：同步到 `162.159.200.1`，偏差 0.68 毫秒，和运营者本机逐秒对得上。

换机器或换机房要重测。两个地址都不通时，timesyncd 会退到 fallback 的域名，域名又可能解析到 IPv6，于是重新卡住。换机房前先测通再写进去。

## 九、agent 怎么拿权限

用 `dev` 登录，靠 `/etc/sudoers.d/agent-ops` 放开四条改状态的命令，不要密码：

```
dev ALL=(root) NOPASSWD: /usr/bin/systemctl restart caddy, /usr/bin/systemctl reload caddy, /usr/bin/systemctl restart systemd-timesyncd, /usr/bin/timedatectl set-ntp true
```

读状态不需要 sudo。`dev` 在 `adm` 和 `systemd-journal` 两个组里，`journalctl` 能读全量日志。`systemctl status`、`ss`、`df` 本来就开放。`ufw` 规则读不到：`sudo ufw status` 要密码，`/etc/ufw/user.rules` 是 `640 root:root`。要核防火墙，请运营者在机器上跑一条 `sudo ufw status verbose`。

加命令前先问一句：这条命令能不能拿来改任意文件，或者起任意进程。能，就不加。

`journalctl` 这类会调分页器的命令别放进 sudo 白名单。sudo 下分页器以 root 跑，`less` 里能开 shell。这个坑用组权限解决，不用 sudo。

出事故收回：`sudo rm /etc/sudoers.d/agent-ops`，或者把整行注释掉。改完都跑一次 `visudo -c`。

服务器上不跑常驻 agent。旧配置开过 `bypassPermissions` 和 `skipDangerousModePermissionPrompt`，两个都是 Claude Code 自己的确认开关，开了就等于跳过确认。这一层和上面的 sudo 白名单是两回事：白名单管得住 root 命令，管不住这两个开关。以后要在服务器上跑 agent，先删这两个开关，再把动作限在白名单那四条命令里。见 [#78](https://github.com/Lil-BobCN/grilling-remote/issues/78)。

巡检脚本能用哪四条命令、能自动重启什么，见第十一节。

## 十、从空机器重建

2026-11-16 定了预置环境也在这台机器上。重建还要装 Docker、建共享 Postgres、从 Mac 的 dump 恢复成品数据库；这几步见第十二节，还没写进本清单。

1. 开一台 Ubuntu 24.04 的机器，系统盘 30 G 起，数据盘 80 G。
2. 建 `dev` 用户，加进 `sudo` 组，放公钥到 `~/.ssh/authorized_keys`。同时按第一节收口 sshd：`PermitRootLogin no`、`PasswordAuthentication no`（写成 `/etc/ssh/sshd_config.d/` 下的 drop-in，`sudo sshd -t` 通过后 reload）；时区设 `Etc/UTC`（`sudo timedatectl set-timezone Etc/UTC`）。改完重新登录确认 `dev` 还能进、root 进不来。原步骤漏了这两项，2026-11-16 演练已补跑验证。
3. `apt install caddy`，来自 Ubuntu 自带源。
4. 开防火墙。22 和 ICMP 对任意来源放行；80、443 只放 Cloudflare IPv4 段。段取自 `https://api.cloudflare.com/client/v4/ips`，15 个段，四个大段按 /16 拆成 33 条，见第二节。`ufw` 逐条加：`sudo ufw allow from <段> to any port 80 proto tcp`，443 同样，最后 `sudo ufw enable`。云控制台的安全组照第二节：SSH 22、ICMP 各一条，80、443 各 33 条，改完点「应用」。2026-11-07 安全组和 `ufw` 都已按这个收窄，见 [#96](https://github.com/Lil-BobCN/grilling-remote/issues/96)。
5. 生成私钥和 CSR：`sudo mkdir -p /etc/caddy/certs`，用 `openssl` 生成 EC 私钥，CSR 带四个 SAN：`afkfactory.dev`、`*.afkfactory.dev`、`afkfactory.space`、`*.afkfactory.space`。两个 zone 都用 Full (strict)，见第十二节。
6. 在 Cloudflare 控制台或 API 用 CSR 签一张 15 年 Origin CA 证书，一张覆盖四个 SAN；把 `origin.pem` 和 `origin.key` 放进 `/etc/caddy/certs/`，属主 `caddy`，私钥权限 600。
6a. 生成 AOP 的 CA 和客户端证书：CA 私钥放 `/root/aop/aop-ca.key`，CA 证书装到 `/etc/caddy/certs/aop-ca.pem`，客户端证书先留着。
6b. 在 Cloudflare 两个 zone 的 zone 级 AOP 各上传客户端证书并打开开关。顺序不能反：先让 Cloudflare 出示证书，再让 Caddy 要求证书。
7. 写 `/etc/caddy/Caddyfile`（源在仓库 `deploy/Caddyfile`）：裸域块写 `afkfactory.dev, afkfactory.space`，`upload.` 子域一个块，都写 `tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin.key`，里面的 `client_auth` 校验 AOP CA。裸域写 `root * /data/www`，`/downloads/*` 加 `Cache-Control: no-cache`；`route` 里先反代 `/app/api/*` 到 `127.0.0.1:8787`，再把 `/download`、`/skills`、`/tutorial`、`/help` 映射到同名 `.html`，`/app` 和 `/app/*` 回退到 `/app/index.html`，其余走 `file_server`；`upload.` 写 `respond "ok"`。Cloudflare 的 Browser Cache TTL 设 0（Respect Existing Headers），见 [#101](https://github.com/Lil-BobCN/grilling-remote/issues/101)。
8. `caddy validate` 通过后 `systemctl reload caddy`。
9. 格式化数据盘，挂到 `/data`，用 UUID 写进 `/etc/fstab`，带 `nofail`。然后建静态目录：`sudo mkdir -p /data/www/downloads && sudo chown -R dev:dev /data/www`。
9a. 装 Node 26（NodeSource）：`curl -fsSL https://deb.nodesource.com/setup_26.x | sudo -E bash -`，再 `sudo apt-get install -y nodejs`，确认 `node -v` 是 26.x。空机器没有 Node，后端跑不起来；这一步原手册漏了。
9b. 把仓库 `deploy/` 传到机器，跑 `sudo bash /tmp/afk-deploy/backend/install.sh`。这一步建服务用户、数据目录和 `/data/app`，装 systemd 单元，换 Caddyfile；还不启动服务。
9c. 恢复账号和订单：把私有仓 `grilling-customers` 克隆到 `/data/customers`，属主给 `afkapp`。私有仓要 token，克隆前先按第八节把 git 凭据放好；`GITHUB_TOKEN` 只是环境变量，服务代码不读它，`git push` 用哪份凭据要在服务器上单独配（credential helper 或 remote URL）。参考命令：

    ```bash
    sudo -u afkapp git clone https://x-access-token:<token>@github.com/Lil-BobCN/grilling-customers.git /tmp/afk-customers-restore
    sudo rm -rf /data/customers
    sudo mv /tmp/afk-customers-restore /data/customers
    sudo chown -R afkapp:afkapp /data/customers
    ```

    克隆后确认 `customers.json` 和 `orders/` 都在，行数和最后一次上传记录对得上。仓库不存在或克隆失败时别往下走，否则恢复出来的是空账号。上面带 `rm -rf /data/customers` 的命令只用于空机重建，已有数据的机器不要跑。
9d. 填 `/etc/afkapp/app.env`（`SESSION_SECRET` 用 `openssl rand -base64 32`；`GITHUB_TOKEN`、`SMTP_PASSWORD` 按第八节），按 `docs/后端服务部署.md` 打包发布第一版，跑 `check.sh`。Caddyfile 已含 `/app/api/*` 反代。
9e. 发布站点和客户包：`AFK_SERVER=dev@<地址> bash deploy/site-publish.sh`，再 `AFK_SERVER=dev@<地址> bash deploy/publish.sh`。空机器 `/data/www` 是空的，不跑这两步站点 404；这一步原手册漏了。`site-publish.sh` 的 rsync 不带 `-i`，本机 ssh-agent 为空时要补 `RSYNC_RSH='ssh -i ~/.ssh/id_ed25519_dev_hk'`。
10. 按第六节改 `timesyncd.conf`。
11. `reboot`，按第三节复核一遍。

## 十一、巡检、告警与到期提醒

2026-11-15 按《服务器运维补白》（I-0047）定。这里只写决定；巡检脚本和外部监控账号归 to-spec。实现前照第三节人工复核。

### 巡检分两路

- 可用性探活：外部免费监控服务，每 5 分钟请求 `https://afkfactory.space/`；`afkfactory.dev` 也留着，但只记录不告警（旧域名兼容）。`upload.` 子域不再使用，上传走裸域 `/app/api/uploads`。连续 2 次失败算故障，发邮件。它不依赖运营者 Mac，也不依赖源站。Cloudflare 自带的 Health Checks 免费套餐没有，Pro 套餐才带。
- 日常体检：Mac 上一个每天跑一次的脚本，SSH 到服务器做只读检查。异常时直接 POST 同一条企业微信 Bot webhook；推送失败 3 次转邮件。脚本不经过工厂调度器，调度器没建好或挂了，都不影响体检。

负责人只有运营者。不承诺分钟级响应，当天看到并处理。agent 负责按时检查、发提醒、附排查命令；运营者负责判断和动手。

### 体检项

| 检查 | 频率 | 正常或阈值 |
| --- | --- | --- |
| `https://afkfactory.space/` | 每 5 分钟 | `200`，响应头有 `cf-ray` |
| `https://afkfactory.dev/` | 每 5 分钟，仅记录 | `200`；内地线路可能间歇失败，不告警 |
| `caddy` | 每天 | `active` |
| `systemctl --failed` | 每天 | 0 个单元 |
| `/` 和 `/data` 磁盘 | 每天 | 低于 80%；90% 算严重 |
| 时钟 | 每天 | `System clock synchronized: yes` |
| 22、80、443 | 每天 | 在听 |
| 客户包下载 | 每天 | `200`，大小和 `customer-kit/README.md` 的打包记录一致 |
| 源站证书、AOP 客户端证书 | 每天 | 剩余天数按到期表提醒 |
| Cloudflare IP 段 | 每天 | 和记录的 15 个 IPv4 段一致 |
| 主机指纹 | 每次 SSH | 和已知指纹一致 |

人工保留四项：`ufw` 规则、云安全组、源站 mTLS 直连验证、客户包 SHA256。前两项要 sudo 密码或控制台，第三项要测试证书，第四项每天下整包太费流量。

不做：响应时间 SLA、WAF 攻击告警、CPU 和内存趋势、备份检查。预置环境装好后，加可用内存阈值和 pg_dump 新鲜度两项，见第十二节；仍然不做趋势。

### 到期表

唯一一份在 `deploy/ops-dates.json`，记九项：域名（两个 zone）、AOP 客户端证书（两个 zone）、AOP CA、源站 Origin CA、私有仓 token（2026-11-16 加，fine-grained PAT，只授 `grilling-customers`）、朝晞云服务器月付、Cloudflare 边缘证书。每项带日期和提前提醒天数。每天体检算剩余天数，到点发提醒。第四、八节里的证书日期是换证说明，不参与提醒计算。

Cloudflare Registrar 默认自动续费，到期前 30 天第一次扣款，失败会重试并发邮件。它的续费邮件保留，作为第二层。日期由 agent 写进表；月付账单日已按控制台账单记：每月 3 日 10:00，下次 2026-12-03；没有自动续费，要手动付。

### Cloudflare 段变更

每天读一次 `https://api.cloudflare.com/client/v4/ips`，和记录的 15 个 IPv4 段比。变了发告警，附新旧差异和两份更新命令：`ufw` 15 条、安全组 33 条。IPv6 的 7 段按 2026-11-07 的决定只记不加。

改动由运营者手动做：安全组在云控制台，`ufw` 要 sudo 密码。agent 不碰。

### 自动化边界

agent 和定时脚本可以做：

- 所有只读检查；
- 现有四条免密命令：重载或重启 caddy、重启对时、打开 NTP；
- 体检发现 `caddy` 停了，自动重启一次并记录；仍失败才告警；
- 推送失败重试 3 次，再转邮件。

必须运营者做：

- 改防火墙，`ufw` 和云安全组都算；
- 改 DNS、Cloudflare 设置、WAF、限速；
- 买、续费、改付款方式；
- 换证书、重建 CA；
- 系统大版本升级、整机重启；
- 回传件、订单数据和成品数据库的恢复；
- 成品破坏性迁移的合并前点头，见第十二节。

可用性探活报警后不自动重启服务、不自动改配置，分不清是源站、Cloudflare 还是网络的问题。日常体检发现 `caddy` 停了，按上面那条自动重启一次。

依据：I-0047 的 grilling 结论；证书日期见第四、八节；域名到期日由 RDAP 查得；Cloudflare 续费规则见 `https://developers.cloudflare.com/registrar/account-options/renew-domains/`；Health Checks 套餐见 `https://developers.cloudflare.com/health-checks/`。

### 容器和网络

- app 容器非 root 运行，不挂 Docker socket，不用 host 网络，只把端口绑在 `127.0.0.1:<端口>`。
- 资源上限：内存 512 MiB、CPU 0.5、pids 256。数字先按经验给，容量表按实测再调。
- 每个软件一个 bridge 网络；共享 Postgres 接入每个网络；app 之间不能互访。
- Postgres 不发布端口。
- 端口从 9100 起分配，记录在 compose 文件里。

### 数据库

- 一个 Postgres 16，每个软件一个 database 和一个 role；role 只能读写自己的库。
- 总钥匙（superuser 密码）在 `/data/products/postgres/.env`，600 root，不进任何 app 容器。
- 每晚 3 点，Mac 上的备份脚本按软件 `pg_dump` 到 `/data/products/backups/`，再同步到 Mac 的专门目录。保留 7 个日备、4 个周备；`/data/products/<交付地址>/data/` 一起同步。连续两次失败告警。
- 第一次交付后做一次恢复演练，之后每半年一次。恢复顺序：停对应 app，drop/create database，`psql` 恢复最新 dump，起 app，跑健康检查。
- 一版之内，数据库迁移必须向前兼容。删列、改类型、批量改数据这类破坏性迁移，部署前先 dump，并在 PR 里标单向门，由运营者在合并前点。

5. `deploy/Caddyfile` 加成品 include；建 `/etc/caddy/products/`；`caddy validate` 后 reload。
6. 建共享 Postgres 容器和总钥匙。
7. 装 `/usr/local/sbin/afk-product` helper，负责部署、回滚和 `pg_dump`；sudo 白名单只加这一条，不给 `dev` docker 组。
8. Mac 上加每晚备份任务和每个成品地址的外部探活。
9. 在第三节复核表加 Docker、Compose、Postgres、成品地址和可用内存的检查。

### 第一次部署和回滚（脚本，未实现）

- Mac 用现有 GitHub 凭证拉合并后的代码，交叉构建 `linux/amd64` 镜像，`docker save` 成 tar，经 SSH 传到源站。
- 第一次部署：Mac 脚本调 helper 建目录、Compose、`.env`、database/role 和 Caddy 路由；`docker load`；`docker compose up -d`；健康检查；发运营者「已上线：地址、版本、耗时」。脚本可重复跑，失败重试不会建出第二套。
- 同一软件再部署：只换镜像 tag，`compose up -d`。
- 失败两次：保留上一版，通知运营者。
- 留最近 3 个版本。回滚是一条命令，指回上一版并重启，完成后通知运营者，不需要运营者点头。
- 源站不放用于拉客户代码的令牌；上传服务现有的建仓令牌保持原样，成品容器读不到它。部署脚本只调 helper，不给 `dev` docker 组。

### 密钥

- 部署脚本随机生成数据库密码和应用密钥，写完两份：Mac `private/成品/<交付地址>.env`，服务器 `/data/products/<交付地址>/.env`（600 root）。
- 仓库和 GitHub 不放密钥。轮换时重新生成、重启容器，旧密码作废。

### 巡检和容量

成品装好后，每天体检加这几项：

| 检查 | 正常或阈值 |
| --- | --- |
| 成品容器 | 每个软件的 app 和服务都在跑 |
| 每个容器内存 | 记录读数，不设趋势 |
| `/data/products/` 磁盘 | 低于 80% |
| `pg_dump` 新鲜度 | 最近一次成功不超过 26 小时 |
| 每个成品地址 | 外部探活每 5 分钟，连续 2 次失败算故障 |
| 可用内存 | 连续 3 天低于 512 MiB、OOM kill、或平台接口变慢，报加机器 |

每上一个软件记一档实测内存，供容量实验。容量表放哪由 to-spec 定，建议 `docs/成品容量记录.md`。
