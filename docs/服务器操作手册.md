两个坑：

本机开着代理软件时，DNS 会被接管。2026-11-07 实测（代理开着），`<域名>` 在本机解析成 `198.18.0.51`，不是 Cloudflare 地址。判断有没有被接管，看返回值是不是 `198.18` 开头。开了 Cloudflare 代理后，公共 DNS 返回的是 Cloudflare 的任播地址（`104.x` 或 `172.67.x`），源站地址只存在 Cloudflare 的 DNS 记录里。

### 访问链路

访客 → Cloudflare 边缘节点 → 源站 Caddy。边缘节点做 TLS 终止、WAF（Web 应用防火墙）、Bot 防护和限速，再把请求送到这台机器。Caddy 用 Origin CA 证书应答，裸域从 `/data/www` 取文件，`upload.` 子域回 `ok`。

源站 80、443 只接受 Cloudflare IPv4 段。2026-11-07 16:25 复核：8 个外部节点直连 80 全超时，8 个节点直连 443 全超时；经 Cloudflare 访问回 200，响应头有 `cf-ray`。SSH 22 仍通。调试和复核要 SSH 到机器上，带客户端证书再对 `127.0.0.1` 发请求，见第三节。

只放 Cloudflare 段不等于只认自家 Cloudflare。别的 Cloudflare 账号也能从 Cloudflare 网络打到源站，不受我们这层 WAF 约束。2026-11-07 起开了 zone 级 Authenticated Origin Pulls（AOP，源站校验 Cloudflare 的客户端证书）：Cloudflare 用我们上传的客户端证书回源，源站只信签发它的私有 CA。global 级没用，它的证书所有账号共用，只能证明请求来自 Cloudflare 网络。细节见下一节。

Cloudflare 侧 2026-11-07 的设置：

| 项 | 值 |
| --- | --- |
| SSL/TLS 模式 | `strict` |
| Authenticated Origin Pulls | zone 级开，自定义客户端证书；global 级关 |
| 最低 TLS | 1.2 |
| Always Use HTTPS | 开 |
| Bot Fight Mode | 开，JS 检测一起开 |
| WAF | Cloudflare Managed Free Ruleset，入口规则动作 `execute` |
| 限速 | `upload.` 子域的 POST，每 IP 每 10 秒 30 次，超了拦截 |

上传服务还没上线，限速规则没在真实上传上试过。

边缘证书是 Universal SSL，覆盖裸域和一级通配，2027-02-01 到期，Cloudflare 负责续期。源站证书换成 Origin CA 后，Caddy 不再向 Let's Encrypt 申请。

### 源站 mTLS（Authenticated Origin Pulls）

源站现在要求 Cloudflare 回源时出示客户端证书。这层叫 Authenticated Origin Pulls（AOP，源站校验回源身份），开的是 zone 级、自定义证书。zone 级对全 zone 生效，`upload.` 子域以后加 A 记录也自动带上这层。

Cloudflare 用我们上传的客户端证书回源，源站只信签发它的私有 CA。别的 Cloudflare 账号拿不到这张证书，握手在 TLS 阶段就断了。global 级不用，它的证书所有 Cloudflare 账号共用，只能证明请求来自 Cloudflare 网络，不能证明来自我们账号。

| 项 | 值 |
| --- | --- |
| Cloudflare | zone 级 AOP 开；global 级关；当前客户端证书序列号结尾 `2C3C`，2028-11-06 到期 |
| 源站 CA 证书 | `/etc/caddy/certs/aop-ca.pem`，root 644 |
| CA 私钥 | `/root/aop/aop-ca.key`，root 600 |
| Caddy 配置 | 两个域名块的 `tls` 里加 `client_auth`，`mode require_and_verify`，`trusted_ca_cert_file` 指向上面的 CA 证书 |

Caddy 2.6.2 的写法是 `trusted_ca_cert_file`，不是新版的 `trust_pool`。它只读文件里的第一张证书；要同时信两个 CA，就写两行 `trusted_ca_cert_file`。

**换客户端证书**

客户端证书 2028-11-06 到期。换证不用动源站。用 `sudo` 进 `/root/aop` 跑：

```bash
cd /root/aop
openssl genrsa -out aop-client-2028.key 4096
openssl req -new -key aop-client-2028.key -out aop-client-2028.csr -subj "/CN=afkfactory.dev"
cat > aop-client.ext <<'EOF'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=clientAuth
subjectAltName=DNS:afkfactory.dev,DNS:*.afkfactory.dev
EOF
openssl x509 -req -in aop-client-2028.csr \
  -CA /etc/caddy/certs/aop-ca.pem -CAkey /root/aop/aop-ca.key \
  -CAcreateserial -out aop-client-2028.crt -days 730 -sha256 -extfile aop-client.ext
chmod 600 aop-client-2028.key
```

1. 把 `aop-client-2028.crt` 和私钥贴进 Cloudflare 的 zone 级 AOP。新传的证书会接管。
2. 从外面跑 `curl -sSI https://afkfactory.dev/`，回 `200` 且响应头有 `cf-ray`。
3. 回控制台删掉旧证书。

删掉 Cloudflare 上的旧证书只是让 Cloudflare 不再用它。源站信的是 CA，旧证书在到期前仍能通过校验。要彻底作废旧证书，把 Caddy 改成 `trusted_leaf_cert_file` 只认当前叶子证书，或者换 CA。

**CA 换证**

CA 证书 2031-11-07 到期。CA 私钥只在服务器上，丢了就重建 CA，源站和 Cloudflare 一起换。

换 CA 时先让源站同时信任新旧两个 CA，避免切换空窗：

1. 把新 CA 证书放到 `/etc/caddy/certs/aop-ca-next.pem`。
2. Caddyfile 里再加一行 `trusted_ca_cert_file /etc/caddy/certs/aop-ca-next.pem`，validate 后 reload。
3. 用新 CA 签一张客户端证书，上传到 Cloudflare，验证回源正常。
4. 删掉旧 CA 那一行和旧证书，reload。

**校验失败时客户端看到什么**

| 场景 | 客户端看到 |
| --- | --- |
| 直连源站，不带客户端证书 | TLS 1.3 握手失败，`tlsv13 alert certificate required`，收不到 HTTP 响应 |
| 直连源站，证书不是本 CA 签发 | 握手失败，`unknown ca` |
| 经 Cloudflare，源站不认 Cloudflare 的证书 | Cloudflare 回 5xx 错误页，访客拿不到源站内容 |
| 经 Cloudflare，正常 | `200`，响应头有 `cf-ray` |

排查时先在服务器上直连源站：

```bash
# 不带证书，应该失败
curl -sSk --resolve afkfactory.dev:443:127.0.0.1 https://afkfactory.dev/

# 带一张本 CA 签发的测试证书，应该回 ok
curl -sSk --cert <测试证书> --key <测试私钥> \
  --resolve afkfactory.dev:443:127.0.0.1 https://afkfactory.dev/
```

第一条报 `certificate required` 才对。第一条能回 `ok`，说明 `client_auth` 没生效；第二条也失败，说明 CA 文件或 Caddyfile 有问题。Caddy 2.6.2 默认的 info 日志里看不到客户端证书校验失败，别只看 `journalctl`。

这层挡的是「别的 Cloudflare 账号从 Cloudflare 网络回源」，挡不住 Cloudflare 账号被盗，也挡不住客户端证书私钥泄露。WAF、限速、防火墙仍然要留。

### 真实访客 IP

Caddy 2.6.2 没有 `trusted_proxies`，源站日志里的客户端地址是 Cloudflare 的 IP。官网是静态页，不需要访客 IP，别为此升级 Caddy。

上传服务接进来时，在 Node 里按这个顺序取：先读 `CF-Connecting-IP`，头缺失时退回 `req.socket.remoteAddress`。这两个值只在请求确实来自 Cloudflare 时才可信。上传服务不要直接对公网监听，绑 `127.0.0.1`，由 Caddy 反代。源站已经只放行 Cloudflare 段，这层挡不住同一台机器上的其他进程，反代仍要做。

### 上传体积上限

免费版单次请求上限 100 MB。超过时 Cloudflare 直接回 `413 Payload Too Large`，请求到不了源站。应用层把上限压在 50 MB，留出余量，并在页面上写清楚。

2026-11-07 实测：50 MB POST 到 `https://afkfactory.dev/` 收到 `200`。Caddy 的 `respond` 会提前回包，curl 可能报 `Failed sending data`，属正常。101 MB 返回 `413`，响应体里有 `cloudflare`。

## 六、时钟

2026-11-07 之前一直不同步。`timedatectl` 里 `System clock synchronized: no`，timesyncd 在跑但对不上。

原因：这台机器只有 IPv4 路由，没有 IPv6。timesyncd 默认解析 `ntp.ubuntu.com`，拿到的是 IPv6 地址 `2620:2d:4000:1::41`，包发不出去，它也不换下一个地址。实测往这个地址发包直接 `Network is unreachable`。

修法：在 `/etc/systemd/timesyncd.conf` 里钉两个能通的 IPv4 地址。实测 `ntp.tencent.com`（`119.28.230.190`）和 `time.cloudflare.com`（`162.159.200.1`）都能通，延迟 3 到 7 毫秒。`ntp.ubuntu.com` 的两个 IPv4 地址反而超时，别用。

```ini
[Time]
NTP=119.28.230.190 162.159.200.1
FallbackNTP=ntp.tencent.com time.cloudflare.com
```

改完 `systemctl restart systemd-timesyncd`，等几秒，`timedatectl` 里应该变成 `yes`。

2026-11-07 04:05 复核：同步到 `162.159.200.1`，偏差 0.68 毫秒，和运营者本机逐秒对得上。

换机器或换机房要重测。两个地址都不通时，timesyncd 会退到 fallback 的域名，域名又可能解析到 IPv6，于是重新卡住。换机房前先测通再写进去。

## 九、agent 怎么拿权限

用 `dev` 登录，靠 `/etc/sudoers.d/agent-ops` 放开四条改状态的命令，不要密码：

```
dev ALL=(root) NOPASSWD: /usr/bin/systemctl restart caddy, /usr/bin/systemctl reload caddy, /usr/bin/systemctl restart systemd-timesyncd, /usr/bin/timedatectl set-ntp true
```

读状态不需要 sudo。`dev` 在 `adm` 和 `systemd-journal` 两个组里，`journalctl` 能读全量日志。`systemctl status`、`ss`、`df` 本来就开放。`ufw` 规则读不到：`sudo ufw status` 要密码，`/etc/ufw/user.rules` 是 `640 root:root`。要核防火墙，请运营者在机器上跑一条 `sudo ufw status verbose`。

加命令前先问一句：这条命令能不能拿来改任意文件，或者起任意进程。能，就不加。

`journalctl` 这类会调分页器的命令别放进 sudo 白名单。sudo 下分页器以 root 跑，`less` 里能开 shell。这个坑用组权限解决，不用 sudo。

出事故收回：`sudo rm /etc/sudoers.d/agent-ops`，或者把整行注释掉。改完都跑一次 `visudo -c`。

服务器上不跑常驻 agent。旧配置开过 `bypassPermissions` 和 `skipDangerousModePermissionPrompt`，两个都是 Claude Code 自己的确认开关，开了就等于跳过确认。这一层和上面的 sudo 白名单是两回事：白名单管得住 root 命令，管不住这两个开关。以后要在服务器上跑 agent，先删这两个开关，再把动作限在白名单那四条命令里。见 [#78](https://github.com/Lil-BobCN/grilling-remote/issues/78)。

## 十、从空机器重建

1. 开一台 Ubuntu 24.04 的机器，系统盘 30 G 起，数据盘 80 G。
2. 建 `dev` 用户，加进 `sudo` 组，放公钥到 `~/.ssh/authorized_keys`。
3. `apt install caddy`，来自 Ubuntu 自带源。
4. 开防火墙。22 和 ICMP 对任意来源放行；80、443 只放 Cloudflare IPv4 段。段取自 `https://api.cloudflare.com/client/v4/ips`，15 个段，四个大段按 /16 拆成 33 条，见第二节。`ufw` 逐条加：`sudo ufw allow from <段> to any port 80 proto tcp`，443 同样，最后 `sudo ufw enable`。云控制台的安全组照第二节：SSH 22、ICMP 各一条，80、443 各 33 条，改完点「应用」。2026-11-07 安全组和 `ufw` 都已按这个收窄，见 [#96](https://github.com/Lil-BobCN/grilling-remote/issues/96)。
5. 生成私钥和 CSR：`sudo mkdir -p /etc/caddy/certs`，用 `openssl` 生成 EC 私钥，CSR 带 `afkfactory.dev` 和 `*.afkfactory.dev` 两个 SAN。
6. 在 Cloudflare 控制台或 API 用 CSR 签一张 15 年 Origin CA 证书，把 `origin.pem` 和 `origin.key` 放进 `/etc/caddy/certs/`，属主 `caddy`，私钥权限 600。
6a. 生成 AOP 的 CA 和客户端证书：CA 私钥放 `/root/aop/aop-ca.key`，CA 证书装到 `/etc/caddy/certs/aop-ca.pem`，客户端证书先留着。
6b. 在 Cloudflare 的 zone 级 AOP 上传客户端证书并打开开关。顺序不能反：先让 Cloudflare 出示证书，再让 Caddy 要求证书。
7. 写 `/etc/caddy/Caddyfile`（源在仓库 `deploy/Caddyfile`）：裸域和 `upload.` 子域各一个块，都写 `tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin.key`，里面的 `client_auth` 校验 AOP CA。裸域写 `root * /data/www` 和 `file_server`，`/downloads/*` 加 `Cache-Control: no-cache`；`upload.` 写 `respond "ok"`。Cloudflare 的 Browser Cache TTL 设 0（Respect Existing Headers），见 [#101](https://github.com/Lil-BobCN/grilling-remote/issues/101)。
8. `caddy validate` 通过后 `systemctl reload caddy`。
9. 格式化数据盘，挂到 `/data`，用 UUID 写进 `/etc/fstab`，带 `nofail`。然后建静态目录：`sudo mkdir -p /data/www/downloads && sudo chown -R dev:dev /data/www`。
10. 按第六节改 `timesyncd.conf`。
11. `reboot`，按第三节复核一遍。
