## 四、服务清单

| 单元 | 干什么 | 开机自启 | 挂了会怎样 |
| --- | --- | --- | --- |
| `caddy` | 用 Origin CA 证书托管 `/data/www` 的静态文件 | 是 | 443 不通，站点和下载打不开 |
| `systemd-timesyncd` | 对时 | 是 | 时间慢慢漂，证书校验和日志时间会歪 |
| `ssh` | 登录 | 是 | 登不上，只能从云控制台进 |
| `unattended-upgrades` | 自动装安全更新 | 是 | 安全补丁不装 |
| `ufw` | 防火墙 | 是 | 规则不加载，对外端口不受这台机控制 |

其余是 Ubuntu 默认带的（cloud-init、snapd、rsyslog、cron、apparmor 等），没配过，也不用管。

caddy 版本 2.6.2，来自 Ubuntu 自己的软件源。配置文件 `/etc/caddy/Caddyfile`，源在仓库 `deploy/Caddyfile`，服务器上以那份为准，不在机器上直接改。

现在两个域名块，都指定 `/etc/caddy/certs/origin.pem` 和 `/etc/caddy/certs/origin.key`：

| 域名块 | 现在做什么 |
| --- | --- |
| 裸域 | `root * /data/www` 加 `file_server`，出静态页和 `/downloads/` 下的客户包。下载路径加 `Cache-Control: no-cache`，让 Cloudflare 每次回源校验，重打包后不会把旧包留给客户 |
| `upload.` 子域 | 回 `ok`。上传服务上线后换成反代 |

静态目录 `/data/www` 属主 `dev`，权限 755，caddy 以 `caddy` 用户读。根路径放了一个临时的 `ok` 占位页，教程页上线后换掉。

改配置的流程：仓库里改 `deploy/Caddyfile`，传到服务器，`sudo install -m 644` 换文件，`sudo caddy validate --config /etc/caddy/Caddyfile`，再 `sudo systemctl reload caddy`。启动方式是 `/usr/bin/caddy run --environ --config /etc/caddy/Caddyfile`。

### 访问链路

访客 → Cloudflare 边缘节点 → 源站 Caddy。边缘节点做 TLS 终止、WAF（Web 应用防火墙）、Bot 防护和限速，再把请求送到这台机器。Caddy 用 Origin CA 证书应答，裸域从 `/data/www` 取文件，`upload.` 子域回 `ok`。

源站 80、443 只接受 Cloudflare IPv4 段。2026-11-07 16:25 复核：8 个外部节点直连 80 全超时，8 个节点直连 443 全超时；经 Cloudflare 访问回 200，响应头有 `cf-ray`。SSH 22 仍通。调试和复核要 SSH 到机器上，对 `127.0.0.1` 发请求，见第三节。

只放 Cloudflare 段不等于只认自家 Cloudflare。别的 Cloudflare 账号也能从 Cloudflare 网络打到源站，不受我们这层 WAF 约束。要只认自家，得开 Authenticated Origin Pulls（mTLS，源站校验 Cloudflare 的客户端证书），现在没开。

Cloudflare 侧 2026-11-07 的设置：

| 项 | 值 |
| --- | --- |
| SSL/TLS 模式 | `strict` |
| 最低 TLS | 1.2 |
| Always Use HTTPS | 开 |
| Bot Fight Mode | 开，JS 检测一起开 |
| WAF | Cloudflare Managed Free Ruleset，入口规则动作 `execute` |
| 限速 | `upload.` 子域的 POST，每 IP 每 10 秒 30 次，超了拦截 |

上传服务还没上线，限速规则没在真实上传上试过。

边缘证书是 Universal SSL，覆盖裸域和一级通配，2027-02-01 到期，Cloudflare 负责续期。源站证书换成 Origin CA 后，Caddy 不再向 Let's Encrypt 申请。

### 真实访客 IP

Caddy 2.6.2 没有 `trusted_proxies`，源站日志里的客户端地址是 Cloudflare 的 IP。官网是静态页，不需要访客 IP，别为此升级 Caddy。

上传服务接进来时，在 Node 里按这个顺序取：先读 `CF-Connecting-IP`，头缺失时退回 `req.socket.remoteAddress`。这两个值只在请求确实来自 Cloudflare 时才可信。上传服务不要直接对公网监听，绑 `127.0.0.1`，由 Caddy 反代。源站已经只放行 Cloudflare 段，这层挡不住同一台机器上的其他进程，反代仍要做。

### 上传体积上限

免费版单次请求上限 100 MB。超过时 Cloudflare 直接回 `413 Payload Too Large`，请求到不了源站。应用层把上限压在 50 MB，留出余量，并在页面上写清楚。

2026-11-07 实测：50 MB POST 到 `https://afkfactory.dev/` 收到 `200`。Caddy 的 `respond` 会提前回包，curl 可能报 `Failed sending data`，属正常。101 MB 返回 `413`，响应体里有 `cloudflare`。

## 六、时钟

2026-11-07 之前一直不同步。`timedatectl` 里 `System clock synchronized: no`，timesyncd 在跑但对不上。

原因：这台机器只有 IPv4 路由，没有 IPv6。timesyncd 默认解析 `ntp.ubuntu.com`，拿到的是 IPv6 地址 `2620:2d:4000:1::41`，包发不出去，它也不换下一个地址。实测往这个地址发包直接 `Network is unreachable`。

修法：在 `/etc/systemd/timesyncd.conf` 里钉两个能通的 IPv4 地址。实测 `ntp.tencent.com`（`119.28.230.190`）和 `time.cloudflare.com`（`162.159.200.1`）都能通，延迟 3 到 7 毫秒。`ntp.ubuntu.com` 的两个 IPv4 地址反而超时，别用。

```ini
[Time]
NTP=119.28.230.190 162.159.200.1
FallbackNTP=ntp.tencent.com time.cloudflare.com
```

改完 `systemctl restart systemd-timesyncd`，等几秒，`timedatectl` 里应该变成 `yes`。

2026-11-07 04:05 复核：同步到 `162.159.200.1`，偏差 0.68 毫秒，和运营者本机逐秒对得上。

换机器或换机房要重测。两个地址都不通时，timesyncd 会退到 fallback 的域名，域名又可能解析到 IPv6，于是重新卡住。换机房前先测通再写进去。

## 七、备份

**这台机器不做备份。** 四条理由：

`/data` 只放得下站点文件，`/data/www` 是静态页和客户包，仓库里都有源；仓库没有的只有凭据和证书。站点只有 `Caddyfile` 和证书、私钥几个文件，重建比恢复快。证书是 Cloudflare Origin CA，15 年有效，不会自动续。私钥只在服务器上，丢了就重新签一张。整机能从同一个镜像重建，步骤见最后一节。

什么时候改主意：`/data` 开始放仓库里没有的东西，或者出现手工改过、重建不出来的配置。到那时再加备份，别提前养一套没人盯的定时任务。

## 九、agent 怎么拿权限

用 `dev` 登录，靠 `/etc/sudoers.d/agent-ops` 放开四条改状态的命令，不要密码：

```
dev ALL=(root) NOPASSWD: /usr/bin/systemctl restart caddy, /usr/bin/systemctl reload caddy, /usr/bin/systemctl restart systemd-timesyncd, /usr/bin/timedatectl set-ntp true
```

读状态不需要 sudo。`dev` 在 `adm` 和 `systemd-journal` 两个组里，`journalctl` 能读全量日志。`systemctl status`、`ss`、`df` 本来就开放。`ufw` 规则读不到：`sudo ufw status` 要密码，`/etc/ufw/user.rules` 是 `640 root:root`。要核防火墙，请运营者在机器上跑一条 `sudo ufw status verbose`。

加命令前先问一句：这条命令能不能拿来改任意文件，或者起任意进程。能，就不加。

`journalctl` 这类会调分页器的命令别放进 sudo 白名单。sudo 下分页器以 root 跑，`less` 里能开 shell。这个坑用组权限解决，不用 sudo。

出事故收回：`sudo rm /etc/sudoers.d/agent-ops`，或者把整行注释掉。改完都跑一次 `visudo -c`。

服务器上不跑常驻 agent。旧配置开过 `bypassPermissions` 和 `skipDangerousModePermissionPrompt`，两个都是 Claude Code 自己的确认开关，开了就等于跳过确认。这一层和上面的 sudo 白名单是两回事：白名单管得住 root 命令，管不住这两个开关。以后要在服务器上跑 agent，先删这两个开关，再把动作限在白名单那四条命令里。见 [#78](https://github.com/Lil-BobCN/grilling-remote/issues/78)。

## 十、从空机器重建

1. 开一台 Ubuntu 24.04 的机器，系统盘 30 G 起，数据盘 80 G。
2. 建 `dev` 用户，加进 `sudo` 组，放公钥到 `~/.ssh/authorized_keys`。
3. `apt install caddy`，来自 Ubuntu 自带源。
4. 开防火墙。22 和 ICMP 对任意来源放行；80、443 只放 Cloudflare IPv4 段。段取自 `https://api.cloudflare.com/client/v4/ips`，15 个段，四个大段按 /16 拆成 33 条，见第二节。`ufw` 逐条加：`sudo ufw allow from <段> to any port 80 proto tcp`，443 同样，最后 `sudo ufw enable`。云控制台的安全组照第二节：SSH 22、ICMP 各一条，80、443 各 33 条，改完点「应用」。2026-11-07 安全组和 `ufw` 都已按这个收窄，见 [#96](https://github.com/Lil-BobCN/grilling-remote/issues/96)。
5. 生成私钥和 CSR：`sudo mkdir -p /etc/caddy/certs`，用 `openssl` 生成 EC 私钥，CSR 带 `afkfactory.dev` 和 `*.afkfactory.dev` 两个 SAN。
6. 在 Cloudflare 控制台或 API 用 CSR 签一张 15 年 Origin CA 证书，把 `origin.pem` 和 `origin.key` 放进 `/etc/caddy/certs/`，属主 `caddy`，私钥权限 600。
7. 写 `/etc/caddy/Caddyfile`（源在仓库 `deploy/Caddyfile`）：裸域和 `upload.` 子域各一个块，都写 `tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin.key`。裸域写 `root * /data/www` 和 `file_server`，`/downloads/*` 加 `Cache-Control: no-cache`；`upload.` 写 `respond "ok"`。
8. `caddy validate` 通过后 `systemctl reload caddy`。
9. 格式化数据盘，挂到 `/data`，用 UUID 写进 `/etc/fstab`，带 `nofail`。然后建静态目录：`sudo mkdir -p /data/www/downloads && sudo chown -R dev:dev /data/www`。
10. 按第六节改 `timesyncd.conf`。
11. `reboot`，按第三节复核一遍。

半小时左右，大半时间在装系统。Origin CA 当场签发，不用等 ACME。
