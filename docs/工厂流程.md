# 这间工厂怎么运转

> 状态：现行

一句话：出 spec 之前的事，由客户在本机 DeepSeek Harness（`dsh`）里问完，文件写在客户机器的 `.scratch/`，再在官网上传页回传给我们。spec 之后，照素材原流程走。中间无人值守，合并后你每天早上抽样看。

> 读法：正文里的「素材」「已定」「已验」「有出处」「推断」「待定」标出这条说法的来源和确定程度。素材原样；你拍过板是已定；本机或服务器跑过是已验；读过原文、用法是我定的是有出处；我设计没验过是推断；还没拍板是待定。
>
> 原文指本机 mattpocock-skills 的技能原文。2026-11-03 读的是 1.3.1，2026-11-05 升到 1.3.2；与流程相关的差异见「Skills 清单」一节末尾。素材指 8 份口播稿。
>

## 一、目标与边界

一台 Mac 加一台云服务器，一个运营者，接多个不懂技术的客户。

三个前提：

- 客户不写 spec，不读 diff。他只说现象、改草稿、点确认。
- 你不盯中间。必点两次：补缺口（C1）、拆票（C4）；小需求只点 C1。合并后你每天早上抽样看。临时还有三处：客户找人、验证问答、出事。
- 客户仓的规则、凭证、验证技能由工厂建，客户不碰。

无人化的边界：中间无人值守，前面有人点头，后面有人抽样。

前面点头，后面抽样，中间才敢放。这是无人化能成立的条件，不算退让。

## 二、四层

| 层 | 回答什么 | 谁负责 | 产出 |
| --- | --- | --- | --- |
| 接单 | 要什么、怎么算成 | 客户 + 本机 `dsh` | `需求草稿.md` 或 `map.md`，加客户确认的结论；验收条件单独存 `验收场景.md` |
| 设计 | 怎么做、拆几张票 | 调度器跑 to-spec，机器拆票，你点两次；小需求跳过 | spec + 票 + 依赖；小需求只有一张实现票 |
| 执行 | 谁先跑、在哪跑 | 调度器 + Sandcastle | 分支 + 提交 + 证据 |
| 治理 | 什么时候停、谁点头 | 你 + 规则 | 抽样、停法、复盘 |

工具落点，六个地方各管一件事：客户的本机 `dsh` 接单，文件写 `.scratch/`；网站放工作区 zip 下载、教程、技能清单和回传上传页；技能随 zip 放在 `.dsh/skills/`；服务器建仓建工单、管仓库令牌，临时中转回传件，导入完成删除、失败留 7 天，不接单；试运行期还跑客户成品，每个软件一套容器和数据库；你的 Mac 跑调度器和容器，也存档客户回传件；GitHub 存工单、代码、PR 和证据，也是唯一的状态；企业微信 Bot 和邮件只做提醒，不回客户（回客户走微信），不做路由，也不点火；人工点在本机 ADE 的工作台 bot chat 里做，bot 读提案、讲给你、按你确认写回；控制台保留作兜底；Orca 是本机 ADE，跑 bot chat、控制台和调试终端。

原则一条：每层只由一个东西负责。研究文档和技能都是零件，不抢流程的位置。

### 执行器和调度器

Sandcastle 不是唯一的执行器。D2 之前不用它，不等于人工执行。活由客户本机的 `dsh`、主机 agent 和确定性脚本干；唯一进沙箱的是生成 verify 技能那一跑。

| 执行器 | 跑什么 | 在哪 | 为什么分开 |
| --- | --- | --- | --- |
| 客户本机 `dsh` | A1 到 A5 接单；写 `.scratch/` 里的文件和原型 | 客户机器 | 客户自己装、自己跑，我们不给 shell，也拦不住写文件 |
| 主机 agent | B2 四份文档、C3 拆票、E3 复盘 | 你的 Mac，仓库直接挂载 | 只读写文档和 issue，不跑客户代码 |
| 补缺口 Agent | C1 补缺口：解压回传件、按原文建客户仓的地图 issue 和决定票、读文件、列题、写父工单评论 | 你的 Mac，读回传件，写客户仓 issue | 要读文件、写推荐，需要模型判断 |
| Sandcastle | B2 生成 verify 技能、D2 实现、D3 自检、D4 评审 | 容器，一票一个 worktree | 要跑代码、要隔离、要并行、要收提交 |
| 确定性脚本 | B1 建仓建单、B2 机械项、D1 对账、D5 合并、E2 部署 | 服务器和调度器 | 不需要模型判断 |

主机 agent 只给读写文件和 `gh` 的权限，不给 shell。要跑代码，进 Sandcastle 或预览环境。预览环境是客户成品在合并前的验证环境，2026-11-16 已定，见第九节 D3 和 `docs/运维手册.md` 第十二节。启动参数和 gh 白名单 hook 见第十九节。

技能不用你敲命令。调度器读工单，决定下一步，替你叫一个 agent 去读那份技能说明。

这张表的意思是：D2 之前的活，多数不用你动手。干活的是客户本机的 `dsh`、主机 agent、补缺口 Agent、脚本和一次沙箱。你点头只在 C1、C4。回传后的决策由你做，to-spec 由调度器自动跑；解压、建图、读文件、列题由补缺口 Agent 做。E1 不再等你点，你每天早上抽样。

#### 调度器和 Sandcastle 的分工

调度器是控制面。它读工单状态，决定下一步，叫执行器干活，再把结果写回工单。它自己不写代码。

Sandcastle 是执行面的一种。给它 agent、沙箱、prompt，它跑一次，收回提交。它不知道整张单走到哪，也不决定下一步。

调度器是普通程序，不是模型。判断靠标签和阻塞边，所以重启接得上。Sandcastle 是调度器代码里的一个函数调用，不会反过来叫调度器。

骨架不止调度器。还有三样：工单状态、证据规则、权限边界。Sandcastle 是手臂，可以换。

```text
每 30 秒：
  读所有 open 工单和标签，跳过 wayfinder 的地图和决定票，不当实现活
  找出该动没动的
  缺 spec    → 调度器自动跑 to-spec
  票就绪    → 叫 Sandcastle 跑一张
  证据齐    → 叫合并脚本
  等你定    → 不动，发提醒
  把结果写回标签和评论
```

#### 调度器凭什么做决定

它不做内容判断，只做路由判断。路由判断能写成一张表：

| 它看到什么 | 它做什么 |
| --- | --- |
| 地图 issue，或地图 issue 的子票 | 不当实现活；只读 `重传：<日期>` 评论，推通知 |
| 父工单是 `状态:已提交`，闸门没答 | 启动补缺口 Agent 列闸门，推给你 |
| 其余单；最新一条关口评论是 `点头：补缺口`，仓库里没有 spec | 调度器自动跑 to-spec |
| 其余单；有 spec，没有子票 | 叫 agent 拆票 |
| 其余单；有子票，最新一条关口评论不是 `点头：拆票` | 停，等你 |
| 其余单；最新一条关口评论是 `点头：拆票`，有没阻塞的票 | 叫 Sandcastle 跑 |
| 小需求；`状态:已提交`，最新一条关口评论是 `点头：补缺口`，有一张 open 子票 | 父工单改 `开发中`，叫 Sandcastle 跑那张票 |
| 小需求；`状态:已提交`，最新一条关口评论是 `点头：补缺口`，没有 open 子票 | 打 `needs-info`，推给你 |
| 小需求却是 `排队中` | 打 `needs-info`，推给你 |
| 票跑完，证据不齐 | 叫自检 |
| 四样证据齐 | 叫合并脚本 |
| 子票全部完成，需求分支没评审 | 叫评审，写 /pr，再叫验证队 |
| 验证队和评审都过 | 叫合并脚本合主干，部署到预置环境，失败回上一版 |

左边全是可检查的事实：标签、文件、子票状态、证据标记。右边全是固定动作。没有一行需要读懂客户在说什么。

需要思考的部分，都在被叫的 agent 里：拆票的 agent、写代码的 agent、评审的 agent。调度器只负责把活递过去。

它像行李分拣线：扫条码，放上对应的传送带。它不知道箱子里是什么。条码错了，箱子就上错飞机。所以功夫要花在条码上，不是让分拣线变聪明。

状态对不上任何一行，它不猜，标 `needs-info` 推给你。

#### 调度器要不要自己写

不用从零写。已经有两个开源的近亲。

`@copperbox/sandcastle-workflow` 是 npm 包加一条 shell 循环。它做的正是 D 段：把 issue 分成 feature，每个 issue 在自己的 Docker worktree 里实现和评审，合进 feature 分支，冲突由 agent 解，跑 verify，开 PR。状态全在 git 和 GitHub 里，进程被杀，下一轮重新推导。

`sandcastle-kit` 是另一种：队列标签、实现加评审、跑项目自己的 lint/build/test、合到本地、出报告。它不推送，也不开 PR。

两个都缺我们的前半段：客户接单、五类闸门、拆票点头、预算和停法、多客户路由。

定了：每个客户仓装一份 `sandcastle-workflow`，我们只写工厂层。它 MIT，版本 0.4.2，作者一个人，星星很少。要 vendor 进来锁版本，不能当黑盒依赖。

它的分组是 planner 每轮重算。我们按 parent issue 固定成员，这一点要改。

## 三、全流程图

两段。中间一条硬线：两边的待问清单都为空，才准写 spec。

```text

  ▼ C1 补缺口：你点第 1 次
  │

  │
  ▼ 地图清完、待问清单为空。调度器自动跑 to-spec
  │
  ▼ 以下照素材原样

  │
  ▼

  │
```

你必点两次：C1、C4；小需求只点 C1。合并不再等你点，你每天早上抽样一次。客户留言和出事时另叫你。

### 一天长什么样（B 店）

**10:00** 客户在自己电脑上用 `dsh` 打开解压好的工作区，说「开始需求澄清」。再说一句要做什么，跟 agent 一轮一轮聊清楚。

**10:04** 验收场景改完，客户说「已经说清楚了」。小需求写 `需求草稿.md` 和 `验收场景.md`；其余写 `map.md`、`验收场景.md` 和 `issues/`。

**10:10** 客户在官网上传 zip。服务器校验，自动建单、建仓；Mac 拉存档。调度器看见新单，经企业微信 Bot 推你一条。

**10:20** 补缺口 Agent 已经解压回传件、按原文在客户仓建好地图 issue 和决定票、把题列好。你收到提醒，在 bot chat 里看每项推荐，答「是」就过。答完和 bot 一起把地图上剩下的项逐条清完，每条由你确认。清完后，工作台 bot 才在父工单写 `点头：补缺口`：最终答案、正文影响两段。调度器下一轮读到，改成 `状态:排队中`，自动跑 to-spec。

**10:22** 地图清完、待问清单为空。调度器自动跑 to-spec。spec 写好后，调度器叫 agent 拆出五张票。

**10:24** 你在 bot chat 里扫一眼票单，说可以。工作台 bot 建子票并写 `点头：拆票`。

**10:25** 调度器读到 `点头：拆票`，开工，先跑一单。

**11:40** 四样证据齐，子票合进需求分支。

**11:41** 验证队和评审都过了，工厂自己合主干，部署到预置环境，失败回上一版。

**11:42** 客户收到交付地址 `https://<客户简称>-<软件简称>.afkfactory.space`。

**第二天早上** 你抽样看前一天合进主干的单。客户要加导出，开新单，回到 10:20。同一个软件的新单复用原仓，只建新父工单和新分支。

小需求走到 10:20 点头后不跑 10:22 到 10:24：工作台 bot 建一张实现票，调度器直接点火，跳到 10:25。

这一天的钟点是示意，没有实测。回传和建仓的时长也没测。

## 四、你出现的地方

一单从头到尾，你必点两次：补缺口（C1）和拆票（C4）。小需求只点补缺口。验证或收尾时可能有一条「需要你答」，次数不定。另有每天早上抽样一次，不属于哪一单。其余时间工厂自己跑。

| 事件 | 什么时候 | 你从哪知道 | 你做什么 | 不回会怎样 |
| --- | --- | --- | --- | --- |
| 补缺口（C1） | 回传校验通过，仓库和工单建好 | 企业微信 Bot 推一条，bot chat 叫醒；题和选项在 bot chat 里看 | 在 bot chat 里答一轮：五类技术选择、标了「你答」的题、合规、接缝、词汇表、查重。每项带推荐，答「是」就过。答完和 bot 逐条清完地图：雾的去处和决定票的结论都由你确认，bot 起草并用 `map.mjs` 写回。小需求还要看 `## 实现票`，确认后由工作台 bot 建票 | 停在等你定，24 小时提醒一次 |
| 拆票（C4） | spec 和票写完 | 企业微信 Bot 推一条，bot chat 叫醒；票单在 bot chat 里看 | 在 bot chat 里看接缝、票单、每票验收条件，说可以；工作台 bot 建票并写 `点头：拆票` | 停在等点头，24 小时提醒一次 |
| 需要你答 | 实现者在 trail 里写了一条 `result=open` 的 gate 行 | 企业微信 Bot 推一条，bot chat 叫醒 | 在 bot chat 里答：同意、不同意，或先搁置；工作台 bot 用 `gate.mjs answer` 写回 `.audit` | 这条线等你，24 小时提醒一次 |
| 客户卡住 | 客户在微信里找客服 | 微信消息 | 回一句，话术见 `customer-kit/安装步骤.md` 的「客服带话」 | 客户等着，单子照常往下走 |
| 每天早上抽样 | 每天早上 8:30 收到前一天合并汇总 | 企业微信 Bot | 读 /pr 正文和提交历史，先看单向门、影响范围大、验证没覆盖到的 | 不拦合并，问题晚一天发现 |
| 出事 | 五种情况，见本节「出事」 | 企业微信 Bot 推一条，邮件兜底 | 看现场，决定继续、换法或停 | 单子停住 |

两条只要知道，不用动手：回传校验通过，单子进队列；工厂自己合主干。推送内容和节奏见 `docs/通知.md`。

这三处人工点都在 bot chat 里做。bot 叫不醒、写回失败或模型不可用时，回控制台，用同一套写回命令；通知正文带控制台命令。

按 B 店那单估，中间没出事，你一共花约五分钟，另加每天早上的抽样。钟点是示意，没有实测。

### 补缺口：一次列完，逐项答「是」

回传校验通过、仓库和工单建好后，补缺口 Agent 解压回传件，先把客户的 `map.md` 和 `issues/NN-*.md` 按原文在客户仓建好地图 issue 和决定票；然后读 Mac 上的 `pending.md`、`需求草稿.md`、`验收场景.md` 和 `GLOSSARY.md`，读客户仓的地图和开放票，把题列好。你不用解压，不用开题单。

形式和客户那边一样，是一轮 grilling。要你定的有六类，逐条列在第八节 C1。每项带推荐答案，你答「是」就等于接受。

答完和 bot 清地图：先读客户仓的 `docs/requirements/{需求名}/决策记录.md`。bot 逐条列出地图的 `Not yet specified` 和开放决定票，每条提一个去处：新建决定票、写进 `Out of scope`、记 `未定`。bot 起草票面、结论和去处文本，你确认后它用 `map.mjs` 写回。清完在地图 `Notes` 加一行链接，指向决策记录。补缺口 Agent 不参与。地图清完才写 `点头：补缺口`。

`点头：补缺口` 分两段：`## 最终答案` 一行一条，`## 正文影响` 引被新答案改掉的正文原文。以后只读父工单的人，看这条评论就知道你答了什么。其余单的父工单改成 `状态:排队中`，调度器自动跑 to-spec；小需求由工作台 bot 先建一张实现票，调度器读到 `点头：补缺口` 后把父工单改成 `状态:开发中`，直接点火。你要重问，就在 chat 里说，工作台 bot 写 `驳回：补缺口`，补缺口 Agent 按理由重列。Mac 上的回传文件是原件，不改写。

不回就停在「等你定」，24 小时提醒一次，它不猜。猜错了返工更贵。这一步估计约三分钟，没实测；清图的时间另算。

### 拆票：扫一眼就点

小需求没有这一步：只有一张实现票，在补缺口时已经建好。

spec 由调度器自动跑 `to-spec` 写，拆票由调度器叫 agent 做。拆完由工作台 bot 在 chat 里给你一屏：接缝、票单、每票的验收条件。

你说可以，工作台 bot 建子票，再写一条 `点头：拆票` 评论，调度器读到才点火。要改就在 chat 里说，bot 写 `驳回：拆票`，拆票 Agent 按理由重拆。这是视频里「人批准拆分」那一步，长期保留。这一步估计约两分钟，没实测。

### 需要你答：看 trail 里的 gate 行

验证或收尾时，遇到只有你能批的事，实现者在 PR 分支的 `.audit/<票号>.tsv` 写一条 gate 行：问什么、为什么问、推荐怎么做、PR 链接。调度器读到 `result=open`，经企业微信 Bot 推你一条提醒。

你在 bot chat 里答：同意、不同意，或先搁置。工作台 bot 用 `gate.mjs answer` 把答案写进票分支的 `.audit`，提交并推送；那一行 `result=answered` 或 `parked`，调度器停止提醒。搁置的缺口留在 trail 里，最后的报告会列出来。

典型的一处是 `correct` 给检查加例外。`interrogate` 和 `no-comments` 的常规问题由调用方 agent 答，只有它们也定不了才升级给你。

不回就停在这条线，24 小时提醒一次。

### 客户卡住：回一句就够

客户在 `dsh` 里卡住，或答不上，会找客服。通道微信为主，电话兜底，话术见 `customer-kit/安装步骤.md` 的「客服带话」。比如客户问「送货费怎么算，我不敢写」，你回一句，把定下的答案告诉他。

客户说不懂的技术题，agent 已按推荐答案往下问，记进 `.scratch/{需求名}/pending.md`，并告诉客户「开工前会有人确认」。这些在开工前由你确认。

这一步不阻塞工厂。你不回他，单子也照样往下走，只是答案会缺一块。

### 每天早上抽样：合并之后看

工厂合主干之前，每个 PR 有一队验证 agent，没写过这份代码，像真实顾客那样点来点去找回归。合并前还有一次评审，分标准和 spec 两轴。两样都过了，工厂自己合主干，部署，客户收到地址。你不用点。

你每天早上看前一天合进主干的单。看什么、发现问题怎么处理，见第十节 E1。

### 出事：只有五种情况会叫你

1. 同一张票试了三圈还没进展。
2. 花的钱超过额度。
3. 碰到禁区。判据是两句话：这段改动能不能验证，出事了能不能回滚。有一条答不能，就停。
4. 同类问题跨票出现两次，它先自动加一条规则重跑，还不过就叫你。新规则要在出错那次的改动上亮红灯，做不到就不自动加，直接叫你。
5. 验证队和评审报的问题，实现者修了还是过不了。当环境问题，停这条线，通知你，附现象和试过的办法。你修环境，不替这个 PR 改结论。

你到了现场，能做的三件事：让它再试一次、换个做法、或者停掉等白天。

### 什么永远不自动

三条边界。

第一，五类技术问题不自动猜。猜错了返工，返工比等你贵。

第二，验证队和评审过不了的 PR，不自己合，也不自己放宽检查。放宽任何一道检查，要验证者的证明，再由你复签。

第三，涉及钱、数据、对外动作的业务参数，不当假设处理，要阻塞等客户答。其余可逆的参数，agent 写成「假设」并标记，客户事后由你经客服带话确认，怎么带归 #52。（推断）

### 为什么人挪到两头

视频默认 spec 和票都经人看过，拆票技能里写着「迭代到用户批准拆分为止」。我们把人挪到前后两头：前面是补缺口和拆票，中间可能有验证问答，后面是每天早上抽样。

挪的理由有两个。客户不懂技术，spec 和票没法让他批，只能你扫一眼。合并照素材：每个 PR 一队验证 agent，合并前评审，过了自己合，人在合并之后看模式，不看单个。

PR 里那层「这一改有多险」的信息，补成两栏：单向门还是双向门、影响范围。见第十节 E1。单向门不再让工厂停下，它决定你抽样先看哪些。

## 五、客户视角：一单怎么走

这一节从客户那边看，按幕讲。每一幕写三件事：客户看到什么、`dsh` 里的 agent 在做什么、工厂在做什么。客户那边的原话样本见 `docs/回传样例/客户侧流程样本.md`。技术细节在第六节到第十节。

### 第一幕 打开

**客户看到**：官网下载 `客户工作区-v1.zip`。新建一个空文件夹，把 zip 放进去，解压到当前文件夹。文件列表里要能看到 `AGENTS.md`。用 `dsh` 打开这个文件夹，说「开始需求澄清」，或直接说「我想做一个……」。

**agent**：第一次打开，还没有 `.scratch/`，先自检。查 `docs/agents/issue-tracker.md`、`docs/agents/domain.md`、`.dsh/skills/` 在不在。缺一个，就说「文件没放对，按官网第 2 步重放」，然后停下，不问需求。三样都在，再讲第一段开场词，请客户说想做什么。

**工厂**：不动。这时候还没有工单。

多套一层文件夹时，根目录里没有 `AGENTS.md`，agent 读不到自检规则。这一种只能靠官网第 2 步的肉眼检查和客服。自检本身 2026-11-07 #26 实测过：缺 `docs/agents/` 或 `.dsh/skills/` 时，agent 报「文件没放对」并停下，不问需求。

### 第二幕 判断大小，定终点

**客户看到**：agent 说一句「你先说你想做什么」。客户说一段模糊的想法。agent 判断大小。小的说一声「这件事不大，今天就能问清楚」。大的说「已经确定需要拆分」，然后一轮列出几个问题，把终点问成一句话。客户自己答。

**agent**：小需求有三条标准：改动落在一个已有功能里，一个会话做得完，验收条件客户已经说清。三条全满足才算小。缺一条走拆分，拿不准也走拆分。小需求用 `grill-with-docs`（追问加术语整理，一轮列出几个问题）问清楚，写 `.scratch/{需求名}/需求草稿.md`。大的用 `grill-with-docs` 问出终点，写进 `map.md` 的 Destination。技术题旁加一句「这题偏技术，不懂就按我的推荐」。客户说不懂，按推荐答案往下问，记进 `pending.md`。对客户不说技能名。

**工厂**：还是不动。

第二幕和第三幕在第一次对话里一次走完。

### 第三幕 拆成票

**客户看到**：终点定了，agent 讲第二段开场词。一张议题代表一个任务，一次对话只定这一件事。最怕三件事：在一张议题里聊另一张的事；说着说着拐到别处；在后面的议题里悄悄改前面定过的事。拆完把清单给客户看：一共几张，每张做什么。顺序由客户定。每张开头写一句，这次是聊、看个样子、动手做，还是去查。

**agent**：写 `.scratch/{需求名}/map.md`，六段。每个决定一个文件 `issues/NN-任务名.md`，票头写 `Type:`（票型）和 `Blocked by:`（被谁挡着）。客户定完顺序，写进地图「接下来」的行序。再按追踪器文档的「选票」规则选第一张，给出一行「继续：需求名 编号 票名」。

**工厂**：不动。

### 第四幕 一次对话一张票

**客户看到**：新开一次对话，把收尾给的那一行原样复制过来。agent 先说走到哪、这次做什么，再做这一张。做完四句话收尾。看个样子的票，agent 做一个单文件 HTML 放进 `prototypes/`，客户双击就能开，看图说话，改两轮。

**agent**：客户发「继续：需求名 编号 票名」，就直接做那张。只发「继续」二字，按追踪器文档的「选票」规则选，有 `Status: claimed` 的票先接着做。开工先把票头 `Status:` 改成 `claimed`，按 `Type:` 调技能：聊用 `grill-with-docs`，看个样子用 `prototype`，我去查用 `research`，动手做用 `task`。客户没听懂，先换短话重讲，再举例子或给选项；答不了、要问别人，写一段能直接转发的话，票保持 `claimed`，答案带回来再写结论。写结论前不另起子代理查冲突；客户的话明显推翻前面定过的内容时，按「改前面定过的结论」处理。结论写一句能独立读懂的话，下一行写「产出文件：相对路径」。收尾由 agent 自己说四句并给继续行，不跑子代理；固定句在 `AGENTS.md` 里只写一份。

**工厂**：不动。

### 第五幕 回传

**客户看到**：全部做完，agent 先清一遍还没问清的事，再说文件核过了，然后提醒客户压缩整个文件夹，到官网上传页登录后拖入，简称和邮箱由账号带出，勾「已问完」。然后等我们联系。文件夹里所有文件都会上传。对话记录在 `~/.dsh/sessions/`，不在工作区里，v1 不回传。

**agent**：不写 `meta.json`，不问简称。说上传之前，先清 `Not yet specified`，再按追踪器文档的「收尾与回传」核八项，包括 `.scratch/` 下有没有这次新加的需求目录。核不过不让上传。

**工厂**：服务器读 `.scratch/`，看四样：勾了「已问完」，`验收场景.md` 在，其余单每张票都是 `resolved`、地图「接下来」为空。小需求改看 `Status: 已问完`。都满足才自动做三件事：建客户仓、建工单、把需求写进仓库。第一次建仓；同一个软件的后续单复用已有仓，只建新工单和新分支。父工单五段从回传件读：客户原话看 `问答记录.md` 开头（小需求看 `需求草稿.md` 第 1 段），结论看 `map.md` 的 Decisions so far，验收条件看 `验收场景.md`，不做清单看 `Out of scope`，需求全文是整个 `.scratch/{需求名}/`。不满足只存快照，不建单。建仓和建单的顺序不能反，票要挂在工单下面，两者得同仓。调度器读到新单，经企业微信 Bot 推你一条。

上传页和接收端点已建（2026-11-15，I-0086），见 `docs/客户工作区.md` 的「回传」一节和 `docs/后端服务.md`。Windows 右键压缩会带上隐藏的 `.scratch/` 和 `.dsh`，2026-11-16 实测，见 `customer-kit/测试记录.md` 的 I-0050 一节；Mac 没验证。

### 第六幕 工厂接手

**客户看到**：上传完成，等我们联系。之后靠微信和邮件收到五档进度，见 `docs/客户进度.md`。

**agent**：不在客户本机跑了。

**工厂**：服务器校验、建仓建单，调度器推进。你出现的地方见第四节，技术细节见第六节到第十节。

## 六、阶段 A：接单

客户在自己机器上装好 `dsh`，一次坐下做完。装的时候人工客服带一下（#23）。我们不在场。

**A1 开口。** 客户解压工作区 zip，用 `dsh` 打开。新需求第一次说「开始需求澄清」，或直接说「我想做一个……」。agent 第一次打开先自检，缺文件就停下，不问需求。通过后，客户还没说想做什么，就问一句「你想做什么？」然后停下；已经说了，讲完开场那段，直接判断大小。之后每次新开对话，客户原样复制上次收尾给的一行。这一行按 `AGENTS.md` 的固定句给出，形如「继续：tanxin-yuyue 01 空档怎么放」。没有装配提示词，提示词②只剩这两句。工作区 zip 从网站下载，技能和 `AGENTS.md` 已在包里。（开口方式：已定，Y-001。提示词②见 `docs/客户工作区.md` 的「agent 靠什么执行」一节。工作区做法见 `docs/客户工作区.md` 第一节）

**A2 按轮问。**（2026-11-13 客户侧流程 v2 改法，见 D-0096、D-0118、D-0131。做法出自 `grilling` 和 `grill-with-docs` 原文）

1. 客户侧的聊类工作统一用 `grill-with-docs`（内部是 `grilling` 加 `domain-modeling`）。小需求直接用；大需求先用它定终点。一轮列出几个问题，每题带推荐答案，并先用一两句话交代背景。
2. 客户答完一轮，agent 再问下一轮。题和题之间的依赖由 agent 自己掌握，依赖还没定下来的题留到下一轮，也不显示「n / 总数」。
3. 事实归 agent 查。客户提到现有网站或同行做法，派子 agent 去看，不问客户。（素材：原文）
4. 决策归决策的人。客户答；客户给倾向、你最后定；你答；agent 自查。后两类不问客户，也不写进客户看的文件，留到 C1 问你。（素材：原文。四类标法是我的）
5. 客户说「看不懂」，agent 用客户自己的词换个说法重讲。还不懂，举两三个具体例子，或把这道题拆成几个选项，每个带推荐答案。原型不在这里做，见 A2a。（有出处）
6. 开口越模糊，题越多（S6）。这是正常现象，不设上限去压。（素材）
7. 问生意时不出现技术词。技术后果用人话写，带推荐。（已定）
8. 分流。听完客户第一段话后，agent 判断这单走哪条路，只分两类。同时满足三条才算小需求。一，改动落在一个已有功能里。二，一个会话做得完。三，验收条件客户已经说清。缺一条，就走 wayfinder。小需求跳过 spec 和拆票，直接实现。其余走 wayfinder，只出决策，不出代码。判据拿不准，也走 wayfinder。不设升级、降级和回退规则。（已定，G-009，取代 G-003）本条只管客户单；本仓自己的任务怎么选入口，见 `docs/agents/issue-tracker.md` 的「开工前先选方法」。小需求回传后建一张实现票，由工作台 bot 在补缺口点头时建，见 `docs/工单模型.md` 的「小需求的实现票」。
9. 客户答不了的题，转给第三人。比如答案在合伙人、会计、懂技术的朋友手里。agent 写一段能直接转发的话，写明问题、背景、选项和推荐；客户转给对方，再把答案带回来。前五单数一数用了几次，再决定留不留。（已定，G-004。本机化是推断，见 #22。to-questionnaire v1 不进客户技能包，2026-11-07 运营者定）
10. 澄清一律在客户本机跑，不再分「碰不碰客户电脑」。成品部署在我们管理的香港服务器上，不装在客户机器上（D-0317）。

## 七、阶段 B：建仓建单

### B1 建仓与建单

顺序不能反：先建客户仓，再建 parent issue。触发点是服务器校验通过：客户在上传页勾了「已问完」，`验收场景.md` 在，且其余单每张票都是 `resolved`、地图「接下来」为空（小需求看 `需求草稿.md` 的 `Status: 已问完`）。

一个软件一个仓。第一次建某个软件的仓时，脚本先建出仓壳，只放初始 commit 和骨架；然后在这个仓里建 parent issue。同一软件的后续单复用已有仓，只建新父工单和新需求分支。仓名用这个软件第一张单的需求名当软件简称，形如 `<客户简称>-<软件简称>`。服务器先读上传包根目录 `软件.md` 认软件。再看 `customers.json.repos[软件简称]` 认仓。旧工作区没有这个文件时，按 `.scratch/` 里出现的 `customers.json.repos` 已知键回退。上传里已经有订单的需求目录跳过，没有订单的建新单。第二个软件的第一张单校验通过时，按同一条路径建新仓。父工单五段按客户包追踪器文档的「回传件结构」读：客户原话、客户确认的结论、验收条件、不做清单、需求全文。客户确认的结论，小需求取自 `需求草稿.md` 的「已经定下的」，其余取自 `map.md` 的 Decisions；验收条件取自 `验收场景.md`。子票挂在 parent 下面，必须同仓。仓没建出来，单没处落。

工单标题用客户那句话。正文五段、四个状态标签、迁移规则，都在 `docs/工单模型.md`，这里不抄。

### spec 之后：素材原样

**C2 /to-spec。**（素材：原文）调度器自动执行。读仓库，用项目词汇，守决策记录。定接缝，用 C1 的结果。按七字段模板写：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。不加第八个字段。不写文件路径和代码片段。

- 锁单点是父工单的 `点头：补缺口`。`to-spec` 由调度器在点头后自动跑；生成 spec 后，工厂直接发成 issue，标题带需求名，挂 `ready-for-agent`，这个标签只作拆票信号。发 spec 前 agent 要重读父工单最新关口，不是 `点头：补缺口` 就不发；发布后发现已解锁，作废这张 spec。客户要重传，得先由运营者写 `改口：重传` 解锁。仓库里可放一份只读副本 `docs/specs/<issue>-<slug>.md`，由脚本从 issue 同步，以 issue 为准。
- 用户故事要覆盖客户确认的每一条场景。

**C3 /to-tickets。**（素材：原文）垂直切片，一片穿过每一层，单独能演示，装得进一个新会话。每张票写验收条件和阻塞边。宽重构是例外，按 expand-contract 排（先加新写法，再分批迁移，最后删旧的）。别切太细：S6 演示里 13 张被嫌太细，改成 5 张。

- 每张票挂成父工单的 sub-issue。拆票先出草案，运营者点头后才建票。
- 子票建出来只挂 `状态:排队中`，不挂 `ready-for-agent`。队列标签 `Sandcastle` 由调度器点火时贴给这一轮选中、没有未关闭阻塞的子票；子票进入 `状态:待验收` 或关闭后摘掉。
- 点火前查有没有活，看子票状态和父工单评论，不看队列标签。spec 只挂 `ready-for-agent`，父工单只挂 `状态:*`。

**C4 你在 bot chat 里说「按这个拆」（第 2 次）。**（素材：to-tickets 第 4 步，迭代到用户批准）工作台 bot 在 chat 里给你接缝、票单、每票验收。这一下长期保留，数你改了几次。（已定）

## 十二、验收条件怎么拿

验收条件靠改，不靠问。客户给现象，agent 给草稿，客户只做一件事：指出哪条不对。

七步：

1. **要一个场景。** 问「上一次这件事发生是什么时候？从头到尾讲一遍」。客户会讲出人、步骤、卡点。
2. **找「行了」的那一刻。** 问「哪一刻你会说行了？眼睛看到什么？手上做了什么？」客户说「好用」，就追问「哪个页面？上面有什么？」说不出来，就让他讲现在怎么做：「微信接龙，做完之后哪一步会消失？」
3. **agent 按模板写草稿。** 每条一个句式：谁，从哪进，做什么，看到什么，什么算不对。一轮给三到六条，每条只写一个行为。
4. **读回去，问「哪条不对」。** 不要问「对不对」，客户会顺口说对。逐条读，让他挑错、删、改。他改的那一句，往往才是真正的验收条件。
5. **做可测检查。** 每条问：能不能点一遍看出来？不能就改写，或者标「人工判断」。「老板知道要备多少」测不了；「后台按时间段分组显示订单」能测。
6. **客户逐条确认。** 每条读出来，让客户挑错、删、改，改完点头。
7. **冻进四个地方。** 客户确认的 `验收场景.md`、parent issue 里确认后的场景、每张票只放它负责的那几条、验证技能。spec 只有七个字段，不加验收条件这一栏，用用户故事覆盖每条场景。

第七步最后一项是关键。验收条件不只给你看，也给 agent 自检。

### B 店走一遍

### 缺口要回客户

纸面推演时，这单卡在一处：一个时段放几单，客户没说。

这属于业务规则，归客户定，技术闸门管不到。默认值要先给，比如每时段 10 单，再让客户改。没有这个数，第 3 条验收条件写不出来。

所以验收条件不会一次问完。拆票时会暴露缺口，缺口回客户补一条。这个回路要有，不然 agent 会自己编一个数。

### 主机 agent 的权限

主机 agent 只读写文件和跑 `gh`，不给 shell。启动方式：

```bash
claude --restricted \
  --tools "Bash,Read,Write,Edit,Glob,Grep" \
  --settings <调度器生成的 settings.json> \
  --model ccs-claude-deepseek--deepseek-v4-flash[1M]
```

三道限制：

1. `--restricted` 拿走 Bash、PowerShell、WebFetch 这类能执行命令或联网的工具。文件工具限制在工作目录内，忽略用户、项目、本地设置，拒绝 `bypassPermissions`。
2. `--tools` 只把 `Bash`、`Read`、`Write`、`Edit`、`Glob`、`Grep` 放回来。
3. `PreToolUse` hook 挂在 `Bash` 上，只放行 `gh`。命令不以 `gh ` 开头就拒；带分号、与号、竖线、美元符、反引号、重定向符号或换行也拒。

hook 输出：

```json
{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "host agent may only run gh"}}
```

放行时把 `deny` 换成 `allow`。

正文走 `gh issue comment --body-file <路径>`，避免正文里的分号和管道符号被 hook 挡住。

验过的（2026-11-15，本机）：

- `claude --restricted --tools "Bash,Read,Write,Edit,Glob,Grep" --settings <含 hook 的配置>` 下，`ls -la` 被拒，`gh --version` 能跑。
- `--restricted` 下不给 `--tools`，Bash 工具直接不在。

没验的：

- hook 在调度器真实 brief 下跑完整 `/to-tickets`。
- gh 子命令白名单的完整清单。实现时按 `/to-tickets` 实际调的命令定，至少要有 `issue`、`pr`、`repo`、`label`，以及旧版 `gh` 用的 `api`。
- `gh alias`、`gh extension` 能让 gh 执行别的命令，白名单必须排除这两个。

### 容器凭证

Sandcastle 只转发 `.sandcastle/.env` 里出现过的键。宿主环境变量不会自动进容器。

```bash
ANTHROPIC_AUTH_TOKEN=<中转 token>
ANTHROPIC_BASE_URL=http://host.docker.internal:15721
ANTHROPIC_MODEL=ccs-claude-deepseek--deepseek-v4-flash[1M]
ANTHROPIC_DEFAULT_HAIKU_MODEL=ccs-claude-deepseek--deepseek-v4-flash[1M]
ANTHROPIC_DEFAULT_SONNET_MODEL=ccs-claude-deepseek--deepseek-v4-flash[1M]
ANTHROPIC_DEFAULT_OPUS_MODEL=ccs-claude-deepseek--deepseek-v4-flash[1M]
CLAUDE_CODE_EFFORT_LEVEL=max
GIT_AUTHOR_NAME=AFK Factory
GIT_AUTHOR_EMAIL=factory@afkfactory.dev
GIT_COMMITTER_NAME=AFK Factory
GIT_COMMITTER_EMAIL=factory@afkfactory.dev
GH_TOKEN=<onboarding 按仓换的 1 小时 token，只限当前客户仓>
```

- 一共 13 个键（含 `SANDCASTLE_IMAGE`）。前六行是模型鉴权，少一个键，容器里的 Claude Code 报 `Not logged in`。
- `ANTHROPIC_BASE_URL` 必须写 `host.docker.internal`。写 `127.0.0.1` 会连到容器自己。
- `CLAUDE_CODE_EFFORT_LEVEL=max` 是推理档。宿主机启动主机 agent 时也要带。
- 四个 git 键给容器里的 `git commit` 用。镜像里没配全局身份。
- `GH_TOKEN` 由 onboarding 用 GitHub App 按当前仓换，1 小时过期；权限是 Issues、Pull requests、Contents、Workflows 读写。pstack 的 PR 操作只用 gh。
- `.env` 在 `.gitignore` 里。凭证不进仓库，也不进客户拿到的代码 zip。

没验的：

- `GH_TOKEN` 在容器里跑 `gh` 的完整链路。2026-11-15 的 docker 实测只验到模型凭证，没验 gh。
- `CLAUDE_CODE_EFFORT_LEVEL=max` 在容器里是否生效。宿主机上生效。
- `ANTHROPIC_MODEL` 只当默认值；`run()` 会按角色显式传模型。容器里只靠这个键时没验。

### Mac 常驻

调度器和回传件拉取由 launchd 管，Mac 重启后自动起。

| 任务 | Label | 干什么 | 日志 |
| --- | --- | --- | --- |
| 回传件拉取 | `com.afkfactory.pull-inbox` | 每 5 分钟跑一次 `factory/bin/pull-inbox.mjs` | `~/.afkfactory/logs/pull-inbox.log` |
| 调度器 | `com.afkfactory.scheduler` | 常驻跑 `factory/bin/scheduler.mjs --loop`，异常退出由 launchd 拉起 | `~/.afkfactory/logs/scheduler.log`；每轮另写 `~/.afkfactory/logs/scheduler-runs.jsonl` |

安装：

```bash
node factory/bin/install-launchd.mjs --repo-root <仓库路径>
```

装完复查：

```bash
node factory/bin/install-launchd.mjs --verify
```

安装会写 plist 和 wrapper，加载两个任务，再检查 `launchctl print`、scheduler 进程、pull-inbox 上次退出码，以及有没有 launchd 之外的第二份调度器。退出码 0 才算装好。缺一项就列出任务名。重装直接再跑一次，脚本先卸旧任务；检查不过会回滚。

常驻只用 launchd 这一条路。不要再用 `nohup` 手工起一份调度器，两份同时跑会重复点火。

凭证只从 `~/.afkfactory/env` 读，plist 里不放 token。env 文件路径可用 `AFK_ENV_FILE` 换。需要的键：

- `AFK_SERVER`（或写完整命令的 `AFK_HELPER`）
- `AFK_SSH_KEY`
- `GITHUB_OWNER`
- `GITHUB_TOKEN`
- `GITHUB_APP_ID`
- `GITHUB_APP_INSTALLATION_ID`
- `GITHUB_APP_PRIVATE_KEY`（默认 `~/.afkfactory/github-app.pem`）
- `ANTHROPIC_MODEL`（或 `AFK_AGENT_MODEL`）

`GITHUB_TOKEN` 是控制面用的细粒度 PAT。容器里的 `GH_TOKEN` 不走它，由 GitHub App 按仓换 1 小时 token，写进客户仓 `.sandcastle/.env`。

调度器启动时先自检这些键，探测一次模型，再校验 `customers.json` 的形状。缺键或格式错就退出，错误里写键名和查过的文件，不带着空配置去匿名请求。运行中每轮看 `customers.json` 的 mtime，变了就重读并重新校验；形状不对当轮报错，不沿用旧表。

调度器状态只在 GitHub。进程重启后按标签和阻塞边重新推导，不重复点火。

## 二十、pstack 怎么接

结论：用 pstack 的做法，不装插件。

读到的事实（2026-11-03，只读，没装，没跑任何脚本）：

1. 官方版是 Cursor 插件。仓库 `cursor/plugins` 的 `pstack/`，提交 `ae5650f`，版本 0.15.36，MIT，版权 Lauren Tan，58 个技能。验证队用到的剧本 `autopilot-full`，并行验证 `swarm`，攻击改动 `interrogate`，都在里面。
2. 这些写给 Cursor 云端 agent。`autopilot-full` 写明每个实现者（owner）是 Cursor 云端 agent。`swarm` 里写死云端环境。`swarm` 和 `arena` 从 `~/.cursor/rules/pstack-models.mdc` 读模型分工。我们的执行在 Sandcastle 容器里，原文装上去跑不起来。
3. Claude Code 有社区移植版 `michael-denyer/pstack-claude`，提交 `513c088`，MIT 加两份 Cursor 的许可文件。它带一个 SessionStart 钩子：每个会话开始，往上下文里注入一段「You have pstack」的强制说明，让任务走 poteto-mode。装进 `~/.claude` 会改变你所有项目的会话，还要和 superpowers 并存。所以不装。

做法（推断，没验）：

1. 只借剧本和技能原文。钉在 `ae5650f`，复制进工厂自己的技能目录，每个客户仓装的时候带上。
2. 改写 Cursor 专有的部分。云端 agent 改成 Sandcastle 容器里的子 agent。`pstack-models.mdc` 改成第十九节的角色表。
3. 借的清单：`autopilot-full`、`swarm`、`interrogate`、`blast-radius`、`create-verification-skill`（带功能地图的例子）、`correct`、`no-comments`。这七项引用到的另装：`comment-sicko`（agent）、`show-me-your-work`、`in-your-own-words`、四个 `principle-*` 技能。arena、shipping、opening-a-pr、babysit、ketchup 不装，取舍见 `factory-skills/pstack/CHANGES.md`。
4. 改写已由 Claude Code agent 完成，在 `factory-skills/pstack/`，逐文件改动见 `CHANGES.md`。11-03 你说「定」。客户仓模板还没建，建好时接进去。没解决的问题和没验的事，见 `CHANGES.md` 的两节同名小节。

`autopilot-full` 里照搬的规则（原文第 2 到 7 步，改写时以原文为准）：

1. 一个实现者从做到合一个 PR。验证队没写过这份代码。
2. 完整验证队在代码就绪的提交上只跑一次。之后的小改只派一个验证者，只改文字的不派。
3. 只因能演示的问题拦下：一次失败的运行，或一行被 PR 改错的文档。其余记成后续事项。
4. 绿灯 CI 本身不放行。合的是验证者证明过的那版代码。
5. 合并前看主干有没有动到补丁依赖的东西。动了才重新跑，不为每次主干变动都重来。
6. 放宽任何一道检查，要验证者的证明，再加一次新的复签。关掉或只报警不拦的检查，一律拿掉。
7. 每隔一段时间巡检所有 agent，按它留下的痕迹判断是不是卡住，不看它自己写的状态。这条对应调度器每 30 秒对账。
8. 收到停止指令，所有实现者零写入。
