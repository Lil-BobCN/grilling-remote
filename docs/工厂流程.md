## 一、目标与边界

一台 Mac 加一台云服务器，一个运营者，接多个不懂技术的客户。

三个前提：

- 客户不写 spec，不读 diff。他只说现象、改草稿、点确认。
- 你不盯中间。必点两次：补缺口（C1）、拆票（C4）。特大单的前五单，开 wayfinder 图之前再点一次。合并后你每天早上抽样看。临时还有两处：客户留言、出事。
- 客户仓的规则、凭证、验证技能由工厂建，客户不碰。

无人化的边界：中间无人值守，前面有人点头，后面有人抽样。

前面点头，后面抽样，中间才敢放。这是无人化能成立的条件，不算退让。

## 二、四层

| 层 | 回答什么 | 谁负责 | 产出 |
| --- | --- | --- | --- |
| 接单 | 要什么、怎么算成 | 网页 agent + 客户 | 确认单 + 验收条件 |
| 设计 | 怎么做、拆几张票 | 机器，你点两次 | spec + 票 + 依赖 |
| 执行 | 谁先跑、在哪跑 | 调度器 + Sandcastle | 分支 + 提交 + 证据 |
| 治理 | 什么时候停、谁点头 | 你 + 规则 | 抽样、停法、复盘 |

工具落点：客户的浏览器接单；服务器接单、开网页、推微信，存草稿、账号和提醒记录，不存工单；你的 Mac 跑调度器和容器；GitHub 存工单、代码、PR 和证据；Orca 是你点闸门、拆票的地方。

原则一条：每层只由一个东西负责。研究文档和技能都是零件，不抢流程的位置。

### 执行器和调度器

Sandcastle 不是唯一的执行器。D2 之前不用它，不等于人工执行。活由网页 agent、主机 agent 和确定性脚本干；唯一进沙箱的是生成 verify 技能那一跑。

| 执行器 | 跑什么 | 在哪 | 为什么分开 |
| --- | --- | --- | --- |
| 网页 agent | A1 到 A5 接单；A2a 里在服务器上写原型页，只写文件，不给 shell | 服务器 | 客户在浏览器里对话，没有仓库 |
| 主机 agent | B2 四份文档、C2 写 spec、C3 拆票、E3 复盘 | 你的 Mac，仓库直接挂载 | 只读写文档和 issue，不跑客户代码 |
| Sandcastle | B2 生成 verify 技能、D2 实现、D3 自检、D4 评审 | 容器，一票一个 worktree | 要跑代码、要隔离、要并行、要收提交 |
| 确定性脚本 | B1 建仓建单、B2 机械项、C1 算闸门、D1 对账、D5 合并、E1 部署 | 服务器和调度器 | 不需要模型判断 |

主机 agent 只给读写文件和 `gh` 的权限，不给 shell。要跑代码，进 Sandcastle 或预览环境。

技能不用你敲命令。调度器读工单，决定下一步，替你叫一个 agent 去读那份技能说明。

这张表的意思是：D2 之前的活由网页 agent、主机 agent、脚本和一次沙箱跑干完，不是你的手干的。你的手只在 C1、C4 出现，特大单的前五单开 wayfinder 图之前再加一下。E1 不再等你点，你每天早上抽样。

#### 调度器和 Sandcastle 的分工

调度器是控制面。它读工单状态，决定下一步，叫执行器干活，再把结果写回工单。它自己不写代码。

Sandcastle 是执行面的一种。给它 agent、沙箱、prompt，它跑一次，收回提交。它不知道整张单走到哪，也不决定下一步。

调度器是普通程序，不是模型。判断靠标签和阻塞边，所以重启接得上。Sandcastle 是调度器代码里的一个函数调用，不会反过来叫调度器。

骨架不止调度器。还有三样：工单状态、证据规则、权限边界。Sandcastle 是手臂，可以换。

```text
每 30 秒：
  读所有 open 工单和标签
  找出该动没动的
  缺 spec    → 叫 Mac 上的 agent 写
  票就绪    → 叫 Sandcastle 跑一张
  证据齐    → 叫合并脚本
  等你定    → 不动，发提醒
  把结果写回标签和评论
```

#### 调度器凭什么做决定

它不做内容判断，只做路由判断。路由判断能写成一张表：

| 它看到什么 | 它做什么 |
| --- | --- |
| 工单标了「已确认」，闸门没答 | 列闸门，推给你 |
| 闸门答完，仓库里没有 spec | 叫 agent 写 spec |
| 有 spec，没有子票 | 叫 agent 拆票 |
| 有子票，没点头 | 停，等你 |
| 点头了，有没阻塞的票 | 叫 Sandcastle 跑 |
| 票跑完，证据不齐 | 叫自检 |
| 四样证据齐 | 叫合并脚本 |
| 子票全部完成，需求分支没评审 | 叫评审，写 /pr，再叫验证队 |
| 验证队和评审都过 | 叫合并脚本合主干，部署 |

左边全是可检查的事实：标签、文件、子票状态、证据标记。右边全是固定动作。没有一行需要读懂客户在说什么。

需要思考的部分，都在被叫的 agent 里：写 spec 的 agent、写代码的 agent、评审的 agent。调度器只负责把活递过去。

它像行李分拣线：扫条码，放上对应的传送带。它不知道箱子里是什么。条码错了，箱子就上错飞机。所以功夫要花在条码上，不是让分拣线变聪明。

状态对不上任何一行，它不猜，标 `needs-info` 推给你。

#### 调度器要不要自己写

不用从零写。已经有两个开源的近亲。

`@copperbox/sandcastle-workflow` 是 npm 包加一条 shell 循环。它做的正是 D 段：把 issue 分成 feature，每个 issue 在自己的 Docker worktree 里实现和评审，合进 feature 分支，冲突由 agent 解，跑 verify，开 PR。状态全在 git 和 GitHub 里，进程被杀，下一轮重新推导。

`sandcastle-kit` 是另一种：队列标签、实现加评审、跑项目自己的 lint/build/test、合到本地、出报告。它不推送，也不开 PR。

两个都缺我们的前半段：客户接单、五类闸门、拆票点头、预算和停法、多客户路由。

定了：每个客户仓装一份 `sandcastle-workflow`，我们只写工厂层。它 MIT，版本 0.4.2，作者一个人，星星很少。要 vendor 进来锁版本，不能当黑盒依赖。

它的分组是 planner 每轮重算。我们按 parent issue 固定成员，这一点要改。

## 三、全流程图

两段。中间一条硬线：两边的待问清单都为空，才准写 spec。

```text
客户说一句话
  │
  ▼ A 接单：客户 + 网页 agent
分轮问：生意 → 载体 → 技术后果 → 场景里会卡住的地方
验收场景草稿，客户删改 → 确认单，客户点头
  │
  ▼ B 建仓建单：脚本。模板仓、验证技能、功能地图
  ▼ C1 补缺口：你点第 1 次
  │
══ 两边的待问清单都为空。这条线以前，没人写 spec ══
  │
  ▼ 以下照素材原样
C2 /to-spec（七字段，发成 issue）→ C3 /to-tickets → C4 你点「按这个拆」（第 2 次）
  │
  ▼
D 调度器逐票跑：/implement、/tdd、沙箱、验证、评审
  │  四样证据齐了，票合进需求分支
  ▼
全部票完成，需求分支上评审一次，写 /pr 四栏
  │
  ▼ E1
每个 PR 一队验证 agent，合并前评审。过了：工厂自己合主干，上线
过不了：当环境问题，通知你。你每天早上抽样一次
  │
  ▼
E2 上线 → E3 复盘 → F 外循环：上线后的反馈进新单
```

你必点两次：C1、C4。特大单的前五单，开 wayfinder 图之前再点一次。合并不再等你点，你每天早上抽样一次。客户留言和出事时另叫你。

## 四、阶段 A：接单

客户在场，一次坐下做完。

**A1 开口。** 输入框加例句加行业词。agent 先复述客户那句话。（已定，Y-001）

**A2 分轮问。**（已定，Y-003、Y-007。做法出自素材）

1. 三段是依赖层。后一段的题挂在前一段的答案下面。前一段没问完，后一段不出现。（已定，Y-003）
2. 段内照 grilling 原文。每一轮把此刻能问的全部问题问完，同一屏放下。每题带推荐答案，措辞让答「是」就等于接受。（素材：原文，S4，S6）
3. 答完，agent 重算待问清单，开下一轮。没有题数上限，也不显示「n / 总数」。到清单为空才算问完。（素材：原文）
4. 事实归 agent 查。客户提到现有网站或同行做法，派子 agent 去看，不问客户。（素材：原文）
5. 决策归决策的人。每题标明谁答：客户答；客户给倾向、你最后定；你答；agent 自查。后两类不上客户屏幕。（素材：原文。四类标法是我的）
6. 客户点「看不懂」，agent 用客户自己的词换个说法重讲（S4 的 wait what）。还不懂，升到原型，见 A2a。原型还看不懂，再转给你。（有出处）
7. 谈不拢的题，比如页面长什么样，做一次性原型让客户点选，再回来问（S4）。双手机预览先顶这个位置。（有出处）
8. 开口越模糊，题越多（S6）。这是正常现象，不设上限去压。（素材）
9. 第 1 段一个技术词都不出现。第 3 段的技术后果用人话写，带推荐。（已定）
10. 分流。第一轮问完后，系统判断这单走哪条路。小单跳过 spec 和拆票。大单走全套。特大单一个会话装不下，走 wayfinder（原文：一个会话装不下，才用它）。系统看三个信号。一，客户肯不肯「第一版只做一条主流程」（准入清单第 8 问，不肯就升级 wayfinder）。二，第一轮之后，互相独立的大块有几个，由网页 agent 数。三，本会话已用的上下文有多大，由程序数 token，阈值等第十七节定了模型再定。前五单，开 wayfinder 图之前你点一次头。（已定，G-003。三个信号是推断，没验）
11. 客户答不了的题，多一条出路：转给第三人。比如答案在合伙人、会计、懂技术的朋友手里。agent 用 to-questionnaire 的做法：先问发给谁、要回什么，再只针对缺口出题。对方点一次性链接，在网页上一题一题答，只能答被转过来的那几题，不开账号。状态多一种「等第三人」，提醒照 24 小时一次。前五单数一数用了几次，再决定留不留。（已定，G-004。素材：to-questionnaire 原文。原文输出 Markdown 文件，网页化和一次性链接是推断）

下面三段的题只是起点。agent 按答案往下问，问到待问清单为空。

第 1 段只问生意，起点是这 5 问：

1. 给谁用。
2. 进来第一件事做什么。
3. 现在这件事怎么做。
4. 做完看到什么会说「对了」。
5. 有没有明确不要的。

第 2 段问载体和走向，起点是这 4 问：

1. 微信小程序、公众号、网页、独立 App。
2. 顾客怎么找到你：扫码、发链接、搜得到。
3. 要不要在线付钱。
4. 有没有现成东西要接。

第 3 段先问经验，再问技术后果，起点是这 3 问。技术后果用人话写，带推荐，客户给倾向，运营者最后定：

1. 你自己做过网站或小程序吗。
2. 数据放哪、账号用谁的。
3. 每月愿意花多少。

**规则**：一屏一轮。每题带推荐答案，3 到 5 个可点选项，永远留「我自己说」。客户没动的题，按推荐算。客户看不懂，走下面 A2a 的台阶。答完能改。第 1 段一个技术词都不出现。

**客户看到**：左边一屏一轮，右边双手机预览（Y-005 不变）。预览下面列「已定」清单，加一句「这一轮 k 个问题」。前面是顾客看到的，后面是他的后台。每答一题，手机上的东西变一次。第 3 段答完，弹一次「今天，和以后」对照。

**依据**：Y-003、Y-007、grilling 和 wayfinder 原文（2026-11-03 读取，1.3.1）、准入清单 14 问、需求澄清研究 8 问。研究里「必答 ≤ 8」的预算不再沿用，该文自己标的是设计直觉。

**A2a 看不懂时的台阶。**（已定，G-005、G-006）

1. 第 0 级：每题的选项旁带示意图和例句。agent 把题、选项、推荐答案输出成数据，前端用固定组件画。（推断）
2. 第 1 级：客户点「看不懂」，agent 用客户自己的词重讲一遍。（有出处：wait-what 原文。原文要求英文受控语法，中文规则要另写）
3. 第 2 级：还不懂，agent 写一个单文件 HTML 原型，放进隔离小窗，客户点着看。先用模板，客户说「都不像」再现场生成一版。现场生成时并行发请求，真流式输出，先出骨架（地图 #4）。状态放内存，不持久化（prototype 原文）。（有出处，网页化是推断）
4. 第 3 级：多屏联动，要在服务器沙箱里构建和截图。先不做。
5. 这几级用的技能是 `factory-skills/clarify/` 里的网页版：grilling、wait-what、to-questionnaire、prototype。原文另存在 `original/`，一个字没改。改写记录和服务器实测见该目录的 `CHANGES.md`。（有出处。实测只在命令行里做过）

**网页 agent 的权限。**（已定，G-006。规则是推断，没验）

1. 只给「写文件」工具，不给 shell。只能写进一个专用目录，不和令牌、数据库放一起。
2. 原型页放进隔离小窗。`iframe` 只开 `allow-scripts`，不开 `allow-same-origin`。页面头加内容安全策略，禁网络请求，禁外部脚本。
3. 原因：页面由模型写。客户说的话和它查到的网页，都可能夹带指令（提示词注入）。小窗里的坏页面，最多只能画图。
4. 这一条改变了上一版的做法：上一版里网页 agent 只管接单对话，不写文件。已落到本文第二节的执行器表。

**A3 验收场景。** 第 1 段答完「做完看到什么会说对了」，agent 起草场景。客户逐条删改，问「哪条不对」。写不出可测条目的，标「人工判断」。确认后的场景放进 parent issue。/to-spec 读它写用户故事。/to-tickets 从 spec 里拆到每张票。票上的验收条件只能从客户确认的场景里拆，要新造，回客户补一条。（已定，11-02，见本文第十节）

## 十、验收条件怎么拿

验收条件靠改，不靠问。客户给现象，agent 给草稿，客户只做一件事：指出哪条不对。

七步：

1. **要一个场景。** 问「上一次这件事发生是什么时候？从头到尾讲一遍」。客户会讲出人、步骤、卡点。
2. **找「行了」的那一刻。** 问「哪一刻你会说行了？眼睛看到什么？手上做了什么？」客户说「好用」，就追问「哪个页面？上面有什么？」说不出来，就让他讲现在怎么做：「微信接龙，做完之后哪一步会消失？」
3. **agent 按模板写草稿。** 每条一个句式：谁，从哪进，做什么，看到什么，什么算不对。先写 3 到 5 条正向，再写 2 条负向。一条只写一个行为。
4. **读回去，问「哪条不对」。** 不要问「对不对」，客户会顺口说对。逐条读，让他挑错、删、改。他改的那一句，往往才是真正的验收条件。
5. **做可测检查。** 每条问：能不能点一遍看出来？不能就改写，或者标「人工判断」。「老板知道要备多少」测不了；「后台按时间段分组显示订单」能测。
6. **客户在确认单上点头。** 放在五行确认单下面，一块「怎么算成」，逐条可改。
7. **冻进四个地方。** 确认单、parent issue 里确认后的场景、每张票只放它负责的那几条、验证技能。spec 只有七个字段，不加验收条件这一栏，用用户故事覆盖每条场景。

第七步最后一项是关键。验收条件不只给你看，也给 agent 自检。

### B 店走一遍

客户原话：「街坊在手机上看今天有啥，挑个时间来拿，我早上知道要备多少。别太复杂，老人家也要会用。不要在线付钱。」

草稿八条：

1. 顾客打开链接，不用登录，看到今天可订的货和取货时段。
2. 选时段、填手机号、提交，看到「订好了」和取货时间。
3. 时段满了，显示「这个时段满了」，不能下单。
4. 老板后台看到当天订单，按时间段分组，每单有手机号和取货时间。
5. 老板能打印这份清单。
6. 顾客取消，名额回到可订。
7. 不出现支付入口。
8. 不登录也能下单，不收身份证。

客户改：「第 5 条不要打印，我要发微信。」改成「老板能把清单复制成一条微信消息」。

### 缺口要回客户

纸面推演时，这单卡在一处：一个时段放几单，客户没说。

这属于业务规则，归客户定，技术闸门管不到。默认值要先给，比如每时段 10 单，再让客户改。没有这个数，第 3 条验收条件写不出来。

所以验收条件不会一次问完。拆票时会暴露缺口，缺口回客户补一条。这个回路要有，不然 agent 会自己编一个数。

## 十八、pstack 怎么接

结论：用 pstack 的做法，不装插件。

读到的事实（2026-11-03，只读，没装，没跑任何脚本）：

1. 官方版是 Cursor 插件。仓库 `cursor/plugins` 的 `pstack/`，提交 `ae5650f`，版本 0.15.36，MIT，版权 Lauren Tan，58 个技能。验证队用到的剧本 `autopilot-full`，并行验证 `swarm`，攻击改动 `interrogate`，都在里面。
2. 这些写给 Cursor 云端 agent。`autopilot-full` 写明每个负责人是 Cursor 云端 agent。`swarm` 里写死云端环境。`swarm` 和 `arena` 从 `~/.cursor/rules/pstack-models.mdc` 读模型分工。我们的执行在 Sandcastle 容器里，原文装上去跑不起来。
3. Claude Code 有社区移植版 `michael-denyer/pstack-claude`，提交 `513c088`，MIT 加两份 Cursor 的许可文件。它带一个 SessionStart 钩子：每个会话开始，往上下文里注入一段「You have pstack」的强制说明，让任务走 poteto-mode。装进 `~/.claude` 会改变你所有项目的会话，还要和 superpowers 并存。所以不装。

做法（推断，没验）：

1. 只借剧本和技能原文。钉在 `ae5650f`，复制进工厂自己的技能目录，每个客户仓装的时候带上。
2. 改写 Cursor 专有的部分。云端 agent 改成 Sandcastle 容器里的子 agent。`pstack-models.mdc` 改成第十七节的角色表。
3. 借的清单：`autopilot-full`、`swarm`、`interrogate`、`blast-radius`、`create-verification-skill`（带功能地图的例子）、`correct`、`no-comments`。这七项引用到的另装：`comment-sicko`（agent）、`show-me-your-work`、`in-your-own-words`、四个 `principle-*` 技能。arena、shipping、opening-a-pr、babysit、ketchup 不装，取舍见 `factory-skills/pstack/CHANGES.md`。
4. 改写已由 Claude Code agent 完成，在 `factory-skills/pstack/`，逐文件改动见 `CHANGES.md`。11-03 你说「定」。客户仓模板还没建，建好时接进去。没解决的问题和没验的事，见 `CHANGES.md` 的两节同名小节。

`autopilot-full` 里照搬的规则（原文第 2 到 7 步，改写时以原文为准）：

1. 一个负责人从做到合一个 PR。验证队没写过这份代码。
2. 完整验证队在代码就绪的提交上只跑一次。之后的小改只派一个验证者，只改文字的不派。
3. 只因能演示的问题拦下：一次失败的运行，或一行被 PR 改错的文档。其余记成后续事项。
4. 绿灯 CI 本身不放行。合的是验证者证明过的那版代码。
5. 合并前看主干有没有动到补丁依赖的东西。动了才重新跑，不为每次主干变动都重来。
6. 放宽任何一道检查，要验证者的证明，再加一次新的复签。关掉或只报警不拦的检查，一律拿掉。
7. 每隔一段时间巡检所有 agent，按它留下的痕迹判断是不是卡住，不看它自己写的状态。这条对应调度器每 30 秒对账。
8. 收到停止指令，所有负责人零写入。
