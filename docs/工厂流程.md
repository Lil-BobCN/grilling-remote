# 这间工厂怎么运转

一句话：客户在网页上说清要什么，验收条件由 agent 起草、客户删改；工厂把 spec 拆成票，在沙箱里逐票实现、自检、评审；证据齐了自动合进需求分支；你最多点三次，加一周一次复盘。客户留言和出事时再叫你。

> 2026-11-02 运营者拍板，这一版替换上一版，成为正稿。
>
> 每个接缝都标了状态：**已定** 指拍过板的；**已验** 指本机跑过的；**推断** 指我设计的，要先做小实验；**待定** 指还没拍板。

## 一、目标与边界

一台 Mac，一个运营者，接多个不懂技术的客户。

三个前提：

- 客户不写 spec，不读 diff。他只说现象、改草稿、点确认。
- 你不盯中间。最多点三处：技术闸门、拆票、验收。临时还有两处：客户留言、出事。
- 客户仓的规则、凭证、验证技能由工厂建，客户不碰。

无人化的边界：中间无人值守，两头有人点头。

两头痛，中间才敢放。这是无人化能成立的条件，不算退让。

## 二、四层

| 层 | 回答什么 | 谁负责 | 产出 |
| --- | --- | --- | --- |
| 接单 | 要什么、怎么算成 | 网页 agent + 客户 | 确认单 + 验收条件 |
| 设计 | 怎么做、拆几张票 | 机器，你点两次 | spec + 票 + 依赖 |
| 执行 | 谁先跑、在哪跑 | 调度器 + Sandcastle | 分支 + 提交 + 证据 |
| 治理 | 什么时候停、谁点头 | 你 + 规则 | 验收、停法、复盘 |

工具落点：客户的浏览器接单；服务器存工单、开网页、推微信；你的 Mac 跑调度器和容器；GitHub 存工单、代码、PR 和证据；Orca 是你点闸门、拆票、验收的地方。

原则一条：每层只由一个东西负责。研究文档和技能都是零件，不抢流程的位置。

### 执行器和调度器

Sandcastle 不是唯一的执行器。D2 之前不用它，不等于人工执行。活由网页 agent、主机 agent 和确定性脚本干；唯一进沙箱的是生成 verify 技能那一跑。

| 执行器 | 跑什么 | 在哪 | 为什么分开 |
| --- | --- | --- | --- |
| 网页 agent | A1 到 A5 接单 | 服务器 | 客户在浏览器里对话，没有仓库 |
| 主机 agent | B2 四份文档、C2 写 spec、C3 拆票、E3 复盘 | 你的 Mac，仓库直接挂载 | 只读写文档和 issue，不跑客户代码 |
| Sandcastle | B2 生成 verify 技能、D2 实现、D3 自检、D4 评审 | 容器，一票一个 worktree | 要跑代码、要隔离、要并行、要收提交 |
| 确定性脚本 | B1 建仓建单、B2 机械项、C1 算闸门、D1 对账、D5 合并、E1 部署 | 服务器和调度器 | 不需要模型判断 |

主机 agent 只给读写文件和 `gh` 的权限，不给 shell。要跑代码，进 Sandcastle 或预览环境。

技能不用你敲命令。调度器读工单，决定下一步，替你叫一个 agent 去读那份技能说明。

这张表的意思是：D2 之前的活由网页 agent、主机 agent、脚本和一次沙箱跑干完，不是你的手干的。你的手只在 C1、C4、E1 出现。

#### 调度器和 Sandcastle 的分工

调度器是控制面。它读工单状态，决定下一步，叫执行器干活，再把结果写回工单。它自己不写代码。

Sandcastle 是执行面的一种。给它 agent、沙箱、prompt，它跑一次，收回提交。它不知道整张单走到哪，也不决定下一步。

调度器是普通程序，不是模型。判断靠标签和阻塞边，所以重启接得上。Sandcastle 是调度器代码里的一个函数调用，不会反过来叫调度器。

骨架不止调度器。还有三样：工单状态、证据规则、权限边界。Sandcastle 是手臂，可以换。

```text
每 30 秒：
  读所有 open 工单和标签
  找出该动没动的
  缺 spec    → 叫 Mac 上的 agent 写
  票就绪    → 叫 Sandcastle 跑一张
  证据齐    → 叫合并脚本
  等你定    → 不动，发提醒
  把结果写回标签和评论
```

#### 调度器凭什么做决定

它不做内容判断，只做路由判断。路由判断能写成一张表：

| 它看到什么 | 它做什么 |
| --- | --- |
| 工单标了「已确认」，闸门没答 | 列闸门，推给你 |
| 闸门答完，仓库里没有 spec | 叫 agent 写 spec |
| 有 spec，没有子票 | 叫 agent 拆票 |
| 有子票，没点头 | 停，等你 |
| 点头了，有没阻塞的票 | 叫 Sandcastle 跑 |
| 票跑完，证据不齐 | 叫自检 |
| 四样证据齐 | 叫合并脚本 |
| 需求分支完，没验收 | 停，等你 |

左边全是可检查的事实：标签、文件、子票状态、证据标记。右边全是固定动作。没有一行需要读懂客户在说什么。

需要思考的部分，都在被叫的 agent 里：写 spec 的 agent、写代码的 agent、评审的 agent。调度器只负责把活递过去。

它像行李分拣线：扫条码，放上对应的传送带。它不知道箱子里是什么。条码错了，箱子就上错飞机。所以功夫要花在条码上，不是让分拣线变聪明。

状态对不上任何一行，它不猜，标 `needs-info` 推给你。

#### 调度器要不要自己写

不用从零写。已经有两个开源的近亲。

`@copperbox/sandcastle-workflow` 是 npm 包加一条 shell 循环。它做的正是 D 段：把 issue 分成 feature，每个 issue 在自己的 Docker worktree 里实现和评审，合进 feature 分支，冲突由 agent 解，跑 verify，开 PR。状态全在 git 和 GitHub 里，进程被杀，下一轮重新推导。

`sandcastle-kit` 是另一种：队列标签、实现加评审、跑项目自己的 lint/build/test、合到本地、出报告。它不推送，也不开 PR。

两个都缺我们的前半段：客户接单、五类闸门、拆票点头、预算和停法、多客户路由。

定了：每个客户仓装一份 `sandcastle-workflow`，我们只写工厂层。它 MIT，版本 0.4.2，作者一个人，星星很少。要 vendor 进来锁版本，不能当黑盒依赖。

它的分组是 planner 每轮重算。我们按 parent issue 固定成员，这一点要改。

## 四、阶段 A：接单

客户在场，一次坐下做完。

### A1 开口

**客户看到**：一句提问「你这店，想让人在网上做什么？」，下面一个输入框。再下面三句例子、六个行业词：预约、问价、登记、库存、收款、其他。

**网页 agent 做**：把客户那句话复述一遍，确认中心思想。然后开始问生意，一个问题都不碰技术。

**依据**：Y-001（首屏输入框）。研究第 1 条原本主张卡片，证据针对的是空白输入框。输入框加例子和行业词，是折中。

### A2 三段问

第 1 段只问生意，5 问：

1. 给谁用。
2. 进来第一件事做什么。
3. 现在这件事怎么做。
4. 做完看到什么会说「对了」。
5. 有没有明确不要的。

第 2 段问载体和走向，4 问：

1. 微信小程序、公众号、网页、独立 App。
2. 顾客怎么找到你：扫码、发链接、搜得到。
3. 要不要在线付钱。
4. 有没有现成东西要接。

第 3 段先问经验，再问技术后果，3 问：

1. 你自己做过网站或小程序吗。
2. 数据放哪、账号用谁的。
3. 每月愿意花多少。

**规则**：一屏一问。每题 3 到 5 个可点选项，永远留「我自己说」。答完能改。第 1 段一个技术词都不出现。

**客户看到**：左边一屏一问，右边双手机预览。前面是顾客看到的，后面是他的后台。每答一题，手机上的东西变一次。第 3 问答完，弹一次「今天，和以后」对照。

**依据**：Y-003、准入清单 14 问、需求澄清研究 8 问。

### A3 验收条件

第 1 段第 4 问答完，网页 agent 立刻起草验收条件。

- 3 到 6 条正向，2 到 3 条负向。
- 每条写清：谁、从哪进、做什么、看到什么、什么算不对。
- 客户逐条删改。问「哪条不对」，不问「对不对」。
- 写不出可测条目的，标「人工判断」，留到验收时人看。

详细拿法见第十节。

**依据**：准入清单第 2 问。原话是「AI 先给 3 条看得见的完成草稿，客户删改」。需求澄清研究第 4 条（先替客户填三成）、第 6 条（给参考、指错、二选一）、第 8 条（人话确认单）。

### A4 确认单

客户看到五行大白话：

1. 做什么。
2. 给谁用。
3. 怎么找到你。
4. 怎么付钱。
5. 什么算成。

下面一块「怎么算成」，逐条列出验收条件。再下面一行「不做」清单。

点「就按这个来」才建单。点之前每行都能改。

**依据**：需求澄清研究第 8 条、Lovable Plan 模式。

### A5 找人

右下角常驻一个「找人」。客户卡住，可以写一句留言。

留言先挂在草稿上，你的手机当场响一下。客户点确认建单时，留言一起写进工单，不丢。你在 Orca 里回一句，客户网页能看到。

这一步不阻塞工厂。客户不等你，单子也照常往下走，只是答案会缺一块。

**依据**：介入点第二次动手。

## 五、阶段 B：建仓建单

### B1 建仓与建单

顺序不能反：先建客户仓，再建 parent issue。

一客户一仓（#13）。服务器先建出仓壳，只放初始 commit 和骨架；然后在这个仓里建 parent issue，把确认单写进去。子票挂在 parent 下面，必须同仓。仓没建出来，单没处落。

工单标题用客户那句话。正文放：客户原话、确认单、验收条件、不做清单。

**依据**：#13、工厂流程 10:12、微信通知选型。

### B2 补满厨房

空 repo 不算建完。十二项不变量见第九节，分两种做法：

- 机械项（初始 commit、五个标签、`check` 命令、CI、`.sandcastle` 五件套、`.gitignore`、`.env.example`、提交前缀）由建仓脚本一次做完。
- 四份要按客户仓改写的文档（AGENTS.md、issue-tracker、triage-labels、domain）由主机 agent 从模板快照改。

**状态：推断。** 脚本和 agent 的这条分界是我划的，实验里看要不要全交给脚本。

建完先跑一遍 `check` 和 `verify`，留下第一张截图。跑不通不算建完。

**依据**：脚手架分层、pstack 的「每仓一个验证技能」。

### B3 通知

推你一条：`B 店 · 预约送货 · 已进队列`。这条只用知道，不用动手。

**依据**：介入点三条通知之一。

## 六、阶段 C：设计

大单点两次，小单点一次。

### C1 分流判断与技术闸门（第 1 次点击）

机器先做一次分流：这单走全套，还是跳过写规格和拆票，直接实现。

小单指改文案、改样式、修小 bug、单页改动。大单指新页面、新流程、接外部系统、多角色。

判断结果写在工单上。你在同一屏看到分流结果和五类闸门。不同意分流，点「改道」。干到一半发现判错，也可以改道，已经写的代码保留。

**依据**：#6 的六步与唯一岔口。

然后机器读确认单，判断这单撞上哪几类闸门，只列撞上的。

五类固定：技术栈、部署到哪、第三方服务与账号、数据怎么存、每月花多少。

每条三个选项，第一个带推荐。客户第 3 段的意思显示成推荐值，不重复问。

你点完才往下。不回就停在「等你定」，24 小时提醒一次。

大约三分钟。

**依据**：#10、介入点。

### C2 写 spec

机器用 `/to-spec`，输入是确认单加闸门决策。

七个模板字段：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。

我们加第八个字段：Acceptance criteria。模板没有这一栏，但票要用。

Implementation Decisions 和 Testing Decisions 由机器填。撞上五类的，用你在闸门里点的结果。

spec 写进客户仓 `docs/specs/<issue>-<slug>.md`。

**依据**：to-spec 原文、准入清单字段表。质量还没测，见第十四节实验 1。

### C3 拆票

机器用 `/to-tickets`，拆成垂直切片。每张票要能单独演示，还要装得进一个上下文窗口。

每张票必须有两条：Acceptance criteria 和 Blocked by。

票是 parent issue 的 sub-issue。阻塞边由机器按技术依赖定，客户不参与。

票上的验收条件只能从客户确认的那份里拆。要新造，回客户补一条。

**依据**：to-tickets 原文、准入清单「技能链的硬性要求」。

### C4 你点「按这个拆」（第 2 次点击）

同一屏给你三样：spec 摘要、票单、每票的验收条件。

点「按这个拆」，或者改一条再点。没点就停着，24 小时提醒。

这是视频里「人批准拆分」那一步。我没有另开一次，折进你已经在的这一屏。

**状态：已定（限前五单）。** 长期留不留，看实验 4 数出你改了几次。

## 七、阶段 D：执行

这一段无人值守。

### D1 调度器对账

每 30 秒读一遍所有 open 工单，找出「该动但还没动」的。

判断依据是工单标签和阻塞边，不看内存。

三个好处：崩了重启接得上；不会同一个活干两遍；出问题能问一句「它为什么觉得这张单不该动」。

一开始只同时跑一单，跑稳了加到五单。客户勾「急」，插到队首，同时推你一条。

**依据**：#12。

### D2 单票实现

一张票一个 worktree（工作树，同一仓库的独立检出），一个 Sandcastle run，一个容器。

prompt 由四样拼成：spec、这张票、仓库 AGENTS.md、相关代码。

先写失败的测试，再实现（TDD）。提交前缀 `FACTORY:`，循环能认出自己上一轮的提交。

**依据**：v1.3 implement、Sandcastle 本机验证、脚手架清单第 12 项。

### D3 自检

每票做完，先跑 `check`：类型检查、lint、单测。

再跑 `verify-<app>`：启动应用、走关键路径、截图、收 trace（运行轨迹）。

验收条件逐条过。过不了的票不算完。

截图要一前一后：改之前一张，改之后一张。

**依据**：pstack 验证技能、#11 四样证据、v1.3 证据栏。

### D4 评审

另一个 agent 读 diff，跑 `/code-review` 两轴：标准、spec。

高风险的票加 `blast-radius`：找出这段改动安全所依赖的那一个事实，跑代码证明它，不写漂亮文章。

评审不过，回 D2，同一票重跑，最多三圈。

**依据**：v1.3 code-review、pstack blast-radius、#12 两关。

### D5 合并到需求分支

四样证据齐了才合：

1. 验证技能跑过。
2. 有截图或 trace。
3. 测试全绿。
4. 评审两轴都过。

子票合到需求分支，不合主干。合并前推你一条通知，不能不让你知道。

解完冲突必须重跑验证。冲突本身不算证据。

**依据**：#11。

### D6 失败与停法

三种停法：

- 同一张票三圈没进展（D4 的评审循环）。
- 钱花超额度。
- 碰到禁区。判据两句话：这段改动能不能验证，出事了能不能回滚。有一条答不能，就停。

两个计数器别混。三圈管一张票的评审循环，到了就停这张票。两次管同一类问题跨票复发：到了先自动加一条规则重跑一次，还不过就叫人。

叫人时给三样：现象、试过什么、建议怎么办。

**依据**：#12、#11、pstack 的「重复失败先改环境」。

## 八、阶段 E：验收与复盘

### E1 验收（第 3 次点击）

需求分支做完，推你一条：待验收。

你看四样：验收条件逐条、前后截图、改动摘要、测试结果。

PR 正文写摘要和证据。再加两栏（待你点头）：单向门还是双向门、影响范围。

## 十、验收条件怎么拿

验收条件靠改，不靠问。客户给现象，agent 给草稿，客户只做一件事：指出哪条不对。

七步：

1. **要一个场景。** 问「上一次这件事发生是什么时候？从头到尾讲一遍」。客户会讲出人、步骤、卡点。
2. **找「行了」的那一刻。** 问「哪一刻你会说行了？眼睛看到什么？手上做了什么？」客户说「好用」，就追问「哪个页面？上面有什么？」说不出来，就让他讲现在怎么做：「微信接龙，做完之后哪一步会消失？」
3. **agent 按模板写草稿。** 每条一个句式：谁，从哪进，做什么，看到什么，什么算不对。先写 3 到 5 条正向，再写 2 条负向。一条只写一个行为。
4. **读回去，问「哪条不对」。** 不要问「对不对」，客户会顺口说对。逐条读，让他挑错、删、改。他改的那一句，往往才是真正的验收条件。
5. **做可测检查。** 每条问：能不能点一遍看出来？不能就改写，或者标「人工判断」。「老板知道要备多少」测不了；「后台按时间段分组显示订单」能测。
6. **客户在确认单上点头。** 放在五行确认单下面，一块「怎么算成」，逐条可改。
7. **冻进四个地方。** 确认单、spec 单独一节、每张票只放它负责的那几条、验证技能。

第七步最后一项是关键。验收条件不只给你看，也给 agent 自检。

### B 店走一遍

客户原话：「街坊在手机上看今天有啥，挑个时间来拿，我早上知道要备多少。别太复杂，老人家也要会用。不要在线付钱。」

草稿八条：

1. 顾客打开链接，不用登录，看到今天可订的货和取货时段。
2. 选时段、填手机号、提交，看到「订好了」和取货时间。
3. 时段满了，显示「这个时段满了」，不能下单。
4. 老板后台看到当天订单，按时间段分组，每单有手机号和取货时间。
5. 老板能打印这份清单。
6. 顾客取消，名额回到可订。
7. 不出现支付入口。
8. 不登录也能下单，不收身份证。

客户改：「第 5 条不要打印，我要发微信。」改成「老板能把清单复制成一条微信消息」。

### 缺口要回客户

纸面推演时，这单卡在一处：一个时段放几单，客户没说。

这属于业务规则，归客户定，技术闸门管不到。默认值要先给，比如每时段 10 单，再让客户改。没有这个数，第 3 条验收条件写不出来。

所以验收条件不会一次问完。拆票时会暴露缺口，缺口回客户补一条。这个回路要有，不然 agent 会自己编一个数。
