# 后端服务

> 状态：现行

一句话：登录、订单、上传共用一个 Node 26 服务，源在 `backend/`，没有第三方依赖。它由独立系统用户 `afkapp` 跑，只听 `127.0.0.1:8787`，Caddy 把 `/app/api/*` 反代进来。注册机是同一服务的命令行入口。给客户发的邮件由 `backend/bin/customer-mail.py` 发，运营者通知仍走 `notifier/`。

来源：2026-11-15 由 I-0086 建成；2026-11-16 按 I-0137 补管理视图、工单评论和已发记录；2026-11-16 按 D-I-0156-ROOT 并入 `docs/archive/合并前-2026-11-16/` 下的后端服务实现和部署两篇。通知模块见 `docs/通知.md`。

## 一、服务进程

| 项 | 值 |
| --- | --- |
| 服务名 | `afkapp` |
| 系统用户 | `afkapp`，`nologin`，不登录 |
| 监听 | `127.0.0.1:8787`，不对公网 |
| systemd 单元 | `/etc/systemd/system/afkapp.service`，开机自启 |
| 程序目录 | `/data/app/current`，软链到 `/data/app/releases/<版本>` |
| 环境文件 | `/etc/afkapp/app.env`，`600 root:root` |
| 数据目录 | `/data/customers`、`/data/uploads`，`700 afkapp:afkapp` |
| 日志 | journald，`journalctl -u afkapp` |
| 对外入口 | 只有 Caddy 的 `/app/api/*` |

D-0166 定了一个 Node 服务，登录、订单、上传同进程。注册机是同一服务的命令行入口，不另起常驻服务。客户邮件由 `backend/bin/customer-mail.py` 以一次性进程发出，SMTP 配置从 `/etc/afkapp/app.env` 读；运营者通知走 `notifier/`，不在这个进程里。现有服务器已有 Node 26；空机重建按手册 9a 装 NodeSource 26.x。

服务不监听公网。`ufw` 和云安全组不用改，80、443 仍只由 Caddy 用。

## 三、密钥

| 密钥 | 放哪 | 干什么 | 怎么换 |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | `/etc/afkapp/app.env` | 读客户仓的工单状态和 `进度 v1｜` 评论，管理视图和客户进度页要用。token 要有客户仓的读权限 | 换 token 后改环境文件，再 `sudo systemctl restart afkapp`。`git push` 用的凭据是另一套，见 `docs/运维手册.md` 第八节 |
| `SESSION_SECRET` | 同上 | 签 `afk_session` Cookie | `openssl rand -base64 32` 生成新值，改环境文件，重启。换掉会让所有登录态失效 |

规则：

- 密钥不进仓库。仓库里只有 `deploy/backend/app.env.example` 的占位值。
- 环境文件 `600 root:root`。systemd 以 root 读，再把变量交给 `afkapp` 进程。服务用户自己不读这个文件。
- 密钥不要写在命令行里。`ssh ... "TOKEN=..."` 会进 shell 历史和进程列表。

客户邮件由 `backend/bin/customer-mail.py` 发。它从环境变量读 `SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASSWORD`、`SMTP_FROM`；导入流程和服务器上的 `afk-uploads send-delivery-mail` 都调它，`deploy/backend/afk-uploads` 先从 `/etc/afkapp/app.env` 导出这几项。运营者通知仍由 `notifier/` 发，SMTP 密码在 macOS 钥匙串，见 `notifier/config.py`。

`SESSION_SECRET` 没填时服务会用临时密钥启动，日志里有一条警告。登录能用，但服务重启后所有人要重新登录，线上不要这样跑。

## 四、接口

路径和字段按 I-0035 的决定 D-0168、D-0169。前端 `site/src/api/account.js` 和 `site/src/pages/UploadPage.jsx` 不用改。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/app/api/health` | 占位服务和真实服务都有，回 `{ok, version}` |
| `POST` | `/app/api/login` | JSON `{email, password}`，成功回 `{user}` 并种 `afk_session` |
| `GET` | `/app/api/session` | 有会话回 `{user}`，没登录 401，账号停用 403 |
| `POST` | `/app/api/logout` | 204，清 Cookie |
| `POST` | `/app/api/uploads` | multipart `file`、`finished`，成功回 `{orders}` |
| `GET` | `/app/api/orders` | 只回自己的单 |
| `GET` | `/app/api/orders/{id}` | 不存在 404，不是自己的 403 |
| `GET` | `/app/api/admin/orders` | 只有 `role=admin` 能读，每单多 `customer`、`issue_url` 和 `messages` |
| `POST` | `/app/api/admin/orders/{id}/messages` | 只有 `role=admin`；JSON `{type, anchor}`，记「标记已发」 |

错误码：400 缺字段或 multipart 坏了；401 未登录；403 账号停用、不是同源、不是自己的单；404 订单不存在；413 超过 50 MB；415 不是 zip；422 路径穿越、解压炸弹、加密包、缺 `.scratch`、认不出软件、账号没有客户档案；429 限速；5xx 服务端错误。

写请求查 `Origin` 或 `Sec-Fetch-Site`，同源才放行。Cookie 名 `afk_session`，`HttpOnly`、`SameSite=Lax`、`Path=/`，线上加 `Secure`。客户 30 天，管理员 7 天。Cookie 里放账号 id、角色、密码哈希前 16 位和过期时间。每次请求重新查账号，停用立刻失效。

## 五、上传判序

1. 查登录态。没登录 401，账号停用 403。登录账号必须在 `customers.json` 里有一行客户档案；管理员账号默认没有，直接 422，提示用客户账号或显式映射。
2. 限速。同一账号 10 分钟 5 次，同一 IP 10 分钟 20 次。超了 429。
3. 收 multipart，只认 `file` 和 `finished`。`finished` 必须是 `true` 或 `false`。
4. 压缩包超过 50 MB 返回 413。不是 `.zip` 或 zip 打不开返回 415。
5. 子进程检查安全，见下表。命中任一条返回 422。
6. 找工作区根目录。规则按 D-0171：根目录有 `.scratch/` 通过；只有一个有效子目录且它有 `.scratch/` 也通过；找不到按四类给提示。
7. `.scratch/` 下没有需求目录返回 422。
8. 认软件。读工作区根目录 `软件.md` 的第一行当软件简称；没有这个文件、空文件、读不出名字时按没有处理。没有 `软件.md` 时，按 `.scratch/` 需求目录名里出现的 `customers.json.repos` 已知键回退；一个已知键都没有时按新软件处理，软件简称取需求目录名。新软件第一次上传带多个需求目录返回 422，不建单，日志记一条 error。软件简称和同一客户已有软件重名（大小写不区分），或对应的仓名 `<客户简称>-<软件简称>` 已属于另一个已知软件时，也返回 422。重名只和 `repos` 里已有的键比；建仓时 GitHub 重名按 D-0221 报运营者。
9. 检查勾选和内容，生成 `missing`。缺 `.scratch/` 不建订单；内容不全仍返回 200，建订单并把 `missing` 写进订单。
10. 写订单记录，订单记 `product`（软件简称）和 `requirement`（需求目录名）。转档写 `已收到｜收包`，通过写 `已收到｜校验`，不通过写 `校验未通过｜等补传`。同一客户、同一软件、同一需求重传沿用原订单号，不建第二张；不同软件或不同需求建新单。

失败和需要人处理的包（`failed`、`validation_failed`、`import_failed`、`import_partial`、`needs_operator`）留在 `/data/uploads/<上传 id>/`，7 天后由启动清扫和定时清扫删掉。成功和进行中的包保留，等导入步骤拉走。

导入按订单逐张记结果。成功写订单的 `import_status: imported`；失败写 `import_failed`，同时写 `import_failure`（原因、下一步、上传号），订单页据此显示失败。一单失败不挡同一包的其他单；有成功也有失败时，上传 `meta.status` 记 `import_partial`。地图旧格式这类要人看的失败记 `needs_operator`。

## 六、工单评论与进度

订单文件里的 `transitions` 只到建单前。建单后的转档由调度器写在父工单评论里，每行以 `进度 v1｜` 开头。服务读工单状态和评论，按订单缓存 60 秒；读失败先用最近一次缓存，没有缓存就只返回订单记录里的转档。

- 工单地址写在订单的 `issue` 字段，写完整链接（`https://github.com/<owner>/<repo>/issues/<n>`），也可以写成 `{owner, repo, number}`。导入步骤还没实现，现有的单这个字段是 `null`，服务跳过读 GitHub。
- 读接口是 `GET /repos/{owner}/{repo}/issues/{n}` 和 `.../comments?per_page=100`。评论最多读 3 页，只取以 `进度 v1｜` 开头的行，时间用评论的 `created_at`。
- 父工单关闭，并且最后停在「待客户验收」时，服务补一行 `客户档：已完成`，时间用 `closed_at`。关票前没到过「待客户验收」的不补。客户页和管理视图都直接看拼接后的 `transitions`。
- 客户接口不返回 `messages`。管理接口才返回，客户页看不到发没发。
- `messages` 数组一条记 `{type, anchor, at}`。`type` 是 `校验未通过`、`待客户验收`、`满 24 小时`；`anchor` 分别是本次上传时间、轮次、最近一次通过校验的上传时间。同一类型、同一锚点只记一条。

相关环境变量：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `GITHUB_TOKEN` | 空 | 读客户仓工单用。空着就不读 GitHub，只显示建单前的转档 |
| `GITHUB_API` | `https://api.github.com` | 测试时指向假服务 |
| `GITHUB_TIMEOUT_MS` | 5000 | 单次 GitHub 请求超时 |
| `PROGRESS_CACHE_MS` | 60000 | 按订单缓存工单状态的时长 |

## 七、管理视图

`/app/admin` 是前端页面，调 `/app/api/admin/orders`。列客户、需求名、当前档、内部细阶段、停留天数、卡住、交付地址、小进度条、消息 / 工单。顶部三个数是进行中、该发消息、卡住，带对应筛选。页面只读，只有一个写动作「标记已发」。

「该发消息」在前端按三条规则算：校验未通过、待客户验收、从最近一次通过校验的上传算满 24 小时。锚点没变、标过已发就不再提示。点「标记已发」调 `POST /app/api/admin/orders/{id}/messages`，服务走订单文件唯一写入模块追加 `messages`，顺手提交并推送私有仓。

管理员账号没有命令行，直接在 `/data/customers/admins.json` 里写一条，密码哈希用 `auth.mjs` 的 `hashPassword` 生成。已有 `admins.json` 时先读出数组，把新行补进去，别整份覆盖：

```bash
cd /data/app/current
sudo -u afkapp node --input-type=module -e "
import { hashPassword } from './lib/auth.mjs'
console.log(JSON.stringify([{
  id: 'a-0001',
  email: 'you@example.com',
  display_name: '运营者',
  password_hash: await hashPassword('换成你的密码'),
  status: 'active',
  created_at: new Date().toISOString(),
  updated_at: new Date().toISOString(),
  disabled_at: null,
  disabled_reason: null,
}], null, 2))
"
```

写完重启服务，用这个邮箱和密码登录 `/app/admin`。

## 九、数据

| 文件 | 内容 |
| --- | --- |
| `/data/customers/customers.json` | 客户数组，字段见 `docs/客户工作区.md` 的「一行写什么」一节 |
| `/data/customers/admins.json` | 管理员数组，字段按 D-0168 |
| `/data/customers/orders/o-0001.json` | 一条订单一个 JSON，字段按 D-0167，另有 `messages` 已发记录 |
| `/data/customers/orders/o-0001.sync-pending` | 推送私有仓失败的待办，后台每分钟补寄一次，成功后删掉 |
| `/data/uploads/<上传 id>/package.zip` | 回传件快照 |
| `/data/uploads/<上传 id>/meta.json` | 这次上传的 SHA256、状态、需求、订单号 |

订单文件只由 `backend/lib/orders.mjs` 写：先加文件锁，写临时文件再原子替换，然后提交并推送私有仓。`/data/customers` 不是 Git 仓库时跳过同步，只写磁盘。

部署成功后 `afk-uploads mark-delivered <订单号> <地址>` 以 `afkapp` 身份调 `backend/bin/mark-delivered.mjs`。它走 `backend/lib/orders.mjs` 的 `updateOrder`：加 `.orders.lock`、原子替换、提交推送私有仓；只写 `delivery`（地址字符串）和 `delivery_url`（完整 URL）两个键。客户邮件仍由 `afk-uploads send-delivery-mail` 调 `customer-mail.py` 发。

推送失败时，订单目录多一条 `<订单号>.sync-pending`，记订单号、需求名、第一次失败时间、最近一次尝试和失败原因。服务每分钟拿这些待办重试一次推送，成功就删掉待办。待办超过 10 分钟还没清掉，积压期间每次重试都记一条 error，带订单号、开始时间和失败原因；`deploy/backend/check.sh` 查近 15 分钟的日志，命中就判巡检失败。待办文件不提交、不推送，私有仓里看不到。

| 数据 | 在哪 | 主副本 | 服务器丢了怎么办 |
| --- | --- | --- | --- |
| 客户账号、管理员、订单 | `/data/customers` | 私有仓 `grilling-customers` | 从私有远端重新克隆 |
| 上传件 | `/data/uploads` | 客户本机 | 导入完成就删；失败留 7 天；丢了让客户重传 |

服务器上不放唯一一份持久数据。备份规则按 `docs/运维手册.md` 第七节；整机丢了按第十节重建。

## 十、客户白名单命令行

在服务器上用 `afkapp` 跑，否则文件属主会变：

```bash
sudo -u afkapp node /data/app/current/bin/customer.mjs add \
  --short-name acme --display-name "Acme 老板" --email boss@acme.example
```

命令会要求输两遍密码，不回显，写完打印 `c-0001`。其他命令：`list`、`show`、`disable --reason`、`enable`、`change-email`、`reset-password`。脚本里用 `--password-stdin` 从标准输入读密码，字段和规则见 `docs/客户工作区.md` 的「白名单和 `customers.json`」一节。

写完会尝试提交并推送私有仓；目录不是 Git 仓库时只写磁盘，并打印一条提示。

密码用 argon2id 存哈希。Cookie 里的版本取哈希前 16 位，换密码、停用后旧会话立即失效。

## 十二、安装

要 sudo，运营者跑。

1. 把 `deploy/` 传到服务器：

```bash
tar -C deploy -czf - . | ssh dev@<服务器地址> 'rm -rf /tmp/afk-deploy && mkdir -p /tmp/afk-deploy && tar -xzf - -C /tmp/afk-deploy'
```

这台 Mac 上普通 `scp -r` 可能报 `Connection closed`。用上面的 tar 管道，或者给 `scp` 加 `-O` 传单个文件。

2. 跑安装脚本：

```bash
ssh -t dev@<服务器地址> 'sudo bash /tmp/afk-deploy/backend/install.sh'
```

脚本做五件事：建 `afkapp` 用户；建数据目录和 `/data/app`；写 `/etc/afkapp/app.env`（已存在不覆盖）；装 systemd 单元并把三个运维脚本放到 `/data/app/bin/`；备份旧 Caddyfile，换新的，`caddy validate` 通过后 `reload`。

脚本不启动服务。第一版发布前先填密钥：

```bash
ssh -t dev@<服务器地址> 'sudoedit /etc/afkapp/app.env'
```

填完权限保持 `600 root:root`。没有第一版时 `/app/api/*` 回 502，静态页和下载不受影响。

3. 复核 Caddy 和防火墙：

```bash
ssh -t dev@<服务器地址> 'sudo caddy validate --config /etc/caddy/Caddyfile && sudo systemctl reload caddy'
```

`ufw` 和安全组不用加端口。

上线前确认三件事：`/data/customers` 已建好并能被 `afkapp` 读写；`/etc/afkapp/app.env` 填了 `SESSION_SECRET`；Caddy 的 `/app/api/*` 仍反代到 `127.0.0.1:8787`。

## 十三、发布

真实服务的源在 `backend/`。在开发机打包：

```bash
bash deploy/backend/package.sh backend 1.0.0
```

发布包根会带 `release.json` 和 `release.manifest`：来源提交、scaffold 指纹和成品模板指纹。`release.manifest` 记每个模板文件的 sha256。`package.sh` 打完打印这三项。旧包没有这两个文件，`check.sh` 只提示，不判失败。

占位服务仍在 `deploy/backend/placeholder/`，只在演练部署路径时用：

```bash
bash deploy/backend/package.sh deploy/backend/placeholder 0.1.0
```

传上去，在服务器上发布：

```bash
ssh dev@<服务器地址> 'cat > /tmp/afkapp-1.0.0.tgz' < output/afkapp-1.0.0.tgz
ssh -t dev@<服务器地址> 'sudo bash /data/app/bin/deploy.sh /tmp/afkapp-1.0.0.tgz 1.0.0'
```

发布脚本做这些：

1. 解包到 `/data/app/releases/<版本>`，属主给 `afkapp`。
2. `/data/app/current` 切到新版本。
3. `systemctl enable afkapp`，`restart`。
4. 轮询健康检查：`/app/api/health` 回 200（只有 200 算过），`/app/api/session` 回 401。
5. 检查不过就切回上一版，打印服务状态和最近日志，退出码 1。
6. 通过后把旧版本记到 `/data/app/previous`。

版本号不能重复。要重发同一版，先删掉旧目录，或者换个版本号。

`deploy/backend/` 下的 `deploy.sh`、`rollback.sh`、`check.sh` 和 `deploy/lib/` 下的 `health.sh`、`fingerprint.sh` 有改动时，要单独换服务器上的旧版。只发程序包不会更新 `/data/app/bin/` 里的这几个文件。五个文件要一起换，脚本靠同目录的共享库判断健康。先把文件传到 `/tmp`，再逐个换掉，以 `check.sh` 和 `health.sh` 为例：

```bash
ssh dev@<服务器地址> 'cat > /tmp/check.sh' < deploy/backend/check.sh
ssh dev@<服务器地址> 'cat > /tmp/health.sh' < deploy/lib/health.sh
ssh -t dev@<服务器地址> 'sudo install -m 755 -o root -g root /tmp/check.sh /data/app/bin/check.sh'
ssh -t dev@<服务器地址> 'sudo install -m 644 -o root -g root /tmp/health.sh /data/app/bin/health.sh'
```

`deploy.sh`、`rollback.sh`、`fingerprint.sh` 同样换。

发布路径的硬约束，接新的外部服务时不变：

- 入口仍是 `server.mjs`，监听 `PORT`，默认 8787，只绑 `127.0.0.1`。
- 必须提供 `GET /app/api/health`，不带登录，回 200。
- 未登录访问 `GET /app/api/session` 回 401，和前端 `site/src/api/account.js` 对上。
- 有依赖就在开发机装生产依赖再打包，或在发布包里带 `node_modules`；服务器不跑 `npm install`，发布时没有网也要能装。
- 登录、订单、上传仍在一个进程里（D-0166）。注册机做成同一个服务的入口，或用同一个 `EnvironmentFile` 的 one-off 命令，不新开常驻单元。
- 客户邮件由 `backend/bin/customer-mail.py` 发，SMTP 配置从 `/etc/afkapp/app.env` 读，调用方负责把那几个变量导进环境；运营者通知走 `notifier/`，SMTP 密码从 macOS 钥匙串取。
- 新增端口要另开票，不能绕过 Caddy 直接对外。

## 十四、回滚

```bash
ssh -t dev@<服务器地址> 'sudo bash /data/app/bin/rollback.sh'
```

脚本把 `current` 切到 `previous`，重启，跑同一组健康检查。检查不过会切回原版本。回滚成功后，原来的版本记进 `previous`，可以再切回去。

回滚后确认版本：

```bash
curl -s https://afkfactory.space/app/api/health
```

回的是旧版本的 `version` 才对。

## 十五、巡检

巡检脚本只读，普通用户就能跑。agent 用 `dev` 登录跑；运营者跑 `sudo` 版，能多查证书到期。

```bash
ssh dev@<服务器地址> 'bash /data/app/bin/check.sh'
```

检查项：

| 项 | 通过的样子 |
| --- | --- |
| 进程 | `afkapp` 是 `active` |
| 端口 | `127.0.0.1:8787` 在听，不是 `0.0.0.0` |
| 健康检查 | `/app/api/health` 回 200（只有 200 算过） |
| 健康接口版本 | 打印 `version` |
| 未登录会话 | `/app/api/session` 回 401 |
| 发布指纹 | scaffold 和成品模板与 `release.json` 的记录一致 |
| 磁盘 | `/` 和 `/data` 低于 90% |
| Caddy | `caddy` 是 `active` |
| 源站证书 | 打印 `notAfter`；没有 sudo 时跳过 |
| 日志 | 过去 24 小时没有 error 级日志 |
| 订单推送积压 | 近 15 分钟没有 `订单推送私有仓超过 10 分钟未成功` |
| 最近请求 | 打印最后 3 条请求行 |

`check.sh --templates-only` 只查发布指纹和模板，本机也能跑。给 `--repo <仓库目录>` 时逐文件对比服务器和仓库，仓库比服务器新也能发现。

自动巡检和告警归 I-0047，本文只写手工检查。I-0047 的每日体检脚本还没建；建的时候把 `afkapp` 的 `active`、`127.0.0.1:8787`、`/app/api/health` 200 和 `/app/api/session` 401 加进去。`afkapp` 重启不在免密白名单，要运营者 sudo；当前先用 `check.sh` 手工跑。

失败时先看 `journalctl -u afkapp -n 100 --no-pager`。发布坏了就回滚；磁盘满了先清旧发布和过期上传件；证书问题按 `docs/运维手册.md` 第四节。

## 十六、日志

服务把每个请求写成一行 JSON 到 stdout，journald 收走。字段：`ts`、`request_id`、`method`、`path`、`status`、`ms`，失败时多一个 `msg`。

```bash
# 跟日志
ssh dev@<服务器地址> 'journalctl -u afkapp -f'

# 找一次失败的请求
ssh dev@<服务器地址> 'journalctl -u afkapp --since "1 hour ago" | grep "\"status\":401"'

# 看警告和错误
ssh dev@<服务器地址> 'journalctl -u afkapp --since "24 hours ago" -p warning'
```

日志轮转由 journald 统一管，不使用 logrotate。看占用：

```bash
ssh dev@<服务器地址> 'journalctl --disk-usage'
```

默认上限够用。要改保留量，改 `/etc/systemd/journald.conf` 的 `SystemMaxUse`，这是全局设置，改前先看现状。

日志不记请求体和密钥。以后保持这条。
