# 任务管理：GitHub Issues

本仓库的任务和产品规格统一放在 GitHub Issues 中，使用 `gh` CLI 操作。
仓库为公开仓库 `Lil-BobCN/grilling-remote`，不放客户数据。在仓库目录内运行时 `gh` 会自动识别。

## 常用操作

- 创建：`gh issue create --title "..." --body "..."`。多行正文用 heredoc。
- 查看：`gh issue view <编号> --json number,title,body,labels,comments`。需要人读全文时加 `--comments`。
- 列表：`gh issue list --state open --json number,title,body,labels,comments`，再按状态和标签筛选。
- 设为子任务：`gh issue create --parent <父编号> ...`，或事后 `gh issue edit <父编号> --add-sub-issue <子编号>`（`gh` 2.94+）。旧版 `gh`：`gh api --method POST repos/<owner>/<repo>/issues/<父编号>/sub_issues -F sub_issue_id=<子任务数据库编号>`。用不了子任务时，在子任务正文顶部写 `Part of #<父编号>`。
- 阻塞：用 GitHub 原生 issue dependencies。加边用 `gh issue create --blocked-by <n>,<n> ...`，或 `gh issue edit <子编号> --add-blocked-by <阻塞编号>`（`gh` 2.94+）。旧版：`gh api --method POST repos/<owner>/<repo>/issues/<子编号>/dependencies/blocked_by -F issue_id=<阻塞任务数据库编号>`。数据库编号用 `gh api repos/<owner>/<repo>/issues/<编号> --jq .id` 取，不是 `#编号`，也不是 `node_id`。所有阻塞项关闭，任务才可开工。
- 数未关闭的阻塞项：`gh api repos/<owner>/<repo>/issues/<编号> --jq .issue_dependencies_summary.blocked_by`。`gh issue view <编号> --json blockedBy` 会带出已关闭的，要过滤：`--jq '[.blockedBy.nodes[] | select(.state == "OPEN")] | length'`。
- 评论：`gh issue comment <编号> --body "..."`。
- 增删标签：`gh issue edit <编号> --add-label "..."` 或 `--remove-label "..."`。
- 关闭：先用 `gh issue comment <编号> --body "..."` 写说明，再 `gh issue close <编号>`。对已关闭的 issue，`gh issue close --comment` 会丢掉评论，退出码仍是 0。

只往本仓库建 issue，不要往上游 `mattpocock/skills` 建。每次会话第一次 `gh issue create` 前，先用 `gh repo view --json nameWithOwner` 核对目标；不是 `Lil-BobCN/grilling-remote` 就先问。

本机坑：`git` 或 `gh pr create` 报 `error: missing config key GIT_CONFIG_KEY_0` 时，是环境里残留了 `GIT_CONFIG_COUNT`。前面加 `env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_VALUE_1` 再跑，不是仓库问题。

## 是否把 Pull Request 纳入分类处理

**否。** 目前只有你自己的提交，没有外部贡献者。以后要纳入时，读 PR 正文和评论要分两次：`gh pr view <编号>`，再 `gh pr view <编号> --comments`（非终端环境下 `--comments` 只打印评论）。

## 其他 Skill 如何操作

- "发布到任务系统" = 创建一个 GitHub Issue。
- "读取相关任务" = 运行 `gh issue view <编号> --json number,title,body,labels,comments`。

## Wayfinder 约定

- **总任务**：带 `wayfinder:map` 标签的 Issue，正文记录笔记、已做决定和仍不清楚的地方。
- **子任务**：优先用 GitHub sub-issue（见"设为子任务"）；不可用时在总任务和子任务正文里互相引用。按类型打 `wayfinder:research`、`wayfinder:prototype`、`wayfinder:grilling`、`wayfinder:task` 标签。地图和它的票只带 `wayfinder:*`，不打 `ready-for-agent`。
- **阻塞关系**：优先用 GitHub 原生 issue dependencies（见"阻塞"）。原生依赖不可用时，在子任务正文顶部写 `Blocked by: #<编号>`。
- **选择下一项**：按总任务里的顺序检查未关闭子任务，跳过仍有未关闭阻塞项或已分配负责人的。
- **领取**：`gh issue edit <编号> --add-assignee @me`，这是一次工作会话的首次写操作。
- **完成**：先评论结论，再跑 `/wrap-up` 和 `/next`。一张票只开一个 PR，没合并之前的提交都推到它上面，不另开；wrap-up 判「改」的文件直接推上去，不开新分支。两样跑完再合并 PR。合并之后关票，最后把链接补到总任务的"已做决定"里。PR 合并后这条分支不再用，要改就开新分支。

## 关票时写什么：四列表

一项决定只在关票那一刻写一次，写进这张票的评论。写入点只有这一处，地图、`docs/decisions.md` 都是它的读取视图。

状态：2026-11-09 起草，没试跑。

### 表的样子

关闭一张票之前，在这张票上贴一条评论，正文是一张四列表。列固定五列，顺序不变：

| 列 | 写什么 |
| --- | --- |
| `id` | 见下面的编号规则 |
| `决定` | 一句话写清定了什么。写实际定下来的内容，不写「已决定」「见正文」 |
| `取代` | 这条取代了哪些编号，逗号隔开。没有写 `无` |
| `解答未定` | 这条回答了地图 `Not yet specified` 里哪些 `U-` 编号，没有写 `无` |
| `产出文件` | 相对路径，多个逗号隔开。没有写 `无` |

一张票定下几件事，就写几行。#17 那种一票三项独立决定的，写三行。

没有结论的票不写表，评论第一行写 `无结论：<理由>`，理由写清为什么关。例：`无结论：并入《四列表与编号规范》，本身不开新决定。`

### 编号规则

编号形如 `D-0002`，`D-` 加四位数字，全仓连续，从 `D-0001` 起。

同一张票的第二条起，加小写字母后缀：`D-0002a`、`D-0002b`。首条不带后缀。

编号写完不再复用。被取代的编号保留在 `docs/decisions.md` 里，标出被谁取代。

新编号取 `docs/decisions.md` 里现有最大号加一。文件还不存在时从 `D-0001` 起。两人同时关票抢到同一个号，`check` 第 1 条会报，后关的那张改号。

### 开放票首行写依据

开放票正文第一行写 `依据：D-0002,D-0005`，列出这张票动手前认定仍然有效的决定。确实不依赖任何已定决定时写 `依据：无`。

号码被取代后，脚本按这行就能列出所有受影响的开放票，不用知道哪张票是从哪张衍生的。

### 两个例子

带取代的例子：

```markdown
| id | 决定 | 取代 | 解答未定 | 产出文件 |
| --- | --- | --- | --- | --- |
| D-0007 | 交接文档放 `$TMPDIR`，不放仓库 | D-0003 | U-02 | 无 |
```

`D-0003` 原本说交接文档放 `docs/handoff/`，这份票推翻它。`docs/decisions.md` 里 `D-0003` 那行标「已废，见 D-0007」。

无结论的例子：

```markdown
无结论：并入《老票迁移》，不单独定决定。
```

### 完成条件

运营者读一遍，能照着一个例子写出一张票的四列表。

## 地图上的变动怎么留痕

一个决定被后来的票推翻，旧票、旧索引行、开放票的前提都要同步处理。否则 `to-spec` 会读到两个互相矛盾的说法。三个动作管这件事：冒头、关票扫描、开工核对。

规则只写在这一节。技能 `wrap-up` 和 `map-gate` 引用本节，不另抄。引用票时写票名，链接包在票名里，不单写编号。

### 冒头

冒头指谈话中冒出来、还没落到票或地图里的新需求。

1. 先记一条，附原话。不当场展开。
2. 会话结束前跑 `/wrap-up`，由运营者逐条判去向：新票、并入已有票、未定、范围外、当场做完。
3. 领取了某张票的会话里发现的事，一律归这张地图，不当散票。判据看在哪发现的，和事情大小无关。
4. 建票前先搜 open 和 closed 票，能并进已有票就并。
5. 运营者点头的才建。

### 关票扫描

关闭一张票之前，先在这张票上评论一份扫描表。没有扫描表，不关票。表有五项：

1. 本票结论，一句话。
2. 产出了什么，推迟了什么。产出的文件写相对路径，「查文件矛盾」靠它找旧文件。例：决定了要写 ADR 但没写，下游票的阻塞要保留。
3. 地图下每张开放票和「未定」每一项，各判一档：无关、前提受影响、与结论矛盾、阻塞变化。每行写一句理由。整表只写「无影响」不算数。
4. 地图 `Decisions so far` 每一行，判现行还是已废。
5. 碰到已关闭决定的矛盾，列出来，由运营者判。agent 不自己判。

按判定结果这样改：

| 对象 | 怎么改 |
| --- | --- |
| 开放票 | 原地改正文，删掉被推翻的前提，末尾记一行「按 <票名> 更新」 |
| 已关闭票 | 正文不动，加评论「被 <票名> 部分取代」，写明哪一部分 |
| 地图索引行 | 保留原行，行首标「已废，见 <票名>」 |
| 已关闭的决定被推翻 | 新开一张取代票，旧票不重开 |
| 阻塞边 | 按第 2 项补加或移除 |

上面「完成」一步照此执行：先贴扫描表，再跑 wrap-up 和 next，把判「改」的推到当前 PR，合完 PR 再关票，最后把链接补到「已做决定」。

### 开工核对

领取一张票之后、动手之前，把票里写的前提和阻塞，对照这张票创建以来关闭的票再查一遍。前提变了，先改票，再开工。

查法：`gh issue list --state closed --search "closed:>=YYYY-MM-DD" --json number,title,closedAt`，日期取这张票的创建日。

### 查越界产出

越界产出指本会话做了别张票的活。那张票的正文还写着待做，不处理就会被重做，或和已有成果打架。

范围是本会话领取的那张票，下称本票。没领取票时，问运营者一次。

1. 列产出。本会话改过的文件（含未提交的）、写过的评论、改过的票，每项一行。
2. 逐条归属。每项先对本票的 `Scope`（票正文里编号列出的要做的事），对不上再对地图下其余开放票的 `Scope`。归属分三档：本票内、属于某张开放票、哪张都不属于。
3. 属于别票的，写做到哪一步：全做、做了一半、只定了方向。每行附一句依据，写文件路径或提交。
4. 出表：产出、归属票、占它 `Scope` 第几条、做到哪一步、建议处理。归属票已有负责人的，在表里标出来，另一个会话可能正在改同一处。
5. 运营者逐行回：并入、留在本票、回退、放着。点头的才动票。

建议处理这样选：

| 情况 | 怎么改 |
| --- | --- |
| 全做完，归属票是 `wayfinder:task` | 归属票正文里划掉那条，写「已在 <票名> 做完」，附提交。票保留，验收后再关 |
| 做了一半 | 原地改归属票的 `Scope`：做完的标来源，剩下的缩小，末尾记一行「按 <票名> 更新」 |
| 只定了方向，归属票是 `wayfinder:grilling` 或 `wayfinder:prototype` | 先问运营者：认这个方向吗？认，归属票改成确认票。不认，成果退回本票 |
| 哪张票都不属于 | 按「冒头」处理 |

决策票存在的目的，是让运营者做决定。成果若已经把答案定死，那张票不能悄悄关，要让运营者明确认一次。

点头后，在归属票上评论一条，写哪个提交、做了第几条、做到哪一步。成果留在原提交里不动，不会浪费。改了归属票之后，它挡住的票能不能开工，由「查阻塞边」查。

### 查文件矛盾

文件矛盾指本会话的新决定或新文档，和仓库里已有文件说法相反。地图和票正文对得上，文件之间却留着两份互相矛盾的说法。`to-spec` 会自己翻仓库，读到旧文件，就把旧方案当现行。

范围是本会话的每条新决定，加上本会话新写或改过的文档。

1. 找旧文件。两路并查。一路是被推翻那张票的关闭评论里列的文件，关票扫描第 2 项要求写路径。另一路是拿新决定里的关键词搜整个仓库，跳过 `docs/archive/`。关闭评论没列路径的旧票，只能靠搜。
2. 比对。搜索命中的每个文件都要判一次：读相关段落，和新决定对一遍，判矛盾、部分矛盾、无关。每行附一句依据，写文件路径和行号。没读的写「未读」和原因，不能整批略过。
3. 出表。单独成「文件矛盾表」，一行一个文件：路径和行号、旧句原文、对应的新决定（票名）、判定、建议改法（写出要加的那句话）。表前第一行写结论：「有 n 个文件说法相反」或「无文件矛盾」。
4. 运营者逐行回：改、归档、合并、放着。点头的才动文件。

建议处理这样选：

| 文件情形 | 怎么改 |
| --- | --- |
| ADR 或决定类文档 | 原文不动。旧文件开头加「已被 <票名> 取代」，新文件开头加「取代 <旧文件路径>」 |
| 流程文档里的句子 | 旧句保留，句末注「已废，见 <票名>」，沿用地图索引行的写法 |
| 旧文件已无保留价值 | `git mv` 到 `docs/archive/`，原路径的引用同步改 |
| 两份都要留 | 合成一份，由运营者定写法 |

标记写在文件开头，`to-spec` 读到这个文件时先看到。动完文件后，在被推翻那张票上加一条评论，写明哪个文件被取代，下次查得到。

搜关键词只找得到用词相近的矛盾。换了说法的找不到，所以关票时要写全路径。

### 查阻塞边

技能 `next` 只读 GitHub 原生阻塞边排下一步。边挂错，`next` 的结论就错。新票建出来之后，没人回头给更早的开放票补边，所以会话结束前查一次。这一项由 `wrap-up` 执行。

范围是本会话新建、或改过前提的票。含本次 `wrap-up` 建议新建、建议改正文的票，还没建的，现有边写「未建」。

1. 每张票写两件事：它被谁挡，它挡住哪些已有开放票。后一项要对着全部开放票扫一遍，不能只看地图里记着相关的几张。
2. 把票正文里写的阻塞（`Direct blockers`、「等 #编号」、`Blocked by`）和原生边逐张比对。两个方向都查：正文写了、没挂边；挂了边、正文没写。再查边指向的票是否已关闭。
3. 取边：对每张票运行 `gh issue view <编号> --json blockedBy`，不过滤已关闭的，这样才看得出指向已关闭票的边。
4. 比对结果交给运营者判。点头的才补加或移除，加边命令见「常用操作」里的「阻塞」条。

### 关票之后：下一步建议

关闭一张子票、把链接补进「已做决定」之后，运营者最想知道的是下一步做哪张。读阻塞关系很费力，所以由技能 `next` 算出来。第一行给一句结论，后面列能同时做的票。

1. 关票后先跑 `/wrap-up`，处理完它列出的新需求和冲突，再跑 `next`，把结论贴在对话里。wrap-up 可能新建票或改票，next 要等它做完再算。
2. 结论不写进票，不存文件，不打标签。它每次现算，存下来就会过期。
3. 运营者随时可以输入 `/next <地图编号>` 重算。

阻塞关系只认 GitHub 原生依赖。

### 查缺口

缺口指跑 `to-spec` 时会逼它凭空编的地方。目的只有一个：让 `to-spec` 拿到够用的输入。终点不用每一句都落地。票拆得太细，地图就永远清不空。

状态：2026-11-08 起草，没试跑。这一项由 `map-gate` 执行。

范围是四样东西放在一起看：终点（Destination）、已关闭子票的结论（用 `map-gate` 第 4 步出的现行决定清单）、`Not yet specified`、`Out of scope`。再加运营者说的铺垫。

1. 先问铺垫。问法见 `map-gate` 第 5 步。运营者的话原样交给子代理当线索，每一条都要查有没有着落。子代理另外自己找，不局限于这些。
2. 拆终点。按原文分句拆，每条抄原句片段，不改写。每条去现行决定、未定项、范围外里找着落。找不到标「无着落」，拿不准标「拿不准」并写原因，不硬判。
3. 分三类。

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| 终点没着落 | 终点某一句，决定、未定项、范围外都没提到 | 过开票三问 |
| 未定项能升票 | 未定项已经能问准成一张票 | 过开票三问 |
| 没验证 | 现行决定里写着「没验证」「待实测」 | 只列，由运营者判，不给建议 |

   未定项里明写归 `to-spec` 或「不在本图开票」的，不算缺口。单列一行「已有归属，不算缺口：n 项」，每项写出处。

4. 过开票三问。三条全是，才建议开票。一，它会落进 spec 的用户故事或实现决定吗。二，现有决定里没有可引的话，`to-spec` 得靠猜吗。三，猜错了，到拆票或开发才发现，改起来贵吗。一、二是、三否的，放进「未定」，spec 里写成假设并标「待定」。拿不准的标「拿不准」，由运营者判。
5. 拆完的线。会进 spec 的每个部分，清单里都有可引的现行决定，或已明确标成「spec 里当假设」，就算拆完，可以跑 `to-spec`。
6. 上限。一轮最多建议 3 张。同一功能区的合成一张。超出的放进「未定」。重跑时，上一轮开的票又带出挡路缺口，不自动再开满，列给运营者判。
7. 怎么给运营者看。先写一行「有 n 个缺口」或「无缺口」，再给一张目录表：编号、一句话、类别。然后一次一条，每条三块，顺序固定。背景：这个缺口从哪来。哪一句终点、哪张票、哪项未定项，原文一句加出处。相关的票各是干什么的，用人话写，假设读的人没看过任何票。依据：为什么算缺口，`to-spec` 现在动笔会怎样。理由里分清已确认事实、合理推测、没核到的地方。推荐：先给结论，再写理由。
8. 建议处理从五种里选：建新票（写票类型和会被哪张票挡）、并入已有票、放进未定、放进范围外、放着。建票前先搜 open 和 closed 票查重，做法同 `wrap-up` 第 8 步。运营者点头的才建。
9. 建了票就停。有「建新票」或「并入已有票」的行，执行完 `map-gate` 到此停下，告诉运营者地图还有票要做，做完再重跑。全是「放进未定」「放进范围外」「放着」，才往下发布。

限制：只能判有没有可引的话，判不了决定对不对。三方都没人想到的缺口查不出来，所以要先问铺垫。

完成条件：一，对照 spec 的「问题与方案」「用户故事」「实现决定」三块，每块写出支撑它的现行决定，或写「无可引」。二，终点每一句、未定项每一项、「没验证」每一句、运营者说的每条铺垫，各有一行：挡路、不挡、已有归属。三，每个缺口运营者都回了。

### 地图清空之后

1. 跑 `/map-gate <地图编号>`，把现行决定清单发成地图评论。
2. 开新会话，只读那条评论，再跑 `to-spec`。
3. 在同一个会话里跑 `/spec-check <地图编号>`，对照清单检查 spec。缺的、写弱的、没有来源的，由运营者逐条判。
