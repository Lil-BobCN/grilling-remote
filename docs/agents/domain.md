# 领域文档

> 状态：现行

本文件说明工程类 Skill 了解代码库时，该怎样读取本仓库的领域知识。

## 开始前先读什么

- 根目录存在 `GLOSSARY.md` 时，先读它。写词条、写决策记录或改术语前，先读它开头的「写词条的规矩」。
- 根目录存在 `GLOSSARY-MAP.md` 时，先通过它找到与当前工作相关的 `GLOSSARY.md`。
- 读 `docs/adr/决策记录.md`。它收够三条标准的决定；完整决策记录在中台。

这些文件不存在时直接继续，不提示缺失，也不提前建议创建。等术语或重要决定
真正明确后，再由 `domain-modeling`、`grill-with-docs` 或
`improve-codebase-architecture` 按需创建。

## 决策记录

完整决策记录在中台（`http://127.0.0.1:8788`，命令行 `中台/dt`）。仓库里的 `docs/adr/决策记录.md` 只收够三条标准的决定，一个文件夹只放这一份。

### 收什么

三条同时成立才写：

1. 难回退：以后改主意，代价明显。
2. 不写会让人意外：后来的人看代码会问「当时为什么这样做」。
3. 真取舍：有真实备选，并为具体理由选了其中一个。

缺一条不写。容易换掉的库、常规做法不写。

### 怎么读

to-spec 默认只读工作区：探索仓库、读 `GLOSSARY.md`、读 `docs/adr/决策记录.md`。不主动读地图，不主动扫中台。

只有记录里的某点起疑，或代码和记录对不上时，才按条目的 `决定：D-xxxx` 和 `来源票：……` 去中台和 GitHub 交叉验证。没有疑问不查。

### 怎么写

每条一节，标题下先写一句话决定，再写为什么、备选、代价，最后四行元数据：

```markdown
### 标题

一句话说这条决定是什么。

为什么：……
备选：……
代价：……

决定：D-xxxx
来源票：I-0164（GitHub #453）
日期：2026-11-17
状态：现行
```

关票时由干活的 agent 判断够不够三条标准。够的写进文件，和关票 PR 同一张；运营者合并 PR 即确认。备选或代价找不到来源时写「未记录」，不补编。文件开头有目录，按领域分组，一行一条：标题、一句话和 D 编号。

### 怎么查

关票前跑一次 `python3 scripts/check-decisions.py`。脚本按每条 `决定：D-xxxx` 核对中台：决定存在、状态与文件一致、被取代的指向新决定、来源票号对得上。脚本只报，不改正文。

### 被推翻时

决定被推翻时，中台自动开影响清单。处理项里加「改决策记录」：agent 改文件里的条目，或把状态标成 `状态：被取代，见 D-xxxx`，运营者确认。

## 明确指出与决策记录的冲突

建议与记录里的决定冲突时，直接指出冲突和重新讨论的理由，不要悄悄覆盖已有决定。例如：

> 这与决策记录里的 D-0382 冲突，但值得重新讨论，因为……
