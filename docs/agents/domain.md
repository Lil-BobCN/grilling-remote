# 领域文档

本文件说明工程类 Skill 了解代码库时，该怎样读取本仓库的领域知识。

## 开始前先读什么

- 根目录存在 `GLOSSARY.md` 时，先读它。
- 根目录存在 `GLOSSARY-MAP.md` 时，先通过它找到与当前工作相关的 `GLOSSARY.md`。
- 读 `docs/adr/` 中与当前工作相关的架构决策记录（ADR）。

这些文件不存在时直接继续，不提示缺失，也不提前建议创建。等术语或重要决定
真正明确后，再由 `domain-modeling`、`grill-with-docs` 或
`improve-codebase-architecture` 按需创建。

## 文件布局

本仓库是单一上下文（没有多包结构）。本仓只放流程、研究、技能和原型，客户代码在各自的客户仓里：

```text
/
├── GLOSSARY.md
├── docs/
│   ├── adr/
│   │   ├── 0001-接单走客户本机-dsh.md
│   │   └── 0002-调度器替代编排循环.md
│   └── agents/
├── factory-skills/
│   ├── clarify/
│   └── pstack/
├── prototype/
└── 素材/
```

## 词汇表格式

格式按 `domain-modeling` 技能的 `GLOSSARY-FORMAT.md`。本仓不另写格式说明，增删词条时读那一份。

## 使用项目已经确定的说法

Issue 标题、重构建议、假设和测试名称里出现领域概念时，使用 `GLOSSARY.md` 已定义的名称，
不要换成近义词。

需要的概念还没定义时，先判断是不是自己造了项目里不存在的说法。确实缺失，再记为
需要通过 `domain-modeling` 解决的问题。

## ADR 准入

只在这三条同时成立时写 ADR：

1. 难回退：以后改主意，代价明显。
2. 不写会让人意外：后来的人看代码会问「当时为什么这样做」。
3. 真取舍：有真实备选，并为具体理由选了其中一个。

缺一条就不写。容易换掉的库、常规做法不写 ADR。

## ADR 修剪

定期按准入三条复检 `docs/adr/`。

- 够不上三条的，删掉。
- 整份被取代的，删掉，只留 git 历史。
- 部分被取代的，保留，开头指向新 ADR。

## 明确指出与 ADR 的冲突

建议与现有 ADR 冲突时，直接指出冲突和重新讨论的理由，不要悄悄覆盖已有决定。例如：

> 这与 ADR-0007 的决定冲突，但值得重新讨论，因为……
