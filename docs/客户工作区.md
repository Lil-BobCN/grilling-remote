# 客户工作区

> 状态：现行

一句话：客户拿到的是一个摆好的工作区 zip。解压到空文件夹，用 dsh 打开，说「开始需求澄清」就开始；一次对话做一张票；全部做完，压缩整个文件夹，在官网上传页登录后上传。本文讲包里有什么、怎么装、agent 靠什么规则跑、`.scratch/` 里产出什么、回传怎么走，以及客户白名单 `customers.json` 怎么维护。

> 2026-11-17 按 I-0159 合并四份文档的现行内容：`客户工作区方案.md`、`客户 AGENTS.md 设计说明.md`、`客户澄清启动提示词.md`、`客户白名单维护.md`。四份底稿在 `docs/archive/合并前-2026-11-16/`。客户侧流程样本移到 `docs/回传样例/客户侧流程样本.md`。客户看到的进度和三条消息见 `docs/客户进度.md`；回传之后的建单和工单见 `docs/工单模型.md`；上传服务实现见 `docs/后端服务.md`；服务器操作见 `docs/运维手册.md`。

## 一、客户拿到什么

官网发一个工作区 zip，当前是 `客户工作区-v1.zip`。zip 内容直接放在根目录，外面不套文件夹。

```text
AGENTS.md
README.txt
技能清单.md
LICENSE
NOTICE.md
docs/agents/issue-tracker.md
docs/agents/domain.md
.dsh/skills/
├── grilling/
├── domain-modeling/
├── grill-with-docs/
├── wayfinder/
├── prototype/
├── research/
└── wait-what/
```

规则：

- `AGENTS.md` 是成品，不是模板。标题下有一行 `工作区版本：v1（<构建日期>）`。
- `docs/agents/` 两份直接提交成品，构建时不跑 `setup`。源文件里已经是中文的 `## 评论`、`## 结论`。
- `技能清单.md` 由 `customer-kit/manifest.json` 生成，官网清单用同一份。
- `README.txt` 只写解压和打开步骤，以及模型 key 放在哪。
- 不放 `setup`、`ask-matt`，不预建 `.scratch/`。`.scratch/` 由 agent 在客户第一次说需求时建。
- 不放 `问题树.md`，客户侧不生成也不读取；旧包里的只作历史。
- 没有装配提示词，也没有提示词①。客户第一次打开由 agent 自检，见第四节。

四个位置各有主人。客户和 agent 都不改 `AGENTS.md`、`docs/agents/` 和 `.dsh/skills/`；客户侧只写 `.scratch/` 和词表。

| 文件 | 谁写 | 谁读 |
| --- | --- | --- |
| `AGENTS.md` | 我们，随 zip 预装 | dsh 每次新会话注入给 agent |
| `GLOSSARY.md` | 客户侧 agent，定词义时写 | agent 每次开工；运营者回传后 |
| `docs/agents/*` | 我们，随 zip 预装 | agent 只读，查追踪器和领域读法 |
| `.scratch/` | 客户侧 agent，写地图、票、草稿、`未定事项.md`、问答记录、决策记录、验收场景、研究、原型 | agent 读写；运营者回传后读 |

`GLOSSARY.md` 不预装，第一个词定下来时才建。词表放根目录一份，只放词义，不放规则。`.dsh/skills/` 和 `docs/agents/` 要改由我们出新 zip。

一个工作区只做一个软件。第一张单建需求目录时，agent 在根目录写一行 `软件.md`，见第九节。

## 二、客户侧技能集

客户侧用七个上游原版技能，照 `mattpocock/skills` 提交 `5863806dd4e15c63174bee4e7515a4256792ecfa` 原样装（2026-11-13 取用）：

`grilling`、`domain-modeling`、`grill-with-docs`、`wayfinder`、`prototype`、`research`、`wait-what`。

只删 `wayfinder` 和 `grill-with-docs` 里的 `disable-model-invocation: true`，`wait-what` 保持上游原样。`next`、`map-gate`、`wrap-up` 三个自建技能已删（D-0117）。

客户规则不进技能正文，分两处：

- 选票、收尾固定句、跟客户说话的规则进 `AGENTS.md`。
- 清雾、未定事项、四类票的文件操作进包内 `docs/agents/issue-tracker.md`（D-0118）。

更新技能时先读 `customer-kit/package/NOTICE.md`，按它复制；不要覆盖客户化的 `AGENTS.md`、`docs/agents/` 和 `README.txt`。复制后对上游跑 `diff -r`，只允许这两处开关差异。技能数、版本和日期以 `customer-kit/manifest.json` 和 `customer-kit/release.json` 为准。

## 三、怎么装

客服只做三件事：让客户确认装的是官网桌面版；让客户把工作区 zip 解压到空文件夹；用 dsh 打开并说一句话。卡住就要卡住那一步的截图。完整步骤、失败信号和截图清单在 `customer-kit/安装步骤.md`，本文只记要点。

支持范围：Windows 64 位、macOS Apple 芯片、macOS Intel（只做静态核对，实机未测）。不支持 Linux。桌面版自带 Node，客户不用装命令行环境。

| 步骤 | 客户做什么 | 客服检查什么 |
| --- | --- | --- |
| 1 | 打开官网 `https://www.deepseek.com/harness`，下载对应系统的桌面版 | 文件名对得上：`dsh-latest-windows-x64.exe`、`dsh-latest-macos-arm64.dmg` 或 `dsh-latest-macos-x64.dmg` |
| 2 | 安装并打开 dsh，在 设置 → 模型 里填好 DeepSeek API key | 应用能打开，能看到选择文件夹的界面；设置里有 key |
| 3 | 从官网下载页下载 `客户工作区-v1.zip` | 文件名完整，下载已完成 |
| 4 | 新建一个空文件夹，名字用日常中文；把 zip 放进去，解压到当前文件夹 | 解压前文件夹是空的；解压后文件列表里直接能看到 `AGENTS.md`。只看到一个文件夹，就是多套了一层 |
| 5 | 用 dsh 打开这个文件夹 | dsh 窗口显示的路径就是这个文件夹 |
| 6 | 第一次说「开始需求澄清」，或直接说「我想做一个……」；之后每次新开对话，原样复制 agent 收尾给的那一行 | agent 先自检，通过后讲开场词；续做时直接做需求名和编号对应的那张票 |

配模型 key：客户在 `https://platform.deepseek.com/` 注册或登录，新建 key，回到 dsh 的 设置 → 模型 填进去，发一句「你好」能回话就算通了。DeepSeek API 按用量计费。客户不想自己注册，告诉客户这一步找运营者，不替客户操作账号。

多套一层文件夹时，根目录没有 `AGENTS.md`，agent 读不到自检规则。没有兜底提示词，靠第 4 步的肉眼检查和客服。

装完交代客户三句话：

1. 每次都打开这个文件夹，不要换。
2. 进度都在 `.scratch/` 里，不要自己改；要改就告诉 agent。
3. 一个文件夹只做一个软件。要做另一个软件，再解压一份到新文件夹。

## 四、客户怎么走

1. **第一次打开先自检。** 没有 `.scratch/` 时，不管客户先说什么，agent 先查 `docs/agents/issue-tracker.md`、`docs/agents/domain.md`、`.dsh/skills/` 在不在。缺任何一个，就说「文件没放对，按官网第 2 步重放」，然后停下，不问需求。
2. **开口。** 客户第一次说「开始需求澄清」，或直接说「我想做一个……」。自检通过、客户还没说需求时，agent 先讲第一段开场词，然后问一句「你想做什么？」并停下。
3. **判断大小。** 同时满足三条才算小需求：改动落在一个已有功能里；一个会话做得完；验收条件客户已说清。缺一条走 wayfinder，拿不准也走 wayfinder。
4. **小需求写 `需求草稿.md`，其余走地图。** 走地图时，先起草验收场景（三到六条，客户逐条删改，写不出可当场验证的标「人工判断」），再写 `map.md` 和 `issues/`，拆完把清单给客户看，顺序由客户定。定终点和建图用 `grill-with-docs` 和 `wayfinder`；聊类票也用 `grill-with-docs`，一轮列出几个问题。
5. **一次对话做一张票。** 客户每次新开对话，原样复制上一轮收尾给的一行，形如「继续：tanxin-yuyue 01 空档怎么放」。只发「继续」二字，按追踪器文档的「选票」规则选。需求名或编号对不上，或那张票被挡着，按跳步规则处理。
6. **每次收尾。** agent 自己说四句：最后要做什么、这次走到哪、定了几条、推荐下一张票并给继续行。不跑子代理。写结论前也不另起子代理查冲突；客户的话明显推翻前面定过的内容时，按 `AGENTS.md` 的「改前面定过的结论」回原票改，结论变了客户能看到的东西时同步改 `验收场景.md`。
7. **全部做完。** 先按追踪器文档的「全部做完后的清雾」清 `Not yet specified`，再照「收尾与回传」核八项。核过了才提醒客户压缩整个文件夹上传；核不过先补，不叫客户上传。

客户会遇到的场景、开场白原文和一次完整会话的样子，见 `docs/回传样例/客户侧流程样本.md`。

## 五、agent 靠什么执行

`dsh` 在新会话第一次请求时自动注入 `AGENTS.md`，之后作为普通消息参与上下文压缩。规则写在那里，客户不用记着粘贴。一句话：`AGENTS.md` 放每个会话都要生效、客户不用记着粘贴的规则；提示词②只做触发器。没有提示词①；提示词②只剩两句：

```text
开始需求澄清。
```

```text
继续：tanxin-yuyue 01 空档怎么放
```

只发「继续」二字时，按 `AGENTS.md` 的「继续」一节和追踪器文档的「选票」规则选下一张票。

提示词只剩触发语的三个理由：

1. 规则只有一份。两份写法一定会漂移，改一处漏一处。
2. 提示词负责「现在开始」，不负责「怎么做」。
3. 新需求和续做的输入不同，这正是提示词该管的事。

### 一条规则放哪里

一条规则进 `AGENTS.md` 之前先回答两个问题：

1. 它要不要在每个会话都生效？
2. 客户会不会忘了粘贴提示词，或者直接开口说需求？

两个都答「是」，就进 `AGENTS.md`；只答一个，留在技能里。

`AGENTS.md` 不走 40 行上限。2026-11-17 核对：343 行，27,943 字节；注入预算 65,536 字节，约占 43%。代价是每次会话多带几万字节，收益是规则不用客户记着粘贴。

| 规则组 | 为什么放 `AGENTS.md` | 放提示词会怎样 |
| --- | --- | --- |
| 说话方式、谁管什么、会话开头三句 | 第一次输出就要生效，续做时也要成立 | 只覆盖开场那一次 |
| 分两类、一次对话一张票 | 客户可能不输提示词直接说需求；对话变长后最容易忘 | 一次性提示没有持续约束力 |
| 单票开工与结论、改前面定过的结论 | 发生在对话中后段，模型容易漏 | 提示词管不到写结论那一刻 |
| 客户没听懂或答不上来、跳步、原型、技术题、偏题 | 卡住的时间点不可预测，跨票反复出现 | 同上 |
| 进度文件位置、验收场景、产出文件 | 写文件发生在会话中后段，改一次要重发 | 路径写死会漂 |
| 第一次自检、「继续：需求名 编号 票名」 | 新对话里 agent 不知道上次做到哪张 | 提示词不知道这次是哪一张 |
| 一个工作区一个软件、会话结尾第四句 | 新想法随时冒出来；收尾在几十轮之后 | 提示词早就不在焦点里 |
| 边界与冲突句、不动客户的文件 | 管的是以后每个会话 | 一次性提示管不了未来 |

### 哪些留在技能里

| 内容 | 放哪 | 为什么 |
| --- | --- | --- |
| 提问轮次和格式 | `grilling/SKILL.md` | 只在提问时用，不占每次会话 |
| 地图和票的机制 | `wayfinder/SKILL.md` | 只在走 wayfinder 时用 |
| 词表 | `domain-modeling` | 有词义要定时用；本工作区不建 `docs/adr/` |
| 决策记录 | 工作区 `AGENTS.md`、`docs/agents/domain.md` | 上游 `domain-modeling` 默认写 `docs/adr/`；本工作区改放 `.scratch/{需求名}/决策记录.md` |
| 原型怎么做 | `prototype/SKILL.md` | 只在有原型票时用 |
| 查资料怎么写 | `research/SKILL.md` | 只在研究票时用 |
| 选票、改旧结论、收尾 | `AGENTS.md` 和追踪器文档 | 客户侧没有这三个技能，规则改成硬规则 |
| 清雾、收尾检查、回传件结构 | 追踪器文档 | 只在全部做完时用 |

规则写成硬规则，是因为模型靠 description 决定调不调技能，可能漏掉。这是合理推测，靠 `customer-kit/测试记录.md` 验。

### 客户侧产出什么

客户侧只落澄清材料，不写 spec。

| 层 | 产物 | 谁写 | 给谁 |
| --- | --- | --- | --- |
| 小需求 | `.scratch/{需求名}/需求草稿.md` | 客户侧 agent | 运营者审 |
| 走 wayfinder | `.scratch/{需求名}/map.md` 加 `issues/` | 客户侧 agent | 运营者审 |
| 逐轮问答 | `.scratch/{需求名}/问答记录.md` | 客户侧 agent | 运营者审阅 |
| 每个需求 | `.scratch/{需求名}/验收场景.md` | agent 起草，客户逐条删改确认 | 父工单的验收条件 |
| 运营者侧 | spec，存成 issue | 运营者决策后手动跑 `to-spec` | 工厂 |

`需求草稿.md` 不是最终规格。运营者决策完，小需求不跑 `to-spec`；其余单补完地图，运营者手动跑 `to-spec`，调度器不触发。

### 确认单和复核

确认单不单独出文件。`需求草稿.md` 的「已经定下的」就是客户点头的部分；走 wayfinder 时，确认在每张票的 `## 结论` 里。`验收场景.md` 开头写「客户确认：日期」，是父工单「验收条件」的来源，不算第二个确认单。

只有小需求在说「问完了」前起一次子代理：用 `subagent_fork` 读对话和 `需求草稿.md`，列出客户说过但没写进草稿的、前后矛盾的、还没定的词。按它列的改，在 `需求草稿.md` 末尾写「复核：……」一行。子代理起不来，就自己重读对话和草稿，写「复核：查过（自查）」。不卡住客户，也不对客户提子代理。

### 证据

- 注入预算 65,536 字节。客户包 `AGENTS.md` 2026-11-17 核到 343 行、27,943 字节。
- `subagent` 是新上下文，`subagent_fork` 继承对话。依据是本机 dsh 0.2.1-rc.5 的 `@deepseek-ai/dsh-base` 包（`cordis.patch.yml:380-395`），不在本仓库；客户机版本没测过。
- dsh 的注入文本写明不覆盖客户的直接指令，所以 `AGENTS.md` 只能劝，拦不住。

## 六、`.scratch/` 里有什么

`.scratch/` 由 agent 在客户第一次说需求时建。一个需求一个目录，一张单一个目录；新单新建目录，旧单的目录不改。

```text
.scratch/xianguopu/
├── map.md
├── 问答记录.md
├── 验收场景.md
├── 未定事项.md
├── 决策记录.md
├── pending.md
├── issues/
│   ├── 01-顾客怎么看到今天有什么.md
│   └── ...
├── research/
└── prototypes/
```

| 文件 | 谁写 | 讲什么 |
| --- | --- | --- |
| `需求草稿.md` | agent | 小需求的草稿：客户原话、问答、已经定下的、技术题、不做清单、复核行 |
| `map.md` | agent | 走 wayfinder 的地图六段：Destination、Notes、接下来、Decisions so far、Not yet specified、Out of scope |
| `issues/NN-*.md` | agent | 一张决定票。票头写 `Type:`，有先后写 `Blocked by:`，正文写 `## Question`、`## 评论`、`## 结论` |
| `问答记录.md` | agent | 开头 `## 客户原话`；之后按轮分节，题目行 `QN：`，客户原话照抄 |
| `验收场景.md` | agent 起草，客户删改 | 三到六条，每条写清谁、从哪进、做什么、看到什么；开头写「客户确认：日期」 |
| `未定事项.md` | agent | 客户暂时定不了的事，写清卡在哪、谁来回话 |
| `决策记录.md` | agent | 客户侧 agent 在 grilling 票里写的决策记录，随需求目录回传 |
| `pending.md` | agent | 技术题，等运营者确认 |
| `research/`、`prototypes/` | agent | 研究结论和单文件原型 |

规则：

- `Not yet specified` 只放还能问清的雾。客户暂时定不了的，移进 `未定事项.md`，从 `Not yet specified` 删掉。清雾三种去向：建新票、移 `Out of scope`、移 `未定事项.md`（D-0119）。
- 客户原话必须落在文件里，运营者才看得到。
- 不生成也不读取 `问题树.md`（I-0147）。
- 上传前检查目录：`.scratch/` 下除当前需求目录外，没有这次新加的需求目录。以前单子留下的目录可以保留；这次新加的并进当前需求目录，再把空出来的文件夹移到工作区外，不删除。

## 七、回传

全部做完，客户压缩整个工作区，在官网上传页登录后上传。上传页和接收端点 2026-11-15 已建（I-0086），实现见 `docs/后端服务.md`。

| 项 | 方案 |
| --- | --- |
| 范围 | 整个工作区，原样上传。有什么传什么，不挑文件 |
| 怎么压 | 客户右键压缩整个文件夹。v1 不做浏览器内打包 |
| `meta.json` | 取消。agent 不写 JSON，不问简称 |
| 身份 | 登录后上传，简称和邮箱由账号带出；勾「已问完」 |
| 服务器认需求 | 先读工作区根目录 `软件.md` 认软件；没有这个文件时，按 `.scratch/` 里出现的 `customers.json.repos` 已知键回退。订单按客户 + 软件简称 + 需求目录名认。已经有订单的目录跳过；当前单在 to-spec 前出现没有订单的新需求目录，整次上传返回 422，不建订单、不建父工单；当前单交付后，没有订单的目录建新单。to-spec 前同一目录重传算同一单；to-spec 后同一目录不能再改，要新建目录 |
| 做完怎么判 | 客户侧先核八项，见下。服务器再看到三样：勾了「已问完」，每张票都是 `resolved`，地图「接下来」为空。小需求看 `需求草稿.md` 的 `Status: 已问完`。不满足只存快照，不建单 |
| 包里多出的文件 | 例如原 zip。服务器只读 `.scratch/`，其余原样存档，不校验 |
| 保存 | 导入完成就删，失败留 7 天。长期存档在运营者 Mac 的 `inbox/`；客户拿到交付地址和代码 zip 就算交付，交付后手动删，不设自动清理 |
| 大小上限 | 50 MB。Cloudflare 免费版单次 100 MB，留余量 |
| 隐私提示 | 上传页和教程各一句：文件夹里的所有文件都会上传，请只放本项目的资料 |

对话记录在 `~/.dsh/sessions/`，不在工作区里，整包不会带出对话。v1 不回传对话记录。

### 上传前的八项检查

全部做完、叫客户上传之前，按这张表核一遍。核不过先补；要客户拿主意的，一次问一句。核不过不要叫客户上传。

| 项 | 走地图（`wayfinder`） | 小需求 |
| --- | --- | --- |
| 票都做完 | `issues/` 下每张票都是 `Status: resolved`。有 `claimed`，先做完那张 | 不看票 |
| 没有剩事 | 地图「接下来」为空；`Not yet specified` 为空。每项要么已建票做完，要么客户同意移 `Out of scope`，要么移进 `未定事项.md` | `需求草稿.md` 第 4 段只剩技术题，技术题已记进 `pending.md` |
| 未定事项 | `未定事项.md` 存在就逐条写了卡在哪；没有就写「无」 | 不看 |
| 验收场景 | `验收场景.md` 存在、非空，开头有「客户确认：日期」 | 同左，按「已经定下的」起草 |
| 客户原话 | `问答记录.md` 开头有 `## 客户原话`，照抄客户第一次说明需求的话 | `需求草稿.md` 第 1 段第一条是客户原话 |
| 不做清单 | 地图 `Out of scope` 已写，没有写「无」 | `需求草稿.md` 第 5 段已写，没有写「无」 |
| 目录 | `.scratch/` 下除当前需求目录外，没有这次新加的需求目录 | 同左 |
| 复核 | 不需要 | `需求草稿.md` 末尾有「复核：」一行 |

八项都过，才说上传那一段。地图「接下来」和 `Not yet specified` 为空，指标题下没有条目，不写「（空）」。

### 回传件怎么变成父工单五段

父工单的格式见 `docs/工单模型.md`。回传件里的来源固定：

| 父工单段 | 从哪读 |
| --- | --- |
| 客户原话 | 走地图：`问答记录.md` 开头的 `## 客户原话`；小需求：`需求草稿.md` 第 1 段第一条 |
| 客户确认的结论 | 走地图：`map.md` 的 `## Decisions so far`，取冒号后面那句，到句末；链接不抄，行末「按第 N 张改」不抄；小需求：`需求草稿.md` 第 3 段「已经定下的」 |
| 验收条件 | `验收场景.md` 的条目，一条抄一条；行末「按第 N 张改」不抄 |
| 不做清单 | 走地图：`map.md` 的 `## Out of scope`；小需求：`需求草稿.md` 第 5 段。没有写「无」 |
| 需求全文 | 整个 `.scratch/{需求名}/`，原样拷进客户仓 `docs/requirements/{需求名}/` |

父工单正文里的「需求全文」写完整 URL，不写相对路径。拷进仓的目录开头写一句：「回传快照，以父工单和 spec 为准，不作为决策来源。」

决策记录随整个需求目录原样拷进客户仓 `docs/requirements/{需求名}/决策记录.md`。

地图 `Decisions so far` 里出现行首「已废」或「已被取代」的行，说明回传件是旧格式。建仓脚本不建单，只存快照，报运营者。

样例：`docs/回传样例/`。样例包里的 `工作区/.scratch/xianguopu/` 能按上表读出五段，结果见 `docs/回传样例/父工单.md`。

### 客户仓里的地图 issue

回传之后，客户仓里除了父工单，还有一张地图 issue。它是客户 `map.md` 在 GitHub 的副本，也是运营者补完剩余项的地方。走地图的单才有这张 issue；小需求没有。

- 形态：正文六段，照 `map.md` 抄。客户每张 `issues/NN-*.md` 变成地图 issue 的子票，标题保留编号和名字。票里的 `## 评论` 变成 issue 评论，`## 结论` 变成关闭前的一条结论评论。地图和父工单在正文里互相链接：地图 `Notes` 记父工单链接，父工单 `## 需求全文` 补一行地图链接。
- 旧包里的 `问题树.md` 不读。它留在 `docs/requirements/<需求名>/` 的快照里，只作历史。
- 谁建：补缺口 Agent，建在父工单之后、`提案：补缺口` 之前。B1 脚本只建仓和父工单。建图按回传原文抄，不改写；格式不对停下报运营者；重试先按编号配对，不能建出两套。
- 标签：地图挂 `wayfinder:map`，决定票挂 `wayfinder:<type>`。不挂 `状态:*`、`ready-for-agent`、`Sandcastle`。父工单和实现子票照旧走 `状态:*` 和 `Sandcastle`。调度器只从父工单的子票里挑实现活，地图和决定票不当实现活。

### 补完地图、to-spec 和重传

- 补完：to-spec 前，运营者按本机 wayfinder 手动补完地图。`Not yet specified` 变成票，逐张做，结论写评论，关票，地图 `Decisions so far` 加一行。补缺口 Agent 不参与。
- 决策记录：运营者补完地图之前先读 `docs/requirements/{需求名}/决策记录.md`；补完在地图 `Notes` 加一行链接。补缺口 Agent 建图仍只读 `map.md` 和票，不强制读决策记录。
- 点头前：`Not yet specified` 为空、开放的决定票都关了、未定事项处理完，才写 `点头：补缺口`。`点头` 仍是调度器放行的唯一信号。
- to-spec 读两处：父工单五段加最新 `点头：补缺口` 定施工范围；地图的六段、决定票和评论补理由和细节。两处冲突，停下报运营者。回传快照只作背景，不当决策来源；决策记录同样是背景，客户仓 to-spec 仍以父工单和地图为准。客户仓默认不建 `docs/adr`，出现信号再加；加了 ADR，to-spec 也读。
- 重传：to-spec 前客户整包重传，父工单五段、快照、状态和旧提案按 D-0219 换。地图跟着换：补缺口 Agent 比对新快照和当前地图，换正文；决定票按编号配对，换正文、追加评论和结论；新包没有的票写 `作废：重传` 再关；新包新有的建出来。运营者自己开的票保留，加 `待复查：重传`，在地图 issue 写一条 `重传：<日期>` 评论列出来。更新完写新 `提案：补缺口`，调度器推「重传地图已更新」。

## 八、白名单和 `customers.json`

`customers.json` 是客户、账号和仓指针的唯一登记表。本文只定这份表的维护办法和数据形状；上传页、接收端点、登录实现、建仓建单归 to-spec，见 `docs/后端服务.md`。

### 名单是什么

- 邀请制：客户先微信联系运营者，运营者确认后加行、发账号；不开放自助注册。
- 登录名就是邮箱；密码由运营者手动设，微信发；忘了找客服重设。
- 客户简称由运营者给，账号带出；需求名由 agent 起，两者不是一回事。
- 服务器凭登录态找到这一行，再决定能不能上传。

### 放在哪、谁是源

- 私有仓 `grilling-customers` 存 `customers.json` 和 Git 历史。不放公开仓。
- 不再单独建 `clients.json`。仓指针并入本文的 `repos`；需求单在订单记录里，不在这份文件。
- 服务器上是这个私有仓的一份克隆；工作副本放在 `/data/customers/`。注册机和上传服务都读这份工作副本。
- 文件只有几 KB；历史和异地备份在私有仓。
- 注册机在服务器上跑，改文件后提交并推送到私有远端。
- 服务凭据（服务器 SSH、GitHub token、Cloudflare token、SMTP 密码等）不放这个仓。

### 谁在什么时候加行

- 只有运营者加行。客服以后只能提申请，由运营者执行。
- 不要手改工作副本；所有改动走注册机，避免漏字段、写坏文件或和上传服务撞车。
- 时机：客户微信联系、确认接单之后，发账号之前。
- 一条命令写一行，分配 `id`；命令要求手动输入初始密码（输两遍），打印 `id`，不回显密码。
- 加行后，运营者微信发：邮箱、初始密码、教程链接。
- 客户还没上传时，`repos` 为空对象。

### 一行写什么

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 内部不变编号，`c-0001` 起；订单和仓指针引用它，换邮箱不断历史 |
| `short_name` | string | 是 | 客户简称；小写英文/拼音，`[a-z0-9][a-z0-9-]{1,30}`，唯一；建仓后不再改 |
| `display_name` | string | 是 | 称呼，给人看，可中文、可重复 |
| `email` | string | 是 | 登录名和联系方式；小写，唯一；换邮箱改这里 |
| `status` | string | 是 | `active` 或 `disabled` |
| `repos` | object | 否 | 客户每个软件的仓名；键是软件简称，值是仓名。建号时为空对象，上传服务首次建或复用某个软件的仓后写入该键 |
| `wechat` | string | 否 | 客服通道；微信为主、电话兜底；不填不影响登录 |
| `note` | string | 否 | 备注 |
| `password_hash` | string | 是 | 登录凭据；只存哈希，不存明文 |
| `created_at` | string | 是 | ISO 8601 UTC，注册机写 |
| `updated_at` | string | 是 | ISO 8601 UTC，每次改动更新 |
| `disabled_at` | string \| null | 否 | 停用时间；启用时清空 |
| `disabled_reason` | string \| null | 否 | 停用原因；停用时必填，启用时清空 |

示例：

```json
{
  "id": "c-0001",
  "short_name": "acme",
  "display_name": "Acme 老板",
  "email": "boss@acme.example",
  "status": "active",
  "repos": {},
  "wechat": "wxid_example",
  "note": "",
  "password_hash": "$argon2id$example",
  "created_at": "2026-11-13T12:00:00Z",
  "updated_at": "2026-11-13T12:00:00Z",
  "disabled_at": null,
  "disabled_reason": null
}
```

### 账号和登录怎么对应

- 登录名 = `email`。大小写不敏感，文件里存小写，登录时也按小写查。
- 密码只存 `password_hash`。运营者手动输入初始密码，注册机负责哈希；`list` 和 `show` 永远不回显密码。
- 运营者忘了自己设的初始密码不影响客户：跑 `reset-password` 重设即可，账号不废。
- 登录成功 → 用邮箱找到这一行 → 状态必须是 `active`。`disabled` 拒绝登录，也拒绝上传。
- 上传还查白名单：登录账号必须在 `customers.json` 里有一行客户档案。管理员账号默认没有，上传直接返回 422；要用客户账号上传，或先把账号显式映射到一行客户档案。
- 上传页用登录态带出 `short_name` 和 `email`，不手填。
- 停用、换邮箱、重置密码后，现有登录失效；会话怎么失效归 to-spec。

### 撤销、启用和换邮箱

- 撤销 = `disable`：状态改 `disabled`，写 `disabled_at`、`disabled_reason`；现有登录失效；上传被拒。
- 不删回传件、仓库、已交付物；在途订单不自动停，运营者在工厂侧手动处理。
- 删除是单独的人工动作，不在注册机里。
- `enable` 恢复：状态改 `active`，清空停用字段；历史仍留在 Git。
- 换邮箱：`change-email` 改同一行；`id`、`short_name`、订单、仓库都不变。旧邮箱立即不能登录，运营者微信通知客户从哪天起用新邮箱。旧值不另存字段，Git 提交里有 diff。

### 仓指针

- 注册时 `repos` 为空对象。
- 填过两个软件后形如 `{"shuiguo": "acme-shuiguo", "kucun": "acme-kucun"}`：键是软件简称，值是仓名。
- 上传服务首次校验通过、建或复用某个软件的仓后，写入 `repos[软件简称]`。只允许它写这个映射，不许碰其他字段。
- 仓名格式 `<客户简称>-<软件简称>`，软件简称用这个软件第一张单的需求名。同一软件的后继单复用这个仓，不改 `repos`。
- 一个客户可以有多个软件，一个软件一个仓。软件简称由客户工作区根目录 `软件.md` 声明，一个客户下不重名，建仓后不改。
- 注册机和上传服务写同一个文件：改前加锁（`flock`），写临时文件再原子替换，提交；冲突重试。

### 注册机命令

```text
customer add --short-name acme --display-name "Acme 老板" --email boss@acme.example [--wechat ...] [--note ...]
   手动输入初始密码（输两遍），写一行，提交，打印 id

customer disable <id|email> --reason "..."
   状态改 disabled，写 disabled_at / disabled_reason，让现有登录失效

customer enable <id|email>
   状态改 active，清空停用字段

customer change-email <id|email> <new-email>
   改邮箱，让旧登录失效；订单和仓不变

customer reset-password <id|email>
   手动输入新密码，更新哈希，让旧登录失效

customer list [--status active|disabled]
customer show <id|email>
   只读，永远不显示密码哈希
```

补充：

- 上传服务回写 `repos` 不走这套命令，是内部函数，只写 `repos` 里的一个键，提交信息写明 `set repos c-0001 acme-shuiguo`。
- 命令用 `sudo -u afkapp` 跑；`afkapp` 读写这份克隆。
- `short_name` 建号时定，之后不改；写错了只能停用该行、新建一行，所以 `add` 时要确认。
- 新邮箱必须唯一；换邮箱前先确认新地址没被别的客户占用。

### 权限、日志和备份

- 工作副本 `/data/customers` 权限 700，属主 `afkapp`；目录、`.git` 和 `customers.json` 都只让 `afkapp` 读写。其他系统用户不可读。
- 日志不打印完整邮箱、密码和密码哈希。
- 私有远端用只限这个仓的部署密钥。
- 私有仓是历史和异地备份。每次改动提交后推送到私有远端；推送失败时本地提交保留，命令报错，下次重试。
- 服务器坏了，从私有远端恢复克隆和工作副本。备份不含服务凭据。

## 九、一个工作区一个软件

一个工作区只做一个软件。软件可以分很多次做，每次一张单。一个客户可以有多个软件。

- 软件简称写在工作区根目录 `软件.md`。第一张单建需求目录时由客户侧 agent 写入，一行，之后不改、不删。服务器靠它认这次上传属于哪个软件；只读第一行，空文件或读不出名字时按没有这个文件处理。
- 旧工作区没有 `软件.md` 时，按 `.scratch/` 里出现的 `customers.json.repos` 已知键回退。已有的键出现在目录名里，就归那个软件。一个已有的键都没有，就按新软件处理。新软件的第一次上传必须只有一个需求目录，软件简称取这个目录名；多个目录时不建仓，报运营者。
- 仓跟软件走：一个软件一个仓，仓名 `<客户简称>-<软件简称>`。软件简称用这个软件第一张单的需求名，客户侧 agent 按软件起名，比如 `shuiguo`，不要按第一个功能起。一个客户下软件简称不重名；重名时服务器拒绝建仓，报运营者。
- 第二个软件的第一张单校验通过时，服务器按新的软件简称建仓，写进 `customers.json.repos`。不加运营者闸门。
- 单跟一次开发走：一张单一个订单号、一张父工单、一条需求分支 `req/<订单号>`。同一软件的后继单复用原仓，建新父工单、新分支；交付地址不变。
- 订单按客户 + 软件简称 + 需求目录名认。`product` 存软件简称，`requirement` 存需求目录名。同一客户同一软件同一需求重传沿用同一个订单号，不加字段。
- 需求目录跟单走：`.scratch/<需求名>/` 是一张单的材料，上传后拷进客户仓 `docs/requirements/<需求名>/`。新单新建目录，旧单目录不改。
- 交付地址跟软件走：一个软件一个地址。第二个软件上线后拿新地址，不复用第一个软件的地址；同一软件的后续单交付到同一地址。地址是 `https://<客户简称>-<软件简称>.afkfactory.space`，和仓名一致；软件生命周期内不变。以后搬机器时加一条具体 DNS 记录盖过通配记录，地址不改。

加功能只有两个窗口：

1. 回传前：并进当前需求目录和地图，上传时还是一单。
2. 回传后、to-spec 前：还是同一单。客户整包重传，服务器记新上传、重跑校验，订单页加一轮。父工单五段和 `docs/requirements/<需求名>/` 快照换成新包，父工单退回 `状态:已提交`，旧的 `提案：` 和 `点头：` 作废，补缺口 Agent 重跑。不新建仓和父工单。客户仓的地图 issue 同时换正文和决定票，见第七节「补完地图、to-spec 和重传」。

小需求只有回传前这一个窗口。上传校验通过、建单后锁住；再要加需求或改主意，等这一版交付后按新单走，见 `docs/工单模型.md`。

其余单 to-spec 跑完、运营者贴了 `ready-for-agent` 后锁单。再要加功能，算新单：客户微信告诉运营者，在同一个工作区新建需求目录，自己在订单页点「传新需求」上传。上一单没交付时只存快照，不建单。

另一个软件：请客户再解压一份到新文件夹，在新工作区里跑一遍澄清。服务器按新工作区的 `软件.md` 建新仓，交付地址另给一个。

客户说两个需求要合成一个软件：现在没有规则，先照客户的话记进 `map.md` 的 `Not yet specified`，告诉客户「这条我记下了，开工前会有人确认」。

## 十、构建和发布

| 项 | 现在 |
| --- | --- |
| 源目录 | `customer-kit/package/`，和 zip 根目录一模一样，含 `.dsh/skills/` 和 `AGENTS.md` |
| 打包 | `bash customer-kit/build.sh`，产物 `customer-kit/dist/客户工作区-v1.zip`，同目录还有 `.sha256` |
| 包名 | 从 `manifest.json` 的版本号读，直接打 `package/`，不套层 |
| 清单 | `manifest.json` 生成包内 `技能清单.md` 和官网清单 |
| 发布 | `AFK_SERVER=dev@<服务器地址> bash deploy/publish.sh`，需要服务器地址和私钥，由运营者跑 |

- zip 要带上隐藏目录 `.dsh`，排除 `.DS_Store`。
- 打包用 `python3` 的 `zipfile`，不用系统的 `zip`。系统的 zip 3.0 给中文文件名不打 UTF-8 标记，Windows 自带解压会按本地代码页读，`技能清单.md` 显示成乱码。`build.sh` 依赖 `jq` 和 `python3`。
- 包内时间戳固定成 `manifest.json` 的日期。同一份内容连打两次，SHA256 一样。
- 版本号现在固定 `v1`。官网下载链接 `https://afkfactory.space/downloads/客户工作区-v1.zip` 不随内容变，每次重打只改日期；同一天重打用 SHA256 区分。要换成新版本号，得同时改官网下载页和所有写死 v1 的链接。
- 改版本号或日期时，要同时改三处：`manifest.json`、`package/AGENTS.md` 第 3 行、`package/README.txt` 前两行。`build.sh` 只用 `manifest.json` 生成包名和 `技能清单.md`，不会改另外两处。
- 发布成功后，脚本把版本、日期、文件名、大小、SHA256 写进 `customer-kit/release.json`。官网下载页读这份记录，页面数字和服务器上的文件始终一致；文件要一起提交。
- 构建是否通过、解压核对和 SHA256 记录在 `customer-kit/README.md` 的「构建记录」和 `customer-kit/测试记录.md`。具体数字以 `release.json` 为准。

## 十一、官网和客服要什么

- 下载页：下载按钮，版本、日期、SHA256。SHA256 可只给客服看。
- 清单页：由 `manifest.json` 生成。
- 三步图：下载，解压到空文件夹，用 dsh 打开并说一句话。第 2 步加那句肉眼检查。
- 上传页：登录后上传，简称和邮箱由账号带出；保留「已问完」勾选和隐私提示。
- 教程页：完整安装步骤、第一次对话会遇到什么；发布归运维。
- 静态页放本仓库 `site/`，和 `manifest.json` 同源，部署到服务器；上传接收端点在 `backend/`。页面路由和实现见 `site/README.md`、`docs/后端服务.md`。

客服以 `customer-kit/安装步骤.md` 为准：六步、每一步的失败信号、首单实测、客服一句话版和截图清单都在那里。

## 十二、验收和没验到的

客户包的验收不看本文，看 `customer-kit/测试记录.md`。本文合并的四份底稿里，2026-11-07 的验收项（三技能、`next`、`map-gate`、`wrap-up`）已随 D-0117 作废，只作历史。

已确认：

- 2026-11-07 #26 在本机跑过：新 Mac 空文件夹解压、用 dsh 打开、说「开始需求澄清」，agent 先自检再讲开场词，不需要装配提示词；两类分流、跳步、原型、自检、三句触发、继续行、词表也通过。之后客户包又重打过，最新结果以 `customer-kit/测试记录.md` 为准。收尾漏 `next`、小需求漏子代理复核两处已按 #95 改成可检查的规则。
- 人为把压缩阈值降到 0.1% 触发两次，`AGENTS.md` 的规则还在；自然长会话的压缩没测。
- `docs/回传样例/` 的样例包能按第七节的表读出父工单五段和验收场景（2026-11-13 本机手工核过）。
- Windows 右键压缩会带上 `.scratch/` 和 `.dsh`（2026-11-16，I-0050）。
- 服务器判重、50 MB 边界、20 并发、重传、限速和 7 天清理已在源站实测，见 `docs/research/上传容量实测.md`（2026-11-16）。

仍未验证：

- Mac 右键压缩是否带上隐藏的 `.scratch/` 和 `.dsh`；2026-11-07 决定不测（没有对应主机）。
- Windows 解压、中文路径、`.dsh` 被隐藏时 dsh 是否正常。
- 客户机的 dsh 有没有 `subagent` 和 `subagent_fork`；归 `customer-kit/安装步骤.md` 的首单实测。
- 客户机上的 agent 会不会按「收尾与回传」核完再让上传，没测；目前只有本机规则和样例。
- 客户机默认的 `workspace-write` 沙箱；本机 2026-11-16 用 `workspace-write` 跑通过，早期这台机器的沙箱后端坏过，用过 `danger-full-access`。

合理推测：

- 模型可能漏调技能，所以把规则写成 `AGENTS.md` 里的硬规则。
- 仓库里「简称」有两个意思：需求名（agent 起，如 `tanxin-yuyue`）和客户简称（运营者给，写进 `customers.json`）。账号带出的是客户简称，目录名是需求名。
