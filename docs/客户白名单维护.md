# 客户白名单维护

2026-11-13 定，来源 [#206](https://github.com/Lil-BobCN/grilling-remote/issues/206)（中台 I-0024）。本文只定 `customers.json` 的维护办法和数据形状；上传页、接收端点、登录实现、建仓建单归 to-spec。

## 一、名单是什么

`customers.json` 是客户、账号和仓指针的唯一登记表。一行一个客户。

- 邀请制：客户先微信联系运营者，运营者确认后加行、发账号；不开放自助注册。
- 登录名就是邮箱；密码由运营者手动设，微信发；忘了找客服重设。
- 客户简称由运营者给，账号带出；需求名由 agent 起，两者不是一回事（见 `docs/客户工作区方案.md` 第十二节）。
- 服务器凭登录态找到这一行，再决定能不能上传。

## 二、放在哪、谁是源

- 私有仓 `grilling-customers`（名字建仓时定；私有，不放公开仓）存 `customers.json` 和 Git 历史。
- 不再单独建 `clients.json`。#13 结论里的「客户 ↔ 仓库 ↔ 需求单」，仓指针并入本文的 `repo`；需求单仍在订单记录里，不在这份文件。
- 服务器上是这个私有仓的一份克隆；工作副本放在 `/data/customers/`（建议路径，落地时定）。注册机和上传服务都读这份工作副本。
- 文件只有几 KB；服务器上的是工作副本，历史和异地备份都在私有仓。
- 注册机在服务器上跑，改文件后提交并推送到私有远端。
- 服务凭据（服务器 SSH、GitHub token、Cloudflare token、SMTP 密码等）不放这个仓，另行管理。

## 三、谁在什么时候加行

- 只有运营者加行。客服以后只能提申请，由运营者执行。
- 不要手改工作副本；所有改动走注册机，避免漏字段、写坏文件或和上传服务撞车。
- 时机：客户微信联系、确认接单之后，发账号之前。
- 一条命令写一行，分配 `id`；命令要求手动输入初始密码（输两遍），打印 `id`，不回显密码。
- 加行后，运营者微信发：邮箱、初始密码、教程链接。
- 客户还没上传时，`repo` 为空。

## 四、一行写什么

ADR 0003 的四字段（简称、称呼、邮箱、仓名）是这张表的核心；本文新增 `id`、`status`、`password_hash`、时间戳和停用字段。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 内部不变编号，`c-0001` 起；订单和仓指针引用它，换邮箱不断历史 |
| `short_name` | string | 是 | 客户简称；小写英文/拼音，`[a-z0-9][a-z0-9-]{1,30}`，唯一；建仓后不再改 |
| `display_name` | string | 是 | 称呼，给人看，可中文、可重复 |
| `email` | string | 是 | 登录名和联系方式；小写，唯一；换邮箱改这里 |
| `status` | string | 是 | `active` 或 `disabled` |
| `repo` | string \| null | 否 | 客户仓名；建号时为空，上传服务首次建或复用仓后回写 |
| `wechat` | string | 否 | 客服通道；微信为主、电话兜底；不填不影响登录 |
| `note` | string | 否 | 备注 |
| `password_hash` | string | 是 | 登录凭据；只存哈希，不存明文 |
| `created_at` | string | 是 | ISO 8601 UTC，注册机写 |
| `updated_at` | string | 是 | ISO 8601 UTC，每次改动更新 |
| `disabled_at` | string \| null | 否 | 停用时间；启用时清空 |
| `disabled_reason` | string \| null | 否 | 停用原因；停用时必填，启用时清空 |

示例：

```json
{
  "id": "c-0001",
  "short_name": "acme",
  "display_name": "Acme 老板",
  "email": "boss@acme.example",
  "status": "active",
  "repo": null,
  "wechat": "wxid_example",
  "note": "",
  "password_hash": "$argon2id$example",
  "created_at": "2026-11-13T12:00:00Z",
  "updated_at": "2026-11-13T12:00:00Z",
  "disabled_at": null,
  "disabled_reason": null
}
```

## 五、账号和登录怎么对应

- 登录名 = `email`。大小写不敏感，文件里存小写，登录时也按小写查。
- 密码只存 `password_hash`。运营者手动输入初始密码，注册机负责哈希；`list` 和 `show` 永远不回显密码。
- 运营者忘了自己设的初始密码不影响客户：跑 `reset-password` 重设即可，账号不废。
- 登录成功 → 用邮箱找到这一行 → 状态必须是 `active`。`disabled` 拒绝登录，也拒绝上传。
- 上传页用登录态带出 `short_name` 和 `email`，不手填（见 `docs/客户工作区方案.md` 第六节）。
- 停用、换邮箱、重置密码后，现有登录失效；会话怎么失效归 to-spec。

## 六、撤销

- 撤销 = `disable`：状态改 `disabled`，写 `disabled_at`、`disabled_reason`；现有登录失效；上传被拒。
- 不删回传件、仓库、已交付物；在途订单不自动停，运营者在工厂侧手动处理。
- 删除是单独的人工动作，不在注册机里。
- `enable` 恢复：状态改 `active`，清空停用字段；历史仍留在 Git。

## 七、换邮箱

- 改同一行：`change-email` 把 `email` 换成新的；`id`、`short_name`、订单、仓库都不变。
- 旧邮箱立即不能登录；现有登录失效；运营者微信通知客户从哪天起用新邮箱。
- 旧值不另存字段，Git 提交里有 diff。

## 八、仓指针

- 注册时 `repo` 为空。
- 上传服务首次校验通过、建或复用客户仓后，回写 `repo`；只允许它写这一个字段。
- 仓名规则和过户归 #13 的结论，不在本文。
- 注册机和上传服务写同一个文件：改前加锁（`flock`），写临时文件再原子替换，提交；冲突重试。

## 九、注册机命令

```text
customer add --short-name acme --display-name "Acme 老板" --email boss@acme.example [--wechat ...] [--note ...]
   手动输入初始密码（输两遍），写一行，提交，打印 id

customer disable <id|email> --reason "..."
   状态改 disabled，写 disabled_at / disabled_reason，让现有登录失效

customer enable <id|email>
   状态改 active，清空停用字段

customer change-email <id|email> <new-email>
   改邮箱，让旧登录失效；订单和仓不变

customer reset-password <id|email>
   手动输入新密码，更新哈希，让旧登录失效

customer list [--status active|disabled]
customer show <id|email>
   只读，永远不显示密码哈希
```

补充：

- 上传服务回写 `repo` 不走这套命令，是内部函数，只写 `repo` 一个字段，提交信息写明 `set repo c-0001 acme`。
- 命令跑在服务器的 `dev` 用户下；`dev` 和上传服务用户都要能读写这份克隆。
- `short_name` 建号时定，之后不改；写错了只能停用该行、新建一行，所以 `add` 时要确认。
- 新邮箱必须唯一；换邮箱前先确认新地址没被别的客户占用。

## 十、文件权限和日志

- 工作副本 `/data/customers/customers.json` 权限 640；目录和 `.git` 只让 `dev` 和上传服务用户读写。
- 其他系统用户不可读。
- 日志不打印完整邮箱、密码和密码哈希。
- 私有远端用只限这个仓的部署密钥。

## 十一、历史和备份

- 私有仓是历史和异地备份。每次改动提交后推送到私有远端；推送失败时本地提交保留，命令报错，下次重试。
- 服务器坏了，从私有远端恢复克隆和工作副本。
- 备份不含服务凭据。
