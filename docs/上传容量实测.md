# 上传容量实测

2026-11-16。对应票 I-0049「上传服务容量实测」。

一句话：2 核 3.8 GiB、没有 swap 的源站，20 个接近 50 MB 的工作区同时上传能扛住，没有 OOM；内存峰值 2.08 GiB，两核打满约 15 秒。50 MB 上限暂时不用改。

## 方法和边界

在源站上起一份临时后端，代码用本仓库 `backend/` 的 1.0.0，和 `/data/app/current` 一致（测试时 `68c7262` 是 `backend/` 最新提交；之后 I-0137 又改了 `backend/`，容量结论没有复测）。临时目录 `/tmp/afk-capacity`，端口 8899，只监听 `127.0.0.1`。生产 `/data/customers` 和 `/data/uploads` 没有读写，生产服务 8787 没有重启。

上传请求从源站本机用 curl 发到临时服务，绕开 Cloudflare 和 Caddy。判序、限速、zip 检查、订单写入、git 提交都照生产代码走。数据目录初始化成 Git 仓库，远端是本机裸仓，模拟私有仓；不推 GitHub。

时间：2026-11-16 04:37–04:45 UTC。

## 50 MB 边界

上限是 50 MiB，即 52,428,800 字节，代码在 `backend/lib/config.mjs:27`。

| 包大小 | 结果 | 耗时 |
| --- | --- | --- |
| 52,300,698 字节 | 200 | 0.81 秒 |
| 52,390,999 字节 | 200（20 个并发，见下） | 11.0–14.7 秒 |
| 52,600,694 字节 | 413 | 0.35 秒 |

超过上限在上传读完后退 413，文案是「文件太大，最大 50 MB」；没写盘，不留失败包。

## 并发

20 个包同时上传，每个 52,390,999 字节，4 个账号各 5 次，同一个来源 IP。这个组合同时撞满每账号 5 次和每 IP 20 次的限速。

| 项 | 结果 |
| --- | --- |
| 成功 | 20/20，全部 200 |
| 整批耗时 | 14.8 秒 |
| 单个耗时 | 11.0–14.7 秒 |
| 聚合吞吐 | 约 67 MiB/s |
| CPU | 平均 67%，峰值 98%（2 核） |
| 服务进程 RSS 峰值 | 2,082 MiB |
| 可用内存最低 | 1,295 MiB（开始时 3,288 MiB） |
| OOM | 没有；内核日志没有 OOM 记录，看门狗没触发 |

另跑过一轮 20 个 48 MB 并发，20/20 成功，整批 16.5 秒。

单个 52 MB 包单独传只要 0.81 秒；20 个一起传时每个要 11–15 秒。整批吞吐和不并发时差不多，瓶颈是 2 核 CPU，不是网卡或磁盘。并发时每个请求体在 Node 里至少占两份（收包的 chunk 和 `Buffer.concat` 的结果），20 份就是约 2 GiB，这是内存峰值的主要来源。

## 判重和重传

判重按账号、软件简称和需求目录名，不按包内容。

| 场景 | 结果 |
| --- | --- |
| 同一账号、同一需求传两次完整包 | 同一张单 `o-0001`，轮次 1→2，两次上传都记进订单 |
| 先传内容不全的包，补完再传 | 第一次 200，`missing` 列出缺的文件；补完沿用 `o-0002`，两次上传都记下。校验未通过后的重传不增加轮次，仍记在第 1 轮 |
| 5 个完整包同时传同一个需求 | 同一张单，轮次 1 到 5 依次记下；订单锁把并发写串起来，没有丢轮次 |

## 7 天清理

`cleanupExpired` 在启动时跑一次（`backend/server.mjs:63`），之后每 10 分钟跑一次（`backend/lib/app.mjs:29-32`）。

| 场景 | 结果 |
| --- | --- |
| 8 天前的失败包 | 启动后删掉 |
| 2 天前的失败包 | 保留 |
| 8 天前的成功包 | 保留 |
| 真实 422 产生的失败包，把时间改到 8 天前再重启 | 删掉 |

时间是改 `meta.json` 的 `at` 模拟的，没有真的等 7 天。

## 容量结论和余量

- 首期 5–20 家客户，按最大 20 个 50 MB 同时上传算，这台机器扛得住，没有 OOM。
- 余量在内存：RSS 峰值 2.08 GiB，可用内存最低剩 1.26 GiB。再抬并发上限或抬 50 MB 上限，内存会先到顶。
- CPU 两核会被打满约 15 秒。官网静态页和上传抢同样的核，这期间的页面延迟没测。
- 磁盘不是瓶颈。根盘 `dd`（direct）594 MB/s，上传聚合 67 MiB/s；生产写到 `/data` 数据盘，那块盘的写入速度没测。
- 典型文字工作区只有几十 KB，50 MB 足够。只有客户放大量照片或 PDF 才会接近上限。

## 没测到的

- 走 Cloudflare 和 Caddy 的公网上传路径。需要 demo 账号密码，本次没有。
- 生产环境推 GitHub。本次用本机裸仓代替；20 并发下 26 次上传提交都在，`git status` 干净。GitHub 网络延迟和失败没测。
- `/data` 数据盘的写入速度。
- 并发上传期间官网页面的响应时间。
- 真实客户的工作区。
- Mac 右键压缩。归 I-0050。

## 顺带发现

`backend/lib/uploads.mjs:230` 只取 `recordUpload` 返回的 `order`，把 `sync` 丢掉。生产上 git 推送失败不会进日志，也不影响上传返回。本次 20 并发用本机裸仓没有失败，生产推 GitHub 没测。这是 1.0.0 的观察；1.1.0 起推送失败会写待办并记日志（D-0357）。去向见票 I-0049 的新需求冒头评论。
