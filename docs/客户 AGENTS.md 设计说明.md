# 客户 AGENTS.md 设计说明

一句话：`AGENTS.md` 放“每个会话都要生效、客户不用记着粘贴”的规则；提示词②只做触发器。

依据是 #25 的结论。正文在 `customer-kit/package/AGENTS-TEMPLATE.md`，148 行，7500 字节。

## 客户侧产出什么

客户侧只落澄清材料，不写 spec。

| 层 | 产物 | 谁写 | 给谁 |
| --- | --- | --- | --- |
| 客户侧小需求 | `.scratch/{简称}/需求草稿.md` | 客户侧 Agent | 运营者审 |
| 客户侧走 wayfinder | `.scratch/{简称}/map.md` 加 `issues/` | 客户侧 Agent | 运营者审 |
| 运营者侧 | spec，存成 issue | 运营者决策后手动跑 `to-spec` | 工厂 |

`需求草稿.md` 不是最终规格。运营者决策完，调用 `ask-matt` 问能不能 `to-spec`，能就手动跑。调度器不触发 `to-spec`。

#24 定了回传只带文件、不带对话记录。客户的原话必须落在文件里，运营者才看得到。

## 判据

一条规则进 `AGENTS.md`，先回答两个问题：

1. 它要不要在每个会话都生效？
2. 客户会不会忘了粘贴提示词，或者直接开口说需求？

两个都答“是”，就进 `AGENTS.md`。只答一个，留在技能里。

## 篇幅

本篇不走 40 行上限。依据是 #25 正文和 2026-11-05 对话第 3 轮。

148 行，7500 字节，占注入预算的 11%。代价是每次会话多带几千字节，收益是规则不用客户记着粘贴。

## 每条规则为什么放这里

| 规则 | 为什么放 `AGENTS.md` | 放提示词②会怎样 |
| --- | --- | --- |
| 说话方式 | 第一次输出就要生效，那时技能还没加载 | 只覆盖开场，之后靠模型自己记 |
| 谁管什么 | 每个会话、每张票都要成立 | 提示词只覆盖开场那一次 |
| 会话开头三句话 | 续做时客户只输“继续” | 提示词不知道这次是第几次 |
| 会话结尾三句话 | 发生在几十轮之后 | 那时提示词早就不在焦点里 |
| 分两类 | 客户可能不输提示词，直接说“我想做…” | 只在粘贴时生效，漏掉直接开口的入口 |
| 一次对话一张票 | 最需要它的时刻是对话变长以后 | 开头写一次，管不到后面 |
| 进度文件位置 | 写文件发生在会话中后段 | 路径写死在提示词里，改一次要重发 |
| 跳步 | 客户坚持时，对话已经很深 | 一次性提示没有持续约束力 |
| 原型 | 客户临时想看，时间点不可预测 | 同上 |
| 技术题 | `pending.md` 跨会话累积 | 提示词只管一次，条目格式会飘 |
| 偏题 | 发生在任意时刻 | 同上 |
| 写结论前查漏 | 跑的时候离提示词最远 | 同上 |
| 边界与冲突句 | 管的是以后每个会话 | 一次性提示管不了未来 |

表里按节归类。同一节里的子条共用这条理由。

开头和结尾都先复述终点：小需求用客户自己说的目标，走 `wayfinder` 用 `map.md` 的 Destination。这样客户每次会话都知道自己在往哪走。

## 提示词②为什么只剩触发语

提示词②只剩两个触发语：

- 新需求：`开始需求澄清。`
- 同一需求续做：`继续。`

三个理由：

1. 规则只有一份。两份写法一定会漂移，改一处漏一处。
2. 提示词负责“现在开始”，不负责“怎么做”。
3. 新需求和续做的输入不同，这正是提示词该管的事。

## 哪些留在技能里

| 内容 | 放哪 | 为什么 |
| --- | --- | --- |
| 提问轮次和格式 | `grilling/SKILL.md` | 只在提问时用，不占每次会话 |
| 地图和票的机制 | `wayfinder/SKILL.md` | 只在走 wayfinder 时用 |
| 词表和 ADR | `domain-modeling` | 只在有词义要定或决定难回退时用 |
| 原型怎么做 | `prototype/SKILL.md` | 只在有原型票时用 |
| 查资料怎么写 | `research/SKILL.md` | 只在研究票时用 |

## 确认单

不单独出文件。`需求草稿.md` 的“已经定下的”就是客户点头的部分。写文件前，Agent 先问“还有要补充或改的吗”。走 `wayfinder` 时，确认在每张票的 `## 结论` 里。运营者审阅时再看一遍。

## 查漏子代理

客户侧也要查漏。用 `subagent_fork`，因为它继承本次对话，还能读地图和票。`subagent` 是新上下文，只看得到写下来的东西，查不出漏写。

起不来时，Agent 自己重读对话和文件，不卡住客户。

## 证据

- `dsh` 在会话第一次请求注入 `AGENTS.md`，之后作为普通消息参与压缩。依据：`@deepseek-ai/dsh-agent-instructions` 的 `README.zh.md`。
- 注入预算 65536 字节。本文件 7500 字节。
- `subagent` 是新上下文，`subagent_fork` 继承对话。依据：本机 dsh 0.2.1-rc.5 的 `@deepseek-ai/dsh-base` 包，`cordis.patch.yml:380-395`，不在本仓库。另有 `@deepseek-ai/dsh-tool-subagent` 的 `README.zh.md`。客户机版本没测过。
- 重开新会话能读到 `AGENTS.md`：`customer-kit/测试记录.md`。
- dsh 的注入文本写明不覆盖用户的直接指令，所以 `AGENTS.md` 只能劝，拦不住。依据：`docs/research/客户澄清改走本机安装（旁支记录）.md`。
