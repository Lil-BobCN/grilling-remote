## 客户侧产出什么

客户侧只落澄清材料，不写 spec。

| 层 | 产物 | 谁写 | 给谁 |
| --- | --- | --- | --- |
| 客户侧小需求 | `.scratch/{需求名}/需求草稿.md` | 客户侧 Agent | 运营者审 |
| 客户侧走 wayfinder | `.scratch/{需求名}/map.md` 加 `issues/` | 客户侧 Agent | 运营者审 |
| 客户侧每个需求 | `.scratch/{需求名}/问题树.md` | 客户侧 Agent | 运营者用 `question-tree` 看三堆、重算 |
| 客户侧走 wayfinder 的逐轮问答 | `.scratch/{需求名}/问答记录.md` | 客户侧 Agent | 问题树的出处、运营者审阅 |
| 客户侧每个需求 | `.scratch/{需求名}/验收场景.md` | 客户侧 Agent 起草，客户逐条删改确认 | 父工单的验收条件 |
| 运营者侧 | spec，存成 issue | 运营者决策后手动跑 `to-spec` | 工厂 |

`需求草稿.md` 不是最终规格。运营者决策完，调用 `ask-matt` 问能不能 `to-spec`，能就手动跑。调度器不触发 `to-spec`。

包里没有 `ask-matt`。`AGENTS.md` 原来提到它的两处，已改成「运营者自己处理，你不做」，见方案第十三节第 5 项。

回传是整个工作区原样压缩，见方案第六节。取消 `meta.json`，agent 不写 JSON，不问简称。对话记录在 `~/.dsh/sessions/`，不在工作区里，v1 不回传。客户的原话必须落在文件里，运营者才看得到。父工单五段从 `问答记录.md`、`map.md`、`验收场景.md` 和 `Out of scope` 读，映射见方案第六节。

## 判据

一条规则进 `AGENTS.md`，先回答两个问题：

1. 它要不要在每个会话都生效？
2. 客户会不会忘了粘贴提示词，或者直接开口说需求？

两个都答“是”，就进 `AGENTS.md`。只答一个，留在技能里。

本篇不走 40 行上限。依据是 #25 正文和 2026-11-05 对话第 3 轮。

## 每条规则为什么放这里

| 规则 | 为什么放 `AGENTS.md` | 放提示词②会怎样 |
| --- | --- | --- |
| 说话方式 | 第一次输出就要生效，那时技能还没加载 | 只覆盖开场，之后靠模型自己记 |
| 谁管什么 | 每个会话、每张票都要成立 | 提示词只覆盖开场那一次 |
| 会话开头三句话 | 续做时客户发「继续：需求名 编号 票名」，或只发“继续” | 提示词不知道这次是第几次 |
| 会话结尾四句话 | 发生在几十轮之后 | 那时提示词早就不在焦点里 |
| 分两类 | 客户可能不输提示词，直接说“我想做…” | 只在粘贴时生效，漏掉直接开口的入口 |
| 一次对话一张票 | 最需要它的时刻是对话变长以后 | 开头写一次，管不到后面 |
| 单票开工与结论 | 开工领取、按 `Type:` 做、写结论、改旧结论都发生在对话中后段，模型容易漏 | 提示词管不到写结论那一刻 |
| 客户没听懂或答不上来 | 卡住的时间点不可预测，跨票反复出现 | 一次性提示没有持续约束力 |
| 进度文件位置 | 写文件发生在会话中后段 | 路径写死在提示词里，改一次要重发 |
| 跳步 | 客户坚持时，对话已经很深 | 一次性提示没有持续约束力 |
| 原型 | 客户临时想看，时间点不可预测 | 同上 |
| 技术题 | `pending.md` 跨会话累积 | 提示词只管一次，条目格式会飘 |
| 问题树 | 登记发生在每一轮提问前，要一直成立。`AGENTS.md` 只记文件位置，登记规则原计划在 `grilling`；2026-11-13 技能回上游原版后不在技能正文里，落点待定（见 I-0079 冒头），路径和别的进度文件放一起 | 路径写死在提示词里，改一次要重发 |
| 验收场景 | 起草在终点定完、拆票之前，后面每张票都可能改它。上游技能不改正文，规则放 `AGENTS.md`，每次会话都看得到 | 提示词只覆盖开场那一次，管不到后面改场景 |
| 偏题 | 发生在任意时刻 | 同上 |
| 开工与收尾 | 开工、写结论前、收尾都在对话中后段。2026-11-13 改成不写技能触发句，选票、改旧结论、收尾按 `AGENTS.md` 的硬规则走 | 提示词②只剩两句，带不了这些规则 |
| 边界与冲突句 | 管的是以后每个会话 | 一次性提示管不了未来 |
| 第一次自检 | 没有提示词①，文件有没有放对只能第一次打开时查。客户也可能先说「我想做……」 | 提示词②只剩两句，管不到客户先说什么 |
| 「继续：需求名 编号 票名」 | 新对话里 agent 不知道上次做到哪张。客户复制一行就能接上 | 提示词不知道这次是哪一张 |
| 一个工作区一个软件 | 新想法随时冒出来，要先问是同一个软件还是另一个 | 一次性提示管不到以后每次新想法 |
| 会话结尾第四句 | 前三句不变，第四句给出继续行；固定句只在 `AGENTS.md` 写一份，每次收尾都要给 | 那时提示词早就不在焦点里 |
| 产出文件一行，不动客户的文件 | 写结论那一刻要写产出文件，算写它的那张票，后面改前面结论时靠它找旧产出。不移动不删除是每个会话都要守的边界 | 提示词管不到写结论那一刻 |

表里按节归类。同一节里的子条共用这条理由。

开头和结尾都先复述终点：小需求用客户自己说的目标，走 `wayfinder` 用 `map.md` 的 Destination。这样客户每次会话都知道自己在往哪走。

## 新增的几处写了什么

理由见上表。这里只记写法。

- 第一次自检。没有 `.scratch/` 时，不管客户先说什么，先自检。查 `docs/agents/issue-tracker.md`、`docs/agents/domain.md`、`.dsh/skills/` 在不在。缺任何一个，就说「文件没放对，按官网第 2 步重放」，然后停下，不问需求。通过后再讲第一段开场词。
- 开工与收尾。每次开工，按「选票」规则核对票存在、没被挡、没做完，再把票头 `Status:` 改成 `claimed`。写 `## 结论` 前，不另起子代理查冲突；客户的话明显推翻已经定过的内容时，按「改前面定过的结论」回原票改。收尾，Agent 自己说四句，给继续行，不跑子代理。写成硬规则，是因为这些步骤发生在对话中后段，模型可能漏掉。这是合理推测，靠方案验收第 3 条测。
- 单票开工与结论。客户发来「继续：」那一行，先核对票在、没被挡、没做完，再把 `Status:` 改成 `claimed`。票头 `Type:` 决定怎么做：`grilling` 聊、`research` 我去查、`prototype` 看个样子、`task` 动手做。写结论前不另起子代理查冲突；客户的话明显推翻已经定过的内容时，按「改前面定过的结论」回原票改。`## 结论` 写一句能独立读懂的话，下一行写「产出文件：相对路径」，`Status:` 改 `resolved`，删 `Blocked by:`，地图 Decisions so far 只抄这一句。回传件的父工单也从这一句读。
- 客户没听懂或答不上来。先换短话重讲，再举例子或给选项、每个带推荐。要看样子才能定的，不现场做原型，仍按被动规则。客户答不了、要问别人，写一段能直接转发的话，票保持 `claimed`，答案带回来再写结论。技术题记 `pending.md`，等运营者确认。这一节接住旧图留下的「答疑路径」缺口。
- 问答记录。走 `wayfinder` 的需求建 `.scratch/{需求名}/问答记录.md`，开头写 `## 客户原话`，照抄客户第一次说明需求的话，带日期；之后按轮分节（`## 第N轮`），题号 `Q1`、`Q2`，客户原话照抄，处理另起一行。小需求不建，问答在 `需求草稿.md` 第 2 段。问题树的 `出处` 写「问答记录 第N轮 QN」。
- 验收场景。终点定完（走地图）或第一轮问完（小需求）之后，agent 起草三到六条，客户逐条删改。每条写清谁、从哪进、做什么、看到什么；写不出可当场验证的标「人工判断」。客户点头后写 `.scratch/{需求名}/验收场景.md`，开头写「客户确认：日期」。后面某张票改了客户能看到的东西，写那张票的结论时一起改这个文件，改完再确认一次。
- 收尾检查。全部做完，先按 `docs/agents/issue-tracker.md` 的「全部做完后的清雾」清 `Not yet specified`，再照「收尾与回传」核七项：票都做完、没有剩事、未定事项、验收场景已确认、客户原话在、不做清单在、小需求有复核行。核过了才说上传那一段。核不过先补，不叫客户上传。
- 「继续：需求名 编号 票名」。第一句以「继续：」开头，且需求名和编号都对得上某张票，就直接做那张，不再自己选。只发「继续」二字，按 `docs/agents/issue-tracker.md` 的「选票」规则选：读地图「接下来」，取第一行没被挡、没人领的；有 `Status: claimed` 的票，先接着做它。需求名或编号对不上，或那张票被挡着，按现有跳步规则处理。
- 一个工作区一个软件。新想法出现时，先问一句：是接着做同一个软件，还是另一个。同一个，在本工作区新建需求目录。另一个，请客户再解压一份到新文件夹。两个需求要合成一个软件，现在没有规则：按客户的话记进 `map.md` 的 `Not yet specified`，告诉客户「这条我记下了，开工前会有人确认」。
- 会话结尾。前三句不变，第四句给出继续行：推荐下一张票，并给出「继续：需求名 编号 票名」。固定句只在 `AGENTS.md` 写一份，追踪器文档、流程样本里不再各写。全部做完时，没有下一张票，也不说继续行；先按 `docs/agents/issue-tracker.md` 的「全部做完后的清雾」清 `Not yet specified`，再照「收尾与回传」核七项，核过再说回传的下一步：压缩整个文件夹，到官网上传页登录后上传，简称和邮箱由账号带出，勾「已问完」。小需求没有地图，不走继续行，收尾时也照「收尾与回传」的表核一遍，再说上传。

## 提示词②为什么只剩触发语

没有提示词①。解压后文件已摆好，第一次打开由 agent 自检。提示词②只剩两句：

- 第一次：`开始需求澄清。`
- 之后：复制收尾给的一行，形如 `继续：tanxin-yuyue 01 空档怎么放`。

三个理由：

1. 规则只有一份。两份写法一定会漂移，改一处漏一处。
2. 提示词负责“现在开始”，不负责“怎么做”。
3. 新需求和续做的输入不同，这正是提示词该管的事。

| --- | --- | --- |
| 提问轮次和格式 | `grilling/SKILL.md` | 只在提问时用，不占每次会话 |

## 确认单

不单独出文件。`需求草稿.md` 的“已经定下的”就是客户点头的部分。写文件前，Agent 先问“还有要补充或改的吗”。走 `wayfinder` 时，确认在每张票的 `## 结论` 里。验收场景单独一份 `验收场景.md`，开头写「客户确认：日期」，是父工单「验收条件」的来源，不算第二个确认单。运营者审阅时再看一遍。

## 小需求复核子代理

只有小需求在说「问完了」前起一次子代理：用 `subagent_fork` 读对话和 `需求草稿.md`，列出客户说过但没写进草稿的、前后矛盾的、还没定的词。按它列的改，在 `需求草稿.md` 末尾写「复核：……」一行。

改前面定过的结论不另起子代理，回原票改；收尾也不跑子代理。子代理起不来，就自己把对话和草稿重读一遍。不卡住客户，也不对客户提子代理。

## 越界产出和文件矛盾（2026-11-07 历史）

2026-11-13 起 `wrap-up`、`map-gate` 已删；越界产出按「偏题」四种记法当场处理，文件矛盾按「改前面定过的结论」处理（D-0132、D-0133）。下面保留当时的做法作历史。

运营者版 `wrap-up` 多了查越界产出，`map-gate` 多读关闭评论里列的文件。客户版取简化版，2026-11-07 运营者定。

- 越界产出。这次对话里做了别张票的内容，比如做第 1 张时顺手出了第 3 张的原型，Agent 自己处理，不给客户出表。在那张票的 `## 评论` 记一句「这张的一部分已在第 N 张做过：……」，并在地图「接下来」那行改一笔。对客户只说一句。只有成果已经把另一张票的答案定死，才问客户「认这个方向吗」。
- 文件矛盾。每张票 `## 结论` 下加一行「产出文件：相对路径」，算写它的那张票，没有就写「无」。后面查旧文件靠这一行。旧文件被推翻时，在第一行加「已被第 N 张取代」。Agent 不移动，不删除客户的文件。范围只在 `.scratch/{需求名}/` 内：`research/`、`prototypes/`、`pending.md`、`需求草稿.md`。
- 阻塞边只查一处：票头 `Blocked by:` 和地图「接下来」里「等 03」是否一致。这一条是按运营者版改的，运营者没单独点过。
