## 一、五条原则

1. 写和判分分开。实现者只读验证技能和测试文件，判分由另一个 agent 跑。（推断）
2. 两头有人，中间无人。（已定）
3. 一层一个负责人。调度器是普通程序，状态在工单标签里。（已定）
4. 工厂自己坏了，不算在票头上。（推断）
5. 机器能查的写成检查，不写成规矩。（有出处：v2 E3、pstack）

## 二、服务器、Mac、GitHub 分工

| 地方 | 干什么 | 不干什么 |
| --- | --- | --- |
| 服务器 | 接单网页、客户草稿、账号、邮件提醒、建仓建工单、推微信、客户成品上线 | 不存工单，不跑客户代码 |
| 你的 Mac | 调度器、agent、Docker 容器、Orca | 不接客户，不开公网 |
| GitHub | 工单和代码 | 只做两边的传话板，不跑任何东西 |

服务器需要 24 小时公网地址。Mac 不需要。

开工怎么传（已定，出处 #1 的拓扑）：

1. 客户点确认。
2. 服务器建客户仓，建 parent issue（父工单），打「已确认」标签，推微信。
3. Mac 上的调度器每 30 秒用 `gh` 读标签。是 Mac 主动往外读。
4. 看到标签变化就派活，结果写回标签。

没有「分配任务」这个动作。标签就是任务。

v2 没说清的三处：

1. v2 第二节写「服务器存工单」，不准确。工单在 GitHub，服务器只存草稿、账号、提醒记录。v3 改。（有出处：#1「不自建工单库」）
2. 调度器怎么发现新客户仓，v2 没写。建议同一个 GitHub 账号下用统一前缀。（推断）
3. 客户成品放哪台服务器没定，#7 还开着。起步合用最省，代价是前台和客户成品互相拖累。客户页面读进度用轮询还是 webhook（GitHub 主动通知），也没定。（待定）

## 三、流程

### A 接单（服务器，网页 agent 加客户）

1. 输入框，一句话开口。（已定，Y-001）
2. 三段问：只问生意，问载体和走向，先问经验再问技术后果。（已定，Y-003）
3. 边界追问：容量、空状态、重复、取消、时间。每项带默认值，客户改。B 店「一个时段放几单」就是这类缺口。（推断）
4. 验收场景草稿：每条写清谁、从哪进、做什么、看到什么、什么算不对。客户逐条删改。（已定，v2 第十节。写成场景是推断）
5. 确认单：五行大白话，加「怎么算成」，加「不做」。点了才建单。（已定）
6. 网页 agent 另外生成一批留出场景（开发时不给实现者看，只在验收前跑）。客户不看，你也不写。（待定，见第七节）

### B 建仓（服务器建壳，Mac 补满）

1. 先建客户仓，再建 parent issue。一客户一仓。（已定，#13）
2. 补满厨房：v2 第九节十二项不变量，加 `verify-<app>` 技能。（已定）
3. 技能钉版本，放进客户仓或烤进镜像，升级走冒烟。上游 to-spec、to-tickets、implement-spec、retro 都带 `disable-model-invocation: true`，模型不会自己调。容器里只有 claude，进不去宿主的 `~/.claude`。（有出处：上游原文和 Sandcastle 验证稿。放法是推断）
4. 每个客户仓一个只限该仓的细粒度令牌。（推断）
5. 留出场景存工厂目录，不放客户仓，实现者碰不到。（推断）

### 你点第 1 次：分流和五类闸门

同 v2 C1。分流结果和五类闸门同屏，大约三分钟。（已定）

### C 设计（Mac 上的主机 agent）

1. 写 spec（规格）。必须写明 seam（接缝，测试能替换和观察的那一层）。上游 to-spec 第 2 步本来要人确认接缝，v2 丢了。（有出处）
2. 拆票，垂直切片，每张票带验收条件和阻塞边。（已定）
3. spec 以 GitHub issue 为准，不另放仓库文件。上游把 spec 发成 issue 并打 `ready-for-agent`。两处都放，按标签认票的调度器会把 spec 当票。（待定。我建议 issue。冲突点是推断）

### 你点第 2 次：接缝、票单、每票验收

同一屏给三样：接缝、票单、每票验收条件。上游 to-tickets 第 4 步要迭代到用户批准，这一屏就是那一步。（前五单保留已定。加接缝是推断）

### D 执行（Mac，无人值守）

1. 调度器每 30 秒对账。同一客户一次只跑一张票，并行放在客户之间。视频里两个例子都偏串行，票之间有依赖。（待定。视频一手材料有出处）
2. 每张票一个 worktree（工作树）、一个容器。先写失败的测试，再实现。（已定）
3. 跑 `check` 和 `verify-<app>`，截图一前一后。（已定）
4. 独立评审 agent 读 diff，跑 `/code-review`。高风险票加 blast-radius。（已定）
5. 再跑留出场景。全过才算这张票完。（推断，先做实验 4）
6. 按依赖顺序合进需求分支。每合一次重跑验证。（已定。并行票合并冲突没测过）
7. 四类停法：
   - 同一张票三圈没进展。（已定）
   - 钱超额度。谁来计量、走中转时用量算在哪，v2 没写。（待定）
   - 碰禁区：这段改动不能验证，或出事不能回滚。（已定）
   - 工厂故障：token 报错、git 环境变量残缺（F-002）这类，重试没用。不计圈数，停整条线并推你。每次执行设挂钟上限，日志不增长由看门狗（watchdog，盯着日志的守护进程）杀掉重来。（推断）

证据是 v2 的四样，加「留出场景全过」。

通知：子票合并不单独推，并进「待验收」那一条。#2 的额度只够推「进队列」和「完成」。（有出处：#2）

### 你点第 3 次：验收

验收页看五样：验收条件逐条结果、前后截图、假设清单、门方向、影响范围。

假设清单：运行中遇到客户没说的可逆业务参数，agent 写成「假设」并标记，验收页集中让客户确认。涉及钱、数据、对外动作的才阻塞。（推断。客户肯不肯点，没验）

门方向由规则判定：碰迁移、删除、凭证、大版本依赖，一律单向门。agent 只能把标签往危险方向改。（推断。上游 /pr 模板自带门方向和影响范围两栏，问题只在谁来填）

### E 上线

合主干，部署，客户收到地址。夜间只合白名单：改文案、改样式、修小 bug。整单才算白名单。（已定。「整单」的口径是推断）

### F 每周复盘

一周抽三个会话，人裁决，只改工厂自己的指令。不自动化。（已定。视频也反对自动化）

## 六、没验的，要做小实验

1. 无头模式能否点名调用 `disable-model-invocation` 技能。
2. 容器里 `/tdd`、`/code-review` 能否被找到。Sandcastle 会话结束后，retro 能否读到会话日志。
3. 实现者能否改 verify 技能和测试文件，只读设置是否生效。
4. 独立评审能否抓住 `return true` 这类作弊。
5. 客户肯不肯点假设清单。
6. v2 第十四节原有的四个实验和两个风险：docker 整链没跑完，并行票合并冲突没测。
