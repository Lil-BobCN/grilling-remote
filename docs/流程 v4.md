## 三、A 接单

客户在场，一次坐下做完。

**A1 开口。** 输入框加例句加行业词。agent 先复述客户那句话。（已定，Y-001）

**A2 分轮问。**（已定，Y-003、Y-007。做法出自素材）

1. 三段是依赖层。后一段的题挂在前一段的答案下面。前一段没问完，后一段不出现。（已定，Y-003）
2. 段内照 grilling 原文。每一轮把此刻能问的全部问题问完，同一屏放下。每题带推荐答案，措辞让答「是」就等于接受。（素材：原文，S4，S6）
3. 答完，agent 重算待问清单，开下一轮。没有题数上限，也不显示「n / 总数」。到清单为空才算问完。（素材：原文）
4. 事实归 agent 查。客户提到现有网站或同行做法，派子 agent 去看，不问客户。（素材：原文）
5. 决策归决策的人。每题标明谁答：客户答；客户给倾向、你最后定；你答；agent 自查。后两类不上客户屏幕。（素材：原文。四类标法是我的）
6. 客户点「看不懂」，agent 用客户自己的词换个说法重讲（S4 的 wait what）。还不懂，升到原型，见 A2a。原型还看不懂，再转给你。（有出处）
7. 谈不拢的题，比如页面长什么样，做一次性原型让客户点选，再回来问（S4）。双手机预览先顶这个位置。（有出处）
8. 开口越模糊，题越多（S6）。这是正常现象，不设上限去压。（素材）
9. 第 1 段一个技术词都不出现。第 3 段的技术后果用人话写，带推荐。（已定）
10. 分流。第一轮问完后，系统判断这单走哪条路。小单跳过 spec 和拆票。大单走全套。特大单一个会话装不下，走 wayfinder（原文：一个会话装不下，才用它）。系统看三个信号。一，客户肯不肯「第一版只做一条主流程」（准入清单第 8 问，不肯就升级 wayfinder）。二，第一轮之后，互相独立的大块有几个，由网页 agent 数。三，本会话已用的上下文有多大，由程序数 token，阈值等第八节定了模型再定。前五单，开 wayfinder 图之前你点一次头。（已定，G-003。三个信号是推断，没验）
11. 客户答不了的题，多一条出路：转给第三人。比如答案在合伙人、会计、懂技术的朋友手里。agent 用 to-questionnaire 的做法：先问发给谁、要回什么，再只针对缺口出题。对方点一次性链接，在网页上一题一题答，只能答被转过来的那几题，不开账号。状态多一种「等第三人」，提醒照 24 小时一次。前五单数一数用了几次，再决定留不留。（已定，G-004。素材：to-questionnaire 原文。原文输出 Markdown 文件，网页化和一次性链接是推断）

**A2a 看不懂时的台阶。**（已定，G-005、G-006）

1. 第 0 级：每题的选项旁带示意图和例句。agent 把题、选项、推荐答案输出成数据，前端用固定组件画。（推断）
2. 第 1 级：客户点「看不懂」，agent 用客户自己的词重讲一遍。（有出处：wait-what 原文。原文要求英文受控语法，中文规则要另写）
3. 第 2 级：还不懂，agent 写一个单文件 HTML 原型，放进隔离小窗，客户点着看。先用模板，客户说「都不像」再现场生成一版。现场生成时并行发请求，真流式输出，先出骨架（地图 #4）。状态放内存，不持久化（prototype 原文）。（有出处，网页化是推断）
4. 第 3 级：多屏联动，要在服务器沙箱里构建和截图。先不做。

**网页 agent 的权限。**（已定，G-006。规则是推断，没验）

1. 只给「写文件」工具，不给 shell。只能写进一个专用目录，不和令牌、数据库放一起。
2. 原型页放进隔离小窗。`iframe` 只开 `allow-scripts`，不开 `allow-same-origin`。页面头加内容安全策略，禁网络请求，禁外部脚本。
3. 原因：页面由模型写。客户说的话和它查到的网页，都可能夹带指令（提示词注入）。小窗里的坏页面，最多只能画图。
4. 这一条改变 v2：v2 里网页 agent 只管接单对话，不写文件。落到 v2 要你说「替换」。

**A3 验收场景。** 第 1 段答完「做完看到什么会说对了」，agent 起草场景。客户逐条删改，问「哪条不对」。写不出可测条目的，标「人工判断」。确认后的场景放进 parent issue。/to-spec 读它写用户故事。/to-tickets 从 spec 里拆到每张票。票上的验收条件只能从客户确认的场景里拆，要新造，回客户补一条。（已定，v2 第十节）

**A4 确认单。** 五行大白话，加「怎么算成」，加「不做」。点了才建单。（已定）

**A5 找人。** 常驻。留言先挂草稿，你的手机当场响。不挡工厂。（已定）

**客户看到的进度。** 一句人话，加最近一张截图。不展示调了什么工具。借 S2 的同事式界面。（推断）

## 四、B 建仓建单

先建客户仓，再建 parent issue。十二项不变量一次补满，加 `verify-<app>` 验证技能。（已定，v2 第五节、第九节）

素材给这一步的依据，和这次加进来的做法：

- 每仓一个验证技能，给 agent 手和眼。没有它，人就是 agent 和工具之间的搬运工（S3，S1）。
- 验证技能分两部分。可重复的 CLI，保证每次跑法一样。功能地图，写应用有哪些功能、用户怎么找到它们（S8）。
- 功能地图每仓一张，放在验证技能目录里。读客户留言和驳回意见时，先对照地图认出说的是哪块。每张票合并时更新它，当作票的完成标准之一。（素材：S8。更新规则是推断）
- 判定明确的步骤写成脚本或 CLI，判断留给 agent（S3）。
- 模板仓带约束。agent 照着现有代码的写法扩展，所以建仓放进去的骨架，就是它以后抄的东西（S8，S1）。按 A1 的行业词做模板，先做预约取货类。一个功能一个目录，import 边界由 lint 拦，一种做法只有一个位置。（素材：S8。模板内容是推断）
- 禁「临时」「先这样」「TODO」这类注释词，用 lint 拦。理由：agent 拿注释给临时补丁找借口（S8，S1）。全禁注释，对要拿走仓库的客户太硬，所以只禁这类词。（素材：S8。范围是推断）
- 技能钉版本。上游 to-spec、to-tickets、implement-spec、retro 带 `disable-model-invocation`，模型不会自己调（原文）。

3. A2 里标「你答」「你最后定」的题。
4. 合规：收不收个人信息，接不接支付。默认都不。（准入清单第 12 问）

## 六、spec 之后：素材原样

**C2 /to-spec。**（素材：原文）读仓库，用项目词汇，守 ADR。定接缝，用 C1 的结果。按七字段模板写：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。不加第八个字段。不写文件路径和代码片段。

- 发成 issue，打 `ready-for-agent`（素材）。仓库里可放一份只读副本 `docs/specs/<issue>-<slug>.md`，由脚本从 issue 同步，以 issue 为准。
- 用户故事要覆盖客户确认的每一条场景。
- 调度器只认 spec 的子票，不认 spec 本身，所以 spec 带 `ready-for-agent` 不会被当票。（推断，要实测）

**C3 /to-tickets。**（素材：原文）垂直切片，一片穿过每一层，单独能演示，装得进一个新会话。每张票写验收条件和阻塞边。宽重构是例外，按 expand-contract 排（先加新写法，再分批迁移，最后删旧的）。别切太细：S6 演示里 13 张被嫌太细，改成 5 张。

**C4 你点「按这个拆」（第 2 次）。**（素材：to-tickets 第 4 步，迭代到用户批准）同一屏给你接缝、票单、每票验收。前五单保留这一下，数你改了几次。（已定）

**D 执行。** 无人值守。

- D1 谁跑循环：S5 列了三种，手动、脚本、agent 当保姆。脚本最可靠，作者推荐大多数人用。我们走脚本：调度器每 30 秒读标签，叫 Sandcastle 跑。（已定，v2。S5 支持）
- D2 单票：一个 worktree，一个容器，一个新会话。`/implement`，在约定接缝上调 `/tdd`。类型检查常跑，单文件测试常跑，全量测试最后跑一次。（素材：implement 原文）
- D2 并行：前沿票同时开。每个实现者先确认自己基于需求分支，合并前把需求分支最新合进自己。合并由合并者子 agent 做，冲突交给强的 agent。（素材：implement-spec 原文，S7）
- D3 验证：`check` 加 `verify-<app>`，启动应用，走关键路径，改前改后各一张截图，逐条过验收条件。每个 PR 一个负责人从做到合，验证队没写过这份代码（autopilot-full）。验证 agent 的数量按风险档定：低风险一个，高风险多个。它们像真实用户那样点来点去找回归，找到就修，修完再来，直到能合。完整验证队只在代码就绪的那个提交上跑一次。之后的小改只派一个验证者，只改文字的不派。（素材：S3，S1，autopilot-full 第 4 步）
- D4 评审：评审者没见过写代码的上下文，分标准和 spec 两轴（素材：code-review 原文，S4）。高风险票再加 interrogate：不同模型各自去攻击这份改动，只留跑一遍能证明的问题（interrogate 原文）。主评审把意见分采纳、考虑、记下、驳回四类，写进评审评论（S1）。高风险档由规则定：单向门、碰迁移删除凭证大版本依赖、影响范围大。
- D5 合并：验证队和评审跑完会留下四样记录，这不是另一道门槛：验证技能跑过，有前后截图或 trace，测试全绿，评审两轴都过。验证队修到能合，票才合进需求分支，不合主干。解完冲突要重跑验证。（已定，v2。素材依据：S3 全自动验证，S7 实现、评审、合并三段）
- D6 停法：同一张票三圈没进展，钱超额度，碰禁区。禁区的判据：这段改动能不能验证，出事能不能回滚。（已定，v2。S3 支持）
- D6 复发：同类问题跨票出现两次，先自动加一条规则重跑一次，还不过就叫你。新规则有门槛：要在出错那次的改动上亮红灯，在修好的版本上通过。做不到就不自动加，直接叫你。（S1。门槛是素材，用在 D6 是推断）
- D6 队伍过不了：验证队和评审修了还是过不了，当环境问题。停这条线，通知你，附现象和试过的办法。放宽任何一道检查，要验证者的证明，再由你复签。关掉或只报警不拦的检查，一律拿掉。（素材：autopilot-full 第 6 步，复签人改成你）
- D7 收尾：全部票完成，在需求分支上跑一次评审，由一个实现者统一修。清理 worktree。（素材：implement-spec 第 7、9 步）

**E1 合并与抽样。**（素材：S3，S5）

工厂做：

1. 写 /pr 正文四栏：摘要，证据（改前一份、改后一份），合并危险（单向门还是双向门），影响范围。（原文）
2. 门方向由规则判定，agent 只能往危险方向改。碰迁移、删除、凭证、大版本依赖，一律单向门。（推断。/pr 没说谁来填）
3. 验证队和评审都过了：工厂自己合主干，部署，客户收到地址。不再按单向门停下。白天夜里同一条规则，夜间白名单并入这里。「人工判断」条目写在 PR 正文里，抽样时先看它们。（素材：S3，S1，autopilot-full 第 5 步：只合验证者证明过的，绿灯 CI 本身不放行）
4. 队伍过不了：当环境问题，停这条线，通知你，见 D6。你修环境，不替这个 PR 改结论。（素材：S3，autopilot-full）
5. 抽样发现问题：先回滚，另开分支改，不重开单。记一条：这次的错，本该在哪一层被挡住。层次是：代码库、静态分析、规则和技能、风格指南加人审（S8）。复盘按层归类。

你抽样（合并之后）：

1. 每天早上看前一天合进主干的单。读 /pr 正文和提交历史，不逐行读 diff。（素材：S1，S3。频率已定：每天早上一次）
2. 先看单向门、影响范围大、验证没覆盖到的。
3. 看模式，不看单个。一个 agent 走捷径是个案。多个 agent 走同一条捷径，就改环境。（S1，S3）
4. 发现问题：回滚，改代码，加规则（S3）。
5. 单向门多的客户，验证要更强，走 D3、D4 的高风险档（S3）。抽样仍是每天早上一次。

假设清单：运行中遇到客户没说的可逆业务参数，agent 写成「假设」并标记，客户事后在进度页点确认。涉及钱、数据、对外动作的才阻塞。（推断）

**E2 上线。** 合主干后部署到预置环境。上线失败能回滚到上一版。客户状态变「可以看了」，收到地址。交付给部署地址加代码 zip。客户明确要仓库，才用他的邮箱建号过户。（已定，v2）

**E3 复盘。**（素材：S5，S1，S3，S8）

1. 一周抽三个会话，人看报告。只给建议，不自动化。理由：agent 自己修自己的发现，会追着假阳性跑（S5）。星期几待定。
2. 只改工厂自己的指令、规则、技能，不动客户那张单。
3. 能变成检查的写成检查，不写成指令。同一个坑第二次踩到才写规则（S1，S5）。
4. 改环境的顺序：架构、类型、lint、测试，文档最后（S1）。五层口径：代码库、静态分析、规则和技能、风格指南加人审（S8）。
5. 新规则要在出过错的历史改动上先亮红灯，没红就不加（S1）。
6. 看到坏模式，第一反应是写一条拦截规则，清理另开单排期（S8）。
7. 园丁：复盘时扫「临时」「先这样」「TODO」和重复写法。先写规则拦住，再排清理（S8）。
8. 删：模型变强后，删掉不再需要的指令。删之前用植入缺陷做 A/B，删后没变差才算数（S1，S3，S4）。植入缺陷集要先建，见第十节。
9. 驳回记录按层归类，看哪一层老是漏。（推断）

**F 外循环。**（推断。素材：S3，S2，S8）

上线之后，客户的反馈有入口：进度页的「找人」和后续留言。

1. 分诊 agent 读反馈，对照功能地图认出说的是哪块，用验证技能复现。
2. 能复现，且在已验收场景范围内：自动开小单，走 C1 的小单路径，跳过 spec 和拆票，仍过 D 和 E1。
3. 是新功能：回复客户「这要开新单」，回到 A。
4. 复现不了：写成一条留言，附现象和试过的办法，推给你。
5. 同类反馈有好几条：合成一单，不每条各开一个（S3：同类报告放在一起看）。

## 十、pstack 怎么接

结论：用 pstack 的做法，不装插件。

读到的事实（2026-11-03，只读，没装，没跑任何脚本）：

1. 官方版是 Cursor 插件。仓库 `cursor/plugins` 的 `pstack/`，提交 `ae5650f`，版本 0.15.36，MIT，版权 Lauren Tan，58 个技能。验证队用到的剧本 `autopilot-full`，并行验证 `swarm`，攻击改动 `interrogate`，都在里面。
2. 这些写给 Cursor 云端 agent。`autopilot-full` 写明每个负责人是 Cursor 云端 agent。`swarm` 里写死云端环境。`swarm` 和 `arena` 从 `~/.cursor/rules/pstack-models.mdc` 读模型分工。我们的执行在 Sandcastle 容器里，原文装上去跑不起来。
3. Claude Code 有社区移植版 `michael-denyer/pstack-claude`，提交 `513c088`，MIT 加两份 Cursor 的许可文件。它带一个 SessionStart 钩子：每个会话开始，往上下文里注入一段「You have pstack」的强制说明，让任务走 poteto-mode。装进 `~/.claude` 会改变你所有项目的会话，还要和 superpowers 并存。所以不装。

做法（推断，没验）：

1. 只借剧本和技能原文。钉在 `ae5650f`，复制进工厂自己的技能目录，每个客户仓装的时候带上。
2. 改写 Cursor 专有的部分。云端 agent 改成 Sandcastle 容器里的子 agent。`pstack-models.mdc` 改成第八节的角色表。
3. 借的清单：`autopilot-full`、`swarm`、`interrogate`、`blast-radius`、`create-verification-skill`（带功能地图的例子）、`correct`、`no-comments`。这七项引用到的另装：`comment-sicko`（agent）、`show-me-your-work`、`in-your-own-words`、四个 `principle-*` 技能。arena、shipping、opening-a-pr、babysit、ketchup 不装，取舍见 `factory-skills/pstack/CHANGES.md`。
4. 改写已由 Claude Code agent 完成，在 `factory-skills/pstack/`，逐文件改动见 `CHANGES.md`。你审，说「定」再接进客户仓模板。没解决的问题和没验的事，见 `CHANGES.md` 的两节同名小节。

`autopilot-full` 里照搬的规则（原文第 2 到 7 步，改写时以原文为准）：

1. 一个负责人从做到合一个 PR。验证队没写过这份代码。
2. 完整验证队在代码就绪的提交上只跑一次。之后的小改只派一个验证者，只改文字的不派。
3. 只因能演示的问题拦下：一次失败的运行，或一行被 PR 改错的文档。其余记成后续事项。
4. 绿灯 CI 本身不放行。合的是验证者证明过的那版代码。
5. 合并前看主干有没有动到补丁依赖的东西。动了才重新跑，不为每次主干变动都重来。
6. 放宽任何一道检查，要验证者的证明，再加一次新的复签。关掉或只报警不拦的检查，一律拿掉。
7. 每隔一段时间巡检所有 agent，按它留下的痕迹判断是不是卡住，不看它自己写的状态。这条对应调度器每 30 秒对账。
8. 收到停止指令，所有负责人零写入。

## 十一、定版后再验（不挡定版）

1. 手工演一遍 grilling：「街坊想订明天上午的砂糖橘」，再演「做个网站」。记轮数、每轮题数、客户接受推荐的比例。
2. 一轮放几个题，客户不嫌多。
3. 推荐答案由谁校准。
4. 无头模式能否点名调用带 `disable-model-invocation` 的技能。
5. 带 `ready-for-agent` 的 spec，调度器是否真的只认子票。
6. 容器里 `/tdd`、`/code-review` 能否被找到。
7. 功能地图能否在每张票合并时自动更新，并和真实界面对得上。
8. 模板仓的约束，客户拿走仓库后能不能看懂。
9. 植入缺陷集，复盘「删」之前要先建。
10. v2 第十四节的旧账：docker 整链没跑完，并行票合并冲突没测。
11. 改写后的验证队和 interrogate，能不能在 Sandcastle 容器里并行跑，并读到第八节的角色表。
12. 钉在 `ae5650f` 的技能，之后 pstack 升级怎么同步。
13. 改写后 `autopilot-full` 新加的 CI 段里，`gh run view --log-failed` 和 `mergeable,mergeStateStatus` 是改写者的译法，原仓库没有这两处写法，也没在真实仓库里跑过。
14. 无人值守时，`correct`、`interrogate`、`no-comments` 里要人批准或回答的地方，只写了动作，没定通知渠道和缺口记在哪。要在 trail store 里定一类记录行。
15. 网页 agent 只写文件的权限，能不能在服务器上真的限住：只能写专用目录，没有 shell。
16. 隔离小窗能不能挡住一个带恶意指令的原型页：禁网络请求，禁外部脚本。
17. 第 0 到 2 级，每一级客户要等多久。地图 #4 里的首 token 时间还没测。
18. to-questionnaire 的一次性链接，能不能限定只答被转过来的题。
19. 分流的三个信号，拿几条真实需求试一遍，看判断对不对。
