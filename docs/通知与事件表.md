# 通知与事件表

2026-11-15 定，来源 [通知链路与事件表](https://github.com/Lil-BobCN/grilling-remote/issues/215)。2026-11-16 按 I-0141 的 D-0334 给四条等人待办加邮件，载体改成企业微信 Bot。推送只给运营者。客户那条线见 `docs/客户进度.md`。

## 一、谁触发

工厂事件里，调度器是唯一触发方。它每 30 秒读一遍客户仓，按状态算出该推的事件，向推送通道的 `webhook`（外部程序调用 Bot 的地址）发 POST。正文是 JSON，带事件名、客户简称、需求名、状态短语、一行摘要、动作和链接。企业微信 Bot 照正文原样发一条消息，不改写，不做路由，不点火。

基础设施告警是另一条触发路径：Mac 上的巡检脚本直接 POST 同一个 webhook，Bot 同样照正文原样发。工厂事件仍只有调度器一个触发方。巡检内容见 `docs/服务器操作手册.md` 第十一节。

- 一个企业微信 Bot 一个内部群，群里只有运营者。Bot 只在群里发消息。手机上点的只算草选，最终决定在 Orca 做。
- 推送只是提醒，不是送达回执。没收到按待办状态重发，见第四节。
- webhook 地址和 key 由调度器保管。通道失败时的重试和兜底见第四节；限流失败不自动重试。
- 推送通道的选型、限流和配置归「通知链换轨」地图（I-0111）。

## 三、每日抽样

每天 8:30 推前一天 00:00 到 24:00 合进主干的单。一单都没有就不发。只列客户简称、需求名和 PR 链接，不写别的。抽样动作不变，见 `docs/介入点.md`。

## 四、重复与失败

- 等人的待办：补缺口、拆票、该跑 to-spec、需要你答。每 24 小时重发一次，正文末尾加 `已等 {N} 天。` 补缺口和拆票等到点头，to-spec 等到仓库里有 spec，需要你答等到 trail 里出现 `answered` 或 `parked`。
- 出事、自己合并、部署完成、新单进队列、needs-info：只发一次。
- webhook 非 200：下一轮重试，最多 3 次，间隔 30 秒。
- 3 次仍失败：出事立刻改走邮件；其余事件等下一次状态变化或 24 小时重复。四条等人待办本来就发邮件，不走这条转投。
- webhook 连续失败 3 次（不分事件）：发一封「通知通道可能断了」邮件，一天最多一封。
- 已推标记：调度器本地文件，按工单加事件名记时间。崩溃重启后最多重复推一次。

## 五、不推的事件

- 开始开发。D-M1-001 已定写本地日志。
- 子票状态变化。
- 待客户验收、客户点头。客户走微信，验收不设时限。
- 三条客户微信和已发记录。管理视图标「该发消息」，发过写订单文件的 `messages`；第 2 条只在「部署完成」推送正文里带一句。
- 客户卡住、客户留言。走微信。
- 驳回、改口、关票。运营者自己写评论或关票。
- gate 行写 `answered` 或 `parked`。等待中的线继续走，不再提醒。
- 父工单关闭。

## 六、邮件

邮件走两条线：

- 兜底：出事、点火超时、通知通道连续失败。出事先推送、再邮件，推送失败时邮件兜底；点火超时只有邮件；通道连续失败由告警邮件报。
- 等人的待办：补缺口提案、该跑 to-spec、拆票提案、需要你答。推送在前、邮件在后，邮件慢不拖推送。

由调度器用独立 SMTP（发信服务）发。基础设施巡检的邮件由巡检脚本自己发，不计入这些；其余发送方仍是调度器。

SMTP、发信域名、退信处理归 to-spec。到达没验，归 [Grok Bot 长时实测：30 分钟过期、例程暂停、限流与邮件兜底](https://github.com/Lil-BobCN/grilling-remote/issues/318)。
