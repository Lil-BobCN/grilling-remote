# 通知与事件表

2026-11-15 定，来源 [通知链路与事件表](https://github.com/Lil-BobCN/grilling-remote/issues/215)。推送只给运营者。客户那条线见 `docs/客户进度.md`。

## 一、谁触发

调度器是唯一触发方。它每 30 秒读一遍客户仓，按状态算出该推的事件，向一条固定 routine 的 `webhook`（外部程序调用 Bot 的地址）发 POST。正文是 JSON，带事件名、客户简称、需求名、状态短语、一行摘要、动作和链接。Grok Bot 照正文原样发一条消息，不改写，不做路由，不点火。

- 一条 routine（例程，Grok Bot 里按计划或事件跑的任务），一个一对一对话。不开群聊：群聊没有 per-Bot 通知开关，审批卡也不显示。
- Bot 只在对话里发消息。手机上点的只算草选，最终决定在 Orca 做。
- 推送只是提醒，不是送达回执。没收到按待办状态重发，见第四节。
- webhook 地址和 key 由调度器保管。routine 被暂停或 key 过期时，webhook 返回非 200；限流失败不自动重试。

## 三、每日抽样

每天 8:30 推前一天 00:00 到 24:00 合进主干的单。一单都没有就不发。只列客户简称、需求名和 PR 链接，不写别的。抽样动作不变，见 `docs/介入点.md`。

## 四、重复与失败

- 等人的待办：补缺口、拆票、该跑 to-spec。每 24 小时重发一次，正文末尾加 `已等 {N} 天。` 补缺口和拆票等到点头，to-spec 等到仓库里有 spec。
- 出事、自己合并、部署完成、新单进队列、needs-info：只发一次。
- webhook 非 200：下一轮重试，最多 3 次，间隔 30 秒。
- 3 次仍失败：出事立刻改走邮件；其余事件等下一次状态变化或 24 小时重复。
- webhook 连续失败 3 次（不分事件）：发一封「通知通道可能断了」邮件，一天最多一封。
- 已推标记：调度器本地文件，按工单加事件名记时间。崩溃重启后最多重复推一次。

## 五、不推的事件

- 开始开发。D-M1-001 已定写本地日志。
- 子票状态变化。
- 待客户验收、客户点头。客户走微信，验收不设时限。
- 客户卡住、客户留言。走微信。
- 驳回、改口、关票。运营者自己写评论或关票。
- 父工单关闭。

## 六、邮件

邮件只做单向兜底，覆盖三类：出事、点火超时、通知通道连续失败。由调度器用独立 SMTP（发信服务）发。Grok Bot 自己的邮件不能无人值守发，routine 发的邮件先存草稿。

SMTP、发信域名、退信处理归 to-spec。到达没验，归 [Grok Bot 长时实测：30 分钟过期、例程暂停、限流与邮件兜底](https://github.com/Lil-BobCN/grilling-remote/issues/318)。

## 七、依据

- 触发方式：调度器是唯一状态源，出事类事件只有它能算。Bot 订阅 GitHub 看不到状态；轮询的最短间隔是 5 分钟，延迟从 5 分钟起，还持续花用量。D-M1-013 已定 Bot 不做路由。
- webhook 机制：官方文档写 POST 带 `Authorization: Bearer {key}` 和可选 JSON 正文，200 只代表已受理；全部 routine 合计 300 次/小时，单条 200 次/小时；最短计划间隔 5 分钟；每次 run 花用量。来源：`https://docs.x.ai/grok-bot/skills-routines-and-automations#webhooks`。
- 推送只是提醒：实测延迟约 15 秒，没有送达或已读回执，见 D-0175。
- 合并推送：D-M1-009 已定。E1 漏写通知，本票补进 `docs/工厂流程.md`。
- 进队列和完成：D-M1-001；完成对应事件表的「部署完成」。
- 补缺口、拆票、出事、点火超时：`docs/介入点.md`、`docs/adr/0005-调度器直接点火.md`。
- 邮件不能无人值守：官方文档写 routine 发的邮件先存草稿，没有无人值守发送选项。来源：`https://docs.x.ai/grok-bot/computer-and-apps#give-your-bots-an-email-address`。
