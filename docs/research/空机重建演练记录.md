> 状态：历史（2026-11-16 的空机重建演练记录，只作证据）

2026-11-16。对应票 I-0071「空机重建演练」（GitHub #258）。

一句话：在一台本机 lima 虚拟机上按 `docs/运维手册.md` 第十节从零重建了一遍，站点、mTLS、上传服务都跑通；手册漏了 Node 安装、账号恢复、站点发布、sshd 收口和时区五步；Cloudflare 两张清单按实际 zone 核对后改了 3 组偏差（Bot Fight Mode 写错、`.dev` 缺设置项且限速指向停用子域、`.space` 缺邮件记录）。都已改进手册，没验到的部分见第五节。

## 三、逐步记录和卡点

### 1. 建 VM

- `limactl disk create afk-drill-data --size 80G --format qcow2`
- `limactl create --name=afk-drill --cpus=2 --memory=4 --disk=30 --mount-none --set='.additionalDisks=["afk-drill-data"]' template:ubuntu-24.04`
- lima 把数据盘自动分区并挂到 `/mnt/lima-afk-drill-data`。演练按手册第九步先 `umount`，再 `wipefs`、`mkfs.ext4`、按 UUID 写 `/etc/fstab`，等于把 lima 的自动处理覆盖掉，和真实云机器的空数据盘等价。

### 2. 用户和系统收口

- `useradd -m -s /bin/bash -G sudo dev`，公钥放 `~/.ssh/authorized_keys`。
- 手册原步骤只写到这里。实测 lima 镜像默认 `PermitRootLogin without-password`、时区 `Asia/Shanghai`，和第一节写的生产状态不一致，补了两步：sshd drop-in 写 `PermitRootLogin no`、`PasswordAuthentication no`，时区 `Etc/UTC`。补跑后 root 登录被拒、`dev` 正常，`timedatectl` 显示 UTC。
- 生产上 `dev` 的 sudo 要密码；演练为了无人值守用了 NOPASSWD，这一项没验。

### 3–4. Caddy 和防火墙

- `apt-cache policy caddy` 在 Ubuntu 24.04 的 `noble-updates/universe` 里是 2.6.2，和手册写的一致，没有版本偏差。
- `ufw` 按第二节的 15 个 IPv4 段逐条加 80/443，加 22，`ufw enable` 后 32 条规则。`sudo ufw status` 显示 22 任意来源、80/443 只放 Cloudflare 段。
- 云控制台安全组在 VM 上没有对应物，没验；生产重建时仍按第二节在控制台点，改完必须点「应用」。

### 5–8. 证书和 Caddyfile

- 手册第 5 步的 EC 私钥和 CSR 生成命令可用；CSR 带 `.dev`、`*.dev`、`.space`、`*.space` 四个 SAN，为以后切 Full (strict) 留好。
- Origin CA 签发和 AOP 上传都要改线上 Cloudflare，按运营者决定跳过；演练用自签证书代替 Origin CA 证书，Caddy 能正常起。
- AOP CA、客户端证书按第四节的命令生成；Caddyfile 直接用仓库 `deploy/Caddyfile`（sha256 `b2c9a4a2…`，与生产一致），`caddy validate` 通过。
- mTLS 验证：不带客户端证书直连源站，TLS 1.3 握手报 `certificate required`；带演练 CA 签的客户端证书，首页 200。和手册第四节「校验失败时客户端看到什么」一致。

### 9. 数据盘和后端

- 数据盘：`umount` → `wipefs -a /dev/vdb1` → `mkfs.ext4 -L afkdata` → `blkid` 取 UUID → 写 `/etc/fstab`（`UUID=… /data ext4 defaults,nofail 0 2`）→ `mount -a`。`df -h /data` 79 G。和第九步一致。
- **卡点 1：空机器没有 Node。** 手册 9a 直接跑 `install.sh` 和发布，但 `deploy.sh` 的健康检查要 `node`；`docs/后端服务部署.md` 写「机器上已有 Node 26，不装第二个运行时」，那是旧机器的事实，不是重建步骤。补跑 NodeSource `setup_26.x` 后装了 26.13.1。手册已补成 9a 步。
- `install.sh` 可以重复跑；建 `afkapp` 用户、`/data/app`、`/data/customers`、`/data/uploads`、systemd 单元、换 Caddyfile 都通过。
- `app.env`：`SESSION_SECRET` 用 `openssl rand -base64 32` 生成；`DATA_DIR`、`UPLOAD_DIR` 用默认值；`COOKIE_SECURE=true`、`ALLOWED_ORIGINS=https://afkfactory.space,https://afkfactory.dev` 与生产一致。
- `package.sh backend 1.0.0` 打出 24 KB 的包，`deploy.sh` 发布成功，`check.sh` 全部通过。
- 建测试账号（`customer.mjs add`）后，登录、`/app/api/session`、`/app/api/health` 都正常。

### 上传服务实测

- 经本机 8787 直连和经 Caddy `https://afkfactory.dev/app/api/uploads` 各传了一次真实 zip（`docs/回传样例/工作区`，7.9 KB），都回 200，建出订单 `o-0001`，`missing` 为空。
- curl 调登录和上传要带 `Origin: https://afkfactory.dev`，否则 403「请求来源不对」。这是 `assertSameOrigin` 的正常行为，不是故障；手册第三节的 curl 示例如果以后要验登录态，记得加这个头。
- **顺带发现一个上传兼容问题，见第六节。**

### 9c. 从私有仓恢复账号和订单

- 生产 `/data/customers` 原来不是 Git 仓库：服务上线时 `/etc/afkapp/app.env` 的 `GITHUB_TOKEN` 是空的，订单和账号只有服务器这一份。
- 2026-11-16 建好私有仓 `grilling-customers`，把现有 `customers.json` 和 `orders/` 提交成 `341b2e4` 推上去；`.git/config` 里是带 token 的 remote，权限 600。
- 演练 VM 里按手册 9c：`git clone` 到临时目录 → 替换 `/data/customers` → `chown afkapp:afkapp`。克隆到同一个提交 `341b2e4`，`orders/` 有 `o-0001.json`、`o-0002.json`，`customers.json` 1 行（`c-0001`），服务健康检查正常。
- 注意：`/data/customers` 是已经有内容的目录，直接 `git clone` 进去会失败；手册的参考命令写成「克隆到临时目录再替换」。替换只在空机重建时做，已有数据的机器不要跑。
- 演练副本验完后断开了它的 remote，避免演练机误推到生产私有仓。

### 10. 时钟

- 写 `/etc/systemd/timesyncd.conf` 钉 `119.28.230.190` 和 `162.159.200.1`，restart 后 `System clock synchronized: yes`。lima VM 本来就能对时，这一步没有区分「钉的地址生效」还是「原有同步」，只确认了不报错。

### 11. 重启后复核

- 05:25:16 发 `systemctl reboot`，约 15 秒后 SSH 回来（第一次探测有竞态，精确值没抓到）。
- 回来后：`caddy`、`afkapp` active；`/data` 自动挂上；`check.sh` 通过；`/app/api/health` 200；无证书直连仍报 `certificate required`，带证书首页 200；客户包下载 200、`cache-control: no-cache`、SHA256 与发布记录一致。
- **卡点 2：`systemctl --failed` 有 1 个单元。** 是 `cloud-final.service`（cloud-init final），原因是 lima 的 per-boot 脚本在装 nerdctl，和生产无关。真实云机器上 cloud-init 一般能跑完；如果重建后看到这个单元失败，先看 journal，再判断是不是 lima/容器环境特有。

## 五、没验到的

1. **云控制台安全组**：VM 没有控制台；生产重建时仍要在控制台按第二节改 68 条，改完点「应用」。
2. **Cloudflare Origin CA 签发**：运营者决定只读核对，没在演练里用 CSR 签证书；实际服务器用自签证书代替。
3. **Cloudflare AOP 客户端证书上传**：同上，没上传；mTLS 只在源站侧用 curl + 客户端证书验证。
4. **整 zone 重建**：没有测试域名，Cloudflare 只通过 API 只读核对了现有 zone 和清单，没从零建一个 zone。
5. **sudo 要密码**：演练用 NOPASSWD，没验运营者输密码的环节。
6. **生产数据恢复**：已补验。私有仓 2026-11-16 建好，生产数据推到 `341b2e4`；演练 VM 从同一提交克隆，订单 2 张、客户 1 行对上。推送前生产 `GITHUB_TOKEN` 是空的，订单只有服务器一份，这一段是演练后才补上的。
7. **上传路径经 Cloudflare**：VM 在私网，经 Cloudflare 的公网链路没走。

## 六、顺带发现

1. **macOS 右键压缩的 zip，中文文件名会乱码。** 用 `zip`（Info-ZIP）和 Finder 同款的 `ditto -c -k` 各打了一个包，文件名都是 UTF-8 字节但没置 UTF-8 标记（flag 0x800）；服务器用 Python 解包时按 CP437 解码，`验收场景.md` 变成乱码，上传校验误报「缺验收场景」。用 Python `zipfile` 打的包（带 UTF-8 标记）上传通过。客户按教程在 Mac 上右键压缩就会踩到，建议单独开票修解包器（尝试 UTF-8 解码兜底），并核对客户教程里的压缩说法。
2. **`.dev` 的 Cloudflare 限速规则指向已停用的 `upload.` 子域**，上传现在走裸域，边缘限速不覆盖。I-0086 关票时已冒头（C-0655 ②），本票没改。
3. **`GITHUB_TOKEN` 只写进 `app.env`，1.0.0 的服务代码不读。** 生产上实际是空的：2026-11-16 演练时 `/etc/afkapp/app.env` 的 `GITHUB_TOKEN` 为空，订单没有外部副本。演练后已填 token、建仓、推送并验证克隆恢复。即使填了，1.0.0 服务代码也不读这个变量，`git push` 靠的是 `/data/customers/.git/config` 里的 remote URL；手册第八节已补说明。I-0137 之后的 `backend/` 会读它取工单评论和 `进度 v1｜` 行。
4. **Cloudflare `.dev` 的 Bot Fight Mode 实际是关的。** 手册旧写「开」，可能是后来被关掉或改 zone 时丢了；要不要开回来由运营者判，本票只把手册改成实际值。
