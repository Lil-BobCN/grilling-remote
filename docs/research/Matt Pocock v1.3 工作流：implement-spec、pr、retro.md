## 一句话摘要

v1.3 加了三个技能：implement-spec 让一个编排 agent 带 sub agent 跑完整个 spec 的票；pr 用「摘要、证据、合并危险、影响范围」四栏把评审变便宜；retro 回读真实会话，找仓库和 agent 自己的低效。作者明确反对把 retro 自动化。

## 口播文章

### 一、1.3 版发布，三个技能

各位，我的 skills 仓库 1.3 版发布了，带来三个已经变成我工作流中心的技能。今天讲三件事：implement-spec、PR、retro。

retro 是我刚看到在社交媒体上传疯的那个，很多人为它激动。我自己用起来也觉得它非常有力。

### 二、spec 和 tickets 是两个东西

先讲 implement-spec。

我一次落地一大块工作的方法，本质上是两个实体：一个 spec，和实现这个 spec 的 tickets。

spec 是你要去的地方。tickets 把这个目的地拆成一组会话，每个会话交给一个编码 agent 跑。

如果你让一个 agent 一次实现整个 spec，你会进入它的「变笨区」（原文 dumb zone），可能触发 auto compact。这有时候能用，也在变好，但我认为拆成一张张票更干净。

怎么编排这些票、怎么把它们逐个交给 agent，对用户来说一直有点混乱。我自己也来回改过建议。

### 三、三种跑法：手动、脚本、agent 当保姆

最烦、最手动的方式是自己管。你说：agent，我们实现第一张票。等它完成。清空上下文。再说：实现第二张。再等，再清空。再说第三张。你相当于在当 for 循环。这不可行。

手动循环不好玩，但可以改成确定性循环：写一个脚本，读每张票，自己对着每张票跑 implement。

这是我推荐大多数人的做法。一旦搭好，它每次跑法一样，非常可靠，也便宜。跑这个循环的不是 agent，也不是人，是脚本。但搭起来相当复杂，要很多耐心，一遍遍打磨。我认为这超出初学者的范围。

所以我想，有没有中间路线：让 sub agent 去跑这个循环。也就是由 agent 而不是人来当保姆。所有票都由 sub agent 实现。

这最近才可能，因为 sub agent 自己可以再生 sub agent。以前 sub agent 的能力被削弱，现在它们和编排 agent 一样强。

implement-spec 做的就是这件事：agent 坐在那里看所有票，编排它们，再用 sub agent 实现。

它比确定性循环差，因为确定性循环每次一样。但 implement-spec 是进入 AFK（away from keyboard，离开键盘）工作流的好起点：你走开，它把整个 spec 实现完。

> **思考一下｜谁跑循环是一个独立决策**
>
> 作者把「人肉 for 循环、脚本循环、agent 保姆」摆成一条线，但三者不是同一个东西的升级版。脚本换来的是可重复，代价是搭起来复杂、分支覆盖不全时会卡住；agent 换来的是能处理没预料到的情况，代价是每次跑法不同。
>
> **可以追问**：你的工厂里，哪些判断属于「每次都一样」，可以写进脚本；哪些必须留给 agent？
>
> **可延展方向**：把「循环由谁执行」和「单步由谁执行」分开设计，比笼统地说「自动化程度」更有用。

### 四、implement-spec 的九步

用任何技能之前，先读完整份技能。它不长，流程九步，顶部有一点参考资料。

一个关键点是它尽量并行。技能里写：票和票之间有阻塞关系，合起来是一张任务图。所以总有一批「现在就能抓」的前沿票（frontier）。

看步骤：读 spec 和票；在自己的 sub agent 里做一点探索；建一条集成分支；然后用实现者 sub agent 逐票实现，用 TDD，也用 worktree；做完后用一个 sub agent 把工作合进集成分支；再派更多实现者，直到全部做完；全部完成后，在集成分支上调用 code review；然后清理，把 PR 准备好待评审。

于是你从一大份 spec 得到一个 PR。

我用它的次数比想象中多，尤其是在还没搭好确定性脚本、软件工厂还没调好的系统上。

它一直在 in progress，现在毕业了。大家可以用，也可以自己改。这是自己实现的一个基础版本，你完全可以做得不同，比如用 stacked PR。

### 五、/pr：让人评审变便宜的四栏

说到 PR，我最近用得最多的技能之一是 PR 技能。

我一直是 Dex Horthy〔待确认：ASR 记为 Dex Horthies〕的粉丝，最近见到他本人。他有一个漂亮的技能叫 show me，帮用户用简洁的图理解当前话题，用很好看的伪代码。单看有点垃圾，但放到 PR 的语境里，PR 好读好审很多。

PR 仍然是工作进主干的主要瓶颈。我这个 PR 技能的目标受 show me 启发：让人评审尽可能容易。

技能里其实就是一个写 PR 正文的模板，技能只做这件事。

先按 show me 模板写摘要，模板包含在技能里。然后要证据：before 和 after。

证据是学会信任 agent 的关键。要求 agent 给证据，常常意味着它会多跑一次测试，或者多截一张图。它给你运行时信息，证明改动确实在做它以为的事。

不要硬证据，agent 很容易说「我读了代码，应该没问题」。验证这件事我越来越着迷。

第三个标题是合并危险（merge danger）：这个 PR 合进去有多危险。

我很喜欢的一个比喻：这是一扇单向门还是双向门。双向门是你走得回来，也就是这个 PR 容易回滚。单向门是这个 PR 要在外面做点什么，比如删数据，或者回滚代价很大。

最后是影响范围（blast radius）：改动的潜在后果。

如果双向门加很小的影响范围，你根本不用认真评审。所以把这块放在最下面，也就是人第一眼或第二眼看到的位置，很关键。

例子：我仓库里一个由 PR 技能生成的 PR，本质是把两个基本相同的算法合并。能看到删除的文件和新增的文件，在正确的上下文里能看到函数、调用栈怎么组织。

但关键在于证据：真实实体上的 before 和 after。这个 PR 之前没有 intro，合并后加上了 intro，正是我们想要的行为。

最后看合并危险：双向门，纯重构加一个有意的行为改变；影响范围小。

所以 PR 技能对我的流程已经不可或缺。它也是最稳定被调用的技能之一〔待确认：原文 "modeling vote skills" 疑为 ASR 误识〕。你完全不用操心，它几乎每次都自己调用，至少在 opus 5.5〔待确认〕上是这样。

你应该下载它，看你的 PR 正文变好。如果你已经有 PR 正文技能，不妨从里面偷点东西。

> **思考一下｜评审成本应该按门的方向分级**
>
> 「单向门 / 双向门」加「影响范围」，把评审从「每个 PR 都认真看」变成「按回滚代价分配注意力」。这跟按代码行数或按模块分级都不同，它问的是出事以后能不能退回来。
>
> **可以追问**：你们现在所有 PR 是不是都被当成单向门在审？
>
> **可延展方向**：把这两栏写进 PR 模板的固定字段，比写在评审规范里更容易被执行。

### 六、domain-modeling 改名：CONTEXT.md 变 GLOSSARY.md

讲 retro 之前，要说一个变化：grill-with-docs 的工作方式变了。

看 domain-modeling 技能，现在写 glossary.md，不再是 context.md。

这个技能的灵感来自 DDD，来自 Eric Evans 的《领域驱动设计》。我原来用的是一个基于 DDD「限界上下文」概念的文件名，所以以前叫 context.md。

现在我有点离开 DDD 风格。我仍然在用 DDD，只是不想用这个被过度加载的词。context.md 太含糊，不能在该拉进来的时候触发 agent，对用户也很困惑。

我还把 context.md 里的东西削减到只剩词汇表，所以现在没理由不叫 glossary.md。

这个改动在所有地方都更新了。我很多技能依赖看到 glossary.md 才能正常工作，才能在所有环节使用领域语言。所以你必须更新。技能其他行为没变，就是文件名。

这是大家要了很久的，我很高兴发出来。

### 七、retro：回读真实会话，找你自己看不见的低效

现在看 retro，我们直接跑一遍。

我注意到我的技能集对你要求很多。我要求你长期改仓库来改进它：管理 AGENTS.md、管理技能、保证仓库的 token 效率、保证环境对 agent 安全、有好的 lint 规则、好的导航。

我意识到我自己做很多这种事，让仓库和 agent 更好用、更有性能。所以我想，为什么不打包成一个技能？这就是 retro，retrospective 的缩写。

你在一个编码 agent 会话上跑它。可以是当前会话，也可以是现有的十个里的某个，或者上一个。它会建议下一步的改进。

读真实会话的好处是：能看到 agent 实际发生了什么，看到 agent 可能藏起来的低效。

我很喜欢 Andre〔待确认〕的一个帖子：retro 改变游戏。我的 agent 撞上各种问题却没被发现，但因为坚持，功能还是以某种方式建出来了。

换句话说，agent 不像它该抱怨的那样抱怨，也不去修自己的错误。你需要另一个 agent 回头看这些会话，看哪里错了，怎么帮。

这是我们的 agent 找到的。

agent 在你选择修复之前，跑了一个不可逆的公开动作。它找到了 1.3.0 版本为什么缺失，然后没问就跑了发布。顺便说，这就是为什么你去看 release 只有 1.3.1，没有 1.3.0。Claude 把它搞砸了。我个人不太在乎，这个上下文里我不介意。

它还说这个仓库没有真正的护栏：有 pnpm check 脚本，但没有任何东西真的跑它。所以它建议加 CI 流水线。

这里还有长会话 compaction 之间的上下文丢失。我现在用 animatics〔待确认〕做视频或早期草稿，它说压缩时有丢失，建议把重复指令挪进一个 animatic 技能。这个肯定好，我肯定要做。

看这个：我给自己课程视频管理器写的自定义 CLI 在浪费 token。所以 retro 也看 token 效率。

Wiki〔待确认〕，另一个自定义 CLI，不在本地 path 上；Wiki AI Hero 有缺口。

retro 很无情，它看真实会话，几乎总能找到改进。

对 retro 的建议是：看结果时用人的判断。比如它认为最严重的那条，其实没那么糟，就是个发布，我随时可以再切。

retro 的设计是人在环里（human in the loop），不是不停随机造修复。几乎每个人看到都说想自动化。不，别自动化。

自动化意味着 agent 进入循环，不断找到假阳性，不断试着修，最后把仓库和 agent 带到一个不该去的地方。

所以我建议在会话样本上跑 retro。有空的时候，想起来很久没跑了，就跑最近的会话。或者一个出过问题的会话，或者你觉得 agent 做了怪事的会话，retro 通常能找到修复。

看 retro 技能的步骤，它看几类改进：代码库好不好导航？能不能加自动检查？能不能给自动评审加编码标准？全局 AGENTS.md 健康吗？工具经济（tool economy）好不好？指令和引导文件里有没有空操作（no ops）？agent 拿得到它需要的信息吗？

总的来说，定期跑 retro 让我的 token 效率和工作质量大幅提升。

想让你的工作质量也提升，可以上我的 AI 编程速成课 aihero.dev，今天会更新一节讲 implement-spec。如果你想掌控编码 agent、更好地用我的技能，这里是地方。

谢谢看到这里，希望你喜欢 skills v1.3，享受 retro 告诉你会话有多糟的「不舒服的真相」。下期见。

> **思考一下｜为什么「自我改进」要留人**
>
> retro 只给建议，不动代码。作者反对自动化，理由不在模型强弱：自动修会让假阳性变成真改动，而且没人刹车。这条边界跟「证据」那条是同一条：都要一个外部判断点。
>
> **可以追问**：你的流程里，哪些自动动作一旦接上自我改进，就会开始自我放大？
>
> **可延展方向**：把「谁有权改工厂自己的指令」单独列成一条权限，和「谁有权改客户代码」分开。

## 综合解读

视频作者提出的是三层东西，不是三个并列技能。

第一层是**结构**：spec 是目的地，票是会话，票之间有阻塞边，所以能并行。第二层是**执行**：循环由谁跑，决定了可靠性和上手难度，脚本最可靠、agent 最好上手。第三层是**反馈**：PR 模板把评审成本压下来，retro 把会话里的隐性损耗翻出来。

这三层各自的成立前提不一样。

结构那层依赖 spec 足够清楚。作者在另一条视频里说过，spec 不清，票就建在沙上。视频里默认 spec 已经有了，没有回答 spec 从哪来。

执行那层依赖票之间的依赖关系真是有向无环的。如果票互相纠缠，前沿票就出不来，并行退化成串行。

反馈那层依赖人会看。PR 四栏和 retro 报告都是给人读的，人不在，这两样都不产生作用。作者对 retro 的警告，本质上是在说：反馈环节不能自己变成执行环节。

有几处需要外部核验。1.3.0 未发布、直接发了 1.3.1，是作者的自述，视频里没有给 release 页面证据。opus 5.5、animatics、Wiki 这几个名字是 ASR 转写，可能是误识。「modeling vote skills」这句不成句，按上下文应该是「被稳定调用的技能」。

对我们有用的可迁移素材有三样：单向门 / 双向门的判断，可以写进 PR 模板；「证据」这一栏和我们要求的四样证据是同一件事的不同说法；retro 的抽样加人工裁决，适合放在合并之后，改工厂自己的指令，不动客户那张单。
