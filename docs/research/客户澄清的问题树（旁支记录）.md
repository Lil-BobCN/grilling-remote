## 为什么单独存

#22 问的是技术题谁答、怎么答。聊到运营者要改推荐答案时，话题转到了题与题的依赖。这个话题不属于 #22。先存在这里，#30 的 Agent 才读得到。

## 两种树

| 树 | 管什么 | 现状 |
| --- | --- | --- |
| issue 树 | 票和票的先后 | wayfinder 已记。原生依赖，本地 Markdown 版写 `Blocked by:` |
| 问题树 | 题和题的依赖 | 没有地方记。A、B、C 三档都缺 |

例子：「要不要备案」依赖「托管在国内还是海外」。托管改了，备案那题要重判。

C 档每张 grilling 票内部也有问题树，所以三档都要管。

## 运营者口述

1. 技术题和别的题互相牵连。改一个关键技术题，可能让整张图推倒重来。
2. 接手时先看整棵问题树，分三堆：没定的；客户不懂、走了推荐答案的；已定但要运营者核实的技术题。
3. 每改一条，重新计算问题树，直到树不再变。
4. 现成技能没有这个功能时，新增一个。

## 来自 #22 的前提

运营者已点头。#22 的结论评论还没写。

- 客户明说不懂的题，Agent 按推荐答案往下问，记进 `.scratch/{简称}/pending.md`。A、B、C 三档共用这一个文件。
- 每条记六项：题目原文、选项、推荐答案、推荐理由、客户当时的相关原话、标签。
- 标签有三种：`客户不懂`、`依赖第 N 条`、`客户已答`。
- 推荐答案查证过的写出处，没查到的写「未核验」。
- 依赖只指向编号更小的条目。
- 运营者改一条推荐答案，依赖它的条目由运营者同批重判。只有客户的业务事实变了，才回问客户，由人工客服带话（#23）。
- 技术闸门（#10）按五类扫规格，不只看 `pending.md`。
