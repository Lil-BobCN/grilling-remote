# 运营工作台选型：Orca 还是开源看板

> 调研时间 2026-11-02。本机 Orca 1.4.244（`com.stablyai.orca`），macOS。
> 全程只读：没有新建 worktree、没有发消息、没有改卡片状态、没有安装任何服务。
> 文里分三种证据强度：**实测**（我在这台机器上跑过）、**代码**（应用包里的语言包、路由清单、CLI 帮助）、**文档**（官方文档或仓库）。

## 结论

用 Orca 当运营工作台，先不装第二个系统。

四个必需动作里，三个是原生的：验收、给客户回话、看 run（一次执行）的过程。第四个「技术闸门」没有现成面板，但能用 Orca 已有的零件拼出来，不写代码就能跑：

| 要办的事 | 落在哪里 | 怎么用 |
| --- | --- | --- |
| 全量工单 | Orca「任务」页 | 直接读 GitHub Issues，按项目（仓库）切换，按负责人和关键词筛 |
| 正在跑的单 | 工作区看板 | 一张卡 = 一个 worktree（独立检出），跨客户同一个看板 |
| 等你拍板 | 看板自定义列「等你定」 | 卡片加未读点，扫一眼就知道有几条堵着 |
| 拍板本身 | 卡片对应的 agent 聊天 | 让 agent 用带选项的提问，手机上点一下，选择直接进它的上下文 |
| 验收 | GitHub 议题 / PR 对话框 | diff、CI 检查日志、评审评论、合并 PR 都在一个窗口 |
| 回客户一句话 | 同一个对话框的评论框 | 写回 GitHub issue，和客户网页读的是同一条线程 |
| 看 agent 干了什么 | 卡片会话、终端、diff | 逐轮对话 + 工具调用 + 完整终端输出，还能全文检索 |

代价说清楚，三条：

1. **闸门要逐卡点开。** 没有一屏列出 5 条单的 3 个选项。卡片上只有一行状态文字，选项在聊天里。
2. **一单一个 checkout。** 卡片单位是 worktree，不是工单。还没开工的单没有卡，只在「任务」页里。
3. **手机端没有独立看板页。** 手机路由里有任务、审阅、diff、终端会话，没有看板。看板要靠桌面或浏览器。

第二选择是 Vikunja：单个容器、自带手机 App、API 齐全。但它补不上「看 run」这一块，等于还是要自建一半。

Plane 太重（自托管 13 个容器，单容器 AIO 官方写明「Not for production」）。Huly 更重（14 个服务、8GB 内存起）。Focalboard 仓库已停维护。OpenProject 官方最低 4 核 4GB，对一个人管单是杀鸡用牛刀。

| --- | --- | --- | --- | --- | --- | --- |
| **Orca** | ⚠️ 有列和未读点，没有汇总面板；点选在聊天里 | ✅ diff + CI 日志 + 评论 + 合并，一个窗口 | ✅ 议题评论框，写回 GitHub | ✅ 会话逐轮 + 终端 + diff + 全文检索 | ⚠️ 有官方 App，局域网 / Tailscale 免账号；看板页和实际手感待验收 | ✅ 一个桌面 App，无额外服务 |

### Orca 的七件事，逐条落到界面

| 运营者要做的动作 | 界面位置 | 证据 |
| --- | --- | --- |
| 看有哪些单在等我决定 | 看板「等你定」列 + 卡片未读点 | 实测：卡片带状态和未读标记；代码：看板设置能加状态、改名、左右移；文档：`--unread`「puts the workspace's unread dot in the sidebar to ask for a person's attention」 |
| 在三个选项里点一个 | agent 聊天里的选项提问（步骤、选项、其他、提交） | 代码：语言包 `native-chat/question/{step,next,skip,otherPlaceholder,send}`、`ask/questionCount` |
| 看验证截图 | GitHub 议题「对话」里的评论 | 代码：`GitHubItemDialog` 有「文件 / 检查项 / 对话 / 评论 / 添加评论 / 发送评论」 |
| 看 diff 摘要 | 议题或 PR 的「文件」页；卡片的 source control | 代码：`filesUnavailable`「无法加载更改的文件」、`未查看/已查看`、并排 / 内联 |
| 看测试结果 | 「检查项」页，失败作业的日志摘录、重跑、让 AI 修 | 代码：`githubChecks`「每项检查最多加载五个失败作业的日志摘录」 |
| 批准或驳回 | 合并 PR / 关闭 PR / 请求评审 / 提交评审评论 | 代码：`合并PR失败`、`拉取请求已合并`、`已添加评审评论` |
| 给客户回一句 | 议题「评论」框 | 代码：`GitHubItemDialog` 的 `添加评论...`、`发送评论`；运行时存在 `github.addIssueComment` |

## Orca 实测到什么程度

### 我实际跑过的（只读）

| 命令 | 结果 |
| --- | --- |
| `orca status --json` | 运行中，runtime ready，版本 1.4.244，能力清单里有 `mobile.tasks.v1`、`pairing.delegated-mobile-devices.v1`、`notifications.remote-push.v1` |
| `orca worktree list --json` | 25 张卡：23 张 in-progress、2 张 in-review；6 张带状态行，8 张关联了 GitHub issue |
| `orca worktree show --worktree name:"Issue 2 …"` | 卡片里存了 `linkedItems`，含 issue 编号、标题、`https://github.com/Lil-BobCN/matt-graph/issues/2`，还有 PR 号 |
| `orca reference find <issue URL>` | 能按 issue 反查工作区；但 scope 写明 `stored-metadata`，只查本地缓存，不去 GitHub 拉 |
| `orca terminal list --json` | 19 个终端在跑，能看出是哪个 agent（codex / dsh） |
| `orca search --index-status --json` | 会话全文索引已开（`enabled: true`） |
| `orca automations list --json` | 0 条；`create` 支持 cron / daily / weekly + `--precheck` 命令 |
| `orca linear team list --json` | 0 个团队，这台机器没连 Linear |
| `orca tab list --json` | 0 个内嵌浏览器标签 |
| `orca artifacts list --json` | 0 条；artifacts 是「发布 HTML/Markdown 成公开链接」，不是证据库 |
| `orca computer get-app-state --app Orca` | 拿到窗口截图，见下 |

界面截图（只读快照）里能直接看到：左侧栏有「搜索 / 任务 / 工件 / 技能 / 自动化 / 智能体仪表盘 / Orca 手机端」；下面是项目区，卡片按「工作中 / 完成」分组，每张卡显示一行状态文字和仓库名。这一条是实打实看见的，不是从文档推的。

### 代码和语言包里确认、但没点开

- **任务页读 GitHub**：语言包里有「浏览 GitHub 议题并从中启动工作区」「搜索 GitHub 议题…」「从议题开始工作区」；设置页列了 GitHub / GitLab / Linear / Jira 四个来源。
- **GitHub 写入**：运行时方法名 `github.listWorkItems`、`github.addIssueComment`、`github.updateIssue`、`github.createIssue`，还有 `github.mergePR`、`github.rerunPRChecks`。
- **看板列可自定义**：看板设置里有「添加状态 / 重命名 / 删除 / 向左移 / 向右移」；CLI 帮助写「custom statuses use their configured id」。
- **手机端**：配对二维码；局域网或 Tailscale 即可，文档原文「手机必须连接此 Wi‑Fi 或通过 Tailscale。无需账号」；Relay 走蜂窝网才要登录。
- **手机网页的路由**（`orcad-template/out/mobile-web/manifest.json`）：共 10 条，其中 `/tasks`、`/review/[worktreeId]`、`/files/[worktreeId]`、`/source-control/[worktreeId]`、`/session/[worktreeId]`、`/agent-history/[worktreeId]`、`/new-workspace` 是干活用的。**没有 `/board`。**

### 卡在哪，四条

**一、技术闸门没有汇总面板。**
卡片只有一行 `comment`（文档原话：「A worktree comment is the short status line on the workspace card.」），没有自定义字段，放不下「选项 A / B / C + 推荐 B」。

Orca 其实有「决策门」这个概念，但它是给 agent 用的：`orca orchestration gate-create --task <id> --question <text> --options <json_array>`，解决用 `gate-resolve --id <gate_id> --resolution <text>`。两个前提把运营者挡在外面：必须先绑一个 orchestration Run（我直接跑 `gate-list` 报 `run_required`），而且只有 CLI，没有界面。语言包里搜「决策门」只出现在设置页的说明文字里。

**二、证据不是对象。**
「这条单做完的证据」在 Orca 里没有对应物。artifact 是另一个东西：文档写「Only a human can turn publishing on or off」，要登录 Orca 账号并在设置里打开；headless 服务器上直接 `sharing_unavailable_on_host`。所以验收证据实际落在 GitHub 议题评论里，Orca 只负责看。

**三、看板单位是 worktree。**
一张卡对应一个独立检出。空单没有卡。25 张卡对一个人来说已经不少，上百条工单会让磁盘和克隆时间吃不消。

**四、手机端没有看板页。**
手机 web 的路由里没有 board。手机能看任务列表、审阅、diff、终端会话，看板要靠桌面。App 里的实际表现我没法只读验证。

## 开源候选逐一评估

四个候选都只看文档和仓库，一台服务都没装。所以下面全是文档证据，没有实测。

### Vikunja（第二选择）

一个 Go 二进制，前端打包在同一个容器里，SQLite 内置。官方安装文档原话：「Both are bundled into one single deployable binary (or docker container). That means you only need to install one thing」。在还在维护的候选里，这是唯一能做到「一条 docker run 就完事」的。

| 维度 | 情况 |
| --- | --- |
| API | v1 有 128 个路径（我下载了 OpenAPI 核对过）；v2 是标准 REST + OpenAPI 3.1，v1 以后弃用 |
| 自定义状态 | 有。每个视图用 bucket 当看板列，可以自己加 |
| 自定义字段 | 没有。OpenAPI 的 128 个路径里找不到字段定义端点，只有 labels / buckets / comments / attachments |
| 评论 | 有。`/tasks/{taskID}/comments`，可以增删改查 |
| 附件 | 有。`/tasks/{id}/attachments` |
| 手机 | 有官方 App，但安装文档自己写「it only supports the very basic features of Vikunja」；网页在手机上的可用性我没实测 |
| 部署 | 1 个容器（要 PostgreSQL 就 2 个） |

四个动作能到什么程度：闸门用「列 + 评论」硬凑，点选要自己写胶水；验收只能挂附件和评论，没有 diff、没有 CI；回客户要另做桥接，因为客户看不到 Vikunja；看 run 完全没有。

- 仓库 <https://github.com/go-vikunja/vikunja>
- 安装 <https://vikunja.io/docs/installing/>
- API <https://vikunja.io/docs/api-documentation/>、<https://vikunja.io/docs/api-v2/>

### Plane

功能最全，也最重。仓库自带的 `docker-compose.yml` 有 13 个服务：web、admin、space、api、worker、beat-worker、migrator、live、plane-db、plane-redis、plane-mq、plane-minio、proxy。

官方有单容器 AIO 镜像，但文档标题下面直接写「Not for production」，并说明「AIO runs every Plane service in one container, so you can't scale, restart, or upgrade services independently」。所以真要上线还是 13 个容器。

API v2 很完整：工作项的评论（增删改查）、自定义属性、状态、附件、活动流、Webhook 都有。自定义状态和自定义属性这块，它比 Vikunja 强。

移动端是硬伤：`makeplane/plane-mobile` 仓库已归档，最后一次提交 2024-01。手机只能用浏览器。

社区版的能力边界，官方只说「at par with the Free tier of the Cloud edition」，自定义属性是否在社区版开放，文档没写清，我没核实。

四个动作：闸门和验收都要写胶水，回客户要桥接，看 run 没有。

- 仓库 <https://github.com/makeplane/plane>
- API <https://developers.plane.so/api-reference/introduction>
- 自托管 <https://developers.plane.so/self-hosting/overview>
- 移动端仓库（已归档）<https://github.com/makeplane/plane-mobile>

### Huly

太重的代表。自托管 compose 14 个服务（nginx、cockroach、redpanda、minio、elastic、rekoni、transactor、collaborator、account、workspace、front、fulltext、stats、kvs），README 写「Minimum: 2 vCPUs and 8 GB RAM」，还提醒升级前必须读 `MIGRATION.md`，跨大版本要按步骤迁移。

为一个人管单维护这套东西，不划算。排除。

- 仓库 <https://github.com/hcengineering/huly-selfhost>

### Focalboard

README 第一行就是警告：「This repository is currently not maintained.」停维护的项目不进选型。排除。

- 仓库 <https://github.com/mattermost-community/focalboard>

### OpenProject（点名排除）

官方系统要求：4 核 CPU、4096 MB 内存、20 GB 磁盘，按「单台服务器 200 用户」设计。我们是 1 个运营者，用不上。

- <https://www.openproject.org/docs/installation-and-operations/system-requirements/>

## 为什么不选自建（或为什么选）

先说结论：**现在不建**。理由三条。

**一、Orca 已经把我们最贵的那块做完了。**
「看 agent 干了什么」是最难自建的部分：会话逐轮记录、工具调用、终端输出、diff、全库检索。自己写要接 agent 的输出流、存日志、做分页读取、处理转义和重绘，还要适配不同 agent。Orca 现在有 19 个终端在跑，会话索引已开，这些已经在工作。

**二、剩下那 0.5 件，用约定就能补，没必要写代码。**
闸门的真实需求是「别漏、能点、点了算数」。用自定义列 + 未读点保证不漏，用聊天里的选项提问保证能点、点了进 agent 上下文。代价是要逐卡打开，这个代价能不能接受，跑两周就知道。

**三、自建的工作台会变成第二份维护。**
UI、权限、移动端适配、GitHub 读写、通知，随便哪一项都比「看板列 + 聊天选项」贵。而且我们没人专职维护它。

什么时候该自建？给一条线：**如果「逐卡点开」每天超过 15 分钟，或者同时堵着 5 条以上待定，就做一页只读的闸门面板**，不要做整套工作台。这一页只干三件事：读 `orca worktree list --json` 拿卡片和状态行，读 GitHub issue 评论拿选项，点选后写一条 issue 评论再把结论发回 agent。一天能做完，坏了也不影响主流程。

## 要给运营者看的原型清单

结论就是 Orca，按运营者自己定的顺序（优先 Orca），**不进入「开源项目原型评审」这一环**。所以下面不是原型，是**半天的现场验收**：用真单跑一遍，验三条。

### 验收三条（半天，用真客户单）

| # | 验什么 | 怎么做 | 通过标准 | 不通过怎么办 |
| --- | --- | --- | --- | --- |
| 1 | 手机上点选项能不能生效 | 手机装 Orca Mobile，扫码配对（同一 Wi-Fi 或 Tailscale，不用账号）。让 worker 在聊天里问一个带 3 个选项的技术问题 | 手机上能看到 3 个选项，点一个，agent 接着往下干，桌面端记录一致 | 退回「手机上回一句话」的降级方案，闸门只在桌面点 |
| 2 | 「等你定」这一列够不够扫 | 手动加一个看板状态 `等你定`，放 5 张卡进去，每张的状态行写成 `等你定：选 A/B/C（推荐 B）` | 不点开卡片，5 秒内能说出「有几条、分别要选什么」 | 每天开一次桌面扫，或做上面那页只读面板 |
| 3 | 回客户的话客户看得见 | 在议题对话框写一句评论，去客户网页刷新 | 客户网页上出现同一句话，作者是你的 GitHub 账号 | 说明客户网页没读 issue 线程，这个前提要先修 |

验收前要先确认两件事，缺一件就白跑：

- Orca 设置 → 任务管理里，GitHub 那栏是「已就绪」（本机 `gh` 已登录 `Lil-BobCN`，权限含 `repo`）。
- 客户网页读的就是这条 GitHub issue 的评论。

### 如果运营者否掉 Orca：Vikunja 原型（1 天）

只验三条，别多做：

1. **纯 API 能不能建单、改列、发评论**，不碰界面。跑通说明胶水可行。
2. **手机 App 能不能改列、能不能看附件**。基础功能够不够用，一天就能试出来。
3. **附件 + 评论能不能当证据位**：把一张验证截图和一段 diff 摘要挂上去，看运营者认不认。

三条都过，再谈把「看 run」用外链补；有一条不过，回 Orca，别在第二个系统上继续加东西。
