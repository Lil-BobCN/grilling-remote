| 票面问题 | 结论 | 证据 |
| --- | --- | --- |
| 验证队能不能在容器里并行跑？ | 能。一个 Sandcastle 容器里，父会话能同时起多个子 agent；子 agent 共享同一个 worktree 和容器，只读验证够用。 | `rehearsal/swarm` 的日志有两行 `Agent(Worker A role row + tests)`、`Agent(Worker B owner row + tests)`；两条都在后台启动，各自读到 `roles.md` 第 21、24 行并跑通 `npm test`；trail 提交 `778e7a6`。 |

## 环境与方法

- 宿主：Darwin 25.5.0 arm64，Node v26.0.0，Docker 29.2.1（colima）。
- 演练仓是一个最小 Node 项目：`src/app.js` 有 `add`；`npm test` 检查 `add`，有 `subtract` 或 `multiply` 时一并检查；`npm run verify:strict` 额外强制检查 `subtract`。
- 容器凭证写进 `.sandcastle/.env`，不进 git。`ANTHROPIC_BASE_URL` 用 `http://host.docker.internal:15721`。
- 每个 `run()` 都用 `branchStrategy: { type: "branch", branch: ... }`，保证一票一个 worktree。
- pstack 技能复制到仓库的 `.claude/skills/`，`roles.md` 和 playbook 放在 `factory-skills/pstack/`。worktree 只带已提交文件，所以两者都先提交。
- 演练驱动 `.sandcastle/rehearsal.mts`，三种模式：`owners`、`swarm`、`conflict`。

## 演练一：容器里并行起子 agent

命令：

```bash
npx tsx .sandcastle/rehearsal.mts swarm
```

做法：一个容器、一个 worktree，brief 第一行点名 `/swarm`，要求两个 worker 同时启动。两个 worker 都只读，分别读 `factory-skills/pstack/roles.md` 的 `swarm workers` 行和 `owner` 行，跑 `npm test`，回报 `PASS` 或 `ISSUES`。父会话等两个结果，写 `.audit/229.tsv` 并提交。

日志关键行（`.sandcastle/logs/rehearsal-swarm-parallel-swarm.log`）：

```text
Agent(Worker A role row + tests)
Agent(Worker B owner row + tests)
Both workers are running in the background (same container, shared worktree, read-only).
```

结果：

- 两个 worker 都返回 `PASS`。
- `swarm workers` 行读到 `claude-code（Sandcastle 容器）`、`flash`；`owner` 行同样读到 agent 和模型。
- trail 四行：`frame`、`worker A`、`worker B`、`aggregate`，提交 `778e7a6`。
- 没有改用独立 worktree 或独立容器：Claude Code 的 Task 子 agent 在当前容器和工作树里跑。对只读验证够用；如果要每个 worker 独立 worktree 和容器，得由调度器为每个 worker 调一次 `run()`，不能靠 Task 子 agent。

## 演练二：独立 worktree 改动回收

命令：

```bash
npx tsx .sandcastle/rehearsal.mts owners
```

做法：两个 `run()` 用 `Promise.all` 同时启动，各自 `branchStrategy` 指向 `rehearsal/owner-a` 和 `rehearsal/owner-b`。两个 agent 都改 `src/app.js` 的同一行：A 加 `subtract`，B 加 `multiply`，各自跑 `npm test` 并提交。

结果：

| 实现者 | 分支 | 提交 | 测试 |
| --- | --- | --- | --- |
| owner A | `rehearsal/owner-a` | `f1e6871` | `ok add`、`ok subtract`、`verify ok` |
| owner B | `rehearsal/owner-b` | `a677f7e` | `ok add`、`ok multiply`、`verify ok` |

- 两次 `run()` 都打印 `Setting up sandbox`，各自建 worktree；主工作树的 `main` 停在 `45c9c56`，没有被改动。
- 两个 `run()` 返回的 `commits` 各有一条，分支保留，worktree 在跑完后清理。
- 这次两条分支改的是同一行，为后面的冲突演练准备。

## 演练三：并行票的合并冲突

前置：`rehearsal/integration` 从 `main` 建，先合 owner A：

```text
b6facb3 rehearsal: merge owner-a into integration
```

命令：

```bash
npx tsx .sandcastle/rehearsal.mts conflict
```

做法：在 `rehearsal/integration` 的 worktree 里合 `rehearsal/owner-b`，冲突落在 `src/app.js` 的 `// operations` 行。merger 子 agent 保留 `subtract`、`multiply` 和原有的 `add`，提交合并；verifier 子 agent 在合并后的 head 重跑 `npm test`；owner 再自己跑一遍。

日志关键行（`.sandcastle/logs/rehearsal-integration-conflict.log`）：

```text
Merge conflict is staged as expected. Now spawning the merger sub-agent.
Agent(Resolve merge conflict as merger)
Merge commit verified: 1c98ec8, clean tree, both functions present. Spawning the verifier sub-agent.
Agent(Verify merged head with npm test)
```

结果：

- 合并提交 `1c98ec8`，父提交是 `b6facb3` 和 `a677f7e`；`src/app.js` 保留三个函数，没有冲突标记。
- verifier 在 `1c98ec8` 上 `npm test` 通过：`ok add`、`ok subtract`、`ok multiply`、`verify ok`。
- owner 的第二遍 `npm test` 也通过。
- trail `c8c8e2a` 有 `merge`、`conflict`、`verify`、`verify` 四行；`verify` 行 evidence 写死合并 SHA 和测试输出。

一个可复现的坑：第一次跑时宿主主工作树正停在 `rehearsal/integration`，Sandcastle 报：

```text
WorktreeError: Branch 'rehearsal/integration' is already checked out in worktree at '/Users/Admin/sc-rehearsal-229'
```

切回 `main` 再跑就正常。调度器给一张票建 worktree 前，要先确认目标分支没有被主工作树占着；这条要写进调度器实现。

另一个观察：这次 `run()` 返回三条提交：`a677f7e`（owner B 早先的提交，合进来的）、`1c98ec8`（合并提交）、`c8c8e2a`（trail）。调度器不能把 `commits` 的数量当成「这张票新做了几次提交」，要看分支相对基线的差异。

## 演练四：自动合并失败回滚

场景：自动合并把 `rehearsal/integration` 合进 `main`，单票测试通过，但合并后跑全量基线检查失败；按 E1 先回滚，再另开分支修。

步骤与结果：

| 步骤 | 命令 | 结果 |
| --- | --- | --- |
| 先合一次正常的 integration | `git merge --no-ff rehearsal/integration` | `2eef9f8`；`verify:strict` 通过 |
| 造一个坏实现者分支 | 从 `main` 建 `rehearsal/bad`，删掉 `subtract`，`npm test` 仍通过 | `8de6ecf` |
| 把坏分支合进 integration | `git merge --no-ff rehearsal/bad` | `93ad029`；单票 `npm test` 仍通过 |
| 模拟自动合并到主干 | `git merge --no-ff rehearsal/integration` | `4fc7c38`；`npm run verify:strict` 报 `not ok subtract: subtract failed` |
| 回滚合并提交 | `git revert -m 1 4fc7c38 --no-edit` | `2b508b2`；`verify:strict` 恢复 `ok add`、`ok subtract`、`strict verify ok` |
| 记录 | 追加 `.audit/229.tsv` 并提交 | `0380cca` |

结论：

- 回滚用 `git revert -m 1 <merge-sha>`，不在主线上 force-push；合并提交必须是真 merge commit，squash 合并要改成 revert 那条 squash 提交。
- 这次触发回滚的是合并后的全量检查，不是单票测试。单票测试只覆盖本票改动，挡不住「合进来把基线弄坏」；自动合并脚本要在合并后跑全量检查，失败就回滚，或者把这一步留给运营者抽样。现在 E1 只写了「抽样发现问题先回滚」，没有写自动合并脚本自己跑全量检查；这条留给调度器和自动合并的实现票定。
- 回滚后的修法是从 `2b508b2` 另开分支改，不重开原票；这次只记录了修法，没有真的再开分支合一次。

## 发现与限制

1. **并行子 agent 的边界**：一个容器里能并行起多个 Task 子 agent，但它们共享同一个 worktree，不是 pstack 原文写的「各自一个 worktree、一个容器」。验证队只读，共享没问题；实现者要独立工作树，必须由调度器对每个实现者各调一次 `run()`。
2. **merger 和 verifier 都能作为子 agent 跑**：merger 在当前 worktree 解冲突，verifier 在合并后的 head 重跑测试，路径都通。
3. **「解完冲突重跑验证」现在靠 trail 记录和人工检查**：trail 行能证明重跑过，但没有调度器读它并拦住没重跑的分支。调度器实现要补这条检查。
4. **`run()` 返回的 `commits` 不等于本票新增提交**：合并会把别的分支的提交带进结果；调度器要按分支差异判断。
5. **worktree 分支冲突**：目标分支已经被主工作树占着时 `run()` 直接报 `WorktreeError`；调度器要先切走或换分支。
6. **没有验到的部分**：GitHub PR、CI、`gh pr checks --watch`、`mergeStateStatus`、真实客户仓、调度器的锁和自动合并脚本都没跑；这些归 to-spec 的实现票。
7. **本票没有改规则**：D2 的合并者子 agent、D5 的「解冲突后重跑验证」都按现行写；演练只回答「能不能执行」。
8. **票面原写「先别领取」**：调度器和自动合并还没出票。本次由运营者建 worktree 领取后按手工演练做；调度器、自动合并脚本和 PR/CI 层仍未实现，第 6 条列了没验部分。
