# 调度器底座与运行验证

> 验证对象：`@copperbox/sandcastle-workflow@0.4.2`，依赖 `@ai-hero/sandcastle@0.12.0`。
> 对应票：[#226 调度器底座与运行](https://github.com/Lil-BobCN/grilling-remote/issues/226)（中台 I-0041）。
> 验证方式：私有测试仓 [`Lil-BobCN/sandcastle-workflow-test`](https://github.com/Lil-BobCN/sandcastle-workflow-test)，noSandbox 本机跑，真实 GitHub issue、分支和 PR，记录原始输出。仓库路径 `/Users/Admin/scwf-test`，无空格。
> 2026-11-15 按 I-0103：`customers.json` 的 `repo` 改成 `repos` 映射（键是软件简称），仓名按 D-0192。本文下面的 `repo` 指针和 `acme-2` 写法是当时的研究记录，以 `docs/客户白名单维护.md` 第八节为准。

## 结论

包能装、能跑，和 Sandcastle 0.12.0 协同正常。一次真跑开出了 ready PR，版本从 0.1.0 自动升到 0.2.0。

崩溃后重启能接上。状态全在 git 和 GitHub，重启会重新推导；残留的 `sandcastle:in-progress` 标签会清掉，残留的 worktree 会删掉再建。

包本身没有锁或租约。两个实例同时跑同一个仓，都会规划同一张票，后启动的实例会删掉先启动实例的 worktree。防重复点火必须由调度器做：每仓一把内核级文件锁，同一时刻只跑一个 `npm run sandcastle`。

客户仓发现只读 `customers.json`。不按前缀扫账号下的仓，也不靠 topics。表里没有的仓不点火。

## 一、安装

在临时目录先装了一遍，再在测试仓装了一遍。两次结果一致。

```text
npm install --include=dev @copperbox/sandcastle-workflow@0.4.2 tsx
added 12 packages in 4s
```

```text
sandcastle-workflow-test@0.1.0
├─┬ @copperbox/sandcastle-workflow@0.4.2
│ └── @ai-hero/sandcastle@0.12.0
└── tsx@4.23.15
```

- 包的 `engines` 要求 Node ≥ 20，本机 Node 26.0.0 通过。
- 包自己声明 `@ai-hero/sandcastle: ^0.12.0`。0.12.x 只有 0.12.0 一个版本，所以这次解析到 0.12.0。Sandcastle 最新是 0.14.0，不在范围内，不会被带上。
- 仍然要在客户仓里把 `@ai-hero/sandcastle` 写成精确版本并提交 lockfile。只靠 `^0.12.0`，以后发了 0.12.1 会漂。
- `npx sandcastle-workflow init` 不需要交互。它在 `.sandcastle/` 下写八个文件，再写 `scripts/sandcastle-loop.sh`。它还往 `package.json` 加 `sandcastle`、`sandcastle:loop` 两个脚本。
- 注意：这个 bin 不认 `--help`、`init` 这些参数，跑起来就是 init。重复跑会拒绝覆盖已存在的 `.sandcastle/`。

## 二、一次真跑

测试仓的配置：

- `sandbox: () => noSandbox()`，agent 跑在宿主机 worktree 里。Docker 整链归 I-0031，本次不碰。
- `maxIterations: 1`，一次跑一轮。
- `verifyCommand` 是 `npm run typecheck && npm run test`，两个脚本只打印 ok。
- 其余字段用包默认值：自动升版本、草稿 PR、`implementerMaxIterations: 100`。
- 模型走本机中转。第一次用 `claude-opus-5-5`，合并阶段中转余额不够；之后换成 `ccs-claude-deepseek--deepseek-v4-flash[1m]` 跑完。

### 结果

- PR：[#2](https://github.com/Lil-BobCN/sandcastle-workflow-test/pull/2)，状态 ready，head 分支 `sandcastle/feature-hello-file`。
- 版本：根 `package.json` 从 0.1.0 升到 0.2.0，提交 `0898d7b`。
- issue #1 保持 open，标签是 `Sandcastle` + `sandcastle:in-review`。
- PR 正文里有一行机器可读标记，记录 feature 的固定成员：

```text
<!-- sandcastle-feature: {"slug":"hello-file","branch":"sandcastle/feature-hello-file","members":[{"id":"1","title":"Add hello.txt with the word hello"}]} -->
```

### 实测到的默认行为

| 行为 | 结果 |
| --- | --- |
| 队列标签 | 默认 `Sandcastle`；只看 open 且带这个标签、没有 in-review 的 issue |
| 分支命名 | `sandcastle/feature-<slug>`、`sandcastle/issue-<id>`，issue 分支名只由 issue 号决定 |
| implementer 上限 | 日志是 `Iteration 1/100`，默认 100 次 |
| 草稿 PR | 单票 feature 在同一轮里建草稿再翻 ready，草稿状态很短；多票 feature 会停在草稿直到成员做完 |
| 自动升版本 | 默认开。release agent 改根 `package.json`，提交前缀 `chore(release):`，本次判为 minor |
| PR 正文 | 有成员 checkbox、版本、生成说明；成员标记写在 HTML 注释里 |
| 合并 | 包从不合目标分支，只开 PR 等人合 |

### 和工厂流程对不上的地方

只记录，不在本票改。

- **提交前缀**：包默认的 implementer 提示词要求 `RALPH:` 前缀，不是工厂流程写的 `FACTORY:`。要改得覆盖 `implement-prompt.md`。
- **planner 自己分组**：它不读 GitHub sub-issue，也不认 parent issue。它按标题、正文和文件重叠猜 feature。工厂流程要求按 parent issue 固定成员，这一层要改写。
- **slug 不稳定**：文档要求同一组 issue 重规划时 slug 不变。实测第一次是 `add-hello-txt`，中断后重规划变成 `hello-file`，旧的 feature 分支被丢下，issue 分支重新合了一次。issue 分支名是稳定的，feature 分支名不是。
- **空提交**：文档说「重新实现已完成的 issue 是 no-op」。实测会多一个空提交 `fcefb69`，内容只写「文件已存在」。git 状态没坏，但会多一次 agent 调用和一个提交。
- **不合并到主干**：工厂流程 E1 要求验证和评审通过后自己合主干。这个包只开 PR。这两条规则要不要改，是另一张票的事。
- **单仓单进程**：包只在一个 checkout 里跑，不认识多客户仓。客户仓发现和进程管理都在工厂层。

## 三、崩溃重启

### 操作

1. 新建 issue #3「Add bye.txt with the word bye」，打 `Sandcastle` 标签。
2. 启动 `npm run sandcastle`。等日志出现 `[implementer:3] Started`，2 秒后杀掉工作流进程和它的 agent 子进程。时间是 06:30:44。
3. 记录现场，再启动一次。

### 杀掉后的现场

- 进程退出码 137。
- issue #3 标签：`Sandcastle` + `sandcastle:in-progress`。这是残留。
- `.sandcastle/worktrees/sandcastle-issue-3` 还在，指向 `sandcastle/issue-3`，分支停在 main 的 `3af73e7`，没有提交。
- 没有 PR。

### 重启后

日志第一行就是：

```text
Issue #3 carries a stale in-progress label; clearing.
```

然后 planner 规划出 `bye-file`，implementer 重新建 worktree、重新实现，提交 `33a1b1c`。reviewer、merger 正常走完，合并提交也落在本地。

第一次推分支时 GitHub 的 git HTTPS 连不上，报 `Empty reply from server`；同一段时间 fetch 也报过 `HTTP2 framing layer`。包把这次 feature 记为失败，进程退出码 0，issue #3 留在队列，没有 in-review 标签。网络恢复后重跑，planner 还是 `bye-file`。这次没有再跑 implementer：`doneAtStart` 从 git 里看出 issue 分支已经合进 feature 分支，只跑了 release（版本已升过，跳过 bump），06:39:49 开出 PR #5，issue #3 打上 `sandcastle:in-review`。

这说明两件事。状态确实从 git 推导，不靠内存；推送失败不会丢已经合并的提交，重跑会从上次做到的地方继续。

### 结论

- **状态接得上**：判断 issue 是否完成用的是 git 集成状态和标签，不是内存。进程死了，重启重新读一遍就知道做到哪。
- **worktree 接得上**：`removeLeakedWorktree` 在建 sandbox 前删掉同分支的残留 worktree，提交在共享仓里，不会丢。
- **进程不会自己回来**：`scripts/sandcastle-loop.sh` 只在退出码 0 时立刻重跑、3 时睡 15 秒再看。退出码 137 这类真错误会让循环停下。重启要由调度器做，包不负责。
- **重规划可能换 feature 分支**：第一次真跑里已经看到 `add-hello-txt` → `hello-file` 的变化。崩溃后如果 PR 还没建，重规划可能再起一个 feature 分支，多一次合并。issue 分支和提交不丢。

## 四、防重复点火

### 源码事实

- `runFeatureFlow` 没有锁文件、没有租约、没有 run id。
- 唯一跟「正在跑」有关的是 `sandcastle:in-progress` 标签。`markInProgress` 在每轮开始时打上，`clearInProgress` 在 finally 里去掉；下一轮 Phase 0 还会把所有残留的 in-progress 标签无条件清掉。
- `removeLeakedWorktree` 在建 sandbox 前强制删掉同分支的 worktree，不检查是谁建的。
- 结果：两个实例同时跑同一个仓，会互相清标签，给同一个 issue 分支建同一个路径的 worktree，后建的删掉先建的，两个 agent 落在同一个目录里。

### 实验

06:40:12 启动实例 A，06:40:14 启动实例 B，同一个 checkout，同一张 issue #4。

两边日志都出现：

```text
Found 1 Sandcastle-labelled open issue(s).
Planning complete. 1 feature(s), 1 workable issue(s):
  foo-file [sandcastle/feature-foo-file] -> workable: 4
[implementer:4] Started on branch sandcastle/issue-4
```

implementer 日志文件里有两个 `--- Run started ---`，时间分别是 06:40:36 和 06:40:38。说明两个 sandbox 都建了，都对着 `sandcastle/issue-4`。

工作区只剩一个 `.sandcastle/worktrees/sandcastle-issue-4`，两个 claude agent 进程同时在跑，都对着同一个 worktree 路径。先建的那个 worktree 被后建的删了。

杀掉两个实例后：

- 两个进程都是退出码 137。
- issue #4 残留 `sandcastle:in-progress`。
- worktree 里只有一个未提交的 `foo.txt`，分支上没有提交。
- 没有 PR。

这证明包本身不防重复点火。重复点火不是理论风险，是两个实例真的会同时干同一张票。

### 调度器要做什么

- 每仓一把内核级文件锁（`flock`），覆盖整个 `npm run sandcastle` 调用。进程死了内核自动释放，不需要清锁逻辑。
- 点火前先拿锁，拿不到就跳过这个仓。
- `in-progress` 标签只给运营者看，不能当互斥。它会被下一轮清掉，也会被另一个实例清掉。
- 锁按仓加，不按 issue 加。包内部对同一 feature 的多个 issue 是并发跑的，按 issue 加锁会误伤。
- 跨机器同时调度需要更强的租约。GitHub 标签做不了原子租约，现在只有一台 Mac，不做。

## 五、读 customers.json 发现客户仓

### 输入和边界

- 登记表：私有仓 `grilling-customers` 里的 `customers.json`。D-0091 定它是客户、账号和仓指针的唯一登记表，字段形状见 `docs/客户白名单维护.md`。
- Mac 上要有一份能读的副本。怎么从私有仓同步到 Mac，归 to-spec 的 Mac 拉取桥，本节只定调度器读什么。
- 调度器配置三项：运营者 GitHub 账号（owner）、本地仓根目录（路径不带空格）、全局并发上限。
- 本票只定读取和发现规则，不写实现。

### 指针格式

`repo` 现在叫「客户仓名」。按下面的规则解析：

| 值 | 怎么用 |
| --- | --- |
| `null` | 还没建仓，跳过 |
| `acme` | 补上配置里的 owner，变成 `owner/acme` |
| `owner/name` | 原样使用。owner 不在配置允许的列表里就拒绝 |

仓名由上传服务建仓或复用仓后回写，调度器不自己起名。`short_name` 唯一；仓名允许 `acme`、`acme-2` 这种后缀（#13 的规则）。

### 每 30 秒的发现与对账

1. 拉本地副本（`git pull --ff-only`）。读失败就用磁盘上最后一次成功的副本，标黄告警。
2. 取 `status=active` 且 `repo` 非空的行，以 `id` 为主键。`id` 换邮箱也不变。
3. 对每一行：
   - 本地没有克隆：先 `gh repo view <完整仓名>` 确认仓存在、owner 对，再 `git clone` 到 `<仓根>/<id>`。
   - 已有克隆：检查 `origin` 地址。和期望值不一致就标错误，不跑。
   - 记一条本地状态：`id`、完整仓名、路径、上次成功时间。这是缓存，每轮以登记表为准。
4. 表里没有、`repo` 为空、`status=disabled` 的行：不点火。不删克隆，不中断在跑的 run。
5. 仓不存在、无权限、owner 不符：标 `repo_error`，按 30 秒、5 分钟、30 分钟退避重试，告警一次。

### 点火

1. 每仓一把内核级文件锁（`flock`）。进程退出时内核自动释放，包括被 kill。
2. 拿不到锁，跳过这个仓。
3. 拿到锁后，先 `gh issue list --label Sandcastle --state open` 看有没有活。没有就释放锁，不启动进程。
4. 有活才跑 `npm run sandcastle`，一次一轮，跑完释放锁。
5. 退出码 0 和 3 算正常。1、137 这类算失败，退避重试，连续失败告警。
6. 全局并发按 D-M1-010：先一单，稳了加到五单。

### 失败处理

| 情况 | 处理 |
| --- | --- |
| 仓不在表里 | 不点火，哪怕仓里有 `Sandcastle` 标签也不碰。给运营者列一条「账号下有队列标签但不在表里」，提醒补登记或清标签 |
| 前缀冲突 | 不按前缀扫仓，所以没有这个失败。上传服务按 `acme`、`acme-2` 分配仓名，调度器只读结果 |
| 两行指向同一个仓 | 只服务 `id` 较小的一行，另一行标错误、告警 |
| 仓建在别处（外部 owner） | 默认拒绝。运营者明确允许后，把 owner 加进配置，并确认 token 有权限 |
| 手工建的仓 | 必须补进 `customers.json`。调度器不扫账号下的仓去猜。没走上传流程的仓 `repo` 为空，等上传服务回写后再点火 |
| 客户停用 | 状态改 `disabled` 后不再点火；在跑的 run 不强制停 |
| 登记表读不到 | 用最后一次成功的副本，告警，继续服务已知仓 |
| GitHub 暂时不可达 | 这一轮跳过，退避重试。不把「读不到」当成「没有活」，也不清状态 |

### 在跑的 run 怎么识别

- 调度器自己：锁被持有、子进程还在。本地状态文件记开始时间、仓、pid、日志路径。
- 包自己：`sandcastle:in-progress` 标签、issue 分支、`.sandcastle/worktrees/` 里的 worktree、草稿 PR。
- `in-progress` 标签只能当提示，不能当租约。下一轮 Phase 0 会无条件清掉它，两个实例还会互相清。真正的互斥只有调度器的文件锁。
- 运营者屏幕：显示「仓、开始时间、当前角色」。角色从日志尾部解析，例如 `[planner] Started`、`[implementer:3] Started`。

### 和包的分工

| 谁 | 管什么 |
| --- | --- |
| 包 | 单仓内的状态推导、崩溃恢复、worktree 清理、分支和 PR |
| 调度器 | 多仓发现、每仓互斥、重启、退避、告警、并发上限、客户停用 |

## 六、和现有决定的关系

- **继承 D-0091**：`customers.json` 是唯一登记表。本节只定调度器怎么读，不重定表。
- **继承 D-M1-010**：每 30 秒对账，状态记在工单和 git 里，不靠内存。本节把「防重复点火」做成每仓文件锁。
- **继承 D-M1-013**：Mac 上的调度器直接点火，Grok Bot 只当窗口和收件箱。本节不改点火方式。
- **和工厂流程 D1/D2 的差距**：工厂流程要求提交前缀 `FACTORY:`、按 parent issue 固定分组、合并到主干。这三样包都不直接支持，需要提示词覆盖或工厂层改写，归后续票。
- **和 D6 点火超时的关系**：D6 要求点火后两分钟没回执就写「点火超时」并打标签、发邮件，不自动补点。本节的重试规则要照这条做：超时告警，但不要在同一把锁里重复点火。

## 七、未验证

- Docker 整链：镜像构建、容器挂载、容器内凭证。归 I-0031。
- 多机同时调度。现在只有一台 Mac。
- reviewer 提意见后的 responder 回路、ready PR 的 refresh/re-bump。
- 大仓库、长任务、并发多个 feature。
- 中转成本。第一次用 opus 跑到 merger 用了约 3 分钟，余额从可用降到 0.03 美元；便宜模型能跑完，但没有逐角色算过账。
