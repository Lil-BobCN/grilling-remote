# 网页预览生成：成本与延迟

> 对应 Issue #4。定价读取日期：**2026-11-01**，单位 USD / 百万 token（MTok）。
> 标注规则：**【实测】**今天直接读到的原文数字，或本地跑出来的数；**【估算】**按文中写出的算式推的；**【第三方】**别人测的，我没有复现；**【待实测】**没有可靠数据，不能当结论用。
> 汇率只用于给直觉：按 1 USD ≈ 7.1 CNY 粗算，不作定价依据。

## 结论

- **钱不是瓶颈。** 生成一页三变体，Sonnet 级模型 **$0.04–0.15**（¥0.3–1.1），Flash 级 **$0.014–0.054**（¥0.1–0.4），Haiku 级 **$0.002–0.007**。一次完整需求澄清（5 轮对话 + 3 次原型 × 3 变体）在 Sonnet 级约 **$0.44（¥3）**，最贵的 Opus 档也不到 **$0.9（¥6.2）**。【估算，算式见下】
- **延迟才是瓶颈。** 单页输出 1,200–4,000 token，按第三方测到的 79–139 token/s 推：单页 **9–50 秒**，三个变体串行 **30–150 秒**。首 token 时间三家都没公布，这一项 **【待实测】**，而它决定用户会不会觉得页面卡死。
- **所以产品上的选择不是"用不用得起"，而是"让用户等哪一段"。** 建议：默认模板拼装（方案 C，几乎零成本零等待），用户说"都不像"再现场生成（方案 A）；要 A 就**三个变体并行发请求 + 真流式 + 先出骨架**，不要排三个队。

### 表 2　页面 token 规模估算

估算方法分两步，第一步是实测，第二步是估算，不混在一起：

1. **【实测】**我按"模型常见输出长相"手写了三个单文件参考页（HTML + 内联 CSS，中文文案），用 `o200k_base` 分词器数 token：

| 参考样本 | 行数 | 字符数 | token（实测） | 字符/token |
| --- | --- | --- | --- | --- |
| 简单登录页 | 77 | 2,405 | 793 | 3.03 |
| 中等表单页（6 字段 + 校验提示 + 错误态） | 121 | 5,444 | 1,633 | 3.33 |
| 列表/仪表盘页（侧栏 + 筛选栏 + 表格 + 分页） | 121 | 6,266 | 2,085 | 3.01 |

实测结论：**代码类 HTML/CSS 大约 3.0–3.3 字符 = 1 token**，约 **10–17 token/行**。这个比例比中文散文（约 1 字 1–1.5 token）更省，但比英文散文（约 4 字符 1 token）更费。

2. **【估算】**模型实际输出比手写样本"胖"：会多空状态、多注释、多两档响应式、多几个 hover 态。按 **×1.5–2.0 膨胀系数**折算，取整后：

| 页面 | 采用值（估算） | 区间 | 依据 |
| --- | --- | --- | --- |
| 简单登录页 | 1,200 token | 900–1,800 | 793 × 1.5–2.0，再留手写样本偏瘦的余量 |
| 中等表单页 | 2,800 token | 2,200–3,600 | 1,633 × 1.5–2.0 |
| 仪表盘页 | 4,000 token | 3,000–5,000 | 2,085 × 1.5–2.0 |

膨胀系数本身是**假设**，不是实测。真实数字只能靠跑 API 读 `usage.output_tokens`，见「待实测事项」第 1 条。

## 三种复杂度页面的单次成本

### 表 3　生成一页（单次调用，含输入 4,000 token）【估算】

输入按 4,000 token 算：固定的设计规范/组件约定约 2,000，对话上下文约 2,000。

| 模型 | 登录页 | 表单页 | 仪表盘 |
| --- | --- | --- | --- |
| Claude Sonnet 5.5 | $0.020 | $0.036 | $0.048 |
| GPT-6.1 Sol | $0.020 | $0.036 | $0.048 |
| Gemini 3.8 Flash | $0.0075 | $0.0135 | $0.018 |
| Claude Haiku 5.5 | $0.0010 | $0.0018 | $0.0024 |
| Claude Opus 5.5 | $0.040 | $0.072 | $0.096 |

算式（以 Sonnet 5.5 生成表单页为例）：

```
输出 2,800 × $10/1,000,000 = $0.0280
输入 4,000 × $2/1,000,000  = $0.0080
合计                        = $0.0360
```

可见**输出占大头（约 78%）**，输入基本是零头。想省钱先砍输出（少生成、生成小的），而不是省 prompt。

### 表 4　三个风格变体【估算】

两种做法，成本差 1.5 倍左右：

| 模型 | 三次独立调用（登录/表单/仪表盘） | 一次调用出三变体（共享壳层，按 2.5× 单页算） |
| --- | --- | --- |
| Claude Sonnet 5.5 | $0.060 / $0.108 / $0.144 | $0.038 / $0.078 / $0.108 |
| GPT-6.1 Sol | $0.060 / $0.108 / $0.144 | $0.038 / $0.078 / $0.108 |
| Gemini 3.8 Flash | $0.023 / $0.041 / $0.054 | $0.014 / $0.029 / $0.041 |
| Claude Haiku 5.5 | $0.003 / $0.005 / $0.007 | $0.002 / $0.004 / $0.005 |
| Claude Opus 5.5 | $0.120 / $0.216 / $0.288 | $0.076 / $0.156 / $0.216 |

2.5× 的来历：三个变体共用 `<head>`、字体、颜色 token 和一部分结构 CSS，比独立三份省，但省不到一半。这是**估算**，实际取决于是否强制共享壳层。

三次独立调用还有一个隐性成本：**并行发三个请求，成本 ×3，但墙上时间不变**。如果按串行做，用户要等三倍时间——这是下面延迟部分的关键取舍。

### 表 5　一次完整需求澄清【估算】

场景定义：5 轮对话澄清（每轮输出约 300 token）+ 3 次原型（每次中复杂度 2,800 token × 3 变体）= 9 次生成。

```
输出 = 5 × 300 + 9 × 2,800 = 26,700 token
输入 = 14 次请求 × 平均 6,000 token = 84,000 token
```

| 模型 | 输出成本 | 输入成本 | 合计 | 约合人民币 |
| --- | --- | --- | --- | --- |
| Claude Sonnet 5.5 | $0.267 | $0.168 | **$0.44** | ¥3.1 |
| GPT-6.1 Sol | $0.267 | $0.168 | **$0.44** | ¥3.1 |
| Gemini 3.8 Flash | $0.100 | $0.063 | **$0.16** | ¥1.2 |
| Claude Haiku 5.5 | $0.013 | $0.008 | **$0.02** | ¥0.15 |
| Claude Opus 5.5 | $0.534 | $0.336 | **$0.87** | ¥6.2 |

**量级：一次万元级的客户沟通，模型成本是几块钱。** 这个数字说明：成本不该参与"做不做"的决策，只该参与"用哪个模型"的决策。

再加三个现实修正（都是**估算**，方向明确、幅度未知）：

- **重试。** 生成的 HTML 常有一两次不能用（标签没闭合、CSS 打架、文案跑偏）。按平均 1 次重试算，上表 ×2。
- **思考 token。** Gemini 4 Argon 明确说输出价含 thinking token，OpenAI 的 reasoning token 也按输出计费。开思考会让输出 token 涨 30%–100%（**待实测**），成本同比例涨。
- **缓存。** 固定设计规范放进 prompt cache，Sonnet 5.5 命中价 $0.10 是标准输入价的 1/20，输入成本能降一个数量级——但输入本来就只占 20%–40%，对总成本影响有限。

省钱的三个真招：**并行只生成用户点开的那个变体**（省 2/3）、**小模型出草稿大模型改**、**模板打底只让模型改差异部分**。

## 延迟拆解

延迟分四段，只有第二段有可靠数据。

### 1. 排队 + 首 token（TTFT）——【待实测】

三家官方定价页和模型页都不公布 TTFT。第三方 Artificial Analysis 的静态数据里，同一批模型的 TTFT 数值量纲不一致（有的看着像毫秒、有的像秒，E2E 时间还对不上），**所以我不引用它的秒数**，只引用单位明确的速度。

这一项恰恰最关键：如果首 token 要等十几秒，用户面对的是空白页，会以为坏了。**这是上线前必须自己测的第一个数。**

### 2. 流式生成——【第三方】速度 +【估算】时间

第三方实测的输出速度中位数（2026-11-01 读取）：

| 模型 | 输出速度（token/s） |
| --- | --- |
| Claude Sonnet 5.5 | 139 |
| Gemini 3.8 Flash | 120 |
| GPT-6.1 Sol | 79 |

按 80–140 token/s 的区间推（这是**推算**，不是实测秒数）：

| 页面 | 输出 token | 完整生成时间 | 首屏（前 300 token）出现时间 |
| --- | --- | --- | --- |
| 登录页 | 1,200 | 9–15 s | 首 token 后约 2–4 s |
| 表单页 | 2,800 | 20–35 s | 首 token 后约 2–4 s |
| 仪表盘 | 4,000 | 29–50 s | 首 token 后约 2–4 s |

公式：`完整时间 ≈ TTFT + 输出 token ÷ 输出速度`。表中不含 TTFT，所以真实值只会更长。

### 3. 前端渲染——【待实测】

流式返回的 HTML 不能边到边挂载：`<style>` 没到时页面会闪一下无样式内容（FOUC）。工程上一般等 `</style>` 或整页闭合再挂载，代价是首屏时间被推到"样式收完"那一刻。这个阈值要实测（见待实测第 8 条）。

### 4. 用户感知

结构上可以说清楚的两件事：

- **首屏比整页早很多。** 登录框、表头这些"看得见的东西"在前 200–400 token 就齐了，大约占整页的 10%–25%。真流式的话，用户不用等 30 秒才看到第一眼。
- **三变体串行不可接受。** 三页 × 30 秒 = 90 秒以上，没人等。要么并行（墙上时间 ≈ 单页），要么先出 A、B/C 后台补，要么走方案 C 直接本地渲染。

## 三个方案对比

### A　每次现生成

- **成本**：三变体 Sonnet 级 $0.04–0.15，Flash 级 $0.014–0.054，Haiku 级 $0.002–0.007。【估算，表 4】
- **延迟**：单页 9–50 s；三变体并行 ≈ 单页，串行 ×3。
- **风格多样性**：最高。能出"用户没想到的第三种"，这是它唯一不可替代的地方。
- **失败模式**：格式坏、CSS 冲突、文案发散，需要前端兜底（沙箱 iframe + 解析失败就重试）。
- **适合**：客户说不清、需要被"意外方案"点醒的时候。

### B　先线框图，确认后再生成正式版

- **成本**：线框图输出 200–500 token（$0.002–0.005），确认后再付正式版全额。总成本约 **A × 1.1–1.3**；但如果因此少一次整页返工，反而比 A 便宜。
- **延迟**：拆成两段，每段更短。线框图 2–8 s 能看（按同样速度推），用户先确认布局，再等 20–40 s 出正式版。**感知上比一次等 40 s 好，总时长差不多甚至更长。**
- **风格多样性**：高，但被"先定布局"收窄了。
- **失败模式**：多一次交互，会掉人。非技术客户可能看不懂灰盒子。
- **适合**：字段多、结构复杂、返工代价大的页面（表单、仪表盘）。

### C　模板拼装（预设组件 + 参数，不走模型或只让模型填参数）

- **成本**：模型只输出参数 JSON（约 300 token/变体），三变体共 900 token → Sonnet 级约 **$0.017**（含输入 4,000），Haiku 级约 **$0.001**；**完全不调模型时是 $0**。【估算】
- **延迟**：本地渲染，前端毫秒级（**待实测**）；如果让模型解析需求出参数，再加 2–6 s（按同样速度推）。
- **风格多样性**：低。只换布局（登录框左/右/下）、配色、圆角，换不出真正的"风格流派"。
- **失败模式**：客户觉得"就这几种"，或者跟自家品牌不像；但**不会坏**，可控、可预测。
- **适合**：MVP 验证阶段，先把"当场看见"这件事跑通。

### 怎么选

**先 C 后 A，不要一上来就 A。**

默认三套模板（左/中/右、或登录框在上/中/下），用户点"都不像"时，才现场生成一版——这时用户已经表达了偏好，A 的命中率更高，也只生成一个变体（省 2/3 钱和时间）。B 适合表单/仪表盘这类结构复杂的页面，用线框图先锁结构。

和 `/prototype` 的关系：`?variant=A|B|C` 单路由切换本来就是模板拼装形态，**C 是它的自然实现，A 是它的退化路径**（一个路由下挂一份即时生成的 HTML）。
