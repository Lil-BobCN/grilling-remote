# 客户仓库脚手架：全套还是分层

> 问题：新建客户仓库时，脚手架该做多全？要不要按不同客户做不同的脚手架？
> 证据截止：本机 `@ai-hero/sandcastle@0.12.0`、`claude` 2.1.296、本仓库 HEAD `c500729`。

## 结论

**不做全套，做分层。** 三层的界线不是"重要/不重要"，而是"有没有东西在读它"。

一个预制文件进仓之前，先回答：**谁读它？** 官方脚手架给出的答案只有四种读者：

1. `.sandcastle/prompt.md` —— 每轮 agent 都读（由 `promptFile` 显式指定）。
2. `.sandcastle/CODING_STANDARDS.md` —— 只有 review agent 读，implementation 不读。
3. `AGENTS.md` —— **不是** Sandcastle 读的，是 claude CLI 自己读的（二进制里写死 `CLAUDE.md`、`CLAUDE.local.md`、`AGENTS.md`、`.claude/AGENTS.md`、`.claude/rules` 这个顺序）。Sandcastle 的官方模板一次都没引用过它。
4. 检查命令（typecheck / lint / test / CI）—— 机器读，结果进 PR。

答不出"谁读它"的文件，**就是零读者文件**。官方五个模板印证了这一点：prompt 里引用的是 `ticket tracker 活数据 + git log + CODING_STANDARDS.md`，`AGENTS.md`、`CONTEXT.md`、`README.md` 一个都没出现。所以脚手架能起作用的面积比想象中小得多，多出来的部分全部是负债。

**"按不同用户做不同脚手架"这个问法本身就是分叉错了地方。** 客户之间的差异有三种，只有一种该改变脚手架：

- 服务槽位不同（tracker / git host / runner）→ 这是 `init` 的三个参数，不是三套脚手架。Sandcastle 官方只给 5 个 workflow 模板（`blank`、`simple-loop`、`sequential-reviewer`、`parallel-planner`、`parallel-planner-with-review`），也没有按客户分叉。
- 需求类型不同（有无 UI、有无持久化、有无 review）→ 落在**条件层**，判定条件是可观测的（见下表），不是靠猜客户。
- 客户"很特殊" → 这时脚手架应该更小而不是更大。因为你的预判越可能错，而**错的部分会被 agent 当成权威指令忠实执行**：一项 320 次运行的实测里，指令文件与代码冲突时，90.1% 的选择跟了旧文件；Claude Code 在 80 次里有 79 次**指出了**这个冲突，然后仍然照旧文件做（arXiv 2610.30571）。

一句话版：**预制接口（文件名、路径、职责、指针、检查命令），不预制内容（术语、决定、规则、进度）。**

## 不变量层

12 项。全部围绕同一件事：**让 AFK 循环能自己判断"这一轮做完了没有"，并且出事时有三道刹车里至少一道真的踩得住。**

行业原话，来自本机 `software-factory` 技能：

> Every trigger is an accelerator. Accelerators without brakes make a slop cannon.
> **Automated checks**: deterministic gates (types, lint, tests) that every run must pass.

反过来说，如果一个东西既不构成刹车、也不被谁读取，它就不属于不变量层。

### 1. 至少一个 commit 和 `main` 分支

空的 git 仓库会让第一轮直接失败。本地实测原话：

> **第 1 次失败**（仓库还没有提交）：`WorktreeError: fatal: ambiguous argument 'HEAD': unknown revision or path not in the working tree.`

这不是理论风险，是踩过的坑。

### 2. `AGENTS.md`，且必须小

本仓库自己的 `AGENTS.md` 是 **22 行**，`git log -- AGENTS.md` 只有一次提交（初始化那个 commit）。这是一个活跃仓库的合理尺度，可用作上限参照。

内容只放三类：

- 没法机械化的约定（比如"用中文写自然语言内容""别写机翻腔"）。
- 非标准做法。这一条有正面证据：AGENTS.md 类文件对"指定非标准编码实践"有效，对"仓库概览"无效（arXiv 2602.11988）。
- 指针。`retro` 技能的原话最狠：

> `CLAUDE.md`/`AGENTS.md`: these files are pushed to the context window of any agent working in this repo. They should be used incredibly sparingly, usually only for **navigation pointers** to other files.

**必须带一句优先级句**，这是本次调研里性价比最高的一条：在文件里明写"本文与代码冲突时以代码为准，并顺手改正本文"。同一项实测：加这一句后，跟代码走的选择从 4.2% 提升到 91.4%，测试通过率从 89.4% 升到 100%，Codex CLI 那 20 次"把老代码改写成符合旧规则"的行为也消失了（arXiv 2610.30571）。

### 3–6. `docs/agents/` 三件套，加真实存在的标签

`issue-tracker.md`、`triage-labels.md`、`domain.md` 是 `setup-matt-pocock-skills` 的产物，也是 `to-spec` / `to-tickets` 的前置条件。技能原文：

> The issue tracker and triage label vocabulary should have been provided to you — run `/setup-matt-pocock-skills` if not.

其中 `triage-labels.md` 在原生 setup 里是**条件项**（"没有安装 `triage` Skill 时，整段跳过"）。但在软件工厂里它是**不变量**：工厂的触发器就是标签。官方示例任务原话：

> **Implementer task** — Trigger: a ticket is labelled ready, by a human or an explore run.

所以工厂不能跳过标签。而且要注意一个容易漏的落差：`triage-labels.md` 只是一张映射表，**标签本身得在 GitHub 上真的存在**。文件写了、仓库没建标签，等于打标签静默失败，tickets 永远进不了"可认领"的池子。建仓脚本里必须有 `gh label create` 这一步。

`domain.md` 之所以是不变量而不是条件项，是因为它规定了**当 `CONTEXT.md` 不存在时怎么办**，而这条规定必须提前写进仓库。原文：

> 这些文件不存在时直接继续，不提示缺失，也不提前建议创建。等术语或重要决定真正明确后，再由 `domain-modeling`、`grill-with-docs` 或 `improve-codebase-architecture` 按需创建。

记住这句话——它是"不该预制 `CONTEXT.md`"的直接依据。

### 7–8. 一条能跑通的检查命令，加一个真的会跑它的闸

拆成两条是因为它们会分别坏掉：命令不存在，和命令存在但没人跑。

- 为什么必须有命令：`implement` 技能的收尾动作就是"运行 typecheck 和测试"（"Run typechecking regularly, single test files regularly, and the full test suite once at the end."）。没有命令，这一步无处落地。
- 为什么必须是"一条命令"：Sandcastle 官方 `sequential-reviewer` 模板把命令名硬编码了 —— "**Verify** — run `npm run typecheck` and `npm run test` before committing."。换语言栈就得改 prompt，这是条件层的事；不变量是"有一条命令能一次跑完类型、lint、测试"。
- 为什么必须有闸：`retro` 技能把没有闸的仓库本身列为一条问题：

> A repo with no **guardrail** (no pre-commit hook and no CI job running its lint/typecheck/test command) is itself a finding: an un-linted repo is a standing missed opportunity, not a neutral default.

### 9–11. `.sandcastle/` 五件套、`.gitignore`、`.env.example`

`init` 生成的东西是固定的五个文件：

```
.sandcastle/
├── Dockerfile      # Sandbox environment (customize as needed)
├── main.mts        # Agent entry point (main.ts in an ESM package)
├── prompt.md       # Agent instructions
├── .env.example    # Token placeholders
└── .gitignore      # Ignores .env, logs/, worktrees/
```

本地实测另加一个 `SETUP_ISSUE_TRACKER.md`（只有选 `custom` tracker 时才有）。

三点必须写进建仓规则：

- **pin 版本**。`npx @ai-hero/sandcastle init` 不带版本号会按 `engines.node` 回退，同一份命令在不同 Node 版本上产出不同模板。本机是 Node 26 + 0.12.0。写死 `@ai-hero/sandcastle@0.12.0`。
- **`init` 不可重入**，别指望它做升级："Errors if `.sandcastle/` already exists to prevent overwriting customizations."
- **`.env` 永不入库，`.env.example` 必须列全所有键**。原因不是洁癖，是实测出来的机制：`resolveEnv` **只遍历 `.sandcastle/.env` 里出现过的 key**，再回退 `process.env`。宿主上配好的 `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` 不会自动进沙箱。漏一个键，容器里就跑成"没登录"。

### 12. 提交信息前缀约定

官方 prompt 靠前缀找自己上一轮的提交：

> ## Recent RALPH commits (last 10) — `!`git log --oneline --grep="RALPH" -10``

> **Commit** — make a single git commit. The message MUST: Start with `RALPH:` prefix

工厂用自己的前缀（比如 `FACTORY:`）没问题，但必须是**约定好的常量**，否则循环每轮都看不到自己的历史，会重复劳动。

## 条件层（附判定条件）

判定条件必须是**可观测的**，不是"感觉这个客户需要"。8 项。

| 触发信号（可观测） | 加什么 | 为什么此时才加 |
| --- | --- | --- |
| 需求里有用户可见的界面，或有 HTTP 入口 | `init.sh` 式脚本：起服务 + 一条冒烟断言 | Anthropic 的初始化实践里，这是失败模式的正面解：failure mode 是 "Claude has to spend time figuring out how to run the app"，解法是 "Write an `init.sh` script that can run the development server"。没有 UI 就没有服务要起，写了也没人跑 |
| 有用户可见行为，且单元测试不足以证明它对 | Playwright / Puppeteer 端到端 | 实测到的失败模式是"功能坏了但单测全绿"，厂商给的解法是显式要求浏览器验证（"Claude mostly did well at verifying features end-to-end once explicitly prompted"）。纯库、纯数据管道不需要 |
| 有持久化（DB、迁移、schema） | `db/migrations/` + 空库重建脚本 + 一条"从零库跑通"的检查 | runner 是一次性的："Nothing on it survives the run"。每轮都从冷环境开始，迁移顺序错一次就整轮报废 |
| 开了自动 review 任务 | `.sandcastle/CODING_STANDARDS.md`（**空壳起步**） | 它只在 review 时读：`retro` 说 "`CODING_STANDARDS.md`: this file is read during review, not implementation."。没开 review 就是死文件 |
| 同一概念出现 ≥2 种叫法，或需求含重构 / 改名 | `CONTEXT.md` | `domain.md` 明文规定按需创建；没有术语摇摆时它只会沉淀成无人维护的词典 |
| 出现一个"返工成本 > 一个 ticket"的决定 | `docs/adr/0001-*.md` | 同 `domain.md`：等决定明确后再写。ADR 的价值是阻止决定被悄悄推翻，没有这类决定时它只是作文 |
| 出现多包信号：`pnpm-workspace.yaml`、`package.json` 的 `workspaces`、含自身 `src/` 的 `packages/*` | `CONTEXT-MAP.md` + 分上下文 ADR | 这是 setup 技能自己给的判定标准，原文："没有这些信号时，默认是单一上下文仓库" |
| 客户要看、要交接、要过审 | `README.md` | 纯人类读者。它在 GitHub 首页有用，但对 agent 无效——"repository overviews, although popular and recommended by model providers, are not helpful"（arXiv 2602.11988）。所以它不属于不变量层，也**不要**写进 AGENTS.md 当指针 |

另有两个**换服务才变**的项，不属于"看项目类型"，属于看槽位：

- 非 GitHub 的 remote → 换 `docs/agents/issue-tracker.md` 的模板（GitLab / 本地 Markdown 三选一）。
- 换 agent provider（codex / pi / cursor / opencode）→ 重新确认 `AGENTS.md` 到底会不会被加载。目前"claude 会读 AGENTS.md"这条，是我在本机 2.1.296 二进制里验证的，不是跨 provider 的保证。

## 不该预制的

这一节每条都给出"加了会怎样"，不是"一般不推荐"。

**1. `CONTEXT.md` 和 `docs/adr/` 的空文件。**
直接违反本仓库 `docs/agents/domain.md` 的白纸黑字："不提示缺失，也不提前建议创建"。空文件进仓后有两个后果：agent 读到空词典会开始自己定义术语（比没有更糟）；而它一旦进了初始化提交，就再没人动它 —— 那正好是"Init Fossilization"这个 smell 的定义。

**2. 进度文件（`claude-progress.txt` / `PROGRESS.md` / `STATUS.md`）。**
这是唯一一处**要明确不照抄** Anthropic 的做法。那边确实让初始化 agent 写 `claude-progress.txt`，因为它的场景是"单一长任务、连续会话、没有 ticket 系统"，记忆只能靠文件和 git。你的工厂不是：官方定义里——

> a run's only memory of earlier runs is the ticket tracker, the git host and the orchestrator.

记忆已经有三个权威源了，再加一个进度文件就是第四个。同一份意义存两处，代价是维护和 token，还会把一个次要信息的显著度抬到不该有的位置（`writing-for-agents` 的 "single source of truth" 那条）。真正的解法是**注入活数据**，不是维护一份手写进度：

> ## Open issues — `!`{{LIST_TASKS_COMMAND}}``
> The list above has already been filtered to issues ready for work and is the sole source of truth for what work exists.

**3. 200 条 feature list / `features.json`。**
同上，它的职责在你这儿已经被 `to-tickets` 的 tickets 取代了，而且 tickets 还多带了 blocking edges（"Give each ticket its **blocking edges**"）。预生成一份 feature 清单，等于绕过 to-spec 直接手写需求，还跟 tracker 打架。

**4. 把客户需求的结论写死进 `prompt.md`。**
官方 prompt 的形状是"角色 + 活数据注入 + 完成信号"，`blank` 模板通篇只有 `<!-- -->` 占位。把某个客户的具体业务结论写进 prompt，下一轮需求变了它就变成过期指令，而 2610.30571 已经量过：过期指令的优先级高于代码。

**5. 语言/框架的规则散文。**
"用 camelCase""函数别太长""提交信息要清晰"这类能机械判定的规则，最高频的配置 smell 就是它：Lint Leakage，出现率 **62%**（100 个热门仓库的挖掘研究，arXiv 2606.15828）。判定规则很简单：**能不能写成一条 lint 规则？能，就写进 linter，别写进散文。**

**6. 不 pin 版本的生成器。**
`npx create-xxx` 不写版本号时，解析器会挑一个 `engines.node` 满足当前运行时的**较旧**版本，而不是最新的。agent 拿到旧模板的输出会当成事实继续往下写。这条有专门的 anti-pattern 名字：Unversioned Scaffolding Commands Pull Stale Templates。

**7. AGENTS.md 里的仓库概览、目录树、技术栈说明。**
不是"太长所以不好"，而是实测**没用还有成本**：给上下文文件后任务成功率总体没有提升，推理成本平均上升 20% 以上；其中"仓库概览"这一类明确被判定为无帮助（arXiv 2602.11988）。
另外，这类内容就是 `writing-for-agents` 说的 cache："The environment is a source of truth too — `package.json` scripts, config files, the directory layout... Leave the one-file, one-command lookups to the environment, where they cannot go stale."

**8. 空目录占位（`src/`、`tests/` 只有 `.gitkeep`）。**
检查命令会"跑绿"，但跑的是零个测试。这是最坏的一种假信号：它让刹车看起来装好了。

**9. 建仓即开全自动（无人工 review、自动合并）。**
`software-factory` 的排序建议是反过来的："Add one automated trigger at a time, throttled at first, with human review on every PR."。这不是文件，是仓设置，但属于同一个决定。

## AGENTS.md 的维护方式

### 三种方案对比

| 方案 | 抗腐化弱在哪 | 证据 |
| --- | --- | --- |
| 模板快照（建仓时复制一份） | 上游后来的修复不回流，每个客户仓各自烂 | 这不是猜测，是被写成 ADR 的实战教训："once repositories were created from the template, there was no systematic way to propagate template improvements ... without manual intervention or repository recreation"（Azure ADR-011） |
| 全局同步（建仓/定时用模板覆盖） | 会覆盖客户仓自己的修改；必须先定义"哪些文件归模板、哪些归客户" | 同上 ADR 的解法就是一份 `sync-config.json`，而它的排除项里赫然有 `copilot-instructions.md` —— 指令文件被**显式排除**，即"fork-owned，永不同步" |
| 每仓手写 | 每个仓都要重新犯同样的错；且没有任何力量阻止它只增不减 | 见下一节的三组数据 |

三种都不是答案。真正的抗腐化不来自"文件从哪来"，而来自**有没有删除的判据**。

### 加规则容易，删规则才是难点

三组相互独立的实测，指向同一个结论：

- **只增不减是默认结局。** 1,867 个仓库、247,694 条指令的生命周期：文件增长 **226%**，每次提交净增 **4.9 条**指令；指令中位数 **39 条**。而且"删不动"会随时间恶化——删除风险随指令年龄增长而下降（越老越删不掉）。更反直觉的是：大改写（wholesale rewrite）这个泄压阀**不管用**，改写前每提交增长 4.1%，改写后 4.9%（arXiv 2608.11095）。
- **让它自己长，会长出病。** 100 个热门仓库里 91 个至少有一项配置 smell；Context Bloat（≥200 行）42%；Init Fossilization（初始化生成后再没改过）**24%**（arXiv 2606.15828）。
- **陈旧内容会被当真。** 把 README 一致性检查器改造后套到 AI 配置文件上，356 个仓库里 **23%** 存在失效的代码元素引用（arXiv 2606.09090）。而 agent 对这些失效引用的反应不是忽略，是"当权威"（2610.30571 的 90.1%）。

顺带一个自查：本仓库的 `AGENTS.md` 也只有一次提交、之后四个 commit 都没动过，形式上就是"Init Fossilization"。现在不算问题（仓库还没有会漂移的代码），但它说明**循环里没有任何东西会自动回头看这个文件**——不装机制，就一定是这个结局。

### 结论：文件所有权 + 块级同步 + 删除闸

不选"全同步"也不选"全手写"，按**文件**分所有权，一个文件只能有一个主人：

| 文件 | 所有权 | 是否随模板更新 |
| --- | --- | --- |
| `docs/agents/issue-tracker.md` | 工厂 | 是（覆盖） |
| `docs/agents/triage-labels.md` | 工厂 | 是 |
| `docs/agents/domain.md` | 工厂 | 是 |
| `.sandcastle/`（除 `.env`） | 工厂 | 是，但通过**重新生成 + diff** 上抛 PR，不静默覆盖 |
| `AGENTS.md` 里的 `## Agent skills` 段 | 工厂 | 是，用标记块就地替换 |
| `AGENTS.md` 其余段落 | 客户 | 否 |
| `.sandcastle/CODING_STANDARDS.md` | 客户 | 否 |
| `CONTEXT.md`、`docs/adr/` | 客户（agent 代写） | 否 |

标记块长这样，让"能不能覆盖"这件事在文件里可见，不靠人记：

```markdown
<!-- factory:begin 本段由软件工厂维护，重建仓时会被覆盖 -->
### 任务管理
...详见 `docs/agents/issue-tracker.md`。
<!-- factory:end -->
```

如果连块级同步都嫌重，那就退到更粗的策略：**不复用文件，复用检查**。加一个每月跑一次的"脚手架体检"任务，只报告缺什么、什么已经失效，不自动改。这比静默覆盖安全，代价是修复靠人。

### agent 改 AGENTS.md 可以，但要装闸

这本来就是官方设计，不是我们要发明的：

> **Retro task** — Trigger: a PR merges, throttled to one merged PR in ten. Does: reads the PR, its ticket, its automated reviews and its run logs, and **proposes changes to the factory's own instructions as a PR**.

配套的还有两条："Because the fix changes the factory itself, it always gets human review"，以及 fix 任务"a failure in a fix run's own work triggers nothing"，防止修复自我串联。

所以"可不可以让 agent 改"答案是**可以**，条件是四条闸：

1. **只能走 PR，永不直接推 main。** 且 PR 描述强制回答两个问题：这条规则是哪个 ticket / PR 逼出来的？**删掉了哪一条？** 第二个问题不是形式主义——净增长 4.9 条/提交就是"没人被要求删"的直接结果。
2. **每条新增带失效条件。** Source（哪个失败催生的）、Applicability（什么条件下才该生效）、Expiry（什么可观测信号出现时可以删）。有三字段，删除就从一个开放判断变成"谓词是否成立"，默认值从"不确定就留着"翻转成"到期就删"。这是 arXiv 2608.11095 唯一给出的可操作解法。
3. **机械校验进 CI。** 至少三条：文里提到的每个路径必须存在（23% 的仓库栽在这）；行数上限（200 行是 Context Bloat 的经验阈值，本仓库现状 22 行，留足余量）；`## Agent skills` 标记块完整。
4. **文件顶部那句优先级句不许删。** 它是唯一一条能把"跟旧指令"扭转成"跟代码"的开关。

再补一条纯设计直觉（没有实测支撑，但和上面数据的方向一致）：**同一个坑第二次踩到才允许写进 AGENTS.md，第一次先问"能不能加一条检查"。** 因为一次性失败催生的规则，往往只覆盖那一次的形状，而它会永久占据每次对话的上下文；`retro` 技能的排序也是这个方向——机械性违规"gets a deterministic check, full stop"，`CODING_STANDARDS.md` 只留给"真正的判断类问题"。

### D 级：本文的设计直觉（没有实测支撑，请当假设）

1. **"谁读它"这个准入判据**。它是从"官方模板只引用两个文件"归纳出来的，方向可靠，但没有做过对照实验证明"零读者文件一定有害"。
2. **块级标记同步**（`factory:begin/end`）。借的是 Azure `sync-config.json` 的所有权思路，但块级实现是我的设计，没在任何真实仓库里跑过。
3. **"同一个坑第二次才允许写进 AGENTS.md"**。顺着"机械规则进检查、判断类进 CODING_STANDARDS"推的，没有实验。
4. **不变量 12 项这个数字**。它不是从数据里算出来的，是我的切分建议；真正硬的只有"必须有一条检查命令 + 一个闸"，其余项目可以按客户讨价还价。

### 一条综合推断（明确标注为推断）

把 2602.11988（上下文文件总体不提升成功率、成本 +20%）和 2610.30571（指令被极端忠实地执行，哪怕它与代码冲突）放在一起看：**指令文件的作用是"放大"，不是"改善"——它让 agent 更听你的，但不会让它更会写代码。** 写对了放大判断力，写错了放大错误，两种情况都要付每次对话的上下文成本。这个结论我没在文献里见到原话，是从两篇的结果推的。
