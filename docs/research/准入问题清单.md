# 准入问题清单：客户答到什么程度才能开工

> 读取日期：2026-11-01。对象是完全不懂编程的客户，目标是让 `/to-spec → /to-tickets → /implement` 这条链直接开工。
>
> 口径：**客户**是提需求的人；**运营者**是这套 agent 的拥有者，负责合并、部署、合规。两者可能是同一个人，但责任不同，不能混着算。
>
> 本文只回答「问什么、为什么问」，不设计界面。界面形态见 [需求澄清界面设计研究](./需求澄清界面设计研究.md)。

## 结论（最重要的 5 条 + 一句为什么）

1. **要解决谁的什么问题。** 因为 `/to-spec` 明写自己不访谈、只把已有对话「合成」成 spec；这句空着，它会补一句听起来合理的，后面每个字段都建在这句上。
2. **做完什么样算成功。** 因为 ticket 的验收条件只能从这句话长出来；没有它，「做完」就等于「代码能跑、测试变绿」。
3. **给谁用、谁绝对不能看。** 因为 user story 的第一格是 actor，权限模型也在这里定；错在数据模型层，改起来最贵。
4. **明确不要什么。** 因为 Out of Scope 是模板必填；不写，agent 会顺手加戏，评审也没有依据判越界。
5. **有没有必须接上的现有东西。** 因为它决定 Implementation Decisions；不答就默认全新，等 PR 出来才发现要接老域名、老数据、老账号。

其余 9 条不是不重要，而是要么可以给默认值，要么该由运营者拍板。

- 第 7、11、12 条是**运营者【必须拍板】**，不要放进客户问卷。客户不知道服务器、合并权限和合规边界，问了只会得到「你看着办」。
- 第 12 条只在收集个人信息时适用；一旦适用，严重程度直接升到最前，不是第 12 位。

## 技能链的硬性要求 vs 行业惯例

先分清四种东西：客户必须给的、AI 自己填的、运营者必须给的、技能链根本不管的。把第四种当第一种问，是问卷变长的主要原因。

| 层级 | 内容 | 依据 |
|---|---|---|
| 客户必须给 | 问题、完成态（现象）、使用者与权限、不做的事、现有系统与数据 | `/to-spec` 的 Problem Statement / Solution / User Stories / Out of Scope；`/to-tickets` 的 Acceptance criteria |
| AI 自己填 | Implementation Decisions、Testing Decisions、阻塞边、seam、技术选型、文件路径 | `/to-spec` 模板；`/to-tickets` 的 vertical slice 规则；`tdd` 的 seam |
| 运营者必须给 | seam 确认、合并与验收人、部署与账号、隐私合规、查重确认 | `/to-spec` 第二步；`software-factory` 的人与重复问题 |
| 技能链不管 | 工期、预算、优先级、视觉、性能、SEO、兼容性、多语言、成功指标、维护 | 两份模板里都没有对应字段 |

### 硬性要求（不答就生成不了完整 spec / ticket）

- **`/to-spec` 的 7 个模板字段**：Problem Statement、Solution、User Stories、Implementation Decisions、Testing Decisions、Out of Scope、Further Notes。客户真正必须给的是前三个和 Out of Scope；中间两个 Decisions 是 AI 的活，Further Notes 是补充。
- **User Stories 要「a LONG, numbered list」并且「extremely extensive」**。客户只给三五个功能点不够，agent 需要足够素材把故事铺开；铺不开就会自己编。
- **`/to-tickets` 每张票必须有 Acceptance criteria 和 Blocked by**。验收条件从客户的「完成态」转写；阻塞边由 AI 按技术依赖定，客户不参与。
- **`/to-spec` 第二步要求「和用户确认 seam」**；`tdd` 也要求「测试只打在预先约定的 seam 上，并和用户确认」。客户听不懂 seam，这条必须运营者代答，否则流程会在这里停住，或者假装确认。
- **`/to-spec` 要求全文使用项目词汇**，`grill-with-docs` 负责产出 `CONTEXT.md`。客户负责给词和纠错，AI 负责定义。
- **`software-factory` 要求每个任务回答「人在哪回来」「怎么防重复」**。这是工厂层硬性要求，客户答不了。
- **`code-review` 的 Spec 轴要有可定位的 spec**；没有就跳过。所以需求入口必须留下一个 issue 或 spec 文件，不能只有聊天记录。
- **`/implement` 要求「at pre-agreed seams」**；seam 没确认，TDD 无法开工。

### 行业惯例（技能链没写，但交付会疼）

- **截止时间、预算、优先级**：技能链没有这些字段；`/to-tickets` 按依赖排，不按价值排。
- **视觉参考、品牌规范**：`/to-spec` 只写「从用户视角的解决方案」，不写视觉。
- **性能、并发、SEO、无障碍、浏览器兼容、多语言**：模板完全没有非功能需求字段。
- **托管、域名、账号、费用**：`software-factory` 提了「用户选择的远程基础设施」，但没说要去问客户。
- **隐私合规、数据留存**：没有任何技能提到。
- **内容素材、上线后维护**：Further Notes 可以放，但不是必填。
- **成功指标（转化率、电话量）**：Problem Statement 可能隐含，但没有独立字段。
- **竞品参考**：`grilling` 可能问，但不是模板要求。

叫「惯例」只是说技能链没写，不是说可以不做。正确的处理是**给默认值或升级给运营者**，而不是拿去问一个不懂技术的客户。

## 意外发现（matt 其实不要求的东西）

1. **`/to-spec` 明确不访谈。** 原文是「Do NOT interview the user — just synthesize what you already know.」它假定前面已经问完了。需求入口是唯一能问客户的地方；到 `/to-spec` 就已经晚了，缺口不会被发现，只会被编圆。这是整份清单存在的理由。

2. **`/to-spec` 模板里没有验收条件，也没有非功能需求。** 常被转述成「场景、用户故事、验收条件」，但原文模板只有 Problem Statement / Solution / User Stories / Implementation Decisions / Testing Decisions / Out of Scope / Further Notes。验收条件是到 `/to-tickets` 才出现的。所以别逼客户写验收条件，问「什么现象算成」就够了。

3. **`/to-tickets` 完全不需要客户。** 它要的是 spec 或对话；阻塞边按技术依赖定；没有优先级、工期、负责人字段。「先做哪个功能」这个问题，客户答了也不会进入 ticket。

4. **客户指定的技术细节不是 spec 要的东西。** 模板甚至明确不要文件路径和代码片段，理由是「很快会过时」。客户可以说「必须用微信登录」「数据必须留在国内」这类约束；「用 React 还是 Vue」应该由实现方定。

5. **「够了」的判据不是清单填完，是 frontier 空。** `grilling` 的结束条件是「每条分支都走过，没有任何东西被默默假设」。清单只是常见 frontier 的枚举；客户答完 14 条，仍然要过一遍「还有没有我们没问就假设了的」。

6. **环境事实不该问客户，业务事实必须问客户。** `grilling` 说「Finding facts is your job, never the user's」。现有网站用什么技术、竞品有没有这个功能，应该 AI 自己查；现在谁在用 Excel、多久做一次，只能问客户。

7. **`/to-spec` 有一处容易被忽略的张力：开头说不访谈，第二步又要求和用户确认 seam。** AFK 链里没有「用户」可确认，所以这个确认必须提前到入口，由运营者代答。否则它要么跳过，要么假装问过。

8. **没 spec 不会报错，只会让评审静默降级。** `code-review` 找不到 spec 时跳过 Spec 轴，只报「no spec available」。于是「缺需求」不会阻塞流程，只会让代码评审退化成只看风格。

9. **入口只落一张表单是不够的。** `/to-spec` 吃的是「current conversation context」，不是字段 JSON。问答过程丢了，合成时就少一大块上下文。入口要么保留问答记录给下游，要么把摘要写足。

10. **`software-factory` 的五问不是客户问卷。** 它问的是工厂里的任务：什么触发、读写哪些服务、触发什么、人在哪回来、怎么防重复。能翻译成客户问卷的，只有第 4、5 问；把五问整段拿去问客户是范畴错误。

11. **`CONTEXT.md` 只是词汇表，ADR 要三个条件同时成立。** 别把客户需求倒进 `CONTEXT.md`，也别为每个客户决定写 ADR；大多数客户需求连一条 ADR 都不需要。

### 本机技能（`/Users/Admin/.dsh/skills/`）

> This skill takes the current conversation context and codebase understanding and produces a spec. Do NOT interview the user — just synthesize what you already know.

> Iterate until the user approves the breakdown.

>
> - [ ] Criterion 1
> - [ ] Criterion 2

> The **frontier** is every decision whose prerequisites are already settled — the questions you can ask _now_ without guessing at answers you haven't heard yet. Ask the whole frontier in one round: number each question and give your recommended answer.

**`domain-modeling/SKILL.md`**

> `CONTEXT.md` should be totally devoid of implementation details. Do not treat `CONTEXT.md` as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else.

> Only offer to create an ADR when all three are true:
>
> 1. **Hard to reverse** — the cost of changing your mind later is meaningful
> 2. **Surprising without context** — a future reader will wonder "why did they do it this way?"
> 3. **The result of a real trade-off** — there were genuine alternatives and you picked one for specific reasons

**`tdd/SKILL.md`**

> Tests verify behavior through public interfaces, not implementation details.

> Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user.

### 官方仓库（`mattpocock/skills`，2026-11-01 用 `gh api` 读取）

**`skills/in-progress/software-factory/SKILL.md`** — https://github.com/mattpocock/skills/blob/main/skills/in-progress/software-factory/SKILL.md

> A **software factory** is a system of agents that turns tickets, PRs and schedules into merged code, deployed on remote infrastructure the user chooses.

> A run never waits for a human: it ends, and the human's later change to the ticket tracker or git host triggers a new run.

> For each task, answer:
>
> 1. What triggers it?
> 2. What does it do, and which services does it read and write?
> 3. What does it trigger next?
> 4. Where does a human re-enter?
> 5. What stops two runs doing the same work?

> A design is finished when every slot names a product (or, for the observability platform, a deliberate none) and every task and ticket source has an answer to every question.

**`skills/in-progress/software-factory/EXAMPLE-TASKS.md`** — https://github.com/mattpocock/skills/blob/main/skills/in-progress/software-factory/EXAMPLE-TASKS.md

> The implementer run here picks the next ticket whose dependencies are all closed, and triggers itself again until no ticket is left.

> Does: reviews the diff against the codebase's standards and the ticket it came from.
