# 调度器直接点火，Grok Bot 只当窗口和收件箱

> 2026-11-15 按 D-M1-013 部分取代：下文「给客户回话」作废，Grok Bot 只当窗口和收件箱，不回客户；回客户走微信。原文不改。
>
> 2026-11-16 按 I-0111 换轨：Grok Bot 退出关键路径，窗口和收件箱改由企业微信群机器人承担，只推提醒，不推选项。邮件兜底已验（D-0323）：独立 SMTP 从本机直发，7 秒内到 Outlook 收件箱。点火方式和 2 分钟阈值不变；下文「Grok Bot」按此理解，原文不改。

2026-11-04 决定。Mac 上的调度器每 30 秒读一遍 open 工单的标签。找到「该动还没动」的，自己启动对应的执行会话，把提示词喂进去。Grok Bot 不做路由，不点火。它只收提醒、把闸门和拆票的选项推到手机、给客户回话；闸门和拆票的决定在 Orca 里做，agent 写回父工单评论。

为什么：Grok Bot 靠例程和 webhook。审批会过期，例程会被暂停，用量会限流，提醒到不了人。点火这条链不能押在它身上。状态只在 GitHub，调度器主动去读，少一层转发。

代价：点火后 2 分钟没回执，调度器在工单上写「点火超时」、打标签、发一封邮件，不自动补点，等人。告警走 GitHub 和邮件，不走 Grok Bot。门铃和 webhook 退场。2 分钟这个阈值是从旧门铃方案沿用的，没实测。

依据：`docs/工厂流程.md` 的「服务器、Mac、GitHub、Grok Bot 分工」一节；同文件的 D6 点火超时那条；C08-U006（2026-11-04）原话「选 C，改回调度器直接点火」。

2026-11-15 补：小需求只有补缺口一次点头。补缺口 Agent 在写 `点头：补缺口` 前建一张实现票；调度器读到 `大小:小需求`、这条点头和那张 open 子票，把父工单直接改成 `状态:开发中` 并点火。不经过 spec、排队中和拆票。见《小需求的工单与点火路径》（I-0028）。
