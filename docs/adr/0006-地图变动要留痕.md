# 地图变动要留痕，to-spec 前先查全图

> 2026-11-09 部分被 [词条与 ADR：决定、台账、依据、推迟](https://github.com/Lil-BobCN/grilling-remote/issues/119) 取代（ADR [0008](0008-决定写在关票评论，台账编译生成.md)）：新会话只读「现行决定清单」评论的做法改成读地图全文、`docs/decisions.md`，需要细节时打开台账里这条决定对应的来源票，地图 `Decisions so far` 只当索引。`map-gate` 与 `spec-check` 都保留，出的清单降为放行报告。下文出清单的步骤按旧规矩读，其余不变。
>
> 2026-11-09 再改：第 2 条里的 `init-trail` 已删除，`map-gate`、`wrap-up`、`next`、`spec-check` 四个保留（D-0009，票 [init-trail 模板引用 scripts/decisions，但技能不装脚本](https://github.com/Lil-BobCN/grilling-remote/issues/137)）。

2026-11-06 决定。地图上的决定被后来的票推翻时，旧票、旧索引行、开放票的前提要同步处理。`to-spec` 之前，运营者跑 `/map-gate`，由一个没参与过前面对话的子代理读完整张地图，出「现行决定清单」，发成地图上的评论。运营者开新会话，只读这条评论，再手动跑 `to-spec`，同一会话里跑 `/spec-check` 对照清单查 spec。关票后跑 `/wrap-up`，补记冒头和冲突，再跑 `/next` 选下一张票。2026-11-08 补：`/map-gate` 在发布清单之前多一步「查缺口」。新子代理列出会让 `to-spec` 凭空编的缺口，运营者逐条判，点头后才建票。建了票就停，做完再重跑。规则见 `docs/agents/issue-tracker.md` 的「查缺口」一节。

为什么：`to-spec` 只综合当前会话已有的内容，原文没有处理矛盾决定的规则。地图里新旧两个说法并存，它只能自己判断，结果不稳。上游 `mattpocock/skills` 有人遇到同类问题，2026-11-05 读到的状态如下。

| 上游议题 | 内容 | 状态 |
| --- | --- | --- |
| #828 | 一条决定推翻设计后，四张开放票正文还停在旧设计 | 开放，标 `ready-for-human`，等作者定修法 |
| #970 | 已关闭的决定被后来的答案证明错了，索引仍像现行 | 2026-10-07 关闭。原因是提案只来自读文字，没有真实会话案例 |
| #341 | 已定答案经 spec、票、实现逐层变弱 | 开放，等作者定 |

上游没有给出现成办法，所以我们自己定。

本仓的实例：2026-11-06 对地图 #1 只读对账，关闭票 24 张，索引 23 行，缺 #18。#4、#16 的索引行仍写网页方案，没有标已废。

定了什么：

1. 规则写在 `docs/agents/issue-tracker.md` 的「地图上的变动怎么留痕」一节。
2. 五个技能放 `.claude/skills/`：map-gate、wrap-up、next、spec-check、init-trail，都只能手动调用。
3. 上游技能原文不改。

代价：每关一张票多一份扫描表。agent 可能漏贴，靠运营者看关票评论。同样的漏法出现三次，加 hook（钩子，自动触发的检查），拦没有扫描表的关票。

没验证：

1. `.claude/skills/` 会不会被加载。
2. agent 会不会照规则贴扫描表。
3. 整张地图和全部关闭票，一个子代理装不装得下。
4. hook 能不能拦住 `gh issue close`。
5. `to-spec` 面对矛盾决定时到底信哪个。现在靠新会话只读清单评论来绕开，没验证它会不会只读那条评论、不去翻地图正文和关闭票。
6. 清单拆成多条评论后，`/spec-check` 能不能取全。
