读地图 $ARGUMENTS 和它的全部子票，查清哪些决定现在还有效。本技能除第 6 步发布清单评论外，只读。地图和票的修改，等运营者逐条确认后另做。

`/to-spec` 只综合当前会话里已有的内容。会话里放进什么，spec 就写什么。所以本技能的产出是一份只含现行决定的清单，发成地图上的一条评论。运营者开新会话，只读这条评论，再跑 `/to-spec`。本会话里读过新旧两边原文，所以不要在本会话接着跑 `/to-spec`。

## 步骤

1. **对账。** 列出地图的全部子票，开放和关闭都要：`gh api --paginate repos/{owner}/{repo}/issues/<地图编号>/sub_issues`。再用标签补一遍，地图自己除外：`gh issue list --state all --limit 200 --json number,title,state,labels --jq '.[]|select(any(.labels[]; .name|startswith("wayfinder:")))|[.number,.state,.title]|@tsv'`。只在标签里出现、不在子票里的，标“没挂在地图下”，列给运营者，由运营者定挂不挂。数关闭票，再数地图 `Decisions so far` 的索引行。完成条件：每张关闭票都有一行索引。缺的列出票名，标“索引缺这一张”。

2. **起新子代理读全图。** 用 Agent 工具，类型选 general-purpose。新子代理只带提示里写的内容，没见过本会话的任何结论。提示里放：地图正文、每张关闭票的正文和最后一条评论、每张开放票的正文。让它给每张票写一行状态（现行、已废、部分取代），再报四类问题，每条带票名和原文一句：
   - 互相矛盾：两条都读起来现行，但不能同时成立。
   - 旧句仍在：被后来的补丁取代的句子，原句还留着，读起来像现行。常见写法是“旧句不改，以这里为准”。
   - 开放票仍指向旧前提。
   - 已关闭，正文却写着“待产出”。
   完成条件：每张子票都有一行状态，每条问题带原文和票名。

3. **运营者逐条判。** 一次给一条：两边原文、票名、你的推荐。运营者回：仍成立、作废、补问客户。涉及已关闭决定的，由运营者判，你只列。完成条件：问题清单里每一条都有运营者的回答。

4. **出现行决定清单。** 写在对话里，分四段，每段一个小标题。现行决定：每行票名带链接，加一句结论。已废（历史，to-spec 不用）：每行票名，被哪张票取代，一句原因。已废句子：旧句还留在地图 Notes 或仓库文档里、读起来像现行的，每条写出处和一句原文，to-spec 看到就忽略。待运营者定：每行票名，加问题一句。一条决定只出现在一段里。完成条件：对账时数过的每张关闭票，都落进前两段之一。

5. **看体量。** 现行决定覆盖不止一个功能区、一份 spec 装不下时，提议按功能区拆成几份 spec，按依赖排好顺序，请运营者选先做哪一份。

6. **放行。** “待运营者定”一段为空，才发布。发布是把清单写成评论：`gh issue comment <地图编号> --body-file -`。单条评论控制在 400 字内，放不下就按段拆成几条，每条第一行写「现行决定清单 <日期> 第 n/m 条」加一句结论。只发现行决定、已废、已废句子三段，发完读回确认没有缺段。然后告诉运营者：开新会话，第一句写「只读地图 <地图编号> 上最新日期的现行决定清单评论，不读地图正文和关闭票，然后跑 /to-spec」。新会话里 to-spec 如果还是引用了旧句，把那句的出处补进已废句子，重发一组。
