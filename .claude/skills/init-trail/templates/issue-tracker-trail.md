## 地图上的变动怎么留痕

一个决定被后来的票推翻，旧票、旧索引行、开放票的前提都要同步处理。否则 `to-spec` 会读到两个互相矛盾的说法。三个动作管这件事：冒头、关票扫描、开工核对。

规则只写在这一节。技能 `wrap-up` 和 `map-gate` 引用本节，不另抄。引用票时写票名，链接包在票名里，不单写编号。

状态：2026-11-06 起草，没试跑。

### 冒头

冒头指谈话中冒出来、还没落到票或地图里的新需求。

1. 先记一条，附原话。不当场展开。
2. 会话结束前跑 `/wrap-up`，由运营者逐条判去向：新票、并入已有票、未定、范围外、当场做完。
3. 领取了某张票的会话里发现的事，一律归这张地图，不当散票。判据看在哪发现的，和事情大小无关。
4. 建票前先搜 open 和 closed 票，能并进已有票就并。
5. 运营者点头的才建。

### 关票扫描

关闭一张票之前，先在这张票上评论一份扫描表。没有扫描表，不关票。表有五项：

1. 本票结论，一句话。
2. 产出了什么，推迟了什么。产出的文件写相对路径，「查文件矛盾」靠它找旧文件。例：决定了要写 ADR 但没写，下游票的阻塞要保留。
3. 地图下每张开放票和「未定」每一项，各判一档：无关、前提受影响、与结论矛盾、阻塞变化。每行写一句理由。整表只写「无影响」不算数。
4. 地图 `Decisions so far` 每一行，判现行还是已废。
5. 碰到已关闭决定的矛盾，列出来，由运营者判。agent 不自己判。

按判定结果这样改：

| 对象 | 怎么改 |
| --- | --- |
| 开放票 | 原地改正文，删掉被推翻的前提，末尾记一行「按 <票名> 更新」 |
| 已关闭票 | 正文不动，加评论「被 <票名> 部分取代」，写明哪一部分 |
| 地图索引行 | 保留原行，行首标「已废，见 <票名>」 |
| 已关闭的决定被推翻 | 新开一张取代票，旧票不重开 |
| 阻塞边 | 按第 2 项补加或移除 |

上面「完成」一步照此执行：先贴扫描表，再关闭子任务，最后把链接补到「已做决定」。

### 开工核对

领取一张票之后、动手之前，把票里写的前提和阻塞，对照这张票创建以来关闭的票再查一遍。前提变了，先改票，再开工。

查法：`gh issue list --state closed --search "closed:>=YYYY-MM-DD" --json number,title,closedAt`，日期取这张票的创建日。

### 查越界产出

越界产出指本会话做了别张票的活。那张票的正文还写着待做，不处理就会被重做，或和已有成果打架。

范围是本会话领取的那张票，下称本票。没领取票时，问运营者一次。

1. 列产出。本会话改过的文件（含未提交的）、写过的评论、改过的票，每项一行。
2. 逐条归属。每项先对本票的 `Scope`（票正文里编号列出的要做的事），对不上再对地图下其余开放票的 `Scope`。归属分三档：本票内、属于某张开放票、哪张都不属于。
3. 属于别票的，写做到哪一步：全做、做了一半、只定了方向。每行附一句依据，写文件路径或提交。
4. 出表：产出、归属票、占它 `Scope` 第几条、做到哪一步、建议处理。归属票已有负责人的，在表里标出来，另一个会话可能正在改同一处。
5. 运营者逐行回：并入、留在本票、回退、放着。点头的才动票。

建议处理这样选：

| 情况 | 怎么改 |
| --- | --- |
| 全做完，归属票是 `wayfinder:task` | 归属票正文里划掉那条，写「已在 <票名> 做完」，附提交。票保留，验收后再关 |
| 做了一半 | 原地改归属票的 `Scope`：做完的标来源，剩下的缩小，末尾记一行「按 <票名> 更新」 |
| 只定了方向，归属票是 `wayfinder:grilling` 或 `wayfinder:prototype` | 先问运营者：认这个方向吗？认，归属票改成确认票。不认，成果退回本票 |
| 哪张票都不属于 | 按「冒头」处理 |

决策票存在的目的，是让运营者做决定。成果若已经把答案定死，那张票不能悄悄关，要让运营者明确认一次。

点头后，在归属票上评论一条，写哪个提交、做了第几条、做到哪一步。成果留在原提交里不动，不会浪费。改了归属票之后，它挡住的票能不能开工，由「查阻塞边」查。

### 查文件矛盾

文件矛盾指本会话的新决定或新文档，和仓库里已有文件说法相反。地图和票正文对得上，文件之间却留着两份互相矛盾的说法。`to-spec` 会自己翻仓库，读到旧文件，就把旧方案当现行。

范围是本会话的每条新决定，加上本会话新写或改过的文档。

1. 找旧文件。两路并查。一路是被推翻那张票的关闭评论里列的文件，关票扫描第 2 项要求写路径。另一路是拿新决定里的关键词搜整个仓库，跳过 `docs/archive/`。关闭评论没列路径的旧票，只能靠搜。
2. 比对。每个找到的旧文件，读相关段落，和新决定对一遍，判：矛盾、部分矛盾、无关。每行附一句依据，写文件路径和行号。
3. 出表。并进 `/wrap-up` 的冲突表，用「碰到的文件」一列。
4. 运营者逐行回：改、归档、合并、放着。点头的才动文件。

建议处理这样选：

| 文件情形 | 怎么改 |
| --- | --- |
| ADR 或决定类文档 | 原文不动。旧文件开头加「已被 <票名> 取代」，新文件开头加「取代 <旧文件路径>」 |
| 流程文档里的句子 | 旧句保留，句末注「已废，见 <票名>」，沿用地图索引行的写法 |
| 旧文件已无保留价值 | `git mv` 到 `docs/archive/`，原路径的引用同步改 |
| 两份都要留 | 合成一份，由运营者定写法 |

标记写在文件开头，`to-spec` 读到这个文件时先看到。动完文件后，在被推翻那张票上加一条评论，写明哪个文件被取代，下次查得到。

搜关键词只找得到用词相近的矛盾。换了说法的找不到，所以关票时要写全路径。

### 查阻塞边

技能 `next` 只读 GitHub 原生阻塞边排下一步。边挂错，`next` 的结论就错。新票建出来之后，没人回头给更早的开放票补边，所以会话结束前查一次。这一项由 `wrap-up` 执行。

范围是本会话新建、或改过前提的票。含本次 `wrap-up` 建议新建、建议改正文的票，还没建的，现有边写「未建」。

1. 每张票写两件事：它被谁挡，它挡住哪些已有开放票。后一项要对着全部开放票扫一遍，不能只看地图里记着相关的几张。
2. 把票正文里写的阻塞（`Direct blockers`、「等 #编号」、`Blocked by`）和原生边逐张比对。两个方向都查：正文写了、没挂边；挂了边、正文没写。再查边指向的票是否已关闭。
3. 取边：对每张票运行 `gh issue view <编号> --json blockedBy`，不过滤已关闭的，这样才看得出指向已关闭票的边。
4. 比对结果交给运营者判。点头的才补加或移除，加边命令见「常用操作」里的「阻塞」条。

### 关票之后：下一步建议

关闭一张子票、把链接补进「已做决定」之后，运营者最想知道的是下一步做哪张。读阻塞关系很费力，所以由技能 `next` 算出来。第一行给一句结论，后面列能同时做的票。

1. 关票后先跑 `/wrap-up`，处理完它列出的新需求和冲突，再跑 `next`，把结论贴在对话里。wrap-up 可能新建票或改票，next 要等它做完再算。
2. 结论不写进票，不存文件，不打标签。它每次现算，存下来就会过期。
3. 运营者随时可以输入 `/next <地图编号>` 重算。

阻塞关系只认 GitHub 原生依赖。

### 地图清空之后

1. 跑 `/map-gate <地图编号>`，把现行决定清单发成地图评论。
2. 开新会话，只读那条评论，再跑 `to-spec`。
3. 在同一个会话里跑 `/spec-check <地图编号>`，对照清单检查 spec。缺的、写弱的、没有来源的，由运营者逐条判。
