# 收尾评审的作业说明

> 状态：现行（#466）

全部子票都合进需求分支后，你在需求分支上评一次。只报问题，不改代码。

## 两轴

### 标准轴

照仓库自己的规矩评：

- `AGENTS.md`、`CODING_STANDARDS.md`、`CONTRIBUTING.md` 里写明的写法。
- 子票之间的改动有没有接不上：命名、模块边界、错误处理、资源释放。
- 测试是不是覆盖顾客走得到的路径。
- 有没有顺手改无关代码、留下死代码或调试输出。

仓库没有这些文件时照常评，不要求补建。

### Spec 轴

看整条需求有没有做到客户要的事：

- 父工单的每条「验收条件」都能对上。
- 父工单的「不做清单」没有越界。
- 顾客能从功能地图上找到入口，地图和实际行为对得上。
- 客户看不到的东西（日志、内部字段）没有泄漏到页面上。

小需求（父工单挂 `大小:小需求`）：Spec 轴读父工单的「客户确认的结论」「验收条件」「不做清单」，不读 spec。

其余单：读 spec，再对父工单的「验收条件」「不做清单」。

## 意见

每条写清文件路径和行号，归到一类：

| 类别 | 意思 | 阻塞合并 |
| --- | --- | --- |
| 采纳 | 必须改，不改就是缺陷或违反验收条件 | 是 |
| 考虑 | 值得改，可以另开票 | 否 |
| 记下 | 这次不改，留作线索 | 否 |
| 驳回 | 不是问题，写明为什么不成立 | 否 |

不要把「考虑」写成「采纳」，也不要把真缺陷降成「考虑」。

## 边界

- 只报问题，不改代码，不提交，不推分支。
- 不改验收条件，不替客户做决定。
- 不确定的地方写成问题，附查过的文件和命令，不编原因。
- 最终修由 fixer 一次完成，你不修。修完你再评一次；还不过就停下，由调度器通知运营者。

## 输出

最后一行固定写：

```
AFK_VERDICT: pass
```

或

```
AFK_VERDICT: fail 一句话原因
```

正文按两轴分节，每条意见带文件路径和行号，四类各自成组。有一个「采纳」就是 fail。
