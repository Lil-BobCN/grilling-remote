# 拆票 Agent

> 状态：现行

拆票 Agent 读 spec，把一张父工单拆成垂直切片，先出提案。运营者点头后才建子票。

## 什么时候跑

同时满足三条：

- 父工单是 `状态:排队中`。
- 客户仓里有 spec（独立 issue，挂 `ready-for-agent`）。
- 父工单下没有子票。

调度器这时叫你跑 `/to-tickets`。小需求不走这一步，它的实现票由补缺口 Agent 建。

## 读什么

- spec issue 全文。用户故事、Implementation Decisions、Testing Decisions 是拆票的主要依据。
- 父工单正文的 `## 验收条件`。子票的验收条件只能从这里拆。
- 父工单正文的 `## 客户确认的结论`。切片顺序要符合客户定下的先后。
- 客户仓代码。找接缝，看这一片要穿过哪些层。

## 怎么拆

一张子票是一个垂直切片。

- 一片穿过每一层：界面、接口、数据都动到，不做「只建表」「只写接口」这种横切。
- 单独能演示：客户能看见这一片做完多了什么。
- 装得进一个会话：一个 agent 一次能做完，不用跨会话接力。
- 别切太细。演示里 13 张被嫌太细，改成 5 张。票数按需要定，不凑整。
- 宽重构是例外，按 expand-contract 排：先加新写法，再分批迁移，最后删旧的。每一步都能单独合并、单独回滚。

标题写一条切片做完后客户能看到什么，不写实现步骤。

## 验收条件

- 只能从父工单的 `## 验收条件` 逐条拆，原文照抄，不改写。
- 父工单可能写 `- [ ] 条目`，也可能写普通 `- 条目`，两种都读成验收条件。`- [x]` 也读，勾选状态不影响分解。
- 父工单没有 `## 验收条件` 一节时读不到条目。先回父工单补这一节，再拆。不要拿「客户确认的结论」或「不做清单」凑。
- 一条父工单验收条件可以拆给多张票，也可以合并，但不能新造。
- 缺一条可测的验收条件，先回父工单补一条，再拆。不要自己编。
- 子票的验收条件写成一个字符串数组，交给 CLI 校验。数组里只放条目原文，不带 `- [ ]` 前缀。不在父工单里的条目会被拒绝，一张票都不建。

## 阻塞边

- 用 GitHub 原生依赖（issue dependencies），不在别处记。
- 正文照抄一行 `Blocked by: #12`。多张写 `Blocked by: #12, #13`。
- 没有阻塞，`## 阻塞` 整段不写，不留「Blocked by: 无」。
- 只有全部阻塞票关闭，这张票才能开工。正文和原生依赖必须一致；边变了，回来改这一行。

## 出提案

先把接缝和票写成两个文件。

`seams.txt` 一行一个接缝，写这一片穿过的边界，例如：

```text
浏览器页面 / HTTP 接口
HTTP 接口 / 数据库
订单状态 / 取货时间校验
```

`tickets.json` 是数组，一张票一个对象：

```json
[
  {
    "title": "顾客打开链接能看到当天水果和卖完的",
    "verticalSlice": "顾客打开链接，看到今天的水果、价格和卖完的。",
    "acceptance": [
      "打开链接，看到当天水果的名单。",
      "卖完的水果标出来，不能下单。"
    ],
    "blockedBy": []
  }
]
```

`blockedBy` 有两种写法：本批票的标题，或从 0 开始的下标。引用本批以外的票会被拒绝。

生成提案：

```bash
node factory/bin/tickets.mjs proposal \
  --seams /tmp/seams.txt --tickets /tmp/tickets.json > /tmp/proposal.md
```

在客户仓里跑时，`factory/` 不在当前目录。用调度器 brief 里给的绝对路径替换 `factory/bin/tickets.mjs`，形式是 `node <工厂目录>/bin/tickets.mjs`。

把输出写到父工单，作为一条评论：

```bash
gh issue comment <父工单号> --body-file /tmp/proposal.md
```

这条评论第一行是 `提案：拆票`。正文列接缝、票单，一张票一行，带序号、标题和验收条件。运营者会在 Orca 里看这一屏。

提案必须由 `tickets.mjs proposal` 生成，不要自己拼 markdown。命令输出的最后一行是隐藏的票单 marker，写法是 `<!-- factory:tickets 票单 JSON 的 base64url -->`。

调度器在这一跑结束后读父工单最新一条 `提案：拆票`，用票单 marker 校验。marker 缺失、解不开或票单为空，这次拆票作业算失败，按退避重跑。所以贴评论时不要删最后那行，也不要改里面的内容。

**提案阶段只出评论，不建任何子票。**

## 等点头

运营者在 Orca 里确认票单后，用同一份提案建票：

```bash
GITHUB_TOKEN=<token> node <工厂目录>/bin/tickets.mjs create \
  --owner <owner> --repo <repo> --parent <父工单号> --from-proposal --point
```

`--from-proposal` 直接读父工单最新一条 `提案：拆票` 末尾的票单，和调度器校验的是同一份。`--point` 建完写 `点头：拆票` 评论，写明建了几张。不用再单独跑 `point` 命令。

建票时会做这几件事：

- 每张票挂成父工单的 sub-issue。
- 标签只挂 `状态:排队中`。不挂 `ready-for-agent`、`Sandcastle`、`大小:小需求`。
- 按 `blockedBy` 写 GitHub 原生依赖。
- 正文三段固定：`## 垂直切片`、`## 验收条件`、有阻塞时加 `## 阻塞`。
- 不改 spec，不改父工单标签。

## 驳回

运营者要求重拆，在父工单写一条评论：

```text
驳回：拆票 <理由>
```

按理由重拆，改完两个文件，再写一条新的 `提案：拆票`。驳回期间不建票。新的提案和点头会盖掉旧的。

## 重跑

同一个 `create` 命令可以重跑。按标题找父工单现有子票，已有就复用，更新正文和验收条件，不建第二张，已存在的阻塞边不重复加。

## 自检

建票前逐项过一遍：

- 每张票是一个垂直切片，单独能演示，一个会话做得完。
- 宽重构按 expand-contract 排。
- 验收条件全部能在父工单找到原文。
- 标题不重复，阻塞只引用本批的票。
- 提案一行一张票，提案阶段没有建票。
- 提案评论最后一行有 `<!-- factory:tickets ... -->` marker，是 CLI 原样输出。调度器会校验，缺了这次拆票算失败重跑。

建票后核对：

- 每张子票只挂 `状态:排队中`。
- 每张子票都挂在父工单下。
- `Blocked by:` 行和原生依赖一致。
- 没有未关闭阻塞的票就是 frontier，调度器只点火这些票。
