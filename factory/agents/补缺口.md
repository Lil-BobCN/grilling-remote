# 补缺口 Agent

> 状态：现行

一句话：父工单建好后，把回传件的 `map.md` 和决定票搬到客户仓，列出要运营者拍的题；运营者答完并补完地图后，写 `点头：补缺口`。

## 开工前

读 `inbox/<上传 id>/meta.json`。`imported` 数组每项有 `order_id`、`requirement`、`product`、`owner`、`repo`、`issue_url`、`branch`。父工单是 `issue_url` 那张。地图和决定票建在同一个仓。

命令默认读环境变量 `GITHUB_TOKEN`。测试和演练传注入的客户端，不碰真 GitHub。

## 一、建图

建图在父工单建好之后、写 `提案：补缺口` 之前。

### 读什么

- `.scratch/<需求名>/map.md`
- `.scratch/<需求名>/issues/NN-*.md`
- `.scratch/<需求名>/决策记录.md` 可以不读。建图只按 `map.md` 和票文件抄。

### 跑什么

```text
node factory/bin/gap.mjs apply-map \
  --scratch <回传件>/.scratch/<需求名> \
  --owner <owner> --repo <repo> \
  --requirement <需求名> \
  --parent <父工单链接>
```

### 它会做什么

- 找带 `wayfinder:map` 标签、正文含父工单链接的 issue。没有就建一张，标题取 `map.md` 第一行。
- 正文六段照 `map.md` 抄。`Notes` 第一行写 `- 父工单：<链接>`，末尾留 `<!-- factory:parent=<链接> -->`。
- 建 `wayfinder:map` 和四种 `wayfinder:<type>` 标签。地图只挂 `wayfinder:map`；决定票只挂 `wayfinder:<type>`，不挂 `状态:*`、`ready-for-agent`、`Sandcastle`。
- 在父工单 `## 需求全文` 补一行 `- 地图：<链接>`。已经有了不重复。
- 每张 `issues/NN-*.md` 建一张决定票。标题保留编号和名字；正文保留 `Type:`、`Status:`、`Blocked by:` 和 `## Question`；`## 评论` 每段发一条 issue 评论；`## 结论` 和 `产出文件：` 行不进正文，结论留到关票前。决定票挂到地图 issue 下面。

### 格式不对就停

抛 `MapFormatError` 时停下，把错误和文件路径报给运营者。不改回传件，也不手改已经建了一半的 GitHub 内容。

这些情况算格式不对：

- 缺六段中任何一段。
- 两张票编号相同。
- `Type:` 不是 `grilling`、`research`、`prototype`、`task` 之一。
- 缺 `## Question`。
- `接下来` 写到某张票，但 `issues/` 里没有这张票。
- 某张票的 `Status:` 不是 `resolved`，却没写进 `接下来`。

### 重试

同一条命令重跑。它先找地图 issue，再按标题开头的编号配对决定票。已有票换正文、补缺的评论，缺什么补什么。不要手工再建一张地图或第二套票。

### 重传

`to-spec` 前客户整包重传时加 `--mode replace`，留给 #462 接。

- 地图正文按新包换。
- 决定票按编号配对，换正文，追加新评论和结论。
- 新包没有的旧票评论 `作废：重传`，再关。
- 新包新有的票建出来。
- 运营者自己开的票保留，逐张评论 `待复查：重传`。
- 地图 issue 加一条 `重传：<日期>` 评论，列出待复查的票。

## 二、列题

建图之后读这些：

- `.scratch/<需求名>/pending.md`
- `.scratch/<需求名>/需求草稿.md`，有就读。
- `.scratch/<需求名>/验收场景.md`
- 客户工作区根目录 `GLOSSARY.md`，有就读。
- 客户仓地图 issue 的六段和它下面的开放决定票。

### 技术题

`pending.md` 的 `## N 标题` 一节一题。读 `- 题目原文`、`- 推荐答案`、`- 标签`。客户说过「不懂，按你的推荐」的，标签写「客户不懂」，推荐答案照抄。

### 业务题

两处来源：

- 地图 `Not yet specified` 里标了「你答」的行。
- `Status: claimed` 的决定票，题目取票里的 `## Question`。

### 每题写清三样

- 题目：客户能读懂的一句问话。
- 推荐答案：能直接执行的选择。不要写「看情况」「再定」。
- 出处：写 `pending.md 1 小程序用哪家云`、`map.md Not yet specified` 或 `票 02 下单要不要先付钱`。出处按「；」拆开逐段核对；以 `pending.md`、`需求草稿.md`、`问答记录.md` 开头但格式对不上的，停下报运营者；其他写法跳过。

### 闸门检查

提案必须覆盖这些。客户已经答过的，把客户答案当推荐值。

1. 五类技术选择：技术栈、部署到哪、第三方服务与账号、数据怎么存、每月花多少。部署默认「我们管理的香港服务器，客户不用买、不用备案、不用碰 DNS」；只支持默认技术栈。
2. 标了「你答」「你最后定」的题。
3. 合规：收不收个人信息，接不接支付。默认都不。
4. 接缝：测试打在哪一层，理想数量是一个。由你提，运营者确认。
5. 词汇表：先读客户工作区根目录 `GLOSSARY.md`。命名由运营者确认后写进客户仓 `GLOSSARY.md`，只放术语。
6. 查重：先搜 open 和 closed 工单，有重复就报运营者。

## 三、写提案

```text
node factory/bin/gap.mjs propose \
  --scratch <回传件>/.scratch/<需求名> \
  --owner <owner> --repo <repo> \
  --number <地图编号> \
  [--recommendations /tmp/recommendations.json]
```

正文第一行必须是 `提案：补缺口`。接着写「地图已还原：<链接>；剩余项在 map 上。」下面一节技术题、一节业务题，每题写题号、题目、推荐、出处。最后是闸门检查。

小需求没有地图，把 `--number` 换成 `--parent`，提案末尾还要列实现票，见第五节。

业务题没有现成推荐时，先用题目原文作键写一个 JSON：

```json
{
  "送货范围怎么定，超区怎么办": "只送镇上，超区自取"
}
```

用 `--recommendations` 传进去。正文里不要留「（待你定）」。

命令会按正文去重，重跑不会发第二条相同的评论。改了内容再跑，会多一条 `提案：补缺口`；调度器只看最新一条。

## 四、写点头

### 先查地图

写 `点头：补缺口` 之前逐项查：

- 地图 `Not yet specified` 为空。
- 地图下的决定票全部关闭。
- `未定事项.md` 里的每件事都有去处。这个文件代码不读，由你人工核。

没补完不写点头。跑 `point` 会被拒绝，父工单留一条提醒。把拒绝原因报给运营者，等他补完再跑。

### 再写

```text
node factory/bin/gap.mjs point \
  --owner <owner> --repo <repo> \
  --number <父工单编号> \
  --answers '<JSON>'
```

`--answers` 传数组，或 `{"answers": [...], "impacts": [...]}`。正文两段：

```markdown
点头：补缺口

## 最终答案

- 技术栈：Next.js + Postgres
- 第 3 题「服务器放国内还是海外」：海外

## 正文影响

- 「要在线支付」（客户确认的结论）：第 4 题作废，正文未改，以本条评论为准。
```

`## 最终答案` 一行一条，带题号或类别。`## 正文影响` 只在最终答案改掉正文某条时写；没有写「无」。父工单正文不改，答案只进评论。

## 五、小需求

只有 `需求草稿.md`、没有 `map.md`。`apply-map` 返回 `{"skipped":"small"}` 就停，不建图，也不跑 to-spec 和 to-tickets。

### 提案

```text
node factory/bin/gap.mjs propose \
  --scratch <回传件>/.scratch/<需求名> \
  --owner <owner> --repo <repo> \
  --parent <父工单链接或编号>
```

第一行仍是 `提案：补缺口`。技术题从 `pending.md` 列，闸门检查照旧。末尾加一节 `## 实现票`，写标题和逐条验收条件：

```markdown
## 实现票

标题：<父工单标题，也就是客户原话>

验收条件：

- [ ] <逐字抄父工单的验收条件>
```

标题用父工单标题。验收条件逐字抄父工单的「验收条件」，不自己加，不删。

### 点头

运营者在 Orca 里确认后运行：

```text
node factory/bin/gap.mjs point-small \
  --owner <owner> --repo <repo> \
  --parent <父工单链接或编号> \
  --scratch <回传件>/.scratch/<需求名> \
  --answers '<JSON>'
```

命令先建实现票，成功后才写 `点头：补缺口`。建票失败就不写点头。评论正文两段和其余单一样，末行写 `实现票：#N`。

顺序不能反。不要先写点头再补票，也不要先建票再改 `## 实现票` 里的标题。

实现票只挂 `状态:排队中`，正文不写 `## 阻塞`。建出来后调度器把父工单从 `状态:已提交` 改成 `状态:开发中`，直接点火这张票。没有 `提案：拆票` 和 `点头：拆票`。

小需求只点补缺口这一次。上传校验通过、建单后就锁住。客户再加需求或改主意，等这一版交付后开新单，不重开实现票。

## 六、驳回

运营者要求重列时，父工单会有一条 `驳回：补缺口 <理由>`。调度器重跑本 Agent，brief 里会附一节「这次驳回的理由」，抄这条评论全文。

- 先读驳回理由，再读已有的地图 issue、它下面打开的决定票和上一条提案，按理由改。
- 回传件按理由改，再重跑 `apply-map` 更新。地图按父工单链接找，决定票按标题开头的编号配对，换正文、补评论，不建第二套，也不手工另建。
- 父工单正文不改。答案和改动只进评论。
- 改完跑 `propose`，写一条新的 `提案：补缺口`。正文和上一条一样时不发；改了内容多一条，调度器只看最新一条。
- 驳回期间不写 `点头：补缺口`，等运营者看完新提案再确认。
- 小需求没有地图，跳过 `apply-map`，按理由改回传件后重跑 `propose --parent`。

brief 里没有「这次驳回的理由」这一节时是第一次建图，不用找驳回评论。

## 七、报给运营者

以下情况停下，一句话说清卡在哪：

- `MapFormatError` 或任何回传件格式问题。
- 父工单缺 `## 需求全文`，或地图链接补不进去。
- `propose` 或 `point` 找不到父工单、地图链接。
- `point` 被地图检查拒绝，把 blockers 原文贴出来。

不要改回传件。不要为了跑通手工补 GitHub 上的半成品。
