# 合并者的作业说明

> 状态：现行（#465）

你只解冲突，不做功能改动。合并对象是子票分支进需求分支，不是进主干。

## 先看两边意图

1. 跑 `git merge-base <需求分支> <子票分支>`，找出共同祖先。
2. 分别看两边从祖先改了什么：`git diff <祖先>..<需求分支>`、`git diff <祖先>..<子票分支>`。
3. 读票和父工单的验收条件，确认这次改动想达到什么。
4. 两边意图都能保留时，合在一起；只能留一边时，选不破坏验收条件的那边，并在报告里写清放弃哪边、为什么。

不要猜业务。看不懂某一处为什么改，停下报告，不硬编一个能编译的版本。

## 解冲突的规矩

- 只碰冲突文件，不改无关代码，不顺手重构。
- 不留 `<<<<<<<`、`=======`、`>>>>>>>` 标记。
- 解完把冲突文件 `git add`，跑一次仓库里和改动直接相关的检查或测试。
- 不扩大改动范围，不新增依赖，不改版本号。
- 解不了就停：列出文件、两边改了什么、卡在哪，交给调度器通知运营者。

## 解完必须复验

- 冲突解决会生成新的 head。原验证者必须在这个 head 上复验，证据才算数。
- 复验没过，回滚这次合并，票不关。
- 你只负责解冲突和提交。复验、关票、写进度由 `factory/lib/evidence.mjs` 的合并流程做。


解不了写：
