# to-spec 的作业说明

你负责把父工单、地图和仓库里的已确认信息合成一份 spec，发成客户仓里的 issue。

## 读什么

按这个顺序读，冲突时以前面的为准：

1. 父工单正文五段。
2. 最新一条 `点头：补缺口`：先读 `## 最终答案`，再读 `## 正文影响`。
3. 最新一条 `改口：` 评论，有的话。
4. 地图 issue 的六段、决定票和决定票的评论。
5. 仓库文件：回传快照、`GLOSSARY.md`、决策记录、现有代码。
6. `问题树.md` 一律不读。`pending.md`、`需求草稿.md` 平时不读；要回看出处才打开，不改写。

父工单和地图冲突时停下，在父工单写清楚冲突点，不自己挑。

## 写什么

按七字段写 spec，不加第八个字段：

1. `## Problem Statement`
2. `## Solution`
3. `## User Stories`
4. `## Implementation Decisions`
5. `## Testing Decisions`
6. `## Out of Scope`
7. `## Further Notes`

规则：

- 每条客户确认的验收项都要有对应的用户故事，包括只在决定票里出现的行为。
- 非应用产出的交付物写清责任方，例如文档、数据迁移、运营配置。
- 平台部署默认值带进 spec 或引用平台文档：每个成品独立 database 和 role、香港服务器、容器部署。
- 正文不写文件路径和代码片段，交稿前自己检查一遍。
- 地图和代码冲突写进 Further Notes；冲突影响实现时停下，在父工单报运营者。

## 怎么交

1. 先在仓库里查有没有满足以下三条的 open issue：挂 `ready-for-agent`、标题或正文含需求名、七字段齐全。有就停下，不建第二张。
2. 没有就写一份草稿到 `.audit/to-spec-<父工单号>.md`，用 `gh issue create` 发到当前客户仓，标题写成「spec：<需求名>」，正文是七字段，挂 `ready-for-agent`。
3. 不建子票，不改代码，不提交，不推分支。
4. 发完在父工单写一条评论，第一行是「工厂已跑 to-spec：<spec issue 链接>」。
