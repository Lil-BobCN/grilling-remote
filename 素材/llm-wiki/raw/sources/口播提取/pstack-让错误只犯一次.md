## 口播文章

### 同一句话，讲了几遍

这一周，你把同一件事跟 AI agent 说了几遍？它回你一句「你说得对」，把问题改掉。两天后，另一个对话里，一模一样的错又出现一次。

Lauren Tan 不再进行这种对话。8 月，她交付了大约 2,500 个 PR（合并请求），平均一天 80 个。代码由 agent 自己合并。她在 SpaceX 的 AI 团队做 GrokBot，同时参与 React 编译器。Matt Pocock 把她列进了「skill 作者前三」。

整套系统全部公开。它是一组叫 pstack 的 agent skills（技能，一段可复用的 agent 指令）。她最新的那个 skill 瞄准的就是这种对话。

你的网店出了 bug，有时候同一件连帽衫会在购物车里出现两次。你让 agent 去修，它查不出原因，于是加了一行代码，在购物车页面上把重复商品藏起来。旁边还留了条注释：临时方案，可以放心忽略。

测试通过，购物车看着正常，bug 还在。第二周，另一个 agent 在愿望单里也发现重复商品，看到隔壁现成的写法，连注释一起照抄。你把它揪出来，解释一遍，又换来一句「你说得对」。

一个月后，这个临时方案已经住进了 40 个文件。没有比临时方案活得更久的东西。

### 盆栽、铁丝和园艺

Lauren 有个比喻。涌进代码库的提交像一盆疯长的盆栽，往哪个方向长由它自己。你每次纠正，只是剪掉一根枝条。第二天，同一根错枝会在别处长出来，因为 agent 总是照抄仓库里现有的东西。像这样的临时方案，几个星期就能传遍整个代码库。

养盆栽的人不这么干，他们给枝条绑铁丝，让树按想要的形状自己长。Lauren 管这叫园艺。她那 2,500 个 PR 里，很多就是在绑铁丝。

> **思考一下｜用约束替代提醒**
>
> 这段把「纠正」和「约束」分成了两种成本不同的动作。纠正要人反复在场，约束只写一次，之后由机器执行。
>
> **可以追问**：你团队里出现第二次的错误，有没有变成代码里的约束？
>
> **可延展方向**：把「重复三次才值得自动化」的经验法则，改成「重复两次就必须写成规则」，代价是规则会变多，需要定期清理。

### 修正阶梯

铁丝是分档的。最高一档是架构：把代码设计成让这个错误根本无从发生。往下一档是 lint 规则或者测试，让 CI（持续集成）拦住它。第三档是写给 agent 读的 skill 或规则。垫底的一档是让人在 code review（代码评审）里把关。Lauren 给这一档贴的标签是 NGMI，意思是注定做不成。

回到购物车。最高档是修数据的形状：每个商品一行，带上数量字段，购物车从结构上就装不下第二件同款连帽衫。然后把散落各处的临时方案删掉。

第二档是一条 lint 规则，专门标出隐藏重复项的代码，并在报错里指向真正的修法。pstack 里的 fix-root-causes 规则，要求 agent 把每个症状都追到根因，这是第三档。你在 code review 里发现第 40 份拷贝的时候，你就是第四档。

### 为什么光有规则还不够

因为 agent 会抄近路，最好的 agent 也会。pstack 是为这样一种 agent 写的：它只看自己打开过的文件，照抄最近的例子，走能编译通过的最短路径。这样的 agent 读到临时方案和它的注释，注释告诉它这么抄没问题。

所以 Lauren 的做法是，让省事的路就是正确的路。GrokBot 背后的框架做任何事都只有一种方式。每个功能有自己的目录，lint 规则拦下错误的 import（引入）。代码注释被全面禁止，因为 agent 总拿注释给临时方案找借口。

这让人类有点抓狂，但 agent 特别喜欢。

### pstack 怎么跑

pstack 是她每个任务爬这道阶梯的方式。它是 Cursor 的免费插件，内置 50 个 skills。你只需要输入一条命令，poteto mode（以她网名 poteto 命名的一键入口），再加上你的任务。

它会从 23 本 playbook（任务剧本）里挑一本，比如修 bug、做功能、优化性能、发布上线。还有一本是睡前启动，一觉醒来全部合并完成。它把 playbook 的步骤复制成一张待办清单，哪一步需要什么，就调用对应的 skill。

这些 skill 里大约一半是单条规则。比如「先删再加」，比如「两次修复都失败，就去质疑它们共同的那条假设」。

整个循环这样跑。活儿来了，一个 bug 报告、一个功能、一个慢页面。poteto mode 挑好 playbook，agent 复现或者摸清问题，设计修法，写代码。接着在跑起来的应用里证明有效，让别的模型来攻击它，最后发布。凡是出过两次的问题，都会变成铁丝绑进仓库。下一圈从一棵更好的树开始。

大部分活儿不是 Lauren 亲手敲的。GrokBot 盯着她的 Slack、X 和 bug tracker，把新的报告变成跑这套循环的项目。她管这个叫外循环。一个人一个月做出 2,500 个 PR，靠的就是它。

### 拿购物车 bug 走一遍

poteto mode 拿到的是「购物车里商品出现两次，先复现」。这选中了修 bug 的 playbook，第一步要求 agent 自己在运行的应用里把 bug 复现出来。

这活儿以前是 Lauren 自己干的。在有验证类 skill 之前，她是 agent 和 Chrome 开发者工具之间的人肉代理。靠一双手来回搬运 trace（调用记录）。现在 pstack 会替你的项目写一个验证 skill：怎么启动应用，怎么确认它正常运行，怎么把页面点一遍并留下证据。再附一张地图，标清楚每个功能在哪儿。

于是 agent 打开这家商店，双击「加入购物车」，拿到了两件连帽衫。

第二步是找原因，而且不许猜。how 这个 skill 派只读 agent 穿过代码，把这次点击从按钮一路追到购物车。why 这个 skill 翻旧提交和旧对话，把上个月那个临时方案挖了出来。agent 一次只验证一个猜想，拿真实证据说话，直到只剩一个站得住脚的。

双击把请求发了两次，购物车来者不拒，两份全存了下来。playbook 对临时方案也有专门一条：一个也许有用的修法只是一个假设，不许上线。

这次修法牵涉按钮和购物车两边，于是 architect 技能介入。它会先写将来要用到这个修法的代码，再去定类型，而且从不相信单一的设计。

两个 agent 在仓库的两份拷贝里分别设计修法。一个在按钮上挡掉双击，另一个改购物车，让同一件商品装不进两次。另一家 AI 实验室的裁判给两个方案打分，主 agent 采纳购物车方案，也保留了按钮的思路。Grok 负责写代码，Opus 5.5 负责做难的决断。先落进历史的是一个失败的测试：加两次，只该得到一件连帽衫。然后修法才落上去。

agent 回到同一个运行中的应用，再双击一次，看到一件连帽衫。能编译不算证据，一个孤零零的绿灯单元测试也不算。

接下来三个模型轮番来拆。interrogate（盘问）这个 skill 把 diff（改动）分别交给 Opus、Sol 和 Grok。主 agent 把发现的问题分成四类：采纳、考虑、记下、驳回。

在全自动模式下，pstack 给每个 PR 派一支验证 agent 小队。它们像真实用户一样在应用里点来点去，专门抓回归，找到就修，修完再来，直到这个 PR 能落地。

### 谁来验收

那这些代码谁审？合并之前，一位裁判、三个模型、一支验证小队。合并之后，是 Lauren 本人。

她每天早上读提交历史，像主厨没法尝遍每一盘菜那样，抽一部分来品尝。如果两个 agent 走了同一条近路，她就加一道铁丝。

第一次放手让 agent 自己合并的那个晚上，她怕生产环境会被弄挂。现在她睡得踏实多了。

> **思考一下｜验收的成本被挪到了哪里**
>
> 验收没有消失，只是从「逐行读代码」变成「读历史、抽样本、加规则」。人的注意力从执行端挪到了规则端。
>
> **可以追问**：抽样的比例由什么决定？抽不到的那部分靠什么兜底？
>
> **可延展方向**：把主厨试菜的抽样逻辑，对照软件发布里的金丝雀发布和错误预算，看哪些环节可以借用。

### /correct：错两次就算模式

她最新的 skill 把循环补上了一块，叫 correct。它读你近期的提交、回滚和 code review 评论，找出 agent 反复在犯的错。错两次就算一个模式，我们那个「藏起重复商品」的临时方案，足足超标了 40 次。

然后它从阶梯顶端开始爬：先做出让重复商品不可能存在的购物车结构，再把每一份临时方案删干净。架构搞不定的，动用类型；类型也不行，就写一条报错信息里直接点名修法的 lint 规则；再往后是测试，文档排在最后。

每一条新检查，都必须在历史里真实发生过的错误上亮红灯。于是新的 lint 规则拿上个月的临时方案一跑，果然红了。它还在 agent 指令里维护一张表，记录每条规则靠什么来落实。

同一天，architect 技能也学会在这些陷阱建成之前把它们认出来。陷阱有三类：同一件事有两种做法，需要手工同步的列表，谁都能 import 的内部模块。拿旧版本做盲测，它的设计得分在 8 分制里高出了大约 1 分。

这套 stack 还在越变越短，这点我没想到。9 月，Lauren 先删掉 34 条指令，这些都是 Opus 5.5 不用叮嘱也会遵守的。删第二批之前，她拿 154 个植入缺陷做 A/B 测试。没有这些指令时，review skill 抓到 142 个；留着指令，只抓到 139 个。

背后的规则一张便利贴就写得下：一条经验如果能变成 lint 规则、检查或者脚本，就把它写进代码，把那句指令删掉。agent 是从它脚下这个仓库里学习的，所以经验应该活在仓库里。

> **思考一下｜指令和代码的分界**
>
> 「能编码的就别写成文字」听着像工程洁癖，实际是在选谁来执行。指令靠模型自觉，规则靠机器强制。
>
> **可以追问**：哪些经验没法编码，只能留在文字里？
>
> **可延展方向**：把这条规则用到写文档、写 SOP 上，看哪些条款其实可以变成检查项。

### 结尾

那么，那个临时方案你还要跟 agent 讲多少遍？

一次。Lauren 的 agent 还是会犯错。但她见过两次的错误，每一个都会变成一道铁丝：一个装不下重复商品的购物车，一条直接指向真正修法的 lint 报错。下一个撞上怪 bug 的 agent，会发现无路可抄。

树还是在疯涨，只不过现在按她的形状在长。

我是 Kevin。AI 或科技圈有新东西，我都会在这儿拆开看看，告诉你值不值这波 hype。订阅，下期见。

## 综合解读

全片的论证是一条链。agent 会照抄仓库里最近的样本，所以人的口头纠正只清掉一处，错枝会在别处长回来。要让错误只犯一次，就得把纠正变成代码里的约束。约束有高低之分，越靠结构越省事，靠人审最费事也最不可靠。pstack 把这道阶梯做成了日常流程，/correct 则把「同一个错出现两次」自动升级成规则。

这条链成立有几个前提。代码库得足够统一，一种做法只有一个目录，lint 才拦得住。CI 要快，否则规则会拖慢每一轮。模型要读得懂 lint 报错，并照着改。PR 的数量要大到一个一个人审不过来，这套流程才显出收益。Lauren 的场景同时满足这几条，换到小团队，收益可能抵不过维护规则的成本。

片中数字都来自视频陈述，未经独立核验。8 月约 2,500 个 PR，每天约 80 个。临时方案扩散到 40 个文件。154 个植入缺陷，抓到 142 个对 139 个。盲测高出约 1 分。9 月删掉 34 条指令。购物车 bug 和那 40 个文件是动画里的示意。B 站简介明确写了不是真实 run，不能当成案例数据引用。

还有一处归属待核对。这支视频说劳伦在 SpaceX 的 AI 团队做 GrokBot。另一支 MTS 访谈里，她和同事都自述来自 Cursor〔待确认〕。

还有一处边界值得留意。「人审垫底」说的是别把人审当第一道防线，不等于取消人审。Lauren 自己每天早上读提交历史，仍然在抽样把关。片子把这一段放在「谁来验收」里，容易被读成「agent 自己合并就不用看了」。实际正相反：验收从逐行看代码，搬到了看历史、看模式、加规则。

可迁移的素材有三个。第一，把「同一个错出现两次」当作立规则的触发条件，别再继续解释。第二，禁掉代码注释这种给临时方案免责的载体，逼着理由写进结构或规则。第三，先想办法把经验编码成检查，再删掉对应的文字指令，用 A/B 验证删了以后有没有变差。
