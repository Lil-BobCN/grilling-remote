## 口播文章

### 生成一个没有正文的草稿 PR

我猜你已经很想试新的 PR 技能了，那就来吧。我们跑 `npm run create-pr`。这是我在环境里额外加的一个小东西，它会基于我们的一个提交创建一个 PR。跑起来会走几步。看起来我之前已经跑过，所以它已经存在，问我要不要替换。要，没问题。

可以看到我们现在有一个草稿 PR，叫 `seed bookmarks notes diff`。看看它，它创建了一个新的 base 分支，也就是我们要合并进去的分支；还有一个 PR 分支，带着我们要合并的额外提交。可以看到所有改动的文件。看 files changed，能清楚看到改了什么，就像真实仓库里的真实 PR。

唯一缺的是 PR 正文，还没写。所以我想请你做的是：拿到这里的 PR 号，我的是 34。然后进入 agent，让它根据 diff 重写 PR 正文。开始前确认你能访问 `pr` 技能的 Markdown 文件，希望它会自动被读到，你不需要手动调用，然后它会给你写一份漂亮的 PR 正文。

### 按三段模板检查

写完之后，试着用伪代码和它生成的描述，理解 diff 里发生了什么；再看它找到的证据，确认改动真的在工作；然后看 merge danger，判断这是单向门还是双向门。从这里你能看出自己会怎么改进它，喜欢什么、不喜欢什么，因为 PR 技能本来就是给你改的，用来适配你自己的流程。

它其实只是我对「PR 正文该长什么样」的一次尝试。记住，目标是速度：让评审更快，同时判断这个 PR 到底需要多少评审。祝你好运，解答集见。

> **思考一下｜先读摘要还是先读 diff**
>
> 模板故意让人先读可视化摘要和证据，再看 diff。顺序本身就是一种评审策略。
>
> **可以追问**：如果摘要和 diff 不一致，应该以哪个为准？
>
> **可延展方向**：把「摘要与 diff 不一致」列为评审的第一个检查项。

## 综合解读

这一集是练习说明，不是论证。可迁移的是：PR 正文先由 diff 生成，再按「摘要、证据、风险」三段检查。

成立前提：项目有 `create-pr` 脚本；PR 技能能被 agent 自动读取；PR 有可对比的 base 分支。

待核验主张：没有需要外部核验的事实。

边界：草稿 PR 的 diff 可能很小或很偏，练习时要选一个能体现三段模板价值的提交。

可迁移素材：从一个提交生成 PR；让 agent 按模板重写正文；按三段逐项检查；把技能改成自己的偏好。
