## 口播文章

### 抽屉和 Markdown 文件都会自己长满东西

如果你给我一个抽屉，我迟早会把它塞满电线；如果你给 agent 一个 Markdown 文件，它迟早会把它塞满垃圾。

在项目里，我们会跑 `npm run reset`，切到一个叫「seed bloated glossary」（种一份膨胀术语表）的提交。我会重置当前分支，然后我们会看到 `glossary.md` 发生了一些变化。这里多了一个 `other terms` 部分，里面有各种东西，可能属于术语表，也可能不属于。所以这一课的任务是修剪这份术语表，并找出应该怎么修剪的规则。

这对任何 Markdown 文件来说都是很自然的事，尤其是仓库里变动很多的时候。如果你不小心，尤其是团队里有人不使用这些技能，你就会看到很多内容被加进这个文件。而且我在这里加的沉积物还算 modest（温和）。我见过几百上千行的术语表，里面很多词根本没人用。所以能把它修剪下来，是用领域语言工作的必备技能。

你的任务是打开 agent，做一次 `grill with docs` 会话，让它把术语表修剪到只剩我们需要的东西。做完之后，我们应该得到一份锋利、可以继续使用的术语表。祝你好运，解答集见。

> **思考一下｜为什么 agent 爱往术语表里加东西**
>
> agent 倾向于把「它读到的所有概念」都当成领域词，尤其是实现细节。文件越大，它越容易继续加，因为已有内容看起来像先例。
>
> **可以追问**：术语表应该由谁负责删？人、agent，还是每次会话结束时自动跑一遍？
>
> **可延展方向**：给术语表加一个「最近使用时间」字段，长期没人引用的词自动进入待删列表。

## 综合解读

这一集是练习说明，不是论证。可迁移的是把「修剪」当成术语表生命周期的一部分，而不是一次性建好就完事。

成立前提：术语表已经膨胀；agent 能读整个仓库并判断哪些词被使用；人愿意逐条裁决删留。

待核验主张：作者说见过「几百上千行」的术语表，这是个人见闻，没有样本或数据。

边界：修剪过度会删掉将来需要的词；修剪不足则文件继续膨胀。作者没有给出量化标准，只说结果应该「锋利」。

可迁移素材：定期 reset 到一个已知的臃肿状态做练习；把「实现细节」和「通用编程词」列为默认删除对象；修剪后立刻用新术语表检查 ADR 和代码注释。
