## 一句话摘要

作者用一个一次性分支里的 Knock 原型，逐项验证签名 token、通知投递、已读/未读、选课通知和偏好开关。过程中卡在 Knock 的偏好设置界面，最后发现这个默认值可以由 Cadence 自己写入，不需要在 Knock 里配。原型关票时留下了主发现和一堆坑，供后续实现参考。

## 口播文章

### 开场：原型是 Wayfinder 里最有意思的部分

好，开始做原型。我告诉你一个秘密：我特别喜欢用 Wayfinder 做原型，这是 Wayfinder 里我最喜欢的部分。这里你能真正看到东西活起来，能以很高保真度和 agent 沟通。我不知道，它就是让后面的一切都变得更好。

好，它已经认领了 `prototype` 技能，要在真实应用里建一个一次性路由，测试全部四项检查。它现在会去看 Knock 文档，弄清楚实际要做什么。它还装了 Node SDK（软件开发工具包）。我觉得可以开始了。我猜它也拉取了之前关于 Knock 的研究，完全知道这里要建什么，因为所有这些都通过 Wayfinder 地图链接起来了。

这是 Wayfinder 很酷的一点。手动做 grilling 和原型时，你总得想着保存信息，确保不在错误的时机清掉上下文。但用 Wayfinder，你做的所有决定都回到地图里，就在那儿。像这样的新会话可以直接拉取需要的东西，非常省 token。

### 第一项检查：签名 token

好，它回来了一些东西。它在一次性分支 `prototype/knock-spike` 上建了 spike，并帮我们跑了 dev server，运行在 `localhost:5199`。它引用了票里需要检查的东西。检查一，签名用户 token，看起来通过了：只用 public key 和 token，第二个用户能读自己的 feed，很好。但检查二到四在等我，看起来我需要去 Knock 里设置一些东西。

我知道我要做什么了。能不能给我建一个向导，设置检查二到四需要的东西？你看，我懒，我有别的事，我还要刷 Twitter。我不想自己点来点去。这就是模型可调用技能的好处：我可以直接说「给我建个向导」，不用手动调用，agent 会自己去拿。

好，我们有了一个新向导：`prototype knock wizard`。我打开一个新终端，在这里跑。浏览器在右边，向导在左边，开始。

### 在 Knock 里建工作流

它说我要创建一个 workflow，我命名为 `discussion reply`。创建好了，现在可以加分类，我加一个 discussion 分类，点保存。然后应该会打开 workflow builder。打开了，我加一个 channel step，选 in-app feed，再选 `cadence feed` 频道。看起来就是右下角这个 in-app feed，点它。现在打开 steps template，把 markdown body 设成这段，我复制过去，直接按 markdown 编辑内容。好，保存更改。希望到这里就结束了。哦不，保存后还要在右上角 commit 到 development。看起来对了，提交到 development。好，应该可以了。

看下一步。哦不错，它实际检查并触发了。我喜欢它真的验证我做的事。现在要建一个新 workflow：new enrollment workflow。我做同样的事，打开 steps template，把 markdown body 设成这段。总的来说，我很高兴用了向导，不然自己点会很痛苦。提交、可触发，按回车继续。

现在下一步说，在 platform preferences 里加 workflow 分类 enrollment，然后在下面把 in-app feed 频道关掉。好，屏幕看起来有点乱。我得找 workflow category enrollment。在这里，preferences、enrollment，看起来像，或者不，也许我要去 defaults。

### 卡住：不知道 Knock 的偏好界面怎么操作

现在我真的不知道我们在干什么了。我就到处点一点，看看能不能弄好。好，我完全迷路了。

所以我回到 agent，抱怨向导不够清楚。我把整个阶段复制粘贴进去，让它有完整上下文：我到了这个阶段，但操作不了 Knock 的界面，你能帮我吗，或者用程序化方式做？现在确实到了这个阶段：我也可以让一个 bot 用 computer use 去点，但理想情况下我想自己开通这些东西，因为我担心把可能产生费用的资源完全交给 agent。不过也许我得克服这个。

好，我想我弄明白了：在这里，这是 preference center。你创建 enrollments 的 preference options，启用之后可以开关渠道类型。右边有 manage preferences 屏幕，可以开关东西，这和 enrollment notifications 分类有关。我可以保存，然后也许去 defaults。但实际上我还是不知道改默认值。所以只走了一半。我至少告诉 agent 我走到哪了。

我觉得我在 preference center 里给 enrollments 分类建了一个 preference，但改不了它的默认值。看看它怎么说。它现在根据我的密钥做一些验证，挺方便。

当然，我们在这里做的所有事、感受到的所有挫败，都是对「Knock 是不是合适产品」的有效验证。这就是原型的作用：感受产品，确认它符合我们想让它做的事。看起来它找到了一个方案：我们不需要在 Knock 里设默认值，因为 Cadence 可以设置。当 Cadence 把讲师同步到 Knock 时，会把 enrollment 的 off 写进他们的偏好，选择加入就翻成 on。我觉得这没问题，因为这样 Knock 里就少了一个要操心的屏幕。所以它说可以跳过向导第三步，然后基本就完成了，可以开始操作原型。

好，听起来不错。呼，希望我们不用再点 Knock 后台了。这出乎意料地难搞。你能看出我不是 Knock 赞助的吧？

### 原型的捷径和生产代码的区别

值得说一句：`prototype` 技能里，它被要求走捷径，不用管生产级代码。所以你会看到这种：它写了 try/catch，但忽略所有错误，基本是 `catch null`，意思是如果失败就忽略。这通常是我在评审里会抓到的，或者期望代码评审抓到的。但对原型来说，不重要。

好，我们去看原型。这个原型是一堆可以点的按钮，用来观察会发生什么；它不负责回答行为对不对。我们以 Liam Thompson 登录。能不能切换？可以，切到 Sarah Chen，不错。先留在 Liam Thompson。

左边有一些按钮可以触发讨论回复。它给了我们要跑的具体检查清单。从 Sarah Chen 开始，点 Emma Wilson 问题的回复，然后切到 Emma，应该大约三秒内出现。我来做。切到 Sarah Chen。我不确定哪个按钮是回复 Emma 的，所以我就把所有回复按钮都点了。可以看到 headless feed 在刷新。切到 Emma Wilson 看看有没有东西。看起来什么都没发生。

所以我问它：作为 Sarah Chen，我看不到回复 Emma Wilson 问题的按钮；我点了所有回复按钮，都没用。又是一次很棒的粗糙 QA。看起来原型里有个实际错误。它回来给了一个更新后的操作序列。

### 第二项检查：通知投递和已读/未读

好，我以 Sarah Chen 登录，通知 Olivia Martinez，按这个。然后以 Olivia Martinez 登录，在她的 headless feed 里应该看到通知。终于，看到它工作了。我可以点这个标记为已读，也可以标记未读，或者全部标记为已看。不错。但 mark all seen 按钮好像不工作。我告诉 agent：我以 Olivia 登录，按 mark all seen，不工作。

那边在跑的时候，我做第四项检查：以 Olivia 或任何学生登录，点 enroll and notify Marcus Johnson。我以 Olivia 登录，然后通知 Marcus Johnson。切换到 Marcus Johnson，看起来对，他收到了 Emma Wilson 的新选课。但我看到「enroll notify Marcus Johnson」时，Marcus 应该什么都收不到，正是我们看到的。然后以 Marcus 身份，点 opt in enrollment，按钮就在下面，点了之后应该已经选择加入。现在切到 James Park，enroll and notify Marcus Johnson。再切回 Marcus Johnson，可以看到 James Park 的新选课。这部分工作正常。

### 第三项检查：偏好开关

好，它回来了一些信息。看起来它看起来坏了，是因为把项目标记为已看并不会让它们变成已读，只有已读项目才会变暗。Knock 里 seen 和 read 是两回事。为了帮你省点脑力，我已经把这三项验证过了。

哇，这是一大轮 QA、大量验证。我觉得我们达到了一个还可以的状态。这些原型 UI 用起来可能很乱，这其实是它们的目的：给你大量按钮，让你折腾功能、试着弄坏它、看逻辑怎么失败。我觉得我们有了一个足够稳的东西。

### 关票：把发现写回地图

我回到 agent，说：好，我对这个原型挺满意，QA 做得差不多了，把学到的东西存回地图。我们现在大约 10.7 万 token，这在预期内，智能区里还有一点空间可以继续迭代。但现在，我觉得我们证明了来这儿要证明的东西。

好，它关闭了原型票。看 resolution 评论。原型的主要发现是「默认关闭」这件事，而且现在是由 Cadence 设置的，不是 Knock 的设置。它还给后面的票留了一些坑。它把我们学到的一切、试过的一切都带回来了。这会成为实现 agent 的丰富上下文。换句话说，接下来实现这个功能的 agent 会很轻松，它有整个实现可以参考，还有我们在原型里发现的所有坑。

我们基本上做了传统敏捷开发里说的 spike：先把难走的路走一遍，让后续开发变容易。干得好，下一集见。

> **思考一下｜「操作卡住」也是验证结果**
>
> 作者在 Knock 偏好界面迷路，这本身说明产品对使用者的理解模型不清晰。他把挫败感当成对产品是否合适的证据，而不只是操作事故。
>
> **可以追问**：怎么区分「我不会用这个产品」和「这个产品不适合我们的场景」？
>
> **可延展方向**：在原型票里单独记一栏「操作摩擦」，包括卡住的地方、需要查文档的地方、需要猜的地方。

> **思考一下｜原型里的捷径要不要记录**
>
> 原型故意忽略错误、走捷径。作者说这些在评审里会抓，但原型不重要。关键是别让原型代码流进生产。
>
> **可延展方向**：给原型分支加一个 README，列出所有故意走的捷径，实现时逐条替换。

## 综合解读

论点链：原型票用一次性分支建 spike；先验证签名 token，再验证通知投递、已读/未读、选课通知和偏好开关；操作 Knock 界面时卡住，反而验证了产品契合度；发现默认值可以由 Cadence 写入，跳过 Knock 配置；关票时把主发现和坑写进 resolution，成为实现阶段的上下文。

成立前提：Knock 提供可用的开发环境和 SDK；原型能跑在本地 dev server；agent 能读票、研究结果和地图；人愿意手动操作第三方后台。

待核验主张：Knock 的 seen 与 read 语义、偏好同步方式、web push 依赖，都是作者在这次运行中观察到的行为，可能随版本变化；「10.7 万 token 仍在智能区」是作者对会话状态的感受；`catch null` 的代码细节是作者对原型代码的描述，若要引用需看实际分支。

边界：原型不验证性能、安全、错误恢复和多用户并发；「操作摩擦」可能来自作者不熟悉产品，而不是产品本身的问题；原型结论需要实现阶段重新验证。

可迁移素材：用一次性分支做 spike；按检查清单逐项验证；把操作摩擦当成产品证据；关票时记录主发现和坑；原型代码不合并，生产实现重写。
