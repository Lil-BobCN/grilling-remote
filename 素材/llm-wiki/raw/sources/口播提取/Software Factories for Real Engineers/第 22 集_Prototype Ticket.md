## 口播文章

### 九张票做完五张，开始做原型

好，九张票里我们做完五张了，我感觉大概不会再增加太多票。下一张我想做的是原型票：Knock 能不能撑住 Cadence。我们现在已经开通了 API 密钥，准备做原型了。

原型的意思是，这是一个以更高保真度看我们正在做的东西的机会。高保真度很酷的地方是，你的反馈质量会很高。所以原型票的关票条件是所有决定都整合进去、原型看起来是你想要的样子；原型做完并不等于可以关票。

所以我希望这些会话在 token 上花得比较多。我们会真正烧掉一些 token，做一次正经的 vibe coding，直接说「不，我不喜欢这个，给我那个」，直到我们的决定出现在代码和原型里。

我们会回到 agent，清掉上下文，然后跑 `Wayfinder`，把这张票传进去。

### 原型按研究产物的方式保存

要记住一点：这些原型的工作方式有点像研究，我们会像保存研究文件一样保存它。回看之前的研究文件「哪个托管通知服务商适合 Cadence」，resolution 在评论里，但完整发现放在一个随机分支里的 Markdown 文件中。这个随机分支本地 agent 可以访问，可以去探索、拉文件，但它不在主检出里。原型也一样：原型放在主检出之外的一个随机分支里。这样 agent 可以引用它，但不会把它误当成真正的代码。

这就是这次练习你会看到的东西。祝你好运，解答集见。

> **思考一下｜原型为什么不算生产代码**
>
> 原型里的错误处理、命名、结构都可能是临时的。放进主检出，agent 会把它当先例；放进一次性分支，它只是参考资料。
>
> **可以追问**：原型里验证过的交互，怎么迁移到生产代码，而不是把原型代码直接搬过去？
>
> **可延展方向**：给原型分支定一条规则：只读不合并，生产实现必须重写。

## 综合解读

这一集是练习说明，不是论证。可迁移的是：把原型当证据，而不是当实现；原型票的完成标准是「决定都被验证」，不是「代码能跑」。

成立前提：API 密钥已经开通；原型可以放在独立分支；agent 能引用分支里的文件；团队接受原型代码不合并。

待核验主张：「高保真度会带来高质量反馈」是作者的经验判断，取决于原型做得够不够真。

边界：原型做得太精细会浪费 token；做得太粗糙又验证不了交互。原型不处理生产级错误、安全和性能，这些要留给实现阶段。

可迁移素材：原型票的完成标准写成「所有决定已验证」；原型代码放一次性分支；resolution 写结论，完整细节放文件。
