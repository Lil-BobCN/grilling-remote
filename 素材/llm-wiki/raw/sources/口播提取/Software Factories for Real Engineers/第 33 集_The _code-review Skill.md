## 口播文章

### 自动评审做得还不够

我们看了一点人工评审，现在看自动评审。在我看来，大多数团队的自动评审做得不够。自动评审是一种非常好的、非常省 token 的节省人力的方式。

理论是：工作从自动检查流到自动评审，最后流到人工评审，每过一个阶段质量都上升。到你进行人工评审时，你希望代码已经尽可能好。换句话说，你不想浪费人的精力去评审垃圾代码。

你可能想问：为什么要做自动评审？不能让实现者第一次就做对吗？我在速成课里讲过一点，这里再讲一遍。实现 agent 有很多工作：探索代码库、实现、调试。而如果你清掉上下文，对产出的 diff 做代码评审，评审 agent 不需要找 diff，不需要探索，diff 就在那儿，已经在代码库的正确位置。它没有任何文件真的需要改。你可以给评审 agent 加载大量指令：我们需要调整这个、做那个、找这些模式并报告。

### 自动评审在子代理里跑

值得说一句，通常的做法是：你在跑实现会话，然后从实现里调用代码评审，代码评审在子代理里跑。换句话说，它当场得到一个全新的上下文窗口。

怎么给这个评审 agent 加载指令？看 `code-review` 技能，里面设置了标准来源：它读 `coding-standards.md`。也就是说，任何你想在自动评审阶段识别的东西，都可以放进 `coding-standards.md`，评审技能会找到它。

其实在这个时间点的仓库里，已经写了一些编码标准。比如：不要写 `any`；不要用 `!`，这是为了阻止它在 TypeScript 上作弊；失败时抛出响应，而不是返回值；用 schema 校验不可信输入。都很合理，模型状态好的时候可能本来就会这么做，但自动评审是多一层防线。

### 为什么把标准藏在评审里

很多人会把这些编码标准放进 `AGENTS.md`，这样代码库里的每个 agent 都会读到。但老实说，我不介意对实现 agent 隐藏这些标准，至少不主动推给它。这意味着实现 agent 可以自由地产出一个粗糙的草稿，然后代码评审带着 `coding-standards.md` 里的额外要求，来把它打磨好。换句话说，实现只负责让它能跑，评审负责让它变好。

希望你现在更理解我为什么喜欢把实现和代码评审分开，也理解你能用哪些方式影响它们的行为，尤其是怎么随着时间改进自动评审。下一课我们会试用代码评审，看看能不能改进这个 PR。干得好，下一集见。

> **思考一下｜实现和评审的职责分离**
>
> 实现 agent 同时探索、实现、调试，上下文已经很重。评审 agent 从干净的 diff 开始，只负责找问题。
>
> **可以追问**：如果实现 agent 不知道编码标准，它会不会反复犯同样的错，浪费更多 token？
>
> **可延展方向**：把高频错误写进实现阶段的简短提示，把长尾规范留给评审阶段。

## 综合解读

论点链：自动检查之后需要自动评审；评审 agent 有干净上下文和现成 diff，比实现 agent 更适合做质量打磨；`coding-standards.md` 是评审的规则来源；实现和评审分开，前者求能跑，后者求变好。

成立前提：项目有 `coding-standards.md`；评审能在子代理里跑；实现和评审的上下文可以分开；团队接受评审阶段修问题。

待核验主张：「大多数团队自动评审做得不够」是作者判断，没有数据；「评审比实现更省 token」取决于项目规模和评审范围；「实现 agent 不需要知道标准」是策略选择，可能增加返工。

边界：如果实现 agent 完全不知道标准，可能产出偏离太远的草稿；评审 agent 也可能漏掉跨文件的设计问题；`coding-standards.md` 太长会稀释注意力。

可迁移素材：实现与评审分开；评审在子代理里跑；用 `coding-standards.md` 做规则来源；把标准放在评审侧而不是实现侧，按需调整。
