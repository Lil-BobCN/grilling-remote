作者把软件工厂的「刹车」分成三层：自动检查、自动评审、人工评审。自动检查只花 CPU，可以大量加；自动评审由 agent 驱动，还有很大挖掘空间；人工评审要解决的问题是看多少、什么时候看。

## 口播文章

### 软件工厂像开车，先学刹车

我们现在知道怎么和 agent 达成一致，也知道怎么规划大块工作，开始走向「软件工厂」。但软件工厂有点像开车：学开车时，第一件事要学什么？是学怎么把车慢下来。如果你只关注怎么加速、怎么推进软件工厂，最后会造出一个巨大的 slop cannon（垃圾喷射器）。我们需要找到减速的方法，提高交付质量，避免把自己烧干。

我觉得软件工厂里有三个主要的刹车，也就是让车慢下来的东西。我在速成课里简单提过，但这里想认真讲一讲。

### 第一层：自动检查

首先是自动检查，也就是确定性的代码质量检查。包括单元测试、类型检查、linter，以及各种可以叠在应用上的检查。这些非常有用，因为它们只花 CPU 周期，不花 token。所以你真的可以放开手，堆大量自动检查，确保 agent 做的是你想要的事。

### 第二层：自动评审

在自动检查之上是自动评审。这个不一样，因为它由 agent 驱动。我们已经见过一点：`code-review` 技能在 cohort 里用过，也在上一节的 `implement-spec` 技能里跑过。但自动评审还有很多油水可以榨，我们很快就会重点讲。

### 第三层：人工评审

最后一层当然是人工评审，真正的人来看代码。这一节我们会重点讲下面两层：自动评审和人工评审。自动检查会在后面的反馈循环那一节讲。

我们会看各种改进人工评审的方法：你到底该看多少代码、在什么情况下看、什么时候用人工评审来改进自动评审。理论上，自动评审可以开始做更多，人工评审可以开始做更少。希望学完这三层之后，我们能在软件工厂开始出货的同时踩住刹车，把质量保持住。干得好，下一集见。

> **思考一下｜三层刹车的成本结构**
>
> 自动检查花 CPU，自动评审花 token，人工评审花人的注意力。三者的稀缺程度不同，所以优化顺序也不同。
>
> **可以追问**：如果自动评审很贵，应该先加自动检查，还是先减少人工评审？
>
> **可延展方向**：给每层刹车记录「拦住了什么」和「误报率」，用数据决定加哪一层。

## 综合解读

论点链：软件工厂不能只会加速；需要三层刹车；自动检查最便宜，可以大量加；自动评审由 agent 驱动，还有优化空间；人工评审要解决注意力的分配问题。

成立前提：项目有可运行的测试、类型检查和 lint；agent 能跑自动评审；人愿意根据风险分配评审时间。

待核验主张：「自动检查只花 CPU、不花 token」在本地跑成立，但 CI 时间和维护成本仍然存在；「自动评审还有很多油水」是作者判断，取决于工具和项目。

边界：自动检查只能验证已经写出来的规则；自动评审可能产生误报和漏报；人工评审仍然是判断产品方向和风险的最后一道。

可迁移素材：把质量手段分三层；优先加确定性检查；用人工评审的发现反过来改自动评审；按风险分配人的注意力。
