## 口播文章

### 人工评审：四条具体意见

好，我们来做一次正经的人工评审。

我看到的是 sidebar 组件，这里有个标签叫 `saved`，会跳到书签页面。我觉得 sidebar 里的东西不应该写 `saved`，应该写它实际去的功能名。我要试着把它说得容易变成编码标准：`saved` 这里感觉不符合我们的术语表。UI 里任何东西都应该用术语表里的词，比如 bookmarks 或 notes。我把这条评论留下。

往下看，`bookmarks.server.test.ts` 里创建了一个 test DB 类型。我觉得它应该放在更全局的地方。我在这里留评论。

测试里的 `beforeEach` 块有个我不太喜欢的地方：这些测试的 setup 没有用我们模块里的实际函数，直接用数据库原始操作。做测试 setup 时，应该确保通过模块已知的函数来做，不要直接调数据库。这样如果以后想换数据库访问方式，测试基本不受影响。

再说一次，这只是我的个人意见，是我过去写代码的方式。所以把它交给 agent、至少让它有个概念是合理的。

我更喜欢上面那种评论不存在。注释很容易和代码一起过期。我更希望代码本身更明显。我特别烦那种只是解释函数在做什么的注释，尤其是函数很简单的时候。

这里我再秀一点领域知识：我们应该在类型系统里区分纯文本和 Markdown。这样每个函数都知道自己该期待什么，也能从类型系统得到更多帮助。Branded types（带标记的类型）很好玩。不知道的人，我以前是，嗯，现在也算是 TypeScript 专家，以前教 TypeScript。所以能秀肌肉就秀一下。

好，我对这些挺满意。我留了四五条评论，看起来可以。现在跑 retro，复盘所有参与创建 PR 34 的会话。

### 运行 retro

`retro` 做的一件事是立刻加载 `writing-for-agents` 技能，因为这个技能告诉它怎么设计好技能、怎么写 `AGENTS.md`、怎么判断它在仓库里看到的东西。这是非常重要的上下文。

它找到了 PR 34 背后的全部六个会话：创建 PR、写正文、代码评审、修复运行等等。这六个会话包括代码评审派生的子代理，很酷，说明它也能看子代理。然后它还会看我的 PR 评论和期望的代码。

`retro` 当然很费 token，因为它要审大量信息才能想出该做什么。当你对多个会话跑 retro，比如 25 个，最好把工作批给子代理，说用四五个子代理去看那些 transcript。

### retro 报告：有些建议过头了

好，它跑完了，返回了一大堆东西。读 retro 报告时我要说：里面有些东西 agent 会搞错。很多人问我，为什么不让 retro 直接把修复应用到代码库，不需要你审？因为 retro 会陷入一种奇怪的循环，不停地想改进，然后改到更糟。

比如这里，它说的某件事是真的，但没有它想的那么严重：代码评审跑了一次找问题，我们修了，但没有再跑一次代码评审。所以它说修复方式是改代码评审技能，加一个最后步骤，修复进去后再跑一遍标准检查。在我看来，这有点太硬核了。你当然可以试，也许是个好主意，但对我来说还好。

第二条：你的偏好没有写下来，而现有代码在教相反的。我的 PR 评论里有一条「让代码自己说明，不要写注释」，但 agent 抄了一个项目惯例：一堆 server 模块里有个大横幅标题。修复提交实际上加了 32 行注释。所以我们的自动评审和我喜欢的代码风格不一致。

另一条评论是「通过模块自己的函数来设置测试」，但很多测试直接调用 `db.insert(schema)`。它说这两条都是判断性问题，所以应该放进 `coding-standards.md`。

它建议的规则是：让代码自己解释，命名和抽取直到注释变得不必要。注释只有在一个代码无法表达的「为什么」上才配存在。我其实会走得更远：如果代码无法表达这个「为什么」，你需要的可能是一份 ADR，而不是注释。不过这条规则我接受。

还有：测试安排通过被测模块来做。测试 setup 调用模块自己的函数；需要函数不存在时，把函数加到模块里，而不是直接插行。它还建议把 Martin Fowler 书里一些没进我代码评审技能的东西加进去，挺好笑。它还说我们应该删掉五个模块里的横幅注释，否则每个新模块都会抄，评审又会标记实现者本来抄对了的代码。所以它说既要更新编码标准，也要更新代码，让实现者抄到好东西。

我告诉 agent：第一条建议我忽略，我不想改代码评审技能；第二条你建议的一切都好。

### 落地：类型、测试类型、删注释、加规则

我们可以把每一条都修一遍。这里面确实有些好主意，但为了让这一课相对短一点，我就说：只实施第二条。其实第五条可能也是个好主意，第六条也是，因为那是我说的 branded types。所以我就这么说：做第二条，不改代码评审技能，然后实施第五和第六条。看看会怎样。

好，它在加这些小的 branded types。比如这个 body，现在明确标记成 markdown，很好。然后它实施第五条：一个共享的 test DB 类型，应该不会花太久。然后删掉模块横幅注释。对，那些注释都没了。现在往 `coding-standards.md` 加两条新规则。很好。

这样下次代码评审时，我们的 `coding-standards.md` 会更接近我们想达到的目标。好，最终总结出来了。

`retro` 老实说是我工具箱里最强大的技能之一。对我来说，它真的改变了对「要不要做人工评审、做多少」的计算。我现在做人工评审会挺兴奋，因为我知道它有意义，而且会给自动评审供能。不仅如此，如果一次编码会话出了问题、产生了 bug，我现在可以 retro 那次会话，确保它不再发生。总之，我希望你和我一样对 retro 技能兴奋。干得好，下一集见。

> **思考一下｜规则和代码要一起改**
>
> retro 指出：只把规则写进编码标准，但仓库里还留着旧惯例，实现者会继续抄旧代码。规则和示例必须同时更新。
>
> **可以追问**：当旧代码和新规则冲突时，应该先改代码还是先改规则？
>
> **可延展方向**：每次加规则时，顺手列出仓库里违反它的现有代码，作为清理清单。

> **思考一下｜为什么不让 retro 自动应用所有修复**
>
> 作者拒绝第一条建议，因为 retro 会陷入「不断改进」的循环，把系统改得更复杂。判断力仍然在人这边。
>
> **可以追问**：retro 的哪些建议类别适合自动应用，哪些必须人工筛选？
>
> **可延展方向**：给 retro 报告分三档：可直接应用、需确认、仅记录。

## 综合解读

论点链：人工评审留下四条流程性评论；retro 读取六个会话和 PR 评论；报告既指出真实问题，也提出过头建议；作者筛选后只采纳编码标准和代码清理，拒绝改代码评审技能；最后加 branded types、共享测试类型、删横幅注释、补两条规则。

成立前提：PR 评论能被 retro 读取；retro 能访问会话和子代理记录；人愿意筛选建议；团队接受规则和代码同时更新。

待核验主张：retro 报告的「32 行注释」「六个会话」「测试直接调 db」等是 agent 的分析结论，作者在讲解中接受，但没有逐行验证；「retro 是最强大的技能之一」是作者的价值判断。

边界：retro 可能把个人偏好误判成通用规则；自动应用修复可能让系统越来越复杂；规则和代码不同步，实现者会继续抄旧惯例。

可迁移素材：人工评审只留流程性评论；规则和代码一起改；给 retro 建议分档；用 branded types 区分文本和 Markdown；共享测试类型；删除会误导实现者的旧注释。
