## 口播文章

### 任务：先找词，再补周边词，最后统一代码

这一集我们要修上一集在应用里发现的问题，具体就是 pending chargeback、reversal、cancellation 这一整套说法。你在这里的第一个任务，是进入应用，找到正确的词，然后让整个应用围绕这个词统一起来。

做法是用 `grill with docs`。在一个全新的会话里，我们使用 `grill with docs`。我要你想一个能启动这场讨论的提示词。注意，在项目历史的这个时间点，我们还没有任何形式的 `glossary.md`。这意味着，当我们创建术语表时，不只是为这个实体创建一个词，很可能还需要定义另外几个词，才能让这条术语成立。事实上，我们可能需要先了解一下这个功能本身，弄清楚它实际处于什么状态，然后才能给它造词。

所以，你的第一个任务是用 `grill with docs` 找到正确的词。第二个任务是把它周围的词补到足够清楚，让这个新词的意思没有歧义。然后，我们用这份术语表统一代码。到这一步结束时，这个功能对用户和对我们都应该清楚很多，代码也会如实反映那个东西是什么。

祝你好运，追问愉快，解答集见。

> **思考一下｜先有词还是先有模型**
>
> 作者把「找词」放在「了解功能状态」之后，但又把「补周边词」当成定词的一部分。这里其实有一个先后顺序的张力。
>
> **可以追问**：如果连功能有哪几种状态都没弄清，能不能先定一个词？
>
> **可延展方向**：把「找词」当成需求分析的第一步，用词的分叉反推状态的分叉。

## 综合解读

这一集不是论证，是练习说明。可迁移的是三步：找词、补周边词、统一代码。第三步才是改代码，前两步都在语言层完成。

成立前提：项目还没有现成术语表，所以新词需要一组周边词才能定义清楚。如果项目已经有术语表，第一步应该是查表，而不是重新造词。

待核验主张：没有需要外部核验的事实。作者隐含假设学习者会主动操作应用、会读代码，而不是只看讲解。

边界：这三步假设功能已经存在、语言混乱但行为可观察。如果功能还没做，找词会变成设计活动，难度和顺序都不一样。

可迁移素材：把「周边词」显式列出来，不要只定义目标词；先弄清状态，再命名；最后才动代码。
