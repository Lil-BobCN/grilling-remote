## 口播文章

### 用听写启动会话

好，我把项目打开，开始用听写输入。这个应用里对 pending chargeback 或 reversal 到底指什么，有很多混乱。我们发给用户的邮件和屏幕上显示的内容，用的说法不一致。我想先给这周围的东西搭一个术语表，把可能需要用到的词找出来，把语言固定下来。

我们把这段发出去，看看它返回什么。可以看到两个技能都成功加载了：`domain modeling` 和 `grilling`。很好。它回来说，我读了退款相关的代码，这是第一轮问题。

### 第一轮问题：代码里其实有四个名字

看起来代码里其实有四个名字。代码本身、数据库 schema、根文件、提交信息里，用的都是 refund。但是课程页面的按钮和表单用的是「取消我的购买」（cancel my purchase），确认邮件和设置页面用的是 reversal，界面上还有 pending chargeback。甚至还冒出一个野生的 cancel，出现在错误提示里：「你看这门课看得太多了，不能取消。」〔待确认：ASR 原文为 "You have watched too much of this course to cancel it."，此处按上下文翻译〕顺便说一句，错误提示绝对算数。说实话，这可能是现在应用最让我受不了的地方：错误提示的文字非常糟糕，和应用程序其他部分的领域语言完全对不上。

所以问题一在问：这个概念我们叫什么？它的建议是 refund。我觉得这个很干净。如果你站在学习者的角度想，你真正想要的是把钱退回来；取消购买只是界面上的说法。所以问题一我同意，refund 说得通。

### 问题二：一个词还是两个词

问题二马上就有意思了。它问：这个东西我们需要一个词，还是两个词？

它说这里其实有两个东西：一个是学习者发起的请求，另一个是钱真正退回去。换句话说，有两个事件：退款请求被创建，以及退款真正发生。你能看到建议里给了一些只用一个词的句子，比如「退款被拒绝了，所以没有退款。」〔待确认：ASR 原文为 "The refund was declined. So nothing was refunded."〕这句话读起来确实很混乱。

不过，在我决定「好，用两个词」之前，我想先做一些场景测试。给我一些 refund request 和 refund 的场景测试，因为这两个词本身也很像。

接着是问题三：真实的拒付（chargeback）在范围内吗？银行发起的拒付，在我们的领域里存在吗？这个问题很好，因为它逼我们给术语表划边界。我们到底定义什么，不定义什么？我知道代码里没有任何东西定义 chargeback，但也许我们需要一个定义，以防将来要处理它。不过对这个问题，我要说：问题三，我们先把 chargeback 排除在范围外。我觉得现在还没到需要它的时候。

这样三个问题就答完了。看看接下来返回什么。

### 场景测试：把边缘情况说清楚

它做了一些场景测试。左边是场景，右边是「如果用两个词」和「如果用一个词」两种回答。

假设 Liam 要求退回他的 79 美元，但还没有人处理。用两个词，会说「Liam 有一个未处理的退款请求」（open refund request）；用一个词，会说「Liam 有一个已申请的退款」（requested refund）。

然后管理员拒绝了。用两个词，会说「他的退款请求被拒绝了，没有发出退款」；用一个词，会说「他的退款被拒绝了」。

再往下看：假设被拒绝后，Liam 又申请了一次。用两个词，意味着他提出了两个退款请求；如果只有 refund 一个词，就变成一次购买、两次退款，而两次都没有退成。你能看到，场景测试让这个功能在语言层面变得非常具体。我们能在语言里思考这些边缘情况。背后的想法是：如果你能谈论这些边缘情况，就说明你能在代码里轻松地给它们建模。

再看几个例子：管理员批准了，但只退 40 美元，不是 79 美元。如果只有 refund，我们可能还需要「申请金额是 79 美元」和「实际退款金额」这两个概念；如果我们有 refund request，那么退款请求是 79 美元，实际退款是 40 美元。

总的来说，这很有说服力：我们需要把 refund request 和 refund 分开。所以问题二，一个词还是两个词，我选两个词，refund request 说得通。

问题四问：退款可以部分退吗？我觉得先总是退全款。问题五问：学习者被拒绝后还能再申请吗？让学习者可以在被拒绝后再申请，我没问题。问题六问：approved 和钱已经退回去是同一件事吗？目前应用没有接任何支付处理，没有 Stripe 之类的东西，所以我们真的只有 refund 和 refund request。不过，如果我们接上支付服务，可能就需要区分了，因为那时会有 pending refund 和 issued refund 的区别。

我们围绕这一点再做些场景测试，找找感觉。我觉得问题六，即使我们还没计划接支付平台，也值得先做一些建模。因为一旦接上，就肯定要处理 pending refund 这类东西。所以，能不能给我一些建议，围绕问题六做场景测试？我们再跑一次，看看会发生什么。

### 第二轮场景测试：退款生命周期

场景测试这个想法太重要、太有用了。不过现在可以看到，它已经把定下来的东西写进 `glossary.md` 了。我们看到里面有了 refund 和 refund request。它还把 chargeback 加进去了，我不喜欢这一点，所以下一轮提示词里我要说：我不想让你加 chargeback，它感觉不属于我们的术语表。

先看看这轮场景测试提出了什么。场景一：退款在周一被批准，支付处理方周四确认。Liam 周二看到什么？如果只有 refund 一个词，那么周二到周四这三天，界面就在说谎：它会显示「已退款」，但事实不是。所以我们需要一个退款生命周期：请求已批准，退款待处理。

场景二：支付处理方因为 Liam 的卡被关闭而拒绝。这种情况下，退款会失败。请求被批准了，但退款失败了。有意思。看起来 refund 和 refund request 都需要挂状态。它上面也正是这么说的：批准一个退款请求，会创建一笔退款，这笔退款从 pending 开始，然后变成 issued 或 failed；退款请求则一直保持 approved。对，这说得通。

我们只是把语言固定下来，就对正在做的功能有了更多清晰度。所以我很满意引入退款生命周期这个想法，这绝对是对的。问题六，我完全同意选 B，也就是生命周期这个方案。上面的场景测试做得不错。看起来问题七这里其实有个 bug：资格判断在页面和路由之间不一致。

我想让你忽略 eligibility 在页面和路由之间的差异，我们另开一个会话处理。我觉得它发现了我在数据库里故意留下的东西，留到后面做。最后，它问了一个实现细节：他们付的「全款」是什么？对，你总是可以用 `amount paid`，它就是干这个的。

好，我对这个结果满意。发出去，看看返回什么。

### 术语表变厚：open、approved、declined

好，我们的术语表变厚了一点。现在有 refund、pending refund、issued refund、failed refund（待处理退款、已发出退款、失败退款）。但还没完，还有几件事没定：退款请求叫什么名字，还没人决定。

我很喜欢它的建议：用 open。它说可以用 requested，这也是我最初的想法，但读起来会结巴：「a requested refund request」（一个已申请的退款请求）。我同意 open refund request 更合理，然后 approved 和 declined 作为已决定状态，完全没问题。它还展示了屏幕上会怎么显示：界面上可以写「Refund request — open — waiting on us」（退款请求，未处理，等我们处理）。

问题十：失败的退款是在原地重试，还是替换掉？问题十感觉超出范围了。我觉得这是接支付处理方时才会决定的事。问题十一呢？

面向学习者的文案说什么？它建议按钮写「Request a refund」（申请退款），邮件主题写「Refund requested」（已申请退款），设置页标题写「Refund requests」（退款请求）。对，这些看起来都很棒。这样屏幕上每个词都会是术语表里的词。问题十一，同意，看起来很好。

退款会改变购买本身吗？退款发出后，学习者会失去课程访问权吗？这笔购买之后会改叫「已退款购买」，还是购买不变、只有钱动了？我给你一点预告：这个我们后面会做。所以现在可以说「还不需要」。问题十二，先标记为范围外，我们以后再处理。

好，我把这些发出去了。看起来我忘了回答问题九。对，问题九没问题。这个语言很好。希望我们快到尾声了。好，它又更新了术语表。

现在我们有了 open refund request、approved、declined。最后还有一个 `grilling` 的共识总结。它提出了一堆代码后续工作和代码改动，把 `amount paid` 暂时列为范围外，还写了 `glossary.md` 现在的内容。所以我要告诉它：好，实施这些代码改动。我本可以用 `implement` 技能，但我觉得这次不需要 code review，所以直接让它做。

### 把术语表落到代码

好，现在我们有一份代码改动清单。可以看到 `schema.ts` 文件里有了 `refund_status`。它其实把数据库里的枚举名改成了 open。这也产生了一次数据库迁移，迁移里会更新现有退款：把 `status = requested` 的退款改成 open。它甚至在修复数据库里所有已有的退款记录。

再看设置路由。这里现在是 `openRefundRequests`，不再是 pending chargebacks。我真的很喜欢看这种东西。你能直接看到自己做的决定落进代码，一切都变得更好读、更好理解。连局部变量名都是 `openRefundRequests`、`openRefundRequest.length`，还有「One refund request is waiting on us.」（有一个退款请求在等我们处理。）

能让 agent 直接翻遍代码，确保所有东西都和你的领域语言一致，成本太低了。这意味着这类重构比以前容易 justify 得多。再看几个文件。课程 slug 这里，改动是 `getOpenRefundRequest`，替换掉 `getRequestedRefund`。甚至代码注释里也一样：以前的 `getCancellationOffer` 现在是 `getRefundOffer`；「如果这笔购买不能退款，就 get open refund request」。清晰领域语言的好处会一路回响到代码里。

我在这里结束这一课，但其实还可以走得更远。比如术语表里，`learner` 这个概念正在被加进来，但还没有正式 mint 成一个新词。`learner` 是对的词吗？也许我们需要区分 users、instructors、learners、admins。一旦你开始这样看世界，真的很难停下来。所以我建议你去自己的一个仓库里，找一个你做过、但语言还不够扎实的功能，用 `grill with docs` 加上场景测试，把它重建一遍。干得不错，领域建模愉快，下一集见。

> **思考一下｜场景测试为什么能逼出模型**
>
> 同一个词放进不同场景，会给出自相矛盾或明显说谎的句子。矛盾就是模型缺了一块东西的信号。
>
> **可以追问**：如果两个词在现有场景里从不冲突，还值得把它们拆开吗？
>
> **可延展方向**：把二选一的场景测试做成固定表格，每次定词时都跑一遍，记录哪些场景无法用现有词说清。

> **思考一下｜术语统一的真实成本**
>
> 改一个词，牵动了枚举、数据库迁移、路由、局部变量、注释和界面文案。术语表不是免费的文档。
>
> **可以追问**：什么时候值得做全局重命名，什么时候只改界面文案就够？
>
> **可延展方向**：把术语表变化、数据库迁移和界面文案放进同一张检查清单，避免只改一半。

## 综合解读

论点链：先让 agent 读代码，列出同一个概念的所有名字；再用场景测试，看候选词在边缘情况下会不会分叉；分叉就说明需要拆概念；拆出来的概念再逼出状态和生命周期；最后把术语表落到 schema、迁移、路由、变量名、注释和界面文案。语言是代码结构的前置，并不只是写代码之前的准备。

成立前提：agent 能读代码、能生成场景；人愿意逐题裁决，而不是一次接受所有建议；应用可运行，数据库能迁移；团队接受一次全局改名的成本。

待核验主张：作者说现在的错误提示文字「非常糟糕」，这是个人判断，不是测量结果；「agent 翻遍代码的成本很低」是主张，实际成本取决于代码库大小和工具；「一旦这样看世界就很难停下来」是作者的自述，不是普遍规律。

边界：作者自己把部分退款、真实拒付、购买状态、失败退款是否重试都推到范围外，说明术语表不是一次做完的。`learner` 也还没有正式定词，术语表仍然有缺口。另一个风险是过度拆分：如果两个词在所有已知场景里都不冲突，拆开可能只增加复杂度。

可迁移素材：用左右两列的场景测试表比较「一个词」和「两个词」；用界面文案反推术语；把 out of scope 明确写进术语表；把枚举重命名和数据库迁移纳入术语统一的成本清单。
