## 口播文章

### 一堆 ADR 也需要修剪

我们已经看到把术语表修剪到合适大小有多大好处，但如果你有一大堆 ADR 呢？

我们打开终端，跑 `npm run reset`，选这个提交，它种下了一堆 ADR。提交叫 `seed-ADR-pile`。哇，我们有一堆 ADR。当你面对这么一大堆 ADR 时，要记得用三条标准去衡量它们。

我们记得这来自 `domain modeling` 技能：ADR 必须难以逆转、必须让人意外、必须是真实取舍的结果。如果有些 ADR 不符合这三条，我们可能就得处理它们。我们有两个选择：要么整个文件删掉，这完全可以；要么标记为废弃（deprecate）。换句话说，如果某份 ADR 值得留着，但不再代表当前决定，我们可以把它标记成「这个决定已经不在代码里了」。意思是我们当时做了这个决定，后来做了另一个决定。如果你想保留决策历史，同时又想让 ADR 保持最新，这很有用。

就像上一个练习一样，我们打开一个新会话，说 `grill with docs`，然后看这些 ADR，能剪掉什么。记住用三条标准衡量，也记住你可以删除或标记废弃。祝你好运，解答集见。

> **思考一下｜删除还是废弃**
>
> 删除让当前目录更干净，但历史只留在 git 里；废弃保留可读的决策轨迹，但会让目录继续变大。
>
> **可以追问**：一份被废弃的 ADR，应该在原文件里标记，还是移到单独的 `deprecated/` 目录？
>
> **可延展方向**：给 ADR 加一个状态字段（有效、已废弃、已被取代），让 agent 读目录时能直接过滤。

## 综合解读

这一集是练习说明，不是论证。可迁移的是把 ADR 当成会过期的资产，定期用三条标准复检。

成立前提：ADR 集中在一个目录；agent 能读代码，判断 ADR 是否仍然成立；团队接受删除或废弃。

待核验主张：没有需要外部核验的事实。三条标准本身在上一集已经出现，这里只是复述。

边界：删除和废弃不是免费的。删除后，虽然 git 历史还在，但 agent 默认不会去翻历史；废弃则要求后续读者理解状态标记。

可迁移素材：定期复检 ADR；删除「从未真正成立」的记录；废弃「曾经成立但已被反转」的记录；把状态写进文件名或正文开头。
