## 口播文章

### 让评审主动修，而不是只报告

好，我们有一个质量可疑地低的 PR，在交给人评审之前，可能想先提高质量。所以我们先拿到 PR 号，然后跑 `code-review` 加 PR 号，我的是 34。但还没完，我还要说：把你发现的问题修掉。

我相信在自动评审里，agent 应该主动去修它注意到的东西。如果自动评审只是产出一堆评论，然后我们把这些评论转给人工评审，那整个流程会更慢。我们的目标应该是让人工评审尽可能快、尽可能高效。换句话说，自动评审应该帮上速度：主动修掉发现的问题，只在遇到有点可疑、拿不准的东西时才交给人。

### 两条轴：标准和 spec

它比较的是两条轴。我们已经讲过编码标准，但我们可能还需要一份 spec 作为评审依据。创建代码的过程很复杂，有时 agent 会走不该走的捷径，所以对着写好的 spec 验证很重要。

当然，你不总是有 spec，有时你直接从 grilling 会话进入实现。但我们的情况有 spec。我在这个 gist 里给你写了一份，用的是典型的 `to-spec` 布局。下面有一个脚本，你可以把它复制成一个 issue，然后把 issue 传给 agent。我自己跑这个脚本，然后拿回来，得到 issue 35。好，这就是我的 spec，我把它传给 agent。原始 spec 是 issue 35。

### 准备就绪

一旦你把 spec 传给它、把 PR 指给它、告诉它修掉发现的问题，我们就准备好了。它应该会发现不少东西，希望我们能得到一个更好的版本，再去正经做人工评审。祝你好运，解答集见。

> **思考一下｜「修掉你发现的」改变了评审的性质**
>
> 只报告的评审产出评论；主动修的评审产出新 diff。后者更快，但也更容易掩盖判断分歧。
>
> **可以追问**：哪些问题应该让评审直接修，哪些必须停下来问人？
>
> **可延展方向**：给评审技能分两档：确定性问题直接修，判断性问题只报告。

## 综合解读

这一集是练习说明，不是论证。可迁移的是：自动评审要对着标准和 spec 两条轴，并且默认主动修。

成立前提：有一个可评审的 PR；有一份可读的 spec；评审 agent 能改代码；人愿意接受评审直接提交修改。

待核验主张：「主动修比只报告更快」是作者判断，取决于修复质量和人的信任程度。

边界：评审直接修可能引入新问题；如果 spec 本身有误，评审会照错的 spec 改；判断性问题仍需人决定。

可迁移素材：评审对着标准和 spec 两轴；让评审直接修确定性问题；只把拿不准的留给人；准备 spec 的脚本化方式。
