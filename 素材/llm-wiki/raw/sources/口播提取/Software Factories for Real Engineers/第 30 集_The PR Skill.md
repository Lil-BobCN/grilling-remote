## 口播文章

### PR 描述为什么难读

我们从人工评审开始，具体想改进两点。第一是速度：让评审人尽可能快地理解 PR。第二是优先级：不是所有 PR 都值得同样的对待，有些 PR 可以少花点时间。

我和 agent 协作时注意到一件事，我一直祈祷它会变好，但它一直没好：agent 写 PR 描述还是很糟糕。它们会写出充满垃圾的 PR 正文，非常难评审，让你根本不想看。很长一段时间我不知道怎么修，我以为 agent 永远会写这种垃圾，控制不了。

直到我发现一个很漂亮的技能：HumanLayer 的 Dex Horthy 写的 `Show Me`。他对我很多工作影响很大。`Show Me` 技能帮用户用视觉方式理解当前讨论的话题。它告诉 agent 跳过开场白，保持文字简短，使用可视化的伪代码解释器。我发现这些伪代码解释器极其有用，尤其是看 UI、看文件职责、看组件交互、看事情随时间怎么发生，用 Mermaid 图；还有组件变更的 diff、文件布局变更、调用树或调用栈变更。

我开始试，发现自己理解改动意图快了很多。换句话说，只是更快地理解代码，我就提高了评审速度，因为在我看代码之前，我已经知道代码为什么被改。

### 把 Show Me 改成 PR 模板

于是我拿 `Show Me` 改了改，做成 PR 用的技能。你进项目跑 `npm run reset add pr skill` 就能看到。它很简单，大部分是 `Show Me` 的副本，描述是「写 PR 正文时使用」。整个技能就是一个写 PR 正文的模板。

顶部是摘要，基本上就是 `Show Me` 那套视觉指示。模板下面有摘要所需的各种部分，全部逐字复制自 `Show Me`。所以顶部摘要是为了尽快拿到 PR 的「为什么」。

### 证据：改前失败，改后成功

但速度还有另一个组成部分：你不仅要知道为什么改，还要确认改对了。换句话说，你想让 agent 尽可能多地给你硬证据，让你觉得自己不用把代码克隆下来、在本地翻一遍、亲手试。

所以 PR 正文的下一部分是证据：改前证据是失败，改后是成功。我们需要改前的证据，让 agent 证明之前确实是坏的。这对 bug 修复和新功能都很关键，它给 agent 多设了一道坎，也向你证明东西真的能用。

技能里有一节专门描述什么叫好证据。具体来说，证据要具体，证明改动有效，前后都要有。截图是 S 级，前提是环境支持、改动是视觉的；基于执行的证据是 A 级，也就是它必须跑代码，拿到控制台输出、测试结果，展示现在失败、现在通过的那个具体测试。证据再次帮助你更快评审，因为你对代码更有信心，至少知道改动在做该做的事。

### 合并风险：单向门、双向门和爆炸半径

那优先级部分呢？怎么把注意力分配给对的 PR？

谈评审优先级可能挺有争议：有些 PR 要评审，也许不是每个 PR 都要评审。在正式讨论之前，我想用技能里的框架来框一下。PR 正文里有一个 merge danger（合并风险）部分，里面是门（door）和爆炸半径（blast radius）。

「门」这个想法不是我的原创，应该来自 AWS。它说每个 PR 要么是单向门，要么是双向门。双向门是你走过去还能走回来：合并了 PR，还能撤销合并，需要时总能走回来。单向门只能往一个方向走：你走过去，就会发生一些事，可能是数据丢失，可能是产生费用，可能是安全影响。单向门甚至可能是给五万人发邮件，或者公共库的破坏性变更。

所以单向门当然要比双向门看得更仔细。merge danger 里还有一件事：这次改动的爆炸半径。也就是说，如果出问题，潜在影响有多大。这和单向/双向不一样：一个双向门如果出错，后果可能很糟，但你能轻松撤回；一个单向门如果有巨大的爆炸半径，你最好相信我会非常仔细地看那个 PR。

这两个概念合在一起，决定你该给这个 PR 多少优先级。有意思的是，这不仅取决于改动本身，也取决于项目。如果你的项目是个人软件，大多数改动，大概 95%，都是双向门；用户还不多，你可以改很多东西。但如果项目在医疗或金融行业，有巨大的安全影响，那很多改动就是单向门。但事实是，不是所有改动都是单向门，你仍然可以把某些 PR 排在另一些前面。仔细看爆炸半径和门，就能把注意力分配好。

你甚至可以说，双向门加小爆炸半径的 PR，根本不需要人工评审，直接在 main 上评审就行。当然，如果想跳过人工评审，我们得先确保自动检查和自动评审非常扎实。别担心，我们会走到那里。

现在请你去页面底部做测验，把这些概念砸进脑子里，因为接下来我们要亲手感受，并在一个真实 PR 上试用 PR 技能。干得好，下一集见。

> **思考一下｜PR 描述是评审的界面**
>
> 作者把 PR 描述当成一个界面来设计：先给视觉摘要，再给证据，最后给风险标签。评审人不需要先读 diff 才能知道该不该读 diff。
>
> **可以追问**：如果 PR 描述很好但代码很差，评审人会不会被描述带偏？
>
> **可延展方向**：让 PR 技能同时生成「这段描述可能掩盖了什么」的自检清单。

> **思考一下｜单向门和爆炸半径是两个维度**
>
> 可逆性和影响范围不是一回事。可逆的大改动和不可逆的小改动，需要不同的评审策略。
>
> **可以追问**：一个双向门但爆炸半径很大的改动，应该按什么标准评审？
>
> **可延展方向**：给 PR 打两个标签：可逆性、影响范围，再用二维表决定评审深度。

## 综合解读

论点链：agent 写的 PR 描述难读，拖慢评审；用 `Show Me` 的可视化摘要让人先懂「为什么」；用前后证据证明「改对了」；用单向门/双向门和爆炸半径决定「花多少注意力」；三者合起来提高评审速度和优先级判断。

成立前提：agent 能生成 Mermaid 图、伪代码和 diff 摘要；项目能跑测试和截图；团队接受把 PR 风险显式标注；PR 技能可以被项目定制。

待核验主张：「agent 写 PR 描述一直很糟」是作者的经验判断；「截图 S 级、执行证据 A 级」是作者的价值排序，不是普遍标准；AWS 的单向门/双向门概念是作者转述，原始出处和措辞需要核对。

边界：可视化摘要可能过度简化，掩盖细节；证据可能只覆盖作者关注的路径；单向门判断依赖人对业务的理解，agent 可能低估风险。

可迁移素材：PR 模板三段式（为什么、证据、风险）；用 Mermaid 和伪代码解释改动；要求改前失败、改后成功的证据；用可逆性和爆炸半径分配评审注意力。
