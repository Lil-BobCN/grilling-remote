## 口播文章

### 从地图生成 spec

好，开始跑 `to-spec`，把 Wayfinder 地图传进去。可以看到它在读所有决策票。`to-spec` 其实不知道 Wayfinder，也不知道 Wayfinder 的流程，但它能理解：这里有大量决策票，我需要把东西都拉出来。

`to-spec` 做的一件事，可以看到它正在做：提出一些 seam（接缝），让我们对着测试。我们会在基于代码的设计那一节多讲，但你能看到，它基本上在给你一个模块的总体视图。这个 seam 看起来不错。发出去，它应该会创建 spec。

好，spec 准备好了。在这里：Cadence 的应用内通知。问题是，Cadence 里的人不知道跟自己有关的事发生了，应用里也没有地方告诉某人发生了什么。

这里有非常多用户故事。多少，61 条？还有一堆实现决定。Knock 是服务商，通知只存在 Knock 里。这里有我们决定过的完整通知目录、触发通知的服务、偏好设置、用户同步、客户端反馈、feed 界面。最底下还有一堆参考资料和后续笔记。可以看到原型分支被明确列出来，整张地图来自所有 issue。

这基本上是把地图压缩成一份可以喂给 agent 的 spec。你其实可以直接把地图传给 agent，说「实现这个」，但有了 spec，一切被摊平，更像是在给 agent 喂饭，让它很容易找到需要的信息。

### 拆票：八张票，先跑 tracer bullet

好，回到 agent，现在跑 `to-tickets`。看起来它把工作拆成了很多小票，我不太介意。我们用 `implement-spec` 跑。`implement-spec` 会并行跑很多任务。可以看到有五张可以并行，我觉得这比拆成更大的票更好。

但老实说，12 张可能太多了，也许降到八张。我这些数字基本是凭感觉定的。这个看起来有八张左右，有初始的 tracer bullet（示踪弹），很好。然后三到七号可以并行，感觉不错。发出去。

现在 spec 下面应该有一堆票。我们有子 issue，八张票准备好实现。概念和决策票一样：有阻塞关系，可以立刻开始。所以我清掉上下文，跑 `implement-spec`，把 spec 号传进去。然后就不管它了，让它跑。回来再做一次复盘，看看怎么样。

### 两小时后的实现现场

好，我们回来了。我离开了几个小时，有一大堆东西被实现了。回到最上面，可以看到它探索了 Knock 原型，看了所有东西，创建了一些探索笔记。〔待确认：ASR 原文为 "cohort of five notes"，笔记目录名不确定〕`implement-spec` 就是这么做的。然后它创建了一个 implementer，合并了第一块实现，再合并第二块。

实现发生在 `feature/notifications` 分支上。这挺巧的。编排器注意到上一个 implementer agent 有些问题：它把 Claude worktree 里的测试文件也捡了进来，导致测试数量重复。于是它让后续 agent 在 Vitest 配置里排除那个文件夹。接着下一个 implementer 建了下一个 tracer bullet，一个 merger agent 把它合并进 `feature/notifications`。然后它一次实现了五张票：feed、完整行为、讨论问题、退款通知、座位认领等等。

我很好奇它怎么合并这些。看起来它先合并了第一个完成的，然后合并了一堆额外的。对，每完成一个分支就合并。这很好。

它能验证的部分就验证：翻页的 after cursor，检查 seen 不等于 read。但还有些东西需要我在浏览器里看。还有东西在进来。好，它把两个分支合并进来，把所有东西合进 integration，然后跑完实现。所有票合并后，它跑代码评审，跑 `code-review` 技能，做 spec 评审和规范评审。

### 代码评审抓到了术语违规

看看它发现了什么。它发现了两处对编码规范和 `glossary.md` 的硬性违反。有意思，它在术语表里发现：你有个东西命名错了。哈哈，新文案用了术语表说不要用的词，太棒了。测试 helper 里加了 `add learner`，还有 `coupon`，出现在 `seat-claim-server.ts` 的错误信息里。太厉害了。还有一些其他异味。

看起来也有一些 spec 差异。我看看它有没有去修。对，现在派了一个 agent 去修。漂亮，应该快结束了。修复 agent 修了全部 15 条评审发现，保留了我说的五件要留的东西。

好，往下看，还有事吗？看起来还有一个向导要跑：在 Knock 开发环境里创建并提交全部八个 workflow，把 discussion reply 移到它自己的分类。然后跑 `npm run knock sync users`，给现有用户默认偏好。最后要在浏览器里检查 UI。

### 用管理 API 代替后台向导

我觉得我实在不想再跑那个破向导、再走一遍 Knock 的界面了。我要厚脸皮一点：有什么是我不用跑向导、不用回 Knock 界面就能测的？我猜你不能用程序创建我需要的所有 workflow 吧？

好，看起来 Knock 确实有 management API 和 CLI，可以从 JSON 文件创建并提交 workflow。如果能用，就需要一个 service token，在 Knock 后台的账号设置里创建一次。我觉得很值得。我要压缩这个会话。压缩的原因是我想保留大部分东西，比如这里做过什么的记忆，但有很多东西可以扔掉。换句话说，我们发给子 agent 的所有信息、它们发回来的所有信息，现在本质上只是一个完成的 PR。我们可以安全压缩，知道 PR 的主要细节都在里面。但我们现在进入了一个不同阶段。

好，研究一下 management API 和 CLI，看看我们需要什么，看你能不能自己处理。我知道为了不碰 Knock 界面，这有点折腾，但可能值得。

好，看起来不错。management API 能做后台向导做的一切。太好了。这意味着我们可以用 agent 在代码里写 Knock workflow，然后跑一个脚本，看起来是 `knock:push workflows`，把一切设置好。这很好。

我马上想到一个问题：以后怎么教 agent 知道这个 `knock:push workflows` 脚本？它当然可以自己发现，但直接告诉它更好。这看起来正是应该写一个技能的场景，确保 agent 以后知道这件事。所以，你能不能写一个很短的技能？我们在速成课里讲过 `writing-for-agents` 技能，正好用上。

它跑的时候，我来做它让我做的事：在 Knock 后台创建 service token，把 `KNOCK_SERVICE_TOKEN` 加进 `.env`，然后推送 workflow。两件事同时做。

跟着做的人，我找到位置了：在 Cadence settings、service tokens 里，可以加一个 service token，我就叫它 local agent。生成，复制到 `.env`。好，我的 `.env` 现在有 Knock service token，还有之前那些东西。

现在跑 `npm run knock:push workflows`，希望它直接加上。不，没有。我猜我们得把错误复制粘贴回 agent。它在这期间写好了 knock workflows 技能，应该很短。对，大约 25 行。讲了凭证、步骤，说「用代码创建或修改 Knock workflow。适用于新增通知类型、修改 workflow 模板或分类，或者 trigger 返回 404 因为 workflow 缺失。」

很好。以后我们的 agent 应该知道这些了。

### 让 agent 自己修推送错误

好，我告诉它跑 push workflows 脚本时报错了。我让它自己跑一次，看能不能工作。看起来缺了一些必需的东西，比如 action URL。我们课程后面还会讲这个，但让 agent 进入这种循环：它对自己在做什么有完整信息，又能安全地按下按钮去试，你最终必然会爬到一个能工作的方案。很多时候 agent 就是没有正确的信息，也修不好出错的东西，因为它们看不见自己在做什么。这个我们后面再讲。

好，就这样，修好了，八个 workflow 全部创建并提交到开发环境。

现在终于可以真正 QA 了。我以 Marcus Johnson 登录。点左上角的通知，可以看到有通知，显示全部已读。点设置图标进入通知设置，有 enrollments、discussion questions、discussion replies。很酷。

Marcus Johnson 有「Building REST APIs with Node」这门课。我找一个真的上过这门课的人。对，Emma Wilson 上过。我找一节课，在这节课上提问。Emma Wilson 问：「为什么这门课这么酷？」发评论，然后回到 Marcus Johnson，他应该收到通知。对，来了：「Emma Wilson 问了一个讨论问题。为什么这门课这么酷？」时间显示刚刚。点它，直接跳到那条评论，很好。

我们可以在这里回复 Emma Wilson，发一条回复。切回 Emma Wilson，哦不错，她也有通知。我喜欢头像也都在里面，很棒的细节。你能看到它多接近我原型想要的样子。它真的进去用了原型，太酷了。通知设置尤其感觉很好，可以看到她的通知更少。

我们实际测一下，把 discussion replies 关掉。回到对话，切到 Marcus Johnson，再回复 Emma Wilson 一句「hey, like this」。因为 Emma Wilson 现在关掉了那类通知，她没有收到通知。

### 收尾：高低保真度各自的分工

这就是用 Wayfinder 做前期规划的好处。我们在高保真度上规划，才能给 agent 最好的上下文，让成品反映我们的决定。比如通知栏的设计，我们做到了很高的保真度，有真正的原型，给了真实反馈。但像设置和下面的通知 feed，这是低保真度做的，我们只讨论了一下，agent 用了自己的创造力。

总的来说，我希望你和我一样印象深刻，也希望你喜欢看完整的 Wayfinder 流程。干得非常好，下一集见。

> **思考一下｜代码评审用术语表当规则**
>
> 评审抓到 `coupon`、`learner` 这些词，说明术语表不只是写作规范，也能变成自动检查的依据。
>
> **可以追问**：术语表的哪些部分可以自动检查，哪些只能靠人判断？
>
> **可延展方向**：把「avoid」词表接进 lint 或评审脚本，让术语违规在合并前暴露。

> **思考一下｜管理 API 替代手工向导**
>
> 作者为了不碰第三方后台，让 agent 研究 management API，最后把 workflow 写进代码。这个转换让配置可版本化、可重复。
>
> **可以追问**：哪些第三方配置值得转成代码，哪些留在后台更合适？
>
> **可延展方向**：把「后台点出来的配置」和「代码里的配置」列成两张清单，定期检查是否漂移。

## 综合解读

论点链：地图转 spec，spec 摊平信息；拆成八张票并行实现；编排器处理 worktree 测试重复等冲突；合并后跑代码评审，用术语表和规范抓出 15 个问题；用管理 API 把 Knock workflow 转成代码和脚本；最后浏览器端到端验证通知和偏好开关。

成立前提：spec 足够详细；agent 能并行跑多个 worktree；代码评审能读术语表和规范；Knock 管理 API 和 CLI 可用；团队接受把第三方配置写成代码。

待核验主张：61 条用户故事、15 条评审发现、八张票、两小时等数字是这次运行的观察；「第一次就能正常工作」的实际结果需要看 PR；Knock 管理 API 的能力和 service token 机制可能变化。作者说「agent 有完整信息就能爬向可行方案」，是经验判断。

边界：并行票越多，合并冲突和 worktree 污染风险越高；代码评审能抓术语违规，但不一定抓得到架构问题；管理 API 替代向导的前提是第三方提供足够完整的 API。

可迁移素材：spec 压缩地图；tracer bullet 先行；并行实现后统一评审；把术语表接进评审；第三方配置转成代码和技能；端到端 QA 要覆盖偏好开关这类反向路径。
