## 口播文章

### 渠道范围：只做通知信息流

好，坐下来准备长跑。我会更专注于自己操作，这一集更像你看我写代码，而不是我过度解释。这样会快一点，你也能看到我怎么走这些地图。

这次 grilling 会话是：每条通知走哪些渠道？问题一：是不是每条通知都落在通知信息流里？我同意。

下一个问题是范围：v1 要不要做邮件？看起来我们已经证明了这一点：我们注册了第三方服务，这个服务以后可以扩展，可以成为所有通知的枢纽。所以我说，邮件不进 v1。

它现在问 web push 要不要进 v1，我也说不。保持范围小，先到终点线。

问题四问：Cadence 已经在发的退款邮件怎么办？它的建议是造一个新词 `transactional email`（事务邮件），和通知区分开。我觉得这太复杂了。我就说：现在都走通知，以后可以扩展通知系统，给那些确实需要邮件的场景加邮件。

### 退款邮件怎么处理

好，我准备好提交第一轮了。它问：退款批准或拒绝的邮件什么时候移除？建议是等通知系统有邮件渠道的时候。我同意。

问题六，它提了一个很好的点：退款请求的收据（refund requested receipt）。这是少数确实需要给用户发通知的场景。它问，是不是继续通过现有 mailer 直接发邮件？但我的看法是，应该把 refund requested 做成一条通知，以后可以由邮件扩展。这是一个很好的例子：实现打破了我们之前定下的规则。

它问：邮件在地图上放哪？范围外，还是尚未指定？它建议范围外，我同意。换句话说，我们以后会做邮件，但现在只专注把所有东西放进通知系统，以后再扩展。也就是说，这张地图基本上限定在 v1，限定在我们马上要做的事。

Wayfinder 地图一个很酷的用法是：这是一张旧的 Wayfinder 地图，已经用 PR 关闭了，我们把当时范围外的东西重新纳入范围，从旧地图扩展。这也是把地图放在 issue tracker 里的好处，它们是很棒的历史记录。

接下来三个问题都是很简单的实现问题，我乐意全部同意。好，我们达到共识，术语表和 ADR 都不用改。好，关票。

### 通知信息流原型：三个变体

这意味着下一张开放的是原型票：通知信息流到底长什么样？好，定了，清掉上下文，跑 Wayfinder 拿下一张 issue。

如果我在真实工作里做，而不是录视频，我可能会同时跑两个。因为看剩下的 issue，我们有两张开放，而且相当独立。在两个 agent 之间切换、让它们 grill 同一件事的不同方面，真的很好玩，也比传统 grilling 省很多时间。会有上下文切换成本，因为你在想一号和二号，但它们都是同一个主题，你是在从两个角度接近同一个主题。但为了拍摄简单，我就一个接一个做。

好，非常兴奋，我们现在 7.29 万 token，原型已经建好了。dev server 在跑，我们看看。`prototype` 技能做界面时会创建几个变体：A、B、C。

看 A，铃铛弹出层（bell popover）。点进去，能看到「James Park 回复了你的问题」「Sarah Chen 回复了你的问题」「Wilson 回复了你的问题」。可以在这里全部标为已读。很好，放在 UI 上方很自然。

看 B。这个原型很酷的一点是可以给 feed 播种。有一个按钮 seed 这个人的 feed。我们现在以讲师 Marcus Johnson 登录，按 seed my feed，应该能看到几条通知弹出来。哦看，八条通知，作为一个抽屉弹出来。我不太喜欢这个，太大了。我想看看通知很多时长什么样。嗯，这个看起来不错。

看 C，inbox 和 toast。这里有完整的通知收件箱，可以正确过滤，也可以全部标为已读。能点开吗？可以，它确实给了链接，不错。但总的来说，我对铃铛弹出层印象很好。

### 已读、未读和 seen 的区别

原型是我强加自己喜好的机会。我有个问题：点它的时候，会去正确的地方，这很好；然后它会标记为已读。而且看起来 seen 和 read 有区别。刷新页面，通知数字没了，但点还在，因为还没读、没处理。我很喜欢这个区别，真的不错。

我的问题是：如果有 40 条会怎样？再按一次 seed my feed 看看。会无限增长吗？如果有 100 条通知呢？我打开 agent 问它。

我很喜欢 A，觉得很棒。能不能给我另一个变体，但我想知道分页有哪些选项？如果有 100 条通知，我们怎么处理？

它问了我一些问题：徽章数字、删除的评论。删除的评论，通知应该从 feed 里消失吗？对，删除的评论应该消失。徽章数字我喜欢。点击应该带我们到尽可能具体的位置。退款请求确认可以自己标记为已读，我同意。

你可以把原型想成高保真 grilling：就是带着一个东西看的 grilling。

### 分页和大量通知

现在它又要做同样的事：加更多铃铛弹出层变体，每个展示不同的分页方式。`prototype` 技能就是这样，不只给一个变体，会给多个，每个都能教你不同的东西。看多个总是更好。这就是 AI 有用的地方：几乎不费力气就能吐出来。

回来，它给了更多变体。seed feed 按钮没了，现在是 seed 8 和 seed 100。我们 seed 100 看看。这个不错，有 9+ 的徽章，我喜欢。然后一大堆通知，底部有 load more 按钮，挺不错。如果无限滚动呢？哦看，它把这个设计也加进去了，很酷。我喜欢它不用我说就自己迭代。

我挺喜欢这个无限滚动。嘿，看，我可以一直往下、往下、往下。三号呢？最新在上，然后 see all 按钮。我其实很喜欢这个布局。顶部区域有点笨重，但我很喜欢无限滚动。我觉得不需要顶部的总数，不需要 unread 按钮，read 按钮感觉可以叫「标记为已读」。我想把文字放回右上角。比如这里，我更喜欢明确的 mark all as read 按钮，而不是那个不太明确的复选框。

我很喜欢这个新设计，不错，但小盒子里的图标需要小一点。好，我有很多视觉反馈要給。我把这些反馈口述完，提交。

### 收敛到 A2

它回来了，把我所有不喜欢的东西都去掉了。我不喜欢那个复选框，应该是对勾。我想到一个问题：已读通知什么时候消失？它们会永远挂在这里吗？也许这也没问题，但我想问 agent，看能不能得到不同的原型。

我们选 A2 作为正式版本，先只在这个上工作。我在想，当用户没有通知、或者没有未读通知时打开通知栏，逻辑怎么走？我们永远显示最近的通知吗？你能想一些方案吗？这是好的用户体验吗，还是应该改进？

我觉得这大概是最后一轮。它做了一件有意思的事：回到更低保真度。它说，要么保留所有历史；要么只显示未读，加一个「查看更早」链接；要么对勾表示完成，点击通知就从弹出层移除；要么未读加一个短近窗，这是它的推荐。其实读完这些，我觉得保留所有历史就挺好，简单、可预测。我同意选一号。

这样，我准备关掉原型票了。我对现在的东西挺满意。好，我们降回低保真，讨论了一个关于原型的问题，没花多少 token 就解决了。

### 偏好设置和最后的迷雾

现在到「Cadence 里的通知偏好怎么工作」。我清掉上下文，说 `wayfinder`，去掉那个 `.env` 之类的东西。这是最后一张票。它问了第一轮问题，我基本都说可以。但我要加一件事：任何接触 Knock 的代码都应该放在某种接口后面，这样需要时可以换服务商。我们会在基于代码的设计那一节多讲，但我肯定想在这里加上，因为 Knock 不错、看起来够用，但如果价格变得很奇怪呢？我感觉以后可能需要换掉。它给了问题九一个小追问，然后我觉得票就完了。这张决策票就这样结束，非常短的 grilling 会话。

好，九张子 issue 全关了。但我不认为地图就完成了。我们还有一大串迷雾，也就是「not yet specified」里的东西。在关闭地图、或者认为地图完成之前，我想最后检查一遍这些尚未指定的东西。

我清掉 agent 的上下文，说 `wayfinder`，把 spec 号传进去。我说：我们已经关了所有票，但「not yet specified」里还有一些东西。能不能就此做一次 grilling 会话？理想情况下，我想在关地图之前清掉所有迷雾。看看它怎么说。

它回来了一堆问题，大多是收尾杂事，可能是已经决定过、只想要我确认的东西。首先是整理：这些决定记在哪？它说就用一张票。值得注意的是，我逐条看完了，全都是明显的 yes，十个全点赞。

好，它现在关闭所有票，或者更准确地说，它创建并认领了一张管道票。地图上的迷雾清空了。就这样，伙计们。所有工作、所有决定，都进了一张非常详细的地图，一个漂亮的索引，涵盖每一次 grilling 会话、每一点原型。它已经可以转成 spec 了。谢谢你的耐心，能走到这里很不容易。我们来看看 agent 拿着这些丰富信息能做得怎么样。干得好，下一集见。

> **思考一下｜范围砍到最小**
>
> 作者把邮件和 web push 都推出 v1，只保留通知信息流。理由是第三方服务以后可以扩展，不需要现在就把所有渠道做全。
>
> **可以追问**：哪些「以后再做」的功能，会在 v1 的数据模型里留下无法回头的坑？
>
> **可延展方向**：在范围外清单里给每条写一句「以后加回来时需要改什么」。

> **思考一下｜seen 和 read 的区分**
>
> 通知数字消失但点还在，表示「看过但没处理」。这个小区别影响用户对通知状态的理解。
>
> **可以追问**：如果产品只有一种「已读」状态，用户会损失什么信息？
>
> **可延展方向**：给通知状态建模时，先画清 seen、read、actioned 三个状态的关系。

## 综合解读

论点链：v1 只做通知信息流，邮件和 web push 推到范围外；退款邮件改走通知；原型比较多个变体后选 A2；用 seen/read 区分和分页方案收敛交互；偏好设置票要求 Knock 代码放在接口后面；最后清空地图上的迷雾，准备转 spec。

成立前提：第三方通知服务可以后续扩展；原型变体足够便宜，可以多试；团队接受 v1 范围收窄；issue tracker 能承载地图和票的历史。

待核验主张：「7.29 万 token」是这次运行的观察；「保留所有历史简单可预测」是作者的产品判断；Knock 的定价和偏好能力可能变化，需要按当前文档核对。作者说「实现打破了之前决定的规则」，这是他对 refund requested 处理方式的判断。

边界：范围砍得越狠，v1 越快，但以后加邮件/web push 时可能要改数据模型；多原型变体增加选择成本，作者最后只保留 A2；迷雾清空不等于所有细节都定了，只是当前版本不需要再决定。

可迁移素材：v1 只做一条渠道；范围外清单要写清以后怎么加回来；原型多给变体再收敛；seen/read 分开建模；第三方服务代码放在接口后面；关地图前清迷雾。
