## 口播文章

### 两路评审并行

好，跑起来看看。它做的第一件事是确定 fixed point（比较基准），这里是 `main`，也就是 PR 的 base。然后它把标准评审和 spec 评审作为后台 agent 启动。

它完成得相当快，两份报告都回来了，它已经准备去修两边的问题。注意它多主动。它处在「让它变好」的阶段，没有把这些决定推给我们。它发现了一堆东西，现在要去修。

### 标准评审：术语、响应规则、注释

完成了，它做了一堆事，给了我们完整的标准报告和 spec 报告。

我们可以看到它在几个地方违反了仓库里写明的规则。缺少课程时返回错误，而不是抛出错误，这违反了 `coding-standards.md` 里一条具体的响应规则。它还用了 learner，但术语表要求说 student。它其实违反了术语表自己对 note 的定义：术语表说笔记对写它的学生是私有的，但它把笔记展示给了讲师。还有大约十几条注释和旁边的代码矛盾，这不好。

它还做了一些判断，或者挑出了一些需要我看的判断。比如 `save.tsx` 里有重复代码，`saved` 上有 N+1 查询，书签和笔记逻辑放在路由文件里、没有测试，还有它说的 data clumps（数据泥团）：一个内联的 body 和 `updatedAt` 类型在两处声明。data clumps 这个词来自 `code-review` 技能本身，因为我在技能里加了一些我认为跨项目通用的代码异味。这意味着即使你没有 `coding-standards.md`，它也能发现一些东西。

顺便说，这里面很多来自 Martin Fowler 的《Refactoring》，那本书有一大串这类清单。我会让它对这些判断性问题用自己的判断。至于标准里的判断性问题，看起来都应该修，所以请继续。

### spec 评审：没实现的、多做的、做错的

然后是 spec 里缺失或不完整的部分。它实际引用了 diff 里没有实现的特定用户故事：课程页面从来没有显示笔记最后编辑时间；笔记框在课程内容下面，而不是视频下面。很好。

还有 spec 根本没要求的东西：一个 instructor student notes 区域。还有实现错的：字符上限是 5,000，不是 2,000；两个 action 都没有检查内容访问权限，所以任何登录用户都能给任何课程加书签或写笔记。

### 修完之后的 PR

然后它描述了改了什么：创建了一些新模块，创建了一堆新测试，在 lesson route 里，action 现在会调用 `requireContentAccess`，很好。底部还有一串决定。

我同意你对「保存空笔记」的处理，说得通。我想请你更新 PR 描述。外键那个 `on delete no action`，你觉得我们应该怎么办？我不太确定怎么解决。这个看起来真的很糟，我们确实得做点什么，但我不太确定做什么。所以我们进入一段对话来弄清楚。

好，在回答我的问题之前，它先去修了几件我说 yes 的事。它现在重写 PR 描述，当然，它拉取了 PR 技能。

看起来它回来了，更新了 PR 描述，并建议保持现状。好，听起来都可以。现在你能不能自己推到 PR？它问我需不需要开一个后续 issue。不用后续 issue。我这么说只是不想录那个流程，但你做代码评审时，确实是发现后续 issue、后续 PR 的好机会。

### 修完后的 PR 正文

现在可以看到它把修复推到了 PR 34。PR 正文被悄悄重写了，反映我们的改动。`saveNote` 里的校验逻辑被拉进了这段漂亮的伪代码：去空格，如果为空就拒绝；如果超过 2000 字符就拒绝；插入时如果有冲突，就替换 body 并移动 `updatedAt`。漂亮。

证据也更丰富了，因为之前没有测试覆盖这个功能，现在它展示确实执行了所有这些测试。看看 merge danger 有没有变。现在还是单向门，爆炸半径还是隐私。不过，现在没有任何讲师或平台管理员视图能读到笔记正文了。所以爆炸半径肯定比之前小。之前学生可能在笔记里写「这门课真烂」，然后讲师读到，可能会被冒犯。或者更糟，我们告诉学生笔记是私有的，但其实不是，这很糟糕。

### 自动评审的价值

希望你现在看到了一个像样的自动评审步骤能带来什么：它能在人看之前大幅提高 PR 质量，不仅对着 spec 比，也对着标准比。不过你会注意到一件事：我们还没有真正点开 files changed 做人工评审。因为我还想先给你看一样东西。干得好，下一集见。

> **思考一下｜自动评审的边界**
>
> 它修掉了术语、权限、注释和 spec 偏差，但外键策略这种需要产品判断的问题，它只给建议，留给人决定。
>
> **可以追问**：怎么让 agent 判断一个问题属于「确定能修」还是「需要人拍板」？
>
> **可延展方向**：在评审报告里分两栏：已修、待决定，待决定项附上选项和后果。

> **思考一下｜注释和代码矛盾**
>
> 十几条注释和旁边代码不一致，说明注释也会漂移。自动评审能抓这种漂移，人工评审很难逐条对照。
>
> **可以追问**：注释应该由谁维护，写注释的 agent 还是评审 agent？
>
> **可延展方向**：把注释一致性检查加进自动检查，而不是只靠评审。

## 综合解读

论点链：自动评审并行跑标准和 spec；标准评审抓术语、响应规则、注释矛盾；spec 评审抓未实现、超范围和实现错误；评审直接修确定性问题，只把外键策略这类判断留给人；修完后 PR 证据更实，隐私爆炸半径更小。

成立前提：有 `coding-standards.md` 和 spec；评审能改代码并推送；后台 agent 能并行跑；人愿意对判断性问题做最终决定。

待核验主张：评审报告里的具体问题（约十几条注释矛盾、N+1、外键限制、权限漏洞）是 agent 的代码分析结论，作者在讲解中接受，但没有逐行验证；「爆炸半径变小」是基于代码改动的判断，需要看最终 diff 确认。

边界：自动评审能修确定性问题，但可能改错或引入新问题；判断性问题仍需人；spec 本身可能有误，评审会照错的 spec 改；自动评审不替代人工对产品方向的判断。

可迁移素材：两轴评审（标准 + spec）；评审直接修确定性问题；把判断性问题分栏留给人；修完后更新 PR 正文和证据；用自动评审缩小人工评审的爆炸半径。
