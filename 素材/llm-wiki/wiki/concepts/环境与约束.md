# 环境与约束

一句话：agent 会照抄最近的例子，走最能编译通过的路。想让它做对，就把对的做法变成唯一省事的路。

## 问题长什么样

S1 的连帽衫例子：agent 查不出重复商品的原因，就在页面上加一行把重复藏起来，还写注释说这是临时方案。测试过了，界面看着正常，bug 还在。下一个 agent 在别处看到这段，连注释一起抄走。一个月后，临时方案住进 40 个文件。

Lauren 的解释是，agent 只看自己打开过的文件，照抄最近的例子，走最短路径。注释还替它把近路解释成合理（S1）。所以她的目标是让省事的路就是正确的路。

## 约束的几种形态

**一种做法只有一个位置。** GrokBot 背后的框架规定，每个功能有自己的目录。lint 规则拦下错误的 import。代码注释被全面禁止，因为 agent 总拿注释给临时方案找借口（S1）。

**类型和架构。** Lauren 把 TypeScript 的类型收窄拿来类比。用类型、判别联合、运行时检查，把可能的状态数量压下去（S3）。架构层面，则让错误在结构上无法表达，比如购物车一个商品一行带数量，就装不下第二件同款（S1）。

**内部框架。** 她们给 Electron 应用写了一个内部框架，叫 Dune〔待确认：拼写〕。它不是 Next.js，但定位类似，带一套很严的 lint 规则和约定，功能靠注册表发现（S3）。

**词汇表和指令。** Matt 这一侧把领域词写进 GLOSSARY.md，把仓库规则写进 AGENTS.md。他的技能要求用户长期维护这些文件，还要保证仓库导航清楚、token 效率高、环境对 agent 安全（S5）。

**确定性脚本。** 判定明确的步骤写成脚本或 CLI，交给机器跑。判断留给 agent。这条在 [[验证与自证]] 里有展开（S3）。

## 从失败里长出来的规则

Lauren 的做法是观察 agent 怎么失败，再决定把这次失败变成什么。能写成 lint 规则的，就写规则；能靠结构避免的，就改结构（S3）。

GrokBot 早期是八个上万行的 god file。她先把功能拆进独立目录，再靠注册表和 lint 维持这个形状（S3）。

Matt 的 retro 在做同一件事的复盘版。它看会话里 agent 在哪卡住，再决定加检查、加词汇、改导航，还是删掉没用的指令（S5）。

## 五层约束与 Dune

这次分享把约束排成五层（S8）。从硬到软依次是：代码库、静态分析、规则加 Bugbot 和技能、风格指南与人工评审。她建议按这个顺序投入。人审是最后一层，不该当第一层。

最硬的一层是代码库。agent 照抄看到的模式，所以改数据结构、改架构，让某类错误根本写不出来，比写规则更省事。

Dune 是 GrokBot 的 agent 友好框架。它把最容易走的路设计成正确的路：功能代码同目录，模块边界用 import 依赖图强制，主进程逻辑不许进渲染线程，渲染线程有 16 毫秒或 8 毫秒的帧预算。它还禁止代码注释，因为 agent 会拿注释给临时补丁找理由。

这套设计对人类不友好，对 agent 友好。她认为这是值得的交换，因为未来参与代码库的人不一定都是工程师。

## 成立前提

代码库要足够统一。要是同一个功能有五种写法，lint 拦不过来。

CI 要跑得动。Matt 发现仓库里有 `pnpm check` 脚本，但没有任何东西真的跑它。于是让 retro 建议补 CI（S5）。

约束要有人维护。规则会过期，技能会膨胀，词汇表会漂移。

## 边界

约束不是越多越好。规则太多，agent 的注意力被切碎，人也不好改。Matt 的 retro 专门挑「无操作指令」和占上下文的工具，就是在做减法（S5）。

小团队未必划算。搭一套严格环境，投入的是工程师的时间，回报要足够大的 PR 量才显出来。S1 的综合解读也提到这一点。
