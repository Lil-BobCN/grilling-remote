# 沙箱与自动接单

一句话：agent 想无人值守，先得关进盒子，再给它一个稳定的任务来源。Sandcastle 把这两件事做成一个 TypeScript 原语。

## 为什么先要沙箱

Matt 的目标是让 agent 完全 AFK（离开键盘）。问题出在权限：agent 每要一个权限就弹一次确认，人不在就卡住（S7）。

直接开 YOLO 模式也能绕过确认，但代价太大。他举的例子是 Claude 删掉 home 目录，或者在企业环境把代码传到第三方（S7）。

他试过现成的 Docker 沙箱，AFK 跑起来问题太多。他想要的是一个简单的 TypeScript 函数：传 agent、传沙箱、传提示词，跑完返回。市面上没有合意的，于是自己写了 Sandcastle（S7）。

## Sandcastle 是什么

一个 TypeScript 库，用来在隔离沙箱里编排编码 agent（S7）。核心就一句 `sandcastle.run`，参数是 agent、sandbox 和 prompt。复杂流程靠 TypeScript 脚本拼出来，库本身不规定流程。

初始化流程（S7）：

1. `npm install` 安装包〔待确认：包名〕。
2. `npx sandcastle init`。
3. 选 agent，比如 Claude Code。
4. 选沙箱提供方，比如 Docker。
5. 选任务来源，比如 GitHub issues。
6. 选模板，比如带评审的并行计划模板。

初始化会生成 `.sandcastle/` 目录，里面有 Dockerfile、环境变量示例和 `main.mts`。还要在 GitHub 上建一个 `sandcastle` 标签，只有带这个标签的 issue 会被接单（S7）。

## 流水线四段

模板给的是四段式（S7）：

| 角色 | 做什么 | 输入输出 |
| --- | --- | --- |
| 计划者 | 读带标签且未阻塞的 issue，排出能做的任务 | 输出 JSON 计划 |
| 实现者 | 每张 issue 一个，在独立分支上写代码，先写测试 | 分支加提交 |
| 评审者 | 提交多于一次时介入，看 diff 和项目规范 | 评审意见 |
| 合并者 | 把所有分支合回主干，处理冲突，关掉 issue | 合并后的主干 |

计划者只看未阻塞的 issue，所以 issue 之间的依赖关系要写清楚（S7）。

评审提示词里可以放项目自己的编码规范。Matt 演示时留了一段空白栏位，让使用者填（S7）。

提示词里有个小语法：在反引号前加感叹号，解析提示词时会先跑这条命令，比如 `git diff`（S7）。

## 可扩展的地方

库对 agent 不作规定，Claude Code、Codex 都能接。流程也不作规定，可以改成开 PR 分支，或者让多个 agent 各写一版再挑最好的（S7）。

Matt 强调，模板里的流程是他自己习惯的写法，不是 Sandcastle 的处方。可迁移的是结构，具体参数要自己调（S7）。

## 成立前提

issue 要干净。标签对、依赖写清楚，计划者才排得出可做的任务。

合并冲突要有兜底。分支多了，冲突会很难看，所以最后那一步交给一个足够强的 agent。

环境变量要备好。API key 和 GitHub token 缺一个就跑不起来（S7）。

## 边界

Sandcastle 假定接单口是 issue，而且有人维护标签。客户直接用自然语言提需求时，中间还差一层翻译。S7 的解读把这一层点成最容易做错的地方：做厚了变成又一轮 grill，做薄了 agent 接到的单没法开工。

安全边界要自己画。沙箱能防误删和外传，但防不了需求本身有问题。
