# 软件工厂

一句话：把从想法到合并的流程拆成可重复的段，用语言、规划和三层刹车控制质量。

## 定义

课程里的「软件工厂」指一条可重复的交付流水线：澄清需求、定领域语言、规划工作、写 spec、拆票、实现、评审、复盘。它是一套把 agent 放进流程的组织方式，并非某个具体产品。

## 来源观点

### 瓶颈移动

课程第 12 集的说法：agent 让实现变便宜后，瓶颈从「活需要有人干」移到「活需要有人规划」。作者想搭一个规划环境，能规划足够大的工作块，喂满手头的 agent。

单次 `grilling` 会话装不下大块工作。压缩会话会丢信息，拆会话又要搬上下文。Wayfinder 是为此做的跨会话规划工具。

### 三个选项

第 28 集给了一条决策树：

| 改动大小 | 做法 |
| --- | --- |
| 很小 | one-shot，让 agent 直接做，之后评审 |
| 中等以上 | 从 `grill with docs` 开始 |
| grilling 中发现雾太大 | 升级成 Wayfinder 地图 |

作者建议默认从 `grill with docs` 开始，因为升级比降级便宜。反过来从 Wayfinder 起步，发现事情很简单时，已经建了一堆用不上的资产。

### 三层刹车

第 29 集把质量控制分成三层：

| 层 | 驱动 | 成本 | 作用 |
| --- | --- | --- | --- |
| 自动检查 | 确定性工具 | CPU | 单元测试、类型检查、lint |
| 自动评审 | agent | token | 对照编码标准和 spec 找问题 |
| 人工评审 | 人 | 注意力 | 判断方向、风险和取舍 |

作者的排序是：自动检查可以大量加，因为只花 CPU；自动评审还有很多空间；人工评审要解决「看多少、什么时候看」。

### 自动评审和人工评审的分工

第 33 集说，实现 agent 要探索、实现、调试，上下文很重。评审 agent 从干净的 diff 开始，只负责找问题。两者分开，实现负责让它能跑，评审负责让它变好。

第 34、35 集进一步说，自动评审应该主动修确定性问题，只把判断性问题留给人。它对着两条轴评审：编码标准和 spec。

### 人工评审改进系统

第 36–38 集说，人工评审的目的不只是修这次代码，还要改进产出代码的系统。同一条评论不该留第二次。评论应该变成编码标准、AGENTS.md 或仓库里的示例代码。

`retro` 技能回读会话，按类别找改进：编码标准、AGENTS.md、工具经济性、自动检查、导航。它只给建议，不自动改代码。

## 已核验事实

本页没有独立核验的外部事实。三层刹车的效果、自动评审的准确率、人工评审的时间节省都来自课程演示和作者判断，没有对照实验。

## 分析

这套结构可以看成三层：

1. 上游：领域语言、术语表、ADR、地图和票。它决定「做什么、叫什么、先后顺序」。
2. 中游：spec、实现、PR。它决定「怎么把决定落进代码」。
3. 下游：自动检查、自动评审、人工评审、retro。它决定「怎么知道做对了，以及怎么让下次更好」。

三层之间的关系是反馈，不是单向流水线。评审发现的问题回到编码标准，retro 再把标准变成下一轮的约束。

## 反例或边界

- 小项目不需要完整流水线。one-shot 加评审就够了。
- 三层刹车都有成本。自动评审花 token，人工评审花注意力，自动检查花 CI 时间。
- 高风险领域不能靠抽样。钱、数据、安全、公开 API 这些单向门，还是要更密的人工评审。
- 软件工厂不解决方向问题。方向错了，流水线越快，错得越多。
- 课程自己说，软件工厂像开车，先学刹车。只会加速会造出 slop cannon（垃圾喷射器）。
