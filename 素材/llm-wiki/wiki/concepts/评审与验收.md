# 评审与验收

一句话：人不再逐行看代码，改成抽样本、看模式、加规则。评审从执行端挪到了规则端。

## 抽样的比喻

Lauren 用主厨试菜解释验收：主厨没法尝遍每一盘菜，但每天要尝一部分（S1）。播客里她把这个动作说得更具体：像工厂的质检员，每天抽一批 PR 细看，找共性（S3）。

她现在的做法是合并之后再看。早上读提交历史，发现问题就回滚、改代码、加 lint 规则（S3）。

## 自动验证顶上之后

全自动模式下，每个 PR 先过一支验证小队。小队在跑起来的应用里乱点，找回归，找到就修，修到能落地（S1）。人看到的已经是过了这一关的代码。

这一层不能替代抽样。验证只能证明它测到的部分，测不到的设计问题和方向问题，还是得人看（S1、S3）。

## PR 四栏

Matt 的 pr 技能只做一件事：写 PR 正文。正文分四栏（S5）。

| 栏 | 写什么 | 作用 |
| --- | --- | --- |
| 摘要 | 按 show-me 模板写最小说明 | 让人快速理解改了什么 |
| 证据 | before 和 after 的实跑结果 | 证明改动确实生效 |
| 合并危险 | 单向门还是双向门 | 决定要不要认真看 |
| 影响范围 | 出事会波及哪里 | 决定看多深 |

四栏的顺序有讲究。门的方向和影响范围放在最后，因为那是人第一眼或第二眼要看的。双向门加小影响范围，可以几乎不细看（S5）。

## 评审员换桌子

Matt 的原则是评审发生在另一张桌子上。写代码的 agent 觉得自己写的东西没问题，所以评审交给两个新 agent。一个对照 spec，找漏做、多做、做错。另一个对照编码规范和经典代码味道（S5）。

写代码的 agent 从没见过那份规范，评审员则专门盯这些毛病。他还把重构从实现环节拿掉，因为 agent 从来不做，挪到评审环节反而合适（S5）。

## 人的判断留在哪

retro 只给建议，不改代码。Matt 明确反对自动化，理由是 agent 修自己的发现会追假阳性，最后把仓库带到不该去的地方（S5）。

Lauren 的版本是：人负责定标准、决定哪些功能不该做、看模式。她把 agent 叫战术程序员，人是上面的战略者（S4、S1）。

## 成立前提

规范要写下来。评审员对照的编码标准和代码味道，得先有形。

评审要有新鲜上下文。同一个会话里的 agent 很难对自己的产出保持怀疑。

抽样要有节奏。每天看一批，比想起来才看更稳。

## 边界

四栏模板解决的是可读性，不解决该不该合并。方向错了，模板写得再清楚也没用。

抽样会漏。漏掉的那部分靠验证和回滚能力兜底，不靠运气。

单向门多的领域，抽样要更密，或者干脆退回逐项看。这一点在 [[信任阶梯]] 的边界里也提到。
