# 评审与验收

一句话：人不再逐行看代码，改成抽样本、看模式、加规则。评审从执行端挪到了规则端。

## 抽样的比喻

Lauren 用主厨试菜解释验收：主厨没法尝遍每一盘菜，但每天要尝一部分（S1）。播客里她把这个动作说得更具体：像工厂的质检员，每天抽一批 PR 细看，找共性（S3）。

她现在的做法是合并之后再看。早上读提交历史，发现问题就回滚、改代码、加 lint 规则（S3）。

## 自动验证顶上之后

全自动模式下，每个 PR 先过一支验证小队。小队在跑起来的应用里乱点，找回归，找到就修，修到能落地（S1）。人看到的已经是过了这一关的代码。

这一层不能替代抽样。验证只能证明它测到的部分，测不到的设计问题和方向问题，还是得人看（S1、S3）。

## 三层刹车（S9）

课程把质量控制分成三层，成本结构不同（S9 第 29 集）：

| 层 | 驱动 | 成本 | 作用 |
| --- | --- | --- | --- |
| 自动检查 | 确定性工具 | CPU | 单元测试、类型检查、lint |
| 自动评审 | agent | token | 对照编码标准和 spec 找问题 |
| 人工评审 | 人 | 注意力 | 判断方向、风险和取舍 |

作者的排序是：自动检查可以大量加，因为只花 CPU；自动评审还有很多空间；人工评审要解决看多少、什么时候看。

课程第 33 集说，实现 agent 要探索、实现、调试，上下文很重。评审 agent 从干净的 diff 开始，只负责找问题。实现负责让它能跑，评审负责让它变好。评审读 `coding-standards.md`，标准越具体，自动评审越能抓到重复问题。

第 34、35 集进一步说，自动评审应该主动修确定性问题，只把判断性问题留给人。它对着两条轴评审：编码标准和 spec。修完后再更新 PR 正文和证据。

## PR 四栏

Matt 的 pr 技能只做一件事：写 PR 正文。正文分四栏（S5）。

| 栏 | 写什么 | 作用 |
| --- | --- | --- |
| 摘要 | 按 show-me 模板写最小说明 | 让人快速理解改了什么 |
| 证据 | before 和 after 的实跑结果 | 证明改动确实生效 |
| 合并危险 | 单向门还是双向门 | 决定要不要认真看 |
| 影响范围 | 出事会波及哪里 | 决定看多深 |

四栏的顺序有讲究。门的方向和影响范围放在最后，因为那是人第一眼或第二眼要看的。双向门加小影响范围，可以几乎不细看（S5）。

课程第 30 集把四栏展开得更细（S9）：

- 摘要改自 HumanLayer 的 `Show Me` 技能，用伪代码、Mermaid 图和 diff 讲清改动，先让人理解为什么改。
- 证据分前后：改前失败，改后成功。截图是 S 级，前提是环境支持、改动是视觉的；基于执行的证据是 A 级，要跑代码、拿控制台输出和测试结果。
- 合并危险同时看两件事：单向门还是双向门，以及爆炸半径。两者组合决定评审深度。
- 优先级随项目变。个人项目大多数改动是双向门；医疗、金融等高风险领域，单向门更多。

## code-review 技能（S9）

课程第 33–35 集把自动评审拆成两条轴：

| 轴 | 依据 | 抓什么 |
| --- | --- | --- |
| 标准 | `coding-standards.md` | 术语违规、响应规则、注释和代码矛盾、代码味道 |
| spec | 用户故事 | 漏做、多做、做错、权限漏洞 |

评审在子代理里跑，拿到新鲜上下文。它不只报告，还直接修确定性问题，只把判断性问题留给人。课程第 35 集的例子：评审抓到十几条注释矛盾、术语违规、未实现的用户故事、字符上限写错和内容访问权限缺失。修完后 PR 的证据更实，隐私爆炸半径更小。

## 评审员换桌子

Matt 的原则是评审发生在另一张桌子上。写代码的 agent 觉得自己写的东西没问题，所以评审交给两个新 agent。一个对照 spec，找漏做、多做、做错。另一个对照编码规范和经典代码味道（S5）。

写代码的 agent 从没见过那份规范，评审员则专门盯这些毛病。他还把重构从实现环节拿掉，因为 agent 从来不做，挪到评审环节反而合适（S5）。

## 人的判断留在哪

retro 只给建议，不改代码。Matt 明确反对自动化，理由是 agent 修自己的发现会追假阳性，最后把仓库带到不该去的地方（S5）。

Lauren 的版本是：人负责定标准、决定哪些功能不该做、看模式。她把 agent 叫战术程序员，人是上面的战略者（S4、S1）。

## retro：把评论变成规则（S9）

课程第 36–38 集把人工评审的目的往前推了一步：评审不只要修这次代码，还要改进产出代码的系统。目标是同一条评论永远不用留第二次。

`retro` 技能读本地保存的会话文件，按类别找改进：编码标准、AGENTS.md、工具经济性、自动检查、导航。它可以看单次会话，也可以看最近若干次会话。多会话时最好把工作批给子代理。

课程里的例子：作者在 PR 里留了「让代码自己说明，不要写注释」，但仓库里有一堆模块横幅注释，修复提交反而加了 32 行注释。retro 建议把这两条偏好写进 `coding-standards.md`，同时删掉仓库里的旧横幅注释。规则和示例代码要一起改，否则实现者会继续抄旧代码。

作者也拒绝了一部分建议。retro 提议改 `code-review` 技能，加一步「修复后再跑标准检查」，作者觉得太硬核，没有采纳。这说明 retro 的输出仍要人筛选，不能自动应用。

## 成立前提

规范要写下来。评审员对照的编码标准和代码味道，得先有形。

评审要有新鲜上下文。同一个会话里的 agent 很难对自己的产出保持怀疑。

抽样要有节奏。每天看一批，比想起来才看更稳。

## 边界

四栏模板解决的是可读性，不解决该不该合并。方向错了，模板写得再清楚也没用。

抽样会漏。漏掉的那部分靠验证和回滚能力兜底，不靠运气。

单向门多的领域，抽样要更密，或者干脆退回逐项看。这一点在 [[信任阶梯]] 的边界里也提到。
