# 修正阶梯与 /correct

一句话：同一个错出现两次，就别再解释，把它变成仓库里的硬约束。约束有高低，越靠结构越省事。

## 阶梯的顺序

S1 给的顺序是：

1. 架构。设计成这个错根本发生不了。
2. 类型。让错的状态表达不出来。
3. lint。报错时直接点名正确修法。
4. 测试。让 CI 拦住。
5. 写给 agent 读的文字指令。
6. 人在 code review 里抓。Lauren 给这一档贴的标签是 NGMI。

不同视频里说法略有出入。S1 前半段把 lint 和测试放在同一档，后半段讲 /correct 时又拆成类型、lint、测试、文档四层。以 /correct 那段的细分更完整。

## /correct 怎么跑

它读你近期的提交、回滚和评审意见，找 agent 反复在犯的错。错两次就算一个模式（S1）。

然后从阶梯顶端往下爬：先看架构能不能让错不可能，再看类型，再看 lint，再往后是测试和文档。每一条新检查，都必须在历史里真实发生过的错误上亮红灯。新的 lint 规则会拿上个月的临时方案跑一遍，能红才算数（S1）。

它还在 agent 指令里维护一张表，记录每条规则靠什么落实。这样 agent 知道哪条是硬约束，哪条只是建议（S1）。

## 为什么必须从顶上爬

同样的错误，用架构修一次就永远消失。用人审修，每次都要有人在场，而且会漏（S1）。

S1 的连帽衫例子把四档都走了一遍。先改数据结构，让购物车装不下第二件同款。再加一条 lint 规则，指向真正修法。然后靠 fix-root-causes 让 agent 追根因。最后才是人审兜底。

## 剪枝和绑铁丝

Lauren 的盆栽比喻：提交像疯长的盆栽，人的纠正只是剪掉一根枝。第二天同样的错枝在别处长回来，因为 agent 照抄现有的东西（S1）。

养盆栽的人给枝条绑铁丝，让树按形状自己长。她管这叫园艺。那 2,500 个 PR 里，很多就是绑铁丝（S1、S3）。

## 一个反向动作：删指令

9 月她删掉 34 条指令，都是 Opus 5.5 不用叮嘱也会遵守的。删第二批前做了 A/B。154 个植入缺陷，没有这些指令时 review skill 抓到 142 个；留着反而只有 139 个（S1 自述）。

规则可以写进代码，也可以从文字里删掉。这一正一反是同一件事：让约束落在能执行的地方。

## 成立前提

仓库要能接受新规则。CI 要能跑新检查。

重复要真能识别。错两次算模式，前提是提交历史、回滚和评审意见都留得下来。

## 边界

人审没有被取消。Lauren 每天仍然抽样读提交历史，只是不把人审当第一道防线（S1、S3）。

阶梯对小团队可能过重。规则维护本身要成本，PR 量不够时，收益抵不过投入。S1 的综合解读也提到这一点。
