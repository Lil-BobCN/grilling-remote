# 验证与自证

一句话：agent 得能自己看到改动的结果，人才敢退出循环。验证是整套方法里最靠前的一块。

## 为什么验证最先做

没有验证，人就是 agent 和工具之间的中转。Lauren 管这个叫人肉代理（meat proxy）。她把 trace 从 Chrome 开发者工具搬给 agent，agent 再改，改完她再去看（S1、S3）。

她说，循环之所以成立，关键在验证那一段。agent 能自己验证，人才从等式里消失（S3）。在 pstack 里，她把验证称作最重要的一个 skill（S3）。

## 验证技能做什么

一份验证技能通常写清楚这些事（S1、S2）：

- 怎么启动应用，怎么确认它健康。
- 怎么点页面，走完一条真实用户路径。
- 怎么留下证据：截图、录屏、trace、控制台和网络记录。
- 功能地图：每个功能在代码里的位置。

GrokBot 的 bot 有自己的电脑，能登录 LinkedIn，也能打开 Chrome 读动态。这是同一个思路的产品化（S2）。Sandcastle 里则是把应用放进 Docker，让 agent 在盒子里随便跑（S7）。

## 把确定性写进 CLI

早期没有 CLI 时，每个 agent 都会重新造一遍验证脚本。同一个应用，每个 agent 写得都不一样，上一个写好的还被丢掉（S3）。

她的做法是把确定的步骤固化成 CLI，外面只包一层薄指令。CLI 调 Playwright 和 Chrome DevTools Protocol，读快照、抓 trace、跑检查。agent 只负责判断哪一步该跑、结果说明什么（S3）。

这样做有三层收益。省上下文、省时间、让不同 agent 的行为一致（S3）。她还把这套判断推到迁移上：能用 codemod 和 AST 改的，就别让 agent 每次重新想（S3）。

## 证据的标准

片子给了一条硬线：能编译不算证据，一个绿灯的单元测试也不算（S1）。PR 模板里要求的是真实实体上的 before 和 after（S5）。Matt 的说法更直接：agent 说「我读过代码，应该没问题」，这不叫验证（S5）。

验证还要看它证明了什么。她在 Cursor 做性能时，要的是可评分的指标，再让 agent 在循环里反复改进，这叫爬山（S3）。

## 规模化的验证

全自动模式下，pstack 给每个 PR 派一支验证小队。它们在跑起来的应用里乱点，专门找回归，找到就修，修完再跑，直到能落地（S1）。

播客里她把这件事叫 fuzzing。代价是 token 消耗大，可以调，比如把十个验证 agent 减到一个（S3）。她的判断是，验证强度决定了她敢放多少权。

## Control Glass：CLI 加功能地图

S3 里她说过验证是第一个让她放手的技能。这次分享把它的构造讲清楚了（S8）。

Control Glass 有两部分。第一部分是命令行工具，让 agent 可重复地运行应用、采 trace、抓堆快照，用实测证据证明功能可用、性能达标。第二部分是功能地图，本质是落到文件里的记忆：应用怎么工作，有哪些功能，用户按什么快捷键、点哪些 DOM 元素找到它们。功能地图放在技能目录里，用自动化维护（S8）。

功能地图解决的是另一类问题。用户在 Slack 只发一张含糊截图，agent 能运行应用也猜不到指哪里。有了地图，它能把请求对到具体功能（S8）。

## 成立前提

应用要能启动。启动不了，或者依赖外部服务起不来，验证技能就无从谈起。

要有可观察的信号。截图、日志、指标、trace，至少要有一类能判断对错。

验证脚本本身要维护。她提到 Cursor 和 SpaceX AI 内部每个应用都有验证技能，并且是自动维护的（S3）。

## 边界

验证能覆盖的，是它能观察到的。视觉和交互可以截图，性能和回归可以跑指标，但「这个功能该不该做」不在验证范围里。

领域越难验证，这套办法越难用。她把可验证性当成能不能走到第五级的前提（S3）。
