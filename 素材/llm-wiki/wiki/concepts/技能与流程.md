# 技能与流程

一句话：skill 就是把流程写成自然语言。两套库不冲突，一段流程用谁的工具都能拼。

## skill 是什么

Matt 的定义最省事：skill 就是 markdown 加英文，本质是一段流程说明（S3）。Lauren 的说法是，把你自己每天做的事提炼成流程，再交给 agent（S3）。

两家都强调，skill 里真正值钱的是问题和判断，不是复制来的命令。S4 说，最早的 grill-me 只有四句话，价值全在问题里。

## Matt 的一条链

从想法到合并，他的技能排成一条链（S4、S5、S6）：

| 阶段 | 技能 | 产出 |
| --- | --- | --- |
| 问清楚 | grill、grill-with-docs | 决策树、词汇表 |
| 写下来 | to-spec | spec 加用户故事 |
| 切开 | to-tickets | 带阻塞关系的票 |
| 实现 | implement、implement-spec | 分支和提交 |
| 交出去 | pr | 四栏 PR 正文 |
| 复盘 | retro | 仓库和指令的改进建议 |

grill 会反过来面试你。它把功能拆成一棵决策树，父节点定了才问子节点，一次问一层，每题给推荐答案。事实类的让它自己去代码里查，决策类的必须你答（S4）。

grill-with-docs 会边问边维护词汇表，给词写定义，也写要避免的说法。你听到不懂的词，打一句「wait what」，它用词汇表重讲一遍（S4）。

to-spec 写问题、修法和用户故事，还要和你确认接缝。接缝是测试将来戳功能的地方，理想数量是 1 个（S4）。

## Lauren 的一层

pstack 是另一套组织方式。它不是一条链，是一张按任务类型分的网。50 个 skill，23 本 playbook，入口只有 poteto mode 一条命令（S1）。

大约一半 skill 是单条规则，比如先删再加，比如两次修复失败就质疑共同假设（S1）。

她还提过一个 recall 技能，用来回读旧会话，把上下文压缩后带进新会话（S3）。这跟 Matt 的 retro 有点像，区别是 recall 面向「接着干」，retro 面向「改环境」（S5）。

## 两套怎么合

播客里的说法很直接：两套互补，谁都可以拿一段来用（S3）。Matt 的 grill-with-docs 负责问清楚，pstack 的执行 skill 负责跑完。中间用 spec 接上。甚至可以各取一半，拼一个自己的 mode。

两个人都强调「自己的刀」：别人的 skill 是参考，最后要长成自己的一套（S3）。

## 技能会越变越小

Lauren 说，去年 skill 里写很多实现细节和命令，现在这些可以删掉，只留工作流。模型变强，skill 会越来越短（S3）。

Matt 也在删。v1.3 去掉了合并冲突技能，因为 harness 自己能处理（S4）。

## 懒加载与体积

Matt 的插件里 27 个技能，16 个只在你叫名字时才会出现，agent 平时看不到。整套装好的技能占 660 个 token（S4 自述）。

这解决了一个现实问题：技能多了，上下文会被撑爆。按需加载比全塞进去省。

## 成立前提

语言要准。词汇表、规则、问题，写得含糊，agent 就只能猜。

skill 要有人维护。模型变强、仓库变了，旧 skill 会变成负担。

要能测量。Lauren 提过，早期最难的是判断一个 skill 到底有没有用（S3）。

## 边界

skill 不是越多越好。S4 提到有个开发者嫌 Matt 的 skill 太防御，转去用 pstack。防御到什么程度，取决于模型能力和任务风险。

skill 也替代不了判断。grill 只负责把决策问出来，答案仍然是你的（S4）。
