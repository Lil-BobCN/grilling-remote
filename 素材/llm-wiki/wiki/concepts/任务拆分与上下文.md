# 任务拆分与上下文

一句话：spec 是目的地，ticket 是会话。每个 ticket 塞进一个干净的上下文窗口，agent 才不会在长上下文里变笨。

## spec 和 ticket 的分工

Matt 把落地一大块工作拆成两个东西：spec 和 tickets（S5）。

spec 写目的地：问题、修法、用户故事、验收条件、不做什么。tickets 写旅程：把 spec 切成一张张能独立跑的票。

ticket 之间可以有阻塞关系，合起来是一张任务图。依赖已满足的票叫前沿票，可以同时开工（S4、S5、S6）。

## Wayfinder：把票再往上收一层（S9）

课程把票分成两种用法。实现票是 spec 切出来的执行单元；决策票是 Wayfinder 地图上的问题单元，解决的是「还没决定的事」，不一定产出代码。

Wayfinder 的结构：

- 地图是一个 issue，存目的地、已做决定、战争迷雾和范围外。
- 决策票是地图的子 issue，用 `blocked by` 连成 DAG。
- frontier 是开放的、未阻塞的、未认领的票，可以并行处理。
- 四种票型：grilling、prototype、research、task。
- 目的地建议定成 spec；地图完成后用 `to-spec` 转成 spec，再走 `to-tickets` 和 `implement-spec`。

所以两层票的分工是：Wayfinder 管「决定什么、先后顺序」，spec 和实现票管「一次会话装什么、怎么落地」。详见 [[wayfinder-地图与决策票]] 和 [[保真度与原型]]。

## 为什么必须切

agent 的上下文一长，推理就变钝。Matt 引用 Dex Horthy 的说法。大约 15 万 token 以内叫智能区，超过叫变笨区，还可能触发自动压缩（S4；变笨区的说法见 S5）。

切 ticket 的规则很土：估算任务要多少 token，除以 15 万。一个百万 token 的重构，大约拆成 7 张票（S4）。

每张票都要能独立跑。S4 说，一张票要穿过数据库到按钮的每一层，自己就是一个小功能。

## 谁来跑这个循环

S5 列了三种跑法。

手动最累：实现第一张，等完，清空，再说第二张。人相当于在当 for 循环。

脚本最可靠：写一个脚本，读票，逐张调 implement。每次跑法一样，也便宜。但搭起来复杂，超出初学者范围。

agent 当保姆是中间路线：一个编排 agent 看着所有票，派 sub agent 去实现。这就是 v1.3 的 implement-spec（S5）。

## implement-spec 的九步

技能本身写得很短，流程九步（S5）：

1. 读 spec 和票。
2. 在自己的 sub agent 里做探索。
3. 建集成分支。
4. 用实现者 sub agent 逐票实现，TDD 加 worktree。
5. 用一个 sub agent 把工作合进集成分支。
6. 继续派实现者，直到做完。
7. 在集成分支上跑 code review。
8. 清理。
9. 准备 PR。

S6 的实测给了一组数。5 张票，9 个 agent，耗时 1 小时 18 分钟。最后合并到一条分支，并清掉 worktree。

## 一个真实案例

S4 讲了 Matt 自己课程应用的一次落地。9 月 25 日提 spec，41 条用户故事。4 分钟内生成 10 张票，票之间带阻塞关系。全部落在一条分支，28 次提交，约 1.4 万行，spec 写完两小时多一点合并（S4 自述）。

同一条视频里还有拆分粒度的反例。演示时 to-tickets 一次切出 13 张票，人嫌太细，要求不超过 5 张。它删掉重建成 5 张（S6）。

## grill 决定 spec 的质量

spec 写得清不清楚，取决于前面问得够不够。grill 把计划拆成一棵决策树，逐个问，每题带推荐答案。小改动大约 6 个问题，一般 20 个左右，极端一次 46 个（S4）。

问出来的结论写进词汇表和 spec。spec 发到 issue 里，打上 ready-for-agent，才算可开工（S4、S6）。

## 成立前提

spec 要够清楚。spec 不清，票就建在沙上。

依赖要真是有向无环的。票互相纠缠，前沿票出不来，并行退化成串行。

harness 要支持 sub agent 和 worktree。不然并行开不起来。

## 边界

切太细也有成本。票越多，合并和上下文重建的次数越多，如上文 13 张票的例子（S6）。

小任务不值得走全套。一个会话能干完的，就在一个会话里规划（S4）。

上下文窗口在变大，压缩也在变好。15 万这个数会浮动，它是经验值，不是常数。
