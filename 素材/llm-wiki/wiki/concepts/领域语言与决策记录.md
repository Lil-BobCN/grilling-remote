# 领域语言与决策记录

一句话：先把词定下来，再写代码。术语表管「叫什么」，ADR 管「为什么不是别的」。

## 定义

**领域语言（domain language）**：用户、产品、代码和 agent 共同使用的一套词。课程借 DDD 的说法，叫 ubiquitous language（通用语言）。同一个词必须在这四处意思一致。

**术语表（glossary）**：仓库里的 `GLOSSARY.md`，记录领域词、定义和要避免的说法。它是约束，不是百科。

**ADR（architecture decision record，架构决策记录）**：一到三句话，记录做了什么决定、为什么。可选写考虑过的方案和后果。

**bounded context（限界上下文）**：公司或应用里一套语言生效的范围。同一个词在不同语境里可以有不同含义，比如产品里的 refund 和财务里的 refund。

## 来源观点

### agent 会生造词

课程第 1 集用一个退款功能演示：同一个动作在界面上叫「取消购买」，邮件里叫「逆转请求」，账户里叫「待处理拒付」，代码里又叫 refund。agent 为了省 token，会把很多含义压进一个生造的名字。用户读不懂，agent 也找不到已有的实现，代码开始重复。

作者的主张是维护一份共享 `glossary.md`。它不只能提高沟通质量，也能改善代码和下游用户体验。

### 用场景测试拆词

第 3 集的关键方法是场景测试。把候选词放进不同场景，看句子会不会自相矛盾。

比如「退款被拒绝了，所以没有退款」这句话，只用一个 refund 就很别扭。拆成 refund request 和 refund 之后，可以说「退款请求被拒绝，没有发出退款」。再往下，批准请求和钱到账之间有时差，于是又拆出 pending、issued、failed 三种退款状态。

作者的判断是：你能在语言里谈论这些边缘情况，就能在代码里给它们建模。

### 代码只给答案，ADR 补推导

第 4 集的比喻：代码是一道只留答案、把推导过程擦掉的题。它说明最后做了什么，不说明排除了哪些方案、为什么。

ADR 的准入标准有三条，同时成立才写：

1. 决定难逆转。
2. 没有上下文会让人意外。
3. 是真实取舍的结果。

作者举的例子是退款窗口按整日而不是按小时计算。这个选择让退款窗口在午夜关闭，比精确到小时多出一段时间。代码里只看到按日计算，看不到为什么。这种决定就值得写 ADR。

### 术语表和 ADR 都要修剪

第 7、8 集讲术语表膨胀。agent 喜欢把实现细节写进去，比如表名、字段名、具体小时数。实现细节会变，术语表跟着变就会过期。通用编程词（button、component、slug）也没有领域约束力。

第 8 集的两条删除规则：

- 删实现细节。
- 删过于通用的词。

修剪时还要决定统一到哪个词。课程里的例子是 learner 和 student：作者本来想用 learner，发现代码里 student 出现 180 次、learner 只有 8 次，最后反过来统一到 student。这是成本判断，不代表 student 在语义上更好。

第 9、10 集把同样的逻辑用到 ADR：够不上三条标准的删除；曾经成立但被反转的，用新 ADR 记录，并在「考虑过的选项」里保留旧做法。被取代的 ADR 留在当前目录里，agent 会把它当成有效决定。

### 一个术语表不一定够

第 11 集回答了几个常见问题：

- 应用变大后，同一个词可能在不同语境里意思不同。规则是：两个 bounded context 想挤进同一份术语表时，就拆。可以用 `glossary-map.md` 指向不同目录的术语表。
- 术语变更要在写 spec 之前合并。代码重命名也放在 spec 之前，这样票指向的是新文件名。
- 好词来自用户。听用户怎么说，从他们的原话里挖词。
- 不需要先有术语表。边做边建，只建当前需要的条目，慢一点。
- agent 不能独占术语表。语言的前提是人和 agent 共享；agent 单方面发明词，团队会用另一套语言。

## 已核验事实

本页没有独立核验的外部事实。课程文件、集数、时长和音频哈希属于提取记录，见来源页 [[software-factories-for-real-engineers]]。术语表和 ADR 的具体效果来自讲者演示，未做对照实验。

## 分析

这套方法把「命名」从写作偏好变成了工程约束。术语表约束 agent 的用词，ADR 约束后来者的改动方向，两者都靠代码评审和 retro 回写维护。

它和 [[任务拆分与上下文]] 的关系是上下游：语言先定，spec 和票才写得准。它和 [[评审与验收]] 的关系是一条反馈回路：评审发现术语违规，retro 把违规变成规则。

## 反例或边界

- 小脚本、一次性原型不一定值得维护术语表。
- 术语表只增不减会变成负担。课程自己用了两整集讲修剪。
- 术语统一不能替代模型设计。名字对了，状态机错了，代码照样是错的。
- 拆 bounded context 有成本。拆得太碎，共享词会重复，跨语境沟通变贵。
- ADR 的三条标准依赖判断。agent 和人可能用同一套标准得出相反结论，课程第 6 集就出现了这种情况。
