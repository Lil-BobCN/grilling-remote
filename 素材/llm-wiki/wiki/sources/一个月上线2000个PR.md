## 一句话摘要

Lauren 讲她一个月上线 2000 个 PR 的方法：先用 Control Glass 让 agent 能验证自己，再把代码库、lint、规则和技能改造成让它默认做对，最后用 GrokBot 接外部事件，触发云端 agent。

## 主要论点

- 做不到从 1 到 5 个 agent 扩到 100 个，根源是不信任。强行并行只会得到低质量 PR、性能退化和缺陷。
- 验证有层次。基础端是验证技能，教 agent 运行应用、采 trace、抓堆快照；另一端是形式化验证，用 Lean、TLA+ 检查业务条件。
- Control Glass 由两部分组成：可重复的命令行工具，以及说明应用怎么工作的功能地图。功能地图的灵感来自网站地图，用自动化维护。
- 验证解决正确性，pstack 和编码技能解决工程质量。两者结合，才能既对又好。
- 代码库是 agent 的记忆。agent 照抄看到的模式，所以要把代码库改造成让坏模式不可能出现。
- 五层约束：代码库、静态分析、规则加 Bugbot 和技能、风格指南与人工评审。她强调按这个顺序投入。
- Dune 是 GrokBot 的 agent 友好框架。原则是让最容易走的路恰好是正确的路，用模块边界和 import 依赖图强制隔离。
- 反模式会像病毒一样传播。Dune 干脆禁止代码注释，因为 agent 会拿注释给临时补丁找理由。
- 团队需要一个园丁角色：清技术债，保留一条统一实现路径，看到坏模式先写 lint 规则拦住。
- GrokBot 负责外部循环，连接 Slack、Datadog、Sentry、PlanetScale，用 Routines 订阅讨论串和告警，自动启动云端 agent。

## 关键数字与案例

- 上个月上线 2000 个 PR（视频口述；B 站简介注明原帖写 2500）。
- 渲染线程预算：60 帧不超 16 毫秒，120 帧不超 8 毫秒。
- 验证技能从加入 Cursor 起做了六个月，持续维护。
- 五层约束和「每次纠正都改环境」是她给出的最终清单。

## 待核验

- 2000 与 2500 的口径差异没有解释。可能是月份不同、统计方式不同，或口述误差。
- Control Glass、Dune、Bugbot、GrokBot Routines 都是听写，需要一手材料核对拼写和产品状态。
- 「五层」的具体分法在口播里略有重叠：规则、Bugbot、技能有时分开说，有时合成一层。
- 分享是公开演讲，演示和数据没有现场验证。
