# 口播素材综览：验证、约束、拆分、验收

8 份口播稿讲的是同一条流水线的不同段。把它们放在一起，能看到四个反复出现的动作。

## 一、先让 agent 能自证

Lauren 把验证称作最重要的 skill。没有验证，人就是 agent 和工具之间的搬运工。Matt 这一侧把证据写进 PR 模板：before 和 after，编译通过不算。两边的共同点是，先解决「怎么知道它做对了」，再谈放手。

## 二、把重复的经验变成约束

Lauren 的修正阶梯从架构往下排，最后才是人审。Matt 的 retro 把会话里的摩擦分成能写成检查、只能写成说明、只能人判断三类。共同点是，能机器执行的别留给人记。

S8 把这件事讲成五层，从代码库、静态分析，到规则加 Bugbot 和技能，最后是风格指南和人工评审。她的建议是按这个顺序投入，人审放最后。Dune 是这五层里最硬的一层：用框架和 import 边界，让错误写法根本表达不出来。

代码库在这里不只是约束，也是记忆。agent 照抄看到的模式，所以团队把经验写进目录结构、lint 和框架，比写进风格指南更可靠。

## 三、按会话预算拆任务

Matt 的 spec 与 ticket 把工作切成能在一个上下文窗口里跑完的单元，票之间用阻塞关系连成图。Lauren 的 playbook 与 sub agent 是另一种切法，按任务类型和职责分。两者都在控制单次会话的负担。

## 四、人退到抽样和定标准

Lauren 每天读提交历史、抽一部分 PR；Matt 让两个新 agent 换桌子评审，人决定哪些建议采纳。共同点是，人不逐行看代码，但保留判断和改规则的权力。

## 四个动作的先后

先有验证，才敢放手；放手之后错误会重复，才需要约束；约束让单次任务变简单，才敢并行；并行之后人看不过来，才需要抽样。顺序反过来做，通常会卡在第一步。

## 还没答案的地方

- 不可程序验证的领域，这套办法能用到什么程度？
- 15 万 token 的阈值随模型变化，怎么更新？
- 两套 skill 拼在一起时，谁负责最终验收？
- 客户直接提需求时，谁把自然语言翻译成 issue？
