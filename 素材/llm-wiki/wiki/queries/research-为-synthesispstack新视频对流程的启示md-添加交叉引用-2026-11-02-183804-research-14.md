# pstack 新视频对流程的启示：交叉引用

## 本页定位

本页为 synthesis 页《pstack 新视频对流程的启示》补齐**交叉引用层**：把一条新的外部证据（meng shao 在 X 上关于 pstack 视频的帖文）接入现有 wiki 的概念网络，标出它印证了什么、与哪些既有页面同构、又在哪些地方与既有记录存在口径差异。

需要先说清楚证据强度：本次可用的外部来源只有一条 [1]，且正文在关键处被截断。因此本页**不试图复述视频内容**，只做三件事——提取可用的元信息、把元信息映射到既有概念页、把无法判定的部分登记为待确认项（见 [[待确认与冲突]]）。

## 证据来源与边界

来源 [1] 是 meng shao 发布在 X 上的一条帖文，标题为「Cursor 官方插件 pstack 的 Agent 工程完全指南」，正文给出两项硬信息并在中途截断：

- **作者身份线索**：pstack 作者为 @poteto，被描述为「Grok @Bot 工程师、React Compiler 核心团队成员」[1]；
- **规模量级**：「她在团队每天合入数百个 PR」[1]，后文缺失。

由此可得与不可得的东西分得很干净：

| 可得 | 不可得 |
|---|---|
| 视频定位是「Agent 工程完全指南」级别的系统性内容 | 视频内的具体流程步骤与阶段划分 |
| 作者的技术背景标签（React Compiler、编译器/基础设施方向） | pstack 的具体命令、目录结构与配置方式 |
| 团队吞吐的量级（数百 PR/天） | 该数字的统计口径（团队总量／单人／含自动生成） |
| 传播渠道与话术框架（「官方插件」「完全指南」） | 视频发布时间、版本对应关系 |

这意味着本页的所有「启示」都属于**结构性推断**，而非对视频内容的转述。凡属推断，下文均显式标注。

## 三个可落地的要点

### 要点一：规模是流程的产物，不是人力的产物

「每天合入数百个 PR」[1] 是这条帖文里信息密度最高的一句。把它与既有记录并置，会得到一个互相印证的量级：[[pstack-作者-每月2500个PR]] 记录的是每月 2500 个 PR（按 20 个工作日折算约 125 个/天），[[一个月上线2000个PR]] 记录的是单月 2000 个 PR 量级。三处说法虽有出入，但都落在一个与「人工逐行评审」不相容的区间里。

对流程的启示因此不是「她的团队很能写」，而是：**当日均合入量超过人工阅读能力两个数量级时，流程必须重构成「Agent 自证 + 抽样验收」，而不是「人写 + 人审」。** 这条推论直接落在 [[技能与流程]]（把重复决策固化为可复用流程）与 [[任务拆分与上下文]]（拆到 Agent 可独立完成的粒度）两页上。

### 要点二：「Agent 工程」被当作一门工程学科来讲

视频标题使用「Agent 工程完全指南」而非「提示词技巧」[1]，这个措辞本身值得记录：它把 agent 的使用从个人技艺抬到**工程约束**层面——环境要可复现、权限要有边界、产出要能自证、验收要能抽样。这与 wiki 中已有的四条主线是同构的：

- 环境先行 → [[环境与约束]]
- 隔离执行 → [[沙箱与自动接单]]
- 自证而非自述 → [[验证与自证]]
- 抽样验收 → [[评审与验收]]

也就是说，新视频在**框架层面**与既有 synthesis（[[口播素材综览]]）方向一致，其增量价值大概率在于具体工程细节，而这部分恰好在截断处丢失。

### 要点三：作者背景解释了方法论的「确定性偏好」（推断）

@poteto 被标注为 React Compiler 核心团队成员 [1]。编译器出身的人做 agent 流程，通常会带有一种可预期的偏好：状态要可观测、变换要可验证、失败要可复现、回滚要廉价。这可以解释为什么 pstack 路线强调规则与验证，而不是强调模型能力——对应 [[信任阶梯]] 中「逐级放权、每级都要求可验证」的结构。

需强调：这是**从身份标签出发的推断**，不是来源 [1] 的陈述，也未见视频内容佐证。

## 与既有叙事的关系

**与 Matt Pocock 路线的关系。** 两者都把「流程」而非「模型」当作变量：pstack 侧强调 agent 工程与验证闭环，[[matt-pocock-skills]] 侧强调 skill 化与 grill→retro 的固定节拍。二者的分工与重叠已在 [[pstack-与-matt-pocock-技能的分工]] 中梳理；新视频若如标题所示覆盖「完全指南」，很可能补上该对比页中 pstack 一侧偏薄的**工程细节**部分。相关素材见 [[matt-pocock-grill-to-retro]]、[[matt-pocock-v1-3]]、[[matt-pocock-skills-实战]]。

**与自动接单路线的关系。** [[Sandcastle]] 走的是「让 AI 自动接单写代码」的接单队列路线（[[matt-pocock-sandcastle]]），pstack 更像「规则 + 验证」的流水线路线。两者是否为同一问题的两种解法，目前证据不足以判断，[[Dune]] 亦待补。

**与既有访谈的关系。** [[一个人如何带一支AI团队-Lauren访谈]] 提供了「一个人带一支 AI 团队」的组织视角，本视频若为同一作者的技术侧讲述，两页可互为表里：一页讲**组织与授权**，一页讲**工程与验证**。

## 待确认与冲突

以下五项需要在拿到视频本体后回填，已同步登记至 [[待确认与冲突]]：

1. **「Cursor 官方插件」的定性。** 来源 [1] 称 pstack 为「Cursor 官方插件」，而 wiki 既有页面多将 [[pstack]] 描述为一套 CLI／工作流工具链。「官方插件」是产品形态的更新，还是转述时的简化，需要以官方文档核对。
2. **吞吐口径差一个数量级。** 「每天数百个 PR」[1] 与「每月 2500 个 PR」（≈125/天）、「一个月 2000 个 PR」在量级上并不冲突，但若「数百」指 500–900，则与月度数差 3–5 倍。可能的口径差异包括：团队总量 vs 单项目、含不含自动生成的依赖升级 PR、以及是否为峰值日。
3. **作者姓名一致性。** @poteto 与 wiki 中出现的「Lauren」是否为同一人，现有来源倾向一致但无直接声明，建议在 [[pstack]] 页统一写法并注明别名。
4. **「Grok @Bot 工程师」这一表述。** 原文在此处格式异常且后文截断，存在转写或 OCR 误差的可能，不宜直接采信为任职信息。
5. **视频与版本的对应关系。** 未知该视频对应 pstack 的哪个版本，因此无法判断其中流程描述是否已过时。
