# Research: 补全「信任阶梯」桥接概念，需要厘清它如何连接前置验证、环境约束与分级评审，并说明 pstack 与 Matt Pocock Skills 中 agent 可信度提升及退到抽样验收的条件。

# 信任阶梯桥接：前置验证、环境约束与分级评审

> 本页补全 [[信任阶梯]] 的桥接层，回答三个问题：信任阶梯靠什么连接前置验证、环境约束与分级评审；agent 的可信度在什么条件下才能提升；以及 pstack 与 [[matt-pocock-skills|Matt Pocock Skills]] 分别在什么条件下允许退到抽样验收。

## 1. 概念基线

### 1.1 五级控制权模型

[5] 给出了一个五级“信任阶梯”模型，核心命题是：人类不会一夜之间信任 AI，控制权需要分级释放。该表以“级别 / 控制权 / 人类角色 / AI 角色 / 典型场景”为列，其中第 1 级为“完全控制”。这说明阶梯的每一级不只规定“AI 能做多少”，也同时规定“人还必须做什么”——控制权与人类角色是一对反向变量。

需要说明的是，现有材料只截取到第 1 级，第 2–5 级的控制权分配与典型场景缺失（见第 7 节）。

### 1.2 爬梯规则

[1] 对 Matt Pocock 与 poteto 对谈的拆解给出了阶梯的动力学规则：每一级的前提都是上一级的信任，而信任只来自“可验证”。这条规则比五级表本身更关键，因为它把“信任”从一种主观态度变成了可操作的工程产物：没有可验证的证据，就不构成升梯理由。

两者合并可得：**信任阶梯是“证据 → 授权”的映射函数**，级别只是这个函数的离散取值。

## 2. 桥接机制：一条链，一个飞轮

### 2.1 三个环节各回答一个问题

| 环节 | 回答的问题 | 对信任阶梯的作用 | 缺失时的后果 |
|---|---|---|---|
| 前置验证 | “这一步做对了吗？” | 提供升梯所需的证据 | 无证据可依，阶梯停在原地 |
| 环境约束 | “这个错还会再犯吗？” | 把一次性证据固化为持久护栏 | 同类错误复发，信任反复清零 |
| 分级评审 | “这一次人要看到多细？” | 按风险分配人的注意力 | 人成为瓶颈，或风险从缝里漏出 |

三者的关系可以概括为：前置验证是阶梯的**输入**，环境约束是防止信任回撤的**止逆机制**，分级评审是阶梯的**输出**。缺少任何一环，阶梯要么爬不上去，要么爬上去也站不稳。

### 2.2 前置验证：阶梯的输入

“信任只来自可验证”意味着验证必须先于授权发生，而不是事后补票。前置验证至少包含两层：

1. **任务本身可验证**：有测试、有原型、有验收标准，能给出通过/不通过的二元信号；
2. **验证发生在授权之前**：先证明这一类任务能被验证，再谈把这一类任务交出去。

在 Matt Pocock Skills 中，`/prototype` 被明确用于“算法验证与原型探索”，`/to-spec` 用于把大型需求拆成可验收的工单[2]。这两步都在为后续授权生产证据。在 pstack 中，对应的是“规划—实作—验收”三阶段中的规划与验收：验收标准在三阶段里被提前定义，实作才有判定依据[3]。

### 2.3 环境约束：阶梯的止逆机制

仅有前置验证，信任会随每次失误回撤；环境约束的作用是让信任只升不降。其做法不是“让 agent 更小心”，而是把失败转化为环境里的一条硬规则，使同类错误在系统层面被挡住。pstack 的表述最直接：错误要变成“系统挡得住的规则”[3]，对应“让错误只犯一次”的思路（见 [[pstack-让错误只犯一次]] 与 [[环境与约束]]）。

Matt Pocock 的 `retro` 技能承担同一职能：读 agent 的对话记录，指出环境应该改哪里[4]。注意这里的因果方向——retro 的产出不是“下次注意”，而是“环境改动”。这正是环境约束与普通复盘的分界线。

[1] 同时提示了一个常见偏差：“约束环境只做了一半”。结合上下文，这大概率指只加了约束、却没有配套的验证或流程改造，导致约束无法转化为可验证的信任；但原文此处被截断，具体所指待确认（见第 7 节）。

### 2.4 分级评审：阶梯的输出

信任阶梯最终要落到“人把注意力花在哪”。分级评审的原则不是“评审越严越好”，而是**按风险分配评审强度**。Matt Pocock 的 `pr` 技能给出的判据很清晰：PR 说明要标出合并风险，只有“退不回来或影响大”的才慢下来逐行读[4]。反过来说，可回滚、影响面小的变更，本来就不需要同等强度的评审。

这条判据是信任阶梯能够节省人力的关键：如果所有 PR 都逐行读，人就是瓶颈，阶梯爬不上去；如果所有 PR 都抽样，风险就不可控。分级评审把“读多细”变成一个由风险决定的变量，而不是由习惯决定的常量。

### 2.5 飞轮：评审发现回流为验证与约束

三个环节不是单向流水线，而是闭环：

```text
前置验证 → 授予自主 → 分级评审 → 发现问题
    ↑                                │
    └──── 新规则 / 新测试 ←── 环境约束 ┘
```

评审中发现的新失败模式，一部分变成测试（增强前置验证），一部分变成规则、钩子或技能（增强环境约束），然后才允许下一轮在更高一级上抽样。缺少这个回流，阶梯就只是一次性的授权，而不是可累积的信任。

### 2.6 两个实现的对照

| 桥接环节 | pstack | Matt Pocock Skills |
|---|---|---|
| 前置验证 | 规划阶段确定验收标准[3] | `/prototype`、`/to-spec`、`/triage`[2] |
| 环境约束 | 错误 → 系统挡得住的规则[3] | `retro` 定位环境改动，且不可自动化[4] |
| 分级评审 | 验收阶段按标准判定[3] | `pr` 标注合并风险，仅高风险细读[4] |

## 3. pstack 中的信任阶梯

pstack 的三阶段是“规划、实作、验收”[3]，与阶梯的三环节存在清晰对应：

- **规划 ↔ 前置验证**：在动手前确定要做什么、怎样算做完，验收标准即验证信号。
- **实作 ↔ 授权执行**：在约束好的环境中执行，允许 agent 自动接单（见 [[沙箱与自动接单]]）。
- **验收 ↔ 分级评审**：按验收标准判定，而不是按感觉判定（见 [[评审与验收]]）。
- **错误 → 规则 ↔ 环境约束**：失败的产出不是被直接修补，而是被抽象成系统能挡住的规则[3]。

pstack 材料中“睡觉时 AI 自己合并”[3] 是阶梯顶端的典型场景：它成立的前提不是 agent 变强了，而是前三个环节已经把可验证性和护栏铺好，人才敢在无人值守时段放行合并。这与 [[Sandcastle]] 所代表的“自动接单”思路共享同一个前提：自动化程度的上限由验证与约束的完备度决定。

## 4. Matt Pocock Skills 中的信任阶梯

把 [2] 与 [4] 的技能按阶梯环节归类：

| 技能 | 阶梯环节 | 作用 |
|---|---|---|
| `/prototype` | 前置验证 | 算法验证与原型探索，先证明可行[2] |
| `/to-spec`、`/triage` | 任务拆分与前置验证 | 把大需求拆成可验收、可分派的工单[2] |
| `pr` | 分级评审 | PR 说明标注合并风险，仅高风险或不可回滚才细读[4] |
| `retro` | 环境约束 | 读对话记录，定位环境应改之处[4] |

其中 `pr` 与 `retro` 构成一对：`pr` 决定“这一次人要花多少注意力”，`retro` 决定“下一次同类变更能不能少花注意力”。前者是消费信任，后者是生产信任。缺少 `retro`，`pr` 的风险判据就只能凭经验，无法随环境改进而放宽。

值得单独强调的是 retro 的不可自动化。材料记录 Matt 明确否定将 retro 自动化[4]。从信任阶梯的角度看，这个立场是自洽的：retro 是环境约束的生产工序，也是整个飞轮中把“人的判断”转成“系统护栏”的关键接口。一旦这个接口被自动化，飞轮就失去了外部校准，阶梯上的授权便不再有新增证据支撑，只能消耗既有信任。

## 5. Agent 可信度提升的条件

综合 [1]–[5]，一类任务要从低一级升到高一级，至少需要同时满足：

- **C1 可验证**：该类任务存在稳定的通过/不通过信号（测试、原型、验收标准）[1][2]。
- **C2 可拆分**：任务能被切成边界清晰的单元，单次变更的影响面可界定[2]。
- **C3 可回滚或影响可控**：失败能被撤回，或影响半径足够小[4]。
- **C4 错误已规则化**：同类失败已经被环境约束挡住，而不是靠人反复提醒[3]。
- **C5 人仍在环内**：retro 与环境设计仍由人掌握，飞轮还在转[4]。
- **C6 操作者具备领域判断力**：[1] 特别指出，能从这套方法中获益的是“有深厚领域知识、又懂一点技术的人”——因为前置验证的验收标准和环境约束的规则，都需要领域知识来定义。

其中 C1 是硬前提，C3 是风险闸门，C4 是防回撤机制。三者缺一，升梯都不成立。C2 决定单次授权的粒度，C5 与 C6 决定这套机制能否长期运转。

## 6. 退到抽样验收的条件

“抽样验收”指人不再逐行审阅每一份 agent 产出，只按比例或按风险抽样，其余交给自动验证与环境护栏。这里的“退”不是能力退步，而是**评审强度的降级操作**：从逐行评审退到抽样评审，前提是信任阶梯已经提供了足够的替代性保障。

允许降级的条件：

1. **验证信号已稳定**：该类任务的测试或验收标准长期给出可靠判定，且抽样未发现遗漏缺陷。
2. **失败可承受**：单次失败可回滚，或影响半径小——这正是 [4] 中“退不回来或影响大才慢下来读”的逆命题。
3. **同类错误已被系统挡住**：错误已经转化为规则，而不是仍依赖评审员记忆[3]。
4. **变更被结构化**：PR 有风险标注、spec 有验收条件，抽样才有可比对的依据[2][4]。
5. **retro 闭环未断**：环境改进仍在持续，抽样释放出来的人力被重新投入到环境约束上，而不是单纯省掉[4]。
6. **授权不跨级**：抽样只适用于已经爬过的那一级任务类型，不能外推到新领域或新任务类型。

**回退触发条件**（应立即恢复逐行评审）：

- 出现不可回滚或高影响变更；
- 进入无历史验证记录的新任务类型；
- 抽样命中缺陷；
- retro 被跳过或自动化，环境规则停止更新；
- 环境本身发生变化（依赖升级、架构调整），旧护栏失效。

回退不是失败，而是阶梯的正常动作：把缺陷写回规则，再重新爬。这与 [[修正阶梯与-correct]] 所描述的修正逻辑一致——修正的终点不是“改对这一处”，而是“让这一类错误不再需要人改”。

## 7. 矛盾、歧义与缺口

1. **五级表不完整**：[5] 只展示了第 1 级“完全控制”，第 2–5 级的名称、控制权分配和典型场景均缺失，无法与 pstack、Matt Pocock 的具体实践逐级对齐。
2. **“约束环境只做了一半”语义不明**：[1] 此处被截断，可能指“只加了约束未加验证”，也可能指“只约束了 agent 未约束流程”，两种解释对桥接模型的含义不同。
3. **retro 不可自动化的理由缺失**：[4] 原文在“Matt 明说……”处截断，只能确定立场，无法确认其论证（是怕失真、怕责任转移，还是怕飞轮失去外部校准）。
4. **没有量化阈值**：所有来源都没有回答“连续多少次成功才能从逐行评审降到抽样”，也没有给出抽样比例。现有材料只能给出定性判据。
5. **pstack 与 Matt Pocock 的术语映射是推断**：[3] 只做总体对比，三阶段与 grill、to-spec、implement、pr、retro 的一一对应并非原文明确表述，参见 [[pstack-与-matt-pocock-技能的分工]]。
6. **两个“信任阶梯”是否同源未知**：[1] 与 [5] 都使用“信任阶梯”一词，但无法确认是否指向同一个模型；若不同源，五级表的权威性需要重新评估。
