# Research: 厘清 Sandcastle 这类沙箱编排工具从“自动接单”扩展到直接接收客户需求时，缺少哪些需求准入、澄清拆解、权限隔离、验证与人工验收环节。

# 从“自动接单”到“接收客户需求”：沙箱编排工具缺失的五个环节

## 摘要

[[Sandcastle|Sandcastle]] 在现有材料中被描述为一个 TypeScript 库：它在受管沙箱内编排 agent，让 agent 针对某个 issue 直接起草 PR [2]；用户可以用自然语言描述期望的流程，并让它运行在 Claude、GPT、Mistral 或本地模型上 [1]；社区实践则是用它在一个 Docker 沙箱里并行调度多个 Claude 会话 [3]。这些能力共享同一个隐含前提：**输入已经是一个边界清晰、可执行、可验收的工作单元**（ticket / issue）。

当输入从“已分诊的工单”换成“客户原始需求”时，原本由人、工单系统与组织流程默默承担的五个环节——**需求准入、澄清与拆解、权限隔离、验证、人工验收**——在工具链中没有对应位置。本文逐项厘清这些缺口、失败模式，以及证据薄弱的环节。

## 1. 被隐藏的前提：issue 已经是“可执行单元”

自动接单流程的起点不是零。一个 issue 能进入队列，通常已经过某人分诊：确认它是缺陷而非咨询、确认范围可界定、确认优先级、确认提问者有权提这个需求。工具从“issue 已存在”这一步开始工作 [2]，因此**它优化的是执行段，而不是理解段**。

这里有一处容易被误读的地方：[1] 所称的“用自然语言描述你想要的，Sandcastle 就构建出 workflow”，指的是**编排流程的编写方式**，不是对客户需求语义的理解与澄清。把前者当成后者，会高估工具在需求侧的能力。[[沙箱与自动接单]] 描述的正是这种“接单—执行”范式，它的成立依赖于单子本身已经足够干净。

## 2. 缺口一：需求准入（intake / admission）

客户需求直接进入时，缺失的第一道关口是**“这条需求该不该进入执行队列”**。工单系统与产品流程通常隐含承担了以下判断，而沙箱编排工具并不提供：

- **分类**：缺陷、功能请求、使用咨询、投诉、重复反馈——只有前两类适合交给编码 agent；把咨询当缺陷修，会产出无人需要的 PR。
- **去重与合并**：同一诉求的多个表述若各自开工，并行能力 [3] 反而会放大冲突。
- **可行性与范围**：需求是否与现有架构冲突、是否该由产品决策而非工程实现。
- **优先级与承诺**：一旦 agent 开出 PR，对外部客户而言可能被理解为“已受理、已排期”，SLA 时钟随之启动。
- **合规与安全筛查**：涉及敏感数据、特定行业监管或客户合同约束的需求，需要人工判定能否进入自动化通道。

失败模式是**准入失守后的连锁反应**：错误的需求被高效实现，返工成本从“澄清一分钟”放大为“评审一个错误 PR”。

## 3. 缺口二：澄清与拆解

客户语言天然带有歧义、缺失的复现步骤、未言明的上下文，甚至 XY 问题（提出的方案并非真实诉求）。自动接单范式假定这些已在工单中被补齐；直接对接客户时，它们必须被**主动生产出来**：

- **澄清循环**：向客户或产品负责人提出结构化问题，并记录答复；
- **假设显式化**：agent 自行补全的每一处歧义都应留痕，而不是静默消失在一个看似合理的 diff 里；
- **验收标准先于实现**：把“客户满意”翻译成可判定的条目；
- **切片**：拆成可独立验证的小步，而非一次交付整块变更。

这一环节与 [[任务拆分与上下文]] 直接对应：拆解粒度既决定上下文是否够用，也决定并行度是否安全——**拆错时，并行调度会让多个 PR 互相冲突**。它也关系到 [[修正阶梯与-correct]]：修正阶梯之所以能逐级升级（小修 → 重规划），前提是存在一份可被违反的规格；没有规格，修正就失去锚点，只剩反复重试。

## 4. 缺口三：权限隔离

沙箱常被当作权限问题的答案。社区讨论中就有这样的表述：如果被权限提示卡住，就“跑在沙箱里” [5]。这混淆了两件不同的事：

| 层次 | 沙箱能提供 | 客户需求场景下的额外要求 |
|---|---|---|
| 执行隔离 | 容器、文件系统、网络边界 [3] | 仍需限定出网白名单与可写路径 |
| 数据隔离 | 通常不涉及 | 跨客户/租户隔离、PII 处理、数据驻留 |
| 凭据隔离 | 通常不涉及 | 按任务授予最小权限、短期令牌、可撤销 |
| 指令/数据边界 | 通常不涉及 | 客户文本是**不可信输入**，可能与系统指令同处一个上下文 |
| 审计 | 通常不涉及 | 谁在何时授权 agent 做了什么、产出流向何处 |

关键在于：**隔离（isolation）不等于授权（authorization）**。一旦 agent 处理的是外部客户提交的文本，工单正文就成为一种可被注入的输入通道；而工具默认拥有读写代码、提交 PR、访问仓库的权限。[[环境与约束]] 讨论的是如何用环境约束行为，但在客户需求场景下，约束必须从“防跑偏”升级为“防越权”。

[6] 提供了一个补充视角：如果没有人对某类决策负责，“agent 会悄悄替你做掉这些决定”。权限缺口的本质往往不是技术性的，而是**授权责任人缺位**。

## 5. 缺口四：验证

验证要回答两个不同的问题：

1. **实现是否符合规格**（verification）——测试、类型检查、回归；
2. **规格是否符合客户意图**（validation）——验收标准、客户试用。

自动接单流程通常有现成测试与维护者的共享上下文作为判据。客户需求则常常两样都缺：既没有测试，也没有公认的“正确结果”描述。更危险的是**自证循环**——同一个 agent 既写实现又写测试，测试通过只证明实现与它自己的理解一致。[[验证与自证]] 指出的正是这一点：自证不等于被验证。

可补齐的做法包括：先写复现测试再修、把每条验收标准映射到至少一个可执行检查、引入独立验证者（不同 agent 或人）、在贴近真实的环境而非仅单元测试中确认、覆盖非功能项（性能、兼容性、可访问性）。

## 6. 缺口五：人工验收与责任归属

[[评审与验收]] 区分了“看过”与“验收”。客户需求场景下，验收还多出几项要求：客户能理解的变更说明、可试用的入口、发布与回滚方案、以及出问题时的升级路径。

[4] 给出的设计模式是：把人的监督嵌入**明确定义的决策点**，在自动化速度与治理之间取得平衡。[6] 更进一步，主张人应“尽早进入并持续留在环内”，并强调架构可理解性与责任归属。但反方观点同样有力：[5] 的讨论认为“人在环内”经常退化为盖章，最后的那个人只是“假装不是瓶颈的瓶颈”。

矛盾指向同一个设计问题：**验收者是否拥有真正的决策权**——能否拒绝、能否要求重做、能否回滚，以及验收记录是否可追溯。若答案是否定的，人工验收只是把瓶颈从开发移到了评审，并未增加控制力。[[信任阶梯]] 提供了分级思路：信任应按任务类别逐级授予，而面向客户、不可逆或涉及数据的变更，可能长期停留在“人审后发布”这一级。

## 7. 五个环节如何串成一条准入流水线

| 环节 | 自动接单时由谁承担 | 直接接客户需求时的状态 | 典型失败模式 |
|---|---|---|---|
| 需求准入 | 分诊人 / 工单系统 | 缺失 | 咨询被当缺陷、重复开工、越权受理 |
| 澄清与拆解 | 提交者 + 维护者默契 | 缺失 | 静默假设、解决错问题、并行冲突 |
| 权限隔离 | 仓库权限模型 | 部分覆盖（仅执行层） | 越权读取、提示注入、凭据外泄 |
| 验证 | 既有测试与 CI | 部分覆盖（易自证） | 测试与实现同源、无验收判据 |
| 人工验收 | 维护者 review + 发布流程 | 缺失或形式化 | 盖章式 review、无回滚、责任不清 |

沙箱编排工具目前稳固覆盖的是表中“执行”一段（把工作单元变成 PR）。上游的准入与澄清、下游的验收与发布，仍裸露在工具之外。可借鉴的做法是把这些环节**显式化为可执行流程**，而非依赖默认上下文——这正是 [[pstack]] 与 [[matt-pocock-skills]] 所代表的“把技能与流程写下来”的路线（参见 [[技能与流程]] 与 [[pstack-与-matt-pocock-技能的分工]]）。

## 8. 矛盾与证据缺口

- **关于人在环内的有效性**：[4][6] 认为结构化的人工监督能提升质量与治理水平；[5] 的实践讨论则认为它常常是表演性合规，甚至成为新瓶颈。目前没有量化证据判断哪种设计在客户需求场景下更优。
- **关于沙箱的作用**：[3][5] 把沙箱当作绕开权限摩擦的手段；本文分析认为这恰恰是客户需求场景下最危险的方向（不可信输入 + 高权限执行）。此判断为综合分析，非来源结论。
- **关于 Sandcastle 本身**：三条相关来源分别是更新日志 [1]、清单条目 [2]、论坛评论 [3]，均未描述其权限模型、准入机制或验收流程；[2] 的条目文本本身即在关键处截断。因此“缺少哪些环节”应读作**基于能力描述的推断**，而非对实现的审计结论。
- **术语滑移**：“自然语言描述即可”[1] 指的是编排流程的编写，容易被误读为需求理解能力。

上述未决点可归入 [[待确认与冲突]] 持续跟踪。

## 9. 值得补充的来源

- Sandcastle 官方文档中的安全模型、权限配置与审计相关页面（用于验证第 4 节推断）
- OWASP Top 10 for LLM Applications（提示注入、过度代理权限）
- NIST AI RMF、ISO/IEC 42001 等治理框架中关于人类监督与责任归属的条款
- 需求工程领域关于歧义检测与澄清提问的实证研究
- 面向客户的编码 agent 事故复盘（越权访问、数据误删类事件）
- spec-driven 工具（GitHub Spec Kit、Kiro 等）在准入与规格化上的实践
- 工单系统（Jira Service Management、Zendesk）的分类体系与 SLA 设计，作为“准入”环节的参照实现

## 10. 小结：一份准入检查清单

在把 Sandcastle 类工具从“自动接单”推向“直接接收客户需求”之前，需要能对以下问题给出肯定回答：

1. 谁决定这条需求进入队列，依据是什么，被拒绝时如何回复客户？
2. 歧义由谁澄清、答复记录在哪里、agent 的假设是否可见？
3. agent 以什么身份、持有哪些凭据、能触达哪些数据，出网到哪里？
4. 除了 agent 自己写的测试，还有什么独立判据证明它做对了？
5. 谁有权验收、能否拒绝与回滚、验收记录能否追溯到来时路？

五个问题分别对应准入、澄清、隔离、验证、验收——也正是当前工具链中尚未被产品化的五段。
