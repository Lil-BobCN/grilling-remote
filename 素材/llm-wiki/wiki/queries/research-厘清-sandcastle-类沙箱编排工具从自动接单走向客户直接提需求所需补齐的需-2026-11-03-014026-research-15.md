# Research: 厘清 Sandcastle 类沙箱编排工具从“自动接单”走向“客户直接提需求”所需补齐的需求接入、工单路由、权限隔离与验收闭环层。

# 从“自动接单”到“客户直提需求”：Sandcastle 类沙箱编排工具的四层补齐

## 摘要与问题界定

[[Sandcastle]] 目前被描述为一个 TypeScript 库：调用方执行一次 `sandcastle.run()`，就能在隔离沙箱中编排 AI coding agent，让它完成任务 [1][3][4]。它的能力高度集中在“执行”这一段——把任务送进沙箱、让 agent 运行、产出代码改动。当需求方从“可信的开发者本人”换成“外部客户”时，缺少的并不是执行能力，而是执行前后的治理层：需求如何进入系统、工单如何派发、权限如何隔离、结果由谁验收。

本文把这四层拆开讨论，并分别说明每层的最小补齐项、它与既有概念的衔接，以及现有材料无法回答的空白。

需要先声明：以下四层框架是对 [1]–[6] 的分析性归纳，并非来源中已有的现成结论。来源 [1][3][4] 基本是同一段产品描述的不同转述；[5] 是一份目标性 issue；[6] 是通用的 Human-in-the-Loop 讨论。**没有任何一份材料直接讨论“客户直提需求”场景**，因此本文大量内容属于推断，已在下文标注。

## 一、现状基线：Sandcastle 是执行原语，不是接单系统

| 维度 | 现状（据来源） | 隐含假设 |
|---|---|---|
| 调用方式 | 单次 `sandcastle.run()` 调用 [1][3][4] | 调用者在场、需求已被人工拆好 |
| 隔离目标 | agent 在 isolated sandbox 中运行 [1][2] | 隔离是为了“不弄坏宿主机/不乱改文件” |
| 运行模式 | “AFK software factory”，完全离开键盘运行 [2] | 中间过程无需人工介入 |
| 定位 | 库（library），可被上层编排 [1][4] | 由调用方自行补齐产品层 |

在本 wiki 的语境里，“自动接单”指的是 agent 从既有任务源（issue、看板、队列）自动领取并执行任务，[[pstack]] 是这类模式的代表；[[Sandcastle]] 提供的是执行侧的沙箱编排原语。两者都止步于“内部可信任务源”，尚未触达“外部客户直接提交需求”这一层。相关背景可参见 [[沙箱与自动接单]] 与 [[pstack-与-matt-pocock-技能的分工]]。

## 二、四层缺口总览

| 层 | 当前状态 | 客户直提后新增的要求 | 最小补齐项 |
|---|---|---|---|
| 需求接入 | 开发者写调用代码 | 异步、非结构化、不可信的外部输入 | 常驻接入服务、结构化采集、澄清回路、准入判定 |
| 工单路由 | 一次调用一个任务 | 多客户、多仓库、并发与优先级 | 会话映射、调度队列、全链路追溯、升级路径 |
| 权限隔离 | 执行级沙箱隔离 | 租户级隔离与越权防护 | 租户作用域、凭证最小化、出口策略、审计 |
| 验收闭环 | 开发者评审 PR | 客户可理解、可签收的验收 | 事先约定 DoD、客户侧验收物、签收与返工循环 |

## 三、需求接入层：把“调用”换成“服务”

`run()` 是库调用，意味着需求在进入系统前必须已经被调用者翻译成任务。客户直提打破了这个前提：

- **常驻接入服务。** 客户需求是异步、随时到达的，而单次函数调用要求调用方在场。需要在 `run()` 之前加一层持久化队列，具备幂等、重试与超时处理——否则一次进程重启就会丢失需求。
- **结构化采集。** 需要把自然语言诉求转成“问题描述 + 验收标准 + 约束 + 优先级 + 期限”。缺少这一步，agent 拿到的是典型的坏上下文，这正是 [[任务拆分与上下文]] 所讨论的问题在上游的放大版。
- **澄清回路。** AFK 模式下 agent 无法中途询问客户。需要异步澄清机制（工单评论、AI 预审问题清单），这与 [6] 提出的 HITL 架构模式一致：在纯 AI 流程中，AI 接收输入后直接执行；在 HITL 流程中，则在关键节点插入人类决策。
- **准入判定。** 需求是否属于代码变更、是否在服务范围内、是否为重复单、提出者是否有权提出（身份与计费归属）。
- **不可信输入标记。** 客户文本是 prompt injection 的天然载体，接入层必须把它标记为不可信，并与其他上下文隔离。

## 四、工单路由层：从“一对一创建”到“派发与调度”

来源 [5] 提供了一份接近路由原语的设计目标：用户创建 session → 系统自动创建对应 sandbox → 在 sandbox 内运行 OpenCode 作为 agent runtime。这是“一个会话对应一个沙箱”的最小映射，但它只解决了**创建**，没有解决**派发给谁、按什么顺序、冲突怎么办**。

补齐项包括：

- **路由决策**：需求应落到哪个仓库、服务、团队或 agent 配置。
- **调度与配额**：优先级、SLA、并发上限、按客户的成本配额（衔接 [[成本与模型]]）。
- **全链路追溯**：工单 ↔ 会话 ↔ 沙箱 ↔ 分支 ↔ PR 的 ID 贯通，否则客户投诉时无法定位是哪次执行出的问题。
- **冲突与依赖**：多个客户同时修改同一模块时的合并顺序与锁策略。
- **升级路径**：agent 失败或置信度低时，转人工处理——这是 [[信任阶梯]] 在路由层的体现。

## 五、权限隔离层：从“执行安全”到“租户安全”

这是四层中最容易被低估的一层。Sandcastle 的隔离目标是执行安全（agent 不要破坏环境），而客户直提需要的是**租户安全**（客户 A 的代码、数据、凭证不能泄漏给客户 B，也不能被恶意输入带出边界）。

当前模型隐含三个假设：调用者可信、仓库内容可信、凭证可以全量授予。客户直提会让这三个假设同时失效。

| 补齐项 | 说明 |
|---|---|
| 租户作用域 | 按客户/工单划分沙箱、文件系统与密钥命名空间 |
| 凭证最小化 | 短时效、按仓库/操作范围授权的 token，而非开发者全权凭证 |
| 网络出口策略 | 限制 agent 沙箱的出网白名单，防数据外泄 |
| 审计日志 | 记录谁提的需求、agent 读了哪些文件、用了哪些凭证、改了什么 |
| 审批门 | 高风险改动（涉及支付、权限、数据删除）必须人工放行，对应 [[信任阶梯]] 的高阶信任 |
| 配额与熔断 | 单租户的资源与成本上限，防止单一客户拖垮整体 |

[[环境与约束]] 里的约束设计在这里需要升级：从“防止手滑”变成“防止越权”。

## 六、验收闭环层：从“PR 评审”到“客户签收”

现状是开发者看 PR（[[评审与验收]]），测试通过即完成自证（[[验证与自证]]），失败则进入 [[修正阶梯与-correct]] 的返工循环。客户直提后，这条链条断在两个地方：客户看不懂 diff；客户不认可“测试通过”等于“需求满足”。

补齐项：

1. **事先约定 DoD（Definition of Done）**：验收标准必须在接单时由双方确认，并尽量转成可自动验证的检查项。这是整层的输入契约。
2. **客户侧验收物**：预览环境、行为演示、录屏，而不是代码差异。
3. **签收 / UAT 循环**：客户确认 → 驳回 → 返工 → 再验收，需要有状态机而非一次性通知。
4. **变更请求治理**：验收中提出的新诉求应开新单，而不是无限扩大原单范围。
5. **结果回流**：验收结论要反哺需求质量评估与 agent 评测，形成真正的“闭环”——需求 → 执行 → 验证 → 客户确认 → 归档/计费，任一环断裂都不算闭环。

[[口播素材综览|口播素材综览]] 中关于“验证、约束、拆分、验收”的讨论可作为这一层的内部参照，但它同样以开发者为中心，尚未覆盖外部客户签收。

## 七、层间耦合与建议落地顺序

四层并非并列，而是有依赖关系：接入层产出的 DoD 是验收层的输入；路由层的租户标识是隔离层的前提；隔离层不成立时，接入层不应对外开放。

建议顺序：

1. **租户隔离与审计**（安全底线）——没有它，开放接入就是事故；
2. **结构化接入与 DoD 约定**（契约）——没有它，验收无法自动化；
3. **路由与调度**（规模）——没有它，只能单客户单任务；
4. **客户验收门户**（体验）——最后做，因为它依赖前三层的输出。

## 八、矛盾、空白与不确定性

1. **“AFK”与 HITL 的张力。** [2] 把 Sandcastle 包装成离开键盘的软件工厂，[6] 则主张关键节点必须有人类决策。在客户直提场景下，接入分诊与验收签收恰恰必须有人参与，AFK 只能覆盖中间执行段。二者并非非此即彼，但产品叙事需要重新划分“哪些环节可以 AFK”。
2. **库与平台的身份模糊。** [1][3][4] 都强调 Sandcastle 是极简库（一次调用），[2] 的描述更像平台/工厂。四层缺口正是“库”与“工厂”之间的距离；来源没有说明 Sandcastle 是打算补齐这些层，还是坚持原语定位、由上层产品补齐。
3. **[5] 的实现状态不明。** 它是一份目标描述（“我希望实现如下能力”），不是已验证的实现；OpenCode 作为 agent runtime 的选择、session 与 sandbox 的生命周期关系，均缺少后续证据。
4. **缺少 Sandcastle 的 API 细节。** `run()` 之外是否有队列、并发控制、密钥注入、沙箱 provider 抽象，来源均未说明。因此文中列出的“缺什么”，有一部分可能是“来源没写”而非“产品没有”——这是本页最大的证据弱点。
5. **没有计费视角的材料。** 客户直提必然带来按客户计量与结算的问题，现有来源只间接涉及 [[成本与模型]]。
6. **术语不统一。** “自动接单”“AFK”“HITL”在不同来源中含义不完全一致，可参见 [[术语表]] 与 [[待确认与冲突]]。

- **工单与路由**：Linear、Jira、Zendesk 的 API 设计与 SLA 实践。
