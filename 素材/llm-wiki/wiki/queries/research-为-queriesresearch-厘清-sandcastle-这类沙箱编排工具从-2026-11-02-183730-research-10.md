# 研究页：Sandcastle 类沙箱编排工具——从「自动接单」到「直接接收客户需求」的缺口与交叉引用

> 本页服务于 `queries/research-厘清-sandcastle-这类沙箱编排工具从自动接单扩展到直接接收客户需求时缺少-2026-11-02-172030-research-4.md`，目标有两个：一是**厘清 "Sandcastle" 指称的是哪一个产品**，二是把新收集的沙箱基础设施资料**挂接到既有 wiki 概念图**上。本页不重复既有页面内容，只做定位、消歧与缺口标注。

---

## 一、一句话结论

新增的三个来源 [1][2][3] 全部在讲**「执行环境」层**——沙箱怎么创建、怎么隔离、怎么预载数据、怎么省钱。它们对「需求从哪来、谁说了算、怎么算做完了」这一层**完全没有覆盖**。因此，把这类工具从[[沙箱与自动接单|自动接单]]推进到「直接接收客户需求」，缺的不是沙箱能力，而是**需求入口、澄清机制与可执行验收标准**这三段。

---

## 二、命名消歧：「Sandcastle」在本 wiki 中有两个所指

这是本页最需要优先处理的问题，否则后续所有引用都会指向错误节点。

| 所指 | 性质 | 本 wiki 对应节点 | 判别特征 |
|---|---|---|---|
| **Matt Pocock 的 Sandcastle** | 让 AI 自动从 issue/任务队列接单并写代码的编排工具 | [[Sandcastle]]、[[matt-pocock-sandcastle]]、[[沙箱与自动接单]] | 关注「接单 → 执行 → 提 PR」闭环，与 [[matt-pocock-skills]] 配套 |
| **TextQL 的 Sandcastle Platform** | 面向 AI 数据分析 Agent 的沙箱基础设施（Provision / Load / Execute / Persist） | 本页（新引入） | 卖点是「沙箱启动时已经认识你的数据」，见 [3] |

建议在 [[Sandcastle]] 页面顶部加一条消歧说明，并在 [[沙箱与自动接单]] 中注明该概念**不覆盖** TextQL 这类「数据感知型沙箱」。二者共享的只有「隔离执行环境」这一层语义，编排逻辑与目标场景完全不同。

## 三、新增来源刻画的能力图谱

### 3.1 AIO Sandbox / AgentRun 路线：通用执行环境

来源 [1][2] 描述的是同一类产品：把 Agent 执行所需的工具链塞进**单个 Docker 镜像**，对外提供统一接口。

- **隔离性**：代码在隔离环境运行，宿主系统不受影响 [1]。注意：来源只承诺「隔离」，未说明隔离边界是容器、microVM 还是别的机制，这直接决定了它能否承载多租户的客户需求。
- **生命周期**：按负载自动创建/销毁沙箱实例 [1]，即 provision 与 teardown 是自动化的。
- **一致性**：统一文件系统 + 统一鉴权，支持镜像定制 [2]。
- **交付效率**：官方口径是「提升 Agent 任务执行与交付效率」[2]，属于定性表述，无基准数据。

对应到既有概念，这一层主要落在 [[环境与约束]]：沙箱即「约束」的物理化——把 Agent 能碰到的世界收缩到一个可丢弃的盒子里。

### 3.2 TextQL Sandcastle 路线：数据感知型沙箱

来源 [3] 是厂商产品页，给出的差异点很明确：**通用沙箱不够用，因为冷启动时没有领域知识**。

- **接口形态**：`POST /v2/sandcastles`，Bearer 鉴权，返回 `sandbox_id`（如 `sc_8f3k...`）[3]。这是标准的「申请—获取句柄」模式，说明沙箱被视为**可寻址的资源**而非一次性进程。
- **预载内容**：60+ 连接器、受治理的指标与 join 本体（governed ontology）、方言适配（dialect reconciliation）、数据粒度上的 RBAC [3]。
- **性能主张**：同一问题下，Agent + warehouse 44s、Agent + 通用沙箱 40s、Agent + Sandcastle 15s，宣称约 3× 加速 [3]。
- **成本主张**：原始 $5.00/1M tokens vs 缓存 $0.50/1M tokens（10×）；单线程成本 432 vs 82 compute units（5.3×）[3]。

这组数字与 [[成本与模型]] 直接相关，但需按第四节的注意事项处理。

### 3.3 两条路线的定位差异

| 维度 | AIO Sandbox [1][2] | TextQL Sandcastle [3] |
|---|---|---|
| 抽象层级 | 通用执行环境 | 领域专用执行环境 |
| 冷启动状态 | 空环境 + 可定制镜像 | 已装载数据本体与权限 |
| 主要收益叙事 | 安全、弹性、省心 | 快、便宜、少 token |
| 适用任务 | 任意代码执行 | 数据分析线程 |

这个对照本身就回答了一部分研究问题：**「通用沙箱」与「领域沙箱」的分野，取决于任务上下文能否被预先编码进环境**。参见 [[任务拆分与上下文]]。

## 四、缺口分析：从「自动接单」到「直接接收客户需求」

既有的[[沙箱与自动接单]]流程有一个隐含前提：**需求已经被人工整理成 issue**。issue 天然携带标题、复现步骤、验收口径和责任人。一旦让系统直接面对客户，这个前提消失。下表把缺口逐项对齐到来源证据与既有页面。

| 环节 | 来源给出的现有能力 | 直接接客户需求时缺什么 | 关联 wiki 页面 |
|---|---|---|---|
| 需求进入 | 无。沙箱只负责「拿到任务之后」[1][2][3] | 需求入口、去重合并、优先级、需求方身份识别 | [[沙箱与自动接单]] |
| 需求澄清 | 无 | 追问机制、歧义消解、假设显式化与回读确认 | [[修正阶梯与-correct]] |
| 上下文装载 | 领域数据可预载（连接器 + 本体）[3] | 非结构化背景：历史决策、既有约束、客户偏好 | [[任务拆分与上下文]] |
| 验收 | 无。只有 Execute 与 Persist [3] | 可执行的验收标准、样例、回归用例 | [[评审与验收]]、[[验证与自证]] |
| 授权边界 | 数据粒度 RBAC [3] | 客户侧可见性边界、跨客户隔离、交付物脱敏 | [[环境与约束]] |
| 成本归属 | token 缓存降本 [3] | 按客户/需求归集的成本与配额，防止单客户拖垮预算 | [[成本与模型]] |
| 自主等级 | 无（默认全自动执行） | 哪类需求可全自动、哪类必须人工确认 | [[信任阶梯]] |
| 流程固化 | 镜像定制 [2] | 需求 intake 的标准化技能与话术 | [[技能与流程]] |

一个值得记录的观察：TextQL 的 RBAC 是**数据权限**（谁能看哪一行的数据），而不是**需求权限**（谁有权提这个需求、谁有权批准交付）。这两者在直接面向客户的场景里必须分开建模，来源 [3] 没有触及后者。

## 六、矛盾、限制与空白

1. **命名冲突（高优先级）**：[[Sandcastle]] 与 TextQL Sandcastle 同名不同物，且都被描述为「沙箱」。若不消歧，[[沙箱与自动接单]] 的读者会得到错误的技术图景。
2. **「通用沙箱是否够用」存在立场对立**：来源 [2] 主张一个镜像整合所有能力即可 [2]；来源 [3] 明确以「off-the-shelf sandbox」为基线并宣称 3× 加速 [3]。但两者测量的任务类型不同（通用代码执行 vs 数据分析线程），**不构成可比的对照实验**。
3. **性能与成本数字均为厂商自述**：44s/40s/15s、$5.00 vs $0.50、432 vs 82 均出自产品页 [3]，未披露模型版本、数据规模、基线定义与测量方法，不可作为中立基准引用。
4. **来源自身的空白**：来源 [3] 的 FAQ 只列出了问题（凭证安全、数据规模、冷启动与隔离），**答案未包含在采集内容中**。其中「cold start and isolation」恰是本议题最关键的一项，建议补采。
5. **隔离强度未定**：来源 [1] 只说「隔离环境」，未说明是容器级还是更强隔离。面向外部客户时，这一项是硬约束而非细节。
6. **缺少反例**：三个来源均为产品/实践宣传材料，没有失败案例、逃逸事件或成本超支的记载，存在明显的幸存者偏差。

## 七、建议补采的来源

- TextQL Sandcastle 的**官方文档与定价页**，尤其是 FAQ 中「cold start and isolation」「credentials」两项的完整答案。
- AIO Sandbox 的**开源仓库与安全模型文档**，确认隔离边界（容器 / microVM / 进程级）。
- 一份**独立第三方基准**，用同一模型、同一数据集对比通用沙箱与领域沙箱，用于校验 [3] 的 3×/5.3× 主张。
- 需求管理侧的成熟流程资料（如 Linear Triage、Zendesk 工单分级），用于补上「需求入口」这一整段空白。
- 关于 human-in-the-loop 需求澄清的学术工作，用于支撑 [[修正阶梯与-correct]] 在客户场景下的扩展。
- 多租户沙箱隔离的安全研究（沙箱逃逸、侧信道），用于评估直接接客户需求时的风险面。
