需要预先说明的是：本次收集到的三份来源**均未直接讨论 Spec Kit 或 token 预算**。[1] 讲的是提示层面的拆分模式，[2] 讲的是多智能体工作流的组合与推荐式编排，[3] 讲的是“Agent 需要工作流才有价值”这一层论断。因此下文中“Spec Kit 是拆分的显式化载体”“拆分粒度受 token 预算约束”等论断属于**跨来源推理**，而非来源直述，已在相应位置标注。

## 一、任务拆分的三种基本形态

### 1.1 串联提示（prompt chaining）

[1] 给出的第一种模式是：对于涉及多个连续步骤的复杂任务，把每个步骤设为一个独立提示，前一步的输出作为后一步的输入。其价值在于**把一次性的巨型上下文切分成若干次小上下文**——每次调用只需装载当前步骤所需的信息。

这一模式对应 [[任务拆分与上下文]] 中的“串行拆分”侧，也与 [[技能与流程]] 中“把流程固化为可复用步骤序列”的主张同构：拆分一旦稳定，就可以被写成技能。

### 1.2 并行子任务

[1] 同时指出可以把任务拆成多个子任务并**并行**运行。并行拆分与串行拆分的关键差别不在速度，而在**上下文隔离**：每个子任务持有独立的上下文片段，互不污染，代价是需要在汇合点做结果合并与冲突消解。

在 [[pstack]] 与 [[matt-pocock-skills]] 的实践中，这类“汇合点”往往就是 [[评审与验收]]；并行产物越多，验收环节的权重越高。相关分工差异见 [[pstack-与-matt-pocock-技能的分工]]。

### 1.3 层级式分解与动态编排

[2] 描述了一种更进一步的形态：**agent 节点生成任务分解，并迭代地向 agent recommender 查询**，完成后由抽取阶段产出结果。与 [1] 的静态拆分相比，这里的分解是**运行时生成、可迭代修正**的，拆分粒度由调度器动态决定，而不是由人预先写死。

[3] 从反面论证了同一件事：AI Agent 本身用途有限，只有赋予角色、目标和结构，通过工作流组织起来才产生实际价值——即**拆分的收益主要来自结构，而非来自模型能力**。

这三种形态可以并置为一条演进线：静态串联 → 静态并行 → 运行时层级编排。[[信任阶梯]] 描述的“随着可靠性上升逐步放权”在此体现为：拆分方式越动态，对 [[验证与自证]] 与 [[环境与约束]] 的依赖越强。

## 二、上下文：拆分真正的收益项

把三份来源并读，可以得到一个比“拆分提高准确率”更精确的表述：

- 拆分的直接作用是**限制单次调用的上下文规模与职责边界**；
- 准确率提升是这一限制的**副产品**，而非拆分本身的属性；
- 因此拆分粒度的上界由“任务可独立完成所需的最小上下文”决定，下界由“步骤间交接成本”决定。

[2] 中的 recommender 机制可以理解为对这一权衡的工程化回答：分解粒度不再由人一次拍定，而是通过迭代查询逐步收敛。这与 [[修正阶梯与-correct]] 的“小步纠偏优于一次性做对”是同一思路在不同层面的应用。

相反的一极是 [[Sandcastle]] 所代表的 [[沙箱与自动接单]] 模式：任务以“工单”为单位整块交给 agent，拆分发生在工单边界而非工单内部。这条路线把上下文管理外包给了工单描述的清晰度。

## 三、Spec Kit 作为“规格→任务”的显式拆分载体

> 以下为推理段落，来源 [1][2][3] 未直接涉及 Spec Kit。

若把 `specticket` 读作 Spec Kit / spec ticket，则它在上述框架中的位置相当明确：**它是把 [1] 的“步骤划分”从提示技巧提升为文档产物的一种载体**。规格文档固定了“要做什么”，任务列表固定了“分几步做”，两者共同构成拆分结果的可审查版本。

这带来两个可检验的推论：

1. **可审查性**：拆分方案成为可 diff 的文本，因此可以进入 [[评审与验收]]，而不只是藏在某次提示里。
2. **可复用性**：同一份规格可派生出不同粒度的任务列表，从而适配不同的 token 预算——这正是 [[技能与流程]] 中“流程资产化”的典型形态。

与 [[matt-pocock-skills]] 的 implement-spec 类技能对照，可以看到同一模式的不同实现：规格是输入，任务是中间产物，PR 是输出。参见 [[matt-pocock-v1-3]] 与 [[matt-pocock-grill-to-retro]]。

## 四、token 视角下的拆分粒度

> 以下同样为推理段落，来源未直接给出 token 数据。

把 `tok` 读作 token 后，拆分决策就变成一个带约束的优化问题：

- **上下文窗口约束**：单步所需上下文必须装得下一次调用；
- **交接损耗**：每次步骤切换都要重新装载背景，串行步骤越多，重复装载越多；
- **并行度约束**：并行子任务会同时占用配额，[[成本与模型]] 中的成本结构直接决定并行是否划算；
- **验收成本**：拆分越细，[[评审与验收]] 的单元数越多，人工复核负担上升。

这解释了为什么 [[pstack]] 这类高吞吐实践（每月数千 PR，见 [[pstack-作者-每月2500个PR]] 与 [[一个月上线2000个PR]]）必须同时具备强自动化验收，否则拆分越细、总成本越高。[[成本与模型]] 与 [[任务拆分与上下文]] 在此是同一个问题的两面。
