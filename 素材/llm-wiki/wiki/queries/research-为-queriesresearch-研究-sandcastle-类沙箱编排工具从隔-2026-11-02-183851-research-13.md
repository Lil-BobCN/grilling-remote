# Sandcastle 类沙箱编排工具的三层演进：隔离执行、自动接单与客户需求入口

> **页面类型**：研究综合（Synthesis）  
> **服务查询**：[[research-研究-sandcastle-类沙箱编排工具从隔离执行自动领取任务到直接接收客户需求-2026-11-02-170228-research-4|研究：Sandcastle 类沙箱编排工具从隔离执行、自动领取任务到直接接收客户需求]]  
> **证据范围**：[1]–[5]  
> **状态**：隔离执行层证据较充分；自动接单层与客户需求入口层证据不足，部分结论为架构推导。

## 摘要

现有五份材料共同勾勒出“沙箱作为 Agent 运行时基础设施”的轮廓：它需要提供隔离、受控、可编程的工作空间，并能承载代码执行、浏览器操作与文件操作 [2][3][5]。其中，风险分级观点明确指出“无沙箱”只适合开发者工具；LLM 生成的代码若直接以进程全权权限运行，风险不可接受 [1]。GKE 文档也把 AI 生成代码视为不受信任代码，主张在沙箱 Python 环境中执行和测试 [4]。

但若把研究对象扩展到 [[Sandcastle]] 这类“沙箱编排工具”，现有材料只充分覆盖了第一层——**隔离执行**。第二层**自动领取任务**所需的队列、租约、幂等、任务上下文与权限模型，材料仅以“多任务独立运行、跨步骤状态延续”一笔带过 [2]；第三层**直接接收客户需求**所需的澄清、规格化、授权、验收与审计，则基本没有被这些来源覆盖。换言之，沙箱解决的是“在哪里跑”，Sandcastle 类工具真正要解决的是“谁把什么任务交给它跑，以及跑完由谁验收”。

## 一、三层能力模型：信任边界而非功能清单

把 Sandcastle 类工具的发展理解为一条信任边界扩张路径，比把它理解为功能堆叠更准确。

| 层级 | 能力描述 | 现有证据 | 主要风险 | 关联页面 |
|---|---|---|---|---|
| L0 宿主直跑 | 无沙箱，直接 `exec()` 或子进程调用，零隔离 | [1] 将无沙箱列为级别 0，仅适合开发者工具 | LLM 代码获得进程全权权限 | [[环境与约束]] |
| L1 隔离执行 | 容器、虚拟机或受限 Python 环境；支持代码、文件、浏览器、终端 | [2][3][4][5] | 沙箱逃逸、凭据泄露、网络滥用 | [[沙箱与自动接单]] |
| L2 自动接单 | 从任务源领取任务，调度、并发、重试、回写 | [2] 仅提多任务独立与状态延续；[[Sandcastle]] 提供实践样本 | 重复领取、任务漂移、失控重试 | [[任务拆分与上下文]]、[[技能与流程]] |
| L3 客户需求入口 | 客户直接提交自然语言需求，完成澄清、规格化、授权、验收 | 现有来源未覆盖；[5] 仅提供浏览器、终端、代码一体的技术前提 | 提示注入、越权、范围蔓延、责任不清 | [[评审与验收]]、[[信任阶梯]] |

表中最关键的是每一层引入的新信任边界：L1 面对不可信的 AI 生成代码，L2 面对可能不遵守流程的自动执行者，L3 面对外部客户输入。隔离深度应随风险增加，而不是一律追求最重沙箱 [1]。这与 [[信任阶梯]] 的思路一致：能力开放程度应与验证能力同步提升。

## 二、隔离执行层：任务内共享，任务间隔离

[2] 对沙箱的界定超出“跑一段代码”：沙箱要提供可编程、受控的工作空间，支持跨步骤数据共享、多轮交互中的状态延续，以及多个任务的独立运行。这里存在一个关键矛盾：同一任务内部需要共享文件、变量与会话状态；不同任务之间必须强隔离，避免状态、凭据和副作用串扰。Sandcastle 类工具若只为每个任务启动一个容器，却不管理 workspace 的生命周期，仍会在“续跑”和“并发”上出问题。

从来源可以确认的执行层能力包括：

- **代码执行隔离**：无沙箱时 LLM 代码以进程全权权限运行 [1]；GKE Agent Sandbox 则在沙箱 Python 环境中隔离不可信代码 [4]。
- **文件与工作区**：沙箱是可编程、受控的工作空间，需要支持跨步骤数据共享 [2]；PPIO Agent 沙箱提供文件操作能力 [3]。
- **浏览器与终端**：PPIO 的云沙箱集成代码运行、浏览器访问与文件操作 [3]；AgentRun AIO Sandbox 把浏览器、终端和代码执行集成在一个容器中，通过 SDK 让 LLM 驱动复杂 Web 任务 [5]。
- **多任务独立运行**：运行时需要支持多个任务的独立运行，避免互相污染 [2]。

来源未覆盖但 Sandcastle 类工具必须具备的能力包括：凭据代理与最小权限、网络白名单、工作区快照与回滚、CPU/内存/时间配额、沙箱冷启动优化。这些属于架构推导，不是上述来源的直接结论，但与 [[环境与约束]]、[[成本与模型]] 直接相关。

## 三、自动接单层：沙箱之上需要“任务语义”

“自动领取任务”不是沙箱能力，而是编排能力。[3][4][5] 提供的是执行环境或 SDK，不是任务队列。[[Sandcastle]] 所代表的“自动接单”模式说明任务源可以接到执行器，但要产品化，至少需要以下语义：

1. **任务源与规范化**：把 Issue、工单、PR、消息等不同来源转换为统一任务对象，并附带目标、约束与完成定义。对应 [[任务拆分与上下文]]。
2. **领取与租约**：通过 claim/lease/timeout 机制避免重复执行；租约过期后任务可被回收。
3. **幂等与副作用控制**：同一任务重试时不应重复发 PR、重复评论或重复触发外部操作。
4. **状态机与回写**：至少区分 queued、running、blocked、review、done 等状态，并把结果回写任务源。对应 [[评审与验收]]。
5. **预算与并发控制**：为每个任务设置 token、时间与费用上限，避免单个任务拖垮整体队列。对应 [[成本与模型]]。
6. **上下文装配**：把规格、代码库约束、历史讨论和相关文件注入执行环境。对应 [[技能与流程]]。

[2] 提到多轮交互中的状态延续，这意味着编排层要把任务状态持久化在沙箱之外；否则沙箱重启或迁移就会丢失进度。由此可以推导：**沙箱可以是无状态的执行单元，编排层才是有状态的控制面**。这也解释了为什么单纯比较沙箱隔离强度，无法判断一个 Sandcastle 类工具是否成熟。

可与 wiki 中 [[pstack]] 的 PR 流水线、[[matt-pocock-skills]] 的 spec→implement→review 技能流程对照阅读；三者分别强调 PR 级任务、技能化流程与沙箱执行，但共同点是都需要把“任务状态”放在执行环境之外。

## 四、客户需求入口层：把不可信输入挡在规格边界外

“直接接收客户需求”常被理解为接一个聊天窗口或工单表单，但真正的变化是输入从“已拆好的任务”变成“未澄清、可能带恶意指令、包含业务承诺的自然语言”。这至少引入四类新问题：

- **范围问题**：客户说“优化一下”不是可执行任务。需要需求前台追问目标、边界、优先级，产出规格与验收标准。对应 [[任务拆分与上下文]]，也可参考 [[matt-pocock-skills]] 的规格驱动流程。
- **授权问题**：客户 A 的数据与客户 B 的沙箱必须隔离；凭据应按租户和任务最小化；高风险操作需要人工批准。对应 [[信任阶梯]]。
- **验收问题**：自动测试通过不等于客户满意；需要预览、试运行、人工评审与签收。对应 [[评审与验收]]、[[验证与自证]]。
- **审计问题**：记录客户输入、工具调用、产物与审批人；出现争议或事故时能够回溯。现有来源未涉及，但对客户侧产品是必要条件。

安全上还有一个容易被忽略的点：客户输入可能包含提示注入，诱导 Agent 读取密钥、访问内网或执行越权操作。宿主隔离只能防止代码逃逸，不能阻止“被授权后的滥用”。[1][4] 把 AI 生成代码视为不可信代码；同理，客户输入也应被视为不可信输入，不能直接变成 shell 命令或持有生产凭据的执行指令。

综合来源后的建议边界如下：

```text
客户渠道 → 需求前台（澄清、规格化、授权）
        → 任务队列（领取、租约、幂等）
        → 执行沙箱（文件、网络、浏览器、代码）
        → 验证与验收（测试、预览、人工评审）
        → 交付与审计
```

其中，**需求前台与执行沙箱应分离**：前台可以接触客户，但不持有生产凭据；沙箱持有最小凭据，但不直接面对客户。AgentRun AIO Sandbox 的浏览器、终端、代码一体化能力 [5] 提供了“让 Agent 操作 Web”的技术前提，但“能操作浏览器”不等于“能安全地接收客户需求”。

## 六、矛盾、缺口与证据强度

| 来源 | 类型 | 可用结论 | 局限 |
|---|---|---|---|
| [1] | 概念性文章 | 按风险匹配隔离深度；无沙箱仅适合开发者工具 | 仅见级别 0 片段，无法核验完整分级 |
| [2] | GitHub 章节材料 | 沙箱是受控工作空间；需支持状态延续与多任务独立 | 偏架构原则，无实现与数据 |
| [3] | 厂商文档 | 云沙箱集成代码、浏览器、文件操作 | 产品视角，缺独立评测 |
| [4] | 云文档 | Python 环境隔离不可信 AI 代码 | 范围较窄，偏代码执行 |
| [5] | 厂商文档 | 浏览器、终端、代码一体化容器 | 不等于客户需求入口 |

主要矛盾与缺口如下：

- **“沙箱”术语粒度不一致**：[2] 指运行时工作空间，[3] 指云服务，[4] 指 Python 执行环境，[5] 指一体化容器。比较不同方案时，必须先说明隔离粒度与接口边界，否则容易把“沙箱产品”与“沙箱抽象”混为一谈。参见 [[术语表]]。
- **L0 的边界可能被误读**：[1] 说无沙箱只适合开发者工具，但 Sandcastle 本身也是开发者工具。关键不在“用户是不是开发者”，而在“执行的代码是否可信”。Sandcastle 执行 AI 生成代码，因此仍应归入需要隔离的场景。
- **厂商材料偏向能力展示**：[3][4][5] 均来自产品/云文档，缺少独立的安全评测、逃逸测试与成本数据；不能仅凭“隔离”声明推断生产可用。
- **自动接单证据不足**：[2] 只给出运行时需求，没有队列、租约、幂等协议；需要 Sandcastle 源码或官方文档补证。
- **客户需求入口基本空白**：没有来源讨论客户澄清、授权、验收与责任边界；[5] 的浏览器能力只是技术前提。
- **“直接接收客户需求”存在歧义**：是指客户直接提交需求，还是 Agent 主动从客户渠道领取需求？两者治理模型不同，需要在查询页中明确。可记录到 [[待确认与冲突]]。
- **缺少量化数据**：冷启动时间、单任务成本、隔离强度、逃逸测试结果、任务成功率均无来源支撑。

## 七、建议补充来源

1. Sandcastle 官方仓库与架构文档：任务领取、workspace 生命周期、并发与权限模型。
2. GitHub Issues、Linear、Jira 的 API 与 webhook 文档：claim、lease、idempotency 的工程模式。
3. gVisor、Firecracker、Kata Containers、E2B、Daytona、Modal 等运行时文档：隔离强度、冷启动与快照能力。
4. OWASP Top 10 for LLM Applications：提示注入、敏感信息泄露、过度代理等风险。
5. 多租户 SaaS 安全与合规材料：SOC 2、ISO 27001、租户隔离与审计日志。
6. 规格驱动开发与验收标准资料：把客户需求转成可测试 spec 的实践。
7. 独立基准：SWE-bench 类任务成功率、沙箱逃逸测试、每任务成本。
8. 现有 wiki 中的实践材料：[[matt-pocock-sandcastle|Sandcastle：让 AI 自动接单写代码]]、[[pstack-让错误只犯一次|pstack：让错误只犯一次]]，用于对照自动接单与评审流程。

## 八、结论

对 Sandcastle 类工具而言，沙箱是必要条件，不是充分条件。现有来源能支撑“如何安全地执行 AI 生成的代码”，但不足以回答“如何自动领取任务”和“如何直接接收客户需求”。后两者要求把沙箱嵌入一个有状态、可审计、可验收的编排系统，并在客户输入与执行环境之间建立规格边界与权限边界。

下一步研究应优先补齐任务领取协议、租户隔离、需求澄清与验收流程，而不是继续比较沙箱隔离的绝对强度。相关讨论可归入 [[沙箱与自动接单]]、[[评审与验收]] 与 [[信任阶梯]]。
