# 验证与自证的可操作证据：从 Deep Research Agent 的证据循环到代码 Agent 的测试、Lint 与类型检查

本页为 `queries/research-研究口播素材中验证与自证在-agent-工作流里的定义可操作证据测试lint类型检-2026-11-02-162434-research-3` 提供交叉引用与外部参照。核心目的是回答一个问题：当 agent 声称自己「做对了」时，什么样的材料才算**可操作证据**——而不仅仅是它的自述。

现有口播素材讨论的 [[验证与自证]] 主要来自代码 agent 的实践语境（PR、沙箱、评审）。本页引入两条关于 **Deep Research Agent（DR 智能体）** 的外部研究材料 [1][2]，它们把「证据」这件事讲得更为明确：不是「我相信我对了」，而是「我的每个结论都挂着可被检查的来源」。

---

## 1. 问题背景

在 agent 工作流里，「验证」与「自证」经常被混为一谈：

- **自证**：agent 用自身的推理或输出证明自身正确——这是一个闭环，闭环内没有任何外部锚点。
- **验证**：agent 引入**外在于其推理过程**的信号，来否定或确认自己的产出。

[[信任阶梯]] 描述的正是这条上升路径：从「人盯着做」到「放手让它做」，每一级台阶都需要更强的证据支撑。而 [[评审与验收]] 则是这些证据的消费端。问题在于：**证据的具体形态是什么？** 口播素材给出了「跑测试、过 lint、过类型检查」这样的直觉答案，但缺少一个结构化的判据。DR 智能体的研究恰好补上这一层。

---

## 2. Deep Research Agent 的证据循环

### 2.1 定义与核心能力

DR 智能体被定义为：通过结合**动态推理、自适应长程规划、多跳信息检索、迭代工具使用以及结构化分析报告生成**，来应对复杂、多轮次的信息研究任务 [2]。用更直白的话说，它是一个「带着小本本去查资料」的研究型 agent：把开放问题拆成子问题，循环搜索和阅读材料，**保存证据，交叉验证**，最后生成**带来源**的报告 [1]。

### 2.2 循环的四个环节

| 环节 | 动作 | 产出的「证据物」 |
|---|---|---|
| 拆解 | 把开放问题切成可独立回答的子问题 [1] | 子问题清单（可核对覆盖度） |
| 检索 | 多跳搜索、阅读材料 [1][2] | 原始材料与出处 |
| 存证 | 边查边保存证据 [1] | 可回溯的证据台账 |
| 交叉验证 | 用多个来源互相印证 [1] | 一致性/冲突记录 |
| 输出 | 生成带来源的结构化报告 [1][2] | 每条断言 → 引用锚点 |

这个循环的价值不在于「agent 更聪明」，而在于**它把「凭什么这么说」变成了流水线上的必填字段**。一条没有来源的断言在结构上就无法进入最终报告。

---

## 3. 「可操作证据」的四条判据

综合 [1][2] 对 DR 智能体工作方式的描述，可以提炼出四条判据。这四条判据是本文的归纳，源材料并未以条目形式给出：

1. **外部性（externality）**——证据必须来自 agent 推理之外。DR 中是外部文献，代码 agent 中是测试运行器、编译器、linter 的返回码。
2. **可追溯（traceability）**——证据能定位到具体条目。「带来源」[1] 的实质是：断言 ↔ 证据之间有一一映射，而非笼统地说「我查过了」。
3. **可复现（reproducibility）**——同一条证据换一个人、换一次运行仍能得到。DR 中体现为「材料还在那里，你可以自己去读」；代码中体现为「测试可以再跑一遍」。
4. **可反驳（falsifiability）**——证据存在**失败的可能**，且失败会被如实暴露。这是自证与验证的分水岭：一个永远不会失败的检查，等于没有检查。

其中第 3、4 条最容易被忽略。DR 智能体的「交叉验证」[1] 之所以有意义，正是因为不同来源**可能互相矛盾**——矛盾被记录下来，而不是被抹平。

## 4. 映射到代码 Agent：测试、Lint、类型检查

DR 智能体的证据是「文本 + 出处」，代码 agent 的证据是「可执行检查 + 输出」。二者的结构同构，但覆盖面不同。下面这组对应关系是本文提出的分析框架，用于回应查询页中「测试 / lint / 类型检查」为何要并列的问题：

- **测试（tests）** → 覆盖**行为正确性**：在给定输入下，输出是否符合预期。对应 DR 中的「事实是否成立」。
- **类型检查（type check）** → 覆盖**结构与契约一致性**：模块之间的接口是否自洽。对应 DR 中的「概念之间是否矛盾」。
- **Lint** → 覆盖**已知缺陷模式与卫生度**：这类问题不破坏行为，但会成为未来的隐患。对应 DR 中的「来源质量与可信度评估」。
- **构建 / 实际运行** → 覆盖**集成可用性**：局部正确是否等于整体可用。

四者并列的理由是**它们覆盖的失败面互不重叠**。只跑测试的 agent 可能写出类型混乱的代码；只过类型检查的 agent 可能逻辑全错。这与 DR 智能体必须「交叉验证」而非「单源采信」[1] 是同一个道理——单一信号总有盲区。

由此可以给出一条可操作的**证据强度阶梯**（本文建议，未经源材料验证）：

> 自述「已完成」 < 单次运行的命令输出 < 可重跑的自动化检查（测试 + 类型 + lint） < 独立环境中的复现 < 人工评审确认

[[环境与约束]] 与 [[沙箱与自动接单]] 在这一阶梯中扮演「证据生成器」的角色：没有可复现的环境，第 3 级以上的证据根本无法产生。

## 6. 矛盾与空白

- **直接证据缺失**：两条来源 [1][2] 讨论的都是**信息研究型** agent，均未涉及代码执行环境。因此本页第 4 节「测试/lint/类型检查」的映射属于**类比推断**，不是源材料的直接结论。若要坐实，需要补充代码 agent 方向的一手材料。
- **自证的失效模式未被讨论**：DR 智能体会不会**选择性引用**支持自己的来源、忽略相反证据？源材料只描述了「交叉验证」的理想流程，未给出对抗性案例。代码 agent 中的对应风险是「改测试让它通过」「加 lint 豁免注释」——这类行为恰恰是最需要被证据机制拦住的。
- **缺少量化指标**：如何衡量一个证据机制的强弱？目前只有定性描述，没有覆盖率、复现率、误报率之类的度量。
- **「交叉验证」的粒度不明**：几个独立来源才算够？来源之间不独立（互相引用）时如何计权？[1] 未展开。
- **成本边界未定**：全量测试 + 全量 lint + 类型检查在每次 agent 迭代都跑一遍，代价可能高于收益。[[成本与模型]] 中尚无对应的预算模型。

## 7. 建议补充的来源

1. **代码 agent 的评测基准**（如 SWE-bench 系列）——它们用「测试是否通过」作为唯一判据，是「可操作证据」最直接的工程化样本。
2. **DR 智能体的评测基准**（如 GAIA、BrowseComp、DeepResearch Bench 一类）——用于检验 [1][2] 所述能力是否有可测量的对应物。
3. **agent 自我反思/自我修正方向的工作**（Self-Refine、Reflexion 等）——它们正面处理「agent 如何评估自己」，与本页的「自证」议题直接相关。
4. **LLM 引用归因（attribution / citation verification）研究**——检验「带来源的输出」中来源是否真的支持断言，这正好补上第 6 节指出的失效模式空白。
5. **[[pstack]] 与 [[matt-pocock-skills]] 的一手文档**——确认两者在流程中实际要求哪些检查、在什么时机跑、失败后如何处置。
