# 沙箱编排工具 Sandcastle：交叉引用与辨析

## 摘要

本页汇总针对「Sandcastle 这类沙箱编排工具」的补充研究，目标是为研究页 `queries/research-…-2026-11-02-171425-research-1.md` 建立与既有 wiki 条目的交叉引用。核心发现有三点：其一，**「Sandcastle」是一个同名但不同指的名称**，至少存在两个互不相关的产品——[[Sandcastle|AI Hero 的 Sandcastle]]（面向编码 agent 的沙箱编排）与 TextQL 的 Sandcastle（面向数据分析负载的 agent 沙箱）[1][2]；其二，AI Hero 版本公开的机制描述高度浓缩，只暴露「单一入口 `sandcastle.run()` + 可配置 branch strategy」这两个要点[1]；其三，这两个要点恰好对应既有 wiki 中 [[沙箱与自动接单]] 与 [[环境与约束]] 所描述的抽象，因此本页的主要价值在于**消歧 + 映射**，而不在于新增机制细节。

> 证据强度说明：本页仅基于两条摘要级来源[1][2]，均为产品自述页面，缺少文档全文、版本号与实现细节。下文凡超出源文的推断均已显式标注。

## 2. AI Hero Sandcastle 的工作模型（源文可支撑的部分）

源文把工作流压缩成两步[1]：

1. **调用**：通过单一入口 `sandcastle.run()` 唤起 agent。所有任务走同一 API，意味着「接单」这一动作被抽象为一个函数调用，而非一组手工脚本。
2. **隔离**：Sandcastle 负责给 agent 做沙箱化，隔离边界由 **可配置的 branch strategy** 决定。

由此可做一个有限推论（**推断，非源文陈述**）：branch strategy 可配置，说明隔离粒度是以 Git 分支/工作区为单位而非以进程或容器为单位——每个 agent 任务落在自己的分支上，产物以分支（进而 PR）形式回收。这与 [[matt-pocock-sandcastle]] 所呈现的「让 AI 自动接单写代码」是同一套思路的接口化版本，也与 [[沙箱与自动接单]] 中「沙箱 + 接单」的组合描述一致。

需要强调的是，源文**没有**说明：branch strategy 有哪些可选值、并发上限、失败重试、权限与网络策略、成本模型。这些是当前知识库的明确空白（见 §6）。

## 3. 「沙箱编排工具」的共性抽象

把两条来源并置，可以抽出这类工具的最小公共结构（**综合推断**）：

- **执行隔离层**：为 agent 提供可丢弃的运行环境（AI Hero 用分支策略[1]；TextQL 用面向分析负载的专用沙箱[2]）。
- **任务分发层**：把「要做什么」以统一入口投递给 agent（`sandcastle.run()`[1]）。
- **产物回收层**：把 agent 的产出以可评审的形态交回（推定为分支/PR）。
- **约束注入层**：把环境边界、可用工具、验证方式预先写进沙箱，而非事后审查——对应 [[环境与约束]] 与 [[技能与流程]]。

这条抽象的用途是：当 wiki 需要讨论 pstack、Matt Pocock Skills、Sandcastle 三者的分工时，可以按「谁负责哪一层」来定位，而不是按产品名罗列。相关讨论见 [[pstack-与-matt-pocock-技能的分工]]。

## 5. 与既有页面的关系（叙述版）

- **与 [[matt-pocock-sandcastle]] 的关系**：该页讲的是「流程长什么样」，本页讲的是「这套流程被封装成什么接口」。二者应互为上下游引用，而不是互相替代。
- **与 [[pstack]] 的关系**：pstack 侧重「让错误只犯一次」的反馈闭环与修正阶梯（见 [[修正阶梯与-correct]]），Sandcastle 侧重「把 agent 关进可丢弃的分支里」。两者可组合：沙箱提供隔离，修正阶梯提供隔离内的收敛机制。分工细节归入 [[pstack-与-matt-pocock-技能的分工]]。
- **与 [[验证与自证]] 的关系**：沙箱容易被误读为「验证」。需明确：branch strategy 提供的是**可回滚性**，验证仍需独立的评审与验收环节（[[评审与验收]]）。
- **与 [[口播素材综览]] 的关系**：若口播/文章素材要同时讲 pstack 与 Sandcastle，需要在术语层面统一「沙箱」「接单」「分支策略」的用法，避免听众把两个 Sandcastle 混为一谈。

## 6. 矛盾、缺口与不确定

**矛盾/冲突**

1. **同名异指**（最重要）：[1] 的 Sandcastle 与 [2] 的 Sandcastle 分属不同组织、不同场景。任何「Sandcastle 是什么」的单句定义都会出错，必须限定归属。
2. **「沙箱」一词的层级不一致**：[1] 的沙箱边界是 Git 分支[1]，[2] 的沙箱是面向数据负载的执行环境[2]。二者不在同一抽象层，直接比较会产生伪结论。

**证据缺口**

3. [1] 仅两条要点，无文档全文；`branch strategy` 的取值集合、默认值、并发模型均未知。
4. [2] 仅一句定位，无接口、无架构、无与通用沙箱（容器/VM）的差异说明。
5. 两条来源都**未提及**成本、失败重试、权限模型、多 agent 协作——而这些恰是 [[成本与模型]] 与 [[环境与约束]] 最需要的数据。
6. 时间性不确定：来源未标注版本或发布日期，无法判断其与 2026 年现状的差距。

**存疑待决**

7. TextQL 的 Sandcastle 是否值得在 wiki 中独立成页，抑或仅在 [[Sandcastle]] 内做一节消歧？建议登记至 [[待确认与冲突]]。
8. 「沙箱编排工具」是否应作为一个概念页独立存在（而非寄生在 [[沙箱与自动接单]] 下），取决于后续能否补齐 3 个以上同类工具的对照材料。

## 7. 建议补充的来源

按优先级排列：

1. **AI Hero Sandcastle 官方文档全文与代码仓库**——用于确认 `sandcastle.run()` 的签名、branch strategy 的选项、并发与失败处理。
2. **TextQL 的 Sandcastle 技术博客/文档**——确认其与通用容器沙箱的差异，尤其是数据负载特有的隔离需求（数据权限、查询隔离）。
3. **同类工具的横向材料**：E2B、Daytona、Modal Sandboxes、Devcontainer / `git worktree` 方案、各编码 agent 自带的 sandbox 模式——用于把「沙箱编排」从单词提升为可对照的概念。
4. **批评性材料**：关于「沙箱隔离给人以虚假安全感」的工程讨论，用于平衡 [[验证与自证]]。
5. **一手实测**：在同一任务上分别用 Sandcastle 与 [[pstack]] 跑一遍，记录并发数、PR 质量、返工率——目前 wiki 全部相关论断都缺少这类数据。
