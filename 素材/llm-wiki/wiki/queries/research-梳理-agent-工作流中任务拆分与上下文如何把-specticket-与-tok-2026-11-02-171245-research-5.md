# Research: 梳理 agent 工作流中「任务拆分与上下文」如何把 spec、ticket 与 token 预算相互换算，并核查 15 万 token 说法的来源、适用条件及其对验证和验收的影响。

# Spec、Ticket 与 Token 预算的换算：任务拆分与上下文治理（含“15 万 token”说法核查）

## 摘要

本页梳理 agent 工作流中三个层次的预算如何相互约束：**spec（需求/规格）→ ticket（可独立验证的任务单元）→ token（单次会话的上下文预算）**。核心结论是：**ticket 是 spec 与 token 之间的换算单位**。一个 ticket 的合格标准不仅是“业务上可交付”，还必须“能在一次上下文预算内闭合，并且自带可判定的验收条件”。凡是无法在预算内闭合的 ticket，问题通常出在拆分粒度，而不是模型能力 [5][8]。

关于“15 万 token”：**本批 9 条来源中没有任何一条直接给出这一数字**。它只能由 [3] 的窗口占比规则反推得到，属于待核实的二手说法，详见第四节。

---

## 一、三层预算模型

### 1.1 Spec 层：稳定信息，以“行/字”计量

Spec 的预算约束体现为**体量与结构**，而不是 token 数。可参照的锚点是渐进披露式配置文件：单文件少于 200 行，常驻记忆只加载前 200 行/25KB [3]。这一层的设计意图是把“永远需要知道的约束”与“按需检索的细节”分开，前者常驻，后者延迟加载。

[4] 给出同一思想的另一种表述：把上下文拆成**稳定信息**与**变化信息**，让变化部分足够精准、长度可控、可验证，再通过缓存、裁剪、摘要、检索把 token 的边际成本压下去。这与 [[环境与约束]] 中“把约束外置到环境而非提示词”的思路一致。

### 1.2 Ticket 层：可独立验证的最小单元

[5] 的六阶段工作流把这一层描述得很具体：**需求单**明确验收标准与约束，**任务卡**把工作拆成可独立验证的单元。这里的“可独立验证”是双重属性：

- 业务属性：有明确的完成判据；
- 上下文属性：验证所需的信息能被装进一次调用，而不必回看完整历史。

[6] 补充了机制层面的解释：Subagents 的关键差异在于通过**任务拆分与上下文隔离**实现复杂性管理，而不是更强的补全。换句话说，拆分是为了让每个执行单元拥有一个“自洽且封闭”的上下文。

### 1.3 Token 层：运行时可观测的预算

[1] 的立场最明确：agent 的 token 治理属于**运行时工程**，不是提示词润色。可执行方案包括：为上下文和任务设置预算、分层保留历史、对工具结果裁剪/分页。

[2] 则把预算写进了协议结构。跨 agent 的 handoff 载荷为：

```
handoff = { task_id, sender, recipient, goal, constraints,
            accepted_facts, artifact_refs, remaining_budget, visited_agents }
```

配合 `remaining_budget <= 0 → stop_and_escalate` 与 `visited_agents` 环检测。这意味着**预算随票据一起流转**：ticket 不仅携带“要做什么”，还携带“还剩多少额度”和“哪些事实已被接受”。

## 二、换算规则与可引用的锚点数字

现有材料没有给出端到端的换算公式，但提供了若干可直接用作系数的锚点：

| 层级 | 约束项 | 锚点数值 | 来源 |
|-|-|-|-|
| 上下文预算 | MCP 工具定义占比 | 超过窗口 10% 即应延迟加载（tool search） | [3] |
| 上下文预算 | 工具描述截断 | 2,048 字符 | [3] |
| 上下文预算 | 常驻记忆 | CLAUDE.md 少于 200 行/文件；MEMORY.md 前 200 行/25KB | [3] |
| 上下文预算 | 单次工具输出 | 1 万 token 警告 / 2.5 万 token 截断 | [3] |
| 任务预算 | 任务描述占比 | 约 30%（“朴素的 30% 规则”，原文表述在采集片段中被截断） | [8] |
| 任务预算 | 剩余额度 | 由 handoff 显式携带，归零即升级 | [2] |

**本页归纳的换算链（推理性表述，不是来源原文）：**

```
可用 token ≈ 窗口上限
           − 工具定义（≤10% 窗口）
           − 单次工具结果（≤25k）
           − 输出与安全余量
           − 常驻记忆（≤25KB）
```

由此得到一个可操作的拆分判据：**若一个 ticket 的“任务描述 + 必要代码/文档 + 预期工具输出”超过上述可用额度，就应当继续拆分，而不是压缩描述**。压缩描述会把成本转移到“猜测需求”上，直接损害验收的可判定性 [5][7]。

## 三、把 spec 拆成 ticket 的操作规则

综合 [5][6][7][8]，可提炼出四条规则：

1. **验收标准前置**。需求单阶段就写清验收标准与约束，任务卡继承之；没有判据的条目不算 ticket [5]。
2. **一个 ticket 一次上下文闭合**。粒度以“能在一轮会话内完成并自检”为准；[7] 强调编码阶段要拆解步骤、避免“一把梭”，并同步控制变更粒度。
3. **隔离即降复杂度**。把长流程切给 subagent，主会话只保留结论与引用（`artifact_refs`），而不是全量对话 [6][2]。
4. **预算显式化**。给每个 ticket 附上 `remaining_budget`，耗尽即触发升级而非静默降质 [2]；这比事后统计 token 更能防止“预算失控” [1]。

与 [[技能与流程]] 的关系：上述规则本质上是把“拆分”固化为技能/SOP 的一部分，让拆分动作可复用、可审查，而不是每次临场判断。可对照 [[matt-pocock-skills]] 的 implement-spec / pr / retro 流程，以及 [[pstack-与-matt-pocock-技能的分工]] 中关于“谁负责拆、谁负责验”的分工讨论。

## 四、“15 万 token”说法核查

### 4.1 来源情况：本批材料不支持

逐条比对后：**[1]–[9] 均未出现 150,000 或“15 万 token”的表述**。最接近的数字是 [3] 的“工具定义吃掉几万 token”“1 万警告 / 2.5 万截断”“10% 窗口”与 [8] 的“30% 规则”。因此该说法在本批证据下**属于未溯源断言**，不应作为既定事实引用。相关登记见 [[待确认与冲突]]。

### 4.2 可能的推算路径（假设，需回溯原始出处）

以下三条都能推出“15 万”量级，但都不是来源明示：

- **路径 A：窗口扣减**。若模型窗口为 200k，工具定义占 10%（20k）[3]，单次工具输出留 25k [3]，输出与余量留 5k–15k，则任务上下文可用额度落在 **140k–150k**。
- **路径 B：压缩阈值**。若自动压缩在接近窗口上限时触发，实践中的“安全作业区间”约为窗口的 75%，200k × 75% = **150k**。
- **路径 C：预算策略值**。团队直接把单会话预算定为 150k（与人无关的工程约定），此时它是**策略参数**而非模型限制。

三者含义完全不同：A 是容量推导，B 是运行时行为，C 是管理约定。**引用时必须说明是哪一种**，否则“15 万”会被误读为硬性上限。

### 4.3 该说法成立所需的前提条件

- 模型上下文窗口为 200k 量级；若窗口为 1M，150k 只是保守策略值，不具备“逼近上限”的含义。
- 工具定义规模可控（已启用 tool search 延迟加载）[3]；若接了多个 MCP server 而未治理，工具定义本身就能吃掉几万 token [3]，150k 的可用余量会被进一步侵蚀。
- 任务为单仓库、单模块范围；跨仓库重构场景下，检索噪声会显著抬高实际占用 [8]。
- 已开启历史分层与工具结果裁剪 [1]；否则历史累积会让“150k”在会话中段就被击穿。

### 4.4 失效场景

- **长程任务**：需要跨多次会话续接时，单会话额度不能直接外推为任务总额度，应改用 [[任务拆分与上下文]] 中的分段预算。
- **验证密集型任务**：评审、跑测试、读失败日志都要占额度，实际可写代码的余量远低于名义值。
- **多 agent 协作**：handoff 本身携带 goal/constraints/accepted_facts，会重复占用上下文 [2]，总消耗高于单 agent 串行。

## 五、对验证与验收的影响

这是本主题最容易被忽略的一环：**预算约束会反过来重塑验收制度**。

1. **验收标准被迫前移**。因为 ticket 必须在预算内闭合，判据不能留到“看结果再说”，只能写进需求单 [5]。这与 [[验证与自证]] 中“先定义什么叫完成”的主张同向。
2. **隔离带来独立评审，也带来信息缺口**。subagent 不共享上下文，评审者只看到 ticket 声明的 `artifact_refs` [6][2]；好处是减少“顺着自己的推理自证”，风险是遗漏未声明的隐含约束。因此 `accepted_facts` 应被视为**已验证事实白名单**，未列入者必须重新验证 [2]。
3. **预算耗尽是一种显式验收状态**。`stop_and_escalate` 让“没做完”变成可观测事件，而不是模型硬撑着输出半成品 [2]。这比事后统计更能保护验收质量 [1]。
4. **粒度错误会伪装成质量错误**。当一个 ticket 反复验收不通过时，应先检查它是否超出了单次上下文预算，再判断是模型能力问题 [8][7]。

这与 [[评审与验收]] 的分层验收、[[信任阶梯]] 的“先小后大放权”可以互相印证：预算和信任一样，都是**按 ticket 逐级发放**的。

## 六、矛盾与空白

- **核心数字缺源**：15 万 token 无原始出处，三条推算路径互不等价（见 4.2）。
- **30% 规则定义不完整**：[8] 的原文在采集片段中被截断，无法确认“30%”指的是任务描述占比、上下文占用比，还是预留余量比例。
- **锚点数字具有时效性**：[3] 的 10%、2,048 字符、1 万/2.5 万等均来自 Claude Code / Codex 的具体实现，会随版本变化，不宜当作恒定常数。
- **缺少 spec→token 的换算系数**：材料未给出“中文/英文文本字数 → token”的比例，而这直接影响 ticket 的体量估算。
- **缺少定量实证**：没有任何来源给出“预算设置与任务成功率”的对照数据，现有论述多为工程经验。
