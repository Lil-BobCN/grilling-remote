# Research: 研究 Sandcastle 类沙箱编排工具从隔离执行、自动领取任务到直接接收客户需求之间缺失的接入、验证、验收与权限控制层，并厘清其与「沙箱与自动接单」这一流程桥接的关系。

# 沙箱编排的接入、验证、验收与权限层

**副标题**：从隔离执行、自动接单到客户需求的缺失环节

**页面类型**：综合（synthesis）｜**建议归档**：`synthesis/沙箱编排的接入验证与验收层`｜**核心关联**：[[Sandcastle]]、[[沙箱与自动接单]]、[[评审与验收]]

> **一句话结论**：Sandcastle 类工具已经把「在隔离环境中执行」与「从 issue tracker 自动领取任务」连接起来，但「客户需求 → 可执行任务」与「代码变更 → 可接受交付」这两端的校验环节，以及贯穿全程的权限与审计，仍未成为这类工具的原生能力；[[沙箱与自动接单]] 因此是整条流水线的中段桥，而不是端到端方案。

## 概述

以 [[Sandcastle]] 为代表的沙箱编排工具，把两件原本分离的事情接在了一起：AI 生成的代码与工具调用在隔离环境中执行，避免污染宿主系统；agent 从 issue tracker 自动领取任务，完成后提交 PR。现有 wiki 把这一组合概括为 [[沙箱与自动接单]]。

但这条链路的两端仍然是断开的。左端，客户需求并不是 issue；它可能是邮件、聊天记录、会议纪要或销售转交的一段自然语言，充满歧义、缺失复现步骤，甚至包含恶意指令。右端，PR 也不是交付；它只是变更提案，仍需验证、评审、验收与权限审计。本文把这两端缺失的能力归纳为四层——接入、验证、验收、权限——并说明它们与「沙箱与自动接单」这一流程桥接的关系。

本文试图回答三个问题：

1. Sandcastle 类工具已经覆盖了哪些环节？
2. 从客户需求到可接受交付，还缺哪些层？
3. 「沙箱与自动接单」在完整流程中处于什么位置？

**核心判断**：

1. 沙箱解决「在哪里执行」，自动接单解决「任务从哪里来」，但不解决「需求是否可信、可执行」与「产出是否可接受」。
2. 「沙箱与自动接单」是整条流水线的中段桥，不是端到端方案；它默认 issue tracker 已经完成了需求清洗。
3. 生产化的关键，是在桥的两端各加一道校验环节：入口环节（接入）与出口环节（验证+验收），并用权限与审计贯穿全程。

### 术语约定

| 术语 | 本文含义 |
|---|---|
| 沙箱（sandbox） | 隔离的执行环境，限制文件系统、网络、资源与系统调用[5][7] |
| 自动接单 | 从 issue tracker 或任务队列领取任务并触发 agent 执行 |
| 接入（intake） | 把客户原始需求转化为可执行、可验证、可授权的任务契约 |
| 验证（validation） | 证明变更符合任务契约与工程标准 |
| 验收（acceptance） | 决定变更是否被接受、是否发布、由谁负责 |
| 权限（permission） | 身份、范围、审批、审计与止损机制 |
| 任务契约 | 接入层输出的结构化任务说明，含目标、非目标、验收标准、风险级别与权限边界 |

更完整的术语对照见 [[术语表]]。

## 1. 已经解决的两段：隔离执行与自动领取

### 1.1 隔离执行：沙箱作为生产边界

AI agent 沙箱通常被定义为一个隔离的执行环境，agent 在其中的操作不会影响宿主系统[7]。在生产语境下，它不只是「跑代码的地方」，而是限制文件系统访问、网络出站等行为的安全边界[5]。

AWS 的实践文章从 Agentic AI 基础设施角度论证了专用沙盒环境的必要性，并给出基于微虚拟机等技术的隔离方案，覆盖代码执行与 Browser Use 两类场景[1]。PPIO 则把 agent 沙箱作为云端运行时基础设施，强调为 AI 生成的代码提供安全隔离的执行环境[2]。

具体实现形态并不唯一：

- 微虚拟机/专用沙箱：强调强隔离与资源边界[1]。
- 云端沙箱运行时：强调弹性与托管[2]。
- Linux 进程级沙箱：例如 Qwen Code 文档中的 bwrap（Bubblewrap）方案，用于限制工具执行[9]。
- Agent 运行时内置沙箱与工具接入：AgentScope Runtime 把沙箱与工具作为运行时能力组织[10]。

选型也不是单维度的。Cosmonic 的指南按 agent 需要沙箱的位置来讨论选型[4]；Northflank 则指出，最佳沙箱取决于 agent 运行什么、需要多少并行环境、以及哪些状态必须保留[6]。这说明「沙箱」是一个谱系，而不是一个产品名。

隔离之外，可观测性是生产落地的另一个瓶颈。有分析指出，沙箱内的每一次模型调用、工具执行和外部访问都可以自动生成调用链与指标；没有这些，agent 的行为无法解释，事故无法复盘[3]。NVIDIA 的实践指南也把沙箱化 agentic workflow 的安全建议作为独立主题[8]。这与 [[环境与约束]] 的关注点一致：环境既是能力来源，也是约束来源。

### 1.2 自动领取：从 issue tracker 到 PR

[[Sandcastle]] 这类工具的另一半能力，是自动领取任务。按现有 wiki 材料与本文研究主题的描述，其典型链路是：轮询 issue tracker → 领取（claim）任务 → 在沙箱中运行 agent → 提交 PR。[[matt-pocock-sandcastle]] 把这一模式概括为「让 AI 自动接单写代码」。

这条链路之所以能成立，依赖一组隐含前提：

- issue 已经是可执行的任务，而不是原始客户对话；
- 仓库有可运行的测试或至少可执行的构建；
- PR 是合适的交付物，合并决策另有流程；
- agent 的权限足以读写代码，但不足以直接发布。

这些前提在 demo 中通常由人类预先满足，在生产中却需要显式建设。[[沙箱与自动接单]] 描述的正是「沙箱」与「接单」之间的桥：它把执行环境和任务来源连接起来，但没有覆盖桥两端的翻译工作。

### 1.3 被低估的编排细节

自动接单的工程细节常被低估：任务需要 lease（租约）避免重复领取，需要幂等键避免重复执行，需要死信队列处理失败任务，需要优先级与配额避免饥饿。这些属于编排层，而不是沙箱层。一个能跑 demo 的 Sandcastle 类工具，可能只实现了「轮询 + 运行」；生产化则要求队列语义、失败恢复与成本上限。

这也解释了为什么「沙箱与自动接单」不能等同于「端到端自动化」：它把执行环境与任务来源接上了，但任务队列本身的治理仍在别处。

### 1.4 一个对照：高吞吐 PR 流的压力

[[pstack]] 的实践展示了高吞吐端的压力：当自动化把 PR 产量推到每月数千个量级时，评审与验收会成为瓶颈。[[pstack-作者-每月2500个PR]] 记录了这种高吞吐工作流；[[pstack-让错误只犯一次]] 的主题——让同类错误不重复发生——则与验证/验收的反馈闭环相呼应。自动接单越成功，越需要验证与验收层的制度化，否则只是把瓶颈从「写代码」转移到「看代码」。

## 2. 缺失层之一：接入（Intake）

### 2.1 为什么不能把客户需求直接接给 agent

把客户邮件、聊天消息或工单描述直接塞给 Sandcastle 类 agent，看似缩短了链路，实际上同时引入三类风险：

1. **语义风险**：客户描述的是现象，不是可执行规格。缺少环境、版本、复现步骤、期望行为与非目标，agent 只能猜测。
2. **安全风险**：客户输入是不可信文本，可能包含 prompt injection，诱导 agent 读取密钥、修改受保护文件或向外部地址发送数据。沙箱能限制爆炸半径[5][7]，但不能把恶意意图变成合法任务。
3. **数据风险**：客户文本可能包含 PII、合同条款、密钥或内部链接。把这些内容原样放入模型上下文，会扩大数据暴露面。

因此，接入层的核心不是「把需求传进去」，而是「把需求翻译成可执行、可验证、可授权的工作单元」。

### 2.2 接入层的职责

可以把接入层理解为一道入口环节，至少包含以下职责：

| 职责 | 说明 | 失败后果 |
|---|---|---|
| 渠道归一 | 邮件、聊天、工单、API、销售转交统一进入一个入口 | 需求散落、重复、遗漏 |
| 结构化 | 用模板收集现象、期望、环境、复现步骤、影响范围 | agent 无法复现，产出偏离 |
| 分类与去重 | 区分 bug/feature/security/question，合并重复项 | 队列污染、优先级失真 |
| 可执行性判定 | 判断是否在代码库范围内、是否可复现、依赖是否齐全 | agent 空转或改错地方 |
| 信任标记 | 标记来源（内部/外部）、可信度、敏感级别 | 把不可信输入当规格执行 |
| 安全清洗 | 检测注入模式、隔离附件与链接、脱敏 PII | 数据外泄、越权操作 |
| 验收标准 | 把期望行为写成可测试的 Given/When/Then 或 checklist | 「做完了」无法判定 |
| 风险分级 | 低/中/高，决定后续评审与权限 | 高风险变更被低规格处理 |

接入层不只是技术组件，也是组织边界：它决定什么需求可以进入自动化队列，什么需求必须人工处理。

### 2.3 任务契约：接入层的输出物

接入层的输出不应是一段更长的自然语言，而应是一份「任务契约」。它既是 agent 的输入，也是后续验证与验收的依据。建议至少包含：

- **目标**：一句话描述要改变的用户可见行为；
- **非目标**：明确不做什么，防止范围蔓延；
- **背景与复现**：现象、环境、版本、日志、截图；
- **验收标准**：可执行的测试或可观察的行为；
- **约束**：技术栈、兼容性、性能、合规、截止时间；
- **风险级别**：决定评审人数、是否需要安全审查、是否允许自动合并；
- **权限边界**：允许访问的仓库、路径、网络域名、数据范围；
- **数据敏感度**：是否含 PII、密钥、客户数据，是否需要脱敏或隔离环境。

这与 [[任务拆分与上下文]] 的关注点直接相连：任务拆分不只是把大任务切小，更是把「客户语言」切成语境自足、验收明确的单元。

### 2.4 人机分工

接入层不应追求全自动。可行的分级是：

- **低风险、结构完整**：自动接入 + agent 辅助分类 + 人工抽检；
- **中风险、存在歧义**：人工确认任务契约后再入队；
- **高风险、外部客户或涉及敏感数据**：人工主导接入，必要时与客户确认「我们理解的需求是 X，将做 Y，不做 Z」。

如果需求来自外部客户，还应增加一步「需求确认」：把任务契约回写给客户或销售确认，避免 agent 基于误解执行。

### 2.5 「直接接收客户需求」的边界

「直接接收客户需求」可以有两种含义：

1. 客户原话直接进入 agent 上下文，并被当作执行指令；
2. 客户通过受控入口提交需求，由接入层结构化后再进入队列。

建议的是第二种：客户通过受控入口提交需求，接入层负责结构化、信任标记与任务契约生成；对话内容不直接作为执行指令。即便入口是对话式，也应把对话限制在信息收集，不把对话内容直接当作执行指令；执行指令由任务契约承担。

如果入口是对话式，还应限制 agent 的承诺权限：价格、交付时间、SLA、退款、法律条款等不能由 agent 自主确认；这些应作为「需要人工批准的外部动作」纳入权限层。同时，客户-facing agent 应披露自动化身份，并提供人工升级路径。

## 3. 缺失层之二：验证（Validation）

### 3.1 验证的三个时点

验证不只是一次 CI。它可以分为三个时点：

1. **执行前验证**：任务是否仍然有效、是否可复现、是否已被其他变更修复、依赖是否可用；
2. **执行后验证**：代码是否通过测试、静态检查、构建、安全扫描，行为是否符合验收标准；
3. **合并后验证**：灰度、冒烟、监控、回滚是否正常。

从现有材料看，Sandcastle 类工具主要覆盖执行后验证的一部分，且容易依赖 agent 自己运行测试；执行前验证与合并后验证通常不在其范围内。

### 3.2 自证不等于验证

[[验证与自证]] 所讨论的「自证」问题在这里非常关键：agent 能运行测试、能报告「通过」，但这是自证，不是独立验证。风险在于：

- agent 可能写出与实现同构的测试，测试通过但规格错误；
- agent 可能只运行了部分测试，或误解了失败原因；
- agent 的「完成」声明缺少可复核的证据。

更稳妥的做法是引入独立验证：

- 由独立 CI 在干净环境中重新运行测试；
- 由 fresh context 的 verifier agent 按验收标准检查，而不是复用实现 agent 的上下文；
- 测试应从任务契约派生，必要时使用 mutation testing 检查测试有效性；
- 输出证据包：命令、日志、退出码、覆盖率变化、构建产物哈希、可观测性 trace[3]。

这与 [[评审与验收]] 的关注点一致：评审者不应替 agent 做基础验证，而应基于证据做判断。

### 3.3 环境可复现性

验证结论只有在环境可复现时才可信。沙箱应固定镜像与依赖锁文件，限制网络出站[5]，并记录运行时版本。若沙箱与生产环境差异过大，测试通过也可能在线上失败；此时需要 staging、canary 或 feature flag 作为补充。

### 3.4 验证失败的处理

验证失败不应无限重试。可行策略是：

- 将失败日志与验收标准一起反馈给 agent，限定重试次数；
- 连续失败后升级为人工处理；
- 把重复失败模式写入规则或检查项，呼应 [[pstack-让错误只犯一次]] 的思路；
- 通过 [[修正阶梯与-correct]] 把纠正动作结构化，而不是每次从零开始。

## 4. 缺失层之三：验收（Acceptance）

### 4.1 验证与验收的区别

验证回答「是否正确地构建」，验收回答「是否构建了正确的东西，以及是否可接受」。测试可以证明代码符合规格，但不能证明规格符合客户需求，也不能决定发布风险是否可接受。

[[评审与验收]] 覆盖评审与验收两个环节；按 [[信任阶梯]] 的思路，自动化程度应随信任积累逐步提高，而不是一次性放开。验收层不只是技术检查，而是责任边界：谁签字，谁对交付负责。

### 4.2 风险分层的验收

| 风险级别 | 典型变更 | 验收方式 |
|---|---|---|
| 低 | 文档、测试、内部工具、无行为变化的 refactor | CI + agent 评审 + 有条件自动合并 |
| 中 | 一般功能、UI、非关键 bug 修复 | 至少 1 名人类评审 + 产品/需求方确认 |
| 高 | 支付、认证、权限、数据删除、公开 API、合规相关 | 2 名评审 + 安全/合规审查 + 灰度 + 客户验收 |

风险分级应来自接入层的任务契约，而不是执行后临时判断。否则 agent 可能把高风险变更「拆小」以绕过审查。

如果需求来自外部客户，还应区分内部验收、客户验收与合同验收：内部验收看工程与安全，客户验收看 UAT 与试用，合同验收看 SLA、合规与交付物清单。

### 4.3 验收记录与责任

验收必须留下记录：

- 谁批准、何时批准；
- 基于哪个版本/commit/产物；
- 依据哪些证据；
- 附带哪些条件（如「先灰度 5%」「需监控 24 小时」）。

这既是审计要求，也是 [[信任阶梯]] 的数据来源：只有知道过去哪些变更被接受、哪些被回滚，才能决定下一阶段是否扩大 agent 的自主权。

### 4.4 反馈闭环

验收不是终点。拒绝、回滚、客户投诉都应回流到接入与验证：

- 拒绝 → 修正任务契约或实现，进入 [[修正阶梯与-correct]]；
- 回滚 → 触发复盘，更新检查项；
- 重复问题 → 写入规则、模板或测试。

[[matt-pocock-skills]] 的 grill → implement → PR → retro 流程，实际上把「接入前的盘问」与「验收后的复盘」都显式化了；[[matt-pocock-grill-to-retro]] 与 [[matt-pocock-v1-3]] 展示了这种全流程技能的组织方式。相比之下，只做「沙箱 + 接单」的工具处于该流程的中段。

## 5. 缺失层之四：权限与审计（Permission & Audit）

### 5.1 权限层是横切关注点

权限不是流水线中的某一站，而是贯穿接入、执行、验证、验收的约束。它要回答：

- 这个 agent 以什么身份运行？
- 它能读哪些代码、数据、密钥？
- 它能写哪些分支、调用哪些外部服务？
- 谁能批准高风险动作？
- 出了事能否追溯、能否止损？

沙箱提供隔离，但不自动产生信任；权限层要按零信任思路设计：每次调用都要有身份、范围与审计。

### 5.2 最小权限与职责分离

对 Sandcastle 类工具，至少应做到：

- **工作负载身份**：每次运行使用独立身份，而不是复用人类的长期 token；
- **仓库/路径/分支范围**：只允许读写任务所需的范围，默认不能推 main；
- **禁止自我批准**：实现 agent 不能合并自己的 PR，不能批准自己的高风险动作；
- **短期凭据**：密钥通过 broker 注入，短 TTL，任务结束即失效；
- **沙箱约束**：文件系统白名单、网络出站白名单、资源配额、超时[5][9]；
- **审计日志**：记录模型调用、工具执行、外部访问、文件变更、审批动作[3]；
- **kill switch**：能立即撤销凭据、停止队列、隔离沙箱。

NVIDIA 的沙箱安全指南强调对 agentic workflow 的实践性安全控制[8]；这与「沙箱隔离」本身不同：隔离是边界，权限是边界内的行为规则。

### 5.3 策略即代码

可以把风险分级映射为可执行策略：

| 风险级别 | 允许 | 禁止 | 需要审批 |
|---|---|---|---|
| 低 | 读代码、开分支、开 PR、跑测试 | 推 main、访问生产密钥 | 无 |
| 中 | 低风险全部 + 部署 staging | 直接部署生产 | 1 名人类 |
| 高 | 只读、生成提案 | 直接变更生产、删除数据、改权限 | 2 名人类 + 安全/合规 |

策略应独立于 agent 的提示词，放在编排层或 CI 中强制执行。否则 agent 可以通过「解释」绕过规则。

### 5.4 客户数据与多租户

如果接入层直接接收客户需求，权限层还必须处理：

- 客户数据隔离：不同客户的沙箱、日志、产物不能互相可见；
- 数据最小化：只把必要字段放入上下文，PII 脱敏；
- 保留与删除：按合同与法规设置保留期；
- 跨境/合规：根据数据分类限制运行区域。

## 6. 与「沙箱与自动接单」的桥接关系

### 6.1 现有概念覆盖的是中段

[[沙箱与自动接单]] 描述的是「沙箱」与「接单」之间的桥：任务从 issue tracker 来，执行在沙箱中，结果以 PR 回去。它解决的是「活从哪里来、在哪里干」的问题。

但这座桥有两个隐含边界：

- **左边界**：issue tracker 被视为已经清洗过的任务源。它不处理客户原话、销售转交、聊天记录。
- **右边界**：PR 被视为交付物。它不处理「这个 PR 是否应该被接受」「谁有权接受」「接受后如何发布」。

因此，[[沙箱与自动接单]] 是整条流水线的**中段桥**，而不是端到端方案。把它当作端到端方案，就会出现「agent 很忙，但交付不可控」的局面。

### 6.2 加上两道校验环节

可以把完整链路表示为：

```
客户需求
   │
   ▼
[接入层] ── 入口环节：结构化、信任标记、任务契约
   │
   ▼
[issue tracker / 任务队列]
   │
   ▼
[沙箱与自动接单] ── 中段桥：领取、隔离执行、开 PR
   │
   ▼
[验证层] ── 出口环节 1：测试、扫描、证据包
   │
   ▼
[验收层] ── 出口环节 2：评审、签核、灰度
   │
   ▼
合并 / 交付 / 发布
   │
   ▼
反馈与复盘 ── 回流到接入与验证
```

权限与审计不占单独一站，而是包住整条链路：身份、范围、审批、日志、kill switch。

### 6.3 与相邻实践的关系

- **Sandcastle**：位于中段，强在隔离执行与自动领取；若要覆盖两端，需要外接接入、验证、验收与权限组件。
- **pstack**：高吞吐 PR 流说明「自动接单」越成功，越需要验证与验收的规模化；[[pstack-与-matt-pocock-技能的分工]] 可以帮助理解不同工具在流程中的位置。
- **Matt Pocock Skills**：grill → implement → PR → retro 的技能化流程，把接入前的规格盘问与验收后的复盘都纳入流程；[[matt-pocock-skills]] 与 [[matt-pocock-skills-实战]] 提供了可对照的样本。

## 7. 分层参考模型

### 7.1 四层边界

如果把四层各用一个词概括：

| 层 | 边界性质 | 核心问题 |
|---|---|---|
| 接入 | 准入边界 | 什么需求可以进入自动化队列？ |
| 验证 | 证据边界 | 什么证据足以证明变更符合规格？ |
| 验收 | 责任边界 | 谁有权接受、发布并承担后果？ |
| 权限 | 安全边界 | agent 能做什么、不能做什么？ |

### 7.2 完整分层表

| 层 | 核心职责 | 关键控制 | 缺失时的典型故障 | 关联页面 |
|---|---|---|---|---|
| 接入层 | 客户需求 → 任务契约 | 模板、分类、去重、信任标记、验收标准、风险分级 | 歧义、注入、PII 泄露、不可复现 | [[任务拆分与上下文]] |
| 编排层 | 队列、领取、优先级、并发、重试、预算 | lease、幂等、优先级、成本上限 | 重复领取、饥饿、成本失控 | [[成本与模型]] |
| 执行层 | 在隔离环境中运行 agent | 微虚拟机/容器、文件系统与网络限制、资源配额、可观测性 | 宿主污染、数据外泄、行为不可解释 | [[环境与约束]]、[[沙箱与自动接单]] |
| 验证层 | 证明变更符合规格 | 独立 CI、测试、扫描、证据包、fresh-context verifier | 假阳性、回归、自证偏差 | [[验证与自证]] |
| 验收层 | 决定是否接受与发布 | 风险分层评审、UAT、签核、灰度、回滚 | 错误交付、橡皮图章、责任不清 | [[评审与验收]]、[[信任阶梯]] |
| 权限与审计层 | 约束谁能做什么、留下证据 | 工作负载身份、最小权限、职责分离、策略即代码、日志、kill switch | 越权、不可追溯、供应链攻击 | [[环境与约束]] |

### 7.3 最小可行生产化清单

- [ ] 客户输入不直接进入 agent，先经过模板与信任标记；
- [ ] 每个任务有可测试的验收标准与风险级别；
- [ ] agent 使用短期、最小权限凭据，不能合并自己的 PR；
- [ ] 沙箱限制文件系统、网络出站、资源与运行时长；
- [ ] 验证由独立 CI 或 fresh-context verifier 完成，产出证据包；
- [ ] 高风险变更需要两名以上人类审批与灰度；
- [ ] 全链路审计日志可追溯，具备 kill switch；
- [ ] 失败重试有上限，并有升级到人类的路径；
- [ ] 定期复盘验收结果，动态调整 agent 自主权。

## 8. 失败模式与反模式

| 失败模式 | 触发条件 | 后果 | 可能控制 |
|---|---|---|---|
| 需求注入 | 客户文本含 prompt injection | 数据外泄、越权操作 | 信任标记、输入清洗、出站白名单、密钥隔离 |
| 任务漂移 | 需求歧义、缺少非目标 | 做错功能但测试通过 | 任务契约、验收标准、人工确认 |
| 自证偏差 | 实现与测试由同一 agent 完成 | 测试编码了错误规格 | 独立测试、mutation testing、fresh-context verifier |
| 橡皮图章评审 | PR 量过大、评审时间不足 | 缺陷漏过 | 风险分层、证据摘要、抽样审计、限制并发 |
| 权限过宽 | 长期 token、仓库管理员权限 | 一次注入即可推 main | 短期凭据、分支保护、职责分离 |
| 沙箱不可观测 | 只记录最终输出 | 事故无法复盘 | 调用链、工具日志、外部访问日志[3] |
| 环境漂移 | 沙箱与生产差异大 | 测试通过、线上失败 | 固定镜像、staging、canary |
| 队列语义缺陷 | 无 lease/幂等 | 重复执行、任务丢失 | lease、幂等键、死信队列 |
| 成本失控 | 无限重试、长上下文 | 账单超支 | 预算上限、最大迭代、模型路由[[成本与模型]] |

## 9. 矛盾、证据缺口与待确认问题

本文的外部证据来自沙箱基础设施资料[1]–[10]，其主题集中在隔离、选型与可观测性，并不直接讨论 Sandcastle 的接入或验收实现。因此，下文涉及 Sandcastle 具体能力的地方，均以现有 wiki 材料与研究主题为据，属于待验证的分析，而非代码审计结论。

1. **来源以厂商指南为主**：现有外部来源多来自沙箱厂商、云厂商与工具文档[1][2][4][5][6][7][8][9][10]，对事故率、逃逸率、投资回报的独立实证较少。本文的分层模型是架构性推论，尚缺现场数据验证。
2. **Sandcastle 的具体能力边界不清**：现有 wiki 材料[[matt-pocock-sandcastle]]更接近演示，未说明其是否支持接入模板、风险分级、逐任务权限、审批门禁。需要查看其配置与实现细节。
3. **「自动验收」仍未解决**：外部来源强调隔离与可观测性[3][5]，但没有给出「何时可以自动接受变更」的判定标准。测试通过不等于产品可接受，这一点在来源中没有被充分讨论。
4. **「沙箱」定义不统一**：进程级 bwrap[9]、微虚拟机[1]、云端沙箱[2] 的安全属性差异很大；比较不同方案前需要先明确威胁模型。
5. **「自动接单」语义含混**：可能指自动分配 issue、自动提交 PR、自动合并、自动部署。不同语义对应完全不同的权限与验收要求。
6. **人类评审的瓶颈**：高吞吐 PR 流[[pstack-作者-每月2500个PR]]提示评审可能成为新瓶颈；但来源没有给出评审工作量与缺陷逃逸率的量化关系。
7. **成本与收益**：沙箱、验证、审计都会增加延迟与成本；在什么任务分布下值得，仍需数据。
8. **厂商强调重点的差异**：AWS 强调专用沙盒环境的必要性[1]，Northflank 则强调最佳沙箱取决于工作负载[6]。两者并不矛盾，但提示不存在一种沙箱形态可以同时满足所有隔离、弹性与状态需求；分层模型应允许替换执行层。

以上问题已汇总到 [[待确认与冲突]]，建议后续用真实项目数据逐项验证。

## 10. 建议补充的来源

- **OWASP Top 10 for LLM Applications**：prompt injection、excessive agency、敏感信息泄露等风险分类，可直接映射到接入层与权限层。
- **NIST AI Risk Management Framework / Generative AI Profile**：治理、映射、度量、管理四类活动，可作为接入与验收的制度框架。
- **SLSA、Sigstore、in-toto**：构建来源与供应链证明，用于验证「这个产物确实来自这次运行」。
- **Firecracker、gVisor、Kata Containers、Bubblewrap 文档**：不同隔离原语的安全属性与性能权衡。
- **Kubernetes 社区 agent sandbox 相关提案**：编排层如何管理沙箱生命周期、配额与多租户。
- **AI Incident Database**：查找 agent 越权、数据泄露、沙箱逃逸的真实案例。
- **SWE-bench、WebArena 等评测**：理解 agent 在真实任务上的能力边界，避免把 demo 成功率当作生产可靠性。
- **ITIL / Zendesk / Intercom 的工单分类与升级实践**：接入层的成熟方法论。
- **Google SRE Workbook 的 canary 与回滚章节**：合并后验证与发布验收。
- **EU AI Act 等法规中的人类监督要求**：高风险场景的验收与记录义务。

## 11. 结语

Sandcastle 类工具的下一步，不是让 agent 更快地写更多 PR，而是把接入、验证、验收与权限做成可配置的层。沙箱与自动接单已经证明了「agent 能干活」；要证明「agent 的活可以被信任」，还需要这两道校验环节与一条贯穿的审计链。
