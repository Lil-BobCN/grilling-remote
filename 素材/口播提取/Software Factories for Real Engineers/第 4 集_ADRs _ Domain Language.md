## 口播文章

### 代码是答案，但没有草稿纸

在探索 `grill with docs` 的过程中，我们看了 `domain modeling` 技能，看了术语表，看了场景测试，也看了怎么把东西弄清楚。但我们还没看 `domain modeling` 技能做的另一件事：编辑和创建 ADR。

ADR 是 architectural decision record（架构决策记录），记录的是已经做过的决定。它存在的原因很简单。如果你读代码，尤其是读注释和实现，代码能告诉你它在做什么。如果代码结构好，它能准确告诉你它返回什么，能用你的领域语言，总体上能解释自己。换句话说，代码能告诉你最后得到了什么，但它不能告诉你你否决了哪些做法、没有走哪条路。代码就像一道只留答案、把推导过程全擦掉的题。

ADR 就是那部分推导过程。它列出仓库或项目里所有重大决定，让人理解历史，避免再犯同样的错误。格式非常小，就在 `domain modeling` 技能的 ADR 格式里。基本模板真的非常短，可以只有一到三句话：我们决定了什么，为什么。可以有可选章节写考虑过的方案和后果，但 ADR 必须非常小、非常紧。

### ADR 的准入标准

人们一看到这个，就会想：我知道 agent 是什么样。你给它一个装满 Markdown 文件的文件夹，它就会不停往里加，这个文件夹会越长越大。那么，加 ADR 的标准是什么？

技能的最后写了这个标准：少用 ADR（offer ADRs sparingly）。这个决定必须难以逆转，必须在没有上下文时让人意外，而且必须是真实取舍的结果。比如，我们决定用 Recharts，或者用 Sonner 做 toast，这值得写 ADR 吗？大概不值得，因为这些很容易拆掉替换。但如果我们从 React 换到 Vue 之类，那就是一个很难走回去的决定，要花很多小时才能到那一步，所以可能值得写一份 ADR。

### 一个具体例子：退款窗口按整日算

我们看一个真实例子，把它变得更具体。在 `courses.slug.ts` 里，有一个 `asDayString` 函数，它在下面的 `getRefundOffer` 里被调用。这个函数返回学习者要求退款时能得到的报价，如果这笔购买不能退款就返回 null。

这段代码不太好读，但可以看到 `isWithinWindow` 是关键。我们实际做的是：如果用户在 9 月 20 日购买，我们不去计算他到期的精确小时，直接按整日计算。如果按小时算，退款窗口会在 10 月 4 日上午 9 点关闭，和他购买的时间一样。但因为按整日算，窗口实际上在午夜关闭，他多出了一大块时间可以发起退款。

这个决定在没有上下文时很让人意外，而且正是 agent 在走代码时完全可能忽略、直接踩过去、在小时和整日之间随便切换的那种决定。以我的经验，应用里到处都是这类决定，它们只被记在代码里，在其他地方很不明显。所以把它们放在顶层的全局 `docs/adr` 文件夹里，agent 更容易找到并翻出来。而且，在决定做出的那一刻就把它们记录下来也很关键。你在 grilling 的时候，正是做决定的时候，所以如果这些决定符合标准，就应该顺手变成架构决策记录。这就是为什么 `grill with docs` 同时做领域建模和架构决策记录。grilling 会话里做的事非常重要，值得把重要的部分记下来。

### 小心次级资料

还要说一句：我通常非常警惕在仓库里放任何描述代码在做什么的 Markdown 文件。这回到一手资料和二手资料的区别。代码库是一手资料，但它比较大。而一份关于部分代码的规格说明或文档，是二手资料，小得多。问题是，二手资料并不是事实的来源。事实的来源是能运行的代码，是真正执行的东西。所以我一直很担心加这些二手资料，因为它们很容易过时，也容易让 agent 困惑。

但 ADR 的用途，只是补上代码里看不到的缺口。它不是代码应该做什么的新的事实来源，只用来解释代码自己解释不了的东西。术语表也是一样。其实，先理解术语表，能让你更容易读懂代码。这两类文档合在一起，只是为了补上代码自己回答不了的部分。我发现，它们值得花时间和 token 去创建和维护。下一集见。

> **思考一下｜ADR 到底该记什么**
>
> 作者的标准是「难逆转、无上下文会意外、真实取舍」三条同时成立，并非只看「重要」。这让 ADR 更像决策的边界标记，不像项目日志。
>
> **可以追问**：一条决定如果很容易逆转，但每次逆转都会让人困惑，它算不算值得记录？
>
> **可延展方向**：在代码评审里加一个问题：这段实现有没有「不看 ADR 就会想改回去」的地方？

## 综合解读

论点链：代码能说明结果，不能说明被排除的选项；缺少推导过程，后来的 agent 或人会重复走弯路；ADR 用一到三句话保存推导；再用三条标准控制数量，避免文档膨胀。

成立前提：代码本身可读；ADR 集中存放，agent 会读；ADR 保持短小，不试图替代代码；团队接受在 grilling 现场记录决定。

待核验主张：作者说「应用里到处都是这类只记在代码里的决定」，这是经验判断，没有给出统计；「值得花时间和 token」是作者的成本收益判断，取决于项目规模和变更频率。`isWithinWindow` 的行为描述来自作者讲解，若要当作事实使用，需要直接读代码确认。

边界：ADR 不是事实来源，代码才是；文档会过时，所以 ADR 只补代码解释不了的缺口。另一个边界是，三条标准本身需要判断力，不同人对「难逆转」的阈值不一样。

可迁移素材：把反直觉的实现选择写成 1–3 句 ADR；用「难逆转、无上下文会意外、真实取舍」三条过滤；在决定发生的当下记录，而不是事后补。
