## 口播文章

### 人工评审的第三个作用

到目前为止，我们从两个角度看人工评审：提高速度，以及怎么排优先级。但我一直把最重要的一点埋在後面：每次做人工评审，我们不只是在检查代码有没有做我们想要的事，还应该想着改进「产出代码的系统」。

当然，这件事也有技能。我们跑 `npm run cherry-pick add retro skill`。〔待确认：ASR 原文此处为 "cherry hyphen pic"，第二处又说成 reset；按上下文应是 cherry-pick，避免重置掉 PR 里的工作〕换句话说，每当我们翻一个这样的 diff，都应该寻找可以下次警告 agent 的模式。我们应该想：哦，我喜欢这个，或者我不喜欢这个；也许它应该那样做，也许不应该。

所以人工评审背后的理论是：你永远不应该把同一条评论留两次。与其不断抓 agent 的错、把时间花在重复评审同样的垃圾上，不如每次留评论时，都把它放进系统里，帮助系统改进。这意味着人工评审不仅改进代码，也改进自动评审和自动检查。现在我们先专注用人工评审改进自动评审，别担心，自动检查后面会回来。

### retro 技能看什么

当然，这件事也有技能。你可以跑 `npm run cherry-pick add retro skill`。我们用 cherry-pick 而不是 reset，因为不想丢掉 PR 里所有好东西。跑完会在 `retro` 目录里得到一个 `skill.md`。

它写的是：retro conductor，对一次编码会话做复盘。用户要求复盘，你在建议改进编码 agent 的环境，以改善未来的运行。

`retro` 做的，是看任意 agent 会话，试着找出改进点。它会在这些类别里找候选：编码标准，这是我们先关心的，它会找可以变成编码标准的东西，并建议改进，所以它看 `coding-standards.md`；它看全局 `AGENTS.md`，找可以精简的地方；它看工具经济性，如果你的 agent 用了自定义基础设施，它检查能不能简化；它还看自动检查，以及我们课程后面会讲的导航。

你可以对单次会话用 `retro`，像我们接下来这样；也可以直接说「retro 看我最近 25 次会话，找找改进」。大多数 harness 会把会话保存成本地文件，方便回看历史。`retro` 技能会找到这些文件，看 agent 当时看到的原始材料，然后建议改进。

agent 通常会默默忍受，不会向你抱怨它的环境有多差。所以人去翻一翻，说「这个有用」或者「这个可能需要改」，它们会非常受益。我发现定期跑 `retro` 会让我震惊：我的 agent 环境原来这么差，有这么多改进机会。我猜你也很想试。那就来吧。干得好，下一集见。

> **思考一下｜同一条评论不留第二次**
>
> 这是一个很具体的效率目标：评审意见是系统改进的输入，不该当成一次性反馈。
>
> **可以追问**：怎么判断一条评论值得变成规则，还是只适合这次改动？
>
> **可延展方向**：给每条 PR 评论加一个标记：一次性、候选规则、已入标准。

## 综合解读

论点链：人工评审不只修代码，还要改进系统；重复出现的意见应该写进编码标准或 AGENTS.md；`retro` 读会话文件，按类别找改进；定期跑能发现环境里的系统性问题。

成立前提：harness 保存会话历史；评审意见能被识别和归类；团队愿意维护 `coding-standards.md` 和 `AGENTS.md`；人愿意花时间做复盘。

待核验主张：「agent 默默忍受差环境」是作者的经验描述；「定期 retro 会震惊你」是个人感受，没有量化；不同 harness 的会话保存格式不同，`retro` 的实际可用性取决于工具。

边界：`retro` 可能把一次性偏好误判成规则；规则太多会让评审和实现都变慢；复盘本身也花 token，尤其是多会话。

可迁移素材：把评审意见变成系统改进；同一条评论不留第二次；按类别做复盘；定期回看会话历史。
