## 口播文章

### 语言本身就是产出质量的一部分

自从 AI 编程在 2025 年 12 月前后变得可行以来，我一直对语言这件事很着迷。〔待确认：ASR 原文为 "in what December 2025"，具体月份听不清〕很多人低估了一点：用户和 agent 沟通时，沟通的质量，会在很大程度上决定产出的质量。我们使用的词、我们定义的东西、语言压缩到什么程度或者啰嗦到什么程度，都会产生很大影响。

现在的模型有个名声，就是不太好交流。你可以想象这样一个场景：你问 agent 一个关于 Cadence（作者的课程平台）的问题，比如「学习者能把钱退回来吗？」它可能回答：「退款资格包络由取消闸门评估，一旦权利租约释放，就转交给拒付结算处理器。」〔待确认：这段是作者模仿 agent 生造术语的例子，ASR 原文为 "the reversal eligibility envelope is evaluated by the cancellation gate..."〕

在我看来，这个回答里有四个生造的名字。这些名字在代码库里根本不存在，是 agent 自己决定这么叫的。agent 之所以生造名字，是因为这样很省 token。它把很多含义压进一个短名字，就能反复复用，不必每次都向自己解释。但对读这句话的用户来说，如果你不知道这些词是什么意思，而 agent 也没有解释，那简直就是噩梦。

所以我认为，最好的解决办法是有一份共享词汇，一份 `glossary.md`，用来在用户和 agent 之间沟通。听起来非常简单，但这个做法会在后面产生很多连锁影响。它是我找到的最好的技巧之一：不只能提高你和 agent 沟通的质量，也能提高 agent 自己的产出质量，改善代码库，还能改善下游用户的体验。

### 一个真实例子：同一个动作，三个名字

比如说，我们的应用里有一个活生生的 issue。它不算 bug，更像是一个语言问题。我们以 Liam Thompson 的身份登录，进入课程，打开「Introduction to TypeScript」这门课，然后点「取消我的购买」。我们看看会发生什么。

我们取消了他的购买，界面显示他有一笔「待处理的拒付」（pending chargeback）。在终端里能看到发给他的邮件，邮件里说他有一个「待处理的逆转请求」（reversal request pending）。也就是说，他请求应用取消购买，收到一封邮件说他的「逆转请求」被接受了，而现在他的账户上显示的是一笔「待处理的拒付」。

这种不一致的语言对用户来说是噩梦。同一个东西有三个名字已经算极端，但同一个东西有两个名字非常常见。而且这不只影响界面，也影响代码。我们 grep 一下 cancellation、reversal、chargeback，会看到代码里有 `getCancellationOffer`、`pendingChargebacks`、`buildReversalEmail` 这些名字。这意味着任何 agent 想走通这套流程，都得把同一个东西的所有不同名字找出来。这也意味着代码会重复，因为 agent 找不到它要找的东西。

### grill with docs：在追问时把语言定下来

修法是这样的：当你在弄清楚要做什么的时候，也把你要用来描述它的语言定下来。我最后落到的做法，是在 `grill me` 技能上做改进，叫 `grill with docs`。

`grill with docs` 使用 `grilling` 技能，`grilling` 基本是它的底座。它上面又叠了一个叫 `domain modeling` 的技能。`domain modeling` 会在你进行追问时主动挑战你的语言：它挑战术语，发明边缘场景，并且在术语一旦定下来时，立刻写出术语表和一组决定记录。

它写出的文件是 `glossary.md` 和 `docs/adr` 文件夹。我配置里的其他所有技能都会读这份术语表，确保自己使用一致的语言。这一节我们会学习怎么用 `grill with docs` 替换 `grill me`，怎么把语言决定定下来，并把它们变成一个漂亮的代码库，老实说，也是一个漂亮的产品。

> **思考一下｜术语表的作用边界**
>
> 作者把术语表当成用户、代码和 agent 之间的共同契约。这个契约越完整，agent 越不需要猜；但术语表本身也会变成需要维护的资产。
>
> **可以追问**：一份术语表要写到多细，才能真正约束 agent，而不是变成没人看的文档？
>
> **可延展方向**：把术语表和代码里的类型、路由、界面文案做一致性检查，让「说错词」变成可以自动发现的错误。

### 从 DDD 借来的只有一个词：ubiquitous

这里很多想法来自 Eric Evans 的《Domain-Driven Design》。DDD 把这叫 ubiquitous language（通用语言）。这是一本很厚的书，我们只取其中一个想法，也许两个，不碰 aggregates（聚合）、event sourcing（事件溯源）这些硬核内容。这里真的只是一份术语表，以及这份术语表的应用。

我希望你从这本书里带走的一个大词是 ubiquitous（无处不在）。这门语言必须在所有地方都一样。团队谈论产品时用的语言，必须和产品本身完全一致；代码使用的语言也必须和所有东西一致。

在 AI 之前，我待过很多项目：产品里实际存在的东西，代码里是另一个名字；所有使用产品的人都叫它一个名字，而真正在做产品的团队叫它另一个名字。在我看来，当你为正在做的东西找到正确名字的那一刻，你基本上就已经把它做出来了。因为你已经知道怎么在对话里使用它、怎么谈论它，然后知道怎么把它框给 AI，让 AI 把它做出来。

这就是这一节要讲的技术。干得不错，下一集见。

## 综合解读

论点链：语言不一致，agent 就只能生造词，或者找不到已有的东西，结果是代码重复、用户困惑。反过来，先把词定下来，沟通就能压缩得当，agent 的产出更稳，代码和界面也更容易统一。

成立前提有三条。第一，agent 会读 `glossary.md`，并且愿意遵守。第二，团队愿意持续维护这份文件。第三，术语足够稳定，不会每两周推翻一次。

待核验主张：作者说「AI 编程在 2025 年 12 月前后变得可行」，这是他的个人判断，不是可核验的行业事实；「三个名字极端、两个名字常见」是经验观察，没有给出数据；「找到正确名字就等于做出来了」是修辞，不是严格的因果结论。

边界：小脚本、一次性原型不一定值得维护术语表。术语表如果只增不减，会反过来变成负担，这也是后面「Pruning the Glossary」要处理的问题。另一个边界是，术语统一不能替代模型设计，名字对了但状态机错了，代码照样是错的。

可迁移素材：把同一个概念的所有别名列成清单；在写 spec 之前先写术语表；用界面文案反查术语是否一致；把异常路径也纳入领域语言，而不只是正常路径。
