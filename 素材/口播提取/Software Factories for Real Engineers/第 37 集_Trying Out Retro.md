## 口播文章

### 对 PR 34 做一次流程导向的人工评审

好，我们要对导致这个 PR 创建的所有会话跑 `retro`。第一步，复制 PR 号，然后跑 `retro`，看所有参与创建 PR 34 的会话。我还要加一句：把所有 PR 评论也抓进来。

所以我会过一遍实际 diff，在 GitHub 上留下我发现的评论。比如这里，我可以逐行评论，写「用 bookmarks，而不是这个」，还有「注释」。这样它就能在本地读到我的评论。

是的，我们这次要做真正的人工评审，但重点在流程，不在代码本身。这条评论有点太偏代码和实现了，我删掉。我们要找的是能进入编码标准、能变成规则的东西，这样就不用反复留同样的评论。

当然，如果你整天看代码、是领域专家，这会更容易。但即使不是，我也建议借这个机会看看代码，真正理解它在做什么。如果你对代码有疑问，可以趁机会问 `teach` 技能，我们在速成课里学过。

所以，做一次简短的人工评审，找出你觉得 `retro` 可以变成编码标准的评论，然后跑 `retro` 命令，让它把你做的一切都读进去，看看返回什么。祝你好运，解答集见。

> **思考一下｜流程评论和实现评论的区别**
>
> 「这里用 bookmarks 而不是 saved」是术语和约定的问题，可以变成规则；「这段逻辑写错了」是一次性实现问题。
>
> **可以追问**：如果一条评论既是实现问题又暴露了规则缺口，应该拆成两条吗？
>
> **可延展方向**：评审时给评论打标签：规则候选、一次性修复、需要讨论。

## 综合解读

这一集是练习说明，不是论证。可迁移的是：人工评审时区分「这次改错」和「以后都该这样」，后者才是 `retro` 的输入。

成立前提：PR 评论可以在本地被读取；`retro` 能访问相关会话；人能做一次简短但有针对性的评审。

待核验主张：没有需要外部核验的事实。

边界：如果评审只关注实现细节，`retro` 只能提炼出零散规则；如果评论太抽象，又难以变成可执行标准。

可迁移素材：评论区分流程和实现；让 `retro` 读取 PR 评论；用 `teach` 技能补代码理解；只留能变成规则的评论。
