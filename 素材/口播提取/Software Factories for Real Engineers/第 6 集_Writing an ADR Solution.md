## 口播文章

### 开场：先想清楚要用的词

好，我打开了 `glossary.md`，也把 Claude Code 和 `grill with docs` 配好了。我要仔细想一想接下来要用什么语言。重点肯定是 refund request、open refund request，然后从那里延伸到 refund、pending refund、issued refund。好，我觉得准备好了。

我们的应用里没有办法真正批准一个 open refund request。我们需要一个让管理员登录后能看到所有可用退款请求、看到这些课程已经有多少进度，然后决定是否批准的界面。我们还需要讨论批准之后会发生什么，因为退款被批准并不是故事的结尾，对吧？退款之后的事我先当作范围外，先专注在批准退款上。但是，open refund request 一旦被批准，我们就需要决定用户对课程的访问权怎么处理，甚至要决定他在哪个时间点失去访问权，以及是否删除他在课程里的进度。

总的来说，这个会话要做的事很多。看看我们能不能做完。

### 第一轮：代码和术语表暴露出的问题

好，它回来说它读了 `glossary.md` 和退款相关代码。可以看到这里的语言很混乱。课程访问权来自 enrollment（选课记录），不是 purchase（购买）。这意味着，如果批准退款后 enrollment 还在，学习者就保住了课程，而且永远不能再买一次。你能感觉到这些句子说出来有多别扭。这告诉我，我们需要做场景测试。

进度也不存在 enrollment 上。课程进度、观看历史和测验尝试，都是按学习者和课程分别存储的。另外，`admin` 在 schema 里有两个意思：可以是用户管理员，也可以是团队成员管理员。它甚至挑战了我们术语表里一些含糊的地方，说术语表写的是「团队批准或拒绝」，但 `team` 在应用其他地方已经指团队许可证了。哇。

它还发现了一个 bug，上一节我们也碰到过：课程页面在学习者完成 50% 的课程后就不再显示退款入口，但服务端 action 并没有检查这个条件。所以学习者理论上可以用 curl 直接打到退款请求。太好了，我们还有一个安全问题要处理。真棒。

### 逐题裁决：谁批准，何时失去访问

第一个问题：谁来决定退款请求？我想了想，应该是 platform admin（平台管理员），他们才有资格做这个决定。问题是，我们叫他们 platform admin 还是 admin？然后 team admin 就叫 team admin。也就是说，有两个选择：admin 加 team admin，或者 platform admin 加 team admin。我更喜欢后者，感觉更清楚。所以，谁来决定退款请求？只让 platform admin 决定。术语表里就把他们称为 platform admin 和 team admin。

它现在问：declining（拒绝）在范围内吗？在。

问题三：学习者什么时候失去访问权？选项是：提出退款请求时、管理员批准时、退款变成 issued refund 时。它建议批准时，我同意。选批准时是合理的，因为如果我们拒绝了他的退款请求，我们还是希望他能继续访问课程。

问题四：访问权被撤销后，他的进度怎么办？删除课程进度、观看历史和测验尝试吗？我同意它的建议，应该保留课程进度。

问题五：退过款的学习者还能再买这门课吗？我同意它的建议。当然可以，他都退款了，为什么不能再买？

问题六更像是界面问题：管理员看到多少进度？我同意它的建议。

问题七：哪条资格规则是对的？学习者看完超过 50% 的课程后，是否应该禁止退款？我同意它的建议。

问题八：界面应该列出哪些请求？我同意它的建议。这些问题里很多偏实现，我不太介意选哪边。这里更多是展示领域建模在起作用。

好，`glossary.md` 更新了。语言里多了一个 people 部分，有了 platform admin 和 team admin，其他条目也同步更新了。有意思的是，往术语表里慢慢加东西，也会让已有条目变清楚。现在所有相关条目里都加上了 platform admin。

### 团队许可证：一个句子读不懂就做场景测试

它现在问：团队许可证购买的退款请求被批准后，会发生什么？如果一个 team admin 买了 10 个座位，没人认领，然后他提出退款请求，而在请求还开放的时候，有人在第三天认领了一个座位，会怎样？

我觉得这段话非常含糊。每当我在 agent 的输出里遇到读不懂的句子，我就立刻想：需要做场景测试。这里说的 seat（座位）到底指什么？团队许可证购买和普通购买有什么区别？「批准会让所有未认领的座位代码失效」。我开始觉得，agent 和人的沟通在这里变得有点硌牙了。所以我先专注问题一，做一些场景测试。

但问题一本身也感觉很棘手。感觉术语表里有缺口，导致沟通混乱。我们能不能做一些场景测试？试试看。

这有点难，因为我基本上是在告诉人，也就是你，去依赖自己对困惑的感受。当你感到困惑时，就把这个感受当成触发器，去更新术语表、改进语言。

好，看看它返回什么。它去查了购买和座位认领的代码。它说代码里管这个叫 `coupon`，退款代码里叫 `seat`，而用户会说 team license。访问权并没有和授予它的那笔购买关联起来。天哪，这挺糟糕的。哇，这个也很糟：退款流程在一种情况下会退错购买。它总是选学习者最近一次购买该课程的记录。所以，我觉得我们找到该 grilling 的地方了，天哪。

这些场景看起来是想把退款周围的语​​言固定下来，让我们理解退款在这个特定情况下到底做什么。比如，Priya 是一个 team admin，她花 790 买了 10 个「Introduction to TypeScript」的座位。她自己不占座位。这和 Liam 花 79 给自己买，是同一类事情，还是不同类？它的建议是不同类。purchase 是总称，individual purchase 是给自己买的，team license 是给别人买的，并授予座位。

我们来做个映射：有 individual purchase，只给用户自己；也可以购买 team license，team license 给你座位。

场景二：Priya 后悔买了团队许可证，而且还没有人认领座位。这种情况下，退款批准后，团队许可证的座位就作废了。我不喜欢「作废座位」（void seat）这个说法，感觉很奇怪。

场景三：请求还开放的时候，有人认领了座位。它建议我们说，退款请求开放期间不能认领座位。这告诉我，这里有一个「已认领座位」和「未认领座位」的概念。如果我们有一条规则依赖于座位是否被认领，那这个概念就值得放进术语表。

场景四：Liam 先给自己买，然后又买了一个团队许可证。这意味着退款请求应该属于某一笔具体的购买。换句话说，我们开始得到一个层级：退款请求指向一笔购买，而购买可以是团队许可证，团队许可证有已认领和未认领的座位。

场景五：Ben 认领了一个座位，然后想要回自己的钱。Ben 认领了 Priya 的一个座位，但他讨厌这门课。他能提出退款请求吗？我同意答案应该是不行。

场景六：Liam 的个人购买退款了，他失去访问权，一周后 Priya 给了他一个座位。这个其实很聪明：他应该重新获得访问权，并且带着之前的进度，就像我们上一轮决定的那样。

我同意这里所有的建议。这确实挖出了一批语言。好，你的建议都很聪明，也挖出了一些关键语言，比如 claimed seat 和 unclaimed seat。我也喜欢你造出 individual purchase 和 team license 这两个词。好，发出去。

### 术语表再修：删掉 access 和 void seat

好，它一下子往术语表里塞了很多东西，所以这里要小心。purchase、individual purchase、team license、seat、unclaimed seat、claim seat，这些都说得通。我很不喜欢 void seat，感觉很不舒服。它还把 access 这个词造出来了，感觉很模糊。我觉得 access 是那种我们其实不需要造词的东西，不需要放进术语表，因为它本来就清楚：一个人有没有访问权是显而易见的。所以我要给它反馈：我不喜欢你加 access 这个词；我也不认为我们需要 void seat 这个术语，而且 void seat 这个组合本身就很糟糕。

你可以用自己的品味。如果术语表里有个词就是不顺眼，那就别用，或者拒绝它。但现在这里有一堆问题：team admin 在哪里给团队许可证提出退款请求？

漂亮的措辞。为了加快这一课，我可能对这些都直接说 yes。但我希望你们欣赏它使用的语言：platform admin 批准一个违反规则的请求；如果两个 platform admin 同时决定同一个请求怎么办。很可爱。当你开始觉得沟通很轻松时，那就是语言在好好干活。我同意上面所有建议。

好，发出去。好，它删掉了 void seat 和 access，很好。我觉得这两个都不是特别承重。现在它达到了共识，给了我们一个所有已决定和已考虑事项的总结。它还说它不建议写 ADR，因为这些决定里没有一个同时满足「难逆转」和「真实取舍」。

我不太同意。我们这里处理的是人们的钱。我想让你再对 ADR 做一遍检查，看看能从这次讨论里抽出什么，因为这里确实做了很多密集的决定，我不想让它们以后丢掉。看看它怎么说。

好，它好像转向了另一边：它说它把每个决定都对照 ADR 的三条测试检查了一遍，现在要写。好，我们看看 `docs/adr` 里有什么。我们有四份 ADR。

### 四份 ADR

第一份：批准退款请求会保留学习者的进度。当 platform admin 批准退款请求时，购买者失去课程里的位置（place），但保留课程进度。注意它有多短，就三行 Markdown，基本上没有别的东西。

第二份：课程里的位置在退款请求被批准时结束。注意这里有「考虑过的选项」：在请求提出时就结束，被否决，因为请求被拒绝的购买者会被白白锁在外面。

第三份：团队许可证退款是全有或全无，并且在退款请求开放期间座位冻结。这里也有考虑过的选项：开放期间可以认领座位，但之后只允许拒绝，被否决了。

第四份有「后果」章节：一个学习者每门课只有一个位置，无论它来自个人购买还是被认领的座位，而这个位置不记录来源。它说后果会传导到代码：退款请求要挂到购买者最近一次购买该课程的记录上。

我其实对这四份 ADR 很满意。它们都非常小，我认为都不显然，也都配得上留在这里。

> **思考一下｜「读不懂」是术语缺口的信号**
>
> 作者把「我觉得这句话别扭」当成触发器，而不是当成 agent 的毛病。这个反应顺序决定了他是去补术语表，还是去改 prompt。
>
> **可以追问**：如果一句话读不懂，怎么判断是术语缺失，还是 agent 本身推理错了？
>
> **可延展方向**：把会话中所有「读起来别扭」的句子收集起来，作为下一轮术语表修订的输入。

> **思考一下｜ADR 的「三条测试」由谁裁决**
>
> agent 第一次判断「没有决定值得写 ADR」，作者用「涉及人们的钱」推翻了它。标准是同一套，判断却不同。
>
> **可以追问**：当 agent 和人用同一套标准得出相反结论时，应该以谁的判断为准？
>
> **可延展方向**：给三条标准各配一个反例，让 agent 在判断前先对照反例，而不是只读标准文字。

## 综合解读

论点链：先用术语表里的词写 prompt，让请求更精确；agent 读代码后暴露「enrollment 与 purchase 脱节」「refund 选错购买」等模型问题；作者用「读不懂就场景测试」把团队许可证、座位、个人购买拆开；新词反过来澄清旧词；最后把密集决定写成四份短 ADR。

成立前提：术语表已经有 refund、open refund request 等基础词；agent 能读 schema 和退款代码；人愿意在长会话里逐题裁决；团队接受一次较大的模型调整。

待核验主张：agent 报告的「访问权没有和购买关联」「退款流程会退错购买」是 agent 的代码阅读结论，作者在讲解中接受了，但没有在画面上逐行验证。若要当事实使用，需要直接核对代码。作者说「语言让后面的一切更有底」是预期，不是已验证结果。

边界：这一集里作者为了加快进度，对一批实现问题直接说 yes，这是教学取舍，不是「所有问题都不重要」的结论。ADR 的三条测试仍然依赖判断，agent 和人可能得出相反结论。「access」被删掉，说明术语表不是越全越好，模糊的大词反而会稀释约束力。

可迁移素材：用「读不懂」触发场景测试；把「已认领/未认领」「个人购买/团队许可证」这类二分概念显式写进术语表；拒绝模糊大词；ADR 保持三行左右；当 agent 说「不需要 ADR」时，用「是否涉及不可逆成本」再检查一遍。
