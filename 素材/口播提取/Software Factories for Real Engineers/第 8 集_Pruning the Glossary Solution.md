## 口播文章

### 提示词：只保留和 Cadence 业务有关的词

我们看看 `glossary.md`，它感觉有点臃肿，我觉得里面有东西不是我们领域特有的。就这样，简单点，不用把事情搞复杂，看看会怎样。

好，问题一回来了：删掉实现细节和通用编程条目。这里有八条，描述的是代码，不是 Cadence 的业务。比如 `refunds` 表、`refunded_at`、`resolved_by user ID`。

我们看看这个。对，`refunds` 表这一条，是 agent 特别喜欢往 `glossary.md` 里加的经典内容：实现细节。它们喜欢把代码的具体细节加进术语表，但术语表不应该包含实现细节。实现细节会一直变。如果你把实现细节放进术语表，那么每次实现变化，术语表都得跟着更新。

这四条尤其没有给对话增加任何东西，也不属于领域模型，它们太贴近实现了。还有一些词太通用，对领域模型没有用。比如 `button` 这一条：「一个可点击元素，用户按下时触发动作。」我觉得现在每个人都知道 button 是什么。`component` 对我们这个具体领域模型来说也太通用了。换句话说，我们想建模的是「课程管理应用」这个领域，component 太泛，对这个模型没有具体用处。`CWD` 也一样，虽然它很短，对非开发者可能也容易混淆，但它不属于术语表，因为它不是 Cadence 特有的。`loader` 和 `slug` 也一样，太通用了。

所以我回复它：问题一，你说得完全对，这些都太偏实现，或者太通用了。

### 问题二：slug 是不是领域词

问题二在说 slug，也就是课程 URL 的安全名称。学习者、讲师或管理员谈到课程时会说 slug 吗，还是这只是路由细节？

问题二，我同意，它只是我们做路由的一个细节，不是 ubiquitous（无处不在）的，不是团队所有成员共享的词。你可以想象，如果 slug 在用户界面里变成重要概念，情况会变。比如界面说「选择 slug」或者「生成 slug」，那 slug 可能就属于领域模型了，因为它带了逻辑，我们需要谈论它、修它的 bug。建术语表是艺术，不是科学，留不留 slug 都有道理。但我喜欢把术语表尽量保持短，所以我选择不留 slug。

### 问题三和四：过期的小时数，含糊的 enrollment

接下来它说 watch limit 过期了。术语表说两小时，但代码现在用的是一小时。来了，这就是 `watch limit`。我们看看，对，这里写的是「看过不到两小时」。所以它把实现细节写进了术语表条目，而这个细节现在已经过期。我们正好看到了把实现细节放进术语表的痛苦。

它的建议是什么？建议删掉具体数字。这样限额变化时，术语表就不会过期。问题三，我同意。

往下看，问题四是什么？这里有一些含糊的说法：`enrollment` 和 `place on a course`。我们在用一个短语，其实可以压缩成一个词。我同意 `enrollment` 说得通。问题四，就用 `enrollment`。

### 问题五和六：lapsed 值得留，learner 需要定词

问题五在说 `lapsed`，它似乎把 lapsed 定义成「曾经有 enrollment，后来因为退款请求被批准而失去它」。我们看看实际定义：「一个不再活跃的 enrollment，在讲师的学员名单上显示为一个徽章。」所以它在用户界面里使用，也会传达给用户。对，我觉得这条值得保留，不过应该把它放到 enrollment 附近。它在这里的定义也写得不错：「一个在学习者课程上失去 enrollment、但仍然保有进度的学习者。」问题五，我同意，不错。

下一个问题问：要不要把 `learner` 定义成一个正式词，指在 Cadence 上课的人？现在我们在把原本散落在其他定义里的东西合并起来。`learner` 在八个定义里被用到，但从来没有定义过。代码里有些地方还写 `student`，这很有意思。

这个问题我真的没有偏好。我觉得两个词一样好，但我们需要统一成一个。我愿意用 `learner`，而且我觉得应该把所有写 `student` 的地方改成 `learner`。这又是一个小胜利，让 agent 更容易导航，也更容易谈论。

它现在问术语表内部的标题怎么组织，我真的不在乎。问题七，你随便，我不管。

### 一个反转：代码里其实更常用 student

好，发出去看看。好，它重写了术语表，从 113 行变成了 87 行。而且 student 和 learner 这件事其实挺有意思：`student` 在 23 个文件里出现了 112 次。那 `learner` 呢？`learner` 在代码库里出现多少次？我们问一下，快速拿个结果，感受一下。

好，看起来代码其实已经大致统一在 `student` 上了。`learner` 只出现 8 次，`student` 出现 180 次。所以看起来应该围绕 `student` 统一。我本来在 learner 和 student 之间五五开，但现在看到改成 learner 的工作量这么大，我更愿意直接用 `student`。我们还应该把现有的 learner 条目改成 student。

它之前还有一个问题九，我回去处理。ADR 里还要继续说 `place on a course` 吗？我们现在基本已经给这个概念选了词，选了 `enrollment`。所以 ADR 是不是应该改成说 enrollment？我觉得应该，这样更干净，而且 agent 每次读 ADR 都会强化这个词。回到问题九：对，更新 ADR 文字，用 enrollment，不再用 place on a course。

### 把新词回写到 ADR 和代码注释

好，这样我们应该接近最终结果了。它在过代码，主要在看注释。注意，注释也是强化领域语言的好地方。我们可以看到 `docs/adr` 文件夹里，它已经更新了这些内容，现在用的是新语言：购买者失去的是 enrollment，这里也用 student 而不是 learner。

它又回来问了几个问题。它问 ADR 的文件名要不要改。要，改成新语言。它还问要不要把代码里的 `place on the course` 也改掉。要，代码里也改成 enrollment 的语言。

你可能会想，这也太硬核了，确保代码处处体现领域语言。但这真的非常必要。老实说，有 agent 之后这些改动太便宜了，为什么不去把应用里所有破窗户都修好，让领域语言在每个地方都一致？

好，它给出了最终总结。我们把术语表修剪下来了，看看最终形态。不错。`watch limit` 被放进了退款部分，这很有用。我确定顶部有一个关于 enrollments 的部分。对，「一个学生在课程上的位置」。people 也有自己的部分：student、instructor、platform admin、team admin。很好。

你会发现，修剪这件事并不简单。到底什么属于术语表、什么不属于，是有艺术性的。但你越关注它，它就越有用。而且还要确保 ADR 里使用的所有语言也同步。现在我们把 place on the course 换成了 enrollments。随着时间推移，我们的语言会越来越准确、越来越精确，代码也会受益。修剪得不错。干得好，下一集见。

> **思考一下｜实现细节为什么会污染术语表**
>
> 实现细节变化快，术语表变化慢。两者绑在一起，术语表就会被代码拖着走，最后失去约束力。
>
> **可以追问**：一个词如果既像领域概念又像实现细节，应该先删掉，还是先观察它是否被界面文案使用？
>
> **可延展方向**：给术语表条目加一条规则：定义里不能出现具体的表名、字段名、数字阈值。

> **思考一下｜用代码词频决定术语**
>
> 作者本来想用 learner，发现代码里 student 出现 180 次、learner 只有 8 次，于是反过来统一到 student。
>
> **可以追问**：如果代码里的用词本身是错的，但改起来成本很高，应该迁就代码还是纠正代码？
>
> **可延展方向**：把「代码词频」作为术语决策的一个输入，而不是唯一依据，和界面文案、用户说法一起看。

## 综合解读

论点链：术语表膨胀后，先删两类杂质：实现细节会过期，通用编程词没有领域约束力；再处理含糊短语，把它压缩成单词；最后用代码里的实际用词决定统一到哪个词，并把新词回写进 ADR、注释和代码。

成立前提：agent 能扫全仓库并统计词频；术语表被当作约束，而不是百科；团队接受一次全局改名的成本；ADR 和注释确实会被 agent 读取。

待核验主张：术语表从 113 行降到 87 行，`student` 在 23 个文件出现 112 次、全库 180 次，这些是 agent 报告的数字，作者在画面上接受，但没有独立复核。若要引用，应重新跑统计。

边界：作者自己说这是「艺术不是科学」。slug 留不留都有道理；删掉 watch limit 的具体数字，避免了过期，但也失去了精确阈值。统一到 `student` 是成本考虑，不代表 `student` 在语义上更好。

可迁移素材：两条默认删除规则（实现细节、通用词）；用词频辅助决定统一到哪个词；术语变更后同步 ADR、注释、文件名和代码标识符。
