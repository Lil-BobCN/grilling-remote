## 一句话摘要

这一集回答五个常见问题：一个术语表够不够、什么时候合并术语变更、好词从哪来、要不要先有术语表、agent 能不能独占术语表。作者的核心回答是：按 bounded context（限界上下文）拆分，决定后立刻更新，从用户嘴里挖词，边做边建，而且必须有人把关。

## 口播文章

### 一个术语表够用吗

好，到这里，我想我们对领域语言怎么运作、ADR 怎么运作、怎么用 `grill with docs` 在开工前把语言磨锋利，以及这样做有什么好处，已经有了不错的把握。下面过几个关于这套方法的常见问题。

第一个问题：一个术语表总是够用吗？应用越来越大时怎么办？应用里已经有一个很好的例子，我们还没把它术语化。在 Cadence 里，测验（quiz）里可以有问题和答案：学习者被问一个问题，然后给出答案，这些在数据库里都是实体。但课程（lesson）里也有讨论（discussion），学习者可以提问，讲师能看到讨论里的所有回答。如果我们对这两者都用 `question` 这个词，很快就会混乱。

一个简单的处理办法是永远加前缀。这样你总是知道自己在说 quiz question 还是 discussion question，永远不单独说 question。这有点像我们已有的 platform admin 和 team admin：它们从不单独被称为 admin，术语表的 avoid 部分专门写了这一点。但你可能会走到另一个极端，前缀加得太多，然后意识到：其实这里有两个不同的对话，各自在用不同的词。

Eric Evans 在《Domain-Driven Design》里谈过这个：任何大项目里都有多个模型在同时起作用。理想情况下，一个大公司用一套语言谈论业务。但实践中，组织不同部分往往不一样。比如我们之前看的 refund 和 chargeback：在产品里，我们用 refund 谈论请求和结果；但在财务部门，他们对实际发生的事有更深的模型。财务需要区分 refund 和 chargeback，而产品根本不需要关心。两个团队都是对的。这就是同一家公司里在用的两套 ubiquitous language。

在 DDD 里，每一个都叫 bounded context（限界上下文），也就是公司某一部分运作的语境。关键是，这两个部分的开发者可能都在往同一个仓库提交代码。所以，如果你的仓库里存在不同的 bounded context，你要把它显式化。好消息是，我在 `domain modeling` 技能里已经想到了这一点。在 `domain modeling` 里，你可以让仓库只有一个语境，根目录一份术语表；也可以用 `glossary-map.md`，把它映射到应用不同部分的不同术语表。这意味着，即使同一个仓库里有不同的 bounded context、不同的说话方式，`domain modeling` 也能处理。ADR 也可以按 bounded context 分开：你可以有一组全局 ADR，影响整个公司时往里加；也可以只给某个 bounded context 用单独的 ADR。规则是：当你感觉有两个 bounded context 想挤进同一份术语表时，就拆。

### 什么时候合并术语变更

下一个问题：什么时候把术语表的更新合并进去？假设我们的循环是 `grill with docs`，然后可能到 spec、ticket、实现、代码评审。术语变更在哪一步合并？

我的看法是：一旦决定做出，并且可能和团队确认了这就是要用的术语，就合并，甚至要在写 spec 之前。这样等你走到实现步骤、在实现 spec 和 ticket 时，代码库已经和你想的样子一致了。也就是说，你可以自己更新 `glossary.md`，确认它看起来完全是你想要的样子，然后再去写 spec 和 ticket。如果你有需要重命名的代码，就像我们在练习里碰到过几次那样，我也会在写 spec 之前做。这样 spec 和 ticket 创建时，指向的已经是重命名后的文件，代码库也更好导航。

### 好词从哪里来

下一个问题：怎么挑好词？好的术语表条目长什么样？

大多数时候，我们是在给别人、给真实用户做应用，他们要在现实世界里用这些东西做事。最好的领域语言来自你的用户。如果你能让产品里的语言，和人们使用产品时的想法对上，你就会得到一个很好用、也很好维护的产品。所以答案很简单：认真听用户说话，从他们用的词里挖术语表的灵感，也挖怎么建应用的灵感。项目早期尤其如此，你应该多和用户聊，想清楚他们需要的东西该怎么建模。

### 需要先有术语表吗

下一个问题：用 `grill with docs` 时，需要先有术语表吗？还是可以边做边建？

我希望这些课已经展示了：你完全可以没有任何术语表就开始，然后慢慢建，随着你长大，把画面逐渐澄清。在我看来，术语表永远不会真正完成。总有一些东西可以定义，或者正处在「快要被定义」的边缘。而且我觉得，往术语表里加东西和修剪它都挺难，需要大量思考，因为你在实时澄清产品。所以我会说：慢一点，只创建你正在做的东西所需要的条目。赶工的另一个问题是，你可能会创建质量很差的条目，然后还得再修剪。所以，只建当前需要的，慢慢来。

### agent 能独占术语表吗

关于领域建模，我还经常被问：能不能让 agent 自己拥有术语表、自己负责处理，完全不需要人在环里？

在我看来，这是把术语表变成垃圾场的最快方式。我们创建这门语言的目的，是让它 ubiquitous：代码里用、团队里用、产品里用。关键在于，团队是人，现在也包括 agent。如果 agent 自己跑出去发明一套术语，那和团队是合不来的，因为团队会用另一套语言。所以我的回答是：不行，agent 不能独自拥有术语表。老实说，维护术语表是人能为代码库健康做出的最高价值贡献之一。

所以，我希望你现在有足够的动力去寻找定义你产品的语言。如果你想多读一点，这本蓝皮书很好，当然我会在下面放链接。还有 Vaughn Vernon 的那本，我放在某个地方，应该在床头柜上。不管怎样，主要想法是，我希望我在这里讲清楚了：一切都是关于 ubiquitous language，找到正确的词，并让这些词在产品里到处被使用。干得好，下一集见。

> **思考一下｜什么时候该拆 bounded context**
>
> 作者给的信号是「两个语境想挤进同一份术语表」。这比按团队结构或代码目录拆分更贴近语言本身。
>
> **可以追问**：如果两个语境 80% 的词相同、20% 不同，拆开会不会让共享部分反而重复？
>
> **可延展方向**：用 `glossary-map.md` 记录每个语境的词表和重叠词，定期检查重叠部分是否在漂移。

> **思考一下｜人为什么必须留在术语表的环里**
>
> 作者的理由是「语言必须在人和 agent 之间共享」；关键不在「agent 做不好」。agent 单方面发明词，就破坏了共享的前提。
>
> **可以追问**：如果 agent 提议一个新词，人应该逐条审批，还是只在它和现有词冲突时才介入？
>
> **可延展方向**：把「新增术语」设为需要人确认的动作，和改代码分开授权。

## 综合解读

论点链：一个术语表在应用变大后会遇到同名不同义；解决办法是按 bounded context 拆，不必无限加前缀；术语变更要在 spec 之前落地；好词来自用户；术语表边做边建；agent 不能单方面拥有语言，因为语言的前提是共享。

成立前提：团队确实存在多个语境；用户可以被接触和访谈；团队接受维护多份术语表和 `glossary-map.md` 的成本；issue tracker 和技能能读这些文件。

待核验主张：作者对 Eric Evans 的转述是概括，不是原文；「维护术语表是最高价值贡献之一」是价值判断；「agent 独占会变垃圾场」是基于经验的预测，不是实验结论。

边界：小项目、单一语境不需要拆 bounded context；前缀加太多会反过来增加沟通成本；「慢一点、只建需要的」在交付压力下很难执行。

可迁移素材：用 `glossary-map.md` 管理多语境；在 spec 之前合并术语变更和重命名；从用户原话里挖词；把术语表的最终决定权留在人手里。
