## 口播文章

### 风险：agent 会不会调用这个技能

好，开始吧。任何我们自己不调用的命令或技能，风险都在于 agent 会不会调用它。我们从速成课里知道，这很大程度上取决于技能描述怎么写、写得多详细、里面有没有引导词，以及它们能不能根据当前任务触发。

来了，太好了。它说：「我给你建一个向导，带你完成 Knock 后台的注册，并把生成的密钥写进 `.env`。」显然它读了所有研究、Wayfinder 地图，以及它依赖的所有票，所以它完全知道我们在流程的哪一步，知道我们选了 Knock，拿到了所有需要的上下文，随时可以开始。它甚至去查了 Knock 文档，查后台的准确路径，这样向导就不会编造步骤。

当然，如果你跟着做，你可能会有一个类似的任务，甚至不是同一个服务，但向导会给你需要的东西，让注册变得非常简单。

### 生成向导，在独立终端里跑

好，我们只用了区区 4.4 万 token，就有了一个 Knock 设置向导的 bash 脚本。像我在问题视频里说的，我不在 agent 里面跑它。我会复制这个小脚本，打开一个终端，在终端里跑。

所以左边是 agent，右边是浏览器，因为向导会自动帮我打开 URL。我按回车，因为我准备好开始了。它打开了 `dashboard.knock.app`，给我一串步骤：注册或登录，为 Cadence 创建账号组织；留在免费开发者计划；不要开始试用或付费计划；用左上角的环境选择器选开发环境。

我已经做了几个初始步骤：注册了，左上角是开发环境，留在免费开发者计划，所以我觉得可以继续。它现在让我把地址栏里的后台 URL 粘进去，留个记录。我把它粘进去。

这些向导的一个很酷的地方是，它完全不连接 agent。所以我可以把密钥粘进去，我知道它永远不会离开我的系统。向导拿这些密钥做什么就做什么，不会把它们发给 agent，再由 agent 发给 Anthropic 之类的地方。

它现在让我点左侧栏底部的设置，找到 channels and sources，然后在应用内 feed 里创建一个 channel，命名为 `cadence feed`。我有点怕密钥出现在屏幕上，所以这一步我自己做。看起来我其实找到了一个已经存在的应用内 feed channel，那我就把 channel ID 粘进去。

接下来复制 API key：左侧栏 platform API keys，复制 public key。好，我做了。流程已经收到了我的 private key 和 secret key。它现在让我在同一个 API keys 页面找到 application signing keys，生成一个 key，复制单行 base64 编码的版本。

注意这有多简单、多不用动脑：它为我们打开正确的页面，告诉我们具体做什么，然后只是一个文本框，我们把东西粘进去。我现在做完了。它让我打开增强安全模式。它对自己的弱点还挺诚实：Knock 文档没说开关在哪，先试 API keys 页面或环境设置。结果在 API keys 页面，所以我按 Y，因为增强安全模式现在开了。

### 四个值写进 .env

好，设置完成，我们往 `.env` 写了四个值。我的 `.env` 现在长这样：feed channel ID、public API key、secret API key、Knock signing key。这当然在 git ignore 里，所以提交时不会进公开仓库，这些只是本地设置。

### 验证：发现签名密钥被截断

我现在回到 agent，说：好，向导跑成功了，你能不能验证一下本地一切正常？然后提交。它现在应该关掉这张票，因为活干完了。看起来它在验证签名密钥的格式，但不把密钥显示出来。agent 知道不要把密钥读进环境变量，但它们不总是做对。可以看到它在尽量不读取密钥的情况下验证一切。

啊，幸好我做了这一步。看起来长的签名密钥没有正确加载，被截断了。我不太想再把每一步走一遍，所以我说：你能不能直接告诉我怎么手动做这一步？我很确定我只需要把签名密钥重新复制粘贴进 `.env`。我现在回到 platform API keys，手动做。

好，我做完了。你能再验证一次吗？我刚复制粘贴了。好，可以，现在一切检查通过。它甚至向 Knock 发了一个真实的签名 token 请求，实际用 API key 测了 Knock API。它现在记录 resolution，并放到地图上。太好了，活干完了。我们知道本地设置能工作，准备好开始原型了。

希望你喜欢 `wizard` 技能。它算是额外的，不是必需的，但我发现一次设置五个不同服务商时，它真的非常有用。干得好，下一集见。

> **思考一下｜向导和 agent 的信任边界**
>
> 向导不连 agent，所以密钥可以留在本地。这个设计把「操作」和「推理」分开，代价是人要手动跑终端。
>
> **可以追问**：如果向导本身需要读 agent 生成的文件，怎么保证密钥不会顺着文件流回模型？
>
> **可延展方向**：给向导加一条规则：只写 `.env`，不打印密钥，不把密钥写进日志。

> **思考一下｜验证发现截断**
>
> agent 验证时发现签名密钥被截断，作者手动重粘。这个错误不是 agent 造成的，但验证抓住了它。
>
> **可以追问**：哪些配置错误可以自动验证，哪些必须靠人眼检查？
>
> **可延展方向**：验证阶段加一条「真实 API 调用」，比只检查格式更能发现配置问题。

## 综合解读

论点链：任务票需要人操作外部后台；`wizard` 技能生成交互式 bash 向导；向导读地图和研究，打开正确页面；人完成注册和取密钥；四个值写进 `.env`；agent 做格式检查和真实 API 调用验证；发现截断后手动修复；票关闭。

成立前提：agent 能根据任务触发 `wizard`；向导能访问研究结果和地图；人愿意在独立终端操作；密钥只存本地 `.env`。

待核验主张：「4.4 万 token」是这次运行的观察，不是固定成本；「向导通常会在合适时触发」取决于技能描述和模型；Knock 的后台路径和免费计划政策可能变化，需要按当前文档核对。

边界：向导适合步骤明确、界面稳定的第三方服务；如果后台改版，路径会过期。真实 API 调用验证很好，但会产生外部请求和额度消耗。作者手动处理了怕密钥上屏的步骤，说明向导不能完全消除人的判断。

可迁移素材：任务票 + 向导；把密钥留在本地；向导只做人能做的步骤；验证用真实调用而不是只看格式；发现截断就手动修，不重跑全流程。
