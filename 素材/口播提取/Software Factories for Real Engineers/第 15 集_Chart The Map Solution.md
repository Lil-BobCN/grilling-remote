## 口播文章

### 初始提示词：只说到够用

好，用一个老派的好提示词开始。我想在 Cadence 里做应用内通知。我想用真实的第三方服务来处理。我想弄清楚要发哪些通知，也需要弄清楚它在应用里到底长什么样。我觉得这些差不多够了。应用内通知是大家都熟悉的东西，这个阶段不需要过度指定。

可以看到它加载了 `grilling` 和 `domain modeling` 技能。所以我们本质上是在做 `grill with docs` 会话，只是多了一点 Wayfinding。

### 第一轮：目的地和范围

好，看看。它的问题从「这张地图的完成状态是什么」开始。它问：应该是一份 spec、一个能跑的构建，还是只做决定？问题一，我说做成 spec。很稳。它知道 spec 和可运行构建是两个主要选项。

它现在问范围：什么算「应用内」？这是 Wayfinding 里非常重要的一部分，尤其在这个早期阶段：弄清楚到底要建什么、目的地长什么样。很容易走太远。我们肯定想要应用内信息流（feed），但我觉得也想要推送通知。也许还可以探索邮件。Cadence 没有移动应用，所以我怀疑应用通知到底有多可行，也许我们需要默认用邮件。

第三个问题：服务商还开放吗？你说真实的第三方服务。它的建议是：选服务商是地图的一部分，由研究票驱动。问题三，对。选服务商肯定属于这张地图。我明确偏好托管第三方服务，我不想自己托管。

我们稍微缩小一点，看看更多文字。它问：这是为了什么？Cadence 目前用的是开发用的 UI 用户切换器，不是真正的认证。这份 spec 应该是生产级功能吗？对，我们要生产级功能。

这些问题都合理，答案也合理。看看它返回什么。

### 第二轮：研究票和角色范围

好，第二轮问题来了。它问：第二个渠道怎么决定？应用内信息流是固定的；推送和邮件，是现在决定、先研究，还是三个渠道都写进 spec？它的建议是开一张研究票。我觉得有道理。问题一，我同意。

注意它对「自己知道什么」很克制。它知道自己需要出去找信息，而 agent 很少这样做，有时它们会没有信息就一头冲。

它问：哪些角色在范围内？术语表里有 student、instructor、platform admin、team admin。看这个，我们的领域建模现在回来报答我们了，我们正在收获之前工作的好处。对，目录肯定要覆盖全部四个角色。

下一个：服务商需要支持什么？它说预构建或 headless 的 React 应用内信息流组件。问题三，我不太在乎 React 组件，我们自己建也没问题。我们主要需要的是开发阶段可用的免费额度。

问题四：要不要在选之前亲手试试服务商？它问，研究把范围缩到两家后，是只看文档选，还是加一张任务票去把两家都注册了？问题四，我想尽量少注册服务。我只想选一个合理的，然后用原型看看它行不行。

问题五是个很好的范围问题：用户可以控制通知吗？是按类别控制，还是按渠道控制？问题五，我同意它的建议。不错。

接下来是领域建模问题：我们叫它什么？我想往术语表里加 notification。它建议 notification，以及把位置叫 inbox；但我更喜欢 notification 和 notification feed。我觉得这两个最自然。

好，很好。这些感觉都不错。甚至在地图创建之前，我已经开始感觉到路了。你懂我意思吧？我明白：我们会做一些研究，然后有一张任务票去注册服务，也许做点原型看看它怎么工作。可以看到它已经在写 `glossary.md`，很好。

### 地图成形：七张票，四种票型

看起来我们达到共识了。它正在创建一堆票，还有一堆东西留在迷雾里、尚未指定。关键是，这张地图大约有七张票，四种票型都出现了：prototype、grilling、task、research。这其实是我第一次跑这个练习，我特别希望它能这样。从老师的角度，我现在非常开心。

看起来都不错，我说「去做吧」。然后我们会注意到，立刻有两个研究子代理被派出去。所以我告诉它：好，继续创建地图。看看会发生什么。

好，它把所有东西都创建了。非常兴奋。可以看到它也在后台启动了两个 agent：一个在研究通知服务商，一个在研究 web push 的覆盖范围。我们打开地图看看。

### 地图的结构

好，可以看到顶部是目的地：为 Cadence 做生产级通知，通过一个托管第三方服务商交付。这里有一些含糊的笔记，很好，它在记住我们画图时做的决定。然后「decisions so far」下面是空的，因为我们还没做决定。下面是「not yet specified」，也就是还在迷雾里的东西。再下面是范围外：我们不做原生移动应用，不自托管通知服务商，不自己建投递基础设施。

底部是票。注意我们能看见哪些是开放的、哪些当前被阻塞，甚至能看到哪些已经分配给子代理。事实上，我正在录的时候，有一张刚刚关闭。所以这两张都被 agent 拿走了。看起来第一张是唯一可用的，这是一次 grilling 会话。右边有 `Wayfinder grilling` 标签，这是它会带进会话的问题。

### 研究结果：Knock 和渠道策略

把这个当练习跑有个麻烦：你最后得到的地图可能和我的差很多。所以这一节我会把每一张地图、每一张票和每一次更新都保存下来。这样你可以完全跟着走，也可以自己画，把我的当参考。

我们已经能看到地图被两个子代理更新了。两张研究票都关闭了，它根据研究选了一个实际服务。看第一张：哪个托管通知服务商适合 Cadence？它保留了原始票和问题，解决方案是使用一个叫 Knock 的服务。它比较了 Novu Cloud、MagicBell 等。这里还做了件聪明事：在评论里给你研究发现摘要，但完整研究保存到一个一次性分支里的真实文件中，任何 agent 都可以去看完整研究。它还链接回原始来源，里面有完整对比。漂亮。

再看地图，另一项研究也有结果了：没有原生应用时，web push 能覆盖多远？它的结论是：邮件应该作为 Cadence 默认的应用外渠道；web push 只有在人们主动选择加入时，才作为额外渠道可信；它发送的所有内容也应该落在通知信息流里。

很好。我们现在有可以查看、可以继续 grill 的研究。地图有了，研究做完了，一切都准备好让我们成功。非常激动。我就是喜欢用 Wayfinder，很好玩。干得好，下一集见。

> **思考一下｜目的地先定成 spec**
>
> 作者把「一份能交给 agent 的 spec」当目的地，没把「做完通知功能」当目的地。这改变了地图上所有票的问法。
>
> **可以追问**：如果目的地是 spec，怎么防止 spec 本身变成另一张没有终点的地图？
>
> **可延展方向**：给 spec 定一个明确的完成标准，比如「每个决定都有对应票，每个票都有结论」。

> **思考一下｜研究票的产物放哪里**
>
> 研究结论摘要写在票的评论里，完整研究放在一次性分支的文件里，还链接原始来源。这兼顾了可读性和可追溯性。
>
> **可以追问**：一次性分支什么时候清理？如果清理了，后续 agent 还能追溯到原始来源吗？
>
> **可延展方向**：把研究产物的路径写进票的正文，而不是只在评论里。

## 综合解读

论点链：面对通知功能的迷雾，先用 Wayfinder 会话定目的地（spec）和范围；范围逐步收窄到应用内信息流、推送、邮件和服务商选择；研究票被识别出来后自动派给子代理；研究结果回填地图，决定服务商和渠道策略；地图同时保留已做决定、未定迷雾和范围外。

成立前提：术语表已经覆盖角色词；issue tracker 支持子票和依赖；子代理能访问外部资料；团队接受托管第三方服务。

待核验主张：Knock、Novu Cloud、MagicBell 的对比是 agent 的研究结果，作者在讲解中接受，但没有独立验证；「web push 只有 opt-in 才可信」「邮件应作为默认应用外渠道」是研究结论，也需要外部核验；「约七张票、四种票型齐全」是这次运行的观察，不是固定产出。

边界：不同人跑同一个练习会得到很不一样的地图；范围问题（要不要做邮件、要不要做推送）是产品决定，不是 Wayfinder 自动得出的；研究结果会过时，服务商价格和能力需要重新核对。

可迁移素材：目的地定成 spec；范围要一轮轮收窄；研究票让 agent 离开键盘去拿事实；地图同时记录已决定、未定和范围外；研究产物要可追溯。
