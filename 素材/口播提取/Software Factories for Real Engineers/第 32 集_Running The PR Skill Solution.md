## 口播文章

### 生成 PR 正文

好，开始：你能不能拿 PR 34，给它写一份 PR 正文？我们试试，看看返回什么。可以看到它成功加载了技能，很好。它现在跑类型检查和测试套件，作为证据。不错。

看看它做了什么。它给了我们一份 PR 正文提案。我不太想在这里逐条看，直接说：好，发出去，看看效果。

它还发现代码里有一些不一致，我们待会可以看看。

### 摘要：用视觉 diff 讲改动

这是它给的摘要。可以看到实际文字非常短，它主要靠这个大的 JSX 风格 diff。它说，在 lesson viewer 里，我们现在有一个书签开关，可以打开和关闭书签；还有 lesson note，写着 save note。在 sidebar 组件里，有一个 saved 按钮，应该会去你的保存笔记；而且只有 students 能看到。

注意它说的是 students，不是 learners，因为 PR 技能会读术语表，确保使用你的领域语言。然后在 saved 路由里，有 bookmarks 和 notes：书签最新的在前，笔记最近编辑的在前。在 instructor student roster 组件里，有 student notes，展示每个学生在这门课各节课上的笔记。在 schema 里，可以看到所有新表：bookmarks 和 notes。

### 证据很弱，但诚实

我得说，这里的证据比较弱。它基本上只是看了代码，然后说：以前课程上没有书签或笔记，也没有 saved 路由。不过它确实告诉我们证据弱：改完之后类型检查和测试通过，但实际上没有测试覆盖书签或笔记。这挺尴尬的。

### 合并风险：单向门，隐私爆炸半径

这里是 merge danger。它说这是单向门，因为迁移 O12 只加表。一个学生写了笔记之后，回滚要么留下孤儿表，要么删掉他们写的内容。这是对的。换句话说，我们给学生机会写笔记，如果回滚，就会删掉他们的数据。

它还说爆炸半径是隐私：术语表里说笔记对写它的学生是私有的，但讲师名单把每个学生的笔记都展示给讲师。这里有矛盾。

### PR 质量低，先跑自动评审

看起来它对这份 PR 的质量不太满意，想改一堆东西。它说 `saved` 每个书签或笔记大概跑三个查询，是 N+1 错误。抱歉，不是 N+1 错误，N+1 通常指可以优化的算法。它还说，这些行引用的 lessons 和 users 不能删除，因为外键用了 `on delete no action`。

总的来说，只读这份相对短的摘要，就塞进了很多信息。我们知道这是单向门，所以可能需要人工评审。但我们也看得出这个 PR 质量相当低，因为连 PR 技能都没花多少 token，就发现了大量不一致。所以在我们花人力手工评审之前，应该先跑点什么。这就是下一步。干得好，下一集见。

> **思考一下｜PR 技能诚实标注证据弱点**
>
> 它没有假装测试覆盖了书签和笔记，明确说「没有测试覆盖」。这种诚实比漂亮的摘要更有价值。
>
> **可以追问**：如果 agent 倾向于夸大证据，PR 模板应该怎么设计才能逼它承认缺口？
>
> **可延展方向**：在证据部分加一栏「没有覆盖的路径」，让缺口显式出现。

> **思考一下｜单向门判断来自迁移**
>
> 这个 PR 的单向性不在于代码难改，而在于数据库迁移加了表，回滚会丢用户数据。
>
> **可以追问**：如果迁移是只加表、不删改，为什么回滚仍然危险？
>
> **可延展方向**：把迁移按「可逆/不可逆/会丢数据」分类，写进 PR 的 merge danger。

## 综合解读

论点链：PR 技能读 diff 和术语表生成摘要；证据阶段跑类型检查和测试，但承认没有覆盖新功能；merge danger 识别出迁移导致的单向门和笔记隐私的爆炸半径；同时发现 N+1 查询和外键限制，说明质量不足以直接交给人。

成立前提：PR 技能能读术语表和 diff；项目能跑类型检查和测试；迁移和数据模型能被分析；agent 愿意在证据不足时明说。

待核验主张：N+1 查询、外键 `on delete no action` 的影响、迁移 O12 的具体行为，都是 agent 的代码阅读结论，作者在讲解中接受，但没有逐行验证。若要当事实使用，需要直接看代码和迁移。

边界：摘要依赖 agent 对 diff 的理解，可能漏掉跨文件影响；证据弱不代表代码一定错，只代表没有验证；单向门判断可能因项目而异。

可迁移素材：PR 摘要用视觉 diff；证据部分要写清未覆盖路径；merge danger 同时看可逆性和爆炸半径；质量低的 PR 先跑自动评审再交给人。
