## 一句话摘要

作者删掉四份够不上 ADR 标准的记录，把一份被反转的决定写成新 ADR，并在新 ADR 的「考虑过的选项」里保留旧做法。最后得到一份约八到九条的健康 ADR 列表。

## 口播文章

### 提示词与第一问：删除还是标记废弃

好，发一个提示词。这个仓库里有一堆 ADR，我想把它们修剪一下，要么删掉，要么标记废弃。看看会怎样。

它在做探索。它没有启动子代理，关键动作是核对 ADR 是否仍然和代码一致。这非常重要。

好，它问了问题一：这里的删除和废弃到底是什么意思？选项一：删掉那些从来就不是值得记录的真实决定的 ADR；废弃那些曾经是真实决定、后来被反转的。选项 B：删掉所有不再适用或从未够格的；反转的决定写进新 ADR 的「考虑过的选项」里，而不是保留旧文件。它推荐 B，因为一份被取代的 ADR 如果还留在 `docs/adr` 里，就是个陷阱：agent 和新读者会把它当成当前决定。

我觉得我同意。A 和 B 差别不大，所以 B 可以。问题一，B 听起来不错。

### 问题二：两份够不上标准的记录

接下来它指出几份 ADR：7 号 Lucide React 和 11 号 Prettier。它说这两份都达不到 ADR 的标准。我们看看 Prettier 那份。它非常非常短：「使用 Prettier，不要改它的设置。每个文件都用仓库初始的 `.prettierrc` 格式化。」

对，这份我觉得不值得写 ADR。它很琐碎，很小，不让人意外，大多数仓库都这么做，而且很容易撤销。再看 Lucide 图标那份：我们比较过 Hero Icons、Phosphor 和 Lucide，Lucide 的图标集最全，而且和我们已经在用的 shadcn/ui 组件匹配，所以图标用 Lucide React。这不让人意外，也很容易撤销。所以我同意问题二，这两份都太琐碎，够不上 ADR 标准。

### 问题三：被反转的决定

看问题三，这看起来是一个已经被反转的决定。我们看看 008 号 ADR 实际写了什么。它说：当请求里没有国家信息时，我们用 IP API 查。看起来这里还考虑过其他选项，而其中一个「考虑过的选项」现在成了实际做法。代码已经不再查 IP API，直接按全价收费。所以这份 ADR 过期了，需要更新。

它的建议是写一份新 ADR，并删掉 008。也就是说，通过写新 ADR 来反转旧决定。我觉得可以。问题三，对，写新 ADR，删掉原来的。值得说一句：删掉 ADR 不等于它消失了，它还在提交历史里，你需要时仍然可以回去看。

这里还有一份 0010：邮件发到服务器日志，现在被 Postmark 取代了。我们现在有一个邮件传输接口。说实话，这份也不值得写 ADR。我们看看：ADR 说退款邮件先写到服务器日志，直到我们选定邮件服务商。现在服务商显然已经选了，所以这就是单纯过期。而且它本来也不值得 ADR，我们随时可以换另一个邮件服务商，这份 ADR 又会变得无关。所以我同意问题四：不用为邮件传输写 ADR，尤其它已经被一个可复用的接口包住了。

### 落地：删掉四份，回写术语表

它说 005、006、009 都通过了 ADR 标准。这个我就先信了。问题五，我相信你的判断，听起来可以。问题六，有些术语和术语表冲突。我同意，顺手把 ADR 改成使用术语表里的词。

好，继续。它很快给出了共识总结。我觉得进展不错。开始实施。

希望这活比较快。对，现在我们有一大块改动。它其实往 `AGENTS.md` 里加了一句「所有图标都来自 Lucide React」。我不确定需不需要这个。我觉得这是 agent 自己能从代码里看出来的指令，所以我要删掉。

接下来，它删掉了四份 ADR，更新了其中几份，改成 platform admins 和 instructors，也就是用术语表里的语言，这很好。最后一份，基本上是对之前 ADR 的反转，里面有「考虑过的选项」：旧实现是在 `ipapi.com` 上查 `x-forwarded-for` 地址，它说我们以前这么做，后来放弃了。这是一份很好的 ADR。这类决定几乎不可能从代码本身看出来，因为它是一个「决定不做某事」的记录。有了它，agent 以后看这个功能时，就不会再尝试旧做法。

就这样，我们现在有一份健康的 ADR 列表，大约八到九条。如果你觉得自己的 ADR 列表失控了，你现在知道该怎么做，也知道该做哪类决定。干得好，下一集见。

> **思考一下｜被取代的 ADR 为什么是陷阱**
>
> 当前目录里的旧 ADR 会被 agent 当成有效决定。它不会自动去读提交历史，也不会猜哪份已经过期。
>
> **可以追问**：如果把旧 ADR 移到 `deprecated/` 目录，agent 是否仍会读到它，并误以为它有效？
>
> **可延展方向**：在 ADR 开头加状态和日期，让 agent 先判断状态再使用内容。

> **思考一下｜记录「决定不做」**
>
> 代码只能证明现在做了什么，无法证明过去主动放弃了什么。作者认为这类否定型决定最值得写 ADR。
>
> **可以追问**：一个被放弃的方案，要过多久才不会再被 agent 重新提出？
>
> **可延展方向**：为每个被放弃的方案写一句「为什么不用」，并附上触发重新评估的条件。

## 综合解读

论点链：ADR 堆积后，先用三条标准复检；够不上标准的删除，曾经成立但被反转的用新 ADR 记录；agent 必须核对代码，确认 ADR 是否仍然成立；最后把术语表的新词回写进 ADR。

成立前提：ADR 集中管理；agent 能读代码并逐份核对；团队接受删除旧文件，依赖提交历史保留记录；术语表已经稳定到可以反向约束 ADR。

待核验主张：008 和 0010 的「代码已经不再这样做」是 agent 的核对结论，作者在讲解中接受，但没有逐行展示验证。005、006、009 是否真的通过三条标准，作者明确说「先信了」，没有独立复核。

边界：删除和废弃各有利弊。作者选删除，依赖 git 历史；如果团队不熟悉翻历史，旧决定的可发现性会下降。作者还删掉了 agent 自行加进 `AGENTS.md` 的图标规则，说明不是所有「 agent 觉得有用」的指令都该保留。

可迁移素材：用三条标准定期复检 ADR；被取代的决定写进新 ADR 的「考虑过的选项」；否定型决定优先记录；ADR 落地时同步术语表用词。
