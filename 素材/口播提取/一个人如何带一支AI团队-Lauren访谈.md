## 口播文章

### 开场：Cursor 和 SpaceX 刚发了 Grok 4.6

节目开始，主持人介绍了两位嘉宾，Lauren Tan 和 Roshan Sadanani，都来自 Cursor。当天早些时候，Cursor 和 SpaceX 联合发布了 Grok 4.6。这期节目既聊新模型，也做 GrokBot 的现场演示。

主持人先问，GrokBot 是什么，Grok 4.6 会带来什么变化。劳伦说，团队为它投入了很久，昨天上线后反响很好，还没试过的人现在就可以注册体验。做这个产品的出发点很简单，让人更容易和 agent 打交道。它一开始只是内部项目，结果市场、运营、工程、产品各个团队都很快用上了，各自找到了适合自己工作的用法。

### GrokBot 是什么：给 agent 一台电脑

主持人追问，内部是怎么发现产品与需求对上的，有没有具体例子。

劳伦说，最早是一支很小的团队在做原型。起初只是他们自己用，后来分享给几个人，她也开始用了。她用 GrokBot 订了《奥德赛》的 IMAX 电影票，70 英寸的屏幕。主持人笑说，这算一个里程碑，一个新基准。

劳伦说，真正让她兴奋的是，agent 能自动完成很多以前想不到的事。GrokBot 有自己的电脑，即使你不在电脑前，它也能继续运行。

主持人又问内部流程：是不是同事先试各种用法，哪些开始受欢迎，再考虑做成商业产品。

罗尚接过这个问题。他说，大体就是这样。Cursor 认为同事们在用产品这件事上很有判断力，尤其是 agent 产品。所以很多产品会先在公司内部发布，收集每天用它的同事的反馈，看是否契合内部需求。这通常是能推向外部的好信号，GrokBot 也走了同样的流程。

罗尚说，GrokBot 特别的地方在于，不管什么岗位，运营、市场，还是别的角色，都能找到用法。很大一部分原因是它能无缝接入你已经在用的工具。再加上它有自己的电脑，是一个可以持续运行的 agent，这种交互体验很新鲜。

### 现场演示：一支猫咪机器人团队

主持人说铺垫够了，请两人开始演示。

劳伦先来。屏幕上是一个 GrokBot 界面，也是她的机器人团队。她说，这里有一个协调 agent，相当于她的幕僚长，知道她的日历安排，也能给其他 agent 发消息，让她了解进展。此刻，幕僚长正在联系负责购物的 Shopee〔待确认：名字拼写〕，了解她最近买了什么。劳伦举例说，比如《奥德赛》的电影票，或者日用品。这是内部发现的一个有趣用法。

她接着说，这些 agent 还有自己的电脑，能登录你用的各种工具。就在刚才，她建了一个能访问 LinkedIn 的营销 agent。点一下按钮，就能看到它自己的屏幕，已经登录了她的 LinkedIn，还通过 Chrome 读取了她的一些动态。

她让这个 agent 更新 LinkedIn，发一条正在直播聊 GrokBot 的动态。主持人提醒，别忘了标记正确的 MTS 账号，MTS Live。

劳伦说，这些 agent 很有意思的一点是，你可以像和同事聊天一样跟它说话。这也是重要的设计灵感：让你感觉自己有一位聪明的同事在聊天里一起工作，不用等轮到自己发言，也不用等它思考完。

她让 agent 去发动态，说一会儿再看进展。接着演示另一个方向：做演示文稿，或者把工作里枯燥重复的部分自动化。Cursor 内部有个频道叫 GrokBot Wins。她让幕僚长整理频道里的反馈，用 Figma Slides 做出来，方便分享。

这时 LinkedIn 动态快要发出去了。主持人看着 agent 的电脑画面，说这也太快了。他希望动态设为所有人可见，也担心账号找错。确认是 MTS Live 之后，大家松了口气。劳伦说，之后也会把这段视频发到 LinkedIn 上。

### 发布会第二天：反馈与设计

主持人问，昨天刚发布，反响怎么样。

劳伦说，反馈非常积极。大家特别喜欢 GrokBot 的形象、动画和标志，觉得很有趣。具体用法的反馈也很多，不少人说它用起来直观，界面像 iMessage。她看到有人把 GrokBot 分享给妈妈，妈妈也开始用了。当然还有很多要修的小 bug，但总体反馈很好。

主持人问，今天的模型发布加上 GrokBot，两者结合现在能做到什么。

劳伦说，Grok 4.6 非常强大。同样的 token 成本，智能水平比 4.5 高很多。她的日常工作是软件工程，经常用它写代码，能力强了很多，速度也快。她也会用 Fable 和 Sol 等模型，但 Grok 又快又便宜，所以很喜欢。

罗尚补充，发布 Grok 4.5 时，他们和 SpaceX AI 团队讨论过一个想法：训练模型不能只考虑写代码。到了 4.6，再加上对 GrokBot 的投入，这些模型让更多事情成为可能。他们期待模型继续进步，也高兴能参与前沿模型的探索。

主持人分享了自己的经历。Cursor 最初主要做 agent 编程，也是他接触 vibe coding 的入口。他用的第一个工具就是 Cursor，一直用到现在。测试 GrokBot 之前他才意识到，同一个工具也能做研究。尽管大家都在说 agent 在扩张，目前仍以编程 agent 为主。因为把 agent 用于日常事务的基础设施和体验都很糟。

他说，OpenClaw 也许是最早走向大众的。但他妈妈恐怕永远不会用 OpenClaw。他自己把 OpenClaw 配到 Telegram 里，界面看起来有点像 GrokBot，也有购物 agent。但它总是出问题，他得一直修。所以他很喜欢 GrokBot 的界面和组织方式。

主持人问，做 GrokBot 时经历了怎样的设计过程。

罗尚说，设计要求基本就是保持简单，这话有点俏皮但很实在。很多 AI 应用给用户很强的控制能力和功能，但能力有时伴随复杂度。所以首要目标是把产品做得简单，消息式界面的一部分灵感来自这里，之后才陆续加入设计细节。

劳伦补充，不敢说全是她做的，但团队确实想做一个干净简单的界面。用 Cursor 的人多半是熟练开发者或高级用户，有很多可调参数和复杂功能，整体是为编程设计的。做 GrokBot 时，他们换了个视角：如果你的 agent 更像一位同事，会是什么样。你不一定想盯着同事问，你现在究竟在调用什么工具，你更想像和人交流一样跟它说话，也想看看它在自己的电脑上做什么。所以界面要尽量简洁、优雅。

主持人说，很高兴同时请到产品和工程两个视角。幕后整个团队也做了很多工作。观众能比较全面地了解做出 GrokBot 需要什么。

> **思考一下｜把 agent 设计成同事**
>
> 消息式界面、独立屏幕、能替你去联系别的 agent，这些细节都在借「同事」的直觉。借得好，用户不用学新概念；借过头，人会把 agent 当成能担责的人。
>
> **可以追问**：同事隐喻里，哪些能力是 agent 真有的，哪些只是界面模仿出来的？
>
> **可延展方向**：把「同事」隐喻和「工具」隐喻放在一起对照，看两种设计各会自动唤起用户哪些期待。

### 谁会用它：从运营到市场，再到 Benny

主持人问，GrokBot 的用户可能与典型的 Cursor 用户不同，你们设想谁会主要使用。

罗尚说，他们觉得对所有人都有用。内部上线后的反应说明，有很多工作特别适合提高效率。最初做这个产品，是因为看到 Cursor 内部有很多人在搭自己的 agent，拼接聊天，做 Slack 机器人。劳伦就做过一个很有名的，到现在还在他们的 Slack 里。搭这些东西需要很多背景信息，于是他们想，能不能把它封装成产品。这些机器人服务过部署工程、软件工程和运营团队，他们希望用一种有趣的方式把能力产品化。

劳伦接过话，说她经常提到自己做的机器人 Benny，头像是一只小狗。最初做 Benny，是因为她挺懒的，想解决一个问题：Cursor 收到很多 bug 报告，她想把它们全修掉。于是她开始想，怎么让 agent 在她睡觉时自动修 bug。这启发了早期的一些实验，比如做一个能持续运行的机器人。

很多人问她 Benny 是怎么做的，怎么做自己的。这些也启发了 GrokBot 的构想。如果人人都能定义自己的机器人，给它身份、一台电脑，再配上例行任务和自动化流程，会怎样。她现在的机器人就是这样，每当有人给 GrokBot 提反馈，它们就自动去修，她只需要审代码。

### 我的工作变成了管理数字同事

主持人问，那你现在的工作是什么，有什么变化。

劳伦说，变得挺有意思，她几乎成了这些数字同事的管理者。更厉害的是，GrokBot 的不少功能也是它自己做出来的，形成了一个挺有意思的反馈循环。agent 能自己分诊、处理问题，也能写代码，连接云端 agent。

主持人问有没有这方面的演示。劳伦说有，正好开着。

中插赞助：Eleven Labs，让 AI 跨渠道、跨模态自然沟通。Neon 让数百万开发者和创业公司把它当后端，可以免费起步，创业公司最高可申请 10 万美元额度。Kong，AI 连接平台，连接 API、模型、agent 和系统，带安全治理。

劳伦继续演示。她刚才问了幕僚长，今天有没有发现值得处理的 bug，它找到了几个。她说，机器人的电脑上开着 X，方便查看。现在她让幕僚长把任务分派出去。这里是一支 GrokBot 团队，每个成员负责不同的功能。稍等一会儿，就能看到幕僚长给不同成员发消息，接着它们去执行任务。完成后，她会收到一个 PR，供她审核，还会有视频和截图。

她展示了另一个例子，是她工程团队里的一个 agent。这个功能不那么显而易见：如果你在 Cursor 配好了云端 agent，GrokBot 可以启动它们。这里有一个云端 agent 在自己的电脑上运行，由这个 agent 管理。现在好几项任务已经在进行，她之后会有一批 PR 要审核。

主持人说，这也让人看到未来软件开发里特别令人兴奋的一面。你和一群执行具体任务的 agent 交流、协作，然后退后一步，成为它们的管理者。这种愿景正以有趣的方式成为现实。

主持人注意到屏幕上有好多猫咪照片。劳伦说，她很喜欢猫，就给它们配了一些搞怪的头像，让 GrokBot 更有个性。默认头像也特别可爱，她加这些照片的时候，默认头像还没上线，就是图个开心。

### 工程师的角色：给 agent 修一条好走的路

主持人转向罗尚：越来越多代码由 agent 完成，人像在幕后协调这些 agent，让它们代为处理各种任务。他问，为什么对这样的未来特别兴奋，它能给人带来什么新能力，是普通观众可能还没意识到的。

罗尚说，用一个词概括就是效率。人们脑子里有很多想法，不论什么岗位。他有很多想在 Cursor 里实现的产品创意，但从想法到做出来，总有瓶颈。

他期待的是把一群 agent 投入到这些问题上，让它们交付高质量成果，同时符合自己做产品的品味和标准。这就是那个愿景，让想法真正成为现实。不管是他管理一群 agent、让 agent 去管理其他 agent，还是和劳伦的 agent 协作，形式都可以。关键是不断压缩这个周期。回头看 Cursor 的发展，很多方面都在朝这个方向走。

主持人问，软件工程团队发生了什么变化，从劳伦加入 Cursor 到现在有什么不同。

劳伦说，在她看来，agent 时代工程师的角色有点像 agent 的工程经理。但如今工程师很重要的一项责任，是把代码库维护到足够好的状态，让产品经理、设计师都能贡献高质量代码。这也是她在推特上常谈的：投入精力做重构、改写，甚至重写代码库，让 agent 能发挥得更好，即使它们有时并不特别聪明。比如把规则和代码风格规范写成真正的 lint 规则或硬性约束，违反了就让 CI 检查失败。

她认为，其中很重要的突破是，作为工程师，她能帮助很多人做到以前做不到的事，自己也能做到以前做不到的事。她在 Cursor 做过很多大型重构和迁移，基本都是自己做的，或者再加一位同事。那些猫咪 agent 忙得不亦乐乎，她改造了很多东西。要是让她自己或者一个工程团队来做，可能要花几个月甚至几年。

主持人说，从外部看，大家可能会想，既然 agent 都能写这些代码，软件工程师的作用是什么。但看实际情况，对这类工程师的需求反而比以往更大。现在做软件，从想到执行的时间被大幅压缩。于是能看到 GrokBot 这样的产品。一开始只是内部做的东西，后来又能用 GrokBot 开发 GrokBot，并投入商业化生产。你们也看到这种趋势越来越多吗。

罗尚说，做原型所需的时间缩短了很多，测试想法特别快。GrokBot 背后的团队能推进得这么快，就是因为这些工具越来越好，模型进步也是重要因素。回到 GrokBot 的出发点，就是怎样让产品越来越有帮助。从趋势看，这些事情会越来越容易。但整个过程中，人仍有很重要的作用，不论是产品判断力，还是其他因素的组合。创意到处都是，看到越来越多想法成为现实，会很令人兴奋。

> **思考一下｜代码库也是给 agent 的接口**
>
> 这段把工程师的工作拆成两半：管理 agent，和维护一个 agent 好走路的代码库。后一半常被忽略，却决定了 agent 能发挥多少。
>
> **可以追问**：你们的 lint 规则里，有多少条是为 agent 写的，有多少条是为人写的？
>
> **可延展方向**：把「为 agent 优化仓库」当成一项工程指标，比如首次提交成功率、CI 反馈时长、规则命中率。

### 米其林厨房：主厨只管两件事

劳伦说，她个人特别喜欢一个类比。她喜欢美食，是个十足的吃货，会把自己的 agent 想象成一个厨房，她称之为米其林厨房。

她的角色变了，不再所有菜都亲自做。现在有一支雇来的机器人和 agent 团队。她通过技能配置、代码重构等方式训练它们，让它们按自己的标准写出好代码。她的角色越来越像主厨，可能负责摆盘，也负责质量把关。

她说，如果你愿意投入精力，打造一支真正能干的 agent 团队，就能完成多得多的工作。再想象一下，团队里每位工程师身后都有这样一支团队，你就能解决更多问题，开发更多功能。当然，并不是每个功能都应该做，但生产力和推进速度确实会大幅提高。

> **思考一下｜品味怎么传下去**
>
> 主厨不炒每一道菜，但每一道菜的标准由他定。标准靠技能配置和重构写进系统，口头交代不够。
>
> **可以追问**：你把标准写成规则以后，怎么发现规则本身过时了？
>
> **可延展方向**：比较厨房的出品标准、设计系统的组件约束、代码库的 lint 规则，看三者怎么把品味固化成别人能执行的东西。

### 下一个功能：给 agent 发短信

主持人说，他很喜欢 Cursor 的内部文化。先把东西做出来，自己测试。员工对工程师、产品人乃至普通用户的需求有一定判断。他问，能不能透露一点接下来会有什么，不方便说也没关系。

罗尚说，他们肯定想继续把 GrokBot 做好。昨天刚发布 beta，收到了大量各种各样的反馈，目标就是让这些助手、机器人尽可能对用户有帮助，所以一定会继续投入。他们也很期待模型变得更好，很高兴能参与其中。总的来说，他们很看好未来，无论编程还是通用 agent 都很有前景。

劳伦说，她个人很期待性能和可靠性进一步提升，作为工程师这是她特别关心的。他们也在讨论一些有意思的功能。比如早期她曾试着在 GrokBot 里加上 iMessage 支持，这样你就可以给机器人发短信。她不知道最后会不会加这个功能，但很多人确实提过这个需求。

她说，核心想法仍是，这些 agent 就像同事。联系同事不一定只能通过 Slack，你还可以发短信、打电话。想象一下，有这样一些随时在线的同事，随时随地都能联系，而且一直为你工作。

主持人说等不及给他们发短信、打电话了。他提到一个梗图：一群 agent 开站会，一个说抱歉，我整个周末都休假了，另一个说可你是 agent 啊。劳伦说，也许 agent 也需要带薪休假和娱乐时间。主持人接话说，带薪休假就是把电脑关掉。

### 70.8% 和 17.32 美元

主持人说，最后还有一点很想聊，因为确实惊人。两位不只是在做 GrokBot，不只做应用层，也在做模型层。Grok 4.6 在 CursorBench 3.2 上的测试结果已经公布，很亮眼。趁还有时间，他想在节目里聊聊。

他说，Grok 4.6 Extra High 得分 70.8%，每项任务平均成本 2.81 美元。作为对比，Fable 5 Max 得分 70.5%，但成本是 17.32 美元。这个变化非常大。他想知道，这会怎样改变普通用户与 agent、与整个 AI 的互动方式。

罗尚说，这确实是他最近常想的问题。因为他在 Cursor 工作，有不限量的 token 可以尽情使用，但很多客户和用户对成本会更敏感。所以他最期待的是有一个非常高效的模型，能力与其他大模型相当，成本却只需要其中一小部分。他觉得这是很多管理者和工程师目前正在讨论的重要话题：使用 AI 的成本不断上升。在这场讨论中，Grok 4.6 是很值得考虑的选择。

他说，每家公司都会根据自己的情况，对采用怎样的模型组合提出不同要求。如果你正在比较那些能力很强的大模型，又希望成本再低一些，Grok 4.6 是一个很好的选择。比如你有 20 美元预算，用来完成所有 AI 任务，每项任务的成本下降后，你就能做更多任务。提升效率很有意思，因为这意味着你能用更多机器人、写更多代码、完成更多事情。整个行业都在朝这个方向发展。

劳伦说，他们在效率上投入了很多，认为这是模型值得发展的方向。当然，智能水平也很重要，所以他们对这些成果很兴奋，基准测试的表现也很好。她尤其期待这样一个出色的模型能把成本降下来。这会让资源没那么充足的创业公司，甚至想尝试新想法的独立开发者，也能获得更强的能力。毕竟 token 费用全靠自己掏腰包，已经有点吃不消了。所以这确实开始让大家站到更公平的起点。

## 综合解读

这场访谈的论点链是这样。agent 产品缺的常常是入口，能力倒在其次。GrokBot 用「同事」这个隐喻解决入口，给它消息界面、自己的电脑、身份和例行任务，你像找同事一样找它。入口打开后，瓶颈回到两处：模型成本和代码库质量。成本靠模型效率往下压，质量靠工程师做重构、把规范写成 lint 和 CI。最后人的位置变成主厨，定标准、做质检、决定哪些功能不该做。整场访谈反复出现的一个词是效率。撑起效率的却是三件不显眼的事：内部同事先试出来的品味，为 agent 改过的代码库，以及能自动执行的规则。

这套说法成立有几个前提。模型要可靠到能自己改代码、自己开 PR。工具生态要允许 agent 登录你常用的软件，比如 LinkedIn 和 Chrome。公司内部要有一批高品味的同事，愿意先试、给得出反馈。成本要下降到公司敢放开 token 用。工程侧还要有现成的 CI 和 lint 基础，规则才落得下去。缺一条，收益都会打折。

片中数字都来自节目陈述，未经独立核验。CursorBench 3.2 上，Grok 4.6 Extra High 得 70.8%，每项任务 2.81 美元。Fable 5 Max 得 70.5%，每项 17.32 美元。GrokBot 发布第二天就收到大量反馈。GrokBot 的不少功能由 GrokBot 自己做出来。

另有一处归属要外部核对。这支访谈里两位嘉宾都说自己来自 Cursor。另一支关于 pstack 的视频却说劳伦在 SpaceX 的 AI 团队做 GrokBot〔待确认〕。罗尚提到的「不限量 token」是 Cursor 员工的内部待遇，不代表外部客户。

还有几处边界。演示是提前排好的，LinkedIn 发帖、分派任务这些环节顺利，不代表每个用户的场景都顺。拟人化有代价。同事能担责，agent 不能，出事时责任仍在人身上。「米其林厨房」依赖主厨有时间尝菜，管理者如果被会议排满，质检会先退化。成本对比是单一基准上的单点结果，不能直接外推到全部工作类型。

可迁移的做法有五个。产品先在内部试出真实用法，再决定是否商业化。把 agent 的交互做成同事的三件套：身份、电脑、消息。把团队规范写进 lint 和 CI，让 agent 撞上硬约束，少靠人提醒。先重构代码库，再谈 agent 提效。最后是抽样质检，像主厨尝菜一样，不求全尝，但要知道尝什么。
