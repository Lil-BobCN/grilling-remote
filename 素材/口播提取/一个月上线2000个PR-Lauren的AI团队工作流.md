## 口播文章

### 2000 个 PR，靠的是信任

上个月，我把 2000 个 PR 上线到生产环境。能做到这一点，很大程度上靠信任。我经常想，怎样信任 agent，让它们在我看不到的时候也产出高质量的工作。

今天的论点是：把 agent 的环境搭好，你就能得到一座个人或团队的软件工厂，产出质量更高、速度更快。

我不喜欢「软件工厂」这个词，更喜欢「米其林厨房」的比喻。技术人员不是在流水线上批量生产标准品，产品里有创造性。即使有了 agent，我们不必亲手做每一项工作，也仍然要对最终结果负责。

还要想厨房怎么布置：主厨、助理、设备、培训、洗碗工，以及厨师和洗碗工的比例。这些都会影响最终的产品。

### 从 Cursor 的性能问题开始

六个月前我刚加入 Cursor，当时它还没成为 SpaceX AI 的一部分，也没有现成的 agent skills。我面对的是全新的代码库和产品。

Cursor 当时在做 Cursor IDE 的替代品，也就是新的 agent window。这个窗口有不少性能问题。经理问我能不能帮忙，因为我在 React 团队待过，看起来合适。

开始后我发现，整个过程特别依赖人工。PR 合入的速度太快，像一堵不断堆高的墙。我不知道应用性能会不会又退化。很长一段时间，我在 Chrome DevTools 里手动分析性能、采 trace、抓堆内存快照。繁琐到让我问自己：都有 agent 了，我还在忙什么？

于是我想，验证技能能不能让 agent 自己运行应用、采集并理解 trace、找到性能热点、反复迭代，让性能自动变好。

### 我不是奔着 2000 个 PR 去的

过去六个月，我的产出大幅提升。但我从没设定「每月 2000 个 PR」这个目标。

后来我意识到，我做的技能、工具和代码库改造，都指向「信任」。当时没想清楚，但心里一直有个念头：我是瓶颈。我得把作为工程师积累的知识传给 agent 团队，这样我不用成为每件事都必须经过的关卡。

### 信任阶梯：从 1 到 5，再到 100

关键在信任。不管你在哪个阶段，都可以问：从哪里开始？

我起步时同时用 1 到 5 个 agent，每个对话都要盯着。不停纠正方向，一次次介入，告诉它该怎么做。你一不在，事情就推不动，或者它做错。我认为这是最难走出的阶段，因为你常常不知道该怎么突破。

归根结底还是信任。你没法从 1 到 5 个 agent 扩到 100 个，因为你不信任它们的工作。强行启动 100 个子 agent 或云端 agent，很快会收到一堆低质量 PR、性能退化和被发布出去的缺陷。

### 验证有两端

怎样更信任 agent？对我来说，一切始于做性能优化时意识到验证的重要。

验证有层次。基础的一端是验证技能。教 agent 运行应用，用 Chrome DevTools 协议或其他调试协议，教它调试、采性能数据、抓堆内存快照。

另一端难得多，至今仍是开放问题：形式化验证。用形式化方法，或者 Lean、TLA+ 这样的语言，检查业务逻辑里必须始终成立的条件，从形式上证明应用一直处于正确状态。

即使做不到形式化验证，绝大多数人也做不到，仅靠验证技能已经能走很远。

### Control Glass：CLI 加功能地图

我加入 Cursor 后，为 agent window 做的第一个技能叫 Control Glass。它是一个验证技能，教 agent 运行应用、采 trace，底层用 Chrome DevTools 协议。

这个技能是逐步迭代出来的，一开始不是这样。控制和验证技能有两个部分。

第一部分是命令行工具。让 agent 能以可重复的方式运行应用、收集 trace 和证据，用实测数据证明代码能工作、性能达标。不要让 agent 每次都临时写脚本，不同会话写出来的脚本可能不一样。把命令行工具放进技能目录，每次都用同一套，再花时间打磨，让它能处理各种场景，把应用正确跑起来。

第二部分是功能地图。这个词是我起的，灵感有点像网站地图。我们在 Cursor 内部用控制技能后，很快发现有人在 Slack 报问题。截图很含糊，只截界面里很小一块，再加三个问号。agent 有控制技能也不明白，它能运行应用，却只能猜用户指什么。

所以我想做一份功能地图。它本质上是落到文件里的记忆。应用怎么工作，有哪些功能，用户怎么找到这些功能，比如按什么快捷键、点哪些 DOM 元素。功能地图放在技能目录里，随代码库保存，我们还用自动化任务持续维护它。

命令行工具加功能地图，这个组合很强。agent 既能稳定控制应用、采 trace，又能理解内部和外部用户发来的请求。我们很快意识到，这些控制和验证技能几乎成了团队的基础设施，会持续维护。agent 能验证自己的工作，这一点非常强大，对建立信任特别有效。

> **思考一下｜验证不是一个动作**
>
> Control Glass 的价值在两部分：可重复的 CLI，和说明应用怎么工作的功能地图。前者给证据，后者给上下文。
>
> **可以追问**：你们的验证脚本，是每个会话重写，还是固化成一套工具？
>
> **可延展方向**：把功能地图当成活文档，跟 UI 改动一起维护，让它成为 agent 找路的地图。

### 正确性之外，还有工程质量

验证主要关注正确性。正确性是这个功能或这段代码能不能实现你想要的行为，比如结账按钮是不是真能完成结算。验证能提供实测证据，证明功能可用。但它说明不了性能和代码质量。

这就需要另一类技能，教 agent 像真正的软件工程师一样工作。我做了一个插件叫 pstack，今天不细讲。里面很多技能来自我自己做工程师时的工作流：调试、功能开发、原型、验证。pstack 提供操作指南和技能，教 agent 按你期望的方式写代码。

在这方面，团队里更有经验的工程师能发挥很大作用。建立一个团队共用的技能仓库，让 agent 更聪明。把技能和验证结合，agent 不仅能确认工作正确，还能保证质量。借助验证，你能拿到真实的性能指标、数字、统计和遥测。

### 重构代码库，为 agent 设计

另一件重要的事是重构，甚至重写架构，让它更适合 agent。我几乎想说，这是软件工程团队最值得做的事之一。如果你真的相信未来代码都由 agent 写，就应该把代码库设计成让它们默认做对。

### 五层约束

建立信任的手段像一个层级，或一条连续的谱系。我列了五个点。

最底层是代码库。代码库是 agent 最好的记忆载体，因为 agent 喜欢沿用看到的模式。这是大语言模型的工作方式：它更可能用上下文窗口里已有的东西来改代码。agent 打开和读取的文件会进入上下文，所以代码库非常重要。agent 不会每个 PR 都重构一遍，它看现有实现，然后照着扩展。

下一层是静态分析：linter、编译器诊断、持续集成。这些是能在代码库里强制执行的规范和约束。当你纠正 agent，发现它总犯同样的错，可以写成 lint 规则。更好的做法是重构代码库，让这类错误从根本上不可能发生。

再往上一层，从硬约束转向指导：规则、Bugbot、技能。agent 工作时会用到它们，但也可能忘了读某条规则，或者操作 agent 的人忽略了规则。它们没那么容易强制执行，但同样是可信环境的一部分。

最后是风格指南，主要靠人在代码 review 里落实。也可以写进规则、Bugbot 和技能；如果不写，评审流程就留下一个大洞。人得逐行看改动，还得记得提意见。面对不断涌入的 PR，这根本做不到。

所以我不建议只依赖风格指南。从风格指南和人工 review 记录入手，看缺了哪些约束，是个不错的起点。但应该认真投入另外四个部分：代码库，用更好的数据结构或算法让某类错误不可能；静态分析；再叠加规则、Bugbot 和技能。

> **思考一下｜约束的分层**
>
> 这段把「纠正 agent」拆成五层，从代码库到人审，越往下越依赖人记得住。顺序反过来用，通常先累死人。
>
> **可以追问**：你们最近一次重复纠正，落在哪一层？能不能往上挪一层？
>
> **可延展方向**：把团队常犯的错列出来，逐条标上「结构能挡」「lint 能挡」「只能靠规则」「只能靠人」。

### Dune：让正确的路成为捷径

在 GrokBot 的代码库里，我们搭了一个叫 Dune 的东西，一个面向 agent 的框架。灵感来自 Cursor agent window 里的大量性能问题，那些教训最终汇成一条原则：agent 喜欢走捷径。那能不能把框架设计成，最容易走的路恰好就是正确的路？

这样的代码库对人类来说可能挺烦，因为能做什么、不能做什么限制得很死。但它对 agent 是理想环境，尤其是上下文很少的 agent。以后参与代码库的人不一定都是工程师，也可能是设计师、产品经理，甚至 CEO。所以要认真想，怎么投入和组织代码库，让那些由忙碌、缺乏背景的人操作的 agent 也能默认把工作做好。

反过来说，如果代码库里已经有反模式，它们会像病毒一样传播。一个小变通，或者一条解释变通做法的注释，agent 特别喜欢照抄。过几天或几周，这种做法就扩散到各处，变成事实上的标准模式，被所有 agent 沿用。

这很糟。每次纠正 agent，都应该花时间想，怎样改代码库、加静态分析、叠加规则和 Bugbot 配置、补技能。

### 代码库是花园

除了米其林厨房，我还喜欢一个比喻：代码库像一座花园。有些临时变通一开始看起来无伤大雅，但 agent 会反复复制。一旦有了这种模式，它就会一遍遍复制，很快你得到一个随意拼凑、维护痛苦、性能问题很多的代码库。

理想的 agent 代码库应该限制足够严，严到人在里面写代码会觉得烦。但它又非常统一、非常标准化，让那些看似无害的坏模式没有立足之地。

最好的例子乍看无害、细想很糟：agent 在代码里留下的注释。刚看到时，我没觉得多坏。里面很多是废话，但人类也写注释：遇到边界情况临时绕过，或者给同事留个提醒，解释一段难懂的代码。

但在 Cursor 的代码库里，我们很快发现，agent 把代码周围的注释当成借口。它解释为什么不去解决真正的问题，只在表面贴一块创可贴，用短期补丁把问题盖住。

所以在 Dune 里，也就是支撑 GrokBot 的框架里，我们干脆禁止了代码注释。原因就是这些：不让 agent 照抄这种模式，再把它传播到整个代码库。

### 园丁和技术债

每个团队都需要一个角色，我叫它园丁。真正的花园需要有人留意那些悄悄长出来、朝你不希望的方向蔓延的东西，比如杂草、害虫。代码库里也会悄悄混进不想要的东西，得尽早消灭在萌芽阶段，别让它到处传播。

Dune 的很多原则围绕三件事。

第一，清理已有的技术债，原因刚才说了。

第二，为大多数推荐模式保留并强制执行一条统一的实现路径。某件事就该有一种约定俗成的做法，让 agent 不用猜。代码库、CI 和 lint 里都要有足够的约束和指引，引导 agent 沿着这条路走。

第三，一旦看到技术债或坏模式，第一反应应该是写一条 lint 规则把它拦下来。不一定非得立刻清理完。有了规则至少能先止住，虽然没彻底解决，但能阻止问题扩大。

所以，认真想怎么防止反模式像病毒一样传播。同时花时间让 agent 清理这些问题，把代码库维持在一种你乐于看到下一个 agent 照着写的状态。

> **思考一下｜反模式的传播速度**
>
> 一个临时补丁，加上一条解释它的注释，就够让下一个 agent 学会这套做法。坏模式不是被教出来的，是被抄出来的。
>
> **可以追问**：你们的代码库里，哪条注释其实在替一个没解决的 bug 找理由？
>
> **可延展方向**：定期搜「临时」「先这样」「TODO 之后修」，把每一条当成一次规则候选。

### Dune 长什么样

不细讲 Dune，只快速看几个有意思的部分。Dune 是我们为 GrokBot 构建的架构和客户端框架。我们在刚才说的那些方面投入很多，建立了大量约定：代码放在哪里，不同部分之间怎么 import。

在 Dune 应用里，一个功能的代码放在同一个文件夹。React 部分有一个入口，可以理解成路由。还有 GrokBot 应用里显示的会话卡片，以及运行在 GrokBot 虚拟机上的宿主端。再加上客户端，共同支撑整个 Dune 应用。

我们在这些部分之间设了严格的边界。举个例子，应该跑在主进程或 Electron 主线程上的逻辑，不允许跑到渲染线程。这是我们刻意保留的隔离，来自 Cursor agent window 的教训。以前有时会看到代码被误导入渲染线程，而且还是很慢的代码。

渲染线程要保证界面流畅。想达到每秒 60 帧，就不能有超过 16 毫秒的任务；想达到 120 帧，要控制在 8 毫秒以内。所以渲染端必须把工作拆成小块，不能一次做完。Dune 里有相应的代码，通过 import 依赖图强制落实这些边界。

这只是一个例子。某种模式曾导致严重的性能问题，我们通过 Dune 的架构设计从根本上消除了它。

### 把团队的经验写进框架

重点不在 Dune 本身。为自己构建一个面向 agent 的框架，才是更有价值的事。它可以把你和团队里优秀工程师口耳相传、没写下来的经验固化下来。

启发是：怎样把过去依赖风格指南、代码 review、工程师互相留言的流程，转化为提炼知识，再写进框架和代码库本身。这样代码库就充当记忆。代码库是你希望保持的状态的一份具体快照。你希望 agent 继续扩展它，所以要把它保持得足够整洁、足够优秀，让下一个 agent 大概率沿用这些模式。

只要在这个过程中投入足够多时间，就能搭出一间米其林厨房，或者说软件工厂。你已经认真建设了那些能让你信任 agent 的基础：代码库、lint 规则、诊断、规则、Bugbot、技能。这些层次结合起来，会带来很强的信任感。

想象一下，你正在 GrokBot 代码库里工作，约束非常严格，几乎很难写出坏代码。那么即使 agent 上下文很少，甚至没做多少推理，也能写出不错的代码。

### 外部循环：GrokBot 加 Cursor

回到米其林厨房，要做的事很多：给 agent 和机器人配技能、工具，训练它们，合理布置厨房，让它们默认就能把事情做对。

厨房里如果某位厨师或洗碗工总被某个东西绊倒，当然要解决，还得确保别人不会再被绊倒。代码库也该这样想：怎样组织它，让知识和背景都不多的 agent 依然把工作做好。

在这方面，GrokBot 和 Cursor 可以形成很有意思的配合。GrokBot 很擅长提供所谓的外部循环。你可以把它连接到各种服务，比如 Slack、Datadog、Sentry、PlanetScale，或者你常用的其他服务。它可以汇总这些信息，据此做出更好的决定。

有些人把这叫公司大脑。我觉得未必需要那么复杂。agent 很擅长使用工具。把工具接进 GrokBot，再让它自动启动云端 agent 之类的任务。你会发现，不用投入很多额外基础设施，就能搭起软件工厂。

不过我要把「软件工厂」这个词划掉，我不太喜欢它。你可以通过 GrokBot 和 GrokBot Routines 这样的机制，搭自己的米其林厨房。它能订阅 Slack 讨论串、Sentry 告警，自动启动相关任务。前面说的代码库和规则，效果会不断叠加。

GrokBot 能自动响应外部循环的事件，启动云端 agent。你还可以设置 Cursor 自动化任务，用 SDK 搭更多机器人，复用已有的 agent 基础设施，完成复杂得多的任务。

如果这些都做好，就能达到这样的状态。自动化任务和 agent 参与 Cursor 开发，自动复现缺陷报告，自动创建 PR。这些能力叠加，为整个团队带来很大价值。

### 总结：每次纠正，都改环境

退后一步，回到这张图。如果你认真建设好这些环节，就能沿着信任曲线往上走。你会越来越信任 agent，也能让更多工作并行推进。让整个团队在这些 agent 基础设施之上继续构建，帮助每位工程师、每位创造者高效写出高质量代码。

最后想留给大家的是这一页。如果这场分享只能记住一件事，就记住这张幻灯片。每次发现自己需要纠正、干预 agent 时，都从这五个方面想：在这个顺序里，哪一步最能让 agent 变得更可靠？

我非常建议按这个顺序考虑。先投入时间，通过代码库、架构和数据结构，让坏模式根本无法出现。然后再考虑静态分析。最后叠加规则、Bugbot 和技能。如果这些都做好，再花时间通过技能提升代码质量，你就会越来越信任这个环境，让 agent 自由发挥。

我个人在这方面投入了很多时间，比如 GrokBot 的代码库。这就是秘诀。其实也没什么秘密，就是大量扎实的工作。

## 综合解读

这场分享的论证是一条因果链。人不敢放手，是因为不信任 agent 的工作。不信任，是因为 agent 既证明不了自己做对了，也证明不了做得够好。验证技能补第一件事，工程质量技能补第二件事。两件事都补上，人才敢把任务并行出去。并行之后，错误会重复出现，于是要把经验写进代码库、lint、规则和技能，让下一次不容易错。规模再往上，就把外部事件接进来，让 GrokBot 自动触发云端 agent。

和已有的口播素材比，这份讲得更系统。S3 播客里她讲过验证、米其林厨房、内外循环。这支视频把验证拆成 Control Glass 的 CLI 和功能地图。它还把环境拆成五层，把「代码库是记忆」讲成一整套 Dune 的设计取舍。

新增的细节有四个。功能地图的来历、Dune 的模块边界、16 毫秒和 8 毫秒的渲染预算、Sentry 和 Datadog 的连接器。

数字上有一处口径差异。这支视频说上个月 2000 个 PR，B 站简介也注明原帖写 2500、视频口述写 2000。S1、S2 用的是 2500。两边都以「上个月」或「8 月」为时间点，无法判断是统计口径不同，还是月份不同。这个冲突保留在 wiki 的待确认页，不合并成一个数。

成立前提有四个。领域要可验证，软件比多数领域好验证。代码库要由团队自己掌控，能改架构、加 lint。团队要愿意接受严格约束，Dune 这种设计对人类并不友好。还要有人持续维护验证技能和功能地图，否则它们会过期。

边界也清楚。形式化验证她只作为方向提了一句，真正能做到的人很少。风格指南和人工 review 仍然是最后一层，只是不该当第一层。禁止注释有代价，人类也失去了写解释的地方，换来的是 agent 不能拿注释当借口。这些取舍都建立在她的团队规模和代码库形态上。

可迁移的素材有四个。验证技能拆成 CLI 加功能地图。用五层清单审计自己的代码库，看重复纠正落在哪一层。把「每次纠正都改环境」当成习惯，而不是修完就算。给反模式设一个园丁角色，先写规则拦住，再安排清理。
