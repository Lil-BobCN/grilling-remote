## 结果（2026-11-25）

模拟和边界演练都通过，运营者 2026-11-24 和 2026-11-25 两次确认。

- 四条路径通过：补缺口确认、补缺口驳回、拆票驳回、拆票确认。每次写回前 bot 复述并等确认，写回都发生在确认之后。
- 四类边界通过：两个父工单并发不串 chat；重复叫醒不重复写评论或建票；Orca 重启后 bot 从 GitHub 读回状态；bot 叫不醒时企业微信和邮件照常送达，控制台能完成写回。
- 和最初方案的区别：不做「每个待办一个 Orca 交互终端」。一个 bot；每个父工单的补缺口和拆票各一个 chat；通知走 `orca_bot` 通道；提案仍由 Agent 写，点头和驳回由 bot 代运营者写。

## 为什么分开

- 修复批次的目标是让第 5 次全链跑通。载体是入口改造，风险大，混进去会拖慢修复。
- 第 5 次测试会暴露人工点到底卡在哪：找不到入口、看不懂题、还是写回太麻烦。先有现场，再定形态。

## 载体怎么做（最初方案，未采用）

这一段是 2026-11-24 的备选，后来没有采用。实际做法见上面的「结果」和中台 I-0239 里的 spec。

1. 每个待办一个 Orca 终端。`console list` 列出待办，`console open` 在 Orca 里起一个终端。
2. 终端里跑交互式 agent，不是现在的一次性 `console show`。brief 带：父工单链接、提案原文、题目和推荐、客户仓路径、允许的写回命令。
3. 运营者用自然语言和它说话：追问、补上下文、说「按推荐答第 1、3 题」。agent 回答，确认后调现有 CLI 写回（`gap.mjs point`、`tickets.mjs create`、`gate.mjs answer`），再写 `点头：` 评论。
4. 留痕：GitHub 评论是正式记录，终端是对话。agent 结束前往父工单写一条摘要，写清答了什么、写了哪条评论。
5. 调度器不用改：它还是读 `点头：` 评论推进。

## 消息怎么传

（这一段按终端方案写，未采用。实际是 bot 在 chat 里讲，运营者确认后 bot 用现有 CLI 写回；正式记录仍是父工单评论。）

- 运营者到 agent：在 Orca 终端里打字。
- agent 到运营者：终端输出；要写回时先说「我准备写这条」，运营者确认再写。
- agent 到工厂：现有的 gap、tickets、gate 命令和父工单评论。
- 工厂到运营者：现有通知，带父工单链接和控制台命令；点开后是同一个终端入口。

## 验收

（按终端方案写，未采用。实际验收看上面的「结果」和 I-0264、I-0265 的记录。）

- 从一条通知点开，只在一个 Orca 终端里看题、追问、回答、确认，父工单出现 `点头：` 评论。

- 终端关掉后，父工单的摘要评论能还原这次谈了什么。
