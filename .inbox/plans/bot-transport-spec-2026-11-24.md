# Spec：工作台 bot 传递人工点消息

> 状态：已拆票，待模拟
> 日期：2026-11-24
> 来源：2026-11-24 运营者和 agent 的讨论；上一个 agent 的 `orca_bot` 通道方案

## Problem Statement

运营者不在 Mac 前时，工厂的人工点走不通。补缺口 Agent 和拆票 Agent 把提案写在父工单，通知只推到手机；手机只能看提醒，不能答题，也不能点头。运营者要回到 Mac，打开 Orca 控制台或 GitHub 评论，才能把决定写回。补缺口和拆票各要一次人工点头，手机上看得到、动不了。

## Solution

用本机 ADE（Orca）的工作台 bot「莹宝（AFK）」做消息传递。调度器或 notifier 在提案出现时叫醒 bot；bot 读父工单的最新关口评论，把题目、推荐、出处或票单讲给运营者；运营者在 chat 里答题、追问、提修改；bot 复述并确认后，用现有 CLI 写 `点头：` 或 `驳回：`；调度器继续按评论推进。

驳回后，调度器重跑对应的 Agent。新 Agent 的 brief 带上驳回理由，读已有的地图、决定票、提案和回传件，更新已有内容，不重建。运营者在新提案出来后再次确认。

一个 bot；每个父工单的补缺口和拆票各一个 chat；通知走 notifier 的 `orca_bot` 通道；微信、邮件和控制台保留作兜底。补缺口和拆票 Agent 的判断不变，关口格式不变，三个人工点不变。

## User Stories

1. 作为运营者，我想在补缺口提案写好时收到手机消息，以便不用打开 Mac 就能答题。
2. 作为运营者，我想让 bot 逐题给出题目、推荐答案和出处，以便判断推荐是否合适。
3. 作为运营者，我想在 chat 里追问「为什么推荐这个」，以便看懂依据再答。
4. 作为运营者，我想让 bot 在写回前复述我的答案，以便发现听错或答错。
5. 作为运营者，我想在写 `点头：补缺口` 前看到「写完就锁单，要改先写改口：重传」的提醒，以便知道这一下的后果。
6. 作为运营者，我想对某道题提异议，让 bot 写 `驳回：补缺口 <理由>`，以便补缺口 Agent 按我的理由重列。
7. 作为运营者，我想让驳回后的新 Agent 更新已有的地图和决定票，不建第二套，以便记录不乱。
8. 作为运营者，我想在新提案出来后再次收到消息，以便看改得对不对。
9. 作为运营者，我想在确认答案后让 bot 写 `点头：补缺口`，正文带最终答案和正文影响，以便父工单留下完整记录。
10. 作为运营者，我想让调度器在点头后自动跑 to-spec，以便不用手动跑。
11. 作为运营者，我想在拆票提案写好时收到手机消息，以便在手机上审票单。
12. 作为运营者，我想让 bot 给出接缝、每张票的标题、垂直切片、验收条件和阻塞边，以便判断拆得合不合理。
13. 作为运营者，我想对票单提修改，让 bot 写 `驳回：拆票 <理由>`，以便拆票 Agent 按我的建议重拆。
14. 作为运营者，我想让重拆只改票，不改 spec，以便三个人工点不变。
15. 作为运营者，我想在点头后让 bot 建票并写 `点头：拆票`，以便调度器开始点火。
16. 作为运营者，我想在手机上完成补缺口和拆票两次点头，以便离开 Mac 也能推进。
17. 作为运营者，我想让 bot 也处理 `需要你答`、`出事`、`needs-info` 和部署结果，以便只盯一个窗口。
18. 作为运营者，我想让 bot 在补缺口阶段列出地图上 `Not yet specified` 的项和开放决定票，以便知道地图还差什么。
19. 作为运营者，我想让 bot 只讲不决定，以便它不会替我做选择。
20. 作为运营者，我想让 bot 只认我在 chat 里的明确确认，以便别的 agent 或调度器的消息不能触发写回。
21. 作为运营者，我想让调度器在人工点出现时叫醒 bot，而不是让 bot 自己巡检，以便不耗巡检次数。
22. 作为运营者，我想在 bot 叫不醒或掉线时仍收到微信或邮件，并能回到控制台，以便工厂不被载体卡住。
23. 作为运营者，我想让同一条待办重复叫醒时不重复写评论或建票，以便重试安全。
24. 作为运营者，我想让两个父工单各有自己的 chat，以便上下文不混。
25. 作为运营者，我想让 bot 在 Orca 重启后从 GitHub 读回状态，以便 chat 不是唯一记录。
26. 作为工厂，我想让 bot 用现有 CLI 和关口格式写回，以便调度器和记录不用改。
27. 作为工厂，我想让 bot 只碰当前父工单和当前客户仓，以便错误不波及别的客户。
28. 作为运营者，我想让 bot 的 SOUL 写清角色边界，以便我能审查它的行为。
29. 作为运营者，我想在第五次演练前做一次小量模拟，以便确认 bot 传递能用。
30. 作为运营者，我想在模拟通过后再改文档、决定和票，以便项目记录和实际流程一致。

## Implementation Decisions

### 载体

- 用一个 bot，沿用「莹宝（AFK）」。SOUL 从「工作台」改成「消息传递」：只读提案、讲给运营者、按确认写回。
- bot 不建图、不跑 to-tickets、不改代码、不改标签、不关票、不动中台和调度器。
- bot 只处理当前父工单和当前客户仓；不读别的客户，不碰生产。
- bot 以运营者身份写 GitHub；不另建账号。评论作者仍是运营者。
- SOUL 的正式副本放在 bot 目录，仓库里放一份只读副本供审查。

### 消息范围

- bot 处理这些消息：`提案：补缺口`、`提案：拆票`、`需要你答`、`出事`、`needs-info`、部署结果。
- bot 只讲，不决定。遇到 `出事`，它讲清试过什么、卡在哪，等运营者说继续、换法或停。
- 补地图仍由运营者做。bot 只列 `Not yet specified` 和开放决定票，检查地图是否补完；建票、关票、改地图不归它。

### 唤醒和路由

- notifier 增加 `orca_bot` 通道。配置有 `enabled` 和 `bot`；事件模板给上面几类消息加这一路。
- 通道发 `orca orchestration send --to bot:<名字> --type handoff`，subject 写角色和父工单，body 写父工单链接、提案评论链接和一句要做什么。
- 每个父工单的补缺口和拆票各一个 chat，标题固定，例如 `补缺口 owner/repo#123`、`拆票 owner/repo#123`。通道先按标题找 chat，找不到就开新的。
- bot 不自己巡检，不用 Orca 的 GitHub 自动化。Orca 的 `github.comment` 不触发运营者自己的评论，工厂的提案正是运营者 token 写的。
- 叫醒失败时 notifier 重试；仍失败走微信或邮件。调度器照常按 GitHub 状态走，不等 bot。
- 24 小时提醒照旧；提醒再叫醒 bot，bot 重读 GitHub，不靠 chat 记忆。

### 读和讲

- bot 读父工单最新关口评论、父工单正文、地图、决定票、回传件、spec。
- 补缺口：逐题讲题目、推荐答案、出处；最后讲闸门检查和地图剩余项。
- 拆票：讲接缝、每张票的标题、垂直切片、验收条件、阻塞边。
- 追问先读现有材料回答；答不了就说「这题要重跑 Agent」，不猜。
- 数据缺、评论对不上、父工单和地图冲突时停下报运营者，不自己挑。

### 写回

- 补缺口点头：普通单用 `gap.mjs point`，小需求用 `gap.mjs point-small`。命令写 `点头：补缺口`，正文带最终答案和正文影响。
- 拆票点头：`tickets.mjs create --from-proposal --point`。命令建子票并写 `点头：拆票`。
- gate 问答：`gate.mjs answer --repo-dir <客户仓>`；需要提交并推送票分支，照控制台 Agent 现在的做法。
- 驳回：你确认后写 `驳回：补缺口 <理由>` 或 `驳回：拆票 <理由>`；提案仍由 Agent 写，bot 不手写提案。
- 写回前重读父工单最新关口；最新不是你要写的那个 `提案：`，就停下问运营者。
- 写 `点头：补缺口` 前必须说清锁单规则：写完就锁单，要改先写 `改口：重传`。
- 同一个待办重复叫醒时，先读现有评论；已有 `点头：` 或 `驳回：` 就不再写。
- CLI 失败时贴完整错误和退出码；不猜，不重复试同一条失败命令。

### 驳回重跑

- 调度器在 `已提交` 看到 `驳回：补缺口` 时重跑补缺口 Agent；在 `排队中`、有 spec、没有子票时看到 `驳回：拆票` 时重跑拆票 Agent。
- `提案：` 和 `改口：` 仍是等待信号，不触发重跑。
- 两个 Agent 的 brief 都要带最新一条 `驳回：` 评论。补缺口 Agent 的说明补一节「驳回」；拆票 Agent 的说明已有「按理由重拆」，只差 brief 把理由递进去。
- 新 Agent 读已有地图、决定票、提案和回传件；`apply-map` 按标签和父工单链接找已有地图，按编号配对决定票，缺什么补什么，不建第二套。
- 新 Agent 更新父工单上的新 `提案：` 评论和地图内容，不重写父工单正文。
- 重跑失败按现有作业退避；新 `提案：` 出来后停止重跑。
- `驳回：` 的写的人从 Agent 改成 bot，代运营者落笔；工单模型的表同步改。

### 模型、权限和兜底

- bot 跑工厂 CLI 前加载 `~/.afkfactory/env` 的 `GITHUB_TOKEN`，不打印内容。
- bot 用与本机工厂 Agent 相同的模型路线；模拟时确认没有 403、额度够。
- bot 继承 Claude Code 的 Bash、Write、Edit，SOUL 是行为约束，不是权限层。SOUL 明确禁止改代码、合并、部署；bot 自己的 MCP 里不需要的移除。模拟验证不越界。
- 控制台继续保留。通知里除了 bot chat，也保留控制台命令作兜底。
- bot 叫不醒、写回失败、模型不可用时，工厂仍按 GitHub 状态走；运营者能回到控制台。

### 文档和决定

- 新决定写：bot 是消息传递，不是执行者；人工点可以在手机 bot chat 里做；调度器叫醒 bot；GitHub 评论仍是正式记录；bot 代运营者写 `驳回：`，提案仍由 Agent 写；不设改 spec 的口，三个人工点不变。
- spec 正文在模拟通过后贴进 I-0239，中台作为单一记录。
- 推翻 D-0347（手机只接提醒）和 D-0350（决定在 Mac Orca 做）。
- 改 D-0341 和 D-0186：运营者在 bot chat 里答，bot 写回。
- D-0338、D-0340、D-0391 不变。
- 更新工厂流程、通知、工单模型、词表、控制台作业说明、两份计划（迭代计划和第五次演练计划）。
- 改 `docs/adr/决策记录.md`：新决定、被取代状态和正文一起改；`scripts/check-decisions.py` 通过。
- I-0239 留作设计票，补一条「方案已定」评论；实现票由 to-tickets 拆。
- I-0228 的分工改成：工作台 bot 对运营者、执行者跑链、记录员独立记。前置加一条：确认调度器跑新代码、notifier 配置和 SOUL 已部署；重启由运营者做，不让 implement-spec 的 agent 动调度器。
- 中台先改，`dt sync` 到 GitHub；不直接改 GitHub。
- 文档、决定和票的修改放在模拟通过之后；模拟前只改实现分支和 SOUL。

### 模拟和演练

- 模拟用 scratch 仓和假父工单，不碰 demo、生产、中台。环境用假回传件（`inbox/<id>/meta.json` 和 `.scratch/<需求名>/`）、预置假 spec、测试调度器和假 ignite；不跑真实 to-spec、Sandcastle、部署，不碰主 launchd 调度器。
- 模拟用临时 `NOTIFIER_HOME` 和测试 `config.json`；主 config 的 `orca_bot` 先保持关闭，模拟通过、第五次演练前再开。
- 假 spec 的标题或正文带需求名，调度器才找得到。
- 先测四个能力：launchd 环境叫醒、bot 用 token 跑 CLI 写评论、手机收到消息、模型额度。
- 再测：单任务从提案到点头写回；重复叫醒不重复写；两个父工单并发不混；Orca 重启后从 GitHub 恢复；bot 离线时微信或邮件兜底。
- 模拟记录放 `.inbox/plans/`，运营者确认后决定是否进入文档修改和第五次演练。
- 第五次演练里，bot 故障时回控制台并记录；演练继续，不因载体停下。

## Testing Decisions

- 好测试只测外部行为，不测私有函数。用现有 seam，不新开 seam。
- 第一个 seam 是 notifier 通道。用假的 `orca` 执行器，断言命令、参数、bot 名、chat、subject 和 body；覆盖未启用、缺 bot 名、命令失败、无密钥、重试和兜底。先例是 notifier 现有测试。
- 第二个 seam 是调度器路由。直接测 `routeParent`：`已提交` + `驳回：补缺口` 要重跑补缺口；`排队中` + spec + 无子票 + `驳回：拆票` 要重跑拆票；`提案：` 和 `改口：` 仍停。先例是调度器现有路由测试。
- 第三个 seam 是作业 brief。用假 runner 捕获 brief，断言最新一条 `驳回：` 评论在里面；断言重跑用的工具白名单没变。先例是调度作业现有测试。
- 端到端模拟不是单元测试，按上面「模拟和演练」跑，记录证据。
- SOUL 不做单元测试，由运营者审查，模拟覆盖行为。
- 重点验收：不确认不写；别的 agent 的消息不算确认；锁单提醒出现；CLI 错误原样报出；重复叫醒不重复写；两个父工单不混；bot 掉线有兜底。

## Out of Scope

- 改 spec 的口，和第四个人工点。
- 让 bot 当执行者：不跑补缺口分析，不跑 to-tickets，不改代码。
- 改补缺口和拆票 Agent 的判断、关口格式和三个人工点。
- 新看板、网页聊天、客户侧对话。
- Orca 定时自动化巡检。
- 多运营者、云端、远程服务器。
- 生产环境和已交付客户。
- 去掉控制台。控制台保留作兜底。

## Further Notes

- 上一个 Agent 提的 `orca_bot` 通道是起点；这份 spec 把它收窄成消息传递，不让 bot 当执行者。
- 现在代码和文档对 `驳回：` 的处理不一致：文档说 Agent 重列或重拆，调度器实际会停。这份 spec 把两边改成一致。
- `驳回：` 的写的人要从 Agent 改成 bot；工单模型的表要同步。
- 12 条讨论结论已经收进 Implementation Decisions：追问、消息范围、补地图、chat 分法、唤醒兜底、掉线、锁单提醒、驳回、模拟标准、演练分工、文档决定、票和 GitHub。
- 还没验证的能力：launchd 叫醒、bot 的 CLI 权限、手机推送、模型额度、按标题找 chat。模拟第一步测这些；不过，后面的先不做。
- 模拟通过前，不改中台决定、不写 GitHub 评论、不动 I-0239/I-0228 的正文。模拟通过后按 Implementation Decisions 的「文档和决定」一次改完，再 `dt sync`。
- 这份 spec 是工厂自己的功能，不进客户仓；tracker 用中台，GitHub 只读镜像。
