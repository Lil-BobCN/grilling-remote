# 任务管理：本地 Markdown

本工作区的任务和澄清记录都存成 Markdown 文件，放在 `.scratch/`。不用 GitHub，不用 git。

客户侧产物是给运营者审阅的澄清材料，不是最终规格。后面的事运营者自己处理。

## 约定

- 一个需求一个目录：`.scratch/<需求名>/`。需求名用英文短词或拼音。
- 小需求的澄清记录：`.scratch/<需求名>/需求草稿.md`。开头写 `Status: 进行中`，问完改成 `Status: 已问完`
- 走 `wayfinder` 的问答记录：`.scratch/<需求名>/问答记录.md`，开头一节 `## 客户原话` 照抄客户第一次说明需求的话并带日期，之后按轮分节，题号和问题树一致。小需求不建这份，问答在 `需求草稿.md` 第 2 段
- 验收场景：`.scratch/<需求名>/验收场景.md`，每条一句话，开头写“客户确认：日期”
- 走 `wayfinder` 的子票：一张票一个文件，`.scratch/<需求名>/issues/NN-<任务名>.md`，从 `01` 编号，不合并成一个文件。每个需求目录各自从 `01` 编号
- 领取状态写在文件开头的 `Status:` 行：`claimed`（已领取）或 `resolved`（已完成）。没有这一行就是没人领
- 讨论记录追加在文件末尾的 `## 评论` 下

## 当技能说“发布到任务系统”

在 `.scratch/<需求名>/` 下新建文件。目录不存在就建。

## 当技能说“读取相关任务”

读对应路径的文件。客户通常会直接给路径或编号。

## Wayfinder 用法

地图是一个文件，每张子票是一个文件。

对客户怎么说、什么时候让他新开对话，见 `AGENTS.md`。这里只写文件怎么建、怎么选、怎么改。

### 建图与拆票

终点定完、验收场景确认后，在同一次对话里建图和拆票。

1. 建目录：`.scratch/<需求名>/` 和 `.scratch/<需求名>/issues/`。
2. 写 `map.md`，六段照下面的骨架。Destination 写终点那一句；Notes 记客户说的约束；接下来先空着；Decisions so far 先空着；Not yet specified 放还问不清的；Out of scope 放客户明确不做的。
3. 拆票：一个决定或一件可演示的事一个文件，文件名 `NN-<简短任务名>.md`，从 `01` 编号。一张票一次对话能定完；定不完就再拆一张，把后半张写进「接下来」。不要按代码层、页面、接口拆。
4. 写票头：`Type:` 写 `grilling`、`prototype`、`research`、`task` 之一；有先后写 `Blocked by:`；没人领不写 `Status:`。
5. 排顺序：把开放票按客户定的顺序写进「接下来」，一行一张。被挡的写「（等 NN 做完）」。
6. 给继续行：按「选票」规则选出下一张，把第一张和「继续：<需求名> <编号> <票名>」给客户。
7. 开工：客户发来继续行，先把票头 `Status:` 改成 `claimed`，再做。

地图骨架：

```markdown
# <需求名> 地图

## Destination

<终点一句话>

## Notes

- <客户说的约束>

## 接下来

- 01 <票名> —— <这次怎么做>

## Decisions so far

## Not yet specified

## Out of scope

```

- **地图**：`.scratch/<需求名>/map.md`，含六段：Destination、Notes、接下来、Decisions so far、Not yet specified、Out of scope。
- **接下来**：按客户定的顺序列开放票，一行一张。每行写编号、票名、这次怎么做。被挡住的，行末写“（等 03 做完）”。做完的票，写结论时把这一行删掉。
- **子票**：`.scratch/<需求名>/issues/NN-<任务名>.md`，从 `01` 编号，骨架见下。
- **类型**：票头 `Type:` 行写 `research`、`prototype`、`grilling`、`task` 之一。这里没有标签，类型只读这一行。
- **阻塞**：票头写 `Blocked by: 01, 02`。列出的票都 `resolved` 后，这张票才算解除阻塞。没有阻塞就不写这一行。
- **选票**：客户第一句带「继续：」且需求名和编号对得上某张票，就做那张。客户没点名，读地图「接下来」，取第一行没被挡、没人领的。按行序，不按编号。有 `Status: claimed` 的票，说明上次停在半路，先接着做它。点名票和另一张 `claimed` 的票同时存在，先说清地图状态，再按 `AGENTS.md` 的「继续」一节跟客户确认。
- **顺序**：拆完票，客户定完先做哪张，顺序写进「接下来」的行序，之后不再改。客户中途想换，按 `AGENTS.md` 的跳步规则处理。
- **领取**：开工前先把 `Status:` 改成 `claimed` 并保存。
- **完成**：在 `## 结论` 下写一句能独立读懂的话，再加一行“产出文件：相对路径”，没有就写“无”。产出文件算写它的这张票，内容属于后面某张票也列在这里。`Status:` 改成 `resolved`，把票头的 `Blocked by:` 行删掉，并把「接下来」里其他票行末等这张票的「（等 NN 做完）」删掉，再把标题和一句结论补进 `map.md` 的 Decisions so far。后面某张票用到前面写的文件，在它的结论里写“沿用第 N 张的 <路径>”。
- **改前面定过的结论**：怎么跟客户说，见 `AGENTS.md` 的「改前面定过的结论」。文件这样改：回那张票改 `## 结论`，在 `## 评论` 记客户原话和「第 N 次对话改」；旧产出文件第一行标「已被第 N 张取代」；地图 `Decisions so far` 那一行换成新结论，末尾标「按第 N 张改」。

四个词对四类票。每张票开头，对客户说一句，用这四个词之一：

| 对客户说的词 | `Type:` | 怎么做 | 产出放哪 |
| --- | --- | --- | --- |
| 聊 | `grilling` | 用 `grill-with-docs` 一轮问一件，带推荐答案，客户自己答 | 结论写票里；问答进 `问答记录.md` 和 `问题树.md` |
| 看个样子 | `prototype` | 用 `prototype` 做一个单文件 HTML，客户双击就能开 | `.scratch/<需求名>/prototypes/` |
| 我去查 | `research` | 用 `research` 查一手来源，每条结论带出处 | `.scratch/<需求名>/research/<name>.md` |
| 动手做 | `task` | 照票里 `## Question` 列的步骤带客户做，做到哪、拿到什么事实都记下来 | 按票里写的产出，放 `.scratch/<需求名>/` 内 |

### 单票怎么做

开工前核对三件事：票在、没被挡、没 `resolved`。客户第一句带「继续：」且需求名和编号都对得上，就直接做那张；没有就按「选票」规则选。核对不过，按 `AGENTS.md` 的跳步规则处理。核对过了，把票头 `Status:` 改成 `claimed`。

客户没听懂或答不上来，怎么说话见 `AGENTS.md` 的「说话」和「客户没听懂或答不上来」。这里只记文件操作：

- 客户答不了、要问别人：把题写成一段可以直接转发的话，写明问题、背景、选项和推荐。在本票 `## 评论` 记“等第三人：<问题>，问 <谁>”，票保持 `claimed`，答案带回来再写结论。
- 技术题：按 `AGENTS.md` 的「技术题」一节，记进 `pending.md`，等运营者确认。

票文件的骨架：

```markdown
# 03 我在哪改价格和库存

Type: prototype
Status: claimed
Blocked by: 02

## Question

老板在手机上改价格和库存，改完顾客那边马上能看到。要定的是后台首页长什么样、改一个价格点几下。

## 评论

客户原话：「我早上忙，最好扫一眼就知道哪个卖完了，点两下就改完。」

## 结论

（做完才写）

产出文件：prototypes/03-后台首页.html
```

没人领时不写 `Status:` 行。没有阻塞时不写 `Blocked by:` 行。票完成时把 `Blocked by:` 行删掉。

地图的「接下来」样子：

```markdown
## 接下来

- 03 我在哪改价格和库存 —— 看个样子，我做个原型给你看
- 04 取货了怎么通知顾客 —— 我去查，查完告诉你（等 03 做完）
```

GitHub 里的 issue、label、assignee、close、comment 这些词，在本工作区都按上面这套文件操作理解。

## 全部做完后的清雾

「接下来」为空、票都 `resolved`、客户还没上传时，先清雾，再走「收尾与回传」。

1. 读 `map.md` 的 `## Not yet specified`。为空就进「收尾与回传」。
2. 不为空，对客户说一句「都做完了，我再检查一遍还有没有没问清的事」，然后一条一条主动过。
3. 每条问客户，按三种去向处理：
   - **还要做**：新建 `issues/NN-<短名>.md`，编号接着现有的往下排，写 `Type:`，加进「接下来」。清雾暂停，按 `AGENTS.md` 的「一次对话一张票」继续；新票做完后再清一次。
   - **不做了**：从 `Not yet specified` 删掉，写进 `Out of scope`，附客户原话。
   - **暂时定不了**：移到 `.scratch/<需求名>/未定事项.md`，写明卡在哪、谁来回话，从 `Not yet specified` 删掉。
4. 清完再走「收尾与回传」。

`Not yet specified` 只放还能问清的雾。客户暂时定不了的，不放这里。

## 收尾与回传

全部做完、叫客户上传之前，按这张表核一遍。核不过先补；要客户拿主意的，一次问一句。核不过不要叫客户上传。

| 项 | 走地图（`wayfinder`） | 小需求 |
| --- | --- | --- |
| 票都做完 | `issues/` 下每张票都是 `Status: resolved`。有 `claimed`，说明上次做到一半，先做完那张 | 不看票 |
| 没有剩事 | `map.md` 的“接下来”为空；“Not yet specified”为空。每项要么已建票做完，要么客户同意移到“Out of scope”，要么移进 `未定事项.md` | `需求草稿.md` 第 4 段只剩技术题，技术题已记进 `pending.md` |
| 未定事项 | `未定事项.md` 存在就逐条写了卡在哪；没有就写“无” | 不看 |
| 验收场景 | `验收场景.md` 存在、非空，开头有“客户确认：日期”。没有就按 Decisions so far 起草三到六条，客户改完、点头后再写 | 同左，按“已经定下的”起草 |
| 客户原话 | `问答记录.md` 开头有 `## 客户原话`，照抄客户第一次说明需求的话 | `需求草稿.md` 第 1 段第一条是客户原话，照抄 |
| 不做清单 | `map.md` 的“Out of scope”已写。没有就写“无” | `需求草稿.md` 第 5 段已写。没有就写“无” |
| 复核 | 不需要 | `需求草稿.md` 末尾有“复核：”一行 |

七项都过，才说上传那一段。“接下来”和“Not yet specified”为空，指标题下没有条目，不写“（空）”。

## 回传件结构

客户压缩整个工作区上传。服务器只读 `.scratch/`，其余原样存档。

一个需求一个目录：`.scratch/<需求名>/`。父工单的五段这样读：

| 父工单段 | 从哪读 |
| --- | --- |
| 客户原话 | 走地图：`问答记录.md` 开头的 `## 客户原话`；小需求：`需求草稿.md` 第 1 段第一条 |
| 客户确认的结论 | 走地图：`map.md` 的 `## Decisions so far`，取冒号后面那句，链接不抄；小需求：`需求草稿.md` 第 3 段“已经定下的” |
| 验收条件 | `验收场景.md` 的条目，一条抄一条 |
| 不做清单 | 走地图：`map.md` 的 `## Out of scope`；小需求：`需求草稿.md` 第 5 段。没有写“无” |
| 需求全文 | 整个 `.scratch/<需求名>/`，原样拷进客户仓 `docs/requirements/<需求名>/` |

另有一份 `未定事项.md`，不进父工单五段。客户暂时定不了的雾都记在这里，写清卡在哪、谁来回话；没有就写“无”。

不写 `meta.json`，不问客户简称。简称和邮箱由上传页账号带出。
